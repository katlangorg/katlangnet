# Frozen Model-C design laws

**Decision date: 2026-10-02. Design settled; production implementation pending.** These laws supersede the earlier candidate qualifications. They do not claim that current `lean/KatLang.lean` or the C# evaluator implements Model C. The existing ten IDs are retained; NEED-FWD is the short statement of NEED-08, not an eleventh independent mechanism.

**Current status:** the paragraph above is the dated design-freeze introduction, kept verbatim. Lean and C# now implement these laws (production closeout, V3 verified); see § Production implementation map and § Result boundary.

## NEED-01 — Supply computations in the caller environment

After selecting one callable identity, form an ordered supply in the caller's captured lexical environment. Each non-spread written argument supplies one demand cell, irrespective of the eventual scalar, sequence, list or empty value. Distinct written computations create distinct cells. An existing parameter supplied as an ordinary argument transports its existing cell, including every available channel; it does not read VALUE first. Already computed components use ready cells. Allocation and transport execute no supplied computation and introduce no invocation.

## NEED-02 — One immutable completed VALUE outcome

The first VALUE demand starts the supplied computation once. Store its completed counted semantic value, with the established value boundary, or its ordinary runtime failure and original provenance. Later VALUE demands observe that outcome without re-execution, redraw, repeat effect or restart. A computation terminating by cancellation stores a sticky cancellation outcome. Static diagnostics are outside the heap. A reached resource limit terminates the run; it is never a recoverable argument value or a clause mismatch. Stored terminal completion cannot restart work. A separately available CALLABLE identity is not derived from a successful VALUE outcome.

## NEED-03 — Executed demands determine effects

Only executed supply opening, inspecting patterns and semantic consumers demand computations. Effects, random draws, suspensions and failures follow their first-demand order. Supply positions do not prescribe effect order. Plain unused bindings execute nothing. Operators, output rows, collection construction and other consumers keep their established internal order and strictness. String interpolation (STR-02) is such a consumer: it demands each hole's VALUE left to right, exactly once per evaluation of the string, and the first failing hole stops every later one. Failure stops subsequent work on that path. No evaluation may speculate on an undemanded computation.

## NEED-04 — Ordered pattern inspection and shared clause supply

After cardinality validation, traverse patterns left to right, recursively in written order. A non-repeated plain binder retains its complete cell. Literals demand their position. A structural pattern demands the whole ordinary eager value, checks kind/shape, and inspects ready components; matching does not create lazy collection elements.

Every occurrence of a repeated name is an inspecting pattern, including its first occurrence. Demand each contribution when that occurrence is visited. At each later occurrence, compare against the accumulated compatible binding immediately, before visiting later patterns. Compare semantic VALUE and value cardinality first, then compatible available callable identities. A VALUE failure wins over identity comparison. Value inequality is ordinary binding `BadArity` (public `ArityMismatch`); incompatible available callable identities are `TypeMismatch`. In a family these incompatibilities are non-match instead. Choose one richest compatible **complete** contribution; never splice a value from one contribution with another's callable. Among equally rich contributions keep the first visited in written traversal order: its complete value — on the Decimal128 tier its exact representation (quantum, zero sign, NaN sign) included — is the binding's (Q-28, N-F, 2026-10-07; exactly C# `BindNeedPatterns` and Lean `bindNeedName`, which keeps the earlier contribution unless a later one is strictly richer). VALUE equality is `==` (`Decimal128.Equals`). Permuting all contributions of one repeated name preserves satisfiability. On success it preserves the bound VALUE up to `==`, callable identity and channel availability; among equally rich compatible contributions, the first in written traversal order supplies the retained representation. Failure reporting follows ordinary binding order (NEED-04, PAT-10, Q-27): when different incompatibilities coexist, permutation may change the error category, blamed contribution, payload, message or span, although every permutation still fails. Sharing one cell twice causes one execution; independent equal spellings do not share.

Collector positions establish exact slice boundaries without reading slice elements. The same traversal rule applies to their fixed prefix/suffix and nested patterns. Each clause attempt uses the same supply cells. Non-match may try the next clause and retains previous outcomes; a runtime failure during required inspection aborts dispatch and is never non-match. A successful branch retains both channels of its bound cells.

> Owner follow-up (2026-10-07): repeated-name compatibility is symmetric; failure reporting is ordered. With `A = 1.0`, `B = 1.00`, `P(x,x,x) = x`, `P(A,B,2)` reports `TypeMismatch`, while `P(A,2,B)` reports `ArityMismatch`. Both are unsatisfiable. This resolves the independent review's earlier blocker by narrowing its over-strong error-category claim; NEED-04 and PAT-10 evaluation order are unchanged. See the Constitution's owner follow-up and `NumericDisplayIndependentReviewTests.MixedThreeContributionConflicts_ReportTheFirstExecutedContract`.

## NEED-05 — Whole-source validation, then runtime demand phases

Apply the existing whole-source validation boundaries: parse, resolve written names, validate signatures/patterns, and validate forwarding contracts before executing validated code. Existing deferred source regions are validated at their established materialization boundary. Argument laziness excuses none of those checks on available written definitions, including an uncalled invalid forwarding definition. Formula lifting still follows the immediate consumer's existing role and zero-supply acceptance law; closed heads gain no new bindings.

**Q-15:** a resolved callable reference whose implicit lift a closed head cannot supply remains its ordinary zero-supply VALUE demand. Reject that demand when it executes, using the callable's established runtime rejection. Do not add a static blocked-lift diagnostic for Math, another value consumer, a selector branch, an alias or a forwarding route. Static roles decide elaboration, not a proof of eventual execution. Actual consumers validate the values they demand. Directly undeclared closed-list names and invalid structural forwarding remain static errors.

Runtime order is: **resolve one callable identity → form supply/open spreads → validate supplied cardinality → inspect patterns/dispatch → execute body consumers**. A callee-resolution failure precedes opening. A required spread failure precedes cardinality rejection and later supply slots. Wrong cardinality rejects before any non-spread VALUE demand, for every callee category. A family of that cardinality with no matching clause reports `NoMatchingBranch`; wrong cardinality reports `ArityMismatch`. Source families still require consistent branch-head arity: mixed heads remain the existing static `BranchArityMismatch`. Arity payloads name the selected signature's actual supplied-slot requirement, not flattened captures; preserve current builtin acceptance facts.

## NEED-06 — CALLABLE projection and fresh invocation

CALLABLE projection obtains the supplied expression's resolved algorithm identity and captured owner without evaluating VALUE. Preserve current identity distinctions, aliases and availability; no algorithm identity is invented for a scalar, capture or selected/computed value. Actual invocation through that channel is fresh and takes an ordinary supply and normal invocation charges. Callbacks and loop steps request this channel; native value slots, operators and selected results request VALUE. If both occur, effects follow their executed order. A VALUE failure does not erase independent identity; neither channel bypasses terminal run state. Preserve each consumer's existing rejection when callable identity is absent; this round does not decide Q-06's diagnostic policy or introduce a new value-to-thunk fallback.

> META-S3-1 replacement wording (2026-10-19; the approved META-S3-R2 text, now reachable from source through `R.Algorithm`, § Callable projection below). CALLABLE projection reads a supplied computation's resolved identity and captured owner without demanding THAT computation's VALUE. Identity-only projection evaluates nothing. A RUNTIME projection — a reference's `.Algorithm` link and navigation through a parameter whose cell is a runtime projection — may demand OTHER cells' VALUE on its callee route, through their ordinary single flights, never the projected cell's own VALUE. No identity is invented for a scalar, capture, list, selection or computed value; a reference exposes its callee only through `.Algorithm`. Actual invocation is fresh, with an ordinary supply and normal charges. Callbacks and loop steps request CALLABLE; native value slots, operators and selected results request VALUE. Effects follow the executed order. A VALUE failure does not erase independent identity; neither channel bypasses run terminality. ABSENCE of callable identity is a SUCCESSFUL projection outcome ("no identity"), never an error; a projection whose computation fails has FAILED: its error, whatever its kind (`NotAnAlgorithm` and `IllegalInEval` included), keeps its kind, span and context everywhere it is observed, and no consumer converts it into "no identity", a clause non-match, a value-receiver route, a fallback or another error. The absence reports (`param(x)`, `dot result`, an invoking slot's role, `captured callee`) are produced only from a "no identity" outcome. (C#: the CALLABLE flight's completion marks a runtime failure, `EvalError.IsProjectionFailure`, read by the absence classifiers; Lean: the typed parameter projection `projectParameterWith`, L2.)

Diagnostic provenance (C# only, META-DIAG-2): a fresh refusal of required META or CALLABLE capability at a supplied slot uses that call's written argument occurrence when known; forwarding does not make it the original argument's occurrence. A VALUE or runtime projection failure originating inside the transported computation keeps its own provenance. Unknown occurrences retain the existing cell-span / attach-if-missing fallback. See `evaluator-and-hosting.md` § Blame for an output-less written argument; Lean errors carry no source locations.

## NEED-07 — Lazy supply, eager collection VALUE

Explicit `E*` opens one supply level. An arbitrary E must be evaluated during supply formation to discover its ordinary value and items; those items become ready cells. An existing collector already represents an exact, known-cardinality slice: opening it transfers its element-cell addresses directly, without VALUE materialization. Slice transfer opens no element value.

A POSTFIX SELECTION forms its selector supply by the same law (variadic postfix selection, October 2026; `sequences-lists-and-calls.md` § Variadic postfix selection): after the receiver's one VALUE demand, every explicit spread selector runs during formation and contributes its items (a collector slice transfers its cells unforced), while each ordinary selector stays a suspended computation demanded left to right only when the selection reaches it. So formation precedes selection: `[10, 20][99, (1 / 0)*]` is `DivisionByZero` (the spread ran before `99` was validated), while `[10, 20][99, 1 / 0]` is `BadIndex` (`1 / 0` is never demanded).

A collector's ordinary VALUE demand materializes **all** its cells left to right into one exact eager list, preserving nested and empty values as elements. Empty slices yield `[]`. `.count`, `.first`, `.sum`, selection and normal collection consumers receive that complete ordinary value. No shape-only count, lazy list node or lazy element rule exists. A collector passed without opening is one collection-valued computation; demanded capture/list reconstruction uses the established eager value boundaries.

## NEED-08 / NEED-FWD — Forwarding transfers supplies

**Forwarding transfers demandable supplies; it does not force them. Pattern matching or supply formation may demand values before forwarding, but the forwarding edge itself performs no VALUE demand.**

FWD-02 keeps its existing selection by binding name and compatible pattern/structure, Q-04 ownership and source-kind laws. Transfer complete cells and their available VALUE/CALLABLE channels, or exact collector slices, preserving identity, provenance, memoized outcome and caller ownership. A collecting source opened for a collecting destination transfers its slice; a fixed source stays one item. Where the current contract permits a collecting source for a fixed destination, pass its collector cell as **one** collection-valued computation, not as expanded slots. Incompatible structure is still refused statically. A structural reconstruction is itself demandable; its evaluation, if required, uses ordinary eager construction. Alias indirection introduces neither force nor a wrapper memo domain. Unnameable families remain callable and aliasable with call-by-need, but have neither a by-name forwarding contract nor a formula-lifting signature. Explicit `F(x)` transports x's cell; that does not equate every static/property aspect of explicit calls with bare forwarding.

## NEED-09 — Single flight, cycles, cancellation and resources

A cell is suspended, evaluating or completed. Publish its transition and one shared completion atomically before user computation starts. Unrelated overlapping demands join that completion; at most one evaluation can be active. Serial evaluation is sufficient; speculative parallelism is forbidden. Detect a dependency cycle before awaiting the edge that closes it, including indirect/async cycles and a cycle across independently started overlapping chains. The result is the ordinary evaluation error **`DemandCycle`** (planned Lean `EvalError.demandCycle`, C# `EvalError.DemandCycle`, public `KatLangErrorCode.DemandCycle`), memoized through the failed dependency chain. Blame the cyclic cell's original supplied-expression span, with a written demand/call context; expose no heap/Force frame. If no source provenance exists, the span is absent. Fresh recursive calls/cells remain ordinary recursion governed by normal limits.

Cancellation belongs to the original run. Cancellation during evaluation completes that cell as cancelled and never restarts it; overlap joins the same completion. A pre-cancelled run executes no argument effect. Cancellation after value completion does not rewrite that stored value, but run-level cancellation observation still rejects subsequent language work. A waiter does not acquire a separate restart or replacement cancellation policy. Reached cancellation/resource terminality is checked before further semantic work, including memo observation, without making a completed failure a branch non-match.

Cell allocation, cell/slice transport, in-flight joining, memo hits and pure callable-identity projection have **zero additional semantic step or invocation-depth charge**. Existing expression-read, resolution, consumer and materialization charges still apply when their established operations execute. First force charges the original expression's actual executed work exactly once, under the existing budget policy; each actual wrapper/target/callback invocation still incurs its normal charge/depth. A cell's implementation frame is not a language invocation. Supply opening retains its existing evaluation/materialization cost. Charge the run's existing monotone budget; optimization cannot spend on undemanded computations, reset a budget, or turn a reached limit into another success. Address transport must share/normalize iteratively, not build recursive thunk chains. Bookkeeping allocation is implementation cost, not a new language step.

> META-S3-1 amendment (2026-10-19; one protocol for both channels, the approved META-S3-R2 text). A cell's VALUE and a cell's RUNTIME CALLABLE projection are each a computation with the same protocol: suspended, active or completed; the transition to active and one shared completion are published atomically before the computation starts; an observer from another flow records its wait-for edge and then joins that completion; at most one computation per cell and channel is ever active, and its outcome is every observer's outcome. The two channels are nodes of the run's ONE wait-for graph (VALUE→VALUE, VALUE→CALLABLE, CALLABLE→VALUE, CALLABLE→CALLABLE). Re-entering a computation that is active in the current logical flow, through either channel, is `DemandCycle` FOR THE RE-ENTERING OBSERVATION ONLY: it is not published at the re-entered computation, which continues; the completed computation's outcome — success, ordinary failure, or a `DemandCycle` it received and returned — is sticky. A resource limit reached by the computation completes it terminally and is retained by the run. Cancellation and host exceptions complete it exceptionally: stored and shared by in-flight observers, never published as a callable outcome and never restarted. At every observation entry, cancellation and terminality are checked before memo access. A projection never runs user code under a cell lock. Identity-only projections (which evaluate nothing and cannot be re-entered) are pure and keep their first published outcome. The asynchronous engine obtains every identity through the one synchronous resolver run as a non-initiating observation (§ Production implementation map), replaying every awaited outcome, published or not, at the demand point that reads it.

## NEED-10 — Retained ownership and separate property cache

A cell retains the caller's resolved lexical bindings, owning activation, run context, hosts, random stream and cancellation token for as long as the cell is reachable. Delayed evaluation does not re-resolve names in a receiver's later stack. Ownership, accessibility and open-provider identity remain unchanged. Cell memoization and the established per-run resolved property-binding cache are distinct. A demanded bare property uses that cache; a demanded explicit `Z()` remains a fresh call, once inside its supplied cell. Two independent supplied `Z()` computations remain independent. An unused property expression performs no access. Sticky cell failure does not make property failures globally cached. No new returned-algorithm Result or cross-run cell API is introduced.

> S1 amendment (2026-10-17, § Call references below): the one new Result kind, the CALL REFERENCE a `meta` parameter binds, is not a returned algorithm — it holds an invocation plan, has no CALLABLE identity and is executed only by `R.Invoke()` — and it is RUN-SCOPED: no API carries it, or the cells it retains, into or out of a run. The sentence above therefore still holds for algorithms and cells.

> CACHE-PUB-1 amendment (owner decision 2026-10-22; `evaluator-and-hosting.md` § Zero-argument property cache): the property cache stays a SEPARATE domain from cell memoization, but a demanded explicit `Z()` — still a fresh call, once inside its supplied cell — is a qualifying zero-supply invocation of `Z`'s binding: when `Z`'s entry is empty and it owns publication, its success establishes the entry a later bare `Z` reuses (the property cache's publication law, never the cell's memo). An invocation through a CALLABLE projection (a parameter's cell, a captured callee cell) names the binding of the cell's written source in its own caller context. Two independent supplied `Z()` computations remain independent executions; an undemanded one performs nothing; a completed cell is never re-executed, so it never publishes twice. No cell is completed, demanded or projected to find the binding.

> META-S3-1 amendment (2026-10-19, § Callable projection below): `R.Algorithm` adds NO Result kind. It is a CALLABLE CHANNEL of a written expression — the captured callee cell, reached through a supplied `.Algorithm` link or a callee position — and, read bare, that callee's ordinary VALUE. Nothing that carries a VALUE carries callable identity: a list, sequence, selection, `if`, call result or property containing or computed from `R.Algorithm` is ordinary data, and the callee cell keeps the captured call's lexical owner, activation and run.


## Result boundary (production clarification, 2026-10-02)

This states NEED-06 ("selected results request VALUE") and NEED-10 ("no new returned-algorithm Result") together; it adds no law. **Algorithm results are calculation values.** A supplied input may expose VALUE and CALLABLE, and binding, transport, forwarding and collector-slice opening preserve both. Result construction — output rows, `if` and clause selection, list and sequence construction, selection, spreading a result, a loop's final state, a property's value, an interpolated string — demands VALUE and produces data. Ready data carries no callable identity, and CALLABLE projection exists only for written references (a name, a transported parameter, an inline block, a structural dot path, an alias), never for a call, selection, collection or capture. So a call result cannot be invoked (`Apply(ReturnF(Inc), 3)` is `NotAnAlgorithm`), a callable read as a result is its zero-supply VALUE demand (`ReturnF(Inc)` is `Inc`'s arity rejection), and an undersupplied call is an arity failure, never a partially applied callable. Bare forwarding (`Wrapper(x) = Target`) invokes `Target` with existing supplies and yields `Target`'s result; it never returns `Target`. A bare nested callable in a closed body is bare forwarding, so a nested algorithm cannot escape its creator either.

S1 clarification (2026-10-17): a call reference (§ Call references) is a calculation value in this sense — results may carry it like any value, it exports no CALLABLE (calling it is `NotAnAlgorithm`), and executing it is the explicit `R.Invoke()`, never projection. What it adds is that a THUNK of one captured invocation can travel inside its run; the run result boundary keeps it from leaving the run.

META-S3-1 clarification (2026-10-19): `R.Algorithm` does not change this boundary. Its CALLABLE exists only where a written expression is projected — a supplied or forwarded `X.Algorithm` (a link), a callback or loop step, or the callee `(R.Algorithm)(x)` — exactly like any written reference; read as a VALUE it is the captured callee's ordinary VALUE (a parameterized callee is its arity rejection), and `[R.Algorithm]`, `if(c, R.Algorithm, 0)` or `Keep(R.Algorithm)` produce data with no identity. `Square(5)(8)` stays unparseable and `Apply(Square(5), 8)` stays `NotAnAlgorithm`.

## Missing callable identity (clarification of NEED-06, Q-06, 2026-10-05; no new NEED law)

NEED-06's frozen text preserved "each consumer's existing rejection when callable identity is absent" and left Q-06's diagnostic policy open. Q-06 decided it (option (a)): when an invoking consumer — a user higher-order parameter, a builtin callback (the `map` transform, the `filter` predicate, the `reduce` reducer), a `while` or `repeat` step, an invoking slot reached through a builtin used as a step — finds no CALLABLE identity, the rejection is `NotAnAlgorithm` for every consumer. It is produced by CALLABLE projection only when an invocation is required (Lean `projectInvokingSlot`, C# `Evaluator.ProjectInvokingSlot`, described by the slot's role), never by demanding VALUE, and an unused invoking slot is never projected. A cell that HAS callable identity keeps its callable's ordinary binder and dispatch verdicts (a zero-parameter callable given an item is `ArityMismatch`). No value-to-thunk fallback is introduced, and the frozen NEED-06 wording above is kept as written. Full statement: `evaluator-and-hosting.md` § The evaluation-error taxonomy.

## Dot expressions in every callable position (clarification of NEED-06, Q-18, 2026-10-05; no new NEED law)

NEED-06 projects a SUPPLIED expression's identity without VALUE; Q-18 decided (C-B3) that a dot expression's CALLEE position reads that same projection, so a dot expression has ONE callable identity wherever a callable is used — supplied argument, forwarded parameter, builtin callback, loop step and callee (C# `Evaluator.ProjectDotPathCallable`, read by supply cells, `ResolveCallee` and the sequence optimizer's recognition; Lean `projectNeedStructuralMember`, read by `projectNeedCallable` and `resolveCalleeAlg`). An argumentless structural path carries its member's own callable, aliases normalized; every other dot expression — a fallback result, an intrinsic `.string`, an argument-bearing edge — is a computed value with no identity, exactly as NEED-06 says of every computed value, so calling it is `NotAnAlgorithm` ("a computed value, not a callable"). Invocation through the projected member is fresh like every NEED-06 invocation: `(Box.V)()` evaluates `V` again and never reads `Box.V`'s property-cache entry (NEED-10's separate cache), while the bare read `Box.V` keeps that entry; since CACHE-PUB-1 (2026-10-22) a `(Box.V)()` that finds the entry empty establishes it, exactly as `Box.V()` does. Full statement: `ownership-and-lookup.md` § Dot-call resolution and missing members. META-S3-1 (2026-10-19): on a structural miss an argumentless edge spelled `Algorithm` is the one dot expression whose identity is a RUNTIME projection (the captured callee of the receiver's reference, CR-14/CR-15): in every algorithm-capable position — supplied, forwarded, callback, loop step and callee — it reads the same callee cell, and member access never navigates through it (`R.Algorithm.n` is the extension call `n(R.Algorithm)`).

## Production implementation map

C# `Evaluation/NeedCell.cs` owns VALUE single flight, sticky completion, cancellation and the active dependency graph. A computation's shared completion (its flight) exists only while the computation is active: the cell publishes the memo or stores the exception and releases the completion in one gate section, so a joined observer awaits its own copy of the task and every later observer reads the memo first (META-LIFE-2, 2026-10-22, for VALUE as for the runtime CALLABLE projection). The graph is ONE wait-for graph for both channels (META-S3-0a, 2026-10-18): its node type `NeedNode` holds the edges, the run's gate, the one reachability test and the one cleanup rule; a cell is its own VALUE node, and a cell whose CALLABLE is a RUNTIME projection (one that may demand VALUE or project other cells) has a second node, its projection node, which carries that projection's flight. Such a projection follows this section's VALUE protocol exactly — one computation outside the cell gate, joiners recording their edge before waiting, re-entry in the same logical flow `DemandCycle` for the re-entering observation only, a sticky outcome (success, absence of identity, ordinary failure, propagated cycle, resource limit retained by the run), stored and shared cancellation or host exception, and terminality checked before the memo at every observation entry. Since META-S3-1 a source program reaches a runtime projection through `R.Algorithm` (§ Callable projection): a supplied `X.Algorithm` LINK cell, and in a run that already has runtime projections a parameter-rooted dot path, get their projection node at construction (`Evaluator.SupplyCell`, `NeedCell`'s written-argument constructor, whose node projects the cell's own suspension); `NeedCell.WithRuntimeProjection` remains the host-built construction point. Every other NEED-06 projection a program performs is identity-only — computed under the cell gate and memoized, with no node, flight or edge — and an ordinary cell carries no CALLABLE-flight state. The graph belongs to the run: the run budget's `NeedDependencyGate` guards every edge between that run's cells, so independent runs never contend. Supported evaluator entry points cannot demand another run's cells, so a parent cell of another run (the current cell inherited by a run that a host operation starts) records no edge and can close no cycle. Internal property-cache keys can retain cells through environments and activations, but include run identity and return only values; internal test adapters must not replay retained evaluation delegates in another run. `Evaluator.Needs.cs` owns supply formation, exact parameter-cell transport, collector materialization, the one inspecting pattern binder, callback Ready adapters and initial loop-state supply. `EvalCtx.NeedEnv` and retained owner activations carry addresses. `Budget.CheckContinuation` observes the run's terminal state without charging.

Asynchronous resolution (META-S3-0b, 2026-10-19; C#-only execution control with no Lean counterpart — the async surface has none — and no language, syntax or observable-outcome change). The async twin obtains every identity (a callee, a dot receiver and its `.string` member re-navigation, a lexical fallback callee, a sequence callback, a loop step) through the ONE synchronous resolver, run by `Evaluator.ResolveAsync` as a NON-INITIATING observation (`NeedCell.ObservationScope`): inside it a VALUE that is not complete and a runtime projection that is not published are never started; each observation answers cancellation and terminality, then the memo or stored exception, then the outcome its resolution RECORDED, and otherwise reports that (cell, channel) pair pending. The adapter then performs exactly that step (`DemandAsync` / `ProjectCallableAsync`) in the current logical flow, records its actual outcome — published or not, a re-entry's flow-local `DemandCycle` included — and reruns the resolver, which reads the recorded outcome at its original demand point, so kind, span, written-slot blame, context, effects and charges are the synchronous resolver's. Every retry follows a step that determined a previously undetermined pair, and the resolver reaches only retry-stable cells, so the resolution ends after at most one step per reachable pair; two fail-loud guards back this (a recorded pair reported pending again; a fresh runtime-projection cell allocated while observing), and an unpublished runtime projection reached synchronously in an async run fails loud. The repeated-name binder awaits both projections directly. Optimizer recognition (`PeekResolve`) and diagnostic enrichment (`NeedCell.PeekCallable`) use the same observation and decline rather than initiate. A run with no runtime projection (every META-free run, and every run that never forms an `.Algorithm` link) runs the resolver directly, allocating nothing. NEED-06 failure provenance: the CALLABLE flight's completion marks an ordinary failure (`EvalError.IsProjectionFailure`, equality-transparent), and the absence classifiers (`IsLiftableError`, `IsAbsentIdentity`) never read a marked failure as "no identity"; identity-only projections are never marked, so static absence is unchanged.

Lean `NeedSuspension`, `NeedState`, `NeedCallableState`, `EvalState.needs`, `supplyNeed`, `demandNeed`, `projectNeedCallable`, `formNeedSupply` and `bindNeedPatterns` model the same operations in the serial authoritative evaluator. `projectNeedCallable` is the total CALLABLE completion shell `NeedProjection.step` (unprojected → projecting → projected; re-entering `projecting` is `demandCycle` and leaves it in place) over `NeedProjection.suspended`, the twin of `NeedDemand.step`; `KatLangArityLaws/NeedControl.lean` § CALLABLE projection control proves its stickiness, re-entry, publication and channel-independence laws and that the `projecting` marker is unobservable for a computation that never touches its own cell's CALLABLE state (`transparent_projection_is_marker_free`), which is why C# identity-only projection needs no marker. Host concurrency and cancellation are C# operational extensions; serial Lean does not claim to model host scheduling. `CoreTests.ModelC` executes the demand laws and heap invariants. The production binder `bindNeedPatterns` / `selectNeedFamilyBranch` is total, so its cardinality, allocation, minimum and plain-binding laws are theorems (`KatLangArityLaws.lean` § Model-C production binder laws, FORMAL-07, e.g. `binder_rejects_unaccepted_supply_before_any_effect`). Since R3 (October 2026) it is the `EvalM` specialization of one generic core (`NeedBinder`, over VALUE, CALLABLE and allocation capabilities), and its demand order is proved too: running the same core in an external boundary trace (`KatLangArityLaws/BinderTrace.lean`) erases exactly to the production run for every channel pair, state and event prefix (`trace_erasure`), and its events follow the syntax-indexed schedule `oneEvents` / `sourcesEvents` — cardinality before inspection, written order, a collector allocated before its pattern, plain non-repeated occurrences silent, an inspecting occurrence's own VALUE first, ready allocations before the nested gate, depth first, nothing after the first failure or non-match (`traced_sources_truncate`) — with the repeated-name order VALUE(current), VALUE(representative), CALLABLE(representative), CALLABLE(current) and its verdict (`repeated_events_are_a_prefix_of_the_canonical_order`, `repeated_name_binding`), and clause-family search and arbitrary-context activation (`KatLangArityLaws/FamilyDispatch.lean`). Two correspondences complete it (`KatLangArityLaws/BinderCorrespondence.lean`): channels whose VALUE demands and CALLABLE projections agree wherever the run invokes them give the identical run (`results_depend_only_on_invoked_cells`), and a head invokes its channels only on cells at inspecting positions — literals, structural patterns, the unpacking receiver, repeated names, aliasing included — or on cells the run allocated (`invoked_cells_are_inspected_or_allocated`), so the channels at a cell bound only by plain, non-repeated names and never reused by an allocation are irrelevant (`plain_cells_are_channel_irrelevant`; the production use assumes supplied addresses below the initial heap size and channels that never shrink the heap; `allocateNeed_fresh_for_valid_supply` proves the local allocation step, while whole-run freshness and the partial channels' heap monotonicity remain unproved, with the latter supported by source inspection); and for every head a clause attempt and the ordinary binding share schedule and final state, differing only where the ordinary binding raises one of four incompatibility errors and the attempt is a non-match (`family_attempt_is_the_ordinary_binding`), while a literal-free head — every ordinary signature — is never a non-match in ordinary mode (`production_signature_binding_is_never_a_non_match`). ## Call references: META capture and `Invoke()` (CallReference S1, 2026-10-17)

S1 makes the M1.5 invocation plan reachable from source. Lean is authoritative (`ParameterKind.metaRef`, `NeedPattern.metaRef`, `NeedCapabilities.reference` = `NeedPlan.reference`, `Result.callRef`, the `Invoke` arms of `evalDotCallCounted`, `exportRunValue`); laws `KatLangArityLaws/CallReference.lean`, guards `CallReferenceGuards.lean`.

* **CR-1 META is a binder capability.** `meta name` (a contextual modifier: `meta` followed on the same line by another pattern item; `F(meta)` and `meta = 3` keep the ordinary name) may modify only a plain, fixed parameter name written ONCE at the top level of an explicitly written ordinary parameter list. Collecting, nested, structural, literal, repeated, inferred and clause-family positions are `InvalidMetaParameter` (parser) / `IllegalInEval` (host-built preflight, Lean `validateAlgorithmTree`). Formula lifting gives a caller an ORDINARY binding that transports its cell into the callee's META slot; a callable alias keeps its target's modes.
* **CR-2 Written-order, inert capture (J8(b)).** After the ordinary cardinality gate, the one R3 binder reaches a META capture in written traversal order (NEED-04 unchanged: an earlier inspecting pattern's failure wins) and reifies the supplied cell: a pure read of its suspension, then ONE fresh Ready adapter cell holding the reference. Nothing executes — no target, no argument VALUE, no supply preparation, no spread, no route resolution — and the original cell is not written. The capturable cells are the WRITTEN INVOCATIONS (META-S3-4, D-2A; C# `IsPlannableCall`, Lean `NeedPlan.callShape?`): a call whose callee is a name, a parameter or an argumentless dot path — every call the parser produces, `(t.Algorithm)(args)` included — and an argument-bearing dot edge `t.N(args)`, an explicitly empty list included. The decision is syntactic, total and evaluation-free; it never asks what the form invokes (§ Generalized capture: its route is decided later). Every other cell — a value, a property read (no implicit provenance), a bare callable, an argumentless dot edge (`Box.G`, `5.Inc`), a computed or host-built callee, an existing reference, a collector — is refused with `NotAnAlgorithm "meta: not a supplied call computation"`; nothing is evaluated to discover a call. A refusal at a binding site names the META parameter being bound (META-DIAG-1, 2026-10-21): the canonical refusal stays the inner error, unchanged in category and description, framed once with `while binding meta parameter 'name'`, and positioned at the argument as written at THAT binding call (META-DIAG-2, 2026-10-22: a forwarded parameter read is its own occurrence — `W(meta s) = while(s)` / `W(Step(0))` points at the `s` in `while(s)`, `F(x) = while(x)` / `F(42)` at the `x` in `while(x)`, never at the argument originally written for the transported cell; an opened spread's item, which has no written slot of its own, and an unknown slot keep the cell's own span, and a locationless module read keeps the attach-if-missing law; C#-only diagnostic metadata, `AnnotateMetaBindingRefusal`'s occurrence) — the declared name, for a user algorithm and a builtin (`while(5)` names `step`) alike, and for a forwarded reference the failing inner binding, never the outer capture. Only that refusal is framed: a direct reification has no binding site and keeps the unframed refusal, and a later route-dependent refusal of a successfully captured invocation (D-1A `invocationRefusal`) names no parameter; cancellation, resource limits and every other error pass unchanged (Lean `NeedPlan.bindingRefusal` through `NeedBinder.captureMeta`; C# `Evaluator.AnnotateMetaBindingRefusal`; pinned by `MetaBindingRefusalDiagnosticTests`). (Until META-S3-4 only a call with a lexical-name or parameter callee was capturable; a dot callee was refused.)
* **CR-3 Identity.** A reference IS its plan: the supplied cell (Lean need address). Any number of plain forwarding hops reach the original cell, so repeated META observations of one cell yield one reference, before or after its VALUE completed (successfully or not), and distinct written calls are distinct references however alike they are spelled — for every invocation form (META-S3-4: `Two(Box.G(1), Box.G(1))` compares two plans; a rebuilt `op.Algorithm(op.Arguments*)` is a NEW plan, distinct from `op`'s, whose supply holds `op`'s ORIGINAL argument cells, CR-11). `==` compares plan identity; there is no ordering. Because a reference is GENERATIVE (each evaluation of a written call cell is a new plan), its identity follows NEED-10's property cache: a bare property `R = Capture(F(1))` read twice is ONE reference (`R == R` is `true`), while the explicit call `R()` evaluates the body again and captures a new cell (`R == R()` is `false`).
* **CR-4 The reference value.** A Ready, opaque, transportable value: properties, parameters, lists, sequences, selection and `if` carry it; it has no CALLABLE identity (`op(3)` is `NotAnAlgorithm`), no members, no number, Boolean or text view, and every inspecting consumer (operators, `if` conditions, numeric aggregates, `.string`) rejects it with its ordinary kind verdict. A META capture of an adapter refuses (no value-to-reference bridge).
* **CR-5 `R.Invoke()`.** On a structural miss an edge spelled `Invoke` is the call-reference intrinsic (J1; DOT-08's template): a declared member `Invoke` still wins, a lexical `Invoke` is never consulted by dot syntax (`5.Invoke()` is `TypeMismatch`; the plain call `Invoke(x)` is unaffected), and the front end never infers `Invoke` as an implicit parameter. The argument list is a route fact checked before the receiver is demanded: bare `R.Invoke` is `IllegalInEval` (never executes), `R.Invoke(8)` is `ArityMismatch(0, 1)` (S1 has no replacement arguments). The receiver is read as `.string` reads it and must be a reference of THIS run. Invocation is `NeedPlan.invoke`: the ordinary call's phases afresh — callee resolved in the CAPTURED caller context (never the invoking site), alias normalization, clause families redispatched, normal charges, frames and cancellation — over the plan's ONE supply, prepared at most once and sticky (spreads run once), binding the SAME memoized argument cells; it never reads or writes the original cell's VALUE and is never a property read.
* **CR-6 Run scope (J4).** A reference never leaves its run: a run result containing one (at any depth), a host-operation argument and text conversion (interpolation) are `TypeMismatch`; a host cannot construct one. C# checks the owning budget and the run's continuation in ONE helper (`Evaluator.CheckCallReferenceOwnership`) before any plan work and again after a successful invocation, so a foreign run's reference is refused, a run that has exited on success, failure or exception cannot execute again, and a cancelled, resource-terminal or required-source-failed run cannot be revived. Serial Lean has one run per state and no cross-run channel. Because only a plan builds a reference and only a run that retains plans (CR-7) allocates one, C# skips the run-result scan in a run that retains none (SEC-01-FU2, an implementation fast path; every retaining run scans, uncharged and cancellable — `evaluator-and-hosting.md` § Call references at the host boundary).
* **CR-7 J7 program gate (C#).** C# retains plans per RUN: the run's structural preflight, which already walks the admitted program graph once before evaluation (root, nested and uncalled bodies, families, opens, parameter patterns, eager modules, host-attached parent scopes), tests every node it visits (`AstStructuralPreflight.MayCaptureCalls`), and plans are retained iff a META capture or binder, a node that may reach a META-declaring builtin (META-S3-3: a name or dot edge spelled `while`/`repeat` — `BuiltinRegistry.MetaBuiltinNames`, read from the registry — or a host-built builtin node of one; every admitted route to such a builtin spells its name or carries its node, and a user declaration of the same name is a conservative false positive), or any DEFERRED MODULE REGION (its modules are unknown), is present; the decision is stored in the run's budget and never changes, and no second traversal is made. A META-free program without deferred regions keeps the ordinary route, including supplied plain-call fusion; a META binder reached in a non-retaining run is an internal failure, never a refusal. Lean is always-on (no gate). Since META-S3-4 a retaining run also plans every supplied ARGUMENT-BEARING DOT EDGE (and every call through an argumentless path), so those cells allocate their plans (a member or extension plan its route object) and lose supplied-call fusion too; the gate itself is unchanged (§ Generalized capture, Performance).

Proof boundary: capture inertia, identity, forwarding, the META arm, conservative extension of META-free binding (`production_meta_free_binding_ignores_reference`) and the run boundary are theorems; that the partial evaluator's `Invoke` arm and drivers call these definitions is source fact with executable guards; `ProductionDiscipline` is proved by `EvaluatorDiscipline.productionDiscipline_holds` (including the S3-4 classifier and projection callbacks); the reachable-state refinement remains open.

## Argument views: `R.Arguments` (CallReference S2, 2026-10-17)

S2 adds the lazy, read-only ARGUMENT VIEW of a call reference. * **CR-8 The view.** On a structural miss an edge spelled `Arguments` is the argument-view intrinsic (`Invoke`'s template: a declared member `Arguments` wins, a lexical `Arguments` is never consulted by dot syntax — `5.Arguments` is `TypeMismatch`, the plain call `Arguments(x)` is unaffected — and the front end never infers `Arguments` as an implicit parameter). The receiver is read as `Invoke` reads it and must be a reference of THIS run (an argument view itself is refused). Obtaining the view is INERT — no target or route resolution, supply preparation, argument VALUE, allocation of cells or cloning — and yields the reference's ONE view: `R.Arguments == R.Arguments` is `true`, `R == R.Arguments` is `false`, a view is never invocable, and it works whether or not the original VALUE completed.
* **CR-9 The view's supply.** Every view operation that reads the SUPPLY reads the plan's ONE sticky supply (`NeedPlan.viewCells`): the recorded preparation, or exactly one formation through the ordinary former in the plan's caller context, shared with the original VALUE and every `Invoke()`, never dispatching the target. Which bundle the supply is depends on the plan's ROUTE (META-S3-4, D-4/D-5: an extension `5.Add(1)` supplies `5, 1`), so reading the supply first establishes the route (§ Generalized capture) — identity resolution only, which through a runtime-projection receiver performs that projection's existing single-flight receiver demand once, with its effects and failures at that point (before `repeat`'s count, RP-1); establishing the route never authorizes executing the captured target, and an intrinsic route has no supply (`NotAnAlgorithm "meta: not a callable invocation"`, D-1A). Preparation demands no ordinary argument VALUE; only an explicit arbitrary spread among the arguments runs during it (once, for every observer), and its failure is sticky.
* **CR-10 Count and selection.** `R.Arguments.count` / `count(R.Arguments)` is the number of EFFECTIVE supplied cells (explicit spreads included; an extension's receiver included, META-S3-4) and demands no cell. Postfix selection over a view keeps ordinary selection order and validation: an empty selection reads nothing (no supply, no route); each selector is demanded and validated (`selectorIndex`: a non-number is `TypeMismatch`, a negative or non-whole number `BadIndex`) BEFORE the supply is read; a valid index then reads the supply (`BadIndex` past its end) and demands ONLY the selected cell, whose VALUE is selected whole (selection is a value boundary; zero-based). Repeated selection reuses the cell's memoized outcome, success or failure. `first`/`last` (and `.first`/`.last`) select the first/last cell, the empty case being the ordinary empty-collection selection failure. Every other collection builtin given a view as its WHOLE collection — `map`, `filter`, `reduce`, `order`, `distinct`, `contains`, `sum`, `atoms`, … — is `TypeMismatch` (`argumentViewUnsupportedMessage`) instead of reading it as a one-element collection or materializing it; a list CONTAINING a view is an ordinary collection.
* **CR-11 The cell-preserving spread.** In an ARGUMENT or SELECTOR supply, a spread slot whose LAST star opens a view (`F(R.Arguments*)`, `F((R.Arguments)*)`, `X[R.Arguments*]`) transports the plan's ORIGINAL cells, in order, each with its own written source (`NeedSupply.slot`'s `SpreadSupply.cells` arm) — no copy, no Ready wrapper, no second preparation, no demand — so undemanded arguments stay suspended, CALLABLE arguments stay callable, and destination and original share memoized VALUEs. A star that would open a view into VALUES — any spread in a value position (`[R.Arguments*]`, `(R.Arguments*, 1)`, a spread row) or an inner star of a stacked spread (`F(R.Arguments**)`) — is `TypeMismatch` (`argumentViewSpreadMessage`); wherever no view is opened the openers are exactly the pre-S2 ones (`openSpreadItems_eq_reopen`).
* **CR-12 Boundaries.** A view obeys CR-4 and CR-6 unchanged: opaque, no text, refused by run results, host-operation arguments and returns and interpolation at any depth (DAG-safe), and every view operation — obtaining, preparing, counting, selecting, spreading — passes `Evaluator.CheckCallReferenceOwnership` before plan work and again after it, so foreign, ended, cancelled, resource-terminal and required-source-failed runs are refused. C# carries the view as an internal facet of the one public `Result.CallReference` variant (`IsArgumentView`); equality is plan identity plus facet.

Proof boundary (S2): inertia, the view supply's single preparation and sharing with `Invoke()`, the demand laws of `count`/`first`/`last`/selection (demand extensionality), the selection precedence, the transport of the plan's recorded cell addresses, the openers' conservative extension and the run boundary are theorems; that the partial evaluator's `Arguments`, `.index`, builtin-binding and spread arms call these definitions is source fact with executable guards; `ProductionDiscipline` (including `evalSupplySpread` and the S3-4 classifier) is proved by `EvaluatorDiscipline.productionDiscipline_holds`; the reachable-state refinement remains open.

Performance (C#): a META-free program without deferred module regions keeps the ordinary route (CR-7) and pays only the gate's per-node type test inside the existing preflight walk. A META-possible program retains one invocation plan per call-shaped supplied cell (one supply slot, no holder object) and loses supplied plain-call pipeline fusion (`DispatchPlannedCounted`: a fused VALUE would leave the plan without the formed supply and cell outcomes a later observation needs); both costs are inherent to retention. A view operation's first preparation forms the captured call's supply once (an explicit spread among its arguments runs then), and a view spread transports the plan's cells without per-argument cells.

## Callable projection: `R.Algorithm` (META-S3-1, 2026-10-19)

S3-1 adds the CALLABLE PROJECTION of a call reference: `R.Algorithm` is the captured invocation's CALLEE as a transportable callable, independent of the invocation's original argument supply. It reuses the existing machinery — the invocation plan, NeedCell's VALUE and CALLABLE channels, the runtime-projection single flight and wait-for graph (S3-0a), the asynchronous resolution adapter (S3-0b), the one binder and the one dispatcher — and adds no Result kind, evaluator, binder, dispatcher or loop operation. * **CR-13 The callee cell.** Every invocation plan has at most ONE canonical callee cell: its ROUTE's callee (META-S3-4: the written callee of a call, the argumentless member path `t.N` of a member route — DOT-09's identity —, the link `t.Algorithm` of the `.Algorithm` route, the lexical fallback of an extension route; an intrinsic route has none, D-1A) supplied in the plan's captured caller context through the one supply-cell constructor — so a parameter callee is that parameter's existing cell (NEED-01) and a name callee an identity-only cell over the name. It is established lazily, by the first observation that needs it, after the plan's route; once the route is established, establishing the cell evaluates, prepares and demands nothing (no target, no argument VALUE, no supply preparation, no spread), while establishing the route itself may demand a runtime-projection receiver (D-4). Concurrent establishment may construct candidates that are discarded unused; exactly one is retained (C# `InvocationPlan.CalleeCell`, compare-and-set; Lean records it in the plan cell), and every observation — CALLABLE projection, bare VALUE, fresh invocation — uses the retained cell. The callee cell belongs to the plan's run; it is available whether or not the plan's own VALUE completed, and using it never reads or writes that VALUE.
* **CR-14 The `.Algorithm` intrinsic.** On a structural miss an edge spelled `Algorithm` reads its receiver exactly as `Invoke` and `Arguments` read theirs and requires a call reference of the current run (the one ownership helper; a number, text, list, argument view or ordinary computed value is `TypeMismatch` "`Algorithm` requires a call reference, got …", a foreign or ended run's reference `IllegalInEval`). It denotes the decoded plan's callee cell: (a) CALLABLE use — a supplied or forwarded argument, a callback, a loop step, or a callee (`(R.Algorithm)(x)`) — uses the callee cell's CALLABLE; (b) a BARE read `R.Algorithm` is the callee cell's VALUE: the captured callee read as an ordinary value in its captured context, with its ordinary zero-supply demand, property cache, computation or arity rejection (`R.Algorithm` of `Square(5)` is `ArityMismatch(1, 0)`; of a captured `Z()` it reads `Z`'s cache entry); (c) `R.Algorithm(args)` is a FRESH ordinary call of the callee cell's CALLABLE with exactly `args` (`R.Algorithm()` supplies nothing — never `R.Invoke()`), named by the plan's written callee for dispatch diagnostics; a callee with no CALLABLE identity is `NotAnAlgorithm "captured callee"`. A declared member named `Algorithm` wins in every position; dot syntax never consults a lexical `Algorithm` (`5.Algorithm` is the intrinsic's `TypeMismatch`; the plain call `Algorithm(x)` is unaffected) and the front end never infers `Algorithm` as an implicit parameter (`AstHelpers.UsesDotMissIntrinsic`, the `AlgorithmIntrinsic` formula-lifting edge kind with a VALUE receiver role). Member access does not navigate through the intrinsic edge: `R.Algorithm.n(args)` is the extension call `n(R.Algorithm, args)`. A written `R.Algorithm(args)` / `(R.Algorithm)(args)` is itself a written invocation (META-S3-4): META captures it as a NEW plan on the `.Algorithm` route, so `R.Algorithm(R.Arguments*).while` loops the captured step from its original arguments and `Loop(meta op) = op.Algorithm(op.Arguments*).while` makes `Step(0).Loop` a loop; its original VALUE keeps exactly this intrinsic's semantics and accounting (the receiver is read by the ordinary invocation receiver evaluator). *History:* until META-S3-4 such a loop had to name the projection first (`RA = R.Algorithm` / `RA(R.Arguments*).while`), because CR-2 refused a dot callee; naming it still works.
* **CR-15 The link.** A SUPPLIED `X.Algorithm` is ONE link cell whose receiver `X` is ONE receiver cell, established lazily and retained exactly as in CR-13, shared by the link's VALUE and CALLABLE: each channel demands that one receiver VALUE (at most once per written slot, its effects and failures shared), decodes the same reference and delegates to the same callee cell's corresponding channel. The link's VALUE is the callee's VALUE, passed through as the callee reports it (a consumer's slot diagnostics read it as if the captured callee were written there). The link's CALLABLE is a RUNTIME projection: a node of the run's wait-for graph under the S3-0a single flight, resolved asynchronously through `Evaluator.ResolveAsync`; it never demands the link's own VALUE nor the callee cell's VALUE. A plan on the `.Algorithm` route (META-S3-4) has such a link as its callee cell: its ONE receiver cell is demanded at most once for the PLAN and shared by the plan's VALUE, every `Invoke()`, its `.Algorithm` and a loop over it (D-3); its first demand is the ORDINARY invocation receiver read (C# `EvalAlgorithmReceiver`, so the plan charges exactly the ordinary checkpoints), and a parameter receiver is that parameter's own cell. Each ordinary invocation still takes the ordinary parameter receiver read (including its checkpoint on the value-receiver route and its error provenance); transporting the cell never replaces that read with an uncharged raw demand. A different written occurrence is a different plan with its own receiver.
* **CR-16 What obtaining and using `R.Algorithm` does (qualified inertia).** It evaluates the receiver through the receiver's ordinary VALUE route (once per link), with that computation's effects, failures, dependencies and source admission, and decodes the reference through the ordinary ownership check. CALLABLE use then projects the callee cell's identity — identity-only resolution in the captured context, except that a callee route through another runtime projection demands that projection's own receiver, each such cell at most once. Bare VALUE use is the callee cell's VALUE; fresh invocation is an ordinary call. Projection itself never executes the plan's captured invocation, prepares or reads its original argument supply, opens its original spreads, demands an argument cell as an argument, reads or writes the plan owner's VALUE, or changes the reference. A failure of receiver VALUE, decode (ownership included) or a projection on the callee route is the projection's FAILURE (NEED-06 replacement wording): a completed link publishes it as its CALLABLE outcome with its original kind, span and context, and a parameter-rooted path over it propagates it (`Use(p) = Apply(p.G, 0)` over a failing `Bad.Algorithm` keeps `Bad`'s error, while `Use(5)` stays the static absence `param(f)`). A re-entry is NEED-09's flow-local `DemandCycle` (`R = Hold(R.Algorithm)` with `Hold(g) = Capture(g(0))`: every use of `R.Algorithm` is `DemandCycle` on every engine, never a host stack overflow or an unproductive async retry).

`R.Algorithm` and `R.Arguments` are independent: obtaining `R.Algorithm` never forms the plan's supply, obtaining `R.Arguments` never resolves the callee, preparing `R.Arguments*` forms the supply once (CR-9), each argument VALUE is demanded only where used, and invoking the target is a separate step — so `R.Algorithm(R.Arguments*)` calls the captured callee afresh over the ORIGINAL argument cells (shared with `R.Invoke()`). A conditional family is re-dispatched by the NEW supply (`R = Capture(F(0))`: `R.Algorithm(3)` selects by 3), and a nested callee keeps its owner's activation, never the consumer's names. The optimized loop consumes a projected step exactly as it consumes any step — after the generic loop has projected it for the actual invocation — and sequence-optimizer recognition reads only published identities through the non-initiating observation: an identity that would need a runtime step is unknown there, so recognition declines and the generic path runs.

## Generalized capture: the plan ROUTE (META-S3-4, October 2026)

META captures a WRITTEN INVOCATION independently of the syntactic form that reaches its callable (owner decisions D-1A, D-2A, D-4; required consequences D-3, D-5). Lean is authoritative (`NeedPlan.callShape?`/`CallForm`, `PlanRoute`, `NeedCell.route`, `NeedPlan.routeOf`/`effective`/`calleeAlong`/`executeAlong`/`invocationRefusal`, `selectDotEdge`/`DotMiss`, `classifyPlanRouteWith`); laws `KatLangArityLaws/InvocationRoute.lean` (with the route-aware `InvocationPlan.lean`, `AlgorithmProjection.lean`, `ArgumentView.lean`, `MetaLoop.lean`), guards `InvocationRouteGuards.lean`; C# `Evaluator.CallPlans.cs` (`IsPlannableCall`, `PlanRouteOf`/`PlanRouteOfAsync`, `ComputePlanRoute`, `DispatchPlannedDotCounted`) and `SelectDotEdge` in `Evaluator.DotCalls.cs`.

* **The domain (CR-2, D-2A).** Syntactic: a call through a name, a parameter or an argumentless dot path, or an argument-bearing dot edge. `Box.Step(0)`, `Math.Abs(-3)`, `(Box.Step)(0)`, `op.Algorithm(op.Arguments*)`, `(op.Algorithm)(op.Arguments*)`, `5.Add(1)` and `Box.V()` are captured; `Box.Step`, `5.Inc` and `Start` are not, so member/property access and explicit invocation stay distinct (DOT-09) and no cell changes kind by runtime lookup. No implicit provenance: `Start = Step(0)` / `Start.while` stays refused.
* **The route.** Each plan has ONE route, decided by the first ROUTE-DEPENDENT operation — VALUE, `Invoke()`, reading the argument supply, `.Algorithm`, a loop's setup — and retained (C#: compare-and-set, the first publication wins; Lean: the plan cell's `route` record, never rewritten). Capture, reference identity, obtaining or comparing the argument view and an empty selection need no route. The route is the ordinary decision for the written form, through THE ONE dot decision ordinary dot evaluation also takes (`SelectDotEdge` / `selectDotEdge`: member-first whatever the spelling, accessibility after selection, a branch-only member its error): **call** (a written call; also `(t.Algorithm)(args)` when `t` declares `Algorithm`), **member** (`t.N(args)` selecting a declared member: callee the argumentless path, supply `args`), **`.Algorithm`** (`t.Algorithm(args)` / `(t.Algorithm)(args)` on a structural miss: callee the link `t.Algorithm`, CR-15), **extension** (any other miss: `F(t, args)`, DOT-03), or **intrinsic** (`t.string(…)`, `t.Invoke(…)`, `t.Arguments(…)` on a miss). A route failure (an inaccessible or branch-only member, a receiver failure) is the plan's failure with its kind, span and context — never absence. A name, parameter or path call has the call route by its source: nothing is classified or allocated.
* **D-3 Receiver sharing.** The `.Algorithm` route's receiver is ONE retained cell for the plan (CR-15), read by the ordinary invocation receiver evaluator; a parameter receiver is the parameter's own cell.
* **D-4 Route before supply.** Reading the effective supply first establishes the route (CR-9) — identity resolution, which through a runtime-projection receiver performs that receiver's existing single-flight demand, once, at that point; it never executes the captured target. `repeat` keeps RP-1: capture, route, supply, count, iterations.
* **D-5 The extension receiver is supplied.** `R = Capture(5.Add(1))`: `R.Arguments.count` is 2, `R.Arguments[0]` is 5, `R.Algorithm` is `Add` (`Apply(R.Algorithm, 7)` is `Add`'s arity rejection) and `R.Invoke()` is `Add(5, 1)`. A member's receiver selects the member and is NOT supplied (`Capture(Box.G(2)).Arguments.count` is 1).
* **D-1A Intrinsic routes.** An intrinsic-shaped capture is inert and legal (`Ignore(5.string())` is the ignoring result; `R = Capture(5.string())`, `R == R` is `true`), and its original VALUE is the intrinsic's ordinary evaluation. It has no callable: every route-dependent reference operation — `R.Invoke()`, `R.Algorithm`, `R.Algorithm(args)`, reading `R.Arguments`' supply (`count`, selection, `first`/`last`, a spread), a loop over it — is `NotAnAlgorithm "meta: not a callable invocation"` ("The captured expression is not a callable invocation …") at that operation. No intrinsic name is refused earlier than an equivalent runtime-selected intrinsic.
* **Operations.** The original VALUE is the ordinary evaluation of the written form along its route — the same node checkpoint, frames (`while evaluating dotCall …` / `call to …`), spans, charges and errors — over the plan's ONE sticky supply (fusion is not attempted, fail-closed). `R.Invoke()` is a fresh execution along the same route over the same supply. `R.Arguments` is the inert view of the route's supply. `R.Algorithm` is the route's callee cell. So `R.Algorithm(R.Arguments*)` reconstructs the captured invocation for every route: `Box.G(1)` → `Box.G(1)`, `5.Add(1)` → `Add(5, 1)`, `op.Algorithm(op.Arguments*)` → `Step(0)`.

Proof boundary: the domain, route stickiness and determinism, the dot-route agreement with ordinary evaluation on selection failure, member, extension and `.Algorithm`, member precedence, the effective callee and supply per route (D-5), the D-1A refusals, failure preservation, the route-aware callee-cell laws (canonical; inert after route establishment) and view laws, and the production classifier's discipline are theorems; that the `partial` evaluator's arms install them is a source fact with executable guards. The serial Lean model claims nothing about C# asynchronous resolution, the compare-and-set, cancellation, J7, diagnostics text or checkpoint accounting, which the C# suites pin (`InvocationRoute/InvocationRouteCorpusTests`, `InvocationRouteTests`).

## Runtime aliases (META-S3-2, October 2026)

A runtime-target callable alias (FWD-02 § Runtime-target callable aliases in `ownership-and-lookup.md`: an open, parameterless body whose one row is a parameter, an argumentless `.Algorithm` link or a parameter-rooted member path, or a chain to one) is ONE BINDING CELL per declaration and declaring activation, supplied through the ordinary supply-cell construction exactly as a plan's callee cell is (CR-13): the row, in the alias's own declaring context (the alias as the head, so its own declarations, opens and captured activation are the ones read — never the consumer's), retained by its stable owner (the declaring activation, or the run).

* **Identity transport.** A parameter row IS the parameter's own cell (NEED-01: nothing allocated). An `.Algorithm` row is a CR-15 link with its one receiver. A parameter-rooted path is a supplied reference cell whose CALLABLE is DOT-09's structural projection: a hit carries the member's identity, a miss is a computed value with none.
* **Two channels, one cell.** The alias's bare read is the cell's VALUE, with property-style provenance (the property body's outcome, never a written-argument slot); every CALLABLE use is the cell's CALLABLE projection followed by FWD-02's eligibility at run time — an identity declaring parameterized structure is the alias's callable, and absence, a value or a zero-parameter identity leaves the alias its ordinary zero-parameter property. For an eligible target both channels share every receiver demand (`A = Mk(5).Algorithm`: `A, A()` evaluates `Mk(5)` once), and a VALUE read never initiates the CALLABLE (a chain's bare read is its runtime alias's cell VALUE).
* **D3 fresh invocation.** `A(args)` and `A()` on an eligible identity are fresh ordinary calls with exactly the written supply; the cell's sticky outcomes are its VALUE and its identity, never a call result.
* **D4 ordinary-property fallback (owner decisions 2026-10-19 and CACHE-PUB-1 extension 2026-10-22).** An ineligible or genuinely zero-parameter runtime target retains ordinary-property semantics. Each explicit `A()` evaluates the terminal alias row freshly. A qualifying zero-supply invocation participates in CACHE-PUB-1 under the alias's OWN binding, declaring scope and activation: its outermost owning success may establish its empty property-cache entry; bare `A` reuses that entry; later `A()` calls never replace it. A parameterized runtime-callable alias retains D3 and does not publish through either the alias's or target's entry. Eligibility checking shares the retained receiver work with the FIRST ordinary observation (a bare read or terminal call), whichever operation performed the projection, never duplicating it. For `A`, `A, A`, `A()`, `A(), A()`, `A, A()` and `A(), A`, an effectful terminal row evaluates 1, 1, 1, 2, 2 and 1 times respectively; `Navigate(A), A` and `Navigate(A), A()` remain one evaluation each. The RF1-D4 local-cache alias and ordinary-property control both yield `(10, 10, 20, 10)` with two `tick()` executions. Reads and qualifying terminal invocations use the ONE property publication owner, success-only and never replacing; no second cache or alias-specific publication law is introduced. The callee's own cache, supplied cells, VALUE/CALLABLE separation, META plans, arity, failures, cancellation and re-entry retain their existing guarantees. C#: `RuntimeAliasBinding`, `TakeTerminalAliasInvocation` and `ZeroArgPropertyPublications`; Lean: the terminal-alias controls and the `read` / `invoke` requests of `evalZeroArgPropertyAccessCounted`. *History:* RF1 (2026-10-19) refused to lend a CALLABLE-only observation's receiver work to a later call or bare read through a flow-local invocation token (Lean `withAliasInvocation`), which made a bare read's value depend on incidental call nesting (`K(x) = x` against `K(x) = Id(x)` under `Navigate(f) = f.K`) and duplicated the receiver evaluation; the final review (2026-10-19) removed the token and the Lean control.

The sharing follows the plan, not the binding cell: an alias declared afresh in each `H(r)` activation over the same `R1` still shares R1's VALUE, while a COMPUTED receiver forms a new plan per row evaluation (`AM = F(3).Algorithm`: `AM(), AM(), AM` is `(4, 5, 4)` with two ticks). ## Required source information

C# records required deferred compilation failures and observed source-processing cancellation in
the owning evaluation budget (`MaterializeRequiredRegionAsync`, shared by branch selection and
algorithm-output materialization). An internal META receiver cannot absorb either and continue.
Source failures keep their original diagnostics and remain non-resource errors; cancellation keeps
its original exception and source token. This retention belongs to one run, not the loader's cache.

Source-size and acquisition limits are host admission policy, applied when the language's source-processing contract requires a source unit, before its contents are used. A deferred unit is processed only when an operation requires its compilation, including required identity information; refusal stops that operation and its run, while an undemanded deferred computation performs no source work.

NEED-03 governs runtime supplied computations, while MOD-07/10 govern required compilation units. Undemanded supplied computations perform no speculative source work; initial source remains initially parsed, and a selected deferred compilation unit includes all its static imports. CALLABLE projection does not demand the member's zero-argument VALUE, but may require compilation to discover declarations: `Apply(M.Inc, 3)` needs M's compiled member identity. `Ignore(F)` transports an already-known family identity without compiling its deferred body. These are source-information requirements, not a second runtime laziness mechanism or a metadata-manifest API.

NEED-07 is unchanged: arbitrary `F(1)*` requires VALUE to form supply before an ignoring callee; opening an existing collector slice transfers cells without demanding them. NEED-09 cell completion and source-loader caches remain separate. Required acquisition observes the established source/evaluation cancellation rules; successful materialization can be reused, while failed materialization is not cached. `IsResourceLimit == false` does not make a reached source refusal recoverable.
