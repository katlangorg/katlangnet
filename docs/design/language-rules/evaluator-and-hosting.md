# Evaluator, hosting, and pipeline rules

The full statement of the rules that AGENTS.md carries in compact form — consequences, examples, the implementation map, and the pinning tests — moved here verbatim from AGENTS.md in September 2026. These rules are as binding as AGENTS.md; the compact bullet there points at the section here. Keep both in step: a rule change edits the compact bullet and the section together.

## Elaboration boundary

The individual elaboration passes are INTERNAL implementation stages: `ParameterDetector`, `ImplicitArgumentResolver`, `PropertyExposureResolver`, `FrontEndPipeline`, and `Parser.ParseSyntax` are not host API, and hosts must not be able to compose partial elaboration — a Detect→Resolve tree without exposure resolution leaves every `Property.Exposure` at the default `Exported`, which the evaluator trusts (pinned by `FrontEndElaborationBoundaryTests` and the non-friend `PublicElaborationSurfaceTests`). The supported public layers are `Parser.Parse`/`ParseAsync` and `KatLangEngine` (complete pipeline), `SemanticModelBuilder` over `ParseResult`, and `Evaluator.Run*` direct evaluation of host-built ASTs (as-is, preflight only, no elaboration). Do not re-publicize a stage or add a partial facade; exposure/ownership metadata is trustworthy only after the complete pipeline finishes. (`ModuleLoader` is internal too — load elaboration alone is even more incomplete: a loader-only tree has had no parameter detection, so spliced module algorithms cannot even bind their arguments; hosts get module loading through `Parser.ParseAsync`/`KatLangEngine.RunAsync` with `RunOptions.DownloadCode`/`AllowedHosts`.)

## Source loading and deferred modules

Default parse/run entry points reject unresolved `load`; only elaboration-enabled paths may consume it. SOURCE LOADING IS ASYNC-ONLY: the one downloader contract is `RunOptions.DownloadCode : Func<string, CancellationToken, ValueTask<string>>` — and it is the ONLY transport: the library ships no default/ambient HTTP downloader (a `ModuleLoader` cannot be constructed without an explicit delegate; `AllowedHosts` governs load-target policy while transport behavior, redirects included, belongs to the host delegate; blank or null `AllowedHosts` entries must fail closed with `ArgumentException` at sync and async options boundaries; trim valid entries and keep loader matching fail-closed even below those boundaries) — module acquisition awaits it inside `ModuleLoader.ElaborateAsync` (an incomplete download genuinely suspends source processing and resumes it at the same point; the downloader is never replayed), and the elaboration-enabled entry points are the asynchronous ones (`KatLangEngine.RunAsync` + async conveniences, `Parser.ParseAsync(source, options)`). The synchronous source-level entry points remain for downloader-less configurations only and reject a downloader-configured options object with `InvalidOperationException` before parsing (enforced in the synchronous `FrontEndPipeline.Process(source, RunOptions?)`) — never a blocking sync-over-async bridge. Parsing and all other elaboration passes stay synchronous CPU work. Loader traversal is routed: load-free subtrees take the calibrated synchronous walk unchanged; load-bearing spines (marked by a linear pre-scan) take `// MIRROR OF`-tagged async twins; clause families are handled by ownership (B2c, branch-lazy module loading): a family-owned open list is shared by every alternative and elaborates eagerly, while each alternative branch body that owns an unresolved load is a DEFERRED module-elaboration region (`DeferredModuleRegions`) that initial elaboration never descends into — its modules are fetched, elaborated, and budget-charged only when evaluation selects that branch (`DeferredModuleRegion.MaterializeAsync`, at the conditional-call selection boundary in the async evaluation family), nested alternatives inside it staying deferred, a never-selected branch performing zero module work, and a root carrying deferred regions requiring the async evaluation entry points; a deferred materialization is OWNED by the evaluations that selected it — concurrent selections share one underlying run, a cancelled evaluation leaves at once with its own token's identity, and the run's download and elaboration are cancelled (linked with the source-processing token, which stays authoritative and keeps its identity) exactly when its last consumer leaves, caching nothing, while ordinary eager loads observe only the source-processing token; the scan and both walks carry a per-level stack-reserve backstop that turns residual exhaustion into the structured `ModuleElaborationStackExhausted` diagnostic. Downloader error semantics are unchanged (thrown or faulted-awaitable exceptions → `load: failed to fetch` unless the source-processing token is cancelled, which stays authoritative). See `docs/design/async-evaluation-2026-08.md` and `ModuleLoaderAsyncTests`.

## Structural depth and parser budgets

Structural AST depth is a C#-only host-safety policy: every entry point that hands a preconstructed or parsed AST to recursive consumers (evaluator `Run*`, `ParseSyntax`, front-end elaboration, the standalone `ParameterDetector.Detect` / `ImplicitArgumentResolver.Resolve` / `ModuleLoader.Elaborate` boundaries, `SemanticModelBuilder`) must run the iterative `AstStructuralPreflight` FIRST, and a new AST node variant must be added to its child enumeration (it fails loudly on unknown kinds; the base-declared `Algorithm` collections are enumerated uniformly for every subtype). The shared `AstWalker.VisitExpr` switch is fail-loud for the same reason — an unhandled variant would be silently skipped by every walker subclass — and `AstWalkerExhaustivenessTests` pins that its sample table covers every declared `Expr` variant. Two non-raisable tiers: fat-frame consumers (evaluation, front-end elaboration incl. the standalone detector/resolver entry points, semantic modeling) use `EvaluationLimits.MaxSupportedAstDepth`; the small-framed walker-class raw-syntax passes and the measured module-loader traversal use `AstStructuralPreflight.RawSyntaxMaxAstDepth` (the loader also bounds nested module loads CUMULATIVELY against that ceiling — a load site's own traversal depth counts against the module it loads). `MaxAstDepth` may only lower the evaluation tier. Pure-expression spines (unary/binary/index/list and the sequence joins) must stay ITERATIVE in `Eval`/`EvalCounted` (`EvalExpressionSpineCounted`) — the ceiling assumes they consume no proportional stack, and the 384 KiB-thread subprocess pin enforces it. Diagnostic expression-name rendering must stay ITERATIVE and OUTPUT-BOUNDED (`ExprNameRenderer`): the evaluator gates accept arbitrarily long internal join/spread chains, so no diagnostic/optimizer path may render an expression recursively. PARSER recursion budgets are CUMULATIVE across grammar mechanisms: `Parser.MaxNestingDepth` is one weighted per-parse counter that never resets inside a nested container/chain/pattern/call (heavy productions carry calibrated surcharges), its per-shape capacities are proven on 1 MiB threads with ≥2x margin, and a nested module's parse starts with the loader's live-frame stack debt (`Parser.ParseSyntax(source, initialNestingDebt)`) — never add a parser mechanism with its own independent budget or reset. Parser lookahead over a token run must perform linear total traversal work, including repeated declaration and recovery checks; do not repeatedly rescan growing prefixes or remaining suffixes. Pin complexity with deterministic traversal observations. The same rule binds walker-class passes over intentionally SHARED structure: an `AstWalker` subclass whose effective `VisitExplicitParameterDeclaration` and `VisitCollectMarker` hooks are both unused (including inherited behavior) must opt out of the base per-declaration loop (`VisitsExplicitParameterDeclarations => false`, pinned library-wide by `AstWalkerDeclarationVisitPolicyTests`), because the N helpers of a wide assignment deconstruction share ONE N-declaration list and a walk that examines it once per helper is O(N²) (K2-R2: the load-elaboration guard). This is distinct from runtime `MaxDepth` and has no Lean counterpart.

## Shared-DAG guarantee

Host ASTs may legally contain SHARED acyclic subtrees (a node referenced from several parents; cycles stay preflight-rejected), and module elaboration itself splices one cached module algorithm at every load site of the same URL. The front-end passes (`ParameterDetector`, `ImplicitArgumentResolver`, `PropertyExposureResolver`, `PropertyDependencyGraphBuilder`, `ModuleLoader` incl. its load-bearing pre-scan, plus the `LoadElaborationGuard`/`FinalPropertyExposure` helper walks) are DAG-SAFE: every walk carries a run-local REFERENCE-IDENTITY memo per constant-context region, so work is bounded by distinct reachable nodes rather than root-to-node paths wherever semantics permit, and rewritten output preserves sharing within one context. Semantics stay tree-equivalent (grace weights accumulate per semantic occurrence through memoized ordered weight effects); the deliberate per-NODE behaviors are diagnostic multiplicity within one diagnostic context and load-site identity within one constant loader context. Load-bearing loader keys include effective live traversal depth because near-ceiling admission is path-sensitive; the same node reached at two such depths intentionally splits. The `ModuleLoader` memo checks live INSIDE the calibrated walk frames — never add a wrapper method or extra async state machine to its recursion spine. A new memoized traversal must keep its explicit variant switch (the memo wrapper adds no dispatch); pinned by `FrontEndDagComplexityTests` and the `AstGraphFuzzTests` front-end shared-vs-cloned campaign. SHARED-DAG GUARANTEE: a legal shared acyclic AST is processed with work bounded by distinct nodes × distinct semantic regions, and traversal-path multiplicity affects neither results, nor diagnostics, nor asymptotic work. Region keys are the minimal complete semantic context, run-local, node/scope identity by reference and name sets by content: detector branch bodies (parent scope, binder set, captured names, reporting mode); resolver nested algorithms — property values, block literals, open targets, branch bodies alike — (the signature SNAPSHOT of the algorithm's FREE reference names in the visible map, the closed binder specification for a branch body, reporting mode); exposure (the region's final visible summaries); summary channel (node, or body plus binder set); order channel (node, shadow context, position); loader (load context plus effective live depth); the editor's `Semantics/SemanticModelBuilder` (node plus scope frame; algorithms additionally plus a branch's binder table). Family-worded diagnostics are stored as templates and replayed per family sharing a body (`same node + same region → reused; same node + different region → independently processed`). Sibling-dependency edges are COMPLETE — every value-position sibling reference in a property's whole value subtree, nested bodies and branch bodies included, with a nested body's own names shadowing and neutral arguments/capture rows transparent — so sibling declaration order is not observable. Explicit exceptions, occurrence-oriented by design (see `SEMANTIC-ALIGNMENT.md`): the semantic model analyzes a body once per family that declares its own binders; a sibling CYCLE resolves its order by declaration order, the one way two reaches of a node can observe different sibling signatures; the loader splits by depth near the ceiling.

## Traversal exhaustiveness

EVERY hand-written `Expr` traversal is exhaustiveness-enforced: no silent `_ => expr` / `_ => null` / `default: break` arm may absorb an unknown variant. The front-end rewriting/collection walks (`ParameterDetector` — ProcessOpenExpr, CollectFreeParams, RewriteParams (ordinary and conditional bodies), ProcessExpr, FindResolveSpan; `ImplicitArgumentResolver` — ProcessOpenExpr, CollectImplicitDeps, RewriteImplicitCalls, ProcessExprNested, CollectReferenceNames; `PropertyExposureResolver.RewriteExpr`; `PropertyDependencyGraphBuilder` — CollectSummarySeed, CollectSiblingDependencyIndices; `ModuleLoader.ProcessExpr` + its async twin) enumerate their intentional leaves explicitly and THROW `InvalidOperationException` on an unhandled variant, and both counted evaluator dispatches (`EvalCounted` / `EvalCountedAsync`) enumerate their sync-delegable leaves (Num, StringLiteral, Grace) the same way so a new recursive variant can never silently bypass the async twin family (`NativeCall` is NOT one: its declared-argument reads are ordinary `Expr.Param` value reads, so it has its own async twin case). ADDING AN `Expr` VARIANT therefore requires, in the same change: `AstStructuralPreflight` child enumeration, `AstWalker.VisitExpr`, every traversal switch above (classify it: recursive case or intentional leaf), both counted dispatches, and the mechanically pinned classifications in `AstWalkerExhaustivenessTests`, `FrontEndTraversalExhaustivenessTests` (reflection-complete sample table + per-traversal dispatch matrix), and `AsyncEvaluation/AsyncDispatchExhaustivenessTests` (reflection-complete async-dispatch policy table + per-recursive-variant async-seam routing) — those suites fail on any current variant a targeted traversal cannot dispatch, so a missing case is a test failure naming the traversal and variant, never a silent skip.

## Budgets and cancellation

Runtime evaluator budgets are OPERATION-LOCAL. Dynamic depth is the only balanced protocol (`EvaluationBudget.TryEnterInvocation` / `TryEnterArgumentEvaluation`, released by `ExitInvocation`); steps, materialized items, and materialized string units are CUMULATIVE and are never refunded by a failure. Two rules hold for every admitted level: a REJECTED enter mutates no counter — not depth, not peak, and not the invocation's own step, because that invocation did not happen (charging it let a lower `MaxDepth` flip an unrelated `MaxSteps` verdict, since a resource-limit failure of a parameter's eager value evaluation is retained on the algorithm binding and the run can continue) — and an ADMITTED level is released exactly once from a `finally`, on success, structured failure, and exceptional unwind. Rejected cumulative work likewise cannot advance auxiliary admission state: in particular, a rejected bulk expression-work step leaves its 4096-checkpoint batch at the boundary so retained errors cannot admit work past an exhausted step budget. `ExitInvocation` is fail-loud on underflow, like `SourceProcessingBudget.ExitModule`: a double release is as damaging as a leak and otherwise invisible. Pinned by `BudgetConservationTests`; `OperationCanceledException` unwind is exercised both by injecting it through the internal `IZeroArgPropertyResultCache` seam and by the real host token. Evaluation host cancellation (`RunOptions.EvaluationCancellationToken`, `Evaluator.Run`/`RunFlat` token overloads) lives ON the run-scoped budget: every budget chokepoint observes the token BEFORE any counter check or mutation (`EvaluationBudget.ObserveCancellation`), each entry point checks it before the structural preflight and again before completing, and the optimized loop executor observes it once per iteration (observation-only — a fully-planned iteration touches a charging chokepoint only where the generic path charges one: planned `if` arguments, temp reads, and temp calls enter the SAME `Evaluator.BudgetScopes.cs` helpers as their generic counterparts, and charging per iteration would break optimized-vs-generic accounting parity). The completion observation closes final operations that have no later charging checkpoint; `RunFlat` and the engine also observe after their bounded host-atom projection. Requested cancellation THROWS `OperationCanceledException` carrying the supplied token and must NEVER become an `EvalError` — a resource-limit-style structured error would be retained on eager parameter bindings and the cancelled run would continue. An uncancelled token changes no counter, verdict, or result; the token is separate from `SourceProcessingCancellationToken` (front-end only). Pinned by `EvaluationCancellationTests` (deterministic mid-run and completion-edge triggering via CANCELLING — not throwing — cache-seam wrappers).

## Async evaluation and host operations

The ASYNC evaluation surface (`Evaluator.RunAsync`/`RunFlatAsync`, `KatLangEngine.RunAsync`) is a host-execution surface with NO Lean counterpart, built as a "sync-delegating async twin spine" (`Evaluator.Async.cs`): the synchronous evaluator remains the semantic oracle; engine `RunAsync` first awaits the async front end (`FrontEndPipeline.ProcessAsync` — module downloads may suspend source processing, see the source-loading bullet above), then an async entry point routes ONCE per run — a run whose zero-arg property cache is not async-capable and whose host-operation set has no asynchronous operation executes the synchronous pipeline inline and completes synchronously (never `Task.Run`, never artificial yielding), while an async-capable cache OR asynchronous host operation routes through the internal `async ValueTask` TWIN family. Every twin is marked `// MIRROR OF <sync name>` and MUST be updated in the same change as its synchronous counterpart — the twins re-implement only awaitable child-evaluation sequencing and share every non-evaluating helper. Twin rules: counted-family mirrors only (plain wrappers are counted projections — the Lean-modelled plain/counted value equivalence); the twin root context pins the GENERIC loop/sequence strategies (fail-loud guard `ThrowIfAsyncStrategyPinningViolated`); the two row-loop funnels carry a twin-only `TryEnsureSufficientExecutionStack` backstop because async frames are larger than the calibrated sync frames and structural nesting passes no invocation chokepoint; cancellation is the Phase 1 contract via the shared budget chokepoints (OCE through the returned task, never an `EvalError`). Divergence is pinned by `AsyncEvaluation/AsyncTwinDifferentialTests`: the language-spec + explorer corpora run through the twin path with outcome AND operational-counter equality against the sync generic strategies, plus a genuine-suspension pass; keep that suite green when touching either family. PUBLIC host operations generalize the Math-module mechanism, not a new subsystem: `HostOperation`/`HostOperations` (`RunOptions.HostOperations`, `Evaluator.Run`/`RunAsync` host-operation overloads) synthesize one ambient prelude property per operation — a parentless wrapper `Algorithm.User` whose body is `Expr.NativeCall("host:" + name, params)` (`':'` keeps host dispatch names disjoint from Math natives) — so resolution, shadowing, arity, and the `A` vs `A()` cache rule are the existing Lean-modelled rules unchanged, and the front end resolves the names through the configuration's extended signature-only semantic prelude (`ParameterDetector.DetectPrevalidated`; a referenced operation never becomes an implicit parameter). The configuration rides the run-scoped `EvaluationBudget`; sync operations dispatch in the shared `EvalNativeCall`, async operations await at ONE guarded `EvalCountedAsync` NativeCall case (invoked exactly once — suspension never replays), and every SUCCESSFUL host return value is normalized into the canonical `Result` representation at the host boundary (`NormalizeHostOperationValue` — the existing `Result.Normalize`, shared by both dispatch paths, applied BEFORE the zero-arg property cache stores the wrapper outcome; failures/cancellation untouched, identity on already-canonical values). Routing is enforced: any async-operation configuration selects the twin path with an async-capable cache (public entries construct one, internal entries fail loud), sync entry points reject async configurations with `InvalidOperationException` before evaluating, and host exceptions/faulted awaitables propagate to the host unchanged (never `EvalError`). Native-call wrapper bodies (Math members AND host operations) read their declared argument names through `LookupNativeArgument`, which IS the `Expr.Param` value read (`EvalParamCounted` projected to its value: `CountedParamEnv`, then `valEnv`, then the algorithm binding) — not a separate lookup rule. The counted tier makes them work DIRECTLY as flat callback and loop-step references (`map(abs)`/`map(Enrich)`), and the algorithm tier makes an argument that bound only on the algorithm channel produce the ordinary value-demand outcome (a parameterized callable's zero-argument arity error, a clause family's conditional value-access error, a zero-parameter algorithm's value or failure) instead of reporting `Unknown name` for the wrapper's own parameter. Because that tier can re-enter an algorithm body, `Expr.NativeCall` is a RECURSIVE variant with its own `EvalNativeCallAsync` twin (the shared pure `ApplyMathNative` keeps the member set from drifting, and host-built native signatures must match authoritative registry metadata exactly, after argument binding, with malformed counts returning structured errors), never a sync-delegable leaf. A same-named ambient value can never be captured or forwarded to host code in place of the bound argument: every binding path shadows the callee's parameter names out of all three inherited tiers (`ShadowInheritedParameterEnvironments` for the counted and algorithm tiers, `ShadowValEnv` / Lean `ValEnv.shadow` for the value tier). See `docs/design/async-evaluation-2026-08.md` and `Hosting/*Tests`.

## Plain/counted ownership

Plain/counted evaluator ownership: where a plain/counted pair is semantically equivalent, the COUNTED implementation is canonical and the plain implementation is its value projection — first in Lean (`eval` is the one-line total projection of `evalCounted`, which matches every `Expr` variant explicitly with no default arm; the call/dot-call/builtin/lookup plain families are `.fst`/`.alg` projections), then mirrored in C# (`ProjectCountedValue` over the counted twins; the former independent plain call/dot-call/builtin implementations and the resolve-only lookup chain are deleted). Never reintroduce an independently implemented plain evaluator body, and never make a counted function delegate its semantics to a plain one — the deliberate exceptions (C# plain-owned leaves Num/StringLiteral/NativeCall/Grace for the async leaf-delegation contract, the slot-view family, the root-program decoration pair, the opens-free direct lookup used by open resolution) are enumerated in `SEMANTIC-ALIGNMENT.md`.

## Zero-argument property cache

The zero-parameter property cache is observable semantics, modeled in Lean: property-value `A` reuses its first successful entry; explicit `A()` neither reads nor replaces A's entry, and nested property reads retain their own rules. Exported bindings use one entry per declaring scope per run across lexical/structural spellings, calls, callbacks, loops, and opens; never add environment identity to their keys. All keys identify the declaring scope structurally, so rebuilding an owner record alone cannot split an entry. Local-only bindings retain all three binding contexts; fresh calls/callbacks/iterations stay distinct even with equal values. Planned exported temps use the run cache; local-only temps use per-iteration/per-call memoization. The evaluator trusts exposure metadata exactly as open/dot lookup do: host-built captures must declare local-only exposure. The front end charges every MAY-selected fallback using the detector's scope-aware `ElaboratedFallbackSelection`; definite structural winners charge no fallback, and navigated members charge their own requirements (a structural path or an opened name is a `PendingReference` the exposure resolver settles at the owning level with the evaluator's lookup order). The detector's verdict is final: exposure never changes what a name resolves to, so there is no recheck round. Lean assigns declaration identities before execution (`identifyPropertyExpr`, with explicit `shared` identities for host DAGs) and fresh activation identities at `EvalCtx.bindParameters`; ancestor keys identify the declaring scope, not a lookup wrapper. Failed properties are never stored; failed parents do not roll back successful child entries. Re-entrant reads begun before a store finish normally but never replace an already completed first-successful entry. Keep `ZeroArgPropertyCacheScopeTests`, cache-key/loop/exposure tests, `LeanAstEncoderTests`, and CoreTests `zeroArg*` guards aligned. Other implementation-only caches need no Lean mirror.

## Numerics

Lean core numeric semantics use `Int`; the C# runtime uses IEEE 754 `System.Numerics.Decimal128` (34 significant decimal digits) end-to-end — literals parse directly into it, arithmetic and every Math function compute in it natively, and there is no `decimal` or `double` stage anywhere in core numerics. Do not silently widen or reinterpret numeric behavior without checking Lean first. Division/modulo by a zero-valued divisor (the EVALUATED value — `1 / 0`, `1 / (1 - 1)`, `1 / -0`, and an underflowed-to-zero divisor all alike) stays the Lean-modeled `divByZero` error and zero-base powers obey the domain-error policy in `src/KatLang/SEMANTIC-ALIGNMENT.md`; `div` uses `Decimal128Numerics.IntegerDivide`: exact mathematical truncation when representable, otherwise leading 34 digits toward zero for finite IEEE quotients (the consecutive-integer domain is |q| <= 10^34, with sparse larger integers also exact). IEEE division overflow and special values are unchanged; the mathematical div/mod identity requires a representable truncated quotient, and its runtime recomposition also requires exact intermediate arithmetic. Other arithmetic follows Decimal128's IEEE behavior (overflow produces a signed infinity, domain violations produce NaN, NaN/±Infinity/−0 are ordinary values). Structural value equality (`==`, `distinct`, `contains`, ValueComparer) uses `Decimal128.Equals` semantics — NaN is one value, quantum is ignored — while the ordering operators are IEEE (comparisons with NaN are false). Transcendental Math results are quantum-canonicalized (IEEE `reduce`, value-preserving) so exact results like `Math.Lg(1000)` stay `3`; ordinary arithmetic is not quantum-canonicalized, so the Decimal128 operation's result quantum remains visible (`0.5 + 0.5` displays `1.0`). `range` alone canonicalizes accepted whole-number bounds before enumeration: exponent 0 except at ±1e34 (exponent 1), and unsigned zero. Keep this at the shared range-validation boundary; do not normalize other whole-integer arguments. Numeric-change ROUTING is two-tier — the "Core numeric semantics" row in `src/KatLang/SEMANTIC-ALIGNMENT.md` is authoritative: Lean-modeled laws on the COMMON EXACT integer subdomain (exact integer arithmetic/comparison, the representative truncating `div`/`mod` cases, the zero-divisor rule where applicable, `0 ^ negative` at its integer instance — the runtime rejects EVERY exponent below zero, the fractional side is Decimal128-only — structural equality, truth testing) change Lean and C# together with Lean-comparable LanguageSpec coverage, while Decimal128-specific behavior (finite precision/range even for integral inputs, fractional values and quantum, NaN, ±Infinity, signed zero, overflow to infinity, gradual underflow, IEEE ordering of specials, non-exact `/`/`avg` results) is an explicit reviewed model divergence pinned by C# tests plus a canonical C#-only LanguageSpec case with a `LeanExclusionReason`, never a fabricated Lean encoding. Do not classify from source spelling alone: "integer input" is not sufficient once a Decimal128 operation rounds or overflows.

## Seeded randomness

KatLang's random operations — `Math.Random` / `random` and `Math.RandomInt` / `randomInt` — draw from ONE run-scoped random stream, and a host may seed it: `RunOptions.RandomSeed` (engine entry points and every convenience over them, the additional-error evaluation after an evaluable load failure included), the `Evaluator.Run` / `RunAsync` / `RunFlat` / `RunFlatAsync` overloads that take a `long? randomSeed`, and the CLI's `--seed <integer>` for `run` and `eval` (`check` refuses it because it does not evaluate). `null` keeps evaluation UNSEEDED and nondeterministic; every `long` is a valid seed and every distinct value names a distinct stream (the seed's bit pattern is the initial state, never folded, hashed, or truncated). This is host/runtime evaluation configuration with NO Lean counterpart: Lean models neither the Math runtime surface nor native random execution, and seeding changes where the raw words come from, never which calls execute — that is decided by the existing Lean-modeled evaluation rules (left-to-right argument evaluation, once-only written arguments including the patterned-call view, lazy `if` branches, the zero-argument property cache with explicit `A()` re-evaluation, callbacks in sequence order, output rows before the engine's `DisplayDecimals` evaluation). A seed reproduces a stream, it never memoizes: removing an earlier random call generally changes every later value (bounded rejection consumes a variable number of raw words).

The stream is run-scoped MUTABLE state on the run's `EvaluationBudget` (`EvaluationBudget.RandomSource`), constructed EAGERLY at budget creation by `RandomSourceFactory.Create(seed, entropyProvider)` — a supplied seed never consults entropy; an unseeded run reads 8 bytes from `Random.Shared.NextBytes` exactly once (the full 64-bit state domain; `NextInt64()` is deliberately not used) and never touches `Random.Shared` again. Because every copied `EvalCtx` carries the budget by reference, nested calls, callbacks, loop frames, property evaluations, the `DisplayDecimals` evaluation, and async suspension/resumption all share the one stream and none can reset or duplicate it; `ApplyMathNative(name, args, randomSource)` receives it EXPLICITLY from `ctx.Budget` in both `EvalNativeCall` and its `MIRROR OF` async twin, with no optional or static fallback. The stream must never live on `RunOptions`, `EvaluationLimits`, or `HostOperations` (immutable configuration), in a static, thread-local, or `AsyncLocal` slot, or in a cache keyed by seed: reusing one options object for sequential runs replays the stream from its beginning, concurrent runs sharing it get independent stream instances from the same seed, and no lock exists on the source because evaluator access within one run is sequential even when an async continuation resumes on another thread. `EvalCtx.Empty` and every direct `EvaluationBudget.Create` caller that supplies no seed remain unseeded.

The production generator is a KatLang-owned SplitMix64 (`SplitMix64RandomSource`, sealed) with the exact published constants, advance-before-mix order, `hi`-then-`lo` 128-bit composition, and top-incomplete-cycle rejection followed by modulo for bounded draws (a bound of 1 still consumes one word; an invalid bound throws before consuming any); the samplers `SampleRandomUnitFraction` (high 17-digit component, then low, on the exact 10^34 lattice) and `SampleUniformInteger` (exact `Int128` span, `2^128 mod span` rejection) are unchanged by seeding and validate before every draw, so an invalid call consumes nothing. Sync/async routing, optimizer strategies (planned loops with generic random rows, fused `filter`/`count` with a random predicate), and unrelated `EvaluationLimits` settings that leave the program's control flow unchanged must all preserve draw count and order; optimizers are never disabled because a seed is present. The exact stream is reproducible for a given KatLang version across platforms, is NOT promised across versions (a deliberate generator, sampler, or evaluation-semantics change is release-noted), and is not cryptographically secure. The full internal contract, with the seed → state map, the constants, the bounded-rejection algorithm, unseeded initialization, and the version-stability policy, is `docs/design/seeded-randomness-2026-09.md`. `Parser.Parse` / `ParseAsync` ignore the seed; the canonical `LanguageSpec` and `SemanticExplorer` corpora carry no random case. Pinned by `RandomSourceTests` (published SplitMix64 vectors plus an independent BigInteger derivation and the test-side `ReferenceRandomOracle`), `RandomFractionSamplingTests`, `RandomIntSamplingTests`, `SeededRandomnessTests`, `SeededEvaluationOrderTests`, `SeededOptimizerParityTests`, `SeededAsyncEvaluationTests`, `SeededConcurrencyTests`, the `SeededStream` scenario of `ConcurrencyDifferentialTests`, and `CliApplicationTests`.
