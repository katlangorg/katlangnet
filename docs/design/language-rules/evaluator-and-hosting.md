# Evaluator, hosting, and pipeline rules

The full statement of the rules that AGENTS.md carries in compact form — consequences, examples, the implementation map, and the pinning tests — moved here verbatim from AGENTS.md in September 2026. These rules are as binding as AGENTS.md; the compact bullet there points at the section here. Keep both in step: a rule change edits the compact bullet and the section together.

## Elaboration boundary

The individual elaboration passes are INTERNAL implementation stages: `ParameterDetector`, `ImplicitArgumentResolver`, `PropertyExposureResolver`, `FrontEndPipeline`, and `Parser.ParseSyntax` are not host API, and hosts must not be able to compose partial elaboration — a Detect→Resolve tree without exposure resolution leaves every `Property.Exposure` at the default `Exported`, which the evaluator trusts (pinned by `FrontEndElaborationBoundaryTests` and the non-friend `PublicElaborationSurfaceTests`). The supported public layers are `Parser.Parse`/`ParseAsync` and `KatLangEngine` (complete pipeline), `SemanticModelBuilder` over `ParseResult`, and `Evaluator.Run*` direct evaluation of host-built ASTs (as-is, preflight only, no elaboration). Do not re-publicize a stage or add a partial facade; exposure/ownership metadata is trustworthy only after the complete pipeline finishes. (`ModuleLoader` is internal too — load elaboration alone is even more incomplete: a loader-only tree has had no parameter detection, so spliced module algorithms cannot even bind their arguments; hosts get module loading through `Parser.ParseAsync`/`KatLangEngine.RunAsync` with `RunOptions.DownloadCode`/`AllowedHosts`.)

## Source loading and deferred modules

Every error produced by source processing blocks evaluator entry in `Run` and `RunAsync`, including a load failure or invalid downloaded source. Recovery trees remain available to parsing and editor consumers; they are never evaluated to obtain additional diagnostics. This also prevents host calls, random draws, evaluation cancellation checks, and evaluator budget charges after a front-end failure. Deferred modules still materialize when a previously valid program selects their branch; an error there stops that evaluation at the materialization boundary.

Default parse/run entry points reject unresolved `load`; only elaboration-enabled paths may consume it. SOURCE LOADING IS ASYNC-ONLY: the one downloader contract is `RunOptions.DownloadCode : Func<string, CancellationToken, ValueTask<string>>` — and it is the ONLY transport: the library ships no default/ambient HTTP downloader (a `ModuleLoader` cannot be constructed without an explicit delegate; `AllowedHosts` governs load-target policy while transport behavior, redirects included, belongs to the host delegate; blank or null `AllowedHosts` entries must fail closed with `ArgumentException` at sync and async options boundaries; trim valid entries and keep loader matching fail-closed even below those boundaries) — module acquisition awaits it inside `ModuleLoader.ElaborateAsync` (an incomplete download genuinely suspends source processing and resumes it at the same point; the downloader is never replayed), and the elaboration-enabled entry points are the asynchronous ones (`KatLangEngine.RunAsync` + async conveniences, `Parser.ParseAsync(source, options)`). The synchronous source-level entry points remain for downloader-less configurations only and reject a downloader-configured options object with `InvalidOperationException` before parsing (enforced in the synchronous `FrontEndPipeline.Process(source, RunOptions?)`) — never a blocking sync-over-async bridge. Parsing and all other elaboration passes stay synchronous CPU work. Loader traversal is routed: load-free subtrees take the calibrated synchronous walk unchanged; load-bearing spines (marked by a linear pre-scan) take `// MIRROR OF`-tagged async twins; clause families are handled by ownership (B2c, branch-lazy module loading): a family-owned open list is shared by every alternative and elaborates eagerly, while each alternative branch body that owns an unresolved load is a DEFERRED module-elaboration region that initial elaboration never descends into — its modules are fetched, elaborated, and budget-charged only when evaluation selects that branch (`DeferredModuleRegion.MaterializeAsync`, at the conditional-call selection boundary in the async evaluation family), nested alternatives inside it staying deferred, a never-selected branch performing zero module work, and a tree carrying deferred regions requiring the async evaluation entry points; the region is CARRIED by the placeholder body that stands for it (`Algorithm.DeferredRegion`, an equality-transparent record slot copied by `with`, never a side table keyed on body identity and never a root mark): the loader clones one placeholder per deferred branch OCCURRENCE (two branches sharing one raw body get two regions while their placeholders keep the body's one `Declaration` — region identity is not declaration identity), each rewriting front-end pass installs a fork of the region it found (the same occurrence plus its own context) on the output view it produces, the non-rewriting declaration validator records its bindings in place, every ordinary `with` view — parent wiring, parameter replacement, a host copy, the flat-binder equivalent — shares the region object and its one materialization, and routing is answered by walking the tree to the first placeholder (`DeferredModuleRegion.RequiresAsyncEvaluation`); a deferred materialization is OWNED by the evaluations that selected it — concurrent selections share one underlying run, a cancelled evaluation leaves at once with its own token's identity, and the run's download and elaboration are cancelled (linked with the source-processing token, which stays authoritative and keeps its identity) exactly when its last consumer leaves, caching nothing, while ordinary eager loads observe only the source-processing token; the scan and both walks carry a per-level stack-reserve backstop that turns residual exhaustion into the structured `ModuleElaborationStackExhausted` diagnostic. Downloader error semantics are unchanged (thrown or faulted-awaitable exceptions → `load: failed to fetch` unless the source-processing token is cancelled, which stays authoritative). See `docs/design/async-evaluation-2026-08.md` and `ModuleLoaderAsyncTests`.

LOAD-TARGET ADMISSION AND MODULE IDENTITY (#13, September 2026; C# host policy, no Lean counterpart). `ModuleLoadTarget` is the ONE owner of which source-written targets reach the downloader, decided before it is invoked on the target as `System.Uri` parses it — never on the written text: an absolute `https` URL; NO user information (refused, and never echoed — it is a credential); a host that is a DNS name with a valid IDNA form or an IPv4/IPv6 literal (an IPv6 zone index is refused); and an allowed host. The allow-list compares CANONICAL forms on both sides — DNS names in lower-case ASCII IDNA form (`Uri.IdnHost`, the form every transport resolves), admitted by equality or as a whole-label subdomain; IP literals in canonical text, admitted by equality only — so letter case and Unicode/punycode spellings of one name match, a trailing dot stays significant (fail closed), any port of an allowed host is admitted, and an entry that is not a bare host admits nothing. Matching the raw Unicode `Uri.Host` is forbidden: it admitted names such as `evil.test` + U+FF0F + `.katlang.org` whose TEXT ends with an allowed suffix while the name has no DNS form, and forwarded them to transports that may NFKC-normalize the authority into another host. An admitted target becomes its CANONICAL MODULE URL — `https://`, the canonical host, the port when not 443, the escaped `PathAndQuery`, no fragment (RFC 3986 §3.5: never sent), printable ASCII, verified to re-parse to itself — and that one string is the module's identity: the per-URL cache key, the cycle key, the exact text `DownloadCode` receives, and the name every diagnostic uses. Every downloader INVOCATION consumes one module slot, committed immediately before the call and kept whatever the call returns; aggregate source is charged for text accepted for parsing and for every further splice of a cached module (next paragraph); failed and rejected fetches are still retried by another load site but each retry is charged, so `MaxModuleCount` bounds downloader invocations per run (formerly failures were free and a 2 MiB source could drive ~70k requests); host cancellation releases only the active frame's aggregate-source reservation, never the charge for a downloader invocation that already occurred. This also bounds retries across evaluations of one parsed tree. Deferred-branch materializations use the same loader, policy, cache, and budget, so a parse result's budget is shared by every evaluation of that tree. Malformed targets containing an at sign are omitted from diagnostics because their credentials cannot be safely isolated; explicitly empty userinfo is refused too. Other invalid targets are quoted bounded to 200 code units with every code unit outside printable ASCII as `\uXXXX` (a lookalike never reads as the delimiter it imitates), and a downloader exception message bounded to 500 with its control, format, separator, and unpaired-surrogate code units escaped. What KatLang cannot see — redirects, DNS answers, resolved addresses, proxies — is the downloader's responsibility, so `AllowedHosts` is a source-host policy, not an SSRF defense on its own; downloaded code runs with the run's host operations. `ModuleLoadingSecurityTests`, `SourceProcessingLimitsTests`.

SPLICES CHARGE THE AGGREGATE (September 2026; C# host policy, no Lean counterpart). A module's names resolve against the scope it is spliced into, so the front end elaborates a cached import view once per enclosing scope — each splice in a distinct scope is a distinct semantic region of the Shared-DAG guarantee — and before this rule a cache hit charged nothing: a 10 KB module spliced into 373 distinct blocks cost 3.2 GB of allocation and 5 s, work growing with the PRODUCT of the root's and the module's sizes (terabytes at the per-source ceilings), and every copy re-reported the module's front-end diagnostics, which no per-source ceiling bounded. Every module-cache entry therefore records the module's ELABORATED WEIGHT (`ModuleLoader.CachedModule.Weight`: the aggregate its own fetch and elaboration charged — its source, plus its nested downloads and nested splices), and every cache-hit splice reserves that weight against `MaxAggregateSourceLength` before splicing; a splice that does not fit is refused at its site with `AggregateSourceLengthExceeded` (wording `load: splicing the already loaded '…' again …`) and the load's established `Num(0)` placeholder — no module slot, no download. Weights compose, so the aggregate bounds the ELABORATED program: a view whose own walk spliced its dependency K times and that is itself re-spliced J times charges J times its full weight. A repeated load in the SAME scope is charged as well (the front end elaborates it once there — conservative and simple). A walk frame's splice charges are recorded on its `SpliceLedger` — part of the loader's walk context, one per frame: the root walk (`ElaborateAsync`), a fetched module's nested walk, and a deferred materialization — and observed host cancellation that abandons the frame releases them together with the frame's own source reservation, so a cancelled materialization can be retried without draining the aggregate; completed nested frames keep their charges, as their source always did, and downloader invocations stay charged. `SourceProcessingLimitsTests.CachedRepeatedModule_IsDownloadedOnce_ButEverySpliceChargesTheAggregate`, `DiagnosticBudgetTests` (`DistinctScopeSplices_*`, `SpliceWeight_*`, `CancelledMaterialization_*`), `ModuleLoaderCancellationTests`.

## Bounded diagnostic lists

BOUNDED DIAGNOSTIC LISTS (September 2026; C# host policy, no Lean counterpart, no language-semantics change). Malformed source produces up to one diagnostic per UTF-16 code unit — a bad character, a stray closer, a semicolon — so, measured before this rule, one 2 MiB source kept 2.1 million diagnostics (up to 464 MB retained, three times what the largest valid program retains), a `;` flood rendered 400 million characters, 699,048 refused `''` targets fit in one maximal root, and `KatLangException.Message` and the CLI `check` loop rendered every one; real non-KatLang files pasted as source report 30–130 per thousand code units. `DiagnosticBag` is the ONE accumulator of one diagnostic LIST: a parse — `FrontEndPipeline` creates it from the run's `SourceProcessingBudget`, and the lexer, the parser, the load guard, the module loader with every module and nested module, and every elaboration pass report into it — or one demand-time materialization of a deferred branch, which gets its own bag from the loader's budget (it becomes that evaluation's `ModuleRegionMaterializationFailed` error; nothing accumulates across attempts or in loader state). Its capacity is `SourceProcessingLimits.MaxDiagnosticCount` (public; default and hard maximum `MaxSupportedDiagnosticCount` = 1000; only lower requests take effect, above-maximum ones clamp, non-positive ones throw). THE PREFIX LAW: a list keeps exactly the first N diagnostics the unbounded operation would report, in reporting order, then — only when more were reported — ONE `DiagnosticCode.DiagnosticCountExceeded` marker: unpositioned (a fact about the list, never about a place in the source), not counted toward N, and carrying the most severe dropped severity (an error for every KatLang diagnostic), so a truncated list always blocks evaluation and truncation never changes whether a list does. A report past N is COUNTED and dropped: no `Diagnostic` is constructed, and the high-volume sites never format a dropped message (the lexer's formatted messages go through the lazy `Report<TState>`; the densest parser flood, stray root closers, uses constant messages). OBSERVATIONAL IRRELEVANCE: every decision reads the bag's counters, never its stored list — clause-head recovery (`ReportedCount`; the lexer hands the parser `lexicalErrorStarts`, recorded for every lexical error whether stored or not, replacing the former binary search over stored lexical diagnostics), the module cache (a module is cached only when `ReportedErrorCount` did not move across its nested walk), failed-module-parse classification (`HasReported(NestingTooDeep | AstDepthLimitExceeded)` on the module's own bag), and materialization success (`HasReportedErrors`) — so the recovery tree, downloads, caching, classification, and evaluation gating are identical at every capacity. Processing continues after exhaustion: its remaining work is the linear source traversal the source-length ceilings already bound (measured 85–590 bytes per code unit past the limit — tokens and the recovery tree — against about 1.8 KB for valid source), and stopping early would have made downloads and the editor's recovery tree depend on the budget. STAGES: a pass whose reports ownership completion may discard and replace — parameter detection and implicit-argument resolution, in the pipeline and in a materialization — reports into `CreateStage()` bags of the same capacity, committed by `AddRange(DiagnosticBag)` exactly as if reported directly (its dropped count included), so a live stage never stores more than one list could. A loaded module's own parse (summarized as one diagnostic at its load site) uses a bag of the run's capacity. BOUNDED PAYLOAD: every stored message is at most `DiagnosticBag.MaxRetainedMessageLength` (4096) UTF-16 code units (a longer one keeps its surrogate-safe prefix and `…`), and text a diagnostic repeats PER REFERENCE is bounded where it is formatted, reading only what it shows: the parameter list of an open target that requires arguments (`ExprNameRenderer.BoundedJoin` over the lazy `ParameterPattern.EnumerateCaptures`, at most 512 declarations examined), the family name of a conditional-branch undeclared identifier (`ExprNameRenderer.BoundName`), and the names of a blocked strict-value forwarding — each had been quadratic (32 KB of source rendered 162 million characters). LINEAR WORK BEHIND THE REPORTS: bounding what a list keeps does not bound the work of deciding what to report, so three analyses a flood drove super-linearly are linear, each pinned by a deterministic traversal observation: parameter detection finds the first written span of EVERY undeclared name of a closed body or branch in ONE walk (`ParameterDetector.FindFirstResolveSpans`, `DetectorSpanSearchExpansions`; a walk per name was quadratic — 200 KB of `u{i} + 1` rows took 11 s, now 0.44 s); implicit-argument resolution judges closed-list forwarding ONCE per callee pattern list and region (`ResolverWalkMemos.MissingForwardingNames`, deduplicated through a set, `ResolverForwardingVerdicts`; judged per reference, twice, with a list-scan dedup it was cubic — 64 KB of `abs(G)` references to a wide `G` took 215 s, now 0.25 s); and the parameter/property collision validator memoizes a node's visited contexts by an INTERNED context id (`ParameterPropertyCollisionValidator.ContextId`: the name-set content key is hashed once per bindings instance, `CollisionContextInterns`; hashing it at every node made one algorithm of P parameters quadratic, valid programs included — 524 KB of `G = v0, v1, …` took 6.8 s, now 0.48 s). The public `Lexer.Tokenize` keeps every token and bounds its diagnostic list at the supported maximum. Downstream renderers — `KatLangException.Message`, `RunResult` display, the CLI `check` loop, a materialization failure's joined message, a host's serializer — are bounded by the list, so no renderer carries a cap of its own. Measured after, at 2 MiB: 1,001 diagnostics and 0.1–0.2 MB retained for lexer and parser floods, exception text at most 199,970 characters. Hosts detect truncation by the code, never by the message. `DiagnosticBudgetTests`, `SourceProcessingLimitsTests`, `RootStrayCloserRecoveryTests`, `ModuleLoadingSecurityTests`, `KatLangErrorCodeTests`, the CLI `DiagnosticFlood_PrintsOneBoundedList`.

## One coordinate space per result

Every source span exposed in the result of processing a document — a `Diagnostic.Span`, an `EvalError.Span`, a `KatLangError.Span`, a semantic-model site — belongs to THAT document's coordinate space (September 2026, public API cleanup Task 3a). `SourceSpan` carries no source identity, so this is the only way a span can be meaningful: a module a document loads is parsed as its own document by the loader (`Parser.ParseSyntax` on the fetched text, positioned in the MODULE's text), but the tree that crosses into the loading document's result is the module's IMPORT VIEW — the same declarations with every source location removed (`ModuleLoader.ToImportView`, the ONE boundary: applied once per fetched module, after the module's own structural preflight and before its nested loads are elaborated or it enters the per-URL cache, so every splice — first or cached, eager or deferred — shares one caller-independent locationless instance; `Expr.Span`, `DotCall.MemberSpan`, `SequenceSpread.SpreadMarkerSpan`, `Property.DeclarationSpans`, parameter and collect-marker spans, and binder-pattern spans are cleared, while declaration identity, deferred-region and provenance slots, deconstruction metadata, exposure, and the written-list bit are carried through the record copy, sharing preserved and a spanless subtree returned as the same instance). The module's OWN parse outcomes never leave the loader in module coordinates: a parse error is one `InvalidLoadedSource` at the load site, and a non-error module parse diagnostic is re-anchored at the load site under its `[while loading url]` prefix. A construct inside the view is then reported at a location the CURRENT document supplies, never at a module-relative coordinate and never at a fabricated sentinel: (1) evaluation errors through the existing attach-if-missing law (`Evaluator.AtSpanIfMissing` / `WithSpan`: an error keeps its own span, acquires the enclosing expression's span only when it has none, and stays spanless when no enclosing expression has one), which positions a module runtime error at the demanding local expression — the reference, dot call, or call the document wrote — for direct, nested, chained-module, and deferred-branch demands alike; (2) loader diagnostics for a load written INSIDE a module (a failed fetch, a cycle, a policy or budget rejection, a nested parse failure) at the IMPORT SITE — the span, in the current document, of the outermost load directive through which that content was demanded (`ModuleLoader._importSite`, part of the swappable walk context; a deferred region records the site its body was reached under, `DeferredModuleRegion.ImportSite`, and its materialization restores it), while the spliced node itself keeps only the load call's own span; (3) front-end diagnostics raised against imported content — a declaration collision, an undeclared identifier in a closed list or branch, a refused open provider, an ineffective Grace marker, a parameter-owned open head, a refused strict-value forwarding — at the import site the pass reached the view through (`ImportSite.OfBlock` for `load('…')` / `open '…'` in expression position, `ImportSite.OfProperty` — the declaring name — for a property whose direct value load elaboration made the module; a nested view inherits the enclosing site; every pass tracks the site as walk state — `DetectionRun.ImportSite`, `ResolutionRun.ImportSite`, the validators' field — consults it exactly where a diagnostic's own span is absent, and a demand-time pass over a deferred body starts from the region's recorded site); (4) provenance notes (`ImplicitParameterProvenance.Span`) for a promotion inside imported content are simply spanless, so the rendered message states the inference without a coordinate while keeping the receiver-aware wording and suggestion (the former `CanPositionAtOrigin` in-module flag is gone), and `ParameterPropertyCollision` names a parameter's position only when the document wrote it. Local diagnostics are positioned exactly as before: the rules above act only where a span is ABSENT. Consequences: no production code keys `SourceSpan` by reference identity (the validators dedup by declaration/target NODE; the semantic model's by-reference module span set is gone — see `editor-semantics.md`), which is what let `SourceSpan` become a value type (Task 3b, next section) without any semantic change; structural rejections of a spanless node are positioned at the nearest positioned ancestor on the preflight's path (`AstStructuralPreflight.SpanOf(node, frames, frameCount)`); and because spans decide NOTHING about elaboration, the hoisted deconstruction right-hand side carries its written row index structurally (`Algorithm.User.AssignmentDeconstructionRowIndex`, merged by `AstHelpers.WrittenRows`), so a module's implicit-parameter order survives its locationless import. NOT modeled: no source identity (`SourceId`, source table, cross-file navigation into module text). Lean has no counterpart: source locations are C# diagnostic metadata. `ModuleCoordinateSpaceTests`, `ModuleLoaderTests`, `BranchLazyModuleLoadingTests`, `SemanticModelTests` (`ModuleProvenance_*`).

## Explicit value-type source locations

A location is either a real half-open source span or it is absent (September 2026, public API cleanup Task 3b). `SourcePosition` is a `readonly record struct` of a 1-based `Line` and a 1-based `Column` (UTF-16 code units from the start of the line, the lexer's contract: `\n` ends a line, `\r` advances nothing, a surrogate pair is two columns), ordered lexicographically by line then column (`IComparable<SourcePosition>`, the comparison operators, `Min`/`Max`); its constructor rejects any coordinate below 1. `SourceSpan` is a `readonly record struct` of two positions, the HALF-OPEN range `[Start, End)`: `Start` is the first covered coordinate and `End` the first coordinate AFTER the covered text, so `[1:1, 1:2)` covers one code unit, `[1:1, 1:1)` is a valid EMPTY span (an insertion point: the end-of-input diagnostic, a missing token, the parser's zero-length recovery marker), and the invariant is `Start <= End` — an inverted range or a zero coordinate is an `ArgumentOutOfRangeException` at construction, whether built from two positions or from four integers. `Contains(position)` is `Start <= p < End` (start included, end excluded, an empty span contains nothing, two spans sharing a boundary never both contain it, multi-line ranges compare lexicographically), `Union` is the hull (min start, max end; an empty operand still extends the hull to its position), equality and hashing are by value, and there is no reference identity anywhere: nothing keys a location by object. `ToString` renders `[1:1, 1:6)` and an empty span as `[1:6]`; the user-facing `KatLangError.ToString` (`[line:column] message`) and every provenance rendering print the START coordinate only, so half-open ends never surface as an inclusive-looking display. ABSENCE IS `null`: every location that can genuinely be missing is a `SourceSpan?` — `Diagnostic.Span` (a whole-document limit such as `SourceLengthExceeded`, `AggregateSourceLengthExceeded`, or `ModuleElaborationStackExhausted`, and a diagnostic against imported content with no import site, are unpositioned), `EvalError.Span`, `KatLangError.Span`, every AST span (`Expr.Span`, `DotCall.MemberSpan`, `SequenceSpread.SpreadMarkerSpan`, parameter and collect-marker spans, binder `NameSpan`s; a collection such as `Property.DeclarationSpans` holds real spans only and spells absence as emptiness), `ImplicitParameterProvenance.Span`, the import sites — and no sentinel coordinate exists any more (the former `(1,1,1,1)` / `(0,0,0,0)` fallbacks are gone; a real span at line 1 column 1 is a real location). The struct's `default` value (all coordinates 0) is NOT absence and NOT a location: the constructors refuse it, `SourceSpanValidator` reports it, and no production code reads a default span as meaningful — a `SourceSpan?` is the only spelling of "no location". ABSENCE MUST NEVER BE *MANUFACTURED* INTO A LOCATION (F2, September 2026): because the element type is a value type, a default-returning query over a collection of spans — `FirstOrDefault`, `SingleOrDefault`, `LastOrDefault`, or any generic helper instantiated at `SourceSpan` — turns emptiness into `default(SourceSpan)`, which the surrounding `SourceSpan?` then carries as a PRESENT location rendering `[0:0]` and, worse, satisfies the attach-if-missing law so no real enclosing span can ever replace it. `Property.DeclarationSpans` is the one such collection a location is read from, and `Property.FirstDeclarationSpan` (`Count == 0 ? null : [0]`) is its ONE reader — used by the generic zero-argument property access and its async twin, the top-level property demand and its async twin, the planned loop temporary (`LoopTempPlan.DeclarationSpan`), `KatLangEngine`'s `DisplayDecimals` anchor, and `ImportSite.OfProperty`. A spanless property is the ordinary case, not an anomaly (a deconstruction's hoisted `$deconstruct$N` source, a module's locationless import view, a prelude or host-operation binding, a host-built node), so its refused invocation stays spanless and takes whatever legitimate location the current document later attaches. `AbsentSourceLocationTests` pins the invariant on the structured `KatLangError.Span` and the rendered diagnostic across the deconstruction, planner, host-built, imported, sync and async paths, and fails the build on any new `Spans.*OrDefault(` in `src/`. Human coordinates and source-text OFFSETS are different concepts and stay separate: `Token.Position`/`Token.Length` are the UTF-16 offset model, and `Token.Span` is DERIVED from them on every read (`[Line:Column, Line:Column + Length)`; no token spans a line break, so the end column is exactly `Column + Length`; the end-of-file token and the parser's zero-length `Bad` marker are empty spans at their position, while a lexer `Bad` token covers its real width — two columns for an unexpected surrogate pair). The lexer's diagnostics are the offending token's own span; the parser positions every diagnostic at a token extent or at the hull of the tokens it names (`Parser.ReportErrorAt` / `ReportErrorAcross` / `ReportErrorFrom`), never at a width-1 fiction past the text. The attach-if-missing law is exactly the Task 3a law under nullable semantics (`Evaluator.AtSpanIfMissing`: inner span present → keep it; inner absent and outer present → attach the outer; both absent → stay absent) with no default-value check. `KatLangError` carries the ONE structured `Span` and no flattened `StartLine`/`StartColumn`/`EndLine`/`EndColumn` channel (a removed public surface; the same for `SourceSpan`'s former `StartLineNumber`/`EndColumn` record members and the `(int line, int column)` semantic-model queries, which take a `SourcePosition`: `FindResolutionAt`, `FindPropertyAt`, `FindScopeAt`, `GetVisibleSymbolsAt`; a site contains its first column and not the column past its last character). An editor mapping to a zero-based, end-exclusive range (Monaco) converts the BASE only (`Line - 1`, `Column - 1`, or none for Monaco's own 1-based ranges) and never adds one to the end again. FRAME-SIZE DISCIPLINE is the one implementation consequence: a span is a 16-byte value (20 as `SourceSpan?`), and reading it eagerly in a recursive frame — a hidden return buffer plus an argument or initializer copy per site — measurably fattened the parser, loader, front-end, and evaluator frames whose 1 MiB envelopes are calibrated (up to +38% for the parser's worst shapes and +31% for the loader, which crossed its `MaxTraversalDepth` gate). Every calibrated recursive frame therefore holds no span temporaries: the parser builds span-carrying nodes and diagnostics in `[MethodImpl(NoInlining)]` leaf helpers (`NumAt`, `ResolveAt`, `BinaryFrom`, `CallFrom`, `ReportErrorAt`, … — `Parser.LeafFrame`), the module loader and the front-end rewriters copy nodes with `with { Child = … }` so the record copy constructor carries the span, and the evaluator's dispatch arms position errors lazily (`WithSpanOf`, `WithPreferredSpanOf`, `ReserveSequenceCaptureAtRows`, `AtFirstSpanIfMissing`, `CalleeResolutionFailure`, `EvalParamCountedOf`/`EvalResolveCountedOf`) so the frame carries a node reference, not a span copy; the measured envelopes after this discipline are at or below their pre-Task-3b values in both configurations. Lean has no counterpart: source locations are C# diagnostic metadata. `SourceLocationTests`, `SourceLocationPublicSurfaceTests` (consumer compile probes: the retired spellings fail to compile with the named errors, the new surface compiles), `TokenTests`, `LexerDiagnosticSpanTests`, `ParserDiagnosticSpanTests`, `RootStrayCloserRecoveryTests`, `Utf16LexerContractTests`, `ModuleCoordinateSpaceTests`, `AbsentSourceLocationTests`, the `AstStructuralDepthProcessTests` and `ConcurrencyDifferentialTests` stack envelopes.
ABSENCE IS FOR WHAT CANNOT BE POINTED AT, NOT FOR A PATH THAT FORGOT TO POINT (September 2026). The law's other half: a WRITTEN slot is precisely locatable, so its failure must carry its location. `EvalExplicitSequenceValueExprSlots` (and its `MIRROR OF` async twin) is the written-slot dispatcher used by list literals and by nested groups inside them, and only its two UNFOLDING arms — a nested `Expr.Capture` and a zero-argument `Expr.AlgorithmExpr` — bypass `EvalCounted`, which positions every arm it owns. Every other element kind fell through to `EvalCounted` and was located, so exactly the block-shaped elements lost their position: `[1, { }, 3]` reported `Algorithm has no defined output.` with NO span, while the same element in a parenthesized group (`(1, { }, 3)`, which reaches `EvalCounted`'s own Capture arm) was located at the block. Both arms now apply the very rule `EvalCounted` applies to the same node — `WithPreferredSpanOf`: the written node's own span, else its first positioned output row — so the list and the group agree exactly, and `AtSpanIfMissing` keeps a span the inner failure already carries, so a nested slot reports at its own precise location rather than at the enclosing one (`[1, [2, { }], 3]` and `(1, [2, { }])` both name the inner `{ }`). Diagnostic POSITION only: error kinds, structured payloads, rendered messages, values, and emitted counts are unchanged, genuine absence is still absence (a host-built element with no span of its own stays unpositioned rather than borrowing the list's), and Lean models no source locations at all. `AbsentSourceLocationTests` § 7.

## Structural depth and parser budgets

Structural AST depth is a C#-only host-safety policy: every entry point that hands a preconstructed or parsed AST to recursive consumers (evaluator `Run*`, `ParseSyntax`, front-end elaboration, the standalone `ParameterDetector.Detect` / `ImplicitArgumentResolver.Resolve` / `ModuleLoader.Elaborate` boundaries, `SemanticModelBuilder`) must run the iterative `AstStructuralPreflight` FIRST, and a new AST node variant must be added to its child enumeration (the `Expr` half, `TryGetExprChild`, is compiler-exhaustive over the closed hierarchy; any other unknown node kind fails loudly; the variant-owned `Algorithm` collections are enumerated through the internal total accessors, so every variant contributes exactly the collections it owns). The shared `AstWalker.VisitExpr` switch statement keeps a fail-loud guard for the same reason — an unhandled variant would be silently skipped by every walker subclass — and `AstWalkerTraversalTests` pins every declared `Expr` variant's child visits. Two non-raisable tiers: fat-frame consumers (evaluation, front-end elaboration incl. the standalone detector/resolver entry points, semantic modeling) use `EvaluationLimits.MaxSupportedAstDepth`; the small-framed walker-class raw-syntax passes and the measured module-loader traversal use `AstStructuralPreflight.RawSyntaxMaxAstDepth` (the loader also bounds nested module loads CUMULATIVELY against that ceiling — a load site's own traversal depth counts against the module it loads). `MaxAstDepth` may only lower the evaluation tier. ## Shared-DAG guarantee

Host ASTs may legally contain SHARED acyclic subtrees (a node referenced from several parents; cycles stay preflight-rejected), and module elaboration itself splices one cached module algorithm at every load site of the same URL. The front-end passes (`ParameterDetector`, `ImplicitArgumentResolver`, `PropertyExposureResolver`, `PropertyDependencyGraphBuilder`, `ModuleLoader` incl. its load-bearing pre-scan, plus the `LoadElaborationGuard`/`FinalPropertyExposure` helper walks) are DAG-SAFE: every walk carries a run-local REFERENCE-IDENTITY memo per constant-context region, so work is bounded by distinct reachable nodes rather than root-to-node paths wherever semantics permit, and rewritten output preserves sharing within one context. Semantics stay tree-equivalent (grace weights accumulate per semantic occurrence through memoized ordered weight effects); the deliberate per-NODE behaviors are diagnostic multiplicity within one diagnostic context and load-site identity within one constant loader context. Load-bearing loader keys include effective live traversal depth because near-ceiling admission is path-sensitive; the same node reached at two such depths intentionally splits. The `ModuleLoader` memo checks live INSIDE the calibrated walk frames — never add a wrapper method or extra async state machine to its recursion spine. A new memoized traversal must keep its explicit variant switch (the memo wrapper adds no dispatch); pinned by `FrontEndDagComplexityTests` and the `AstGraphFuzzTests` front-end shared-vs-cloned campaign. SHARED-DAG GUARANTEE: a legal shared acyclic AST is processed with work bounded by distinct nodes × distinct semantic regions, and traversal-path multiplicity affects neither results, nor diagnostics, nor asymptotic work. Spliced module content is where source multiplies the REGIONS: each splice of one cached view into a distinct scope is a distinct region, so every cache-hit splice charges the view's elaborated weight against the aggregate source ceiling (§ Source loading and deferred modules, SPLICES CHARGE THE AGGREGATE) — regions × nodes of module content stay bounded by `MaxAggregateSourceLength`, not by the product of two source sizes. Region keys are the minimal complete semantic context, run-local, node/scope identity by reference and name sets by content: detector branch bodies (parent scope, binder set, captured names, reporting mode); resolver nested algorithms — property values, block literals, open targets, branch bodies alike — (the signature SNAPSHOT of the algorithm's FREE reference names in the visible map, the closed binder specification for a branch body, reporting mode); exposure (the region's final visible summaries); summary channel (node, or body plus binder set); order channel (node, shadow context, position); loader (load context plus effective live depth); the editor's `Semantics/SemanticModelBuilder` (node plus scope frame; algorithms additionally plus a branch's binder table). Family-worded diagnostics are stored as templates and replayed per family sharing a body (`same node + same region → reused; same node + different region → independently processed`). Sibling-dependency edges are COMPLETE — every value-position sibling reference in a property's whole value subtree, nested bodies and branch bodies included, with a nested body's own names shadowing and neutral arguments/capture rows transparent — so sibling declaration order is not observable. Explicit exceptions, occurrence-oriented by design (see `SEMANTIC-ALIGNMENT.md`): the semantic model analyzes a body once per family that declares its own binders; a sibling CYCLE resolves its order by declaration order, the one way two reaches of a node can observe different sibling signatures; the loader splits by depth near the ceiling.

SHARED IMPLICIT ARGUMENTS (FE-2, September 2026; C# front-end representation/performance, NO semantic change and no Lean counterpart). ## Traversal exhaustiveness

`Expr` is a C# `closed` record hierarchy (`Ast.cs`): its direct descendants are exactly the sealed nested variant records, mirroring Lean-modeled forms plus the front-end/native-only forms, and the compiler knows the set is finite. A switch EXPRESSION over `Expr` that names every variant is therefore proven exhaustive by the compiler with no catch-all arm, and because `CS8509` (a non-exhaustive switch expression) and `CS8655` (an unhandled `null` input) are errors in `src/KatLang` and `tests/KatLang.Tests`, a missing variant fails the BUILD at every such dispatch, naming the variant it does not cover. Every full-hierarchy dispatch that is naturally expression-shaped is written that way, with no `_ =>` arm: the structural preflight's child enumeration (`AstStructuralPreflight.TryGetExprChild`), the evaluator dispatch trio (`Eval`, `EvalCounted`, and its `// MIRROR OF` twin `EvalCountedAsync`, whose enumerated sync-delegable leaf group — Num, StringLiteral, Grace — is the one place a variant may run through the synchronous leaf core; `NativeCall` is NOT one: its declared-argument reads are ordinary `Expr.Param` value reads, so it has its own async twin case), `ResolveAlg`, `ExprKind`, the static structural-member classification (`AstHelpers.ResolveStaticStructuralMemberProvider`), and every REWRITING or SEARCHING front-end walk (`ParameterDetector` — ClassifyOpenTargetHeads, ProcessOpenExpr, RewriteParams, ProcessExpr, SpanSearchChildren; `ImplicitArgumentResolver` — ProcessOpenExpr, RewriteImplicitCalls, ProcessExprNested; `PropertyExposureResolver.RewriteExpr`; `PropertyDependencyGraphBuilder.CollectSummarySeed`; `ModuleLoader.ProcessExpr`). Multi-statement arms are extracted into named helpers so the dispatch itself reads as a table; a helper that CONTAINS a recursive evaluation adds one frame per nesting level and is admitted only where the calibrated depth pins (`AstStructuralDepthProcessTests`) still hold. The compiler cannot check a switch STATEMENT, so the eight side-effect walks whose arms are inherently statement-shaped — `AstWalker.VisitExpr`, `ParameterDetector.CollectFreeParams`, `ImplicitArgumentResolver.CollectReferenceNames` / `CollectImplicitDeps`, `PropertyDependencyGraphBuilder.CollectSiblingDependencyIndices`, `ModuleLoader.ProcessExprAsync` (its awaiting loops must stay inside the one calibrated frame), the iterative `Parser.ScanPendingForGraceSpan`, and `SemanticModelBuilder.VisitExpr` — enumerate their intentional leaves explicitly and keep a runtime guard that THROWS `InvalidOperationException` on an unhandled variant; never add a silent `default: break` to one of them, and never force one into an artificial value-returning switch expression. Deliberately PARTIAL classifiers with a semantic "other" arm (`ResolveAlgForOpen`'s `BadOpenForm`, `ZeroArgumentValueDemandError`'s anonymous shape, the loop planner's "unsupported → generic path", the parser's open-form normalization, the expression-spine machines' non-spine guard, `ExprNameRenderer`'s fallback spelling) are not full-hierarchy dispatches and keep their defaults. Tests cover what the compiler does not: `AstWalkerTraversalTests` pins the walker's per-variant child visits, `FrontEndTraversalTests` pins the runtime-guard matrix of the statement-form walks plus intentional-leaf reference identity and per-pass recursive-child semantics, and `AsyncEvaluation/AsyncExpressionDispatchTests` pins per-variant sync/async outcome equality and per-recursive-variant async-seam routing with genuine suspension. The ONE test-side variant enumeration is `tests/KatLang.Tests/ExprVariantCatalog.cs`; the behavioral tables above (and the static-classification and Lean-encoder sample tables) are ratcheted against it so a new variant fails a test until it has a row, because a present-but-childless arm is compiler-exhaustive and still wrong. ADDING AN `Expr` VARIANT therefore means: satisfy the compiler at every exhaustive dispatch (each error names the variant), classify it in the eight guarded walks, and give the behavioral tables a row.

The same contract covers every KATLANG-OWNED FINITE VARIANT HIERARCHY (September 2026): `RunResult` (`KatLangEngine.cs`), `EvalError`, `Result`, `Algorithm`, `Pattern`, `ParameterPattern`, `CallableBindingNode` (`Signatures/CallableBindingPlan.cs`; internal since the September 2026 public API audit, like the rest of the evaluator's signature and binding planners), and `ErrorContext` (`ErrorContext.cs`) are `closed` records exactly like `Expr`. Each is a finite set KatLang itself defines — `Algorithm`, `Pattern`, `ParameterPattern`, `Result`, and `EvalError` mirror Lean inductives, `RunResult` and `CallableBindingNode` are C# host/binding shapes, and `ErrorContext` is the typed C# refinement of the free-text `String` in Lean's `withContext` — and none is an extension point: a `private` or `private protected` ordinary constructor had never closed them, because a record's synthesized copy constructor is `protected`, so `sealed record Rogue(RunResult o) : RunResult(o)` compiled from another assembly and could reach a production "unknown variant" fallback (`ErrorContext`, which declares no constructor at all, was derivable through its synthesized protected ordinary constructor as well). With `closed`, a foreign derivation is `CS9382` and a switch expression naming every variant is compiler-exhaustive, so the former unknown-variant arms are gone: `RunResult.RenderDisplay`, `KatLangEngine.EvaluateToAtoms(Async)`, and `OutputFormatter.RenderDisplay` (a switch statement converted to an expression around a `RenderSuccess` helper); `EvalError.Code` (context wrappers are unwrapped iteratively before the exhaustive terminal dispatch) and `KatLangError.FormatEvalError`, whose `_ => error.ToString()!` had been silently rendering `DuplicateProperty` and `DuplicateBranchPattern` — evaluator errors reachable only from host-built trees — as record `ToString()` text, now given messages; `Result.ToItems`/`AsNum`, the evaluator's `ResultToExprLeaf`/operand and item descriptions, and the structured layout's block-line test; `Algorithm.WithParent`/`WithParams`/`IsFunctionShapedAlgorithm`, `CallableSignature.FromAlgorithm`, `PropertyExposureResolver`, `PropertyDependencyGraphBuilder.CollectAlgorithmSummary` (statement converted to expression), and the semantic model's property-info construction (whose `null or Algorithm.Builtin` arm keeps the nullable input honest); the pattern matchers `MatchPattern`/`MatchCountedPattern` (statements converted to expressions around bind/sequence-value helpers — Lean's `matchPatternInto` is the same total match) and the branch-head formatter; `MissingCapturePattern`, `BuildPatternArgument`, `CallableBindingPlan.CreateNode`, `ContainsSequenceValuePattern`. A `_` arm survives only where it is a SEMANTIC default — a partial classifier (`IsResourceLimit`, `IsLiftableError`, `Result.ValueCount`/`SingleAtomicNumber`/`SpreadItems`/`StructureItems`, `Pattern.TopLevelArity`, which mirrors Lean's own wildcard), a nullable input (`SupportsLexicalDotCall`), or a host-constructible enum kind (the parameter binders' `BadArity` defaults) — and guarded statement-form walks (`ValueTextRenderer.AppendValue`, `FrontEndRegionKeys`, `ParameterPropertyCollisionValidator`, `TryCreateBinderParameterPattern`, `CallableSignature.AddParameters`, `SemanticModelBuilder.CollectParameterPatternSpans`, `FreeReferenceNames`, `CollectAlgorithmSiblingDependencyIndices`) keep their fail-loud defaults, since the compiler checks no switch statement. This is not a guarantee for every existing walk: `Pattern.BoundNames`, pattern hashing, and `SequenceValueParameterPattern.Captures` have no unknown-variant guard, and the result comparer/hasher retains its existing semantic and permissive defaults. Those sites require an independent coverage decision when adding a variant. `EvalError` keeps one INTERNAL variant (`ModuleRegionMaterializationFailed`), so a consumer's switch over it is never exhaustive — hosts classify through `EvalError.Code`/`KatLangError.Code` — while every other root is consumer-exhaustive. Pinned by `ClosedHierarchyContractTests` (`tests/KatLang.Formatting.PublicApi.Tests`), which compiles generated consumer probes with the SDK pinned in `global.json` against the built `KatLang.dll`: every derivable constructor route (the copy constructor; for `ErrorContext` the ordinary constructor too) is refused with `CS9382` and nothing else — each probe overrides the root's abstract members, so a missing override can never be the reason it fails —, a built-in variant of every root is constructible, the generated no-catch-all switches compile for every all-public root, an omitted variant fails, and the `EvalError` switch fails; the closed set itself is ratcheted against the assembly's `IsClosedTypeAttribute` metadata and recorded in the public API baseline (`public closed record`). `KatLangErrorCodeTests` pins that every `EvalError` variant renders a message. Closing a hierarchy is a compiler contract, not a CLR seal (an already-compiled foreign subtype can still load and is outside the supported hierarchy); do not close a type that is a deliberate extension point (`OutputFormatter` is derivable by design: a protected constructor, documentation inviting derivation, stated guarantees, and `PublicFormatterExtensionTests`), and never restore a `_ => throw` unknown-variant arm to a switch expression over a closed hierarchy. `ErrorContext` is the one root closed for OWNERSHIP rather than exhaustiveness (September 2026): its thirteen variants are the structured evaluation frames KatLang attaches through `EvalError.WithContext` — produced only by the evaluator and the sequence optimizer — and a foreign subtype could inject arbitrary `FormatMessage()` behavior into the otherwise closed `EvalError` graph while gaining nothing over the supported free-text channel (`TextErrorContext`, i.e. `EvalError.WithContext(string, inner)`, the exact image of Lean's string context), which hosts keep, together with every built-in context's public constructor. Its production consumers are not full-hierarchy dispatches and were not converted: `KatLangError`'s recognizers are deliberately PARTIAL, keyed on one `(context, inner error)` shape each, over the generic `{context}: {message}` arm that renders any other pairing through the virtual projection; `KatLangEngine.IsTopLevelNoProgramOutput` likewise recognizes one shape. ## Variant-owned Algorithm payload

`Algorithm` (`Ast.cs`) is the closed three-variant hierarchy of the Lean inductive, and since September 2026 its payload is owned by the variant exactly as each Lean constructor carries its own fields. The base type has NO payload member and no `init` accessor: it carries the two equality-transparent runtime slots (`Declaration`, `DeferredRegion`), the Lean-total functional updates `WithParams`/`WithParameters`/`WithParameterPatterns` (the identity on `Builtin` and `Conditional`, which have no parameter list — Lean's `withParams`/`withParameterPatterns`, modeled behavior rather than a fallback), and the clause-elaboration factories `ElaborateClauseGroup`/`ElaborateClauseDefinition`. `Algorithm.User` (Lean `.mk`) owns `Parent`, `ParameterPatterns`, `Opens`, `Properties`, `Output`, and `HasExplicitParameterList`, plus `FindDuplicatePropName()`; `Algorithm.Conditional` (Lean `.conditional`) owns `Parent`, `Opens`, and `Branches`, plus `HasDuplicateBranchPatterns()`; `Algorithm.Builtin` owns `Id`. Before this change the base exposed ten virtual `{ get; init; }` payload properties (`Parent`, `Parameters`, `ParameterPatterns`, `Params`, `Opens`, `Properties`, `Output`, `Branches`, `ExplicitParameters`, `ExplicitParameterPatterns`) that `User` overrode partially, `Conditional` barely, and `Builtin` not at all, so `builtin with { Properties = … }`, `conditional with { Output = … }`, and `user with { Branches = … }` compiled and produced states Lean's inductive cannot represent (a probe showed `F.X` on a conditional with smuggled properties returning the member). Every such state is now a COMPILE error for every caller: a consumer gets `CS0117` (no such member) for a wrong-variant or base-typed payload write, `CS0200` for the read-only projections, and `CS1061` for a base-typed payload read, witnessed against the compiled assembly by the pinned SDK's compiler in `AlgorithmPublicSurfaceTests` (non-friend), which also compiles the positive control — every legitimate construction, update, and exhaustive consumer switch. Consequently a WRITE always narrows to the owning variant: the front-end passes match `Algorithm.User`/`Algorithm.Conditional` and `with` the variant (`ParameterDetector.ProcessUserAlgorithm`, `ImplicitArgumentResolver.ProcessUserAlgorithmRegion`, `ModuleLoader.ProcessAlgorithm`'s `else if (alg is Algorithm.User user)` arm, `PropertyExposureResolver.ProcessUserAlgorithm`), the evaluator's `WithParent` switches per variant, `ParameterDetector.ProcessConditionalBranchBody` rebuilds a branch body per arm — a host-built family in body position still has its OWNED `Opens` elaborated and their heads classified against the branch binders, keeps its branches, and receives none of the user-only row processing; only the payload-free `Builtin` returns at once — and a helper that mutates payload through a base-typed parameter is the thing this rule forbids — it would recreate the writable fake-universal slot.

Inside the assembly the Lean-total READS keep their spelling. `AlgorithmAccessors` (`AlgorithmAccessors.cs`) is an `internal static class` with a C# 14 `extension(Algorithm algorithm)` block whose properties are Lean's total functions: `Parent` (`parent`), `ParameterPatterns`, `Parameters`, `Params` (`params`), `ParameterCount` (`(params a).length`), `Opens`, `Properties` (`props`), `Output`, `Branches`, `HasExplicitParameterList`, and the total methods `FindDuplicatePropName()`/`HasDuplicateBranchPatterns()` — each an exhaustive switch expression over the closed set with no catch-all arm (a new variant fails the build there instead of silently inheriting `[]`), returning the owner's field and the empty value (`null`, `[]`, `OutputBundle.Empty`, `0`, `false`) for the others. An extension property has no `init` accessor, so `algorithm.Opens` reads on a base-typed value but `algorithm with { Opens = … }` does not compile; when the receiver is statically a variant its own instance member binds instead. The accessors are `internal`, so friend assemblies (`KatLang.Tests`, `KatLang.Benchmarks`, `KatLang.ParserFuzz`) read base-typed values the same way; a NuGet consumer narrows or uses the typed roots. The preflight child enumeration (`AstStructuralPreflight.TryGetExprChild`), `AsScopeCtx`, `LookupProp`, and every other total read go through them unchanged in spelling.

`User.ParameterPatterns` is the ONE stored parameter channel — Lean `.mk`'s `parameterPatterns` field. `Parameters` (Lean `parameters a = (parameterPatterns a).flatMap captures`) and `Params` (Lean `params a = (parameters a).map name`) are LIVE projections computed on every read and never stored: an empty stored pattern list returns the shared empty list, and a nonempty flat capture list uses one array per projection. Nested sequence-value patterns use the iterative `ParameterPattern.FlattenCaptures` with traversal/list storage (plus a name array for `Params`); the flat allocation bound does not cover nested or zero-capture grouped patterns. Nothing derived is stored because the caller-owned pattern list (and a nested `SequenceValueParameterPattern.Items` list) is read through — a host that mutates it sees the current state through every projection and every `with` copy (`AlgorithmParameterNamesTests`, `LoopStrategyPreparationTests.HostOwnedCallableMetadata_*`), and the loop-step snapshot (`SnapshotGenericLoopStepBindingContract`) snapshots the ONE channel. Pinned by `AlgorithmOwnershipTests` (explicitness per construct, the corpus law that a written list's captures are source-backed except the recovery binder and the synthetic deconstruction helper, lifted captures joining an inferred signature and never a written one).

## Budgets and cancellation

Runtime evaluator budgets are OPERATION-LOCAL. Dynamic depth is the only balanced protocol (`EvaluationBudget.TryEnterInvocation` / `TryEnterArgumentEvaluation`, released by `ExitInvocation`); steps, materialized items, and materialized string units are CUMULATIVE and are never refunded by a failure. The following balanced state protocols are encoded as `readonly struct` scopes disposed from a `using` — `Evaluator.BudgetLevel` for the depth chokepoints, `Parser.NestingLevel`/`Parser.DelimitedProduction` for the parser budget and owed closers, `LoopRunFrame.TempMemoSuspension` for the planned temp memo, and `ModuleLoader.WalkContextScope` for the loader's sink/traversal-base/token swap during a deferred materialization — so an exception, an early return, cancellation, or recovery can never skip the restore; a refused enter changes no owned state. Evaluator try-enter helpers yield a no-op default scope on refusal; parser entry throws its structured nesting-limit exception. Default instances of every scope restore nothing. The parser, loop memo, and loader scopes validate owner-held `StateScopeStack` tickets before restoration, rejecting duplicate, stale, or out-of-order disposal without changing state. Source-module budget entry/exit remains a separate `try`/`finally` protocol. A LOOP STEP invocation is deliberately outside the depth protocol (final audit, September 2026, recorded as a design question): `RunStepSlots` charges one step per iteration and never depth, because an iteration repeats work without nesting — so recursion routed through loop steps (`Step = Step.repeat(1, x)`) nests host frames `MaxDepth` never sees and is bounded only by the host-stack backstop (`EvaluationStackExhausted`, never an overflow); charging depth per step invocation would change every loop program's `peakDepth` and the planned/generic counter parity, so it is not done here. Two rules hold for every admitted level: a REJECTED enter mutates no counter — not depth, not peak, and not the invocation's own step, because that invocation did not happen (charging it let a lower `MaxDepth` flip an unrelated `MaxSteps` verdict, since a resource-limit failure of a parameter's eager value evaluation is retained on the algorithm binding and the run can continue) — and an ADMITTED level is released exactly once by its `using` cleanup, on success, structured failure, and exceptional unwind. Rejected cumulative work likewise cannot advance auxiliary admission state: in particular, a rejected bulk expression-work step leaves its 4096-checkpoint batch at the boundary so retained errors cannot admit work past an exhausted step budget. `ExitInvocation` is fail-loud on underflow, like `SourceProcessingBudget.ExitModule`: a double release is as damaging as a leak and otherwise invisible. Pinned by `BudgetConservationTests`; `OperationCanceledException` unwind is exercised both by injecting it through the internal `IZeroArgPropertyResultCache` seam and by the real host token. Evaluation host cancellation (`RunOptions.EvaluationCancellationToken`, `Evaluator.Run`/`RunFlat` token overloads) lives ON the run-scoped budget: every budget chokepoint observes the token BEFORE any counter check or mutation (`EvaluationBudget.ObserveCancellation`), each entry point checks it before the structural preflight and again before completing, and the optimized loop executor observes it once per iteration (observation-only — a fully-planned iteration touches a charging chokepoint only where the generic path charges one: planned `if` arguments, temp reads, and temp calls enter the SAME `Evaluator.BudgetScopes.cs` helpers as their generic counterparts, and charging per iteration would break optimized-vs-generic accounting parity). The completion observation closes final operations that have no later charging checkpoint; `RunFlat` and the engine also observe after their bounded host-atom projection. Requested cancellation THROWS `OperationCanceledException` carrying the supplied token and must NEVER become an `EvalError` — a resource-limit-style structured error would be retained on eager parameter bindings and the cancelled run would continue. An uncancelled token changes no counter, verdict, or result; the token is separate from `SourceProcessingCancellationToken` (front-end only). Pinned by `EvaluationCancellationTests` (deterministic mid-run and completion-edge triggering via CANCELLING — not throwing — cache-seam wrappers).

## Async evaluation and host operations

The ASYNC evaluation surface (`Evaluator.RunAsync`/`RunFlatAsync`, `KatLangEngine.RunAsync`) is a host-execution surface with NO Lean counterpart, built as a "sync-delegating async twin spine" (`Evaluator.Async.cs`): the synchronous evaluator remains the semantic oracle; engine `RunAsync` first awaits the async front end (`FrontEndPipeline.ProcessAsync` — module downloads may suspend source processing, see the source-loading bullet above), then an async entry point routes ONCE per run — a run whose zero-arg property cache is not async-capable and whose host-operation set has no asynchronous operation executes the synchronous pipeline inline and completes synchronously (never `Task.Run`, never artificial yielding), while an async-capable cache OR asynchronous host operation routes through the internal `async ValueTask` TWIN family. Every twin is marked `// MIRROR OF <sync name>` and MUST be updated in the same change as its synchronous counterpart — the twins re-implement only awaitable child-evaluation sequencing and share every non-evaluating helper. Twin rules: counted-family mirrors only (plain wrappers are counted projections — the Lean-modelled plain/counted value equivalence); the twin root context pins the GENERIC loop/sequence strategies (fail-loud guard `ThrowIfAsyncStrategyPinningViolated`); the two row-loop funnels carry a twin-only `TryEnsureSufficientExecutionStack` backstop because async frames are larger than the calibrated sync frames and structural nesting passes no invocation chokepoint; cancellation is the Phase 1 contract via the shared budget chokepoints (OCE through the returned task, never an `EvalError`). Divergence is pinned by `AsyncEvaluation/AsyncTwinDifferentialTests`: the language-spec + explorer corpora run through the twin path with outcome AND operational-counter equality against the sync generic strategies, plus a genuine-suspension pass; keep that suite green when touching either family. PUBLIC host operations generalize the Math-module mechanism, not a new subsystem: `HostOperation`/`HostOperations` (`RunOptions.HostOperations`, `Evaluator.Run`/`RunAsync` host-operation overloads) synthesize one ambient prelude property per operation — a parentless wrapper `Algorithm.User` whose body is `Expr.NativeCall("host:" + name, params)` (`':'` keeps host dispatch names disjoint from Math natives) — so resolution, shadowing, arity, and the `A` vs `A()` cache rule are the existing Lean-modelled rules unchanged, and the front end resolves the names through the configuration's extended signature-only semantic prelude (`ParameterDetector.DetectPrevalidated`; a referenced operation never becomes an implicit parameter). The configuration rides the run-scoped `EvaluationBudget`; sync operations dispatch in the shared `EvalNativeCall`, async operations await at ONE guarded `EvalCountedAsync` NativeCall case (invoked exactly once — suspension never replays), and every SUCCESSFUL host return value is normalized into the canonical `Result` representation at the host boundary (`NormalizeHostOperationValue` — the existing `Result.Normalize`, shared by both dispatch paths, applied BEFORE the zero-arg property cache stores the wrapper outcome; failures/cancellation untouched, identity on already-canonical values). Routing is enforced: any async-operation configuration selects the twin path with an async-capable cache (public entries construct one, internal entries fail loud), sync entry points reject async configurations with `InvalidOperationException` before evaluating, and host exceptions/faulted awaitables propagate to the host unchanged (never `EvalError`). Native-call wrapper bodies (Math members AND host operations) read their declared argument names through `LookupNativeArgument`, which IS the `Expr.Param` value read (`EvalParamCounted` projected to its value: `CountedParamEnv`, then `valEnv`, then the algorithm binding) — not a separate lookup rule. The counted tier makes them work DIRECTLY as callback and loop-step references (`map(abs)`/`map(Enrich)`), and the algorithm tier makes an argument that bound only on the algorithm channel produce the ordinary value-demand outcome (a parameterized callable's zero-argument arity error, a clause family's conditional value-access error, a zero-parameter algorithm's value or failure) instead of reporting `Unknown name` for the wrapper's own parameter. Because that tier can re-enter an algorithm body, `Expr.NativeCall` is a RECURSIVE variant with its own `EvalNativeCallAsync` twin (the shared pure `ApplyMathNative` keeps the member set from drifting, and host-built native signatures must match authoritative registry metadata exactly, after argument binding, with malformed counts returning structured errors), never a sync-delegable leaf. A same-named ambient value can never be captured or forwarded to host code in place of the bound argument: every binding path shadows the callee's parameter names out of all three inherited tiers (`ShadowInheritedParameterEnvironments` for the counted and algorithm tiers, `ShadowValEnv` / Lean `ValEnv.shadow` for the value tier). See `docs/design/async-evaluation-2026-08.md` and `Hosting/*Tests`.

## Plain/counted ownership

Plain/counted evaluator ownership: where a plain/counted pair is semantically equivalent, the COUNTED implementation is canonical and the plain implementation is its value projection — first in Lean (`eval` is the one-line total projection of `evalCounted`, which matches every `Expr` variant explicitly with no default arm; the call/dot-call/builtin/lookup plain families are `.fst`/`.alg` projections), then mirrored in C# (`ProjectCountedValue` over the counted twins; the former independent plain call/dot-call/builtin implementations and the resolve-only lookup chain are deleted). Never reintroduce an independently implemented plain evaluator body, and never make a counted function delegate its semantics to a plain one — the deliberate exceptions (C# plain-owned leaves Num/StringLiteral/BoolLiteral/Grace for the async leaf-delegation contract, the slot-view family, the root-program decoration pair, the opens-free direct lookup used by open resolution) are enumerated in `SEMANTIC-ALIGNMENT.md`.

## Zero-argument property cache

The zero-argument property cache is observable semantics, modeled in Lean: property-value `A` reuses its first successful entry; explicit `A()` neither reads nor replaces A's entry, and nested property reads retain their own rules. Exported bindings use one entry per declaring scope per run across lexical/structural spellings, user-call arguments, callbacks, loops, and opens; never add environment identity to their keys. The cache serves VALUE reads only: a builtin VALUE slot (`sum(A)`, `count(A)`, `if(true, A, 0)`, loop initial state and `repeat` count, `range`/`atoms` arguments, the `reduce` initial accumulator) and the `.string` receiver demand the named algorithm directly through the zero-argument value-demand law and neither read nor store its entry (Lean `evalArgumentValueCounted` → `evalZeroArgumentDemandOutputCounted`) — and since dot-call passes the receiver as the ordinary leading argument, the dotted spelling of a builtin call (`A.sum`, `A.count`, `A.take(2)`) is that same slot and bypasses the entry exactly as the written spelling does (September 2026; the former receiver-only cache reuse was an accidental asymmetry and is removed) — and since parentheses group syntax, the redundantly grouped spellings (`sum((A))`, `if(true, (A), 0)`, `(A).sum`, `(A).string`) ARE those same slots and bypass the entry identically (the former "captured spelling reads the cached value" asymmetry was the parser keeping a capture layer around a bare name; it is removed with that layer). A genuine VALUE-position read still goes through the entry: a property whose body reads `A` (`V = A` then `V.count` demands `V` and reads `A` from the cache), a comparison or list element (`A == A`, `[A]:0`), a user-call argument. The difference between a demand and a value read is observable for random- or host-backed properties and as a materialization difference (`A.count + A.sum` builds `A` twice; `V = A` then `V.count + V.sum` builds it once); it is documented in the tutorial's caching section, and whether a builtin VALUE slot should read the cache at all (closing the gap per the value-demand law) is the open design question recorded there — never to be answered for one spelling alone. All keys identify the declaring scope structurally, so rebuilding an owner record alone cannot split an entry. Local-only bindings retain all three binding contexts; fresh calls/callbacks/iterations stay distinct even with equal values. Ordinary environments use list reference identity; the planned loop environment supplies an explicit per-iteration identity through `ValueEnvironmentCacheIdentity`: `Evaluator.Concat`, the shared helper that prepends a binding's own entries to an inherited tier, always mints a fresh list — never returning an operand even when the other is empty — because two activations that bind nothing new (`Inner()` twice, a zero-parameter callback, a stateless iteration) must still be two binding contexts, while the shadow helpers (`ShadowValEnv`/`ShadowAlgEnv`/`ShadowCountedParamEnv`) may keep their instance because a shadowed inherited tier is a view of the caller's context, not a new one (`EnvironmentIdentityInvariantTests`). Planned exported temps use the run cache; local-only temps use per-iteration/per-call memoization, suspended for the duration of a planned temp call by the owned `LoopRunFrame.TempMemoSuspension` scope (`LoopTempMemoSuspensionTests`). The evaluator trusts exposure metadata exactly as open/dot lookup do: host-built captures must declare local-only exposure. The front end charges every MAY-selected fallback using the detector's scope-aware `ElaboratedFallbackSelection`; definite structural winners charge no fallback, and navigated members charge their own requirements (a structural path or an opened name is a `PendingReference` the exposure resolver settles at the owning level with the evaluator's lookup order). The detector's verdict is final: exposure never changes what a name resolves to, so there is no recheck round. Lean assigns declaration identities before execution (`identifyPropertyExpr`, with explicit `shared` identities for host DAGs) and fresh activation identities at `EvalCtx.bindParameters`; ancestor keys identify the declaring scope, not a lookup wrapper. Failed properties are never stored; failed parents do not roll back successful child entries. Re-entrant reads begun before a store finish normally but never replace an already completed first-successful entry. Keep `ZeroArgPropertyCacheScopeTests`, cache-key/loop/exposure tests, `LeanAstEncoderTests`, and CoreTests `zeroArg*` guards aligned. Other implementation-only caches need no Lean mirror.

## Numerics

Lean core numeric semantics use `Int`; the C# runtime uses IEEE 754 `System.Numerics.Decimal128` (34 significant decimal digits) end-to-end — literals parse directly into it, arithmetic and every Math function compute in it natively, and there is no `decimal` or `double` stage anywhere in core numerics. Do not silently widen or reinterpret numeric behavior without checking Lean first. Division/modulo by a zero-valued divisor (the EVALUATED value — `1 / 0`, `1 / (1 - 1)`, `1 / -0`, and an underflowed-to-zero divisor all alike) stays the Lean-modeled `divByZero` error and zero-base powers obey the domain-error policy in `src/KatLang/SEMANTIC-ALIGNMENT.md`; `div` uses `Decimal128Numerics.IntegerDivide`: exact mathematical truncation when representable, otherwise leading 34 digits toward zero for finite IEEE quotients (the consecutive-integer domain is |q| <= 10^34, with sparse larger integers also exact). IEEE division overflow and special values are unchanged; the mathematical div/mod identity requires a representable truncated quotient, and its runtime recomposition also requires exact intermediate arithmetic. Other arithmetic follows Decimal128's IEEE behavior (overflow produces a signed infinity, domain violations produce NaN, NaN/±Infinity/−0 are ordinary values). Structural value equality (`==`, `distinct`, `contains`, ValueComparer) uses `Decimal128.Equals` semantics — NaN is one value, quantum is ignored — while the ordering operators are IEEE (comparisons with NaN are false). Transcendental Math results are quantum-canonicalized (IEEE `reduce`, value-preserving) so exact results like `Math.Lg(1000)` stay `3`; ordinary arithmetic is not quantum-canonicalized, so the Decimal128 operation's result quantum remains visible (`0.5 + 0.5` displays `1.0`). `range` alone canonicalizes accepted whole-number bounds before enumeration: exponent 0 except at ±1e34 (exponent 1), and unsigned zero. Keep this at the shared range-validation boundary; do not normalize other whole-integer arguments. Numeric-change ROUTING is two-tier — the "Core numeric semantics" row in `src/KatLang/SEMANTIC-ALIGNMENT.md` is authoritative: Lean-modeled laws on the COMMON EXACT integer subdomain (exact integer arithmetic/comparison, the representative truncating `div`/`mod` cases, the zero-divisor rule where applicable, `0 ^ negative` at its integer instance — the runtime rejects EVERY exponent below zero, the fractional side is Decimal128-only — structural equality, Boolean logic over Boolean operands) change Lean and C# together with Lean-comparable LanguageSpec coverage, while Decimal128-specific behavior (finite precision/range even for integral inputs, fractional values and quantum, NaN, ±Infinity, signed zero, overflow to infinity, gradual underflow, IEEE ordering of specials, non-exact `/`/`avg` results) is an explicit reviewed model divergence pinned by C# tests plus a canonical C#-only LanguageSpec case with a `LeanExclusionReason`, never a fabricated Lean encoding. Do not classify from source spelling alone: "integer input" is not sufficient once a Decimal128 operation rounds or overflows. ACCURACY AND ARRANGEMENT (final audit, September 2026, Decimal128 tier): `Math.Ln`/`Lg`/`Log` evaluate arguments in [0.5, 1.5] through the log1p reformulation (`Decimal128Numerics.NaturalLog`, `Log10`, `Log`; `Lg` divides by the runtime's `ln 10`), and a delegated power — a fractional exponent, one beyond `long`, or a negative integral exponent whose positive power overflows — of a base whose MAGNITUDE is in [0.99, 1.01] is `exp(y · ln |x|)` (a negative base takes the integral exponent's parity sign, so `(-b) ^ n` is exactly `(-1) ^ n · b ^ n` on both sides of every routing boundary: the band once admitted only positive bases, and `(-0.9999999999999999999999999999999999) ^ 1e34` kept four correct digits — numeric audit #6, September 2026, `Evaluator.DelegatedPower`) with the exponent product, the fractional exponential, and `e^n` computed as 80-place fixed-point approximations, with final Decimal128 rounding once (`NearOnePower` over `RoundRational`), because the runtime's `Decimal128.Log` loses about log10(1/|x − 1|) digits to cancellation near 1 and `Pow` inherits that loss — and because a power loses log10 |y · ln x| digits whenever that product IS rounded to 34 digits (the hostile pass measured 123–2,089 ulp for a rounded-product composition; sample powers are pinned at one ulp against a binomial-series oracle and separately derived arbitrary-precision constants; logarithm truncation is amplified by the exponent, conservatively below 10^-39 in the evaluated product band, and the result is not interval-certified); the tutorial's "correct to roughly the last digit or two" claim is pinned against an INDEPENDENT BigInteger series oracle in `Decimal128NearOneLogarithmTests` (one ulp), never against the runtime functions themselves. `order` is a STABLE sort under `Decimal128.CompareTo` and `orderDesc` its reverse (`Evaluator.SortStable`; Lean `sortIntsAsc`/`sortIntsDesc`): ascending equal-comparing values keep their written order and descending reverses those groups, observable through the quantum and zero sign display preserves, so the arrangement never depends on the runtime sort algorithm. `DisplayDecimals` rounds midpoints AWAY FROM ZERO — the rule `Math.Round` applies — in `ValueTextRenderer.FormatAtom`, which lays out an already-rounded value; the runtime fixed-point formatter's own tie rule (changed in .NET 11 RC1) is never the owner. `avg` is the EXACT mean (numeric audit #6, September 2026): the exact total divided by the count, rounded once. `sum` stays the left-to-right Decimal128 sum, which can round on the way, so `avg` keeps `total / count` bit-for-bit — IEEE quantum and zero sign included — only while every addition was exact (decided cheaply from the result quanta by the ONE `SumNumbers` loop, and exactly when that is inconclusive), and otherwise divides the exact BigInteger total once (`Evaluator.AverageFiniteNumbersExactly` over `Decimal128Numerics.TryExactDecimal128`, Horner-assembled so thousands of distinct quanta stay cheap); the mean formerly divided the rounded running sum unless it overflowed, so `avg((1, 1e34, -1e34))` was `0`. A NaN or infinite element keeps the ordinary IEEE result. C#-only spec cases `logarithm-near-one-is-accurate`, `order-is-stable`, `display-decimals-rounds-ties-away-from-zero`, `avg-is-the-correctly-rounded-exact-mean`, `negative-near-one-base-power-is-sign-symmetric`.

## Boolean values

BOOLEANS ARE A VALUE KIND, NOT A NUMBER (September 2026). `true` and `false` are first-class scalar values — Lean `Result.bool`, C# `Result.Bool` — written as the reserved literals `true` / `false` (lexer keywords `KeywordTrue`/`KeywordFalse`, parsed to `Expr.BoolLiteral` / `.boolLiteral`; in a clause head they are the literal patterns `Pattern.LitBool` / `.litBool`, so `F(true) = …` and `F(1) = …` are different clauses). Being keywords they are never identifiers: they can be neither declared nor shadowed and never become implicit parameters, and a head such as `true = 1`, `false(x) = x`, or `public true = 1` is the targeted `UnexpectedToken` diagnostic at the literal ("'true' is the reserved Boolean literal, not a name: it cannot be declared as a property, clause, or parameter, and it cannot be shadowed."), reported by `Parser.ReportReservedLiteralDeclaration` after `IsReservedLiteralDeclarationHead` recognizes the head under the ordinary declaration-head line rule; the head is skipped so the body parses as an ordinary row. PRODUCERS: every comparison chain (`Expr.Comparison`, `syntax.md` § Operator precedence, comparison chains, and prefix `not`) — its links are the ordering operators `<`, `>`, `<=`, `>=` (numeric scalar operands only; `Evaluator.TryCompareNumeric` is the ONE ordering comparison, shared by the generic link application `Evaluator.ApplyComparison` / Lean `applyComparison` and the planned-loop arm) and the total structural equality `==`/`!=` over every value kind (`true == 1`, `false == 0`, and `true == 'true'` are `false`, never errors; `Result.ValueComparer` tags Booleans with `BoolTag`, so `distinct` and `contains` treat them as ordinary items), and a chain is `true` iff every adjacent link holds (`1 < 2 == true` compares `2` with `true`, which is `false`; a `false` link never stops the chain, an error does) — the logical operators `and`/`or`/`xor`/`not`, and `contains`. CONSUMERS: `if`, `filter`, the `while` continuation flag, and the logical operators read the ONE truth view `Result.asBool?` / `AsBool` — a Boolean value, or a redundant singleton sequence boundary around one (`(true)` is `true`, exactly the normalization `asInt?`/`AsNum` applies to numbers) — and reject everything else. THERE IS NO NUMERIC TRUTHINESS: no `0`/nonzero convention, no first-atom flattening (`Result.atoms`/`ToAtoms`, `truthValue?`/`TruthValue`, and `singleAtomicTruthValue?`/`SingleAtomicTruthValue` no longer exist), so `if(1, a, b)`, `not 1`, `1 and 2`, `filter{x}` over numbers, and a numeric `while` flag are all value-kind errors. A Boolean is never a number and a number is never a Boolean: there is no implicit conversion in either direction, `expectInt`/`ExpectInt` reject a Boolean with `typeMismatch "Expected a number, got a Boolean value"` (so arithmetic through the numeric-scalar operand message, `range`, `take`, `repeat` counts, and the Math natives all reject it), the atom views `languageAtoms`/`hostAtoms` omit it (`atoms(true)` is `[]`; `runFlat`/`EvaluateToAtoms` never show a Boolean — hosts read the structured value), and `.string` keeps its numeric-receiver contract. Booleans are NOT ORDERED: `true < false` and `true > 0` are the numeric-scalar operand rejection, and no `false < true` order exists. The logical operators require a Boolean on BOTH sides (`requireBooleanOperand`/`RequireBooleanOperand`: "operator `and` expects Boolean operands, but the left operand was numeric value 1", wrapped in the same binary-operand context as the numeric rejection) and both operands are evaluated left to right before the operator applies — the established evaluation order, no short circuit; `not` requires a Boolean operand ("operator `not` expects a Boolean operand, but the operand was …"), while `-` rejects a Boolean as a numeric-scalar operand error. Every Boolean-REQUIRED position reports the ONE `typeMismatch` message `booleanRequiredMessage`/`BooleanRequiredMessage` — "`<role>` must be a Boolean value (true or false), but was `<operandDescription>`", roles "if condition", "filter predicate result", "while continuation flag (the step's last output)" — so a number in a predicate position is reported as the value-kind mismatch it is, never as an arity, implicit-parameter, or resolution error; `operandDescription`/`DescribeOperand` names the value kind first ("a Boolean value: true", "numeric value 1", "a sequence value with 2 sequence elements: (true, false)"). The `while` flag is the step's LAST output; a single-output step's one slot is both the next state and the flag, so it must be Boolean too (`Step = x - 1, x > 1` is the shape; `Step = x - 1` alone is rejected). Booleans participate in every structural rule like any other scalar: `true, false` is a two-row output, `(true)` normalizes, `[true, false]` is an exact list, deconstruction and collecting bindings bind them, callbacks and the zero-argument property cache carry them, and DISPLAY is lowercase `true` / `false` everywhere (`ValueTextRenderer.FormatBool`, `Result.boolText`, the neutral spec encoding). The planned-loop evaluator mirrors all of this: its unboxed numeric fast path serves arithmetic and ordering only, `not`/`and`/`or`/`xor` and every rejection delegate to the shared `ApplyUnaryOperator`/`ApplyBinaryOperator`/`ApplyComparison` (a planned comparison chain applies each link through the same `ApplyComparison` as the generic spine machine, `LoopOptimizer.EvalLoopComparisonPlan`), a planned `if` and the optimized `while` flag read `PlannedLoopValue.AsBool` and report the same messages as the generic paths, and the sequence-pipeline fusion consumes `EvalFilterPredicateTruth`, which applies the Boolean rule. Pinned by `BooleanValueTests`, `EvaluatorOperatorTests`, `EvaluatorIfBuiltinTests`, `EvaluatorLoopTests`, `EvaluatorSequenceCallbackTests`, `LexerTests`, `ParserTests`, the Lean `CoreTests` (`Numerics`, `Conditionals`, `ListValues`, `SequenceCallbackBuiltins`, `ParityGuards`), `KatLangArityLaws` (`asBool_*`, `asInt_bool_none`), and the `LanguageSpecCases`/`SemanticExplorerCases` differential artifacts.

## Seeded randomness

KatLang's random operations — `Math.Random` / `random` and `Math.RandomInt` / `randomInt` — draw from ONE run-scoped random stream, and a host may seed it: `RunOptions.RandomSeed` (engine entry points and every convenience over them), the `Evaluator.Run` / `RunAsync` / `RunFlat` / `RunFlatAsync` overloads that take a `long? randomSeed`, and the CLI's `--random-seed <integer>` for `run` and `eval` (`check` refuses it because it does not evaluate). `null` keeps evaluation UNSEEDED and nondeterministic; every `long` is a valid seed and every distinct value names a distinct stream (the seed's bit pattern is the initial state, never folded, hashed, or truncated). This is host/runtime evaluation configuration with NO Lean counterpart: Lean models neither the Math runtime surface nor native random execution, and seeding changes where the raw words come from, never which calls execute — that is decided by the existing Lean-modeled evaluation rules (left-to-right argument evaluation, once-only written arguments including the patterned-call view, lazy `if` branches, the zero-argument property cache with explicit `A()` re-evaluation, callbacks in sequence order, output rows before the engine's `DisplayDecimals` evaluation). A seed reproduces a stream, it never memoizes: removing an earlier random call generally changes every later value (bounded rejection consumes a variable number of raw words).

The stream is run-scoped MUTABLE state on the run's `EvaluationBudget` (`EvaluationBudget.RandomSource`), constructed EAGERLY at budget creation by `RandomSourceFactory.Create(seed, entropyProvider)` — a supplied seed never consults entropy; an unseeded run reads 8 bytes from `Random.Shared.NextBytes` exactly once (the full 64-bit state domain; `NextInt64()` is deliberately not used) and never touches `Random.Shared` again. Because every copied `EvalCtx` carries the budget by reference, nested calls, callbacks, loop frames, property evaluations, the `DisplayDecimals` evaluation, and async suspension/resumption all share the one stream and none can reset or duplicate it; `ApplyMathNative(name, args, randomSource)` receives it EXPLICITLY from `ctx.Budget` in both `EvalNativeCall` and its `MIRROR OF` async twin, with no optional or static fallback. The stream must never live on `RunOptions`, `EvaluationLimits`, or `HostOperations` (immutable configuration), in a static, thread-local, or `AsyncLocal` slot, or in a cache keyed by seed: reusing one options object for sequential runs replays the stream from its beginning, concurrent runs sharing it get independent stream instances from the same seed, and no lock exists on the source because evaluator access within one run is sequential even when an async continuation resumes on another thread. `EvalCtx.Empty` and every direct `EvaluationBudget.Create` caller that supplies no seed remain unseeded.

The production generator is a KatLang-owned SplitMix64 (`SplitMix64RandomSource`, sealed) with the exact published constants, advance-before-mix order, `hi`-then-`lo` 128-bit composition, and top-incomplete-cycle rejection followed by modulo for bounded draws (a bound of 1 still consumes one word; an invalid bound throws before consuming any); the samplers `SampleRandomUnitFraction` (high 17-digit component, then low, on the exact 10^34 lattice) and `SampleUniformInteger` (exact `Int128` span, `2^128 mod span` rejection) are unchanged by seeding and validate before every draw, so an invalid call consumes nothing. Sync/async routing, optimizer strategies (planned loops with generic random rows, fused `filter`/`count` with a random predicate), and unrelated `EvaluationLimits` settings that leave the program's control flow unchanged must all preserve draw count and order; optimizers are never disabled because a seed is present. The exact stream is reproducible for a given KatLang version across platforms, is NOT promised across versions (a deliberate generator, sampler, or evaluation-semantics change is release-noted), and is not cryptographically secure. The full internal contract, with the seed → state map, the constants, the bounded-rejection algorithm, unseeded initialization, and the version-stability policy, is `docs/design/seeded-randomness-2026-09.md`. `Parser.Parse` / `ParseAsync` ignore the seed; the canonical `LanguageSpec` and `SemanticExplorer` corpora carry no random case. Pinned by `RandomSourceTests` (published SplitMix64 vectors plus an independent BigInteger derivation and the test-side `ReferenceRandomOracle`), `RandomFractionSamplingTests`, `RandomIntSamplingTests`, `SeededRandomnessTests`, `SeededEvaluationOrderTests`, `SeededOptimizerParityTests`, `SeededAsyncEvaluationTests`, `SeededConcurrencyTests`, the `SeededStream` scenario of `ConcurrencyDifferentialTests`, and `CliApplicationTests`.

## Display decimals and the host default

A completed run has ONE effective display-decimals setting, decided once by `KatLangEngine.ResolveDisplayOptions` (shared by `Run` and `RunAsync` through `ProjectEvaluationOutcome`) and carried by the `RunResult` as its internal `DisplayOptions.Decimals` (September 2026; C#-only host configuration, no Lean counterpart — Lean models no rendering):

1. a top-level `DisplayDecimals` property the program DECLARES decides — the root's OWN property (`Evaluator.LookupPropBinding` over the root's properties; a nested or open-provided `DisplayDecimals` is not the program's setting, exactly as before), evaluated as an ordinary zero-argument value demand AFTER the program output under the same run budget, random stream, and zero-argument property cache, then validated (one numeric value, a non-negative integer, at most `RunOptions.MaxDisplayDecimals`);
2. otherwise the host DEFAULT `RunOptions.DefaultDisplayDecimals` — the CLI's `--display-decimals <integer>`, valid for `run` and `eval` and refused by `check`, which does not evaluate;
3. otherwise canonical full-precision display (`null`).

A declared property is authoritative even when it is INVALID or its evaluation FAILS: the run fails with that property's own diagnostic whatever the host configured — the default is a fallback, never error recovery. The three states stay structurally distinct and no falsy or default-value shortcut may collapse them: the evaluator's one top-level property probe (`EvalTopLevelZeroArgPropertyCounted` and its `MIRROR OF` async twin) returns `null` exactly when the root declares no such property, without touching the property cache; a declared property's evaluation failure is an ordinary evaluation error; and a declared `0` — like a default of `0` — is a real setting, never absence.

The default is display-only HOST configuration with no language presence. It is never injected as source text or as an AST property, so name resolution, ownership, shadowing, collisions, spans, diagnostics, the semantic model, and completion see the program exactly as written (`Parser.Parse` / `ParseAsync` ignore it, and a program that reads `DisplayDecimals` without declaring it still has an implicit parameter). It is consumed only AFTER evaluation, so it costs no evaluation step, depth, or materialization, draws no random word, invokes no host operation, adds no cancellation checkpoint, and creates no cache entry; configuring it changes no `Result` value, emitted count, output row, host atom, error, or diagnostic — only rendered numeric text. The accepted range `0` through `99` has ONE owner, the public `RunOptions.MaxDisplayDecimals` — a VALIDITY bound, deliberately not a `MaxSupported*` clamping ceiling — read by the source-property validation, by the `DefaultDisplayDecimals` init accessor (which throws `ArgumentOutOfRangeException` when the options object is initialized, so an invalid default never reaches a synchronous or asynchronous entry point and never becomes a source diagnostic), and by the CLI, which sees only KatLang's public surface and reports an out-of-range or malformed value as a usage error through the value rule it shares with `--random-seed`. Every rendering surface reads the result's one `DisplayOptions` — `RunResult.ToDisplayString` / `RenderDisplay`, the `exact` / `readable` / `concise` formatters, custom `OutputFormatter`s through `BoundedOutputWriter.AppendAtom`, and the structured-layout measurer — through the ONE `ValueTextRenderer.FormatAtom`, so the default gets exactly the property's rounding (midpoints away from zero), invariant digits, special-value spellings, signed-zero rule, and display-length bound. The setting never lives in static, thread-local, `AsyncLocal`, or other process-wide state; `RunOptions` is immutable, and a declared property never writes back into it. Pinned by `Hosting/DefaultDisplayDecimalsTests` (precedence; the invalid-override, override, rendering-equivalence, and absence laws; raw-outcome, step, random-stream, host-operation, and cache neutrality; sync/async parity; every formatter; the LanguageSpec corpus differential), `ZeroArgPropertyResultCacheTests`, the `DisplayDefault` scenario of `ConcurrencyDifferentialTests`, `PublicFormatterExtensionTests`, and `CliApplicationTests`.

## Diagnostic transparency of synthetic frames

A user-facing diagnostic describes the KatLang program the programmer WROTE. The generic evaluation-context enrichment — the frames that read `while evaluating call to F`, `while evaluating property P` — names user-semantic constructs only; a frame the FRONT END synthesized to lower a surface form is DIAGNOSTICALLY TRANSPARENT and contributes no frame at all (September 2026, F3). The transparency test is the parser's STRUCTURAL provenance mark, never the spelling of a name: `Algorithm.IsSyntheticDeconstructionFrame` is the ONE predicate, reading `Algorithm.User.IsSyntheticDeconstructionPlumbing` (the hoisted `$deconstruct$N` right-hand-side source, `IsAssignmentDeconstructionSource`, and each target's inline projection helper, `AssignmentDeconstructionTarget`).

Assignment deconstruction is the one surface form that is lowered this way: `x, *y, z = RHS` becomes a hoisted zero-parameter source property plus one anonymous inline helper per target, each helper applied to that source (`Parser.AddDeconstructionProperties`). Both are invisible to the programmer, so neither may be named. Before F3 both were, and the leak was not rare — the helper's frame was attached to EVERY failing deconstruction: `x, y = 1/0, 2` reported `while evaluating call to {...}: Division by zero`, `x, y = { }` reported `while evaluating call to {...}: Property '$deconstruct$0' has no defined output.`, and a deconstruction whose right-hand side deconstructed again stacked two `{...}` frames.

The rule is suppression of the synthetic frame, never of context in general. Genuine user-written frames keep their identity, their payloads, and their outermost-to-innermost ORDER: `Bad(n) = n / 0` with `x, y = Bad(1)` still reports `while evaluating call to Bad: Division by zero`, and `Outer` calling `Inner` through a deconstruction still reports both, in that order, with only the helper's frame gone from between them. A deconstruction's OWN binding failure keeps its assignment-focused wording (`DeconstructionBindingContext`, "Assignment pattern `x, y` expects 2 values …"), which is the same principle applied to the shape error rather than to a frame.

Implementation map — two attachment points, both already the single place their frame is built, so sync, async, and planned execution share one decision:
- Call frames: `Evaluator.CallDiagnosticName.FromExpression` marks a callee `IsDiagnosticallyTransparent` when it is an `Expr.AlgorithmExpr` over a synthetic frame, and `WithCallCtx` / `CalleeResolutionFailure` then attach nothing. `EvalCallCountedExpr`, its async twin `EvalCallCountedExprAsync`, and the optimizer's shared `WithPlannedCallBoundary` all derive their name through it.
- Property frames: `Evaluator.WithPropertyContextOnMissingOutput` takes the RESOLVED algorithm and attaches no property frame for a synthetic source, so an output-less right-hand side stays the written expression's own failure at the written expression's own span. A builtin argument slot passes `null` (a written argument is never deconstruction plumbing).

Diagnostics only. Error kinds, structured payloads, evaluation values, counts, and source spans are unchanged — a reported span is exactly the span reported before F3 — and the suppression removes only a `WithContext` layer, so classification that resolves through wrappers (`EvalError.IsResourceLimit`, `Code`, the terminal-error walk) is untouched. Resource limits were already exempt from context enrichment and stay exempt. C#-ONLY: Lean's `CtxMsg.call` applies to every call in Lean's model, which has no surface parser, no deconstruction lowering, and therefore no synthetic frame to mark; the two differential corpora compare the innermost error CATEGORY (`errCategory` discards `withContext` outright), so no Lean guard can observe a context frame. Pinned by `DeconstructionDiagnosticTransparencyTests` — including a generated shape × failure-origin matrix, a corpus-wide net over `LanguageSpecCorpus` and `SemanticExplorerCorpus`, the genuinely-suspending async twin, and optimized/generic parity — with `DeconstructionBindingTests` keeping the wording rules.

Two consequences worth stating because a name-based filter would get them wrong. A WRITTEN identifier whose text resembles the internal convention (`deconstruct`, `synthetic`) is an ordinary property and keeps its frame. And a host-built `Expr.Call` over an `Expr.AlgorithmExpr` is a USER-AUTHORED anonymous callable — the parser emits that shape for deconstruction helpers only — so it still reports `while evaluating call to {...}`.

## Blame for an output-less written argument

A WRITTEN VALUE ARGUMENT THAT PRODUCES NO OUTPUT IS DIAGNOSED AT THAT ARGUMENT (September 2026, F5). Four situations look alike in the final argument count and are not the same thing, and no diagnostic may collapse them:

1. **No argument was written.** An arity failure, decided by the binder before anything is evaluated: `F()` with `F(x) = x`, `count()`.
2. **An ordinary value argument was written and its expression produced no output.** That argument's own failure: `F({ })`, `count({ })`, `Coll({ })`, `F(1 + { })`.
3. **An argument produced a legitimate EMPTY VALUE.** One ordinary value, never a missing output: `F([])`, `F(())`, `F('')`, `count([])`, `Coll(())` is `[()]` and `Coll([])` is `[[]]`.
4. **An explicit SPREAD legitimately supplied zero items.** A legal supply wherever the callable accepts it: `Coll(Empty*)`, `Coll(()*)`, `Coll([]*)` are each `[]`. A spread operand that has no output at all is its own separate `EvalError.SpreadMissingOutput`, never the argument blame.

The distinction follows SLOT PROVENANCE — which written argument expression, if any, produced the slot (diagnostic identity only, never read by a binder) — and is never inferred from the final supplied-item count. This matters most for a collector, which legally accepts zero supplied items: `Coll({ })` must not become `Coll()`.

Case 2 used to be reported through whichever frame happened to enclose it, because a bare `EvalError.MissingOutput` escaping an argument was claimed by the enclosing call. `count({ })` read `Cannot call 'count' because it has no defined output` — blaming a builtin that is perfectly well formed, and describing the program as though the source had been the argumentless `count()`; `Coll({ })` blamed `Coll`; `if(c, { }, 2)`, `take(xs, { })`, `range({ }, 3)`, `atoms({ })` and `F(1 + { })` blamed their callees; `(1, 2, 3).take({ })` and `{ }.count` blamed the receiver expression. A NAMED argument was already correct, because a name makes its own blame decision while it is evaluated (`PropertyEvaluationContext` for `sum(L)`, `ParameterEvaluationContext` for `F(a) = sum(a)`); the gap was every shape with no name to report.

The rule is now the ONE `Evaluator.BlameWrittenArgumentForMissingOutput`: a bare `MissingOutput` escaping a written argument is wrapped in the public `ArgumentEvaluationContext`, which carries the argument's `OpenExprName` spelling (`{...}`, `({...}, 1)`, `(1 + {...})` — the same spelling `CallContext` and `DotCallContext` use) and is positioned at the written argument (`AtSpanIfMissing`, so a span the error already carries is kept). It renders as `The argument `{...}` has no defined output.` under the callee's own frame, which is retained exactly as it is for a named argument.

The argument wrapper copies the inner error's existing span before applying the argument-span fallback. Thus `P([1, {}])` and `map([[1, {}]], P)` keep the inner block's precise location even when `P` uses nested patterns or collectors; adding argument blame must not replace the written-element location with the containing argument's extent. The S3 hostile review pins these compositions in `AbsentSourceLocationTests` and `OutputLessArgumentBlameTests`.

Implementation map — the provenance already existed at both argument-assembly boundaries and is simply carried to the diagnostic decision:
- Builtin slots: `ResolvedArgumentAlgorithm.Source` already threaded the written argument expression through the zero-argument value-demand law. `BlameDemandedArgumentForMissingOutput` keeps its `Expr.Resolve` / `Expr.Param` arms and blames every other shape through the ONE helper. This covers the value slots of `count`, `sum`, `take`, `range`, `atoms`, `if`, the loop controls, and the `reduce` initial accumulator; a CALLBACK slot is never demanded, so a higher-order argument is never turned into a value demand.
- User-call slots: `ParameterPatternInput.Source` is the user-call twin of that field, set by `BuildCallArgumentInputs` (and its `MIRROR OF` async twin) for every non-spread written slot. Each site that surfaces a retained `ValueError` — the collecting segment, the normal capture, `GetSequenceValuePatternItems`, and clause-family argument assembly — goes through the ONE `SurfacedSlotValueError`.
- `BlameWrittenArgumentSlot` is the user-call entry point, and it deliberately does NOT blame an `Expr.Resolve` or `Expr.Param` source: a written slot is evaluated as an ordinary expression there, so a name has already made its own blame decision — including the deliberate transparency of the parser's hoisted deconstruction source, whose bare `MissingOutput` must keep bubbling to the written assignment target (see § Diagnostic transparency of synthetic frames).

A callee that genuinely has no output of its own KEEPS the callee blame: `F = { A = 1 }` called as `F()` or `F(1)` still reports `Cannot call 'F' because it has no defined output`, which is correct there.

Laziness, evaluation order, and evaluation counts are unchanged. Slots are still evaluated left to right exactly once; a slot that failed is RETAINED rather than raised when it has an algorithm channel, so an argument nobody demands is not an error at all (`F(x, y) = x` called as `F(1, { })` is `1`) and later slots still evaluate; the blame is built only where a demand actually surfaces the failure, and nothing is re-evaluated to discover it. A FIXED parameter keeps its established report — the demand happens inside the callee when the body reads the parameter, so `F({ })` with `F(x) = x` reports `Parameter 'x' has no defined output: the argument bound to it is …` at that read, which names the argument the caller has to change without claiming the callee. That path also keeps its pre-existing re-derivation of the argument (the algorithm binding retains only resource limits, so the demand re-evaluates the bound algorithm); changing it would change observable host-effect counts, so F5 deliberately left it alone.

Diagnostics only, and C#-ONLY. The structured error kind and payload are unchanged (the innermost error is still `EvalError.MissingOutput` and `KatLangError.Code` is still `KatLangErrorCode.MissingOutput`), values, emitted counts, cache behavior, budgets and cancellation are unchanged, and `KatLangErrorCode`, `DiagnosticCode` and every existing member are unchanged. The one public-surface ADDITION is the `ArgumentEvaluationContext` variant itself: `ErrorContext` is consumer-exhaustive (only `EvalError` deliberately keeps a non-public variant, pinned by `ClosedHierarchyContractTests.HierarchyWithAnInternalVariant_IsNeverExhaustiveForAConsumer`), so a new frame MUST be public, and a host switching over `ErrorContext` with no catch-all arm gains one arm — the reviewed cost of a new frame in this hierarchy, recorded in the regenerated `PublicApiBaseline.txt` exactly as `ParameterEvaluationContext` was. Lean's `errCategory` discards `withContext` outright, so no Lean guard can observe a context frame. Pinned by `OutputLessArgumentBlameTests` (the four situations, fixed-arity and collector and builtin receivers, first/second/middle blame, nested frames, dotted calls and receivers, evaluation order and exactly-once host-effect counters, sync/async and generic/optimized agreement, a genuinely suspending run, host-built ASTs, and the F2/F3 invariants) and by the canonical `output-less-argument-is-not-an-omitted-argument` `LanguageSpecCorpus` case, which is Lean-guarded on the error category and pins the collector distinction as executable specification.
