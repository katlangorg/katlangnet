# Syntax rules

The full statement of the rules that AGENTS.md carries in compact form — consequences, examples, the implementation map, and the pinning tests — moved here verbatim from AGENTS.md in September 2026. These rules are as binding as AGENTS.md; the compact bullet there points at the section here. Keep both in step: a rule change edits the compact bullet and the section together.

## Lexical identity and physical lines (Q-65)

Names are exact, case-sensitive strings compared ordinally, without case folding or normalization. LF defines a physical line break. CR is whitespace and does not create a line break; CRLF files are supported through their LF. Backslash is not a physical-line continuation operator: outside a string it is a lexical error. Literal backslashes in raw single-quoted strings and the admitted escapes of double-quoted strings keep their string meanings.

A physical newline separates complete expressions by default. Grammar role has priority: if the following significant syntax can start an independent expression or declaration, it remains independent; otherwise a token that can continue the preceding expression/list does so. Incomplete syntax (a trailing operator/comma/dot, recognized `=` head or open delimiter) also continues. This final 2026-10-14 rule supersedes the strict 2026-10-13 choice and the initial fixed-set Option-B formulation.

| Following syntax | Across-LF role | Reason |
| --- | --- | --- |
| `.`, expression-list `,` | Continuation | Existing member/list grammar |
| `+`, `/`, `div`, `mod`, `^`, comparisons, `and`, `or`, `xor` | Binary continuation | No independent prefix expression |
| Attached `-2`, `-x`, `-(E)`, `--2` | Independent expression | Eligible attached unary minus |
| Detached `- 2`, `-` followed by later operand | Binary continuation with a preceding left operand | No eligible unary role |
| Leading `* B` | Binary multiplication with a preceding left operand | Prefix collect is a binding role; a binding declaration wins |
| `not`, Grace `~`, `(`, `{`, `[` | Independent expression | Existing prefix/group/block/list roles; no later-line call/selection |
| Declaration head | Declaration | Never an operand |

Unary `-` is an attached prefix operator, not a signed numeric token. Negative literal pattern signs also require exact attachment (owner clarification 2026-10-14): `F(-2)` remains valid; `F(- 2)`, line/comment-separated signs and nested detached signs are syntax errors. Pattern.LitInt still stores the same literal value. The shared `IsDirectlyAttached` checks exact source offsets; whitespace, tabs, comments and newlines break unary attachment. Detached prefix minus without a left operand is a focused syntax error and is not recovered as an attached unary node. Binary subtraction is whitespace-insensitive: `10-2`, `10 -2`, `10- 2`, `10 - 2`, `10 -` newline `2` and `10` newline `- 2` subtract. `10` newline `-2` is two output rows. `--2` is nested unary minus; `- -2` at expression start is invalid, while `10` newline `- -2` is subtraction of -2. Precedence is unchanged: `-2 ^ 2` is `-(2 ^ 2)`, `(-2) ^ 2` has a negative base, and `2 ^ -2` is valid while `2 ^ - 2` is invalid. Attached non-numeric negation retains its evaluation TypeMismatch.

Leading comma continues simple property, clause and deconstruction RHS output lists as well as root/brace outputs and other expression-list contexts: `P = 1` newline `, 2` has the same body slots as `P = 1, 2`. It adds no comma syntax to other grammar categories; pattern lists and `open` target lists retain their own rules. Independent next-line slots still end a simple body. `F` newline `(1)` never becomes a call; `Data` newline `[0]` never becomes selection. A line-final star announces multiplication; actual spread requires an explicit same-line boundary (§ The spread marker).

The one continuation policy reuses the operator precedence registry and consults `StartsIndependentExpression`, `IsAttachedUnaryMinus` and the declaration-starter relation. Comments, reported lexer characters and blank lines are transparent to significant-token lookup, but cannot reconstruct attachment. Indentation, runtime values, inferred types, callable arity and resolution never decide syntax. The accessibility invariant is default separation with a continuation token announcing itself on its line; the preceding line alone cannot always settle whether the expression has ended. No empirical accessibility superiority is claimed.
Pins: `LexerTests.Tokenize_LoneCarriageReturn_IsWhitespaceThatBreaksNoLine`, `Utf16LexerContractTests`, case-distinct `ParserTests`, and `OwnerLexicalDecisionTests` and `RestrictedLeadingContinuationTests` (scoped leading continuation, AST/slot equivalence, exclusions, declaration recovery, star preservation, no backslash continuation and string escape distinction). Lean receives the elaborated core and does not implement lexing or physical-line syntax.

## Parentheses group syntax

PARENTHESES GROUP SYNTAX; THEY DO NOT INTRODUCE A SEMANTIC BOUNDARY (September 2026). A parenthesized group whose content is exactly ONE non-spread expression slot is that expression, whatever the expression's kind: `(x)`, `((x))`, `(~x)`, `(F(1))`, `(Obj.X)`, `(A[0])`, `(first(A))`, `([1, 2])`, `({ ... })`, `((1, 2))`, `(if(c, a, b))`, and `(())` elaborate to the very node that `x`, `F(1)`, `Obj.X`, `A[0]`, `first(A)`, `[1, 2]`, `{ ... }`, `(1, 2)`, `if(c, a, b)`, and `()` do. The ONE decision is `Parser.IsRedundantGrouping` — no declarations, exactly one slot, the slot is not a spread — and it never inspects the inner expression's kind, so there is no list of "kinds that keep a written level" for any layer to depend on. Consequences, all pinned: `E ≡ (E) ≡ ((E))` for the resulting value and emitted count; for normalization (`((1, 2))` IS the pair, `(())` IS `()` — grouping never suspends normalization); for every binding — fixed, collecting (`Coll((S))` is `Coll(S)`), patterned, and clause-family selection; for storage and property reads (`X = (E)` stores what `X = E` stores); for caching and value demand (`(A).count`, `count((A))`, `if(true, (A), 0)`, `(A).string` are `A.count`, `count(A)`, `if(true, A, 0)`, `A.string` — the same zero-argument property read, through the one property cache, as the ungrouped spelling; a random- or host-backed property draws the same number of times in both spellings); for selection (`(A)[0]` is `A[0]`); for the dot-call receiver (`(Obj).V` navigates `Obj`'s own member exactly like `Obj.V`, `(3).A.B` is `B(A(3))`, `(A).Coll` is `Coll(A)` by the collector law); for explicit spread (`(E)*` is `E*`, `(E)*.F` is `F(E*)`); for evaluation count and order (an argument is the same one supplied computation in both spellings, evaluated at most once, when and if it is first demanded, and a failing argument fails at the same demand; Model C, NEED-01/02); for error kind; for the callable target (`(F)(1)` is the call `F(1)`, `(~F)(1)` is `~F(1)`, and `(Box.G)(2)` calls the member `Box.G` exactly as `Box.G(2)` does — Q-18 C-B3: a dot expression has one callable identity, so grouping never changes it); for the `open` target (`open (M)` and `open ((M))` are `open M`, classified by the same owner walk); for the front-end lifting rules (`Math.Abs((A))` is the same VALUE-role position as `Math.Abs(A)`); and for every execution strategy (the optimizers see the same tree, so a planned loop plans `(T) + (T)` exactly as `T + T` and filter/count fusion fires for `(A).filter(P).count` exactly as for `A.filter(P).count`). The only groups that survive as `Expr.Capture` / `.capture` are the ones whose parentheses DO something: several written slots (`(1, 2)`, a sequence value) and a lone spread slot (`(A*)`, the capture of an item supply into one value — `capture : Supply -> Value`; a spread is a slot-level construct, not a value expression, so its group is not redundant). Those keep the capture laws unchanged: no algorithm identity (`Apply((Inc, Dec))` supplies no CALLABLE identity, so invoking it is `NotAnAlgorithm`, Q-06), no structural members (`(A*).V` and `(A, B).V` fall back lexically), not an open target (`open (M, N)`, `open (M*)` are `BadOpenForm`). Two syntactic facts are NOT boundaries and stay as they are: a marker after a closing parenthesis decorates the group, not a name, so `(x)~` is rejected by the one-name Grace eligibility rule (Grace and collect markers decorate the NAME token), and `(a.b)(1)` is call syntax on the argumentless dot edge `a.b` while `a.b(1)` is the member edge with arguments (the grammar attaches `[CallArgs]` to the dot edge itself); since a dot expression has ONE callable identity (Q-18 C-B3), `(a.b)(1)` calls the member exactly as `a.b(1)` does when `a` declares `b`, while a computed `a.b` is not callable — both pre-existing grammar productions, not parenthesis semantics. PATTERN DELIMITERS ARE NOT EXPRESSION GROUPING (the structural-pattern model, September 29 2026; [`sequences-lists-and-calls.md` § Structural patterns]): redundant grouping is a rule about EXPRESSIONS, and no pattern is ever unwrapped. `F((a, b))` declares ONE parameter slot whose argument must be a SEQUENCE value of two elements and `F([a, b])` one slot whose argument must be a LIST of two elements, while a sequence pattern with exactly one non-collecting item — `F((x))`, `F(((x)))`, `F(([x]))`, `F(((x, y)))`, `F(((true)))` — is the front-end error `SingletonSequencePattern` (`Parser.SingletonSequencePatternDiagnostic`), never a spelling of `F(x)`: a sequence value never has one item (`(7)` IS `7`), so such a pattern describes a boundary no value has. `F((*xs))` is not a singleton (the collector-only sequence pattern takes any SEQUENCE), and `F([x])` is the one-element pattern. The binder opens the argument's VALUE one level through the pattern's own kind (Lean `bindNeedOne` / C# `BindNeedPatterns` over `Result.sequencePatternItems?` / `listPatternItems?`; formerly `bindParameterPattern` / `Evaluator.GetStructuralPatternItems`) and never a written-slot view of the group the ARGUMENT was written with — `explicitItems?` / `ExplicitSequenceValueItems`, the former second view that let `F((B))` bind `[[1, 2]]` where `F(B)` bound `[1, 2]`, are DELETED and must not return — so a call-site group is still erased: `F(S)`, `F((S))`, `F(((1, 2)))`, `F({S})`, and `F((S*))` bind the same value. Spans are the only difference the group leaves: the unwrapped node takes the group's extent (F6, below), except that a NAME occurrence keeps its exact identifier span because that span IS the occurrence the semantic model builds reference, hover, and rename sites from (`WithGroupExtent`). Lean cannot see the parser, so the rule is pinned through the derived-AST corpora (`parentheses-group-syntax` and the updated `capture-suppresses-*`, `open-capture-target-rejected`, `redundant-call-parens-canonical`, `grace-in-redundant-group-is-grace-on-the-name` spec cases; `SemanticExplorerTests.DerivedLeanPrograms_MirrorParserParenthesisNormalization`), by `RedundantParenthesesTransparencyTests` (the `E ≡ (E) ≡ ((E))` observer matrix over root output, call arguments, collecting and patterned binding, spread, dot receivers, selection, lists, storage, callbacks, loop state, operators, builtin slots, and `.string`, each under the generic, optimized, and genuinely suspending async strategies, plus host-counted evaluation order and seeded-random cache probes), `OutputBundleSplitTests`, `GroupedExpressionSpanTests`, `ParserTests`, and the Lean guards in `CoreTests/CollectingParameters.lean`, `CoreTests/DotCallSemantics.lean`, and `CoreTests/OutputBundle.lean` (where a host-built single-row `capture [e]` is documented as an AST-channel shape that evaluates to `e`'s value). Selection chooses a value, dot-call passes a value, spread opens a value, parentheses group syntax.

## Delimiters, grouping extent, and unary spans

Delimiter model: `(...)` is sequence/expression grouping and call-argument syntax, `[...]` is list construction, and only `{...}` (and the root) creates an algorithm-level lexical scope. Algorithm-level declarations — `open`, property/clause definitions, deconstruction bindings — are parser-rejected inside parentheses with a targeted diagnostic pointing at `{ ... }`; brace blocks work in any expression position, including as call arguments, and their opens/local properties never leak into the surrounding scope. The parser may keep temporary Algorithm/Block structures for parenthesized sequences internally; the observable invariant is that no diagnostic-free parenthesized expression contains algorithm-level declarations. Recover unmatched root `)`, `]`, and `}` tokens in the same scope, retaining later declarations and output for editor analysis; keep the parse erroneous and preserve nested delimiter ownership. THE DELIMITER-OWNERSHIP LAW (final audit and the #9 parser-recovery audit, September 2026) decides who resolves every closing delimiter, and a closer is NEVER consumed as junk while a construct is open: (1) every nested body loop (`ParseAlgorithmBodyParts`), list, operand parse, and clause-head parse ENDS at a closer of any kind and leaves it for the innermost open construct; (2) that construct resolves it in ONE place, `Parser.ExpectCloser`: its own closer is consumed; a closer an ENCLOSING construct is waiting for (`Parser.IsOwedCloser` over the open-delimiter counts `_openParens`/`_openBrackets`/`_openBraces`) is reported as this construct's missing closer and left for that owner, which closes there (`[ (1, ]`: the group reports its missing `)`, the list closes at the `]`); a closer NO open construct is waiting for is reported as the mismatch it is and consumed as this construct's closer (`(1, 2]`, `{1, 2)`, `F((1, 2], 3)` are one diagnostic each, and `X = { A = (1, 2]` newline `Later = 5 }` keeps `Later` in `X` where it was written); (3) only with no construct open is a closer a top-level stray — `)`, `]`, and `}` alike, reported as "Unexpected '…' at the top level" and consumed in place (a root `]` used to take the primary fallback, with a different message and an invented placeholder row). Operand recovery follows the same law: a trailing comma or a missing operand before a closer (`F(1, )`, `(1 + )`, `[1, ]`, `{1, }`) reports one `UnexpectedToken` at the closer, recovers the slot as a placeholder, and never consumes the closer — before #9 a closer nothing was waiting for was consumed there as junk, which left the construct open to the end of the file whenever the typo was a WRONG closer (`(1, }` newline `B = 2` swallowed `B` with cascading `DeclarationInParentheses` reports); an unowed closer is now left silently for the innermost construct, whose mismatch diagnostic reports it. CONSEQUENCE: every closer closes at least one open construct, so a malformed region whose delimiters balance by COUNT — whatever their kinds — closes every construct it opens, and a declaration written after it on a new line stays where it was written. The price is paid only by an EXTRA closer followed by more content (`{ 1, ) 2 }` now reports the mismatch and the orphaned `}`), never by later source. Because a non-consuming return must be matched by a loop that ENDS at the token, the exhaustive delimiter-soup sweep in `RootStrayCloserRecoveryTests` (every string over the delimiter alphabet up to five characters) pins termination, a linear diagnostic count, and the count-balanced consequence, and `MalformedSourceRecoveryTests` repeats the sweep over declaration-head and continuation tokens. Semicolon recovery consumes the `;` and stops at a declaration head, a closer, or the end of input instead of claiming the next line's declaration as a slot. Pinned by `RootStrayCloserRecoveryTests` and `MalformedSourceRecoveryTests`. A GRACED name inside redundant parentheses is the graced name whatever the marker's weight (`Parser.IsRedundantGrouping` never looks at the inner kind: `(~obj).V` is `~obj.V`, the ordinary structural-first dot edge on `obj`, and `(~a)(b)` is the call `~a(b)`) — Grace is stripped before evaluation and never changes selection; pinned by `OutputBundleSplitTests`. GROUP EXTENT (F6): an expression the parser unwraps from redundant grouping parentheses keeps the group's FULL written extent as its `Span` (`Parser.WithGroupExtent` — nested groups accumulate, `((1))` spans all five characters, and a registered operator-chain depth is transferred to the re-spanned copy so the chain guard keeps counting through the group); the span is the ONLY thing that changes, so `(1) + 'a'` is located from the `(` while AST shape, grouping semantics, and evaluation are untouched. The ONE exception is a name occurrence (`Expr.Resolve`, and the graced occurrence `Expr.Grace` wraps): `(x)` is the node `x` with the exact span of the identifier `x`, because that span is the occurrence the semantic model builds reference, hover, and rename sites from — a source-position fact only, never a semantic one. Line-sensitive diagnostic wording therefore never reads an unwrapped node's span: the line-final-star explanation decides from the TOKEN stream (`Parser.IsLineFinalOperator`, the operand's first significant token), so `A * (` newline `B)*` is the ordinary misplaced spread whatever the grouped name's span. Pinned by `GroupedExpressionSpanTests` and `StarSyntaxTests`. Likewise a unary operand rejection — the one numeric-operand `TypeMismatch` of `-` for every non-numeric operand, `-'a'`, `-()` and `-(1, 2)` alike (Q-27; `-()` and `-(1, 2)` were the numeric conversion's `BadArity` until October 5 2026) — as well as the Boolean-operand rejection of `not [1, 2]`, carries the unary expression's span from the ONE `Evaluator.ApplyUnaryOperator` (F5; `UnaryOperandSpanTests`), never a spanless error.

The braces of an INTERPOLATION HOLE are not delimiters of this model: they are their own tokens (`InterpolationHoleOpen` / `InterpolationHoleClose`), the hole creates no scope and admits no declaration, and it is an OWNERSHIP BARRIER for the delimiter-ownership law — a closer inside a hole is resolved inside it, never by an enclosing construct, and the hole's own `}` is the one closer it is owed. A literal brace in string text is `{{` / `}}`, and a lone `}` there is the lexer's `UnmatchedBraceInString`, never a root stray closer (§ Strings and interpolation).

## Comma and same-line items (SYN-07A)

Comma is the explicit expression-list separator, and on one physical line it is the ONLY separator (SYN-07A): whitespace never creates a slot boundary, so `1, 2, 3` is three slots while `1 2 3`, `F(1 2)`, `(1 2)`, `[1 2]`, `2(3)`, `A[0](1)`, `2m`, and `P = a b` are the targeted parse error `DiagnosticCode.UnseparatedSameLineItem` (public `KatLangErrorCode.UnseparatedSameLineItem`), reported at the first token of the second item with ONE generic message naming the three repairs (a comma between slots, an operator to continue the expression, a new line for a declaration) and never guessing intent. ONE ownership point decides slots — `Parser.StartsNextExpressionListSlot`, reached by every expression-list context through `ParseExpressionListOperand` — and the body loop's per-item row check decides declarations: `open`, property/clause definitions, deconstruction patterns, and `public …` must begin a physical line or follow the opening `{` directly (`1 P = 3`, `x = 3 y = 4`, `{ d = 2 n * d }` are the same error). Parameter-pattern lists (clause heads and nested sequence and list patterns) follow the same rule through their own ONE boundary decision — `Parser.StartsUnseparatedPatternItem`, reached through `ParsePatternItems`, over the atom grammar's starter set `CanStartPatternAtom` (a star counts only when an operand follows it — the SYN-07B classifier — so a star nothing can follow keeps its existing marker or closing-delimiter recovery) — reporting the SAME code with a pattern-worded message that names the comma as the only repair, and recovering the item as the next pattern of the SAME head: `F(a b) = a + b` recovers as `F(a, b) = a + b`, so the head's `)` and `=` are found where written and nothing leaks to the enclosing scope; a next-LINE pattern without a comma is NOT admitted (parameter lists have no newline separator) and keeps the ordinary closing-delimiter diagnostic, after which the head's recovery skips to the head's own `)` (clause-head confinement, see the line rules below), so `F(a` newline `b) = a + b` reports one parse diagnostic and keeps its body (the skipped `b` declares no parameter, so the body's `b` then gets the ordinary closed-list undeclared-identifier error). Recovery is a slot boundary, never a grammar hole: the second item stays the next slot of the SAME list (`P = a b` keeps `b` in P's body and leaks nothing to the enclosing scope; `F(1 2)` recovers as a two-argument call) or the declaration it spells, and recovery sites that already own a boundary (rejected Grace runs, detached markers, stray root closers, bad tokens, open-target leftovers, single-token primary recoveries) call `OwnSameLineItem` so the separator rule stays silent there — one diagnostic per malformed boundary. A newline is a separate mechanism — a body/statement/output boundary: at root output or inside an explicitly open context (`(`, `[`, `{`, an argument list) a newline between independent expressions separates slots (so `1`/`2`/`3` on three lines are three output slots and `F(` newline `1` newline `2` newline `)` is a two-argument call), but a simple property body ends at a newline before an independent next-line expression. Designated leading tokens continue its existing expression/list instead. Ordinary expression continuation is never a slot boundary: `F(1 -2)` is the one argument `1 - 2`. Root output consumes a bare expression list as output slots; call syntax consumes it as argument slots; parentheses materialize it as one sequence value. Parsing must not depend on callable arity, runtime values, inferred types, or any other semantic information. Pinned by `SameLineSeparatorTests` and the `same-line-*` `LanguageSpecCorpus` cases.

## Line rules and declaration heads (F7)

Call, selection and annotation continuations bind on the same physical line only; leading dot follows the Q-65 table. A `(` or `{` after a callable target on the same physical line is a call delimiter even across whitespace, while a physical newline never continues a closed expression into a call. A CALLABLE TARGET is a callable reference only (Q-18 C-B3, decided October 5 2026): a name, a graced name, an argumentless dot edge, or a redundant group of one — the parser's call gate admits exactly `Expr.Resolve`, `Expr.DotCall { Args: null }` and `Expr.Grace` — so a call never follows an already computed call result: `X.Mk(1)()`, `R.M(a)()` and `R.M(a){ … }` report `DiagnosticCode.UnseparatedSameLineItem` at the second item exactly as `Mk(1)()` does, and the member call is written `(X.Mk)(1)` or `X.Mk(1)` (formerly the gate admitted every dot edge, so `R.M(a)()` parsed as a call of the computed result). For multiline calls, open the delimiter before the newline. The postfix selection bracket `[`, postfix Grace remains same-line only; binary operators use grammar-priority continuation. Star retains the separate SYN-07B/Q-33 law below. Designated leading continuation follows the table above, including member chains and expression-list commas. Definition bodies and open target lists end before independent next-line items; incomplete syntax and designated tokens retain their scoped continuation rules. Root and brace bodies separate independent newline output slots. DECLARATION HEADS ARE LINE-LOCAL (F7): every declaration lookahead (`LookaheadIsEqualsFrom`, `LookaheadIsParenEqualsAfterName`, `LookaheadIsBindingPatternAssignmentFrom`, `LookaheadThroughTildesToPropertyDefFrom`, the `public` lookaheads) applies the ONE predicate `Parser.IsHeadToken`: a simple definition/deconstruction head shares one physical line; a clause head's name and `(` share a line, its closing `)` and `=` share a line, and the list inside the open parentheses may span lines; `public` and any rejected head markers share their name's line, so a newline never assembles a head after the fact — `Foo` newline `(x) = x + 1`, `A` newline `= 1`, `Foo(x)` newline `= x + 1`, and `x, y` newline `= 1, 2` keep the first line as its closed output row and reach the stray-`=` diagnostic (`Parser.StrayEqualsDiagnostic`, `DiagnosticCode.UnexpectedToken`), comments and indentation changing nothing. Explicit continuation AFTER a recognized head is deliberate and unchanged: the body of `A =` / `Foo(x) =` may start on the next line like a trailing operator's operand, and a trailing `.` continues its dot chain (`a.` newline `b` is `a.b`). Pinned by `DeclarationHeadLineRuleTests` and the `declaration-head-never-spans-lines` `LanguageSpecCorpus` case.

A DECLARATION HEAD IS NEVER AN OPERAND (#9 parser-recovery audit, September 2026). A line that ends in an incomplete expression — a trailing binary or comparison operator, `^`, `and`/`or`/`xor`, a trailing `,` or `.`, a prefix `-` or `not`, or the `=` of a definition, clause, or deconstruction whose body would begin on the next line — continues onto the next line only into an EXPRESSION. When the next line begins a declaration head, that head is never the missing operand, slot, selector, member, or body: the incomplete line is the one error, reported at the token that dangles ("Expected an expression after '+'. The next line begins a declaration, which never continues an expression."; for a trailing `.`, "Expected property name after '.'. …"), and the declaration keeps its scope and visibility (`1 +` newline `Good = 41`, `x,` newline `y = 1, 2`, `A =` newline `B = 1`, `1 +` newline `public Good = 41`). Taking the head's name as the operand used to tear a correctly written one-line head into an operand plus a stray `=` — reported with the head-line explanation, as though the declaration were the malformed part — and to lose the declaration (with its visibility, or a whole `open`). No valid program ever has a declaration head in operand position (its `=` could only be stray), so this changes recovery only. The decision is `Parser.RecoverAtOperandStart`, at the one operand chokepoint (`ParsePrimary`), plus the member position of `ParseDotCallContinuation`, and it uses THE declaration-starter relation `Parser.StartsDeclaration` — `open`, property, clause, binding-pattern, and invalid-Grace heads, `public`-led heads, and reserved-literal heads (`true = …`) — the same relation the slot boundary, semicolon recovery, open-target recovery, and the star classifier stop at, so every loop stops exactly where the operand is refused (the relation first omitted the reserved-literal heads, and `A` newline `true=` looped forever: a non-consuming refusal must be matched by every loop that could re-admit the token). The star's own declaration exception (SYN-07B), semicolon recovery, and the dangling `open A,` list already followed this rule; the rule now holds for every continuation token. The genuine newline-split heads are unchanged: the stray `=` of `A` newline `= 1`, `x, y` newline `= 1, 2`, or `Foo` newline `(x) = …` keeps the head-line explanation, while a stray `=` that follows other content on its own line (`A = x = 1`, `[A = 1]`) says that `=` only ends a declaration head at the start of a row and points at `==` (`Parser.StrayEqualsFollowsSplitHead`). Q-65 extends the protection to a head that shares the line of a LEADING continuation token (`1` newline `+ Good = 41`, `x` newline `, y = 1, 2`, `A` newline `.Good = 41`), never to a head after a MID-line operator, comma, or dot: `X = a + b = c`, `[1, b = 2]` and `X = A.b = 3` keep `b` as the operand or member and report the same-line stray `=` (`Parser.PreviousLeadsItsPhysicalLine`; `RestrictedLeadingContinuationTests`).

CLAUSE-HEAD CONFINEMENT (#9). A clause head is recognized only when its parentheses close within themselves (`Parser.TryFindClauseHeadClose`): the prospective head is itself an open construct, including at the root. Any mismatched closer inside it makes it no head; ordinary delimited parsing resolves that closer. A scan must never cross a mismatch to find a later `) =`, because source after the already-closed region belongs to the enclosing scope (`F(]` newline `Good = 41` newline `) = 1` retains `Good`). A recognized head's recovery never leaves its own region: a token the pattern grammar cannot use is reported once and the rest of the head is skipped to the head's own `)` (`SynchronizeToClauseHeadClose`); an opening `{` in a pattern is reported and skipped with its whole group (`F({a, b}) = …` keeps its `)`, its `=`, and its body; `[` opens a list pattern since the structural-pattern model of September 29 2026, so `F([a, b]) = a + b` is valid); a closer is never consumed by pattern recovery (`F() = 1` reports once); the reserved-literal head skip consumes exactly the recognized head (`false(x = 1) = 2`). The head's `)`, `=`, and body are therefore found where written — `F(x +) = x`, `F(1 + 2) = 3`, `F(a.b) = 3` are one diagnostic each where they used to cascade into up to eight and leak the body to the enclosing scope as output rows. A head that needed recovery keeps its clause (and its declaration) in the family but takes part in no cross-clause check — duplicate patterns, top-level pattern arity, and output arity are judged among the clean heads only, with the first clean head as the reference; equality-transparent internal `CondBranch.HasRecoveredHead` metadata carries that same decision through elaboration to editor signature selection — so a malformed clause never poisons a valid one with a spurious `DuplicateBranchPattern` or `BranchArityMismatch`. Several collecting bindings at one pattern level (in an ordinary or literal-headed clause, or a deconstruction) are reported as before and recover as the FIRST collector with the later ones ordinary fixed bindings, so no recovered tree carries a shape a valid program cannot have (the callable binding planner behind editor signatures rejects such a shape outright; `SemanticModelBuilder.Build` used to throw on `F(*a, *b) = a`). Every lexical error inside a head also makes it recovered, including an inserted separator (`F(x @ y) = x`) or a malformed number/string recovered by the lexer; the parser cannot infer cleanliness from newly added parser diagnostics alone. Synthetic recovery binders have unique, unwritable names, absent spans, and equality-transparent `IsRecoveryPlaceholder` presentation metadata, so they cannot capture a real `_error_` declaration or conflate separate holes.

A PHYSICAL LINE BREAK is the line feed alone: `\r\n` breaks the line through its `\n`, and a lone `\r` is whitespace that advances no line and no column (it still ends a comment, or a string of either quote kind with any hole still open in it), so every line rule above reads a CR-only file as one physical line. Stated in `KatLang.ebnf` and pinned by `LexerTests` and `Utf16LexerContractTests`.

REPORTED CHARACTERS ARE INVISIBLE TO THE GRAMMAR (#9). The lexer reports each character it cannot recognize once (`UnexpectedCharacter`) and keeps it in the token stream as a `Bad` token, so token consumers such as colorizers still see every code unit. The parser skips that token exactly like a comment (`Parser.IsSkippedByGrammar`, the one predicate behind `Current`, `Advance`, `Previous`, `NextSignificantIndex`, and `PreviousSignificantIndex`), so no grammar decision — continuation, slot boundary, declaration lookahead, star classification — turns on it, and the parser never reports it again (at the START of the document, where no significant token precedes the current one, `Previous` never answers with a comment: the line reference is the reported character a missing operand would claim — the nearest one before the current token — or else the current token itself, so a leading comment changes no decision and `# c` newline `$+` recovers exactly like `$+`, found by the #14 campaign as FZ-R2): `A @= 1` is the declaration `A = 1`, `F@(x) = x` the clause, `F(x)@ = x` too, `1@ + 2` the sum, `A@.B` the member access, `open @Math` the open, and `[1` newline `@ 2]` the two-item list. Where the grammar needs a piece exactly where such a character stands — between the previous significant token and the current one — the character IS that piece, filled without a second report (`Parser.TakeReportedCharacterBeforeCurrent`): a missing operand followed by a closer, the end of input, `,`, `;`, or a token that continues the expression on that line (`(1 + @)`, `F(1, @)`, `1 < @ < 2`; a placeholder at the character's span), the operand a declaration on the next line refuses (`1 +` newline `@` newline `Good = 2`), a member name (`A.@`), an open target (`open @` on the `open` line, `open M, @`) or the comma between targets, a pattern item (`F(x, @) = x`, whose head is then a recovered head), and the comma between two same-line items (`P = 1 @ 2` keeps both slots in `P`). In operand position the fill is limited to followers the surrounding construct takes next, so every other follower still reaches the ordinary operand path that consumes it, and a loop handing the same token back always makes progress. A skipped run fills at most one missing piece: `A.@ 1` uses the character as its member placeholder and still reports the missing comma before `1`. Structure is never filled: a construct still missing its closer or a head its `=` reports that as its own error (`(1 @` reports the missing `)`), and marker attachment stays exact source adjacency, so a character between a marker and its name or operand also detaches it (`A@*` is a detached spread marker). Consequently a valid program with a reported character written at any token boundary not next to a marker parses to the same program with the lexer's diagnostic as its only one, and that diagnostic alone keeps the document from evaluating. Pinned by `MalformedSourceRecoveryTests` (including that law over every tutorial and executable-specification program), `SameLineSeparatorTests`, and `CliApplicationTests`.

## Star roles

The star `*` has three roles resolved purely syntactically: prefix COLLECT MARKER in binding patterns, postfix SPREAD MARKER on a completed expression, and infix multiplication — the marker surfaces match the semantic directions `collect : Supply -> ListValue` and `spread : Value -> Supply`. PREFIX `*name` is the ONLY collecting BINDING syntax, valid only in binding positions — explicit parameter lists (`F(*items)`, `F(first, *middle, last)`), nested structural parameter patterns, sequence and list alike (`F((x, *y, z))`, `F([h, *t])`), and assignment deconstruction, including the single-target form `*items = RHS`. The collect marker must be DIRECTLY attached to its binding name (exact source-offset adjacency — no whitespace, comment, or newline between; `* items` is a targeted attachment error that never creates a collecting binding, and `**items` is a repeated-marker error), and exactly one marker forms a binding. Prefix `*` is NOT an expression operator: in expression position it reports a targeted collect-marker diagnostic and recovers to the following operand. The old spellings `name...`, `...name`, `spread(expr)`, and `expr.spread` are NOT KatLang syntax: there is no ellipsis token (`...` lexes as three dot tokens and fails through ordinary parsing) and `spread` is an ordinary identifier with no reserved meaning.

## The spread marker (SYN-07B) and the marker attachment law

The postfix spread marker is `expr*`, directly attached to its operand, and valid only in an explicitly closed same-line spread context (Q-65 owner addendum, 2026-10-14). A same-line comma, closing delimiter, fluent dot or another closed spread layer establishes that context: `A*, B`, `F(A*)`, `[A*]`, `Data[Indexes*]`, `A*.F`, and `(A**)`. A physical line-final star always announces multiplication, including before EOF, a later-line closer or a declaration. `7*` at EOF is a missing multiplication operand, never scalar spread; `7*` newline `X = 8` diagnoses the dangling star and preserves X. Both `A*` newline `B` and `A *` newline `B` multiply with ordinary precedence; comments and blank lines manufacture no spread boundary. A leading star can likewise be binary continuation under grammar priority, unless it starts a collecting declaration. This supersedes only the conflicting line-final classification from Q-33/SYN-07B; collect binding and spread VALUE semantics are unchanged.

Classification precedes attachment: actual spread requires exact source-offset adjacency (`F(A *)` is `InvalidSpreadMarker`); multiplication is whitespace-insensitive. Prefix collect and Grace retain their existing attachment rules. A spread before another supplied item needs a same-line comma. A spread-ending definition uses a same-line closing delimiter (`X = (A*)` or `X = { A* }`); a declaration or EOF cannot close it implicitly. Bare root-final `Values*` is intentionally incompatible with the former syntax: express spread in an explicitly closed receiver, or put a real following output after a same-line comma. Capture/brace closure makes one value and must not be described as preserving root row cardinality. The schematic spread expressions below denote slots with the required explicit boundary.

The marker lowers at parse time to the ONE unary `Expr.SequenceSpread` node (Lean `sequenceSpread`) — never to a Call or DotCall — so there is a single evaluator path, no ordinary call/property value boundary is introduced, and the operand is evaluated exactly once. Chained spread is compositional: `value**` equals `(value*)*` — each extra written star spreads the value that the previous star's supply re-captures at the ordinary expression boundary (`spread` then `capture` then `spread`), so a multi-item supply is a fixed point (`[[1, 2], [3, 4]]**` supplies the two inner lists unchanged) and only a lone structured item opens one more boundary (`[[7]]**` supplies `7`); it is NEVER recursive flattening. `value**next`, `value** next`, and `value**` newline `next` are targeted errors — the second star is multiplication with a spread operand, never exponentiation. A spread expression is legal ONLY as a whole expression-list slot (root/body rows, call argument slots, group and list elements, definition body slots), as the operand of another spread, or as the FLUENT DOT-CHAIN receiver: `operand*.Member(...)` lowers at parse time to the ordinary LEXICAL call `Member(operand*, ...)` with the spread as the leading argument slot — the receiver is an item supply, not a value, so structural member lookup never applies (`x.Calculate*.Target` builds the same AST as `Target(x.Calculate*)`, and further postfix continuations chain on the call result). GROUPING THE SPREAD CHANGES THE RECEIVER, and the difference is the ordinary capture rule, not a star rule: `A*.F` keeps the spread a SUPPLY and lowers to the lexical call `F(A*)` (items become argument slots), while `(A*).F` is a CAPTURE receiver — ONE ordinary leading argument whose value is the captured sequence: `(A*).F` is `F((A*))`. With `A = (1, 2, 3)` and `Coll(*xs) = xs`, `A*.Coll` collects the three items `[1, 2, 3]` while `(A*).Coll` collects the ONE captured value `[(1, 2, 3)]` — values stay values, so the collector never opens its argument. The same holds for a list operand: with `A = [(1, 2)]`, `(A*).Coll` collects the captured value `[(1, 2)]`, and `A*.Coll` collects the one spread item `[(1, 2)]` because spread-produced items are never reopened. At fixed arity, `A*.count` is an arity error (three argument slots) where `(A*).count` is 3; beside a collector, a fixed suffix receives the grouped value whole (`(A*).F` with `F(*mid, last)` binds `last` to that value), while the fluent form supplies separate slots. (`(A)*.F` is different again — that groups only the OPERAND, so it stays the fluent supply form.) Using a spread expression as a unary/binary operand is a targeted parse error with unwrap recovery; a spread is a legal whole selector SLOT of a postfix selection (`Data[Indexes*]`), and a star before a `[` is never a spread receiver — `A*[0]` is the multiplication `A * [0]` (capture-then-select is `(A*)[0]`, select-then-spread `A[0]*`).

## Postfix selection

POSTFIX SELECTION SYNTAX (October 2026; the semantics are `sequences-lists-and-calls.md` § Variadic postfix selection). `PostfixOp = "[" [ ExpressionList ] "]"`: a `[` on the SAME physical line as the receiver's final token (same-line spaces and tabs allowed — `Data [0]`, `Grid [0] [1]`, `Data() [0]`) opens the selector list of a postfix selection over ANY completed postfix-level expression — a name, a group, a capture, a list literal, a number, a string, a block, a call result, a dot edge (`BuildData(n)[0].sum` selects then calls). The selector list is the list literal's production (`Parser.ParseSelectionContinuation` through `ParseExpressionListOperand`): zero or more slots, commas between same-line slots and newlines between rows once the bracket is open (`Data [` newline `0,` newline `1` newline `]`), whole-slot spreads, the SYN-07A separator rule inside (`Data[0 1]`), the #9 delimiter ownership (a `]` closes the selection; `F(Data[0)` reports and leaves the `)` to `F`) and the cumulative nesting budget (`SelectionNestingSurcharge`, the list literal's 3 units per level). The chain depth is the receiver's (`GuardExpressionChainDepth` over the target only). A `[` on a LATER line never continues the previous expression: it begins a new list literal (`Data` newline `[0, 1]` is two rows). A `[` that a recovery already owns stays that recovery's next slot. A selection is never a call target (`A[0](1)`, `A[0] {1}` are `UnseparatedSameLineItem`), and `[` is never a call delimiter. THE RETIRED COLON: `:` is not KatLang syntax; a same-line `expr:selector` reports `DiagnosticCode.RetiredColonSelection` over the `:` and its old primary selector and recovers as the selection it meant (`Pair:0` → `Pair[0]`; a spread receiver before the `:` is unwrapped silently, so `values*:0` is ONE report), a `:` with no same-line primary after it reports alone, a `:`-led line reports the same code, and a `:` that begins an interpolation hole or follows the hole's completed expression stays `InvalidInterpolationHole` (a `:` where the hole's expression still needs an operand, `"{a + :0}"`, is that operand's own `RetiredColonSelection`, and the hole adds no second report). A prefix-Grace selector is an old primary too: `xs:~i` recovers as `xs[~i]`. The lexer still produces `TokenKind.Colon` (stable public enum) so the migration diagnostic can be reported. Pinned by `PostfixSelectionSyntaxTests`, `ParserTests.Parse_SameLineSelection_RemainsPostfixSelection`, `SameLineSeparatorTests`, `StarSyntaxTests.BracketAfterAStar_IsMultiplication_NeverASelectionOfTheSpread`, `ListValueTests.BracketAfterExpression_OnTheSameLine_IsPostfixSelection`.

## The `open` declaration

`open` is a declaration/import directive, not an output expression: it takes ONE comma-separated target list (`open A, B, C`; a string target is a hole-free string literal of either quote kind — `open 'url', A` or `open "url", A` — and an interpolated string target is `DiagnosticCode.InterpolationNotAllowedHere`, consumed as one atom), parsed by a dedicated comma-list parser into individual targets (resolve, argumentless dot-call path, block, or string-load sugar). Each algorithm allows at most one `open` declaration, and it is the body's IMPORT PREAMBLE: it precedes every declaration and output row of that body — clause definitions included, because `P(a) = a` declares a property exactly as `P = a` does, so `P(a) = a` / `open Lib` and an `open` between two clauses of one family are `InvalidOpenDeclaration` like `P = a` / `open Lib` (the parser buffers clause definitions in their families until the body ends, and its placement check counts them explicitly; constitution PV-25). The rule is per body: each nested `{ ... }` body, a clause body included, has its own preamble, and an `open` still resolves a head declared later in the same body. A target is an open form ALL the way down: the HEAD of a dotted path's receiver chain must itself be a name, a `{ ... }` block, or a `load` module (`AstHelpers.OpenTargetHead`, the one decomposition every static consumer reads; Lean `resolveAlgForOpen` recurses through the receiver), so `open 5.N`, `open F(1).N`, `open (A, B).N`, `open [A].N` and `open ('url').N` are `BadOpenForm` at the head exactly like `open 5`, `open F(1)`, `open (A, B)`, `open [A]` and `open ('url')` — the parser used to check the outer node only, and the evaluators refused such a head only when some lookup consulted the level (constitution PV-11). The first target must begin on the same physical line as `open` (`open` newline `A` is a missing-target error and `A` stays a separate row). Comma keeps its normal explicit line-continuation behavior — `open A,` newline `B` and `open A` newline `, B` both continue the list — and a leading `.` continues a dotted target (`open A` newline `.B` is `open A.B`), but a plain newline never continues `open`: `open Math` newline `Math.Pi` is an open plus a report row. `;` and a bare same-line second target are NOT open-target separators (`open A ; B` and `open A B` report a missing-comma diagnostic, never two targets). An explicitly comma-closed spread-marked open target (`open A*, B`) parses to a spread expression and is rejected by open-form validation — spread is not an open form. Operator forms (`open -~x`, `open ~x + 1`, `open ~x < 1`, `open x[~y]`, `open 1 + { ~k }`) are rejected the same way (`BadOpenForm`), and their recovery tree is still fully elaborated: parameter detection and implicit-argument resolution process an operator-form target's operands exactly like a capture target's rows (`ParameterDetector.ProcessOpenExprCore`, `ImplicitArgumentResolver.ProcessOpenExprCore`), so every written Grace is consumed, nested blocks are elaborated, and dot-call fallbacks are normalized — the post-elaboration contract (`DotCallElaborationInvariant`: no Grace survives, every fallback explicit) holds for diagnostic recovery trees too (found by the #14 campaign as FZ-R1; these passes once treated operator forms as host-only leaves).

## Operator precedence, comparison chains, and prefix `not`

Diagnostic postfix targets follow the same binding-tier rule as operator operands: unary expressions and negative host literals retain their parentheses in dot/call receivers, selection receivers, and spread operands (`(-a).f`, `(not a).count`, `(-2)[0]`, `(-2)*`). Dropping that grouping changes the expression being described. Diagnostic rendering bounds its pending work as well as its output: both expression names and planned-loop chain descriptions schedule links one at a time, including arbitrarily wide host chains.

A host-built chain with no links has no source spelling. Its diagnostic name is the explicit placeholder `<comparison with no links>`, never its first operand's name: evaluating that operand is followed by the chain's `true` result, so naming just the operand would imply a different expression.

Precedence from loosest to tightest: `or` < `xor` < `and` < prefix `not` < the ONE comparison tier (`<` `>` `<=` `>=` `==` `!=`) < (`+` `-`) < (`*` `/` `div` `mod`) < prefix `-` < `^` (right-associative) < postfix `.`, selection `[…]`, and call application.

COMPARISON CHAINS (September 2026, a pre-release breaking change with no compatibility layer): equality and ordering no longer occupy separate tiers. All six comparison operators share one precedence level, and consecutive UNPARENTHESIZED comparison operators at one syntactic level form ONE comparison chain — the dedicated AST variant `Expr.Comparison(First, Links)` / Lean `Expr.comparison first links`, one `ComparisonLink(Op, Operand)` per written operator, the operators drawn from `ComparisonOp` (Lean `ComparisonOp`), which is disjoint from `BinaryOp`: a comparison is never a binary node, and a one-link chain (`a < b`) is the ordinary comparison. The chain has ADJACENT-PAIR semantics: `a < b <= c == d != e` means `a < b`, `b <= c`, `c == d`, `d != e`, and is `true` iff every link holds; mixed chains are ordinary (`a < b == c`, `a == b < c`, `a != b <= c`), and `!=` compares adjacent pairs only — `1 != 2 != 1` is `true`, never "all distinct". Each link keeps the operand rules of its operator unchanged (total structural `==`/`!=`, numeric-scalar-only ordering, Booleans unordered, the string rejections). Parentheses are explicit expression boundaries: a parenthesized comparison is an ordinary operand that never merges into the surrounding chain, so `(a < b) == true` compares the group's Boolean, `a < (b == c)` orders a number against a Boolean (the ordinary rejection), and `(a < b) == (c < d)` compares two Booleans; redundant parentheses around a whole chain leave one chain re-spanned to the group (F6). EVALUATION is incremental and left to right — `Evaluator.EvalExpressionSpineCounted`'s Comparison case (iterative, one spine frame per chain), its `// MIRROR OF` async twin, and `LoopOptimizer.EvalLoopComparisonPlan` for the planned loop, all applying each link through the ONE `Evaluator.ApplyComparison` (Lean `applyComparison`, `evalComparisonCounted`): evaluate operand 1, evaluate operand 2, compare, evaluate operand 3, compare it with the PREVIOUS VALUE, and so on. Every operand is evaluated EXACTLY ONCE (the previous operand's value is carried to the next link; the parser never lowers a chain to `and`, which would evaluate the middle operand twice); a `false` link never stops the chain (KatLang's eager Boolean composition — `3 < 2 < true` still compares `2 < true` and reports that link's ordering rejection); an error terminates it in the ordinary way (a failing earlier operand or link means the later operands are never evaluated; resource-limit errors also terminate evaluation, and host cancellation throws OperationCanceledException with the supplied token). A host-built chain with no links evaluates its first operand and is `true`. A link's rejection carries the operand-shape context of ITS two operands — `while evaluating `2 < true``, never `(1 < 2) < true` — at the hull of the two operands' spans (`Evaluator.ComparisonLinkSpan`; the chain's own span when an operand is unpositioned). Implementation: `Parser.ParseExpressionCore` treats `ComparisonPrecedence` (5) specially in the precedence-climbing loop — the right operand climbs from the additive tier (so it can never absorb a comparison operator), consecutive grammar-continuing comparison operators extend one link list (`ExtendComparisonChain`, which rejects spread operands in written order — the first operand when the chain opens, then each link operand), and the chain closes at the first non-comparison token (`CreateComparisonExpression`, which constructs the node and applies the chain-depth guard, one level per chain however many links); `BinaryOperatorPrecedence`/`ComparisonOpOf`/`BinaryOpOf` replace the former binary-op table; `KatLang.ebnf` spells the tier as `ComparisonExpr = AdditiveExpr { ComparisonOperator AdditiveExpr }` with the chain semantics annotated. Malformed input never recovers into a different valid chain (a missing operand is a placeholder link, spread operands are rejected in every position in written order, a misplaced `not` recovers as a parenthesized operand). Pinned by `ComparisonChainParserTests` (structure, the pairwise precedence contract, parentheses, spans, line rules, recovery), `ComparisonChainEvaluationTests` (adjacent pairs, exactly-once through host-operation counters and seeded draws on the sync, async, and planned paths, eager-after-false, error ordering, link spans and contexts, strategy and twin parity), `ExprNameRendererTests.Golden_ComparisonChains_RenderExactly`, CoreTests `ComparisonChains.lean`, the language-spec cases `comparison-chains-compare-adjacent-pairs` and `comparison-chain-is-eager-after-false` (their Lean programs derived from the parsed chain AST, so parser tests and Lean/C# differential tests are two distinct layers), and — from the September 2026 hostile audit of a downstream "`a < b == c` is false" claim — `ComparisonChainAuditTests` (the audited chains as one flat node, adjacent-pair truth on the generic, async-twin, and planned-loop strategies, the left-associated reading reachable only through written parentheses and disagreeing, exactly-once left-to-right traces of the `a < b == c` shape, adjacent-operand link contexts, and the editor model over chain operands) with the explorer specials `chainLtThenEq`, `chainLtThenGt`, `chainNeThenLt`, and `chainFalseFirstThenEqFalse`, whose derived Lean guards discriminate adjacent pairs from left association. The final review of September 2026 added `ComparisonChainDifferentialOracleTests` — generated chains and parenthesized trees judged by an independent value model on the generic, optimized, planned-loop, and suspended-async strategies (exactly-once left-to-right operand traces, eager past `false`, the first failure ending the chain, and parentheses as the only chain boundary in the tree, its diagnostic names, and its value), mutation-verified against every strategy's chain evaluation — and the explorer specials `chainGroupedNotOperand`, `chainParenLeftUnderOrdering`, `chainNegatedBasePower`, `chainNegatedPowerOperand`, `chainGroupedNegatedBasePowerOperand`, `chainArithmeticTiers`, `chainMiddleOperandError`, and `chainGroupedSelectionReceiver`, which pin the tier's precedence neighbours, grouping on either side of a link, an operand's own error between links, and a grouped chain as a postfix receiver against Lean.

`not` is NOT a member of the prefix-unary tier that `-` occupies: it binds less tightly than every comparison, arithmetic, and power operator and more tightly than the binary logical operators (comparisons > not > and > xor > or, Python-style, September 2026), so `not x > 3` parses to `Unary(Not, Comparison(x, [> 3]))` — it is `not (x > 3)` — `not a < b < c` negates the whole chain, while `not a and b` is `(not a) and b`, `not not x > 3` nests, `not x + 1 > y` negates the whole comparison, and `not 0 ^ 0` is still `not (0 ^ 0)`. Parentheses override the rule: `(not x) > 3` compares the negation itself (a type error for a numeric `x`, never special-cased) and `not (x > 3)` is the same tree as the bare spelling. Unary `-`, the and/xor/or ladder, the per-link comparison semantics, and the newline rules are unchanged by these rules: `-x ^ 2` is still `-(x ^ 2)`, `1 + -x` still parses, a line ending in `not` or in a comparison operator (like a line ending in any binary operator) is incomplete and continues on the next line, and a `not`-led line starts an independent expression, while a comparison-led line continues the existing chain (Q-65, 2026-10-14). A `not` at its tier may begin a whole expression or the operand of `and`/`xor`/`or`; where a comparison, arithmetic, power, or prefix-minus operand is required (`1 + not x`, `a == not b`, `2 ^ not x`, `-not x`) the parser reports `DiagnosticCode.UnexpectedToken` at the keyword with a message naming the ladder and the parenthesized repair (`Parser.MisplacedNotDiagnostic`), and recovers by parsing the negation as if it were parenthesized. A same-line `not` after a star is rejected as unseparated syntax; a physical line-final star always announces multiplication and cannot close as spread before `not` or a declaration. Spread requires explicit same-line closure (current SYN-11/Q-65). Implementation: `Parser.ParseExpressionCore` handles `not` as the `NotPrecedence` (4) prefix arm of the precedence-climbing core, `ParseUnary` handles only `-`, `ParsePrimary` diagnoses a misplaced `not`, and `KatLang.ebnf` spells the tier as `NotExpr`. DIAGNOSTIC NAMES follow ONE precedence-tier rule so the rendered text reads back as the rendered AST (`ExprNameRenderer.BindingTier` with the slot tiers `LeftOperandTier`/`RightOperandTier`/`PushComparisonOperand`/`PushDiagnosticUnaryOperand`; Lean `bindingTier`, `leftOperandTier`, `rightOperandTier`, `comparisonOperandTier`, `unaryOperandTier` in `exprDiagnosticName`): a chain renders flat (`a < b <= c == d`), a chain operand that is a nested chain, a `not`, or a logical binary keeps its parentheses (`(a < b) == c`, `(not a) == b`, `a == (b and c)`) while arithmetic, powers, prefix minus, and postfix forms read back bare (`a + b < c * d`, `-a ^ b < c`), a chain under a tighter operator or under prefix minus keeps its parentheses (`(a < b) + c`, `-(a < b)`) and reads bare under `not` and the logical operators (`not a < b`, `a < b and c < d`), nested binaries keep exactly the parentheses the ladder needs (`(a + b) * c`, `a - (b - c)`, `(a ^ b) ^ c`, `(a or b) and c`, bare `a + b + c`, `a ^ b ^ c`, `a or b and c`), prefix operands likewise (`-(a + b)`, `-(-a)`, `-(not a)`, `not (a and b)`, bare `-a ^ b`, `not not a`), and a `not` operand of any tighter operator is parenthesized on either side (`(not a) + b`, `a * (not b)`) and stays bare under the logical operators (`not a and b`). The `Open` spelling still self-parenthesizes every binary and chain name. A dot-call context's RECEIVER description is written in postfix position — the rule the edge's own name uses (`ExprNameRenderer.RenderDotReceiver` over `PushDotReceiver`) — because every edge name composes it with the member (the dot-call context frame of a rejected `(-2).f`, which since Model C is the extension call `f(-2)`'s `ArityMismatch`, and the missing-output message of `Obj.M`): `(-2).f` is named `(-2).f`, never `-2.f`, which reads back as `-(2.f)`; a receiver that already binds as tightly as a postfix form keeps its `Open` spelling (`ComparisonChainHostileReviewTests`: `DotReceiverDescriptions_ComposeIntoTheEdgeTheyName`, `RejectedDotEdgeNames_PreservePostfixReceiverGrouping`, and `DiagnosticNames_RoundTripOperatorTrees`, which reads both spellings back). Pinned by `ParserTests` (`Parse_NotOverAComparison_*`, `Parse_NotVersusLogicalOperators_*`, `Parse_NotAsATighterOperand_*`, `Parse_NotAcrossNewlines_*`, `Parse_NotAndUnaryMinus_KeepTheirOwnTiers`), `BooleanValueTests` (`Not_BindsBelowTheComparisons`, `Not_BindsTighterThanTheLogicalOperators`, `ExplicitGrouping_KeepsTheOtherStructure_AndTypesAccordingly`), `StarSyntaxTests.NotAfterAStar_IsNeverAMultiplicationOperand`, `ExprNameRendererTests` (`Golden_NotOperandParenthesization_RendersExactly`, `Golden_DiagnosticNameMode_IsPrecedenceFaithful`), CoreTests `notOperandDiagnosticNameParenthesizesRebindingOperands` and `binaryDiagnosticNamesReadBackFaithfully`, and the language-spec cases `not-binds-below-comparisons` and `not-cannot-be-a-tighter-operand`.

## Strings and interpolation

STRING SPELLINGS (STR-02, decided October 2026, superseding STR-01). KatLang has two string spellings and ONE string value kind. A SINGLE-QUOTED string `'…'` is RAW and unchanged: its text is exactly the code units between the quotes, with no escapes and no holes (`'a\nb'` keeps its backslash, `'{x}'` is the text `{x}`, `'"'` is a double quote), so it cannot contain `'`, a line feed or a carriage return. A DOUBLE-QUOTED string `"…"` has exactly SIX escapes — `\"` (a double quote), `\\` (a backslash), `\n` (a line feed), `\t` (a tab), and the doubled braces `{{` and `}}` (literal braces) — and may contain INTERPOLATION HOLES `{expression}`. Every other backslash sequence (`\r`, `\u…`, `\x…`, `\0`, `\{`, `\'`, …) is `DiagnosticCode.InvalidStringEscape` at the two-character escape — never a silent backslash; the token keeps the written characters for recovery — and a lone `}` in the text is `DiagnosticCode.UnmatchedBraceInString`. There is no prefix (`$"…"`, `f"…"`), no verbatim form, and no multiline string: a string, its holes included, begins and ends on one physical line (a line feed ends it, and so does a lone carriage return, which is otherwise transparent to line numbering).

LEXING (C#-only surface syntax; Lean has no lexer). A double-quoted string WITHOUT holes is ONE `TokenKind.StringLiteral` carrying its decoded text in `Token.StringValue` — the token kind of a single-quoted string — so `"abc"` and `'abc'` are the same literal to every later stage. An interpolated string is a PAIRED token structure on one line: `InterpolatedStringStart` (the opening quote), the decoded text runs as `InterpolatedStringText` (an empty run produces no token), each hole as `InterpolationHoleOpen`, the ordinary tokens of its expression, and `InterpolationHoleClose`, and finally `InterpolatedStringEnd` (the closing quote). Inside a hole, braces nest as ordinary braces (`"{ {1} }"`) and strings of either quote kind are ordinary string tokens (`"{'}'}"`; `"{"in{x}"}"` nests). The lexer scans a string's extent before tokenizing it: a string or a hole that does not close on its line is ONE `StringLiteral` token from the opening quote to the line end with ONE diagnostic at the innermost open construct — `UnterminatedStringLiteral`, or `UnterminatedInterpolationHole` naming the hole still open — so the parser never sees a partial structure and the next line lexes independently. A `#` in the text of either string kind is text; a `#` inside a hole cannot start a comment (`InvalidInterpolationHole`). Scan and tokenization keep their state on a heap frame stack, never one CLR frame per nesting level, and the pairing (start↔end, open↔close, both on the opening line) is a structural guarantee the parser relies on.

PARSING. A hole-free double-quoted string parses to `Expr.StringLiteral`; an interpolated string parses to `Expr.InterpolatedString(Head, Links)` (Lean `.interpolatedString head links`): the decoded head text, then one `InterpolationLink(Hole, Text)` per hole, the hole's expression and the decoded text written after it (possibly empty). The parser never builds an `InterpolatedString` without links. An interpolated string is an ordinary PRIMARY: it may stand wherever an expression may, it is a slot like any other (`F("{1}", "{2}")`, `["{3}"]`), the ordinary postfix continuations follow it, and it never takes a call (`"{1}"(2)` is `UnseparatedSameLineItem`: a call may follow only a callable reference). A HOLE is ONE ordinary expression, parsed inside the hole's owned production (`Parser.EnterInterpolationHole`). The production charges the parser's ONE cumulative weighted nesting budget (`InterpolationHoleNestingSurcharge` on top of the expression's own levels, calibrated by the 1 MiB probes — `ParserNestingDepthTests`, `AstStructuralDepthProcessTests`), and it is an OWNERSHIP BARRIER: entering it saves and zeroes the enclosing constructs' owed-closer counters, so a closer written in a hole never closes a construct opened outside it (`F("{ ) }")` reports the `)` inside the hole and leaves `F(` to close on its own terms), and its own `}` is the one closer it is owed (`Parser.IsOwedCloser`).

THE HOLE RESTRICTIONS, each `DiagnosticCode.InvalidInterpolationHole`, reported ONCE at the offending token and recovered by skipping to the hole's own close, so the rest of the string and the following declarations survive (`Parser.RecoverInterpolationHoleTail`): an empty hole (`"{}"`, `"{ }"`); a hole-level comma (`"{a, b}"` — write one hole per value, `"{a}, {b}"`, or one sequence value, `"{(a, b)}"`); a hole-level `:` (`"{xs:0}"`, `"{x:F2}"` — interpolation has NO format specifiers, and `:` is no selection anywhere; a selection is written with brackets, `"{xs[0]}"`, which needs no grouping); a hole-level `=` (`"{X = 1}"`, `"{x=}"` — a hole is never a declaration, and there is no self-documenting form); a token after the expression (`"{1 2}"`, `"{1)}"`); and a token that cannot begin one (`"{,}"`). A hole whose expression parse already reported, or that holds a character the lexer reported, adds no second report. A bare spread hole (`"{xs*}"`) is the ordinary `MisplacedSpread` — a hole is no item-supply slot — while a spread inside a group is an ordinary capture (`"{(xs*)}"`). Same-line items and separators are a hole's own business: inside a hole a comma is never a slot separator and a second item is never `UnseparatedSameLineItem`, only the hole's `InvalidInterpolationHole`.

LITERAL-ONLY POSITIONS. A clause-head literal pattern, an `open` target and a `load` URL need FIXED text, so a hole-free double-quoted string serves as each (`F("a") = 1`, `open "https://…"`, `load("https://…")`), while an interpolated string is `DiagnosticCode.InterpolationNotAllowedHere` in a pattern (at any depth of a structural pattern) and as an open target (`Parser.RejectInterpolatedStringHere` consumes it as one atom), and an interpolated `load` URL is the loader's `InvalidLoadDirective` ("load URL must be a literal"). A `load` written in a hole is a RUNTIME position, refused like any runtime-position load and never spliced. Token-level scans (clause-head lookahead, the stray-`=` analysis, malformed-pattern recovery) step over a whole interpolated string as ONE atom through the partner table (`Parser.InterpolationPartner`), so delimiters and `=` inside holes never belong to the enclosing line's structure.

FRONT END. A hole is an operand of the ENCLOSING owner's written row — never a scope and never a slot list — so every front-end rule reads it exactly as it reads an operand: name resolution and ownership are the enclosing algorithm's; a hole's free names become that owner's implicit parameters in order of FIRST SEMANTIC OCCURRENCE (`F = "{b}-{a}"` is `F(b, a)`); Grace in a hole weights the owner's own names (`F = "{b}-{~a}"` is `F(a, b)`) and a marker on a closed level is `InvalidGraceMarker`; a hole is a VALUE role of the unified formula-lifting law (`ownership-and-lookup.md`), so a callable that requires arguments lifts (`G = "v{Inc}"` is `G(x)`) while one that accepts zero arguments is read; closed lists and clause branches check a hole's names like any written name. A brace block inside a hole is its own owner, as anywhere. The semantic model gives every identifier in a hole an ordinary site with its exact identifier span; string text produces no site (`editor-semantics.md` § Interpolation holes).

A lexer-rejected string token keeps its recovery text for analysis, but cannot authorize a module download. Unterminated strings or holes, invalid escapes, and unmatched text braces therefore never supply a URL to `open` or `load`. The parser preserves this provenance on the literal through copies (`Expr.StringLiteral.IsRecoveryLiteral`); the loader refuses the directive before target admission or downloader invocation. This reads every lexical-error position, including reports omitted by the diagnostic-list cap. Other valid imports retain their ordinary elaboration schedule.

## Source-like diagnostic fragments

Diagnostic expression fragments retain their syntactic parent context. Precedence alone is not sufficient for a callee: `(a.f)(...)` is a call on the argumentless dot edge `a.f`, whereas `a.f(...)` is a dot edge with arguments. `ExprNameRenderer` keeps that callee grouped. Raw parser suggestions also preserve the complete Grace weight, including cancelling markers (`~x~`), and prefix member Grace (`a.~~f`); collapsing or dropping these annotations could change the suggested program's parameter order. Rendering a hostile host weight stays bounded, including `int.MinValue`. A STRING renders as KatLang source too: single-quoted when its text can be written that way (no quote and no line break), otherwise double-quoted with exactly its escapes and its braces doubled — a carriage return, which no KatLang string can spell, shows as `\r` so the name stays one line — and an INTERPOLATED string renders as written, `"head{hole}text…"`: every text run re-escaped, each hole in operand shape through a link cursor bounded like a wide list (no rendered expression writes a hole-level `:`, since selection renders brackets, so a hole is never grouped for one), and a hole whose name could begin with a brace — a block at the left end of its spine — spaced (`"{ {...} }"`, `"{ {...}.X }"`; `ExprNameRenderer.MayRenderLeadingBrace`, Lean `holeMayRenderLeadingBrace`) so that `{{` never reads back as a literal brace (`ExprNameRenderer.PushInterpolationLink`; Lean the `.interpolatedString` arm of `exprDiagnosticName`).

The read-back guarantee concerns displayed operator grouping. Calls and opaque blocks deliberately elide interiors as `(...)` and `{...}`; these are diagnostic placeholders, not executable syntax. `DiagnosticName` also has an established operand-shape projection of zero-shape blocks to their output values, mirrored by Lean. Internal sequence joins, structural/debug descriptions, and truncated names are not complete source serialization. `SourceLikeDiagnosticRenderingTests` independently parses the unelided grouping, exercises all source-like modes, and pins public error and parser-suggestion paths.
