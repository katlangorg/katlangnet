## Parentheses group syntax

PARENTHESES GROUP SYNTAX; THEY DO NOT INTRODUCE A SEMANTIC BOUNDARY (September 2026). A parenthesized group whose content is exactly ONE non-spread expression slot is that expression, whatever the expression's kind: `(x)`, `((x))`, `(~x)`, `(F(1))`, `(Obj.X)`, `(A:0)`, `(first(A))`, `([1, 2])`, `({ ... })`, `((1, 2))`, `(if(c, a, b))`, and `(())` elaborate to the very node that `x`, `F(1)`, `Obj.X`, `A:0`, `first(A)`, `[1, 2]`, `{ ... }`, `(1, 2)`, `if(c, a, b)`, and `()` do. The ONE decision is `Parser.IsRedundantGrouping` — no declarations, exactly one slot, the slot is not a spread — and it never inspects the inner expression's kind, so there is no list of "kinds that keep a written level" for any layer to depend on. Consequences, all pinned: `E ≡ (E) ≡ ((E))` for the resulting value and emitted count; for normalization (`((1, 2))` IS the pair, `(())` IS `()` — grouping never suspends normalization); for every binding — fixed, collecting (`Coll((S))` is `Coll(S)`), patterned, and clause-family selection; for storage and property reads (`X = (E)` stores what `X = E` stores); for caching and value demand (`(A).count`, `count((A))`, `if(true, (A), 0)`, `(A).string` are `A.count`, `count(A)`, `if(true, A, 0)`, `A.string` — direct demands of the property's algorithm, never a cached value-position read; a random- or host-backed property draws the same number of times in both spellings); for selection (`(A):0` is `A:0`); for the dot-call receiver (`(Obj).V` navigates `Obj`'s own member exactly like `Obj.V`, `(3).A.B` is `B(A(3))`, `(A).Coll` is `Coll(A)` by the collector law); for explicit spread (`(E)*` is `E*`, `(E)*.F` is `F(E*)`); for evaluation count and order (an argument is evaluated exactly once, in the same position, in both spellings, and a failing argument stops assembly at the same point); for error kind; for the callable target (`(F)(1)` is the call `F(1)`, `(~F)(1)` is `~F(1)`); for the `open` target (`open (M)` and `open ((M))` are `open M`, classified by the same owner walk); for the front-end lifting rules (`Math.Abs((A))` is the same registry-strict position as `Math.Abs(A)`); and for every execution strategy (the optimizers see the same tree, so a planned loop plans `(T) + (T)` exactly as `T + T` and filter/count fusion fires for `(A).filter(P).count` exactly as for `A.filter(P).count`). The only groups that survive as `Expr.Capture` / `.capture` are the ones whose parentheses DO something: several written slots (`(1, 2)`, a sequence value) and a lone spread slot (`(A*)`, the capture of an item supply into one value — `capture : Supply -> Value`; a spread is a slot-level construct, not a value expression, so its group is not redundant). Those keep the capture laws unchanged: no algorithm identity (`Apply((Inc, Dec))` is an arity error on the value thunk), no structural members (`(A*).V` and `(A, B).V` fall back lexically), not an open target (`open (M, N)`, `open (M*)` are `BadOpenForm`). Two syntactic facts are NOT boundaries and stay as they are: a marker after a closing parenthesis is not attached to a name, so `(x)~` is the marker-attachment error (Grace and collect markers attach to the NAME token), and `(a.b)(1)` is call syntax on the dot RESULT while `a.b(1)` is the member edge with arguments (the grammar attaches `[CallArgs]` to the dot edge itself) — both pre-existing grammar productions, not parenthesis semantics. PATTERN PARENTHESES ARE CALL-SHAPE SYNTAX, NOT A RUNTIME BOUNDARY: `F((a, b))` declares ONE parameter slot whose argument must open to two items, `F(((*xs)))` one slot that opens to one item that itself opens (a one-element list supplies that outer structural level; scalars also bind through the ordinary one-item fallback at each pattern level, without any runtime wrapper); the binder opens the argument's VALUE one level (`bindParameterPattern` / `GetSequenceValuePatternItems` over `Result.structureItems?`, the same opening deconstruction uses) and never a written-slot view of the group it was written with — `explicitItems?` / `ExplicitSequenceValueItems`, the former second view that let `F((B))` bind `[[1, 2]]` where `F(B)` bound `[1, 2]`, are DELETED and must not return — so `F(S)`, `F((S))`, `F(((1, 2)))`, `F({S})`, and `F((S*))` bind the same value, and `((x))` never rejects a pair for being "one written slot". Spans are the only difference the group leaves: the unwrapped node takes the group's extent (F6, below), except that a NAME occurrence keeps its exact identifier span because that span IS the occurrence the semantic model builds reference, hover, and rename sites from (`WithGroupExtent`). Lean cannot see the parser, so the rule is pinned through the derived-AST corpora (`parentheses-group-syntax` and the updated `capture-suppresses-*`, `open-capture-target-rejected`, `redundant-call-parens-canonical`, `grace-in-redundant-group-is-grace-on-the-name` spec cases; `SemanticExplorerTests.DerivedLeanPrograms_MirrorParserParenthesisNormalization`), by `RedundantParenthesesTransparencyTests` (the `E ≡ (E) ≡ ((E))` observer matrix over root output, call arguments, collecting and patterned binding, spread, dot receivers, selection, lists, storage, callbacks, loop state, operators, builtin slots, and `.string`, each under the generic, optimized, and genuinely suspending async strategies, plus host-counted evaluation order and seeded-random cache probes), `OutputBundleSplitTests`, `GroupedExpressionSpanTests`, `ParserTests`, and the Lean guards in `CoreTests/CollectingParameters.lean`, `CoreTests/DotCallSemantics.lean`, and `CoreTests/OutputBundle.lean` (where a host-built single-row `capture [e]` is documented as an AST-channel shape that evaluates to `e`'s value). Selection chooses a value, dot-call passes a value, spread opens a value, parentheses group syntax.

## Delimiters, grouping extent, and unary spans

Delimiter model: `(...)` is sequence/expression grouping and call-argument syntax, `[...]` is list construction, and only `{...}` (and the root) creates an algorithm-level lexical scope. Algorithm-level declarations — `open`, property/clause definitions, deconstruction bindings — are parser-rejected inside parentheses with a targeted diagnostic pointing at `{ ... }`; brace blocks work in any expression position, including as call arguments, and their opens/local properties never leak into the surrounding scope. The parser may keep temporary Algorithm/Block structures for parenthesized sequences internally; the observable invariant is that no diagnostic-free parenthesized expression contains algorithm-level declarations. Recover unmatched root `)` / `}` tokens in the same scope, retaining later declarations and output for editor analysis; keep the parse erroneous and preserve nested delimiter ownership. NESTED DELIMITER OWNERSHIP ALSO BINDS RECOVERY (final audit, September 2026): primary-expression recovery never consumes a closing delimiter an ENCLOSING construct is still waiting for (`Parser.IsOwedCloser` over the open-delimiter counts `_openParens`/`_openBrackets`/`_openBraces`), nor the end of input — a trailing comma or a missing operand before the closer (`F(1, )`, `(1 + )`, `[1, ]`, `{1, }`) reports one `UnexpectedToken` at the closer, recovers the slot as a placeholder, and lets the owner close at its written closer, so later declarations stay in the scope they were written in (they used to be swallowed into the still-open construct with cascading `DeclarationInParentheses` reports); a closer nothing is waiting for (`{ 1, ) }`, a stray `]` at the root) keeps the junk recovery. Because a non-consuming return must be matched by a loop that ENDS at the token, every nested body loop (`ParseAlgorithmBodyParts`) ends at an owed closer of ANY kind — `)` and `}` unconditionally, `]` while an enclosing list is waiting for it (`[ (1, ]`: the group reports its missing `)`, the list closes at the `]`) — and the exhaustive delimiter-soup sweep in `RootStrayCloserRecoveryTests` (every string over the delimiter alphabet up to five characters) pins termination with a linear diagnostic count. Semicolon recovery consumes the `;` and stops at a declaration head, a closer, or the end of input instead of claiming the next line's declaration as a slot. Pinned by `RootStrayCloserRecoveryTests`. A GRACED name inside redundant parentheses is the graced name whatever the marker's weight (`Parser.IsRedundantGrouping` never looks at the inner kind: `(~obj).V` is `~obj.V`, the ordinary structural-first dot edge on `obj`, and `(~a)(b)` is the call `~a(b)`) — Grace is stripped before evaluation and never changes selection; pinned by `OutputBundleSplitTests`. GROUP EXTENT (F6): an expression the parser unwraps from redundant grouping parentheses keeps the group's FULL written extent as its `Span` (`Parser.WithGroupExtent` — nested groups accumulate, `((1))` spans all five characters, and a registered operator-chain depth is transferred to the re-spanned copy so the chain guard keeps counting through the group); the span is the ONLY thing that changes, so `(1) + 'a'` is located from the `(` while AST shape, grouping semantics, and evaluation are untouched. The ONE exception is a name occurrence (`Expr.Resolve`, and the graced occurrence `Expr.Grace` wraps): `(x)` is the node `x` with the exact span of the identifier `x`, because that span is the occurrence the semantic model builds reference, hover, and rename sites from — a source-position fact only, never a semantic one. Line-sensitive diagnostic wording therefore never reads an unwrapped node's span: the line-final-star explanation decides from the TOKEN stream (`Parser.IsLineFinalOperator`, the operand's first significant token), so `A * (` newline `B)*` is the ordinary misplaced spread whatever the grouped name's span. Pinned by `GroupedExpressionSpanTests` and `StarSyntaxTests`. Likewise a unary operand rejection — the string rejection AND the numeric-conversion `BadArity` of `-()`, `-(1, 2)` — as well as the Boolean-operand rejection of `not [1, 2]`, carries the unary expression's span from the ONE `Evaluator.ApplyUnaryOperator` (F5; `UnaryBadAritySpanTests`), never a spanless error.

## Comma and same-line items (SYN-07A)

Comma is the explicit expression-list separator, and on one physical line it is the ONLY separator (SYN-07A): whitespace never creates a slot boundary, so `1, 2, 3` is three slots while `1 2 3`, `F(1 2)`, `(1 2)`, `[1 2]`, `2(3)`, `A[1]`, `2m`, and `P = a b` are the targeted parse error `DiagnosticCode.UnseparatedSameLineItem` (public `KatLangErrorCode.UnseparatedSameLineItem`), reported at the first token of the second item with ONE generic message naming the three repairs (a comma between slots, an operator to continue the expression, a new line for a declaration) and never guessing intent. ONE ownership point decides slots — `Parser.StartsNextExpressionListSlot`, reached by every expression-list context through `ParseExpressionListOperand` — and the body loop's per-item row check decides declarations: `open`, property/clause definitions, deconstruction patterns, and `public …` must begin a physical line or follow the opening `{` directly (`1 P = 3`, `x = 3 y = 4`, `{ d = 2 n * d }` are the same error). Parameter-pattern lists (clause heads and nested sequence-value patterns) follow the same rule through their own ONE boundary decision — `Parser.StartsUnseparatedPatternItem`, reached through `ParsePatternItems`, over the atom grammar's starter set `CanStartPatternAtom` (a star counts only when an operand follows it — the SYN-07B classifier — so a star nothing can follow keeps its existing marker or closing-delimiter recovery) — reporting the SAME code with a pattern-worded message that names the comma as the only repair, and recovering the item as the next pattern of the SAME head: `F(a b) = a + b` recovers as `F(a, b) = a + b`, so the head's `)` and `=` are found where written and nothing leaks to the enclosing scope; a next-LINE pattern without a comma is NOT admitted (parameter lists have no newline separator) and keeps the ordinary closing-delimiter diagnostic. Recovery is a slot boundary, never a grammar hole: the second item stays the next slot of the SAME list (`P = a b` keeps `b` in P's body and leaks nothing to the enclosing scope; `F(1 2)` recovers as a two-argument call) or the declaration it spells, and recovery sites that already own a boundary (rejected Grace runs, detached markers, stray root closers, bad tokens, open-target leftovers, single-token primary recoveries) call `OwnSameLineItem` so the separator rule stays silent there — one diagnostic per malformed boundary. A newline is a separate mechanism — a body/statement/output boundary: at root output or inside an explicitly open context (`(`, `[`, `{`, an argument list) a newline between independent expressions separates slots (so `1`/`2`/`3` on three lines are three output slots and `F(` newline `1` newline `2` newline `)` is a two-argument call), but a simple one-line property body ends at the newline. Ordinary expression continuation is never a slot boundary: `F(1 -2)` is the one argument `1 - 2`. Root output consumes a bare expression list as output slots; call syntax consumes it as argument slots; parentheses materialize it as one sequence value. Parsing must not depend on callable arity, runtime values, inferred types, or any other semantic information. Pinned by `SameLineSeparatorTests` and the `same-line-*` `LanguageSpecCorpus` cases.

## Line rules and declaration heads (F7)

Postfix continuations bind on the same physical line only. A `(` or `{` after a callable target on the same physical line is a call delimiter even across whitespace, while a physical newline never continues a closed expression into a call. For multiline calls, open the delimiter before the newline. Indexing `:`, postfix grace `~`, binary operators, and the postfix `*` spread marker are also same-physical-line only (a line-final `*`, spaced or not, is multiplication whose right operand continues on the next line whenever that line starts with an operand, and otherwise a spread marker that must be attached — SYN-07B and the marker attachment law, see the star rule below). A leading `.` is the supported method-chain continuation. Definition bodies and open target lists are line-bounded: a newline ends the body, so an expression on a following line — at any indentation — is a separate output row parsed by the surrounding output/algorithm context, never a body continuation. (A same-line comma, an already-open delimiter, a same-line binary operator, and a leading `.` still continue the body. Root output and algorithm/brace bodies, by contrast, keep the expression list open across newlines, so a newline there separates output slots.) DECLARATION HEADS ARE LINE-LOCAL (F7): every declaration lookahead (`LookaheadIsEqualsFrom`, `LookaheadIsParenEqualsAfterName`, `LookaheadIsBindingPatternAssignmentFrom`, `LookaheadThroughTildesToPropertyDefFrom`, the `public` lookaheads) applies the ONE predicate `Parser.IsHeadToken`: a simple definition/deconstruction head shares one physical line; a clause head's name and `(` share a line, its closing `)` and `=` share a line, and the list inside the open parentheses may span lines; `public` and any rejected head markers share their name's line, so a newline never assembles a head after the fact — `Foo` newline `(x) = x + 1`, `A` newline `= 1`, `Foo(x)` newline `= x + 1`, and `x, y` newline `= 1, 2` keep the first line as its closed output row and reach the stray-`=` diagnostic (`Parser.StrayEqualsDiagnostic`, `DiagnosticCode.UnexpectedToken`), comments and indentation changing nothing. Explicit continuation AFTER a recognized head is deliberate and unchanged: the body of `A =` / `Foo(x) =` may start on the next line like a trailing operator's operand, and a trailing `.` continues its dot chain (`a.` newline `b` is `a.b`). Pinned by `DeclarationHeadLineRuleTests` and the `declaration-head-never-spans-lines` `LanguageSpecCorpus` case.

## Star roles

The star `*` has three roles resolved purely syntactically: prefix COLLECT MARKER in binding patterns, postfix SPREAD MARKER on a completed expression, and infix multiplication — the marker surfaces match the semantic directions `collect : Supply -> ListValue` and `spread : Value -> Supply`. PREFIX `*name` is the ONLY collecting BINDING syntax, valid only in binding positions — explicit parameter lists (`F(*items)`, `F(first, *middle, last)`), nested sequence-value parameter patterns (`F((x, *y, z))`), and assignment deconstruction, including the single-target form `*items = RHS`. The collect marker must be DIRECTLY attached to its binding name (exact source-offset adjacency — no whitespace, comment, or newline between; `* items` is a targeted attachment error that never creates a collecting binding, and `**items` is a repeated-marker error), and exactly one marker forms a binding. Prefix `*` is NOT an expression operator: in expression position it reports a targeted collect-marker diagnostic and recovers to the following operand. The old spellings `name...`, `...name`, `spread(expr)`, and `expr.spread` are NOT KatLang syntax: there is no ellipsis token (`...` lexes as three dot tokens and fails through ordinary parsing) and `spread` is an ordinary identifier with no reserved meaning.

## The spread marker (SYN-07B) and the marker attachment law

The spread expression has ONE spelling: the postfix marker `expr*`, and its reading is LAYOUT-INDEPENDENT (SYN-07B): the NEXT significant token decides, never whitespace before the star, never source attachment, and never the physical newline after it. When a token that can begin a multiplication operand follows the star — on the same line or on a later one — the star is infix MULTIPLICATION (`a*b`, `a* b`, `a *b`, `a * b`, `a*` newline `b`, and `a *` newline `b` all multiply; the trailing star continues exactly like every trailing binary operator). The ONE exception is a following DECLARATION head (`Name = …`, `Name(pattern) = …`, a binding pattern, `open`, `public`, `~Name = …`), decided through the same declaration-starter relation the slot boundary uses (`Parser.StartsDeclarationAt`): a declaration head is never an operand, so `a*` newline `b = 1` is a spread row followed by a definition. The star is the SPREAD MARKER when the surrounding syntax closes the expression before any operand could follow: a comma, a closing `)`/`]`/`}`, end of input, a token that cannot start an expression (`.`, `;`, `==`, …), or a declaration head — so `F(A*)`, `[A*]`, `A*, B`, `A*,` newline `B`, and a program-final `A*` are all spreads. THE MARKER ATTACHMENT LAW is a SEPARATE, LATER check (`Parser.ParseSpreadMarkerContinuation`, after classification): every structural/annotation marker is directly attached to the syntax it modifies — collect `*name`, spread `name*`, Grace `~name` / `name~` — through the ONE attachment helper `Parser.IsDirectlyAttached` (exact source offsets; whitespace, comments, and newlines all break attachment), while ordinary operators may be spaced freely. A star classified as a spread marker but detached from its operand (`F(A *)`, `(A *)`, `A *` at end of input or before a declaration head) is the targeted parse error `DiagnosticCode.InvalidSpreadMarker` (public `KatLangErrorCode.InvalidSpreadMarker`), spanning the operand through the last star of the malformed run and recovering to the plain operand — never silently a spread, never silently a multiplication — so whitespace can only separate the valid `A*` from the rejected `A *`, never turn one valid operation into another. Likewise a detached Grace marker (`~ x`, `x ~`, `~ ~x`, `a.~ t`) is `InvalidGraceMarker` with the attachment message and recovers to the plain name with no weight, and a detached collect marker (`* items`) is the existing `InvalidCollectMarker` attachment error on every binding surface. Consequences: a spread ROW followed by another output row needs the trailing comma (`A*,` newline `B`; a bare `A*` newline `B` is `A * B`), and a DEFINITION body ending in a spread that an output row follows must be closed (`y = (A*)` capture parentheses, or `y = { A* }`), because the trailing star continues the line-bounded body across the newline like any trailing operator (`X = A*` newline `B` is `X = A * B`). The one line-dependent star is the `*`-LED LINE: a same-line star always belongs to the expression before it, so a collecting deconstruction `*r = …` starts its own line (`A* *r = 1, 2` on one line reads its second star as a further — detached — spread marker of `A` and is rejected by the attachment law). Do not put attachment or same-line-only lookahead back into the postfix star DECISION (`IsPostfixSpreadMarkerStar`), and do not add a heuristic attachment guard there (the newline-tolerant binding-pattern scan makes such guards misfire on `A*` newline `B = 5`); pinned by `StarSyntaxTests` (layout-independence section) and `MarkerAttachmentTests` (the whole marker table). The marker lowers at parse time to the ONE unary `Expr.SequenceSpread` node (Lean `sequenceSpread`) — never to a Call or DotCall — so there is a single evaluator path, no ordinary call/property value boundary is introduced, and the operand is evaluated exactly once. Chained spread is compositional: `value**` equals `(value*)*` — each extra written star spreads the value that the previous star's supply re-captures at the ordinary expression boundary (`spread` then `capture` then `spread`), so a multi-item supply is a fixed point (`[[1, 2], [3, 4]]**` supplies the two inner lists unchanged) and only a lone structured item opens one more boundary (`[[7]]**` supplies `7`); it is NEVER recursive flattening. `value**next`, `value** next`, and `value**` newline `next` are targeted errors — the second star is multiplication with a spread operand, never exponentiation. A spread expression is legal ONLY as a whole expression-list slot (root/body rows, call argument slots, group and list elements, definition body slots), as the operand of another spread, or as the FLUENT DOT-CHAIN receiver: `operand*.Member(...)` lowers at parse time to the ordinary LEXICAL call `Member(operand*, ...)` with the spread as the leading argument slot — the receiver is an item supply, not a value, so structural member lookup never applies (`x.Calculate*.Target` builds the same AST as `Target(x.Calculate*)`, and further postfix continuations chain on the call result). GROUPING THE SPREAD CHANGES THE RECEIVER, and the difference is the ordinary capture rule, not a star rule: `A*.F` keeps the spread a SUPPLY and lowers to the lexical call `F(A*)` (items become argument slots), while `(A*).F` is a CAPTURE receiver — ONE ordinary leading argument whose value is the captured sequence: `(A*).F` is `F((A*))`. With `A = (1, 2, 3)` and `Coll(*xs) = xs`, `A*.Coll` collects the three items `[1, 2, 3]` while `(A*).Coll` collects the ONE captured value `[(1, 2, 3)]` — values stay values, so the collector never opens its argument. The same holds for a list operand: with `A = [(1, 2)]`, `(A*).Coll` collects the captured value `[(1, 2)]`, and `A*.Coll` collects the one spread item `[(1, 2)]` because spread-produced items are never reopened. At fixed arity, `A*.count` is an arity error (three argument slots) where `(A*).count` is 3; beside a collector, a fixed suffix receives the grouped value whole (`(A*).F` with `F(*mid, last)` binds `last` to that value), while the fluent form supplies separate slots. (`(A)*.F` is different again — that groups only the OPERAND, so it stays the fluent supply form.) Using a spread expression as a unary/binary operand or an indexing target/selector is a targeted parse error with unwrap recovery.

## The `open` declaration

`open` is a declaration/import directive, not an output expression: it takes ONE comma-separated target list (`open A, B, C`; string targets use single quotes — `open 'url', A`), parsed by a dedicated comma-list parser into individual targets (resolve, argumentless dot-call path, block, or string-load sugar). Each algorithm allows at most one `open` declaration. The first target must begin on the same physical line as `open` (`open` newline `A` is a missing-target error and `A` stays a separate row). Comma keeps its normal explicit line-continuation behavior — `open A,` newline `B` and `open A` newline `, B` both continue the list — and a leading `.` continues a dotted target (`open A` newline `.B` is `open A.B`), but a plain newline never continues `open`: `open Math` newline `Math.Pi` is an open plus a report row. `;` and a bare same-line second target are NOT open-target separators (`open A ; B` and `open A B` report a missing-comma diagnostic, never two targets). A spread-marked open target (`open A*`) parses to a spread expression and is rejected by open-form validation — spread is not an open form.

## Operator precedence, comparison chains, and prefix `not`

Diagnostic postfix targets follow the same binding-tier rule as operator operands: unary expressions and negative host literals retain their parentheses in dot/call receivers, index targets, and spread operands (`(-a).f`, `(not a).count`, `(-2):0`, `(-2)*`). Dropping that grouping changes the expression being described. Diagnostic rendering bounds its pending work as well as its output: both expression names and planned-loop chain descriptions schedule links one at a time, including arbitrarily wide host chains.

A host-built chain with no links has no source spelling. Its diagnostic name is the explicit placeholder `<comparison with no links>`, never its first operand's name: evaluating that operand is followed by the chain's `true` result, so naming just the operand would imply a different expression.

Precedence from loosest to tightest: `or` < `xor` < `and` < prefix `not` < the ONE comparison tier (`<` `>` `<=` `>=` `==` `!=`) < (`+` `-`) < (`*` `/` `div` `mod`) < prefix `-` < `^` (right-associative) < postfix `.`, `:`, and call application.

COMPARISON CHAINS (September 2026, a pre-release breaking change with no compatibility layer): equality and ordering no longer occupy separate tiers. All six comparison operators share one precedence level, and consecutive UNPARENTHESIZED comparison operators at one syntactic level form ONE comparison chain — the dedicated AST variant `Expr.Comparison(First, Links)` / Lean `Expr.comparison first links`, one `ComparisonLink(Op, Operand)` per written operator, the operators drawn from `ComparisonOp` (Lean `ComparisonOp`), which is disjoint from `BinaryOp`: a comparison is never a binary node, and a one-link chain (`a < b`) is the ordinary comparison. The chain has ADJACENT-PAIR semantics: `a < b <= c == d != e` means `a < b`, `b <= c`, `c == d`, `d != e`, and is `true` iff every link holds; mixed chains are ordinary (`a < b == c`, `a == b < c`, `a != b <= c`), and `!=` compares adjacent pairs only — `1 != 2 != 1` is `true`, never "all distinct". Each link keeps the operand rules of its operator unchanged (total structural `==`/`!=`, numeric-scalar-only ordering, Booleans unordered, the string rejections). Parentheses are explicit expression boundaries: a parenthesized comparison is an ordinary operand that never merges into the surrounding chain, so `(a < b) == true` compares the group's Boolean, `a < (b == c)` orders a number against a Boolean (the ordinary rejection), and `(a < b) == (c < d)` compares two Booleans; redundant parentheses around a whole chain leave one chain re-spanned to the group (F6). EVALUATION is incremental and left to right — `Evaluator.EvalExpressionSpineCounted`'s Comparison case (iterative, one spine frame per chain), its `// MIRROR OF` async twin, and `LoopOptimizer.EvalLoopComparisonPlan` for the planned loop, all applying each link through the ONE `Evaluator.ApplyComparison` (Lean `applyComparison`, `evalComparisonCounted`): evaluate operand 1, evaluate operand 2, compare, evaluate operand 3, compare it with the PREVIOUS VALUE, and so on. Every operand is evaluated EXACTLY ONCE (the previous operand's value is carried to the next link; the parser never lowers a chain to `and`, which would evaluate the middle operand twice); a `false` link never stops the chain (KatLang's eager Boolean composition — `3 < 2 < true` still compares `2 < true` and reports that link's ordering rejection); an error terminates it in the ordinary way (a failing earlier operand or link means the later operands are never evaluated; resource-limit errors also terminate evaluation, and host cancellation throws OperationCanceledException with the supplied token). A host-built chain with no links evaluates its first operand and is `true`. A link's rejection carries the operand-shape context of ITS two operands — `while evaluating `2 < true``, never `(1 < 2) < true` — at the hull of the two operands' spans (`Evaluator.ComparisonLinkSpan`; the chain's own span when an operand is unpositioned). Implementation: `Parser.ParseExpressionCore` treats `ComparisonPrecedence` (5) specially in the precedence-climbing loop — the right operand climbs from the additive tier (so it can never absorb a comparison operator), consecutive same-line comparison operators extend one link list (`ExtendComparisonChain`, which rejects spread operands in written order — the first operand when the chain opens, then each link operand), and the chain closes at the first non-comparison token (`CreateComparisonExpression`, which constructs the node and applies the chain-depth guard, one level per chain however many links); `BinaryOperatorPrecedence`/`ComparisonOpOf`/`BinaryOpOf` replace the former binary-op table; `KatLang.ebnf` spells the tier as `ComparisonExpr = AdditiveExpr { ComparisonOperator AdditiveExpr }` with the chain semantics annotated. Malformed input never recovers into a different valid chain (a missing operand is a placeholder link, spread operands are rejected in every position in written order, a misplaced `not` recovers as a parenthesized operand). `not` is NOT a member of the prefix-unary tier that `-` occupies: it binds less tightly than every comparison, arithmetic, and power operator and more tightly than the binary logical operators (comparisons > not > and > xor > or, Python-style, September 2026), so `not x > 3` parses to `Unary(Not, Comparison(x, [> 3]))` — it is `not (x > 3)` — `not a < b < c` negates the whole chain, while `not a and b` is `(not a) and b`, `not not x > 3` nests, `not x + 1 > y` negates the whole comparison, and `not 0 ^ 0` is still `not (0 ^ 0)`. Parentheses override the rule: `(not x) > 3` compares the negation itself (a type error for a numeric `x`, never special-cased) and `not (x > 3)` is the same tree as the bare spelling. Unary `-`, the and/xor/or ladder, the per-link comparison semantics, and the newline rules are unchanged by these rules: `-x ^ 2` is still `-(x ^ 2)`, `1 + -x` still parses, a line ending in `not` or in a comparison operator (like a line ending in any binary operator) is incomplete and continues on the next line, and a `not`-led or comparison-led line after a closed row never continues it. A `not` at its tier may begin a whole expression or the operand of `and`/`xor`/`or`; where a comparison, arithmetic, power, or prefix-minus operand is required (`1 + not x`, `a == not b`, `2 ^ not x`, `-not x`) the parser reports `DiagnosticCode.UnexpectedToken` at the keyword with a message naming the ladder and the parenthesized repair (`Parser.MisplacedNotDiagnostic`), and recovers by parsing the negation as if it were parenthesized. Because `not` can never begin a multiplication operand, a star followed by `not` is the spread marker (SYN-07B), exactly like a following declaration head. DIAGNOSTIC NAMES follow ONE precedence-tier rule so the rendered text reads back as the rendered AST (`ExprNameRenderer.BindingTier` with the slot tiers `LeftOperandTier`/`RightOperandTier`/`PushComparisonOperand`/`PushDiagnosticUnaryOperand`; Lean `bindingTier`, `leftOperandTier`, `rightOperandTier`, `comparisonOperandTier`, `unaryOperandTier` in `exprDiagnosticName`): a chain renders flat (`a < b <= c == d`), a chain operand that is a nested chain, a `not`, or a logical binary keeps its parentheses (`(a < b) == c`, `(not a) == b`, `a == (b and c)`) while arithmetic, powers, prefix minus, and postfix forms read back bare (`a + b < c * d`, `-a ^ b < c`), a chain under a tighter operator or under prefix minus keeps its parentheses (`(a < b) + c`, `-(a < b)`) and reads bare under `not` and the logical operators (`not a < b`, `a < b and c < d`), nested binaries keep exactly the parentheses the ladder needs (`(a + b) * c`, `a - (b - c)`, `(a ^ b) ^ c`, `(a or b) and c`, bare `a + b + c`, `a ^ b ^ c`, `a or b and c`), prefix operands likewise (`-(a + b)`, `-(-a)`, `-(not a)`, `not (a and b)`, bare `-a ^ b`, `not not a`), and a `not` operand of any tighter operator is parenthesized on either side (`(not a) + b`, `a * (not b)`) and stays bare under the logical operators (`not a and b`).
