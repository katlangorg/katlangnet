# Ownership, lookup, and binding rules

The full statement of the rules that AGENTS.md carries in compact form — consequences, examples, the implementation map, and the pinning tests — moved here verbatim from AGENTS.md in September 2026. These rules are as binding as AGENTS.md; the compact bullet there points at the section here. Keep both in step: a rule change edits the compact bullet and the section together.

## The resolution model in one place

Every layer — the evaluator (sync, async, planned), parameter detection, implicit-argument resolution and its sibling-order channel, exposure/dependency analysis, open validation, and the editor model — answers "what does this occurrence denote?" by the same ordered rules (name-resolution audit #8, September 2026):

1. **Owner walk.** Search outward by owning scope — the occurrence's body, each enclosing algorithm or branch body, the root, and the prelude as the outermost property level (builtins, `Math`, the Math aliases, and a run's host operations). At each level a PARAMETER binding (written, inferred, collecting, grouped, or a branch binder — never one that automatic parameter forwarding added, see § Automatic parameter forwarding preserves existing bindings) is asked before the level's PROPERTIES (any visibility); the first level that declares the name decides. A property may not share a name with a parameter of its own or an enclosing algorithm (declaration error), so the tie rule only matters in recovery trees.
2. **Opens, only after the whole walk.** If no level declares the name, the `open` providers are consulted level by level, innermost first; a level's targets count once per PROVIDER — the declaration they resolve to in its declaring scope, never their spelling or position (Q-19 D-I, § Open provider identity) — each provides only its PUBLIC members, and the first level at which any provider supplies the name decides — one provider selects its member, two or more select NOTHING: a WRITTEN name that reaches such a level is the front end's `AmbiguousOpen` (Q-29 A-U, § Static open ambiguity), and a lookup only evaluation decides (a dot fallback the receiver decides, a host-built tree) is the evaluators' `ambiguousOpen`. An open therefore never overrides anything owned, a builtin or host operation included.
3. **Promotion, only after both.** A name nothing declares or provides becomes an implicit parameter of the innermost algorithm without a written parameter list; under a closed list or in a branch body it is an error. A dot edge's fallback name is such an occurrence by the selection lattice (Q-75 F-A): an inferring body collects it unless the fallback is never selected, and a closed list or branch body checks it only when the fallback is certain.
4. **Structural first on dot edges.** `R.M` looks `M` up among the receiver's DECLARED members (any visibility, any spelling — `string` included) first, at every level of a chain; only a structural miss falls back — to the `.string` intrinsic when `M` is `string` (Q-17 S-C; a lexical `string` is never consulted), otherwise to the lexical callable `M` of rule 1–3, as the ordinary call `M(R, args)`. A declared but inaccessible member is its own error, never a fallback.
5. **`open` is static.** A target's head is an ordinary occurrence (a parameter-owned head is an error, never a farther declaration); a target must resolve — head through the direct chain (never another open), dotted steps through public declared members — and must need no call.
6. **Identity decides, spelling never.** The selected declaration carries its identity to every consumer: value and algorithm positions are one decision projected onto two channels; builtin behavior (laziness of `if`, optimizer fusion, the Math value-demand contract) follows the resolved identity; a user `Alias = A` is a new declaration, while forwarding the same bound callable keeps its identity; a dot expression carries ONE callable identity in every algorithm-capable position, callee included (Q-18 C-B3: an argumentless structural path is its member, everything else a value); accessibility is checked on the selected member afterwards and never changes the selection.

**Automatic parameter forwarding changes none of these answers** (Q-04, decided September 28 2026). It runs after the six rules have decided every written name, reuses the PARAMETER bindings they select to supply a lifted callee's inputs, and adds a parameter only for a name no parameter binding supplies — a forwarded parameter that no written name ever denotes. There is no second round of selection after forwarding.

The sections below state each rule in full.

## Ownership-first lookup

Ownership-first lookup is fundamental. Keep lookup behavior aligned across evaluator, parser/front-end elaboration, parameter detection, and semantic tooling. The evaluator's two lookup spellings — `LookupLexical` (reached by a bare name in VALUE position, `X`; returns owner+binding for the zero-arg property cache) and `LookupLexicalResolvedAlgorithm` (reached from ALGORITHM position: a callee `X()` or a dot-call target `X.m`) — are ONE implementation since M8+M9: the algorithm spelling is the projection of the binding-carrying chain (mirroring Lean, where `lookupLexical` projects `lookupLexicalProperty`), so ownership-first, open dedup, ambiguity, scope-level precedence, and prelude fallback exist once per engine; `LookupTwinEquivalenceTests` keeps both spellings observable so an independent fast path cannot silently regrow. Beyond that there are TWO C# lookup implementations — the evaluator's chain and `ElaboratedScopeLookup` (shared by `ParameterDetector` and `Semantics/`) — and they must select the SAME declaration, not merely both resolve: the detector's verdict rewrites the program (an unresolvable name becomes an implicit parameter), so a front-end disagreement changes what the evaluator runs. `LookupCoherenceTests` pins that relation with unique per-declaration sentinels; the `open`/visibility family in `SemanticExplorerCases.lean` pins the Lean/C# side. `open` targets count once per semantic PROVIDER (Q-19 D-I, § Open provider identity): `open A, A`, `open A, (A)` and `open Sub, Lib.Sub` for one declaration are ONE provider, not an ambiguity, while two declarations or two written blocks stay two however equal; bounded `Evaluator.OpenExprName` text is presentation only and never decides identity, and the complete-spelling key `Evaluator.OpenTargetDedupKey` survives only as a pre-resolution optimization (one spelling at one level resolves one target) — that rule lives in Lean `resolveAllOpens` and must be mirrored by BOTH C# implementations.

## The owner walk

The OWNER WALK is the front-end half of ownership-first, and `ElaboratedScopeLookup.SelectOwnedDeclaration` is its ONE implementation (Lean: `selectOwnedDeclaration` / `elaboratesToParameter`, stated beside `shouldTreatAsImplicitParam` because `ScopeCtx` carries properties but no parameters): search outward by owning scope over the two kinds of OWNED declaration — the parameter bindings a scope binds (written, inferred, or a branch body's pattern binders) and the properties it declares — and the first owner that declares the name decides, a parameter beating a property of the SAME owner in an invalid recovery tree. Properties matching parameters of the same or any enclosing lexical algorithm are declaration errors, checked by `ParameterPropertyCollisionValidator` after automatic parameter forwarding, forwarded parameters included (Lean: `conflictingOwnedNames` / `validOwnedDeclarations`) — with ONE root exemption: the root program is never called, so its completed signature (names it could not resolve, or names forwarding lifted into it) is checked against the root's OWN declarations only and never blamed on a property nested in a deeper owner; such a name surfaces as the root's `UnresolvedImplicitParams` evaluation error, positioned at the first output row of the root by the ordinary missing-arguments span rule — or at the member token when that ONE name came from a missing member on a statically known receiver (diagnostics-only; see the dot-call bullet) — (`Lib = { public Q = 1 }` beside the root row `Q + 1` is a missing `open Lib`/`Lib.Q`, not a conflict in `Lib`; pinned by `ParameterPropertyCollisionTests.RootPhantomParameter_*`). Consequences that must hold together: a captured ancestor parameter beats a property of any FARTHER owner (the root's and the prelude's alike, so `F(pi) = { pi + 1 }` binds the parameter), a nearer property beats an outer parameter only in invalid recovery source, the nearest of several enclosing parameters wins, and a direct reference and one from a nested body always agree. `open` and the prelude keep their SEPARATE later policy: opens are consulted only after the whole owner walk (`LookupLexicalPropertyMatches`), so an owned parameter beats an inner `open` exactly as an ancestor-owned property does, and the prelude participates only as the outermost property level. Ownership is NOT the promotion question — `IsBoundName` still stops promotion at any visible property or opened name, unchanged. The owner map is `ParameterOwnership` (name → owning level, nearest wins by construction; never a counted depth), threaded through detection beside the scope chain — detection runs before automatic parameter forwarding, so it holds name-resolution parameters only, and the collision validator, which sees forwarded ones, takes a shared implicit-signature template as ONE layer owned by its level (FE-3, never a shared owner); the detector's parameter classification (`ShouldRewriteAsParam`) and receiver classification (`ResolveReceiverNameProvider`) must both go through the shared walk, and the editor's scope visibility is its enumeration form — derived per frame as persistent layers (parameters before the level's own properties, opens after every direct name) and pinned against the eager chain walk `ComputeEagerReferenceSymbols` (FE-4b; see [`editor-semantics.md` § Scope visibility and module provenance]). Pinned by `ParameterOwnershipTests`, `LookupCoherenceTests` (the `ownership.*` cases), and the `ownership-*` `LanguageSpecCorpus` cases.

## Open, exposure, and accessibility (K1-08)

`open Name` may target a lexically visible private head, but open-provided names and dotted open steps select PUBLIC members (a private step reports `NotPublicProperty` before any capture check); structural dot access selects DECLARED members including private ones. SELECTION NEVER DEPENDS ON EXPOSURE (K1-08): a public captured member participates in precedence and ambiguity, and the unique selected member is checked afterwards by `Evaluator.IsAccessibleFrom` / Lean `memberAccessible?`. Capture requirements retain the exact semantic owner, including transitive requirements across shadowing: `Property.RequiredAncestorParameters` / `.localCapturedAncestorParams names` supply diagnostic names, while internal `CaptureRequirements` / Lean `PropDef.requiredOwnerDepths` retain owner positions relative to the declaring scope. Host-built trees without owner metadata use the nearest binder of each supplied name. Both elaborated lists have immutable backing that properties may SHARE (FE-4a; [`evaluator-and-hosting.md` § Shared-DAG guarantee]): the exposure pass decides requirement identity by name AND owning scope — same-named parameters of different owners stay different requirements — and only then projects each property's final set into its lists, whose content is the whole meaning (names; owner depths relative to the property's OWN declaring scope), so two properties with equal contents may share backing without merging declarations, owners, or activations. Distinct nonempty wrappers preserve the existing reference-based list fields in generated Property equality and hashing; collection reference identity is not semantic requirement identity. Accessibility requires the matching declaration AND activation in the site's lexical chain, including already captured ancestor activations of a static nested provider. Runtime declaration tokens distinguish clause families and distinct algorithms even when they share names, properties, opens, or output nodes; activation tokens distinguish successive calls. Both are FIELDS of the runtime model, never a side table (Lean: `Algorithm.declarationId`, `ScopeCtx.declarationId`/`activation`, `EvalCtx.headScope`): `Algorithm.Declaration` is minted once per constructed `User`/`Conditional` and carried by every record copy — a `with` copy is a view of the same written declaration, whether the evaluator, the front end, or a host made it — while a `ParameterActivation` is minted per parameterized body entry or clause match, compared by reference, and carried by the activated `ScopeCtx` (`ScopeCtx.Owner`/`Activation`; the entered body's is `EvalCtx.HeadScope`, cleared by every push). A host-constructed scope has no owner, so it establishes identity only by being the same object. A conditional publishes its matched binders on its family scope. Parameter reads use the owning activation's value, algorithm, and counted channels, never a shadowing caller's binding. Compile-time branch analysis may share equivalent relative binder/open contexts without merging runtime families. Structural paths and open-provided names carry transitive capture requirements through `PendingReference`, preserving per-activation caching — a BARE opened name read by a sibling property is settled by the same one settlement (`PendingResolution.ResolveVisibleName`: the declaring chain's own properties first, then the declaring level's and its ancestors' opens), so `Y = X` beside `open Lib` with a capturing `Lib.X` is local-only exactly like `Y = Lib.X` and `Y = { open Lib  X }` (final audit, September 2026: it was classified Exported and the run cache leaked the first activation's value). An escaping reference carries an UNRESOLVED open candidate (the opener's target head was not the opener's own property) outward level by level, and the level that DECLARES the head settles it there — `PropertyDependencyGraphBuilder.AddEscaping` through the ONE local-head settlement `TryResolveLocalHeadCandidate`, the same one `MakeOpenCandidates` applies when the opener declares the head — because the evaluator resolves the target from the opener's direct chain outward and the nearest declaration wins; a head declared BETWEEN the opener and the settling level used to be carried past its declaration, so `Outer(p) = { Mid = { Lib = { public X = p }  Inner = { open Lib  X }  Inner }  Mid }` classified `Mid` exported and `Outer(1), Outer(2)` displayed `1 1` from the run cache (final hostile pass; `LocalMemberAccessTests.OpenTargetHeadDeclaredBetweenTheOpenerAndTheSettlingLevel_*`, spec case `ownership-open-head-between-opener-and-settling-level-charges-the-capture`). An OPEN PROVIDER must have zero effective call parameters, cannot be a clause family, and cannot be a prelude builtin — bare or as the HEAD of a dotted target (`open count.X` is refused like `open count`, never left to promote the opener's names to implicit parameters): `OpenProviderValidator` runs after signature completion and both evaluators reject the final provider with `IllegalInOpen` — the validator refuses a builtin head (`open count`) eagerly, in the same rule as a parameterized provider, matching the evaluator's and Lean's refusal by kind. Exported-property cache identity remains separate from runtime accessibility identity. Intermediate owners in `Lib.Sub` are static navigation, so parameterized or inferred-parameter intermediates are allowed if every selected edge is accessible and the final provider needs no call. A family exposes no branch members structurally (`LocalOnlyConditionalAlgorithm`), while a self-contained branch-local provider works inside the branch and nested bodies. Classification cannot invalidate selection, so no outer re-elaboration/recheck exists; the local dependency-summary fixed point remains. Pinned by `LocalMemberAccessTests`, `ZeroArgPropertyCacheScopeTests`, `FrontEndDagComplexityTests`, the exposure lookup cases, and independent `CoreTests/NameOwnership.lean` guards.

## Static-open ownership (SYN-03 / F2)

The dependency summary is expanded through each declaring ancestor once. A member seed already describes requirements relative to its owner's parent, so navigation and provider settlement exclude that owner from the remaining expansion path. Re-expanding it can duplicate provider identity levels and lose captured requirements. A qualified open can also carry a path back through its own intermediate owner; repeated local-path equations close by set-union idempotence, with the declaring algorithm, summary-map snapshot and bound-owner exclusions kept distinct. No incomplete result enters the completed-summary memo. `ModuleLawPostCommitReviewTests` pins nested qualified paths, captured values, exposure and declaration permutations.

STATIC-OPEN OWNERSHIP (SYN-03 / F2): `open` is resolved statically — it never opens a runtime value, and there is no dynamic `open` — but lexical ownership still applies to the target's HEAD name (`Lib` in `open Lib` / `open Lib.Sub`), which parameter detection classifies through the ONE owner walk (`ElaboratedScopeLookup.SelectOwnedDeclaration`, called from `ParameterDetector.ClassifyOpenTargetHeads`) exactly like every other bare-name occurrence. If the nearest binding is a parameter — explicit, inferred, collecting, grouped, a branch binder, or any of these captured from an enclosing owner (never one automatic forwarding added) — that parameter owns the name; a parameter cannot be opened, so the head elaborates to `Expr.Param` (not an open form in either engine: `IsCoreOpenForm` / Lean `Expr.openForm?`, so evaluating any such tree yields `BadOpenForm`) and the front end reports `DiagnosticCode.OpenTargetIsParameter` at the head's span. It NEVER searches farther outward: adding or removing a farther same-named declaration (a root property, an enclosing property, an opened or module-provided member) changes neither the verdict nor the report, so `F(Lib) = { open Lib … }` is rejected with or without a root `Lib`. The rejected target provides no names (the same recovery rule as a rejected capture target), so the closed-list check and inference see nothing through it, and the editor classifies the head as the parameter reference it is (`OccurrenceKind.OpenTargetReference` with the parameter's declaration — never a farther property's). The never-called program root's phantom signature is NOT a callable binding for this decision (`ParameterOwnership.CallableBindings`, the F1 exemption): a nested `open Q` beside an unresolved root row `Q.X` stays a static lookup and evaluation reports the unresolved root input. Lean states the rule as `elaborateOpenHead` beside `elaboratesToParameter`; pinned by `StaticOpenOwnershipTests`, the `ownership-open-*` `LanguageSpecCorpus` cases, `LookupCoherenceTests.ownership.parameterOwnedOpenHeadResolvesToTheParameter`, and the F2 guards in `CoreTests/NameOwnership.lean`.

## Static open-target validity (audit #8)

Every `open` target must RESOLVE, whether or not any name is ever looked up through it: a written target whose name head no enclosing declaration or prelude member provides (an open head resolves through the direct chain — the evaluator's `lookupLexicalDirect` — never through another open), or whose dotted step — from a name head or from an INLINE head alike, a written `{ ... }` block or a loaded module (`open { ... }.S`, `open load('url').S`) — names a member the receiver lacks, declares privately (open paths select public members), or declares only inside conditional branches (a family exposes no members), is the front-end error `DiagnosticCode.UnresolvedOpenTarget` (host family `KatLangErrorCode.UnresolvedOpenTarget`) at the target, reported by `OpenProviderValidator` beside the provider rule and worded after the step that fails. Every static consumer reads the SAME decomposition of a target into its head and dotted steps (`AstHelpers.OpenTargetHead`): the parser's form check (a head that is not a name, a block, or a `load` module is `BadOpenForm` at the head — see [`syntax.md` § The `open` declaration]), the static resolution (`ElaboratedScopeLookup.ResolveOpenTarget`) and its diagnostic, parameter detection's head classification, and dependency/exposure analysis, which settles an inline-headed provider at its own open level exactly as the evaluator reads it (`PropertyDependencyGraphBuilder.TryChargeInlineOpenProvider`: the block is wired to the prelude, so only its own requirement names survive). Before constitution PV-11 (September 29 2026) the diagnostic described name-headed paths only, so `A = { open { public X = 1 }.Nope  X }` ran with `X` promoted to `A`'s parameter and `open load('url').Shwn` did the same while `Lib = load('url')` / `open Lib.Shwn` was refused; and dependency analysis charged a VALID block-headed provider as providing nothing, so a name it provided escaped to an enclosing `open` and a property reading it was classified local-only (`Outer.Y` refused where the bare-block and name-headed spellings read 5) or missed an `ambiguousOpen` (`OpenTargetHeadValidityTests`). Before this rule the front end silently dropped such a target (`ElaboratedPropertyScope.GetResolvedOpenProviders` omits it), so its names were promoted to implicit parameters, while both evaluators — which resolve ALL of a level's opens as soon as a lookup consults that level (Lean `resolveAllOpens`) — failed only if some lookup happened to reach it: `open Lib, Nope` with `X` from `Lib` was accepted by the front end and refused at runtime, and `A = { open Nope  X }` ran with `X` as an implicit parameter. Lean's surface spec refuses to promote through most failing opens too (`shouldTreatAsImplicitParam` propagates every lookup error except `unknownName`, which it cannot tell apart from the probed name's own absence — an unknown open head included); the front end now refuses every such target directly, so no accepted program reaches that distinction. A parameter-owned head keeps `OpenTargetIsParameter`, a builtin head or provider `IllegalInOpen`, and an illegal target shape the parser's `BadOpenForm`; a local-only captured step stays the evaluator's per-site accessibility question. Like `IllegalInOpen`, the report is per WRITTEN target (each is a site the author fixes). Pinned by `NameResolutionAuditTests`, `LookupCoherenceTests` (`providers.*`), and `DiagnosticCodeTests`.

## Open provider identity (Q-19 D-I, decided 2026-10-06)

An `open` list counts the PROVIDERS its targets resolve to, by the language's one callable identity — the declaration in its declaring scope (the evaluators' `SameRepeatedCallableIdentity`, Lean `sameRepeatedCallableIdentity`: NEED-04's relation) — never by spelling, position, member names, member values or source text. `open M, M`, `open M, (M)` and `open Sub, Lib.Sub` inside `Lib` for one declaration `Sub` are ONE provider in either order; two written blocks (`open { public X = 1 }, { public X = 1 }`) and two declarations with identical bodies stay TWO; a member alias never merges its owner with another provider; a loaded module is ONE declaration wherever it is held (`open A, B` over two holders of one URL, `open 'u', 'u'`, `open A, 'u'` — Q-32 I-U below). The front end computes the static form of the same identity once (`OpenProviderIdentity`: the provider's declaration, then its declaring owners outward to the root level; a written block and a loaded module are declared at the root level wherever they are named), and every consumer that counts providers reads it — elaborated lookup (`ElaboratedScopeLookup.GetResolvedOpenProviders` / `ResolveOpenProvider`, and with it detection, the static ambiguity check and the editor), exposure settlement (`OpenLevelSettlement`), the summary channel (`ResolvedOpenCandidate` identities, `DistinctProviders`), and implicit-argument resolution (`OpenProvider.ResolveProvider`). The evaluators resolve each target and drop one whose identity equals an earlier one (`Evaluator.ResolveAllOpens`; Lean `resolveAllOpens`, where an unidentified hand-built declaration counts as its own provider); the complete-spelling key `Evaluator.OpenTargetDedupKey` remains only as the pure pre-resolution optimization it is. `OpenProviderIdentityTests`, `CoreTests/OpenProviderIdentity.lean`, `OpenTargetDedupKeyTests`, the `open-two-spellings-one-provider`, `open-identical-inline-blocks-two-providers` and `open-distinct-declarations-stay-distinct-providers` spec cases.

## Static open ambiguity (Q-29 A-U, decided 2026-10-06)

Provider OVERLAP is legal: two opened algorithms may contain the same name, so adding an unused member to one library never breaks a program that opens it beside another. A WRITTEN name whose lexical resolution reaches an open level at which two or more DIFFERENT providers supply it names no declaration, so it is the front-end error `DiagnosticCode.AmbiguousOpen` (public `KatLangErrorCode.AmbiguousOpen`, the existing family) at the written occurrence — whether or not evaluation would ever demand it (demand governs computations, never what a written name means): a never-read property, an unselected `if` branch, a callee, an operand, a receiver, a callback block, a closed list or a clause branch alike. Lexical precedence decides first — a parameter binding (excluded by the owner walk), an owned property of any level, or a nearer open level that provides the name ONCE — and providers are counted by identity (§ Open provider identity). A dot edge's fallback name is a written use only when the edge CERTAINLY takes its fallback (the Q-75 lattice's Always: `5.X`, a statically known receiver lacking the member — checked at the member token); a structural hit (Never) is no lookup of the opened name at all, and a fallback the runtime receiver decides (MAY: `p.X`) stays the evaluators' run-time `EvalError.AmbiguousOpen`, as does every lookup of a host-built tree. ONE implementation: `ParameterDetector.ReportAmbiguousOpenUse` over `ElaboratedScopeLookup.FindAmbiguousOpenProviders`, in the rewrite walk that visits exactly the rows a body writes (once per occurrence per region; a provisional elaboration reports nothing). The message names the providers as written and the two repairs (qualify the name, or open only one provider). Lean models no front-end rule (FORMAL-02): its `ambiguousOpen` remains the evaluator's verdict. `StaticAmbiguousOpenTests` (positions, precedence, the Q-75 fallback oracle rows, host-built trees, the editor, bounded wording), the `ambiguous-open-written-use-is-static` and `ambiguous-open-unused-overlap-is-valid` spec cases.

## Open ambiguity in dependency analysis (audit #8)

Every consumer counts providers by identity (§ Open provider identity). An inline block or module head keeps a separate provider for each written block, including dotted paths such as `open { ... }.S` (each written block is its own declaration), while `open load('url').S` and `M = load('url')` / `open M.S` reach the ONE declaration of the module. The decomposition `AstHelpers.OpenTargetHead` (Lean `Expr.openTargetHead` in `resolveAllOpens`) is shared, so diagnostic abbreviations such as `{...}.S` never merge or split providers. This rule is shared by runtime lookup, static lookup, and dependency analysis. `OpenTargetHeadValidityTests`, `CoreTests/NameOwnership.lean`, and the `inline-headed-open-paths-keep-distinct-providers` spec case pin ambiguity, missing/private members of the first provider, and named-path controls.

Exposure/dependency analysis charges exactly the declaration the evaluator reads, and an ambiguous open reads NONE: the settlement of an escaping reference (`PropertyExposureResolver.PendingResolution.Resolve`) consults the escaped levels' providers and then the owning level's and its ancestors' opens ONE LEVEL AT A TIME — each carried `OpenCandidate` records its opener level (`ProviderLevel`) — and the first level at which any target publicly provides the head decides: a sole provider charges its member's requirements, two or more charge nothing (the evaluator's `ambiguousOpen`). Taking the first-listed provider made the verdict depend on target order: with `A.X` capturing `p` and `B.X` self-contained, `public Y = { open A, B  X }` was classified local-only and `Outer.Y` refused with `LocalOnlyProperty`, while `open B, A` reached the true `AmbiguousOpen`. Pinned by `NameResolutionAuditTests`.

## Inline and module open targets: rooted at the prelude, validated like any body (MOD-06; Q-61, October 2026)

An inline `{ … }` target has no declaration site of its own, so it is elaborated and evaluated as a separate region rooted at the PRELUDE: it sees the builtins and host operations, none of the opener's properties, parameters or branch binders, and names it cannot resolve become implicit parameters of its own members (`X = 5` / `A = { open { public Y = X + 1 } ⏎ Y }` / `A` is an `ArityMismatch`: `X` became `Y`'s parameter). A loaded module is rooted at the prelude in EVERY position — opened directly (`open 'url'`, `open load('url')`) or held by a property (`Lib = load('url')`, `open Lib`, `Lib.X`) — see § Loaded modules. A NAMED provider whose value is a WRITTEN block (`open Lib` for `Lib = { … }`) keeps its definition site. ROOTING DECIDES VISIBILITY, NEVER VALIDITY: inside an open target every front-end rule applies exactly as in any other body and in every phase — eager, or inside a selected deferred compilation unit (`evaluator-and-hosting.md` § Source loading and deferred modules) — name resolution, bare forwarding by compatible binding name with no renaming (§ Callable aliases and bare forwarding), formula lifting and the rules for inferred signatures, and every validator. A declaration that is invalid as a property body is invalid as an open-target member: `open { N(y) = y ⏎ public P(x) = N ⏎ public X = 1 }` is `UnforwardableParameter` at the bare `N` exactly as `M = { … }` is, and `open { C1(a, *p) = a ⏎ C2(b, *q) = b ⏎ public K = C1 + C2 }` is `InvalidCollectingBinding`. The resolver's walk over open targets (`ImplicitArgumentResolver.ProcessOpenExprs`, from a user algorithm's opens and — for a host-built tree — a clause family's) reports into the caller's diagnostic sink like every other region of the pass, so its verdicts — `UnforwardableParameter`, `UnforwardableCallable`, `UnliftableClauseFamily` and the inferred-signature `InvalidCollectingBinding` — are reported there as everywhere: at the written reference in the document's own text, at the import site for module content, as a `ParseFailure` eagerly and as the selection's `EvalFailure` inside a deferred unit, with the same multiplicity as equivalent property-held source, including its shared-region diagnostic deduplication; a recovered signature exists only beside its error and never reaches evaluation. (Constitution X-48, resolved October 2026: the walk ran with no sink, so these programs were accepted — the second example evaluated its recovery signature, `K(1, 2, 3)` giving `3`.) Pinned by `OpenTargetResolverValidationTests` (every reporter in every position and phase, valid controls, Q-04 ancestor reuse, declaration orders, multiplicity, hostile shapes) and `SemanticModelTests.InvalidOpenTargetMember_ReportsTheResolverDiagnostic_OnAnUnchangedModel`.

## Loaded modules: hygienic source units, one declaration per canonical URL (Q-31 H-P + Q-32 I-U, decided 2026-10-06)

A loaded module is its own source unit ROOTED AT THE PRELUDE (Q-31 H-P). Its free names resolve in its own declarations, its own opens, and then the prelude (builtins, `Math` and its aliases, the run's host operations) — never at the load site: the site's properties, opened names, prelude shadows (`sum`, `abs`, `Math`, a host operation's name) and parameters never reach it, whichever spelling holds it (`open 'u'`, `M = load('u')`, `open M`, `open load('u')`, a load in a nested body, a parameterized owner or a deferred branch), so `open 'u'` ≡ `M = load('u'); open M` ≡ `M.Member` and the module's own declarations still beat the prelude. A name the module cannot resolve is an implicit parameter of the module member that uses it (PAR-03, MOD-06; a free name in the module's OUTPUT rows makes the module itself parameterized, so it is callable as `M(x)` and refused as an open provider). A site parameter reaches a member ONLY through the ordinary call laws written at the site — an explicit argument, bare forwarding by name (FWD-02: `G(n) = { M = load('u') ⏎ M.V }` supplies `V(n)` from `n`), or formula lifting (PAR-07) — never by the module reading the site; Q-04's sources are parameter bindings only, so site properties never reach a module either. A module's signatures and validity are therefore site-independent (no `ParameterPropertyCollision` between a holder's parameter and a module declaration).

One canonical URL is ONE module declaration per compiled program (Q-32 I-U): one elaborated module, one member binding, one callable identity, one open provider, however many directives, holders, owners, branches and spellings reach it. Holders stay separate bindings of their own — a holder's bare read of the module's OUTPUT is cached under the holder (FWD-02) — distinct canonical URLs are distinct declarations even when they serve identical bytes, and an explicit call stays fresh. Source admission is unchanged (Q-71): one fetch per canonical URL per operation, every splice charged as before.

## Dot-call resolution and missing members (G-24)

THE DOT ROUTE (Q-17 S-C, decided October 5 2026). An ordinary non-spread edge `R.n(args?)` resolves in ONE order, from ONE property lookup in the sync evaluator, the async twin and Lean alike (`EvalDotCallCounted` / `evalDotCallCounted`): (1) a DECLARED structural member `n` wins whatever its spelling — `string` included — and accessibility is checked after selection (K1-08); (2) a member declared only in clause branches is `LocalOnlyProperty`; (3) on a structural MISS, `n == string` is the number-to-text intrinsic (its argument rule and receiver reads unchanged); (4) otherwise the extension fallback `n(R, args)`. A lexical `string` is never consulted by `.string` (`string(x) = 99` / `3.string` is `'3'` while the written call `string(3)` is 99), `R*.n(args)` stays `n(R*, args)`, and every static view follows the same route (`ResolveStaticStructuralMemberProvider`, the alias static path `IsStaticPath` / `ResolveAliasStep` / Lean `Expr.staticAliasPath?`, the formula-lifting edge kinds, the sibling-dependency walk, and the editor, which resolves a declared `string` member to its declaration and an intrinsic one to the builtin). Formerly the intrinsic was tested FIRST on every algorithm receiver, so a declared `string` member was unreachable through dot syntax. Dot-call uses structural lookup first and lexical fallback second, at EVERY level of a chain: a receiver that is itself an argumentless dot edge — a `.string` edge included, so `Obj.string.Q` reads the declared `string` member's `Q` — is NAVIGATED through its declared structural members before either channel of the outer edge is consulted (`resolveDotReceiver` / `ResolveDotReceiver`, the ONE receiver-position resolution shared by the sync evaluator, the async twin, and the sequence optimizer's shadow check), so `Lib.Sub.Q` reads `Sub`'s own `Q` before any lexical `Q(x)` and `A.B.C.D` traverses every level; a declared intermediate member that is inaccessible from the site (a local-only member outside its owner's activation — the member-accessibility law of K1-08 applied at every level, so selection never depends on exposure) or a conditional-branch intermediate member is that edge's `LocalOnlyProperty` error, never a fallback (private members stay reachable); a receiver without the member, an argument-bearing edge (`Lib.Sub().Q`), and an intrinsic `.string` (a structural miss) are values, so the chain continues by extension fallback (`3.A.B` is `B(A(3))`; dot-call passes the receiver as the ordinary leading argument of that call — `sequences-lists-and-calls.md` § The dot-call receiver). Navigation is identity-only (no intermediate edge is evaluated). On the higher-order channel a SUPPLIED dot expression is projected the same identity-only way (Model C, NEED-06; Lean `projectNeedCallable` → `projectNeedStructuralMember`): an argumentless structural path yields its member's own callable (`Apply(Lib.F, 5)` calls `Lib.F`; `P(Lib.X, Lib.X)` is one identity), any other dot expression — an argument-bearing edge, a lexical fallback, an intrinsic `.string` — none. ONE CALLABLE IDENTITY (Q-18 C-B3, decided October 5 2026): the CALLEE position reads the SAME projection (C# `ResolveCallee` → `ProjectDotPathCallable`, shared with supplied cells and the sequence optimizer's recognition; Lean `resolveCalleeAlg` → `projectNeedStructuralMember`, aliases normalized by `resolveAliasTarget`), so `(Lib.F)(5)` is `Lib.F(5)` — the same member, frames, binder, family dispatch and alias target — `(Box.V)()` is the fresh call `Box.V()` (it never reads or populates `Box.V`'s cache entry), and a computed dot callee such as `(5.Inc)()` is `NotAnAlgorithm`, worded "a computed value, not a callable" (`EvalError.NotAnAlgorithm("dot result")`, rendered by `KatLangError.TryFormatComputedDotCallee`). Parentheses never change identity. The zero-parameter wrapper (`resolveAlg .dotMember` / `ResolveDotCallAlgorithm`) survives only as the internal CARRIER of a dot RESULT used as a receiver, never a program-visible callable (the former DOT-09 callee wrapper identity is retired), and a call written after an argument-bearing edge (`R.M(a)()`) does not parse (`syntax.md` § Line rules and declaration heads). The front end mirrors the same rule through the ONE compositional static classification `AstHelpers.ResolveStaticStructuralMemberProvider` (detector receiver classification, editor dot-member resolution, and the scope-free dependency view; `StaticStructuralMemberProviderKind.KnownFailure` marks a statically failing intermediate edge, selection `Never`). Structural lookup, receiver injection, fallback order, and diagnostics must stay consistent across Lean and C#; pinned by `ChainedDotStructuralPrecedenceTests`, CoreTests `chained*`, and the `dot-chain-*` `LanguageSpecCorpus` cases. A MISSING MEMBER ON A STATICALLY KNOWN RECEIVER (G-24) is never a RESOLUTION question: a known receiver (`Math`, a block, a module) that lacks the member falls back lexically exactly like any receiver, an unresolved fallback name in an inferring body is inferred as an implicit parameter exactly like a bare name, under a closed list or clause branch it is CHECKED exactly like a written callee name (Q-75 F-A, § The static obligation of a fallback name below), and a visible lexical callable of that name is a VALID fallback (`Ceiling(a, b) = b * 2` makes `Math.Ceiling(2.1)` the call `Ceiling(Math, 2.1)`, i.e. `4.2`). Static receiver knowledge never changes resolution; beside deciding whether a fallback is certain, it is used for diagnostics: the detector's occurrence recorder stamps `ImplicitParameterProvenance.DotMemberOrigin` at promotion and a diagnostic-only walk after exposure completion discards receiver claims/hints invalidated by provider changes (the receiver described exactly as the evaluator's dot-call context describes it), the report leads with the shared `Property 'X' was not found on `R`` clause plus the fallback explanation, a member-bearing receiver's suggestion comes from its OWN declared member surface only (`NameSuggestions` member-typo policy: wider length-scaled threshold, initial-letter safeguard (a unique one-edit correction may change the initial on names of at least five characters), no lexical name offered in its place — `Math.Min` never suggests `min`; a memberless receiver keeps the ordinary lexical policy), and a single such unresolved parameter is positioned at the member token when it belongs to the current source (an imported module keeps the local demand span). No layer may branch on the receiver's spelling (SYN-05). Pinned by `ReceiverAwareMissingMemberDiagnosticsTests` and the `dot-fallback-on-known-receiver-stays-valid` `LanguageSpecCorpus` case. ATTACHMENT (invalid-state §3.4): a provenance note is ONE object per promotion — the moment one detection run over one body, in one front-end context, first promotes the name — and every record that stands for that promotion references the same object: the inferred capture (`CaptureParameterPattern.InferredProvenance`, the first carrier), the declarations flattened from it, every caller signature implicit argument resolution lifts that capture INSTANCE into, the dot edge whose fallback occurrence caused the promotion (`Expr.DotCall.InferredFallbackProvenance`, stamped by the detector's `RewriteDotCall`), and the note lists the evaluator snapshots onto `ArityMismatch`/`UnresolvedImplicitParams`. Each carrier holds the reference in a private equality-transparent `RuntimeStateSlot<T>` field behind an internal init-only property, so the SYNTHESIZED copy constructor propagates it through every `with` (the resolver's and exposure's edge rewrites, the evaluator's span-attaching error copies) with no registration step and no hand-written copy constructor, while record equality, hashing, and printing never see it. The finalizer mutates the note in place BECAUSE it is shared — its verdict (forget the receiver claim, restrict the suggestion, forget the origin position inside a module) must reach every lifted caller without rewriting an executable node — and it is the only mutator, running before its tree is published (inside the synchronous pipeline, or inside a deferred region's gated materialization over notes that materialization minted), so evaluation only reads. The suggestion itself is DEFERRED (FE-1): a promotion captures only its immutable canonical candidate context (a `SuggestionQuery` from the detection run's `SuggestionContexts` — never a scope chain, which stays confined to its front-end operation), and the note computes the suggestion on its FIRST READ, when a diagnostic renders it, as that query's result with the finalizer's confirmed receivers applied in order (a forgotten claim drops it for good), publishing the pure value atomically — so a read never changes what the note says, and a program that renders no suggestion compares no candidate (`DeferredSuggestionProtocolTests`, `SuggestionContextDifferentialTests`). Nothing forks a note: a body elaborated again in another context (a module spliced under a second owner, a shared host subtree under two owners, a materialized branch, a re-detected tree) is a new promotion with a new note, which is why independent contexts reach independent verdicts, while two references under ONE owner share one elaboration and one note. Pinned by `ImplicitParameterProvenanceAttachmentTests`.

### The static obligation of a fallback name (Q-75 F-A, October 5 2026)

A dot edge whose structural lookup misses IS the call `n(R, args)` (§ above), so its fallback name owes what a written callee name owes — exactly when the edge certainly takes that route. The ONE decision is the existing `LexicalFallbackSelection` lattice over the edge's structural-MISS verdict, which parameter detection computes with the scope-aware receiver classification and stamps on every edge (`Expr.DotCall.ElaboratedMissSelection`, `AstHelpers.GetStructuralMissSelection`, read back through `EffectiveMissSelection`): `Never` — the receiver statically declares the member, or the edge fails statically — means no fallback name exists; `Conditional` (MAY) — the receiver is a parameter, an opaque reference, or a navigated path over one, which may or may not declare the member at run time; `Always` (MUST) — the receiver is a value expression, or a known algorithm that declares no such member. A `.string` edge never has a fallback name (`LexicalFallbackSelectionOf`: its miss route is the intrinsic). The two front-end questions read the lattice differently (`ParameterDetector.CollectsFallbackName`): an INFERRING body (implicit signature) collects the name whenever the selection is not `Never` — unchanged — while a CLOSED explicit parameter list or a clause-branch body (the declared-name check) checks it only when the selection is `Always`. `Get(obj) = 5.size` is then the same `UndeclaredIdentifier` as `Get(obj) = size(5)`, positioned at the member token (`FindFirstResolveSpans` visits a checked edge's member between its receiver and its arguments), worded with the G-24 receiver clause — "Property 'size' was not found on `5`, so `5.size` is the call `size(5)`; 'size' is not declared in the explicit parameter list or otherwise visible here." — and offering a known receiver's own near member (`Math.Ceiling` suggests `Math.Ceil`; bounded by `MaxClosedBodySuggestionAttempts`). A `Conditional` edge carries no static requirement (`Get(obj) = obj.size` is valid, and a receiver lacking `size` reaches the runtime fallback), and neither does `p.string.Q`: its `.string` edge navigates a parameter, so `Q`'s selection is MAY. A branch body behaves exactly like a closed list whether or not the branch is ever selected (the check is static), and the plain (non-dot) undeclared-name messages are unchanged. Formerly a closed list asked only the definite question of plain names, so `Get(obj) = 5.size` elaborated and failed at run time, while `Get(obj) = size(5)` did not elaborate. Lean models no front-end rule (FORMAL-02). Pinned by `DotSemanticsDecisionTests` (the Q-75 matrices and the static-obligation metamorphic relation), `ReceiverAwareMissingMemberDiagnosticsTests`, `ImplicitParameterDiagnosticsTests`, and the `closed-list-must-fallback-name-is-checked`, `closed-list-may-fallback-name-is-runtime` and `branch-must-fallback-name-is-checked` spec cases.

## Builtin identity and the zero-argument value demand (SYN-05)

BUILTIN CALLABLES ARE ORDINARY PRELUDE BINDINGS, and IDENTITY — never spelling, never arity — decides semantics (SYN-05). Lexical resolution selects exactly one callable without considering the argument count; the resolved callable then determines its signature and behavior: `resolve name -> select ONE identity -> assemble the ordinary argument supply -> bind against THAT signature -> invoke`. KatLang has no overloading by arity, so a nearer property or parameter named `if`, `count`, or `sum` shadows the prelude binding COMPLETELY — `if(x) = x + 1` makes `if(1, 2, 3)` an arity error against `if(x)`, never a fallback to builtin `if/3` — and a bound parameter may carry any callable under a builtin's name (`Apply(if, x) = if(x)`). There is NO reserved-name mechanism, in either engine: do not add `ReservedNameValidator`, a `BuiltinDescriptor.IsReservedName` flag, reserved-name tables, `ReservedName` diagnostics, or grammar productions excluding builtin names from binding identifiers. (`BuiltinRegistry`'s reserved-name check and `HostOperations.ReservedPreludeNames` are unrelated: they govern who may BUILD the prelude — a Math alias or a host operation may not collide with a builtin — not what source may declare.) Consequently NO layer may branch on a callee's written spelling: the parser is purely syntactic about calls (it never counts arguments from a callee name, so a wrong-arity builtin call is an ordinary evaluation-time `ArityMismatch` against the resolved signature, and is inert in an unevaluated property exactly like `count(1, 2, 3)`), and a builtin recognizer such as the loop optimizer's `if` planning may use the spelling only as a lookup KEY taken from registry metadata (`Evaluator.BuiltinDisplayName`) before confirming `Evaluator.ResolvesToBuiltinAlgorithm`. Lean already models exactly this — `preludeAlg` declares `if` with one ordinary `publicProp`, and `NameOwnership` treats the prelude as the outermost property level of the owner walk — so a spelling gate anywhere in C# is a divergence from the authoritative model. Builtin `if`'s ONE intrinsic behavior is its invocation (`if(condition, whenTrue, whenFalse)`: evaluate the condition, then only the selected branch); that laziness belongs to the resolved builtin, disappears when the name is shadowed, and never applies retroactively to a value the caller already built (`if(true, Risky*)` evaluates all of `Risky` under the ordinary `expression -> value -> supply` rule). A builtin VALUE slot demands its SELECTED argument through the ONE zero-argument value-demand law (C# `ZeroArgumentValueDemandRejection`/`ZeroArgumentValueDemandError`, Lean `zeroArgumentDemandError?` — the factored rejection half of the value-position `Param`/`Resolve`/block arms): a resolved callable that cannot accept zero supplied arguments is the ordinary arity rejection at the argument's reference and its body is never entered (under a closed list, `Probe(u) = if(true, Inc, 0)` with `Inc(x) = x + 1` is "Property 'Inc' expects 1 parameter…", never `Unknown name: x`; a body that would not read its parameter is rejected all the same — in an inferring formula the value slot lifts the reference instead, § The unified formula-lifting law), a conditional is `ConditionalValueAccessError`, a written block `UnresolvedImplicitParams`; an UNSELECTED slot is never demanded; CALLBACK slots that supply arguments (`map`/`filter`/`reduce` steps, loop steps) never consult it; `reduce`'s initial accumulator keeps its dedicated hint but decides through the shared rejection law and retains the demanded family's name. Collection arguments and fixed VALUE/whole-number controls consult the same law after ordinary fixed-arity binding, and DEMAND an accepted item as soon as the descriptor identifies its VALUE slot during left-to-right call-item assembly, before later argument effects, so a collecting-only callback argument is never eagerly evaluated (`DemandSequenceBuiltinCallItemValue` / `demandSequenceBuiltinCallItemValue`, then `SequenceBuiltinValueDemandError` / `sequenceBuiltinValueDemandError?`); call-item and suffix preparation preserve the written source without demanding callback positions. Every builtin VALUE slot (`if` condition/branches, `while`/`repeat` initial state, the `repeat` count, `atoms`, `range` — `EvalResolvedArgumentCounted`, Lean `evalArgumentValueCounted` over `ResolvedArgumentAlgorithm.Source`/`source?`) and the ordinary-dot `.string` receiver (`EvalDotStringReceiverAlgOutput`) go through it; pinned by `LazySlotZeroArgumentDemandTests`, `CoreTests/ValueDemand.lean`, and the `lazy-slot-demand-*` `LanguageSpecCorpus` cases. Pinned by `BuiltinCallableIdentityTests`, `IfBuiltinArityPayloadTests`, the `builtin-callable-is-an-ordinary-prelude-binding` / `no-arity-based-callable-selection` / `if-*` `LanguageSpecCorpus` cases, and `CoreTests/NameOwnership.lean`. NOTE: `load` is NOT covered by this rule — it is still recognized by raw spelling (`AstHelpers.TryGetUnresolvedLoadArguments`) as a front-end/module directive; that asymmetry is deliberate-for-now and is not a licence to re-privilege a callable's spelling.

## Math members, host operations, and the prelude in every layer (audit #8)

**Math members are recognized by what a name resolves to.** A Math FUNCTION member has three spellings — the qualified `Math.Sin`, the prelude alias `sin`, and the canonical `Sin` an `open Math` provides — and one registry descriptor (`MathCallableFacts`). The front end's registry-proven value-demand contract (a Math member's arguments are strict value positions, so a referenced callable that requires supplied arguments lifts its implicit parameters — one that works with no arguments is read as a cached value instead, Q-03 — and a closed list that cannot supply them is diagnosed) belongs to the CONSUMER, so it applies to every spelling that resolves to the member and to none that does not (`AstHelpers.TryGetRegistryProvenMathCalleeFacts`): the qualified and alias spellings are recognized by shape (the prelude is reached before any open, so a caller's shadow predicate is all ownership needs), and the opened spelling by the identity verdict parameter detection stamps on the name (`Expr.Resolve.ElaboratedMathMember`, set only when the owner walk leaves the name to the opens and exactly one open provides it from the prelude's own `Math`). Dotted-call equivalence carries the contract through fallback: a dot edge whose lexical fallback MUST be selected (a non-`string` edge whose `ElaboratedMissSelection` is `Always`) on a Math member is the call `x(receiver, args)`, so `A.sin` lifts `A` exactly as `sin(A)` does and `2.pow(A)` as `pow(2, A)` — the unified formula-lifting roles classify the edge as that call (`FormulaLiftingRoles.EdgeKind`, shared by the resolver's rewrite and dependency collection and by the sibling-order channel; the former dedicated `AstHelpers.HasRegistryProvenStrictValueFallback` / `IsStrictValueMathMember` had no remaining consumer and were deleted with Q-18); a fallback that is only possibly selected keeps its receiver and arguments neutral. Before, `open Math` + `F = Sin(A)` and `F = A.sin` elaborated `F` without `A`'s parameter (a runtime arity error) while `sin(A)` lifted it, and a closed `F(x) = Sin(A)` or `F(x) = A.sin` escaped the front-end diagnostic (`ClosedListStrictValueDiagnosticTests` had pinned the dot receiver as never lifting — a measured scope boundary of the then-behavior, now the direct call's rule). LIFTING a Math function referenced bare as a value follows the unified formula-lifting law (§ The unified formula-lifting law, September 30 2026): the lifting signature is keyed by the resolved member, never by the route, so the alias `sin`, the qualified `Math.Sin` and the opened `Sin` lift alike (formerly the lift was route-based and the opened `Sin`, like every opened callable, was never forwarded). FWD-02's LONE-ROW alias eligibility is identity-keyed too since October 1 2026 (the alias, `Math.X` and the opened name are callable-alias targets alike; formerly route-based, an opened name excluded), and a callable ALIAS of a member carries the consumer contract by its normalized target: with `A = abs`, `A(Inc)`, `Inc.A` and a dotted alias member's call `Lib.A(Inc)` give `Inc` the VALUE role exactly as `abs(Inc)` does, so a closed `K(z) = A(Inc)` is the same run-time zero-argument demand as `K(z) = abs(Inc)` (since Q-15, 2026-10-02; until then both were the same front-end diagnostic, triggered through the deleted `ImplicitArgumentResolver.ResolvesToStrictValueMathMember`). A host operation's arguments are values for lifting, never strict. The qualified member reference is also the callee in an ordinary call such as `(Math.Abs)(A)`: the callee stays in algorithm position, its own parameters are supplied by the call, and the same strict contract lifts A's dependencies and diagnoses blocked forwarding. At run time the grouped callee IS the member (Q-18 C-B3: a dot expression has one callable identity), so `(Math.Abs)(A)` is `Math.Abs(A)` in every respect — no Math-specific resolution exists (the qualified-native gate `TryResolveQualifiedMathNativeReference` is deleted), and a user-defined `Math = { public Abs(x) = 100 }` gives 100 for `(Math.Abs)(3)`, `Math.Abs(3)` and `map([1], Math.Abs)` alike. User callables keep neutral arguments.

**Identity of the three spellings as bindings.** The alias and the canonical member are DISTINCT property bindings that share one algorithm (the alias property's value IS the member's algorithm object, so dispatch and signatures cannot drift): the zero-argument cache keeps one entry per binding, and repeated-name callable identity (declaration + declaring scope chain + activations, Lean `sameRepeatedCallableIdentity`) sees the alias wired under the prelude and the opened member wired under `Math`, so `P(f, f) = f` binds `P(pi, pi)` and, under `open Math`, `P(Pi, Pi)`, but rejects `P(pi, Pi)`. A qualified `Math.Pi` is an argumentless structural path, so on the algorithm channel it IS the `Math` module's `Pi` member — the very binding `open Math` provides (Q-18 C-B3): under `open Math`, `P(Pi, Math.Pi)` binds one identity, while `P(pi, Math.Pi)` rejects exactly like `P(pi, Pi)`. Math functions cannot be compared this way at all: they carry no value, and repeated callables must.

**Host operations are prelude members in every layer.** A run's `HostOperations` extend the prelude the evaluator resolves against, and every front-end layer must see the same prelude: parameter detection and open validation already did; exposure analysis (`PropertyExposureResolver.Resolve`, whose recorded chain also serves deferred-region materialization) and the editor model (`SemanticModelBuilder.Build(ParseResult)`, through the host configuration the parse result carries, `ParseResult.HostOperations`) now do too. Because the prelude precedes every open, an operation named like an opened library's member is what a bare reference selects: charging the library member made a self-contained property local-only (`Outer.Inner` refused), and the editor named the library member the evaluator never reads. Completion lists the operations as prelude names (`SemanticModel.PreludeSymbols`). Pinned by `NameResolutionAuditTests`.

## Zero-argument value demand follows actual call arity (September 2026)

A callable may satisfy a ZERO-ARGUMENT VALUE DEMAND **if and only if an ordinary call supplying zero arguments can bind it** (C# `Evaluator.AcceptsZeroSuppliedArguments`, Lean `Algorithm.acceptsZeroSuppliedArguments`). Eligibility is arity, never parameter-list emptiness. Before this rule the law rejected a demand whenever the callable declared any parameter, so `Only(*xs) = xs` — whose ordinary call `Only()` is perfectly legal and yields `[]` — could not be read as a value at all, and the rejection reported the flattened declared capture count (`Head(x, *rest)` claimed two parameters where its own call reports one required item).

**The rule is the binder's own.** `ParameterPattern.MinimumSuppliedSlots` / `ParameterPattern.minimumSuppliedSlots` states the arity check `BindNeedPatterns` / `bindNeedPatterns` performs, and those binders now read it rather than re-deriving it: every top-level pattern consumes exactly ONE supplied slot whatever it contains — a structural group, sequence or list, is one slot the binder opens afterwards — and a COLLECTING capture at that level consumes NONE, because it collects whatever is left after the fixed prefix and suffix bind (an empty leftover is the exact empty list). A clause family decides by its own dispatch rule instead: it accepts zero supplied arguments exactly when some branch's top-level pattern has arity zero, which is the branch the family dispatcher (`selectNeedFamilyBranch` / `BindNeedFamilySupply`) selects for an empty supply (a flat multi-binder core equivalent always has at least two parameters, so it never accepts). A BUILTIN is deliberately not decided by the law at all: `zeroArgumentDemandError?` passes it through so `EvalBuiltinValueCounted` / `evalBuiltinValueCounted` raises the builtin's own rejection, which is the very message `sum()` produces.

Consequently:

* `Only(*xs) = xs` is eligible: `Only`, `(Only)`, `((Only))`, `if(true, Only, 0)`, `count(Only)`, `Only.count`, `Obj.M`, a fixed user parameter that reads its argument, a root output row — the direct value demands produce the collected empty list, exactly as `Only()` does; `count(Only)` and `Only.count` consume that value and return `0`.
* `Head(x, *rest)`, `Tail(*rest, z)`, `Mid(x, *rest, z)`, `Pair(x, y)`, `P((x, y))`, `P((x, *rest))`, `P((*xs))`, `P([*xs])` and `G((a, b), *rest)` are not: each requires at least one supplied value — a structural pattern binds ONE supplied value of its own kind (`P((*xs))` a sequence, `P([*xs])` a list), it never accepts none.
* The rejection reports the TRUE minimum supplied count (`Head` 1, `Mid` 2, `P((x, y))` 1, `G((a, b), *rest)` 1) in the ordinary structured `ArityMismatch` at the demand site, so the demand and its ordinary zero-argument call can no longer claim different numbers. The demand law reads that rule directly and deliberately does NOT consult `CallableArityFacts`; since the F4 correction the facts state the same per-level rule (`G((a, b), *rest)` is min 1, unbounded max — see `CallableArityFactsPerLevelTests`), so the two can no longer report different minimums.

**Eligibility is all that changed.** An accepted demand evaluates through the ONE funnel `EvalZeroArgumentDemandOutputCounted` / `evalZeroArgumentDemandOutputCounted` (with its value projection): a callable declaring no top-level pattern is its output exactly as before, a pattern list that accepts the empty supply is bound by the ORDINARY binder against that empty supply — so the collecting parameter holds `[]` while the body runs and the callee's names shadow all three inherited tiers as a written call's do — and a zero-accepting family dispatches through ordinary conditional dispatch. The funnel's common arm is a bare delegation to the very core the demand sites called before, and the binding arm's locals live in a separate non-inlined frame, because nested blocks and property reads recurse through it inside the calibrated 1 MiB stack envelopes.

Everything else is untouched:

* **Cache policy.** A bare property-style demand still takes the run cache (`isCacheableZeroArgPropertyAlgorithm` now reads the same acceptance rule, so a newly eligible property is on the SAME path an ordinary zero-parameter property is on), and `Only()` keeps its established direct-call bypass. Builtin VALUE slots — `count(Only)` and the dotted `Only.count` alike — read the same entry (since September 27 2026 a builtin argument that names a property resolves on its value channel to the ordinary property read; how a property value is consumed does not affect caching — see `evaluator-and-hosting.md` § Zero-argument property cache).
* **The algorithm channel.** A callback, a higher-order argument and a loop step still receive the callable: `map((1, 2), Only)` is `[[1], [2]]`, never `[]`. So does a callable FORWARDED through a parameter: a user call binds `Apply(Only, xs)`'s parameter on both channels (the value `[]` and the algorithm `Only`), and a builtin slot that INVOKES its argument — the `filter` predicate, the `map` mapper, the `reduce` reducer, a `while`/`repeat` step — invokes the ALGORITHM-channel binding (`ResolvedArgumentAlgorithm.invoked` / `InvokedAlgorithm`), so `Apply(f, xs) = xs.map(f)` selects the same callable as `xs.map(Only)`, from a nested block capturing the parameter too; plain binding performs no VALUE evaluation, and invoking-slot projection obtains the independent callable identity without forcing. The descriptor identifies VALUE slots during left-to-right assembly: demand finishes before the next argument is evaluated. Collecting-only callables and zero-arity families in CALLBACK slots remain unevaluated.
* **Value-context lifting reads the SAME rule (Q-03, decided September 28 2026).** *If a callable works with no arguments, using its name alone reads its cached value, even if it declares optional or collecting parameters; `A()` evaluates it again.* The front end's decision to lift a referenced callable's parameters into the enclosing signature — in any VALUE position of the unified formula-lifting law (§ The unified formula-lifting law): an operand, a list or capture element, an index target, a spread operand, a builtin value slot, a Math, host or family argument, a fallback dot receiver, a block or callback body that uses it in an expression — happens BEFORE the law, and it asks this law's question: a callable that accepts zero supplied arguments is NEVER lifted, because declaring a parameter does not by itself make a bare reference a call. Its reference stays this demand, read through the cache, in every position. ONE predicate serves both halves: `ParameterPattern.AcceptsZeroSuppliedSlots` (`MinimumSuppliedSlots` is zero), read by `Evaluator.AcceptsZeroSuppliedArguments` for a user algorithm and by the resolver's `RequiresSuppliedArguments` (over `CallableSignature.AcceptsZeroSuppliedArguments`) for every value-role reference whatever its category, and at root-row preservation; Lean states it as `liftsBareValueReference`, with the law `bare_reference_lifts_iff_not_cacheable` (lifting and cache eligibility are complements). Before the decision the lift judged "declares any parameter", so `Only + 1`, `[Only]` or `abs(Only)` turned a collecting-only `Only` into the fresh call `Only(xs*)`, lifted a collecting `*xs` into the enclosing owner (which at the root could only forward an empty supply), and bypassed the entry its neutral positions read: `Roll == Roll` was `false`, `first(Pair)` and `Pair:0` read different evaluations, and a formula chain re-ran its base 2^k times (PV-03). A callable that REQUIRES a supplied argument (`Inc(x)`, `Head(x, *rest)`, `P((*xs))`) is lifted and forwarded exactly as before, so a lifted FIXED root parameter still leaves an argument nobody can supply. Consequences: a body whose ONE row is the bare name is NOT a value position but a callable alias or bare forwarding (§ Callable aliases and bare forwarding; decided September 29 2026, superseding Q-03's former alias clause, under which `Alias = Cnt` was a zero-parameter property holding Cnt's value): `Alias = Cnt` IS Cnt's callable — read bare, it is Cnt's zero-supply demand under its OWN cache entry, one evaluation for the alias's binding — and with `Cnt(*xs)`, `G(*xs) = Cnt` forwards G's same-named collector, `Cnt(xs*)`, while `G(p) = Cnt`, which forwards nothing to it, reads Cnt's cached value; in a formula, forwarding by shape reaches only a grouped stream `H((*xs))` or `H([*xs])`; a closed parameter list never blocks such a reference (formerly PV-27: the closed-list strict-value diagnostic, itself removed by Q-15, reported it); and because an owner lifts only from callees that require arguments, an implicitly lifted signature requires arguments itself — unless enclosing parameter bindings already supply the required ones (Q-04: the formula `H = [Head]:0` inside `F(x)` forwards only `*rest`, so `H` accepts zero arguments and is then read like any such callable). Explicit calls, with or without arguments, stay fresh. * **Laziness, charges, cancellation, optimizer.** An unselected builtin slot is still never demanded, the depth-only argument charge is unchanged, and the loop planner never plans a callable with an explicit parameter list as a temp (such a step falls back to the generic strategy).

## Automatic parameter forwarding preserves existing bindings (Q-04, September 2026)

THE LAW (the owner's decision of constitution open question Q-04, option (a), September 28 2026): **automatic parameter forwarding must not change what an existing name refers to.** Its boundary: **automatic forwarding reuses parameter bindings only — own written or inferred parameters, and accessible captured parameters of enclosing owners, clause-branch binders included. Properties, opened names, module members and prelude builtins are never forwarded as parameters.**

Two operations answer two different questions, and the second never feeds back into the first:

* **Name resolution** — *what does this written identifier denote?* — is `ParameterDetector` (the six rules of § The resolution model in one place). It decides every written name, promotes names nothing binds, and reports undeclared ones in closed bodies. Its verdicts are final.
* **Automatic parameter forwarding** — *which EXISTING parameter binding can satisfy this callee parameter?* — is `ImplicitArgumentResolver`. When a lifted reference in a FORMULA (a bare value-position reference, inside an expression, to a callable that requires supplied arguments, § Zero-argument value demand — a body whose ONE row is the bare callee is a callable alias or bare forwarding instead, § Callable aliases and bare forwarding) needs a callee parameter `n` — formula lifting is BY BINDING NAME, however many times the callee names `n` (§ Formula lifting is by binding name) — its argument is the binding a WRITTEN parameter reference of `n` would denote at the referencing body: the body's own written or inferred parameter; otherwise the nearest enclosing parameter binding the owner walk reaches before any same-named property — an ancestor's written or inferred parameter, a clause-branch binder, the never-called root's inferred names (`ImplicitArgumentResolver.ForwardableParameters`: per level, the enclosing name-resolution parameters minus every name the level declares as a property, persistent and keyed into the resolver's region memo by canonical content). Only when neither exists does an INFERRING body receive a new parameter `n`: appended after its own names (PAR-05), keeping the callee's pattern shape and kind, and marked as a FORWARDED parameter (`Algorithm.User.ForwardingParameterStart`, `NameResolutionParameterPatterns` is the prefix before it). A CLOSED body — a written parameter list or a branch pattern — receives nothing: the reference stays the zero-argument demand (a Math position remains an ordinary runtime zero-argument demand, per Model-C Q-15), and a closed body's lone bare row — bare forwarding — reuses the same bindings by name and is rejected (`UnforwardableParameter`) rather than adding one. Opens never take part: they are not owner levels, so an opened `n` leaves the walk undecided and the body gets a forwarded parameter.

A forwarded parameter is an ordinary parameter for every CALLER — arity, order, binding, activation, exposure — and a same-named property of its owner or of a body nested in it is still `ParameterPropertyCollision` (Lean `OwnerLevel.forwarded` is part of `conflictingOwnedNames`). But it is never what a written name denotes: the owner walk, open-head classification, Grace eligibility, the editor's scope visibility (`SemanticModelBuilder.CreateScope` declares only the name-resolution prefix) and the evaluator's reads of written names never see it — a written `Param` node is owned by a name-resolution parameter at or below the forwarding owner (the reuse rule guarantees no nearer forwarded parameter of that name exists), and a written `Resolve` is a property lookup. So nothing is re-selected after lifting: the former `ParameterDetector.CompleteOwnership` pass, which re-ran the owner walk against the completed signatures and made every same-named written reference denote a lifted parameter, is deleted, together with its synthesized-call origins, signature-preserving re-resolution, and Grace revalidation. A synthesized argument is a spanless `Param` read (or `name*` when a collecting destination meets a collecting SOURCE binding — the reused enclosing binding's kind counts, FWD-02), and a callee group is rebuilt as its own structural kind from the bindings its captures stand for (§ Callable aliases and bare forwarding; forwarding preserves bindings and structural kind), so the callee receives exactly the binding an existing written reference already denotes.

Consequences, all pinned:

* `A = y + 1` / `F(y) = { G = y * 1000 + A ⏎ H(y) = G ⏎ H(100) }` / `F(3)` is `3004`, exactly the inlined `G = y * 1000 + (y + 1)`: G reuses F's `y` and takes no parameter, so H's unrelated `y` cannot reach it. Before the decision G received its own `y`, completion made the written `y` follow it, and the program gave `100101` (PV-01). Extracting a sub-expression into a property therefore never changes the binding of a name that was already resolvable.
* A helper that reuses its owner's parameter is an ordinary zero-parameter property — local-only, one evaluation per activation of its owner (PROP-08) — so a neutral `if` argument reads it (`Report(width, height) = { Doubled = Area * 2 ⏎ if(width > 1, Doubled, 0) }` is 24, formerly `ArityMismatch`), and so do callback and loop-step blocks (`map([1, 2], { A + e })` inside `F(n)` binds only `e`).
* A same-named PROPERTY is never forwarded: `v = 99` / `Need(v) = v` / `Outer = Need + 1` still infers `Outer(v)` (`Outer(7)` is 8), so an unrelated property elsewhere can never turn a parameterized formula into a zero-parameter one. A written reference to the property is never rebound either: in `Outer = { Inner = v ⏎ Inner + Need }` Inner's `v` stays 99 (`Outer(7)` is 106, formerly 14). The same holds for an opened member (formerly `ownership-later-lifted-parameter-beats-inner-open`, now `forwarded-parameter-leaves-an-opened-reference`) and a builtin (`NeedMin(min) = min + 1` / `Safe = NeedMin + min((3, 4))` / `Safe(10)` is 14: the written `min(...)` still calls the builtin, formerly `NotAnAlgorithm`), while parameters named like builtins stay parameters to forward (`Clamp(x, min, max)` / `Safe = Clamp + 0`).
* A formula under a closed parameter list forwards an accessible enclosing parameter too: `A = y + 1` / `G = { F(x) = A + 0 ⏎ F(1) + y }` / `G(10)` is 21, with or without a strict Math wrapper (K1-04 had pinned the refusal, which the decision supersedes; the strict and the ordinary formula positions still agree). The LONE row `F(x) = A` is not a formula but bare forwarding (FWD-02), which reuses the same enclosing `y` by name and leaves F's own `x` unused, so the same program with `F(x) = A` is 21 as well.
* A forwarded parameter gives no meaning to a written name nothing declares: `Need(v) = v` / `Outer = { F(0) = 0 ⏎ F(n) = v ⏎ F(1) + Need }` is `UndeclaredIdentifier` in the branch body (formerly completion rescued it with Outer's forwarded `v`).
* Explicit shadowing is untouched: in `Outer(y) = { Inner(y) = A * 2 ⏎ Inner(10) + y }`, A's `y` inside Inner is Inner's own (`Outer(3)` is 25). A NEARER owner decides: under `Outer(y) = { Mid(y) = { Inner = A ⏎ Inner } … }` the alias Inner is A's callable (A's `y`), and Mid's lone row forwards Mid's own `y` to it, never Outer's.
* Aliases are NOT formulas (FWD-02, decided September 29 2026, superseding "aliases are formulas too"): inside `F(x)`, the bare `H = Head` with `Head(x, *rest)` is a callable alias of Head — Head's own `(x, *rest)` — and ignores F's `x` (`H(10, 20)` is 11), while the formula `H = [Head]:0` reuses F's `x` and forwards only `*rest`, so it accepts zero arguments (it is then read, never lifted, Q-03; `H(10, 20)` inside `F(4)` is 6). A grouped callee pattern keeps its reused capture in a formula (`P((a, b))` inside `F(a)`: `G = P + 0` takes only `b` — a sequence group left with one binder IS that binder, the invalid singleton `(b)` is never manufactured — and calls `P((a, b))` with F's `a`, so `G(5)` inside `F(10)` is 15).
* A shared (DAG) body reached under owners with different parameter names is rewritten once per distinct set of forwardable bindings (the region-memo key); deferred branch regions carry the bindings in their resolver context.

Lean states the rule as `forwardingSource` (beside `liftsBareValueReference`) over the name-resolution owner chain, with the proved laws `forwarding_reuses_exactly_the_written_parameter_binding`, `forwarding_never_supplies_a_property`, `forwarding_never_supplies_an_undeclared_name`, `fresh_forwarded_parameter_only_without_a_parameter_binding`, `forwarded_parameter_changes_no_written_binding` and `forwarded_parameter_still_conflicts_with_a_same_named_property` (`KatLangArityLaws.lean`), and `CoreTests/ForwardingBindings.lean` evaluates the decided and the superseded elaborations side by side. Pinned in C# by `AutomaticForwardingBindingTests` (six routes and host-call counts, the elaborated tree, the editor model, and generated added-dependency and extraction metamorphic families), `OwnershipConformanceTests` (mask bit 4 = forwarded, against `CoreTests/NameOwnership.lean`), and the `forwarding-reuses-a-captured-ancestor-parameter`, `forwarding-never-supplies-a-property-an-open-or-a-builtin`, `forwarded-parameter-leaves-an-opened-reference` and `forwarded-parameter-names-nothing-in-a-closed-body` `LanguageSpecCorpus` cases.

## Formula lifting is by binding name (September 2026)

THE RULE (decided September 29 2026, reversing the Q-72 refusal of the same day; narrowed to formulas by the alias and bare-forwarding rules, next section): **formula lifting is by binding name, regardless of how many times that name occurs in a callee's parameter patterns.** A caller owns ONE binding for a given parameter name; when a formula USES a callee — in an operand, a list element, an index target, a strict Math argument, a callback body, beside other dependencies — and the callee uses that name in several parameter positions, the lifted call supplies the caller's one binding to every occurrence. It is the composition rule formulas already follow across callees, applied without exception within one callee:

* `F(x) = x + 1` / `G(x) = x * 2` / `H = F + G` is `H(x) = F(x) + G(x)` (`H(3)` is 10) — one name shared by two callees;
* `P(x, x) = x` / `Twice = P * 2` is `Twice(x) = P(x, x) * 2` (`Twice(7)` is 14; `Twice(7, 7)` is an arity error, because Twice has one parameter) — one name used twice by one callee.

The language does not distinguish the two cases. ONE merge builds the lifted signature: the callee captures are walked left to right and a capture is skipped when an earlier capture — the owner's own, an earlier dependency's, an earlier one of the same pattern, inside a group too — or a reused enclosing binding (Q-04, previous section) already binds its NAME (`ImplicitArgumentResolver.AppendMissingPatterns` / `MissingCapturePattern`, PAR-05's first-occurrence order); a group keeps its KIND for the names that are new there — a sequence group left with ONE non-collecting binder IS that binder (the singleton `(x)` is not a pattern), a list group keeps its brackets (`[a]` is the one-element pattern), and a group left with no new binder contributes nothing. So with `D = [P]:0`, `P(x, x, x)` lifts `x`; `P((x, a), x)` lifts `(x, a)`; `P(x, (x, a))` lifts `x, a`; `P(x, [x, a])` lifts `x, [a]`; `P((x, y), (z, x))` lifts `(x, y), z`; `P((x, x))` lifts `x`; `P([x, x])` lifts `[x]`; `P(x, (x, *rest))` lifts `x, (*rest)`; `P(x, *rest, x)` lifts `x, *rest` — never a formula signature that repeats a name, and never one parameter per occurrence. ONE builder makes the synthesized call (`BuildImplicitCallArguments`): the callee's own patterns rebuilt from the caller's bindings (`P(x, x)`, `P((x, a), x)`, `P(x, [x, a])`, `P(x, rest*, x)` — each group rebuilt as its own kind, next section), so every occurrence of a name reads that one binding, and a collector is re-spread exactly when its SOURCE binding collects (FWD-02), never because a name repeats. A closed list or branch pattern that declares the name forwards its own binding into a formula (`Q(x) = P + 0` is `Q(x) = P(x, x) + 0`); one that does not follows the ordinary closed-list rule (`Q(y) = P + y` keeps `P` the zero-argument demand, in a Math position too — since Q-15 no front-end report names the missing `x`). Which positions lift and which callables lift are the unified formula-lifting law's (next section) — value positions lift and callable positions (`Apply(P)`, callees, callbacks, loop steps) keep the reference, for every category of callable, opened and structural members and clause families included — and a bare ROOT row is its callable's own zero-argument demand; none of these general rules has a repeated-name case.

**A body whose ONE row is the bare callee is not a formula.** `Some = P` is a callable alias of P — a call through it is P's own call, with two independent arguments, which must be equal — and `Q(x) = P` is bare forwarding (next section): Q's one binding `x` reaches both occurrences by name, `P(x, x)`, the same call the formula `Q(x) = P + 0` builds, under a closed list that never gains a parameter. The alias-signature deduplication this section formerly stated (`Some = P` as `Some(x) = P(x, x)`, recorded by the Q-72 reversal and the review that followed it) is superseded, and so is the exact-alias wrapper that replaced it (binding indirection, October 1 2026).

The relation to Q-05 (`sequences-lists-and-calls.md` § Collecting parameter lists, deconstruction, and callbacks: REPEATED NAMES ARE CONSTRAINTS, NOT MERGES) is exact: **a repeated name constrains independently supplied arguments; when a formula supplies the same caller binding to several occurrences, each occurrence receives that same complete binding, and no synthetic value/callable merge occurs.** The direct `P(7, 8)` — and the alias `Some(7, 8)` — write two arguments, and they must agree. `Twice(v)` evaluates its one argument once and binds it — the value and callable of that ONE argument, or its recorded failure (Q-01) — and each of P's slots reads that binding: the occurrences agree by construction on a value, and a callable-only or failed argument is its own failure, exactly as through the written `Same(x) = P(x, x)`. That equivalence is the pinned metamorphic law: formula lifting is observationally the explicit call that writes the same caller binding into every matching callee slot.

A group that dedupes down to one name keeps the law of its own kind. With `P((x, x)) = x` and `Some = [P]:0`, Some takes the bare binding `x` and calls `P((x, x))`, so `Some(v)` is the written `Some(x) = [P((x, x))]:0` for every `v`: `Some(7)` is `7`, `Some([7])` is `[7]`, `Some((7, 8))` is `(7, 8)` — each occurrence receives the whole binding, and the pair `(v, v)` is always a sequence. With `P([x, x]) = x` and `Some = [P]:0`, Some takes the one-element list pattern `[x]` and calls `P([x, x])`: `Some([7])` is `7`, `Some([[7]])` is `[7]`, while `Some(7)` and `Some((7, 8))` are the kind mismatch and `Some([7, 8])` the list arity error of the written `Some([x]) = [P([x, x])]:0`. A further formula forwards each surviving group as the same kind again (`Next = [Some]:0`). `RepeatedNameInsideOneSequenceGroup_LiftsTheBareBinding`, `RepeatedNameInsideOneListGroup_KeepsTheOneElementList` and `AnotherFormulaOverASurvivingGroup_RebuildsItAsTheSameKind` pin these observations against the written formulas; Lean's `CoreTests/RepeatedNameConstraints.lean` evaluates the corresponding elaborated trees.

History: the Q-72 decision (September 29 2026) had refused such a reference with a front-end error, reasoning that forwarding by name collapses independent occurrences into one input. It was reversed the same day: a caller binding forwarded to several slots is one input deliberately supplied to each — the reading formulas already give `H = F + G` — and only independently supplied arguments are constrained. The refusal, its diagnostic, its signature query and report memo, and its Lean specification are removed. FWD-02 (next section) later took the lone-row forms out of formula lifting — an open lone row is a callable alias and a closed one bare forwarding — so lifting a callee's names into a SIGNATURE concerns formulas only.

Lean models no signature construction: `forwardingSource` decides per NAME, which is exactly this rule, and `CoreTests/RepeatedNameConstraints.lean` evaluates the lifted elaborations (`Lifted(x) = [P(x, x)]:0`, a nested group, a collector) beside the callable aliases, the explicit calls and the Q-05 guards (bare forwarding's are in `CoreTests/AliasForwarding.lean`); the Lean programs of the `implicit-forwarding-is-by-binding-name` and `repeated-name-wrapper-keeps-independent-arguments` spec cases are derived from the C# elaboration. Pinned in C# by `ImplicitForwardingByBindingNameTests` — per generated shape: one caller binding per name, equivalence with the explicit same-binding call on satisfying, traced, failing and callable-only arguments, and rename-apart; every formula position (operators, comparisons, unary, lists, index target and selector, row spread, strict Math argument and dot-fallback receiver, deconstruction, blocks and nested properties that use the callee, a closed list and a branch pattern that bind the name, sibling formulas, a loop step, a callback) against the explicit call on six routes with host-call logs and seeded random draws; closed lists; module text; and an invariant over the whole executable specification that no inferred signature repeats a name (a callable alias has no signature of its own) — and by `RepeatedNameAdversarialReviewTests`.

## The unified formula-lifting law (September 30 2026)

THE LAW (decided September 30 2026; constitution Q-11, Q-12 and Q-13 collapse, FOR FORMULAS, into this one rule, while the lone-row alias and bare-forwarding rules stay FWD-02's, next sections): **a formula lifts a reference exactly when the reference's ROLE is a value use and the callable it RESOLVES to has a lifting signature that requires supplied arguments.** The two facts are independent — every observed lifting decision factors as role × signature (the re-investigation of September 30 measured 0 of 144 role/signature cells breaking the product) — and each has ONE implementation. No callable CATEGORY is an exception: once a callable has a lifting signature — a user algorithm, a builtin, a Math member, a host operation, an opened or dotted member, a nameable clause family alike — a formula lifts it by this one rule. Formula lifting is one of FOUR distinct mechanisms, and the other three are unchanged: the callable alias and bare forwarding (a body whose one row is the bare callee, FWD-02) and the explicit call (its written arguments, whatever the callee's names).

**The role is what the immediate consumer does with the slot** (C# `FormulaLiftingRoles`; Lean `LiftingRole`, `LiftingCalleeKind`, `liftingSlotRole`, `builtinLiftingSlotRole`). A VALUE role: an operand of a unary, binary, logical or comparison operator; an index target or index part; a spread operand; a list or capture element; an output row or a deconstruction's right-hand side; the receiver of an intrinsic `.string` (a structural miss — a `.string` edge that selects a declared member navigates its receiver, Q-17 S-C); and every argument slot whose callee demands its value — a builtin's collection, value and whole-number controls and surplus positions (static roles: at run time, under Model C, cardinality is checked before any slot is demanded, so a surplus slot is never demanded — formerly it was value-evaluated before the arity verdict, PV-05; `if` takes three values; a loop's count and initial state are values), a Math member's and a host operation's arguments, and a clause family's arguments (a static role retained by NEED-05; at run time a family demands only what its patterns inspect, PAT-07). A CALLABLE role: a call's callee; a builtin callback (`map`, `filter` and `reduce` steps) and a loop step; a whole argument of a user callable (its binder decides at run time, and a plain capture keeps both channels — call arguments stay neutral, sub-choice A1); an argument of a callee known only at run time (a parameter, an unresolved name, a computed value); and the receiver of a dot edge that NAVIGATES a structural member or whose dispatch only the runtime receiver decides. A dot edge whose lexical fallback is selected IS the call `F(receiver, args)`: its receiver is slot 0 and its written arguments slots 1.. of the fallback callee, so `R.F(args)` and `F(R, args)` infer alike. No role depends on how many arguments a call supplies. The role is RECURSIVE — a compound expression in any slot is examined and its own children take the roles of THEIR consumers (`Id(Inc)` keeps `Inc`, `Id(Inc + 0)` lifts it) — and BLIND TO LAZINESS: an `if` branch is a value position whether or not a run selects it, exactly as a free name written there becomes a parameter, and lifting never changes which branch a run evaluates. After a spread slot a builtin's positions are known only at run time, so a later position is a value only when every declared position of that builtin is one. The resolver's dependency collection and rewrite and the sibling-order channel (`PropertyDependencyGraphBuilder`) read the SAME classifier, so what a formula lifts, how it is rewritten, and which sibling must be processed first cannot drift.

**The signature is what the resolved callable contributes** (C# `ImplicitArgumentResolver.TryResolveLiftable`; Lean `Algorithm.liftingSignature?`, `builtinLiftingSignature`, `familyLiftingSignature?`) — ONE identity-keyed source, never the route that reached the callable. The reference is resolved in the language's own order — the owner walk over the document's properties, then the prelude (the builtins, the Math module and its aliases, the run's host operations; `load` is a front-end directive and has none), then the opens level by level (one public provider selects, two select nothing) — and a structural dot path `R.M` by its member. A user algorithm contributes its parameter patterns as processed; a callable alias contributes its NORMALIZED TARGET's signature (lifting looks through aliases, so an alias has no signature, kind or role of its own); a builtin its callable interface, `BuiltinDescriptor.ToolingPlainSignature` (the registry's parameter names, a loop's variadic initial state as `*init`); a Math member or host operation its declared parameters; an opened or dotted member its own signature, read from its processed provider. A CLAUSE FAMILY contributes one whole-value slot per top-level position (its common arity, PAT-03), each named by its clauses: a clause that binds a PLAIN parameter at a position votes that name — a literal, a structural pattern and a binderless group vote nothing, being dispatch detail rather than leaves of the signature — every vote for a position must agree, every position needs one, and the names of different positions must be distinct (by-name lifting would otherwise feed one binding to independent positions: `P(a, 0)` / `P(0, a)` is not `P(a, a)`). A family whose clauses fail any of these has NO lifting signature and no name is ever invented: it stays explicitly callable, and an INFERRING formula that would lift it is the front-end error `DiagnosticCode.UnliftableClauseFamily` at the reference, naming the position and why (`S(1) = 1` / `S(-1) = -1` / `G = S + 0`). A closed list or branch pattern forwards only same-named existing bindings (PAR-04) and such a family names nothing, so there the reference keeps its ordinary zero-argument demand and runtime check, like every blocked reference. Diagnostic reasons cached by callable identity contain no occurrence name: `UnliftableClauseFamily` names the current reference, including when several bindings share one family AST. Each unliftable-family reference reports once per rewrite region, using reference identity independently of rewrite sharing. A reference to nothing static — a parameter, an unresolved name, an ambiguous open, a runtime receiver's member — has no lifting signature.

**Everything else is unchanged, and composes with the law.** Q-03: a callable whose signature accepts zero supplied arguments is never lifted, whatever its category — it is read through the cache. Q-04: forwarding reuses existing parameter bindings by name; a property, an opened name or a builtin is never forwarded as a SOURCE (the law widens which CALLEES lift, never what supplies them). PAR-04: closed lists gain no forwarded name. Model-C Q-15 leaves every blocked reference as an ordinary runtime zero-argument demand, including Math; an unused argument or unselected branch never reaches it. Directly written undeclared names remain front-end errors. No strict-value diagnostic observation or lazy-depth replay remains. PAR-05: first-occurrence order, one parameter per binding name. X-02: the composed signature must be one a programmer could write (next section). FWD-02: a body whose ONE row is the bare callee is a callable alias or bare forwarding, never a formula — and since aliases became binding indirection (October 1 2026) its eligibility is identity-keyed like lifting: a builtin, a host operation, an opened or dotted member and a clause family are alias targets like every parameterized callable, so `C = count` is a callable alias of `count` while the formula `C = count + 0` is `C(collection)`. THE ROOT CLAUSE: a bare ROOT output row naming a callable that requires supplied arguments is never lifted into the never-called root, whatever the callable's category, so evaluation reports that callable's own zero-argument rejection at the reference (`abs`, `Math.Random`, `count`, `Lib.Inc` and a family alone at the root are their own arity or branch errors; formerly the two Math spellings lifted there and reported the root's `UnresolvedImplicitParams`), while a root FORMULA lifts like any other (`abs + 0` needs the root's `x`).

**Every read sees the signature its turn gives (processing order).** Lifting reads the PROCESSED signature of what a reference resolves to, so the resolver processes a level's properties in dependency order (`PropertyDependencyGraph`, `ImplicitArgumentResolver.PropertyLoop`). The reads the sibling-order channel classifies — with THE role classifier — are hard edges; the reads it can only anticipate (a nested body's `open` whose head is a sibling; a bare sibling argument of a callee the channel cannot classify, whose role only the rewrite knows) are SOFT preferences, honored among the properties the hard edges leave ready, so they never block the order. A read that nevertheless reaches a pending property processes it ON DEMAND (`PropertyLoop.EnsureOnDemand`) together with its pending hard-dependency closure, dependencies first — the order its turn would have had — and never ahead of a dependency still in progress. The members of a SIBLING CYCLE — closed by hard edges, soft preferences, or both (`PropertyDependencyGraph.CyclicIndices`) — and every property that hard-depends on one are never processed early: a cycle keeps its processing-order fallback, as every sibling cycle always has (a member processed first reads the others' unprocessed signatures). Two siblings that `open` each other therefore form a cycle, and a member read before its provider's turn does not yet carry the parameters its own lifting adds (its written and detected ones it always carries); outside cycles, declaration order is unobservable. A CYCLE IS ONE UNIT OF THE ORDER (X-04, October 1 2026): the order is Kahn's over the condensation of the hard edges (`PropertyDependencyGraph.TopologicalOrder`) — a cycle (a strongly connected component of more than one property) is ready once every sibling its members read outside it is processed, it is released only when no property outside a cycle is ready, its members are processed together in declaration order (the fallback), and soft preferences decide among ready cycles as among ready properties. Soft preferences can also close a cycle around hard units. The final order settles the combined hard/soft condensation before releasing consumers outside it (`SettleSoftCycleConsumers`), preserving the hard scheduler's internal order within each combined component. Thus a soft-blocked opened consumer cannot enter the cycle's fallback; no within-cycle call is recomputed (Q-76 stays open). The fallback is therefore confined to the cycle's members: a property that reads a cycle is not part of it, follows ALL of its members and reads their settled signatures. Formerly the order appended EVERY property still waiting at the first stall, cycle members and their acyclic dependents alike, in declaration order, so a consumer declared before the cycle read an intermediate signature: `C = B + z` / `A = { Helper = B + 0 ⏎ x + 1 }` / `B = y + A` / `C(1, 2, 3)` inferred `C(z, y)` and failed with an arity mismatch, while `C` declared last inferred `C(z, y, x)` and gave 7 — now every declaration order gives `C(z, y, x)` and 7. Only the members' relative order stays observable, and only through the members: with `A = { Helper = B + 0 ⏎ P + 1 }` (where `A`'s `p` comes from lifting `P = p * 10`), a `B` processed before `A` reads `A` without it — whatever the position of `B`'s consumers. Pinned by `SiblingDependencyCycleTests` (the order's laws against a brute-force component oracle and the former order on every level without a hard/soft cycle, retaining every combined component's former internal order; a declaration-order metamorphic matrix over source programs on six routes; the editor model). On-demand processing — the one place two rewrites stack — stays within the structural depth budget (`ImplicitArgumentResolver.DemandDepthBudget`: the live depth plus ten units per active demand must leave room for the demanded property's structural height under `EvaluationLimits.MaxSupportedAstDepth`; beyond it `DiagnosticCode.AstDepthLimitExceeded` at the demanded property, deterministic and never a host stack overflow). With the soft preferences no known program reaches on-demand processing at all — the whole test suite and the re-investigation corpus make none — so it is the safety net for a read no channel edge anticipates. Consequences, all pinned: `Total = count + 0` is `Total(collection) = count(collection) + 0`; `Next = Lib.Inc + 0` and `{ open Lib ⏎ Inc + 0 }` take `x`; `Fam = E + 1` with `E(0) = 100` / `E(n) = n` is `Fam(n) = E(n) + 1`; `G = if + 0` is `G(condition, whenTrue, whenFalse)`, `G = repeat + 0` is `G(step, count, *init)`, and a host `trace(x)` makes `G = trace + 0` take `x`; `[Inc, Inc * 2]`, `(Inc, 0)`, `Inc.string`, `Inc.count`, `take([1, 2, 3], Inc)`, `abs(Inc)` and `E(Inc)` lift, while `Apply(Inc)`, `map([1, 2], Inc)`, `repeat(Inc, 2, 0)` and `f(Inc)` keep `Inc`; `G = if(c, 1, Bad)` is `G(c, x)` and still evaluates `Bad` only when `c` is false; a formula's lifted calls evaluate, charge, draw random numbers and call host operations exactly as the explicit calls it abbreviates, and extracting a helper formula (`H = F + 1`, `G = H * 2`) agrees with inlining it (`G = (F + 1) * 2`). ## Inferred signatures are held to the rules of written ones (X-02, September 30 2026)

THE LAW (decided September 30 2026, X-02): **a signature the front end infers must be one a programmer could write.** Formula lifting composes an owner's signature from its callees' contracts; a composition no source may declare is the DEFINITION's front-end error, reported when the definition is elaborated — never a later call's failure and never a host exception. ONE validator decides validity everywhere (C# `ParameterPattern.FindSignatureViolation`, Lean `ParameterPattern.signatureViolation?`): the parser's rules for a written head, the resolver's check of an inferred one (composed from shared template facts, `ImplicitSignatureTemplate.TemplateFacts.SignatureViolation`, so FE-3 sharing stays linear), and — for the collector rule — the pre-evaluation validation of a host-built tree. Its rules, in the parser's order: no one-item sequence pattern (the singleton rule), at most ONE collecting parameter per pattern level (VAR-02), and no repeated name that includes a collector (a repeated fixed name stays a Q-05 constraint).

The witness: `C1(a, *p) = a` / `C2(b, *q) = b` / `K = C1 + C2` would infer `K(a, *p, b, *q)` — two distinct collectors at one level, which no parser accepts. Before the rule the front end inferred it silently: `K(1, 2)` threw the binding planner's `InvalidOperationException` out of `KatLangEngine.Run` on every route, a bare read misreported "expects 3 parameters", and the editor model threw while building the signature. Now it is `DiagnosticCode.InvalidCollectingBinding` at the second callee's reference, naming both collectors and the callees that need them ("Formula lifting cannot complete this definition's signature: it would need the collecting parameters '*p' (needed by 'C1') and '*q' (needed by 'C2') at the same pattern level … Call 'C2' with explicit arguments, or declare this definition's parameters explicitly."). A collecting NAME shared by two callees is ONE binding (`C(n, *xs)` twice is `K(n, *xs)`; `K = while + repeat` is `K(step, *init, count)`), collectors in their own groups are legal (`(a, *p)` beside `*q`), and a collector-only callee is never lifted at all (Q-03), so it never composes one. The same rule holds across every category the unified law lifts (`C1 + while` is rejected). Recovery is the parser's for a written head — the first collector of each level stays and a later one becomes fixed (`ParameterPattern.KeepFirstCollectingCapturePerLevel`) — so the recovered tree carries only valid signatures and the editor model builds. A host-built tree with two collecting captures at one level is `IllegalInEval` before evaluation in both engines (`PreEvaluationAstViolation.MultipleCollectingCaptures`, Lean `Algorithm.hasMultipleCollectingCaptures`): a deliberate host-AST compatibility change, since C# formerly threw the planner's exception for a top-level pair and both engines bound a nested second collector as a suffix pattern.

THE OUTPUT RULE IS HELD TO THE SAME STANDARD (X-07, October 1 2026): an algorithm that has parameters must define an output (Lean `validateExplicitParamOutputInvariant`, which `runResultM` runs before evaluation). The parser checks every WRITTEN parameter list on the raw syntax tree; an inferred list is final only after inference, so once implicit-argument resolution has completed every signature the front end re-checks the completed ones with the evaluator gate's own test — a stored parameter-pattern list that is not empty and no output row (`InferredParameterOutputValidator`; a written list is never reported twice) — and reports the same `DiagnosticCode.ExplicitParametersRequireOutput` before evaluation: at the first occurrence of the first parameter inferred from a name the definition uses (signature order, the written list's convention), else at the definition (a parameter forwarded to a callable it uses has no occurrence of its own; the program root, which no definition writes, at its first written row), else at the import site of the module content it lies in; worded for inferred parameters ("This algorithm takes the implicit parameter 'x' but does not define an output…", never "declares explicit parameters"). `F = { a, b = x, 1 }` / `trace(5)` was an UNPOSITIONED evaluation failure of the whole program; it is now the front-end error at `x`, and nothing runs. A deferred module region's provisional body is judged when it materializes, not by the evaluator gate at the start of the run (a name its module supplies reads as undeclared there — evaluator-and-hosting.md § Source loading and deferred modules). Pinned by `InferredParameterOutputValidationTests`.

Lean laws `x02_distinct_top_level_collectors_are_an_invalid_signature`, `shared_collecting_name_is_one_valid_binding`, `collectors_in_their_own_groups_are_valid`, `nested_level_with_two_collectors_is_invalid`, `repeated_name_with_a_collector_is_invalid_while_fixed_repeats_are_constraints` and `valid_signature_has_at_most_one_top_level_collector` (`KatLangArityLaws.lean`) and the guards of `CoreTests/StructuralPatterns.lean` § 10. Pinned in C# by `InferredSignatureValidityTests` (every lifting position, six routes and both engine entry points without a host exception, the recovered tree and the editor model, the validator against the parser for written heads, template-fact composition, and the host-built pre-evaluation rule), `UnifiedFormulaLiftingTests.DistinctCollectors_FromAnyCategory_AreTheDefinitionsFrontEndError`, and `PatternBindingErrorPrecedenceTests.SecondCollectingCapture_IsIllegalBeforeEvaluation`.

## Callable aliases and bare forwarding; forwarding preserves bindings and structural kind (FWD-02, September–October 2026)

THE RULES (decided September 29–30 2026; aliases as BINDING INDIRECTION decided October 1 2026, superseding the exact-alias wrapper; FWD-02 owns them). **A body whose ONE written row is a bare reference to a callable that declares parameterized callable structure is a CALLABLE ALIAS when its body is open, and BARE FORWARDING when its parameter list is written: an alias is a second name for the target's callable itself; bare forwarding reuses already-existing compatible bindings BY NAME — it never renames a binding, never adds one to the closed list, never matches by position, and never converts an incompatible top-level parameter pattern because nested leaf names coincide. An explicit call means exactly what is written. Formula lifting is a separate, by-name inference mechanism.** Six forms are distinguished by what is written, never by compiler internals:

| You write | Meaning |
|---|---|
| `A = F` | a CALLABLE ALIAS of `F`: `A`'s callable IS `F`'s; `A` keeps its own binding |
| `A(p) = F` | BARE FORWARDING: reuse `A`'s existing compatible binding named `p` for `F`'s parameter `p`; infer nothing, rename nothing |
| `A(p) = F(p)` | an EXPLICIT CALL: the written arguments; the caller's and the callee's parameter names need not match |
| `A = F(p)` | a FORMULA whose parameter `p` is the free name written in it |
| `A = F + 1` | FORMULA LIFTING: `F`'s required parameter names become `A`'s inferred parameters, by name |
| `A(p) = F + 1` | a formula under a CLOSED list: it may use existing bindings (its own `p`, Q-04's enclosing ones), never add one |

**Do not equate `A(p) = F` with `A(p) = F(p)`.** With `Sub(y, x) = y - x`, `G(x, y) = Sub` hands G's `y` to Sub's `y` and G's `x` to Sub's `x`, so `G(10, 3)` is -7, while `G(x, y) = Sub(x, y)` passes its arguments in the written order and gives 7. The two agree only when the names do.

* **Eligibility** (`ImplicitArgumentResolver.DeclaresParameterizedStructure`, Lean `Algorithm.declaresParameterizedStructure`). The row names the callable ITSELF, so the rule reads the DECLARED callable structure of the ONE identity name resolution selects — owner walk → prelude → opens → structural dot path, looking THROUGH aliases to the normalized target — never the lookup route and never zero-argument acceptance: every builtin (`if`, the callback builtins and the loops included), every clause family (nameable or not), a user algorithm with at least one completed parameter pattern (`Only(*xs)` included, although `Only()` is legal), a Math member (the alias, `Math.X` and the opened name alike) and a host operation, whether reached directly, opened, dotted, from a loaded module, inside a deferred region, or through another alias. A ZERO-PARAMETER target is NOT an alias: `Z = tick()` / `A = Z` stays an ordinary property whose body reads `Z`, cached as usual (`A, Z, A` evaluates `Z` once). Never an alias, because no ONE static identity exists: a callable parameter (known only at run time), an ambiguous open, an unresolved name (which stays the body's implicit parameter, as before), a member only a runtime receiver could provide. The ROOT's rows are never completed (the root is never called). A deconstruction declaration's right-hand side is a WRITTEN row of its body (`AstHelpers.WrittenRows`), so a body with a deconstruction beside the bare callee has two written rows and is a formula, while ordinary property declarations beside the row keep it an alias (`A = { k = 1 ⏎ F }`).
* **Callable alias.** An open body with no parameter of its own (`A = F`, `A = { local declarations ⏎ F }`, an inline block `{ F }`) becomes `Algorithm.Alias` (Lean `Algorithm.alias`): BINDING INDIRECTION, with two identities kept apart.
  * The BINDING is the alias's own: its declaration, span and exposure, its lexical binding and zero-argument cache key, its editor symbol, its written name in diagnostics, and the declarations its own body makes — never its target's members.
  * The CALLABLE is the target's: every callable operation through `A` uses the normalized target, resolved in the ALIAS's declaration scope (never re-resolved at a use site; a later nearer `F`, a parameter named `F`, another open cannot change it) — calls, the roles of their arguments (X-45: `A = abs` / `K = A(Inc)` lifts `Inc` exactly as `abs(Inc)` does), arity, clause dispatch (`F = Fact` / `F(1, 2)` is `Fact`'s own no-matching-branch failure), builtin adapters (`C = count`; `I = if` keeps `if`'s laziness; `M = map` never demands its callback for an empty collection; `R = repeat` keeps the loop's minimum arity), callbacks and loop steps, the callable channel of an argument, bare forwarding and formula lifting (the target's contract and lifting signature), and callable identity (`P(f, f) = f(7)` / `A = Only` / `P(A, Only)` binds ONE callable).
  * Nothing is synthesized: no wrapper algorithm, no inherited signature, no call. An alias is no invocation — it charges no evaluation step, no depth and no binding context, and a call through it reports its target's failures under ONE frame naming the written alias.
  * A bare read of an alias (`A` as a value) is its target's zero-supply demand stored under the ALIAS's OWN cache entry: `Only(*xs) = tick()` / `A = Only` / `A, Only, A` evaluates `Only`'s body twice — once per binding — and `A()` is a fresh call that populates nothing.
  * Written member access never follows an alias: `A.K` looks for `A`'s own member (the evaluator resolves a written receiver RAW, `ResolveReceiverHead`; Lean `resolveDotReceiver`) and otherwise falls back lexically; `open A` is refused for every alias (`RequiresArguments`; "is a callable alias, not a namespace"). A callable passed THROUGH the alias is the target, so `Navigate(f) = f.K` / `Navigate(A)` reads the target's member exactly as `Navigate(F)` would. Namespace aliasing is a different, future feature.
  * The evaluator normalizes at the binding chokepoints only — lexical lookup (`LookupLexical`, over `LookupLexicalRaw`), a navigated member, an inline block, the top-level property read — with safety nets at call, callback and demand dispatch for host-built trees: ONE iterative chase (`Evaluator.ResolveAliasTarget`, Lean `resolveAliasTarget`), memoized per alias binding and resolving scope (`AliasTargetKey`: the binding and the structural identity of its scope chain) on the declaring activation, or run-wide outside every activation, every link of a chain remembered at once; no host recursion proportional to a chain, no re-chase per call. A host-built alias whose target is no static path, or whose static chase cycles, is `IllegalInEval` before evaluation (`PreEvaluationAstViolation.AliasTargetNotStaticPath` / `AliasCycle`; Lean `validateAlgorithmTree`, `staticAliasCycle`), and the runtime chase rejects a cycle through an `open` the same way, never by a hop limit.
  * The editor shows the alias under its own name with its target's parameters (`C(collection)`) and names the target (`PropertyInfo.AliasTarget`: `count(collection)`; an unnameable family as `U (clause family without nameable positions)`); go-to-definition from the alias row reaches the target, and the alias symbol is its own declaration. One target surface is shared by every alias of it.
* **Bare forwarding.** A written parameter list (`G(params) = F`) or a clause branch (`G(head) = F`) keeps its own CLOSED signature, and each top-level parameter pattern of `F`'s FORWARDING CONTRACT — the lifting signature of the NORMALIZED target, through every alias, identity-keyed whatever route reached it — is supplied from an EXISTING binding (`BareForwardingArgument`; Lean `bareForwardingArgument` / `bareForwardingRow` / `bareForwardingRowOf`). A target with NO forwarding contract at all — an unnameable clause family, whose clauses name no position — is the front-end error `DiagnosticCode.UnforwardableCallable` (public `KatLangErrorCode.UnforwardableCallable`; narrowed Q-77, decided October 1 2026), positioned at the written callee and naming it, never a silent zero-argument demand (`S(1) = 1` / `S(-1) = -1` / `SA = S` / `W(x) = SA` is rejected; write `W(x) = SA(x)`):
  * a callee CAPTURE `n` is supplied by the body's own TOP-LEVEL capture `n`; when the body binds no `n` at all, by the enclosing parameter binding a written `n` would denote there (Q-04: an ancestor's parameter, a clause binder, the root's inferred names — never a property, an opened name or a builtin); a body that binds `n` only INSIDE one of its structural patterns holds an element, never a whole-value parameter, so that capture is unforwardable;
  * a callee STRUCTURAL parameter is supplied only by one of the body's own top-level patterns with the SAME contract — kind, shape, names and collectors (C# `ParameterPattern.ContractComparer` structural equality, Lean `ParameterPattern.sameContract`) — rebuilt as itself; enclosing bindings are plain named values and never supply one, and a structural pattern is never assembled from same-named leaves;
  * a collector that nothing of its name supplies receives no argument (a collector accepts none); any other parameter nothing supplies is UNFORWARDABLE: the front-end error `DiagnosticCode.UnforwardableParameter` (public `KatLangErrorCode.UnforwardableParameter`), reported once per callee parameter at the bare reference — at the import site inside module text, re-issued per family for a shared branch body — with the row left as written, never an evaluator arity message.

  So: `F(p) = p * 2` / `A(p) = F` is `F(p)` (10 for `A(5)`); `F(q) = q * 2` / `A(p) = F` is rejected — A's `p` is never renamed to `q`, whatever the arity; `F(p, q) = p + q` / `A(p) = F` is rejected — an explicit list is closed, so `q` is never inferred (write `A(p, q) = F` or `A(p) = F(p, 10)`); `F(p)` / `A(p, unused) = F` forwards `p` and leaves `unused` unused; `F = 10` / `A(p) = F` is 10 (a callee that declares nothing is not a target at all); `Single([x]) = x` / `G(x) = Single` is rejected — G's whole `x` never becomes Single's `[x]` because the leaf names coincide — while `G(x) = Single(x)` is the explicit call (`G([7])` is 7) and `G([x]) = Single` forwards the same pattern (`G([7])` is 7); `Add((x, y)) = x + y` / `G(x, y) = Add` is rejected — nothing manufactures the pair — while `G((x, y)) = Add` forwards it; `F([a, b])` / `A([x, y]) = F` is rejected — positions inside a pattern are never renamed either. Only the SOURCE binding's kind decides a re-spread: a collecting source into a collecting destination of the same name re-spreads exactly its items (`G(*xs) = F` with `F(*xs)` is `F(xs*)`, FWD-01's `spread (collect S) = S`), while a fixed source reaches a collector as ONE item (`G(xs) = F` with `F(*xs)`: `G((1, 2))` collects `[(1, 2)]`) and a collected list reaches a fixed parameter WHOLE (`G(*xs) = F` with `F(xs)`). Repeated callee names follow the same rule: `P(x, x) = x` / `Q(x) = P` hands Q's ONE binding `x` to both occurrences, `P(x, x)` — the call a formula builds too; the two slots are then ordinary arguments reading one binding, which Q-05 compares and never merges. A branch head offers its binders and its literal-free top-level items (`G(n) = F` with `F(n)` forwards the binder; `G(0) = F` with `F(v)` is rejected, since the pattern binds no `v`). When every callee parameter is an unsupplied collector, nothing is forwarded and the row stays the bare name — Q-03's cached read, never an invented call (`F(*xs) = xs` / `A(p) = F` reads F's own `[]`).
* **Explicit call.** `A(p) = F(p)` is an ordinary written call and never reaches the rule: its arguments are exactly the written expressions, whatever `F` calls its parameters. It is deliberately NOT the same thing as the bare row.
* **Written-call formula.** `G = F(exprs)` is an ordinary formula: its parameters are the free names WRITTEN in `exprs`, in first-appearance order with the ordinary Grace arithmetic, so `G = Add((x, y))` is exactly `G(x, y) = Add((x, y))` whatever `Add` calls its binders, and `G = Single([x])` takes one parameter `x`.
* **Formulas keep formula lifting.** A body that USES a callee inside an expression is formula lifting, by binding name (§ Formula lifting is by binding name), with Q-04's reuse of enclosing parameter bindings. An OPEN formula infers what bare forwarding refuses to add (`F(q) = q * 2` / `A = F + 1` is `A(q)`); a CLOSED formula adds nothing either: `F(q) = q * 2` / `A(p) = F + 1` keeps `F` the zero-argument demand — accepted by the front end in this non-strict position and the runtime arity error `F` expects 1 (a Math position follows the same runtime zero-argument demand, per Model-C Q-15) — never a renamed `p`, while `F(p) = p * 2` / `A(p) = F + 1` reuses `p` (`A(5)` is 11). By-shape forwarding (`H((*xs))` fed from a caller's single top-level stream) belongs to formulas only; a lone row never forwards by shape. Formula lifting is the one place a callee's binder names reach a caller's SIGNATURE (`H = [F]:0` infers F's `x`; renaming it renames H's parameter). That is the deliberate distinction of this section: formula lifting infers dependencies by name, bare forwarding reuses existing bindings by name, an explicit call maps written arguments.

**Renaming the callee's parameters** affects each form as its mechanism says, and the tests pin all four: an ALIAS takes the new names with it (it IS the callee's callable); BARE FORWARDING may become unforwardable (intended — `A(x) = F` depends on `F`'s name `x`); an EXPLICIT CALL is unaffected (`A(p) = F(p)`, `G = Add((x, y))`); FORMULA LIFTING lifts the new name.

**Every synthesized call forwards existing bindings unchanged and rebuilds each structural pattern as its own kind** (FWD-02 with the structural-pattern model):

* **An existing binding is forwarded unchanged.** A fixed binding is supplied as its whole value — never opened, never wrapped — and a collecting binding that is re-spread supplies exactly its collected items: in bare forwarding and a formula when BOTH the destination capture and the SOURCE binding collect (FWD-02's source-kind rule). (A callable alias synthesizes nothing: it IS its target's callable.) This holds whatever route supplies the binding: the owner's own parameter, a closed list's own binding, a reused enclosing binding (Q-04), and a name an earlier capture already bound (by binding name).
* **A rebuilt structural pattern keeps its kind.** A SEQUENCE group is rebuilt as a sequence — the written capture `(a, b)`, `()` for the empty group, or the one lone non-spread item itself where the group reduces to it (the written `C((xs))` IS `C(xs)`, so the invalid singleton is never manufactured) — and a LIST group as a list literal `[a, b]`, `[]`, `[x]`, `[items*]` (`ImplicitArgumentResolver.BuildPatternArgument` / `BuildSequenceArgument`, Lean `ParameterPattern.sourceArguments` / `sequenceArgument`). Nesting keeps every level's kind.

Consequently every synthesized call is exactly the call a programmer would write. In a formula, a caller's collecting stream is re-spread into the group it came from, by name or by shape (`Use(*items) = [LC]:0` with `LC([*xs]) = xs` calls `LC([items*])`), and a group that holds no new binder contributes nothing to the lifted signature while the call rebuilds it as the empty structure of its own kind (`L = [E]` with `E((), []) = 1` takes no parameter and holds `[E((), [])]`, while the alias `A = E` IS `E`, whose two groups are its parameters). There is no kind conversion anywhere.

## Grace (F10, Q-16 G-O)

Grace `~` is a front-end parameter-order annotation on exactly one bare name occurrence (`~x` / `x~`), written DIRECTLY attached to that name (marker attachment law: `~ x` and `x ~` are `InvalidGraceMarker` attachment errors that recover to the plain name with no weight; `~~x` and `~x~` are attached runs); it is not a general expression operator, the markers on that occurrence — and on repeated occurrences of one name in one owner — add up as ordinary weights, and elaboration strips it before evaluation.

GRACE IS OWNER-LOCAL AND REQUIRES AN OWN INFERRED PARAMETER (Q-16 G-O, decided 2026-10-07; F10). Grace belongs to its OWNER: the innermost algorithm-level scope — the root, a property body, a brace block in any expression position, a clause-branch body — whose written rows (`AstHelpers.WrittenRows`: output rows and hoisted deconstruction right-hand sides, through every transparent construct) contain the marked occurrence. A nested brace block or property is an owner of its own whatever encloses it, and deconstruction hoisting never moves an occurrence to another owner. A marker is valid exactly when its occurrence becomes one of the owner's OWN inferred parameters — the one place its weight is consumed (`CollectFreeParams`, then `GraceMovement` over the owner's own list; forwarded names are appended afterwards, PAR-05) — and the weight is applied as far as the ordering allows. SATURATION IS NEVER AN ERROR (Q-16(1) E: eligibility, not movement): a single own inferred parameter (`F = ~x + 1`), a name already at the boundary it points to, excess weight, a neighbour moving the same way with at least as much remaining weight, a cancelled weight (`~x~`; `~x` with `x~`) and the own/lifted boundary (`A = p - q` / `F = A - z~` infers `F(z, p, q)`) are valid, and a cancelled marker is still validated for its binding. Every other occurrence has no inferred parameter for the weight to attach to and is the front-end error `DiagnosticCode.InvalidGraceMarker` ("Grace cannot reorder 'x' because …"): an occurrence whose binding is already fixed — an explicit parameter or clause binder, a captured parameter of an enclosing algorithm (written there, or inferred there because that owner's own rows use the name, PAR-03: `F = x * 100 + Apply({ y - ~x })` is `InvalidGraceMarker`, while in `F = Apply({ y - ~x })` the `x` is the block's own), a visible property, a builtin, an opened name, a dot member that always resolves structurally (or any `.string` edge, which selects a declared member or the intrinsic and never a lexical callable, Q-17 S-C) — and ANY occurrence on a CLOSED level: under an explicit parameter list, and on a clause branch's OWN level, whose head is its complete input specification (PAT-04) — its output rows and its deconstruction right-hand sides alike (constitution PV-49: `F(n) = { a, b = (~n, 1)  a + b }` in a family once ran silently; `ConditionalBranchDeconstructionGraceTests`).

A clause branch is closed at its own level ONLY (Q-16(2) O). An algorithm nested in the branch — an inline block, a grouped block, a trailing-brace callback, a dot receiver or argument, a callback, an `if` slot, a deconstruction slot, a block inside a block, a property, a property returning a block, a nested family's nested owners, at any depth — is an ordinary owner that infers its own signature and owns its Grace in every spelling: `Apply(f) = f(1, 10)` / `F(0) = Apply({ y - ~x })` / `F(0)` is `9`, exactly like the named `F(0) = { B = y - ~x ⏎ Apply(B) }`. Its inferred parameters are supplied by its caller and never added to the branch, and a branch binder seen from it is an enclosing parameter (`F(n) = Apply({ x - ~n })` is `InvalidGraceMarker`, reported once). A definition body written as ONE brace block (`G(k) = { y - ~x }`, or `({ y - ~x })`) IS the branch body, so its rows are the branch's own; only a block written inside the body is a nested owner. Adding a sibling clause (turning a single clause into a family) never changes a nested owner's verdict.

The ONE authority is the parameter detector's per-owner rewrite pass: `ParameterDetector.ReportIneffectiveGrace` under the region's eligibility policy (`ImplicitSignature`, `ClosedExplicitList`, `ClosedBranch`), once per occurrence per region through a diagnostic visit set, with a reason from the same owner walk the editor resolves with (never naming the family, so a branch body shared by several families reports one accurate diagnostic). The parser keeps only Grace SYNTAX — attachment, one bare name, compound-operand rejection, the clause-head pattern grammar, graced open targets; its former lexical branch-body scan (`Parser.ScanPendingForGraceSpan`, which also descended into nested blocks — a side effect of the pre-#143 shared `Expr.Block`, X-08 — and duplicated the detector's reports) is deleted. Consequently, in a LOAD-BEARING branch (one deferred compilation unit, MOD-10 / Q-61) a branch-own-level marker is reported when the unit is selected, like that unit's other elaboration errors, and an unselected unit is never materialized to report it; every eagerly elaborated branch is still validated before evaluation, selected or not. Grace never changes resolution, selection, values, callability or evaluation. The ORDER is the movement law below. Pinned by `GraceOwnershipSemanticsTests`, `GraceEffectivenessTests`, `ConditionalBranchDeconstructionGraceTests`, `GraceMovementLawTests` and the `grace-on-bound-name-rejected`, `grace-under-explicit-list-rejected`, `grace-in-branch-deconstruction-rejected`, `grace-saturation-is-valid`, `grace-in-branch-nested-block-belongs-to-the-block` and `grace-on-branch-binder-in-nested-block-rejected` `LanguageSpecCorpus` cases. A graced name inside REDUNDANT PARENTHESES is the graced name (PARENTHESES GROUP SYNTAX, September 2026): `(~a).V` is `~a.V` — the ordinary structural-first dot edge on `a` with `a` moved earlier, so a bound algorithm's own `V` is read and a number falls back to the lexical `V` exactly as `a.V` and `(a).V` do — and `(~a)(b)` is the call `~a(b)`; the parser's `IsRedundantGrouping` never looks at the inner kind, so the group is erased whatever the marker's weight and Grace can never change selection (`OutputBundleSplitTests`, the `grace-in-redundant-group-is-grace-on-the-name` spec case).

GRACE MOVEMENT (X-49, decided 2026-10-08; `GraceMovement`, applied by the detector once per inferring owner). The owner's OWN inferred names start in first semantic occurrence (PAR-05), each with its exact summed weight as its REMAINING weight: prefix −1 and postfix +1 per marker, summed over every eligible occurrence, opposite markers cancelling before anything moves, as unbounded integers (`System.Numerics.BigInteger` — never an int saturation, wrap or clamp; the detector's shared-node memo re-applies one exact per-visit delta per reach, so a shared subtree weighs what its duplicated tree weighs). Movement runs in exactly two passes, with the schedule fixed by the first-occurrence identities and their INITIAL weights — never by current positions, spellings or dictionary order: (1) every name with a POSITIVE weight takes one turn, from the LAST-occurring to the first-occurring; (2) then every name with a NEGATIVE weight, from the FIRST-occurring to the last-occurring; a zero-weight name takes no turn. In its turn a name requests one adjacent exchange per unit — with the next name for a positive weight, the previous for a negative one — and each exchange moves its remaining weight one unit toward zero. A step is impossible, and the turn ends, at the end of the own list or when the neighbour moves the same way with at least as much REMAINING weight — rightward `remaining(q) >= remaining(p)`, leftward `remaining(q) <= remaining(p)` — compared on CURRENT remaining weights before the step (the patent's strict comparison); an unmarked neighbour or one moving the other way never blocks. A passed name keeps its remaining weight. Weight a name cannot use — at an end or against such a neighbour — STAYS with it and keeps blocking later movers that push the same way no harder: `F = ~a * 100 + b * 10 + ~~c` is `F(a, c, b)` (a keeps −1 at the front; c passes b and then cannot pass a, whose remaining weight equals its own), and `SumOfParams = a~~ + b~` is `SumOfParams(b, a)`. The forwarded tail is appended afterwards (PAR-05, PAR-07), so no name crosses the own/lifted boundary. Each turn makes at most n − 1 exchanges, so at most n(n − 1) in all whatever the weights. Why this order: running rightward movers first and from the end, then leftward movers from the front, means the mover nearer its destination moves first, so no movement is lost because a same-direction blocker had not moved yet; a rightward and a leftward mover can only meet when the rightward one is written first, so the passes resolve every meeting in source order. An equivalent reading, used only to explain and to cross-check (equal on the investigation's 208,196 states, not proved): turns in first-occurrence order, where a mover blocked by a same-direction neighbour that has not moved yet lets it move first. Examples: `K = s * 100 + ~x * 10 + ~y` is `K(x, y, s)`; `Z = s~ * 100 + x~ * 10 + y` is `Z(y, s, x)`; `K = a * 100 + b~ * 10 + ~~c` is `K(c, a, b)`, as without `b~` (before X-49 a position cursor skipped the displaced `c` and gave `K(a, c, b)`); `K = a~ * 100 + b * 10 + ~c` is `K(b, c, a)` (prefix-first movement would give `(c, a, b)`); `K = ~a * 100 + ~b * 10 + c` is `K(a, b, c)`; `K = a~ * 1000 + b~ * 100 + c~ * 10 + d` is `K(d, a, b, c)`; `K = a * 1000 + ~b * 100 + ~c * 10 + ~d` is `K(b, c, d, a)`; `K = a + b~ + c~ + d~ + ~e` is `K(e, a, b, c, d)`. GUARANTEED: first-occurrence order without effective markers; a lone marked name moves exactly its weight, stopping at the end; own-direction monotonicity (one more postfix marker never moves a name earlier, one more prefix marker never later, and the name never overtakes in the wrong direction a name it was behind); equal accumulated weights keep their first-occurrence relative order; every marked name takes its turn, and every leftover is held by an end or a same-direction neighbour with at least as much remaining weight; a contiguous equal-weight run moves as a unit in either direction when every parameter outside that run has zero weight; prefix-only markings (one per earlier-written name that must end up after it) and postfix-only markings (one per later-written name that must end up before it) give exactly the intended order; saturation is never an error; the order depends only on own first-occurrence positions and total weights, in every owner and spelling. NOT guaranteed: contiguity of an equal-weight run when other parameters also move (`K = a~ * 1000 + b~ * 100 + ~c * 10 + ~d` takes `(c, a, d, b)` and `K(1, 2, 3, 4)` is `2413`; both `(a, b)` and `(c, d)` are split); mirror symmetry (`a + b~ + ~c` is `(c, a, b)`, `c~ + ~b + a` is `(b, c, a)`); independence (a marker on one name may change how two others end up); displacement bounded by a name's own markers (others may carry it, as `e` above); a move never undone (a strictly stronger same-direction mover may pass it back: `a + ~b + ~~c` is `(c, b, a)`); "desired position minus written position" as a recipe. Equal accumulated weights preserve their original relative order. A contiguous equal-weight run moves as a unit when every parameter outside that run has zero weight. Other moving parameters can split the run while preserving its relative order. `GraceMovementLawTests` (the canonical examples on six routes, the patent's FIG. 6, 7, 9–12 and 14, every state of 1–5 names with weights −3…3 against an independent oracle, monotonicity, equal weights, final-state blocking, groups, recipes, residual weights, aggregation, exact large weights and shared DAGs, owners, lifted tails, renaming, explicit-list twins), `lean/CoreTests/GraceMovement.lean` (a standalone model whose `#guard` table the C# suite also checks), the `grace-front-first-movement` spec case.

## Parameter channels and shadowing

A bound name has one shared NeedCell carrying independent VALUE completion and optional CALLABLE identity. Every explicit call, callback, branch activation and loop step shadows that name on all inherited channels, and retained owner activations preserve captured parameter cells. A value read forces that cell; a call-position lookup projects its callable identity without VALUE evaluation. Transport preserves the exact address, original provenance and caller environment. Invoking the callable is fresh; it does not replace a completed VALUE success or failure. The older value/counted/algorithm environments remain only for already-produced data and supported host/optimizer contexts; new argument acquisition uses NeedEnv. See `call-by-need.md` NEED-06 and NEED-10.
