# Ownership, lookup, and binding rules

The full statement of the rules that AGENTS.md carries in compact form — consequences, examples, the implementation map, and the pinning tests — moved here verbatim from AGENTS.md in September 2026. These rules are as binding as AGENTS.md; the compact bullet there points at the section here. Keep both in step: a rule change edits the compact bullet and the section together.

## Ownership-first lookup

Ownership-first lookup is fundamental. Keep lookup behavior aligned across evaluator, parser/front-end elaboration, parameter detection, and semantic tooling. The evaluator's two lookup spellings — `LookupLexical` (reached by a bare name in VALUE position, `X`; returns owner+binding for the zero-arg property cache) and `LookupLexicalResolvedAlgorithm` (reached from ALGORITHM position: a callee `X()` or a dot-call target `X.m`) — are ONE implementation since M8+M9: the algorithm spelling is the projection of the binding-carrying chain (mirroring Lean, where `lookupLexical` projects `lookupLexicalProperty`), so ownership-first, open dedup, ambiguity, scope-level precedence, and prelude fallback exist once per engine; `LookupTwinEquivalenceTests` keeps both spellings observable so an independent fast path cannot silently regrow. Beyond that there are TWO C# lookup implementations — the evaluator's chain and `ElaboratedScopeLookup` (shared by `ParameterDetector` and `Semantics/`) — and they must select the SAME declaration, not merely both resolve: the detector's verdict rewrites the program (an unresolvable name becomes an implicit parameter), so a front-end disagreement changes what the evaluator runs. `LookupCoherenceTests` pins that relation with unique per-declaration sentinels; the `open`/visibility family in `SemanticExplorerCases.lean` pins the Lean/C# side. Named `open` targets deduplicate first-occurrence-wins by `Evaluator.OpenExprName` (inline blocks get positional keys and never dedup), so `open A, A` is ONE provider, not an ambiguity — that rule lives in Lean `resolveAllOpens` and must be mirrored by BOTH C# implementations.

## The owner walk

The OWNER WALK is the front-end half of ownership-first, and `ElaboratedScopeLookup.SelectOwnedDeclaration` is its ONE implementation (Lean: `selectOwnedDeclaration` / `elaboratesToParameter`, stated beside `shouldTreatAsImplicitParam` because `ScopeCtx` carries properties but no parameters): search outward by owning scope over the two kinds of OWNED declaration — the parameter bindings a scope binds (written, inferred, or a branch body's pattern binders) and the properties it declares — and the first owner that declares the name decides, a parameter beating a property of the SAME owner in an invalid recovery tree. Properties matching parameters of the same or any enclosing lexical algorithm are declaration errors, checked by `ParameterPropertyCollisionValidator` after signature completion (Lean: `conflictingOwnedNames` / `validOwnedDeclarations`) — with ONE root exemption: the root program is never called, so its completed signature (names it could not resolve, or names forwarding lifted into it) is checked against the root's OWN declarations only and never blamed on a property nested in a deeper owner; such a name surfaces as the root's `UnresolvedImplicitParams` evaluation error, positioned at the first output row of the root by the ordinary missing-arguments span rule — or at the member token when that ONE name came from a missing member on a statically known receiver (diagnostics-only; see the dot-call bullet) — (`Lib = { public Q = 1 }` beside the root row `Q + 1` is a missing `open Lib`/`Lib.Q`, not a conflict in `Lib`; pinned by `ParameterPropertyCollisionTests.RootPhantomParameter_*`). Consequences that must hold together: a captured ancestor parameter beats a property of any FARTHER owner (the root's and the prelude's alike, so `F(pi) = { pi + 1 }` binds the parameter), a nearer property beats an outer parameter only in invalid recovery source, the nearest of several enclosing parameters wins, and a direct reference and one from a nested body always agree. `open` and the prelude keep their SEPARATE later policy: opens are consulted only after the whole owner walk (`LookupLexicalPropertyMatches`), so an owned parameter beats an inner `open` exactly as an ancestor-owned property does, and the prelude participates only as the outermost property level. Ownership is NOT the promotion question — `IsBoundName` still stops promotion at any visible property or opened name, unchanged. The owner map is `ParameterOwnership` (name → owning level, nearest wins by construction; never a counted depth), threaded through detection beside the scope chain; the detector's parameter classification (`ShouldRewriteAsParam`) and receiver classification (`ResolveReceiverNameProvider`) must both go through the shared walk, and the editor's `ComputeVisibleSymbols` is its enumeration form. Pinned by `ParameterOwnershipTests`, `LookupCoherenceTests` (the `ownership.*` cases), and the `ownership-*` `LanguageSpecCorpus` cases.

## Open, exposure, and accessibility (K1-08)

`open Name` may target a lexically visible private head, but open-provided names and dotted open steps select PUBLIC members (a private step reports `NotPublicProperty` before any capture check); structural dot access selects DECLARED members including private ones. SELECTION NEVER DEPENDS ON EXPOSURE (K1-08): a public captured member participates in precedence and ambiguity, and the unique selected member is checked afterwards by `Evaluator.IsAccessibleFrom` / Lean `memberAccessible?`. Capture requirements retain the exact semantic owner, including transitive requirements across shadowing: `Property.RequiredAncestorParameters` / `.localCapturedAncestorParams names` supply diagnostic names, while internal `CaptureRequirements` / Lean `PropDef.requiredOwnerDepths` retain owner positions relative to the declaring scope. Host-built trees without owner metadata use the nearest binder of each supplied name. Accessibility requires the matching declaration AND activation in the site's lexical chain, including already captured ancestor activations of a static nested provider. Runtime declaration tokens distinguish clause families and distinct algorithms even when they share names, properties, opens, or output nodes; activation tokens distinguish successive calls. Both are FIELDS of the runtime model, never a side table (Lean: `Algorithm.declarationId`, `ScopeCtx.declarationId`/`activation`, `EvalCtx.headScope`): `Algorithm.Declaration` is minted once per constructed `User`/`Conditional` and carried by every record copy — a `with` copy is a view of the same written declaration, whether the evaluator, the front end, or a host made it — while a `ParameterActivation` is minted per parameterized body entry or clause match, compared by reference, and carried by the activated `ScopeCtx` (`ScopeCtx.Owner`/`Activation`; the entered body's is `EvalCtx.HeadScope`, cleared by every push). A host-constructed scope has no owner, so it establishes identity only by being the same object. A conditional publishes its matched binders on its family scope. Parameter reads use the owning activation's value, algorithm, and counted channels, never a shadowing caller's binding. Compile-time branch analysis may share equivalent relative binder/open contexts without merging runtime families. Structural paths and open-provided names carry transitive capture requirements through `PendingReference`, preserving per-activation caching — a BARE opened name read by a sibling property is settled by the same one settlement (`PendingResolution.ResolveVisibleName`: the declaring chain's own properties first, then the declaring level's and its ancestors' opens), so `Y = X` beside `open Lib` with a capturing `Lib.X` is local-only exactly like `Y = Lib.X` and `Y = { open Lib  X }` (final audit, September 2026: it was classified Exported and the run cache leaked the first activation's value). An escaping reference carries an UNRESOLVED open candidate (the opener's target head was not the opener's own property) outward level by level, and the level that DECLARES the head settles it there — `PropertyDependencyGraphBuilder.AddEscaping` through the ONE local-head settlement `TryResolveLocalHeadCandidate`, the same one `MakeOpenCandidates` applies when the opener declares the head — because the evaluator resolves the target from the opener's direct chain outward and the nearest declaration wins; a head declared BETWEEN the opener and the settling level used to be carried past its declaration, so `Outer(p) = { Mid = { Lib = { public X = p }  Inner = { open Lib  X }  Inner }  Mid }` classified `Mid` exported and `Outer(1), Outer(2)` displayed `1 1` from the run cache (final hostile pass; `LocalMemberAccessTests.OpenTargetHeadDeclaredBetweenTheOpenerAndTheSettlingLevel_*`, spec case `ownership-open-head-between-opener-and-settling-level-charges-the-capture`). An OPEN PROVIDER must have zero effective call parameters, cannot be a clause family, and cannot be a prelude builtin — bare or as the HEAD of a dotted target (`open count.X` is refused like `open count`, never left to promote the opener's names to implicit parameters): `OpenProviderValidator` runs after signature completion and both evaluators reject the final provider with `IllegalInOpen` — the validator refuses a builtin head (`open count`) eagerly, in the same rule as a parameterized provider, matching the evaluator's and Lean's refusal by kind. Exported-property cache identity remains separate from runtime accessibility identity. Intermediate owners in `Lib.Sub` are static navigation, so parameterized or inferred-parameter intermediates are allowed if every selected edge is accessible and the final provider needs no call. A family exposes no branch members structurally (`LocalOnlyConditionalAlgorithm`), while a self-contained branch-local provider works inside the branch and nested bodies. Classification cannot invalidate selection, so no outer re-elaboration/recheck exists; the local dependency-summary fixed point remains. Pinned by `LocalMemberAccessTests`, `ZeroArgPropertyCacheScopeTests`, `FrontEndDagComplexityTests`, the exposure lookup cases, and independent `CoreTests/NameOwnership.lean` guards.

## Static-open ownership (SYN-03 / F2)

STATIC-OPEN OWNERSHIP (SYN-03 / F2): `open` is resolved statically — it never opens a runtime value, and there is no dynamic `open` — but lexical ownership still applies to the target's HEAD name (`Lib` in `open Lib` / `open Lib.Sub`), which parameter detection classifies through the ONE owner walk (`ElaboratedScopeLookup.SelectOwnedDeclaration`, called from `ParameterDetector.ClassifyOpenTargetHeads`) exactly like every other bare-name occurrence. If the nearest binding is a parameter — explicit, inferred, lifted, collecting, grouped, a branch binder, or any of these captured from an enclosing owner — that parameter owns the name; a parameter cannot be opened, so the head elaborates to `Expr.Param` (not an open form in either engine: `IsCoreOpenForm` / Lean `Expr.openForm?`, so evaluating any such tree yields `BadOpenForm`) and the front end reports `DiagnosticCode.OpenTargetIsParameter` at the head's span. It NEVER searches farther outward: adding or removing a farther same-named declaration (a root property, an enclosing property, an opened or module-provided member) changes neither the verdict nor the report, so `F(Lib) = { open Lib … }` is rejected with or without a root `Lib`. The rejected target provides no names (the same recovery rule as a rejected capture target), so the closed-list check and inference see nothing through it, and the editor classifies the head as the parameter reference it is (`OccurrenceKind.OpenTargetReference` with the parameter's declaration — never a farther property's). The never-called program root's phantom signature is NOT a callable binding for this decision (`ParameterOwnership.CallableBindings`, the F1 exemption): a nested `open Q` beside an unresolved root row `Q.X` stays a static lookup and evaluation reports the unresolved root input. Lean states the rule as `elaborateOpenHead` beside `elaboratesToParameter`; pinned by `StaticOpenOwnershipTests`, the `ownership-open-*` `LanguageSpecCorpus` cases, `LookupCoherenceTests.ownership.parameterOwnedOpenHeadResolvesToTheParameter`, and the F2 guards in `CoreTests/NameOwnership.lean`.

## Dot-call resolution and missing members (G-24)

Dot-call uses structural lookup first and lexical fallback second, at EVERY level of a chain: a receiver that is itself an argumentless, non-`string` dot edge is NAVIGATED through its exported structural members before either channel of the outer edge is consulted (`resolveDotReceiver` / `ResolveDotReceiver`, the ONE receiver-position resolution shared by the sync evaluator, the async twin, and the sequence optimizer's shadow check), so `Lib.Sub.Q` reads `Sub`'s own `Q` before any lexical `Q(x)` and `A.B.C.D` traverses every level; a declared local-only or conditional-branch intermediate member is that edge's `LocalOnlyProperty` error, never a fallback (the established one-level accessibility rule; private members stay reachable); a receiver without the member, an argument-bearing edge (`Lib.Sub().Q`), and the `.string` intrinsic are values, so the chain continues by extension fallback (`3.A.B` is `B(A(3))`; dot-call passes the receiver as the ordinary leading argument of that call — `sequences-lists-and-calls.md` § The dot-call receiver). Navigation is identity-only (no intermediate edge is evaluated) and the higher-order channel is untouched: `resolveAlg`/`ResolveAlg` still lifts every general argumentless dot expression to its zero-parameter wrapper identity. The front end mirrors the same rule through the ONE compositional static classification `AstHelpers.ResolveStaticStructuralMemberProvider` (detector receiver classification, editor dot-member resolution, and the scope-free dependency view; `StaticStructuralMemberProviderKind.KnownFailure` marks a statically failing intermediate edge, selection `Never`). Structural lookup, receiver injection, fallback order, and diagnostics must stay consistent across Lean and C#; pinned by `ChainedDotStructuralPrecedenceTests`, CoreTests `chained*`, and the `dot-chain-*` `LanguageSpecCorpus` cases. A MISSING MEMBER ON A STATICALLY KNOWN RECEIVER (G-24) is never a resolution or validity question: a known receiver (`Math`, a block, a module) that lacks the member falls back lexically exactly like any receiver, an unresolved fallback name is inferred as an implicit parameter exactly like a bare name, and a visible lexical callable of that name is a VALID fallback (`Ceiling(a, b) = b * 2` makes `Math.Ceiling(2.1)` the call `Ceiling(Math, 2.1)`, i.e. `4.2`). Static receiver knowledge is used ONLY for diagnostics: the detector's occurrence recorder stamps `ImplicitParameterProvenance.DotMemberOrigin` at promotion and a diagnostic-only walk after exposure completion discards receiver claims/hints invalidated by ownership or provider changes (the receiver described exactly as the evaluator's dot-call context describes it), the report leads with the shared `Property 'X' was not found on `R`` clause plus the fallback explanation, a member-bearing receiver's suggestion comes from its OWN exported member surface only (`NameSuggestions` member-typo policy: wider length-scaled threshold, initial-letter safeguard (a unique one-edit correction may change the initial on names of at least five characters), no lexical name offered in its place — `Math.Min` never suggests `min`; a memberless receiver keeps the ordinary lexical policy), and a single such unresolved parameter is positioned at the member token when it belongs to the current source (an imported module keeps the local demand span). No layer may branch on the receiver's spelling (SYN-05). Pinned by `ReceiverAwareMissingMemberDiagnosticsTests` and the `dot-fallback-on-known-receiver-stays-valid` `LanguageSpecCorpus` case. ATTACHMENT (invalid-state §3.4): a provenance note is ONE object per promotion — the moment one detection run over one body, in one front-end context, first promotes the name — and every record that stands for that promotion references the same object: the inferred capture (`CaptureParameterPattern.InferredProvenance`, the first carrier), the declarations flattened from it, every caller signature implicit argument resolution lifts that capture INSTANCE into, the dot edge whose fallback occurrence caused the promotion (`Expr.DotCall.InferredFallbackProvenance`, stamped by the detector's `RewriteDotCall`), and the note lists the evaluator snapshots onto `ArityMismatch`/`UnresolvedImplicitParams`. Each carrier holds the reference in a private equality-transparent `RuntimeStateSlot<T>` field behind an internal init-only property, so the SYNTHESIZED copy constructor propagates it through every `with` (the resolver's, completion's, and exposure's edge rewrites, the evaluator's span-attaching error copies) with no registration step and no hand-written copy constructor, while record equality, hashing, and printing never see it. The finalizer mutates the note in place BECAUSE it is shared — its verdict (forget the receiver claim, restrict the suggestion, forget the origin position inside a module) must reach every lifted caller without rewriting an executable node — and it is the only mutator, running before its tree is published (inside the synchronous pipeline, or inside a deferred region's gated materialization over notes that materialization minted), so evaluation only reads. Nothing forks a note: a body elaborated again in another context (a module spliced under a second owner, a shared host subtree under two owners, a materialized branch, a re-detected tree) is a new promotion with a new note, which is why independent contexts reach independent verdicts, while two references under ONE owner share one elaboration and one note. Pinned by `ImplicitParameterProvenanceAttachmentTests`.

## Builtin identity and the zero-argument value demand (SYN-05)

BUILTIN CALLABLES ARE ORDINARY PRELUDE BINDINGS, and IDENTITY — never spelling, never arity — decides semantics (SYN-05). Lexical resolution selects exactly one callable without considering the argument count; the resolved callable then determines its signature and behavior: `resolve name -> select ONE identity -> assemble the ordinary argument supply -> bind against THAT signature -> invoke`. KatLang has no overloading by arity, so a nearer property or parameter named `if`, `count`, or `sum` shadows the prelude binding COMPLETELY — `if(x) = x + 1` makes `if(1, 2, 3)` an arity error against `if(x)`, never a fallback to builtin `if/3` — and a bound parameter may carry any callable under a builtin's name (`Apply(if, x) = if(x)`). There is NO reserved-name mechanism, in either engine: do not add `ReservedNameValidator`, a `BuiltinDescriptor.IsReservedName` flag, reserved-name tables, `ReservedName` diagnostics, or grammar productions excluding builtin names from binding identifiers. (`BuiltinRegistry`'s reserved-name check and `HostOperations.ReservedPreludeNames` are unrelated: they govern who may BUILD the prelude — a Math alias or a host operation may not collide with a builtin — not what source may declare.) Consequently NO layer may branch on a callee's written spelling: the parser is purely syntactic about calls (it never counts arguments from a callee name, so a wrong-arity builtin call is an ordinary evaluation-time `ArityMismatch` against the resolved signature, and is inert in an unevaluated property exactly like `count(1, 2, 3)`), and a builtin recognizer such as the loop optimizer's `if` planning may use the spelling only as a lookup KEY taken from registry metadata (`Evaluator.BuiltinDisplayName`) before confirming `Evaluator.ResolvesToBuiltinAlgorithm`. Lean already models exactly this — `preludeAlg` declares `if` with one ordinary `publicProp`, and `NameOwnership` treats the prelude as the outermost property level of the owner walk — so a spelling gate anywhere in C# is a divergence from the authoritative model. Builtin `if`'s ONE intrinsic behavior is its invocation (`if(condition, whenTrue, whenFalse)`: evaluate the condition, then only the selected branch); that laziness belongs to the resolved builtin, disappears when the name is shadowed, and never applies retroactively to a value the caller already built (`if(1, Risky*)` evaluates all of `Risky` under the ordinary `expression -> value -> supply` rule). A builtin VALUE slot demands its SELECTED argument through the ONE zero-argument value-demand law (C# `ZeroArgumentValueDemandRejection`/`ZeroArgumentValueDemandError`, Lean `zeroArgumentDemandError?` — the factored rejection half of the value-position `Param`/`Resolve`/block arms): a resolved callable that cannot accept zero supplied arguments is the ordinary arity rejection at the argument's reference and its body is never entered (`if(1, Inc, 0)` with `Inc(x) = x + 1` is "Property 'Inc' expects 1 parameter…", never `Unknown name: x`; a body that would not read its parameter is rejected all the same), a conditional is `ConditionalValueAccessError`, a written block `UnresolvedImplicitParams`; an UNSELECTED slot is never demanded; CALLBACK slots that supply arguments (`map`/`filter`/`reduce` steps, loop steps) never consult it; `reduce`'s initial accumulator keeps its dedicated hint but decides through the shared rejection law and retains the demanded family's name. Collection arguments and fixed VALUE/whole-number controls consult the same law after ordinary fixed-arity binding, and DEMAND an accepted item as soon as the descriptor identifies its VALUE slot during left-to-right call-item assembly, before later argument effects, so a collecting-only callback argument is never eagerly evaluated (`DemandSequenceBuiltinCallItemValue` / `demandSequenceBuiltinCallItemValue`, then `SequenceBuiltinValueDemandError` / `sequenceBuiltinValueDemandError?`); call-item and suffix preparation preserve the written source without demanding callback positions. Every builtin VALUE slot (`if` condition/branches, `while`/`repeat` initial state, the `repeat` count, `atoms`, `range` — `EvalResolvedArgumentCounted`, Lean `evalArgumentValueCounted` over `ResolvedArgumentAlgorithm.Source`/`source?`) and the ordinary-dot `.string` receiver (`EvalDotStringReceiverAlgOutput`) go through it; pinned by `LazySlotZeroArgumentDemandTests`, `CoreTests/ValueDemand.lean`, and the `lazy-slot-demand-*` `LanguageSpecCorpus` cases. Pinned by `BuiltinCallableIdentityTests`, `IfBuiltinArityPayloadTests`, the `builtin-callable-is-an-ordinary-prelude-binding` / `no-arity-based-callable-selection` / `if-*` `LanguageSpecCorpus` cases, and `CoreTests/NameOwnership.lean`. NOTE: `load` is NOT covered by this rule — it is still recognized by raw spelling (`AstHelpers.TryGetUnresolvedLoadArguments`) as a front-end/module directive; that asymmetry is deliberate-for-now and is not a licence to re-privilege a callable's spelling.

## Zero-argument value demand follows actual call arity (September 2026)

A callable may satisfy a ZERO-ARGUMENT VALUE DEMAND **if and only if an ordinary call supplying zero arguments can bind it** (C# `Evaluator.AcceptsZeroSuppliedArguments`, Lean `Algorithm.acceptsZeroSuppliedArguments`). Eligibility is arity, never parameter-list emptiness. Before this rule the law rejected a demand whenever the callable declared any parameter, so `Only(*xs) = xs` — whose ordinary call `Only()` is perfectly legal and yields `[]` — could not be read as a value at all, and the rejection reported the flattened declared capture count (`Head(x, *rest)` claimed two parameters where its own call reports one required item).

**The rule is the binder's own.** `ParameterPattern.MinimumSuppliedSlots` / `ParameterPattern.minimumSuppliedSlots` states the arity check `BindParameterPatternList` / `bindParameterPatternList` performs, and those binders now read it rather than re-deriving it: every top-level pattern consumes exactly ONE supplied slot whatever it contains — a sequence-value group is one slot the binder opens afterwards — and a COLLECTING capture at that level consumes NONE, because it collects whatever is left after the fixed prefix and suffix bind (an empty leftover is the exact empty list). A clause family decides by its own dispatch rule instead: it accepts zero supplied arguments exactly when some branch's top-level pattern has arity zero, which is the branch `matchCallBranches` selects for an empty argument list (a flat multi-binder core equivalent always has at least two parameters, so it never accepts). A BUILTIN is deliberately not decided by the law at all: `zeroArgumentDemandError?` passes it through so `EvalBuiltinValueCounted` / `evalBuiltinValueCounted` raises the builtin's own rejection, which is the very message `sum()` produces.

Consequently:

* `Only(*xs) = xs` is eligible: `Only`, `(Only)`, `((Only))`, `if(true, Only, 0)`, `count(Only)`, `Only.count`, `Obj.M`, a fixed user parameter that reads its argument, a root output row — the direct value demands produce the collected empty list, exactly as `Only()` does; `count(Only)` and `Only.count` consume that value and return `0`.
* `Head(x, *rest)`, `Tail(*rest, z)`, `Mid(x, *rest, z)`, `Pair(x, y)`, `P((x, y))`, `P((x, *rest))`, `P((*xs))` and `G((a, b), *rest)` are not: each requires at least one supplied value, and a nested pattern's scalar one-item fallback binds ONE value rather than accepting none.
* The rejection reports the TRUE minimum supplied count (`Head` 1, `Mid` 2, `P((x, y))` 1, `G((a, b), *rest)` 1) in the ordinary structured `ArityMismatch` at the demand site, so the demand and its ordinary zero-argument call can no longer claim different numbers. The demand law reads that rule directly and deliberately does NOT consult `CallableArityFacts`; since the F4 correction the facts state the same per-level rule (`G((a, b), *rest)` is min 1, unbounded max — see `CallableArityFactsPerLevelTests`), so the two can no longer report different minimums.

**Eligibility is all that changed.** An accepted demand evaluates through the ONE funnel `EvalZeroArgumentDemandOutputCounted` / `evalZeroArgumentDemandOutputCounted` (with its value projection): a callable declaring no top-level pattern is its output exactly as before, a pattern list that accepts the empty supply is bound by the ORDINARY binder against that empty supply — so the collecting parameter holds `[]` while the body runs and the callee's names shadow all three inherited tiers as a written call's do — and a zero-accepting family dispatches through ordinary conditional dispatch. The funnel's common arm is a bare delegation to the very core the demand sites called before, and the binding arm's locals live in a separate non-inlined frame, because nested blocks and property reads recurse through it inside the calibrated 1 MiB stack envelopes.

Everything else is untouched:

* **Cache policy.** A bare property-style demand still takes the run cache (`isCacheableZeroArgPropertyAlgorithm` now reads the same acceptance rule, so a newly eligible property is on the SAME path an ordinary zero-parameter property is on), and `Only()` keeps its established direct-call bypass. Builtin VALUE slots — `count(Only)` and the dotted `Only.count` alike — still demand directly and bypass the entry.
* **The algorithm channel.** A callback, a higher-order argument and a loop step still receive the callable: `map((1, 2), Only)` is `[[1], [2]]`, never `[]`. So does a callable FORWARDED through a parameter: a user call binds `Apply(Only, xs)`'s parameter on both channels (the value `[]` and the algorithm `Only`), and a builtin slot that INVOKES its argument — the `filter` predicate, the `map` mapper, the `reduce` reducer, a `while`/`repeat` step — invokes the ALGORITHM-channel binding (`ResolvedArgumentAlgorithm.invoked` / `InvokedAlgorithm`), so `Apply(f, xs) = xs.map(f)` selects the same callable as `xs.map(Only)`, from a nested block capturing the parameter too; ordinary eager parameter binding can already have evaluated `Only()` to establish the value channel, and callable-slot selection adds NO further value demand; every VALUE slot (the collection, loop initial state, `if` branches, `reduce`'s `initial`) reads the bound value and never re-runs the body, and a parameter bound on the value channel only has no callable to invoke. The descriptor identifies VALUE slots during left-to-right assembly: demand finishes before the next argument is evaluated. Collecting-only callables and zero-arity families in CALLBACK slots remain unevaluated.
* **Value-context lifting.** The front end's decision to lift a referenced callable's parameters into the enclosing signature (an arithmetic operand, a list element, a registry-strict Math argument) happens BEFORE the law and is unchanged for collecting and fixed parameters alike. A lifted parameter keeps its kind, so a lifted COLLECTING root parameter now makes the program accept the empty supply — which is exactly what the explicitly called spelling of the same row already did — while a lifted FIXED one still leaves an argument nobody can supply.
* **Laziness, charges, cancellation, optimizer.** An unselected builtin slot is still never demanded, the depth-only argument charge is unchanged, and the loop planner never plans a callable with an explicit parameter list as a temp (such a step falls back to the generic strategy).

Pinned by `ZeroArgumentDemandArityTests` (the metamorphic law over the signature families, host-built signatures, parentheses transparency, the algorithm channel, cache and host/random execution counts, genuine async suspension, cancellation, and the reported minimums), `LazySlotZeroArgumentDemandTests`, `ForwardedCallableChannelTests` (the forwarded algorithm channel), `AlgorithmParameterNamesTests`, `CoreTests/ValueDemand.lean`, the `minimum_supplied_slots_*` / `zero_argument_*` / `collector_binder_empty_supply_*` laws in `KatLangArityLaws.lean`, and the canonical `zero-argument-demand-follows-actual-call-arity` and `forwarded-callable-keeps-its-algorithm-channel` `LanguageSpecCorpus` cases.

## Grace (F10)

Grace `~` is a front-end parameter-order annotation on exactly one bare name occurrence (`~x` / `x~`), written DIRECTLY attached to that name (marker attachment law: `~ x` and `x ~` are `InvalidGraceMarker` attachment errors that recover to the plain name with no weight; `~~x` and `~x~` are attached runs); it is not a general expression operator, repeated markers on that occurrence use ordinary weight arithmetic, and elaboration strips it before evaluation. GRACE MUST BE EFFECTIVE (F10): the marker is meaningful only on a FREE bare-name occurrence that implicit-signature collection promotes to a parameter of the enclosing algorithm — the one place its weight is consumed. On an occurrence whose binding is already fixed — an explicit parameter, a captured parameter of an enclosing algorithm, a visible property, a builtin, an opened name, a dot member that always resolves structurally (or the `.string` intrinsic), and ANY occurrence under a closed explicit parameter list — it is the front-end error `DiagnosticCode.InvalidGraceMarker` ("Grace has no effect on 'x' because …"), reported by `ParameterDetector.ReportIneffectiveGrace` from the REWRITE pass (once per occurrence per region through a diagnostic visit set; run-local `GraceOrigins` carries stripped markers through implicit resolution so ownership completion revalidates their final bindings, including cancelling zero-weight markers), never a silent no-op; the reason comes from the same owner walk the editor resolves with, and conditional branch bodies keep the parser's own rejection (`GraceEffectPolicy.NotReported`). Pinned by `GraceEffectivenessTests` and the `grace-on-bound-name-rejected` / `grace-under-explicit-list-rejected` `LanguageSpecCorpus` cases. A graced name inside REDUNDANT PARENTHESES is the graced name (PARENTHESES GROUP SYNTAX, September 2026): `(~a).V` is `~a.V` — the ordinary structural-first dot edge on `a` with `a` moved earlier, so a bound algorithm's own `V` is read and a number falls back to the lexical `V` exactly as `a.V` and `(a).V` do — and `(~a)(b)` is the call `~a(b)`; the parser's `IsRedundantGrouping` never looks at the inner kind, so the group is erased whatever the marker's weight and Grace can never change selection (`OutputBundleSplitTests`, the `grace-in-redundant-group-is-grace-on-the-name` spec case).

## Parameter channels and shadowing

A user call binds each parameter on the value channel, the algorithm channel, or both, and the callee then evaluates in the CALLER's environments extended with its own bindings — that inheritance is what lets a nested property read an ancestor-owned parameter and a nested call invoke an ancestor-owned callable. A BOUND PARAMETER OWNS ITS NAME ON EVERY CHANNEL: every binding site — user calls (flat fixed, patterned, item-supply/collecting), clause-family binders, sequence-builtin callbacks, and generic and planned loop steps, in both engines and in the async twin — shadows the callee's parameter names out of ALL THREE inherited tiers: the value environment (`ShadowValEnv` / Lean `ValEnv.shadow`), the counted callback-parameter environment (`ShadowCountedParamEnv` / `CountedParamEnv.shadow`), and the algorithm environment (`ShadowAlgEnv` / `AlgEnv.shadow`). The two context tiers are shadowed by ONE shared helper — C# `ShadowInheritedParameterEnvironments`, Lean `EvalCtx.bindParameters` — and a new binding path must go through it rather than filter one tier ad hoc. Consequences: a parameter bound ONLY on the algorithm channel (a higher-order argument, or any argument whose value evaluation failed) read in value position reaches its algorithm binding — the ordinary zero-argument value demand, its arity error, or the conditional value-access error — never a same-named caller value; and a parameter bound ONLY on the value channel read in call position (`f(2)`, the lexical dot-call fallback `2.f`, forwarding through `Pass(f)`) fails as not-callable exactly like the standalone program, never invoking a same-named caller callable. Lookup never falls through to a caller binding merely because the inner binding is unusable in the requested position — this is lexical name shadowing, not overload resolution across channels — while names the callee does not bind stay visible (`Inner(x) = f(x)` inside `Apply(f)` still calls the received `f`). Without this, a callee silently computed with an unrelated caller value or callable, and which caller parameter names collide with a callee's became observable.
