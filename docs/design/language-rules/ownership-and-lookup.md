# Ownership, lookup, and binding rules

The full statement of the rules that AGENTS.md indexes in compact form — consequences, examples, the implementation map, and the pinning tests. The detail moved here verbatim from AGENTS.md in September 2026; in November 2026 the dense statements AGENTS.md still carried moved here too, as the **Summary** list that opens a section. These rules are as binding as AGENTS.md; its index entry points at the section here. Keep them in step: a rule change edits the index entry, the section's summary and its full statement together.

## The resolution model in one place

Every layer — the evaluator (sync, async, planned), parameter detection, implicit-argument resolution (its signature analysis and its rewrite, B3-5★), exposure/dependency analysis, open validation, and the editor model — answers "what does this occurrence denote?" by the same ordered rules (name-resolution audit #8, September 2026):

1. **Owner walk.** Search outward by owning scope — the occurrence's body, each enclosing algorithm or branch body, the root, and the prelude as the outermost property level (builtins, `Math`, the Math aliases, and a run's host operations). At each level a PARAMETER binding (written, inferred, collecting, grouped, or a branch binder — never one that automatic parameter forwarding added, see § Automatic parameter forwarding preserves existing bindings) is asked before the level's PROPERTIES (any visibility); the first level that declares the name decides. A property may not share a name with a parameter of its own or an enclosing algorithm (declaration error), so the tie rule only matters in recovery trees.
2. **Opens, only after the whole walk.** If no level declares the name, the `open` providers are consulted level by level, innermost first; a level's targets count once per PROVIDER — the declaration they resolve to in its declaring scope, never their spelling or position (Q-19 D-I, § Open provider identity) — each provides only its PUBLIC members, and the first level at which any provider supplies the name decides — one provider selects its member, two or more select NOTHING: a WRITTEN name that reaches such a level is the front end's `AmbiguousOpen` (Q-29 A-U, § Static open ambiguity), and a lookup only evaluation decides (a dot fallback the receiver decides, a host-built tree) is the evaluators' `ambiguousOpen`. An open therefore never overrides anything owned, a builtin or host operation included.
3. **Promotion, only after both.** A name nothing declares or provides becomes an implicit parameter of the outermost inferring level (an algorithm without a written parameter list) whose own rows use it — a nested level sees it as a captured ancestor parameter, and a name used only inside a nested level is claimed by that level (PAR-03); a closed list's own level and a clause-branch body never gain it, so an occurrence in their own rows is an error. A dot edge's fallback name is such an occurrence by the selection lattice (Q-75 F-A): an inferring body collects it unless the fallback is never selected, and a closed list or branch body checks it only when the fallback is certain.
4. **Structural first on dot edges.** `R.M` looks `M` up among the receiver's DECLARED members (any visibility, any spelling — `string` included) first, at every level of a chain; only a structural miss falls back — to the `.string` intrinsic when `M` is `string` (Q-17 S-C; a lexical `string` is never consulted), otherwise to the lexical callable `M` of rule 1–3, as the ordinary call `M(R, args)`. A declared but inaccessible member is its own error, never a fallback.
5. **`open` is static.** A target's head is an ordinary occurrence (a parameter-owned head is an error, never a farther declaration); a target must resolve — head through the direct chain (never another open), dotted steps through public declared members — and must need no call. A transparent reference opens its TARGET's public namespace under the target's provider identity, and a forwarding carrier its own public declarations (OD-C, § Whole-algorithm transport).
6. **Identity decides, spelling never.** The selected declaration carries its identity to every consumer: value and algorithm positions are one decision projected onto two channels; builtin behavior (laziness of `if`, optimizer fusion, the Math value-demand contract) follows the resolved identity; a transparent reference `Alias = A` IS `A`'s identity, while a braced `C = { A }` is a structure of its own (M4★, § Whole-algorithm transport), and forwarding the same bound callable keeps its identity; a dot expression carries ONE callable identity in every algorithm-capable position, callee included (Q-18 C-B3: an argumentless structural path is its member, everything else a value); accessibility is checked on the selected member afterwards and never changes the selection.

**Automatic parameter forwarding changes none of these answers** (Q-04, decided September 28 2026). It runs after the six rules have decided every written name, reuses the PARAMETER bindings they select to supply a lifted callee's inputs, and adds a parameter only for a name no parameter binding supplies — a forwarded parameter that no written name ever denotes. There is no second round of selection after forwarding.

The sections below state each rule in full.

## Consumer-directed observation (CDO-1, owner-approved 2026-10-31)

**Summary.** The rules of this section in dense form, with their implementation anchors and pinning tests; the full statement follows.

- CDO-1 CONSUMER-DIRECTED OBSERVATION (owner-approved 2026-10-31; consolidates Model-C, SYN-05, Q-03/Q-04, M4★, FWD-02, NEED-06 and CACHE-PUB-1 — supersedes none of them, adds no syntax, coercion or equality): a written name resolves ONE lexical binding without evaluating it, whatever its consumer, argument count or demand (formula lifting transforms a use, never selects another binding); transport preserves its lazy VALUE and CALLABLE capabilities. The immediate consumer decides whether to demand VALUE, project CALLABLE, or invoke with a written supply. CALLABLE projection never demands THAT computation's VALUE (runtime routes may demand others; their failures are never absence), and calculated results never gain callable identity (`Apply(F())` passes F's result). A bare VALUE read is eligible exactly when the ordinary binder accepts the empty supply (`Only(*xs)` yes, `Head(x, *rest)` no) and reads the cache; `F()` is a fresh explicit invocation that never reads or replaces an entry (CACHE-PUB-1 may establish an EMPTY one), never shorthand for bare `F`; no partial application. M4★ distinguishes transparent `A = F` from structural `A = { F }`; formulas `A = F + 1`, closed by-name forwarding `A(p) = F` and explicit `A(p) = F(p)` keep their own rules, and a root row `F` is a VALUE consumer, not alias formation. Ownership, activation and cache domains stay stable (a NeedCell's one VALUE is not the property cache). NEED-04 repeated-name matching is unchanged. `ConsumerDirectedObservationTests`. [`ownership-and-lookup.md` § Consumer-directed observation]

**A KatLang name resolves to a binding, independently of how the binding is consumed. A consumer determines whether it transports that binding, projects its callable identity, demands its calculated value, or explicitly invokes the algorithm. A bare name is not universally shorthand for an empty-argument call.**

CDO-1 is a CONSOLIDATION, not a new mechanism: it restates in one place what Model-C (`call-by-need.md` NEED-06/NEED-10, § Result boundary), SYN-05 and Q-03 (§ Builtin identity and the zero-argument value demand, § Zero-argument value demand follows actual call arity), Q-04 and the formula-lifting law, M4★ (§ Whole-algorithm transport), FWD-02 (§ Callable aliases and bare forwarding) and CACHE-PUB-1 (`evaluator-and-hosting.md` § Zero-argument property cache) already decide. It supersedes none of them and erases none of their documented exceptions. These rules and their detailed sections must remain consistent with the approved decisions; an unresolved normative conflict requires owner clarification. It changes no syntax, operator, coercion or equality. **NEED-04 repeated-name matching, `Same(x, x)` compatibility, mixed callable/value repeated names and Q-28 representative selection are untouched** (`sequences-lists-and-calls.md` and `call-by-need.md` NEED-04 own them).

1. **CDO-R1 — resolution is consumption-independent.** Resolving a written name selects the ONE lexically applicable binding (§ The resolution model in one place: owner walk, opens, promotion, structural dot edges, static `open`, identity) without running its output. The consumer's role, the argument count and whether a result is demanded never change which declaration the name denotes (SYN-05: no layer branches on spelling or argument count). Static formula lifting may transform a USE of the binding (it supplies the callee's required parameters by name); it never selects a different binding (Q-04).
2. **CDO-R2 — CALLABLE and VALUE are distinct observations.** Projecting the callable channel obtains the algorithm identity and its lexical owner without demanding THAT supplied computation's VALUE (NEED-06). A RUNTIME projection — an `.Algorithm` link, parameter-rooted member navigation — may demand OTHER cells on its route; such a failure keeps its kind and is never read as callable absence (META-S3-1 wording of NEED-06). Absence is a successful "no identity" outcome. Ordinary calculated values never acquire algorithm identity (§ Result boundary).
3. **CDO-R3 — VALUE consumers demand a value.** Arithmetic, value `==`/`!=`, root output rows, value-requiring builtin slots, selection and the other value positions demand the binding's VALUE under their established strictness, lazy-argument behavior, emitted-count boundary and property caching. This does not override source elaboration (Q-03 lifting, Q-15 closed lists), closed signatures, or the specially defined argument roles of user calls and callbacks (a user call's whole argument stays neutral; an invoking slot projects CALLABLE).
4. **CDO-R4 — explicit invocation is a call.** `F(args)` invokes the selected callable with precisely the supplied items, through ordinary cardinality, pattern and body rules; there is no partial application and no callee guessing. `F()` is an explicit ZERO-SUPPLY INVOCATION, not a synonym for bare `F`: it executes freshly and never reads or replaces an established zero-argument entry, and under CACHE-PUB-1 an eligible successful zero-supply invocation may publish an entry only when that origin is empty.
5. **CDO-R5 — bare VALUE demand uses actual zero-supply acceptance.** A bare value read is eligible exactly when the selected callable's ORDINARY BINDER accepts an empty supply (`Evaluator.AcceptsZeroSuppliedArguments` / Lean `Algorithm.acceptsZeroSuppliedArguments`), never because a parameter list is syntactically empty: a collecting-only `Only(*xs)` may be read bare (its cached zero-supply demand), `Head(x, *rest)` cannot (its ordinary minimum-cardinality rejection). Builtins and clause families keep their own rejection and dispatch rules (`tick` its invocation-required refusal), and formula lifting and the root clause keep their behavior (§ Zero-argument value demand follows actual call arity, § The unified formula-lifting law).
6. **CDO-R6 — transport preserves available capabilities.** Supplying or forwarding a written reference preserves its lazy NeedCell with its CALLABLE and VALUE capabilities, without forcing VALUE, unless an explicit spread or another existing inspecting consumer requires it (NEED-07/NEED-08). `Apply(F)` may receive `F` as a callable; `Apply(F())` receives `F`'s calculated result, which has no algorithm identity — an invoking consumer reports its absence (`NotAnAlgorithm`, Q-06) without demanding it, and a VALUE consumer demands it (an argument-requiring `F` then fails `F()`'s own arity). A value-only input is never silently converted into a callable. META call references (`meta` parameters, `R.Invoke()`, `R.Algorithm`) stay their own contract (`call-by-need.md` § Call references).
7. **CDO-R7 — written definition forms remain distinct.** Under M4★ an eligible open `A = F` is a TRANSPARENT REFERENCE to `F` at any target arity — full target identity, members, callable routing, VALUE and cache origin; an eligible `A = { F }` is a STRUCTURAL FORWARDING CARRIER — its own structure and members, fresh forwarding of every explicit call, delegated bare VALUE, no alias-owned zero-argument entry; `A = F + 1` is a FORMULA whose value use may lift `F`'s required parameters by name; a closed `A(p) = F` is BARE FORWARDING by matching existing binding names, while `A(p) = F(p)` is an ordinary explicit call. A root output row `F` is a VALUE consumer, never alias formation. A literal `A = 7` (a constant), a named reference `A = F` and an output expression that evaluates a name are three different things.
8. **CDO-R8 — identity, ownership and caches remain stable.** Lexical declaration and activation ownership, members, transparent references, structural carriers, open-provider identities, property publication and per-supply memoization stay distinct concepts. Resolution, transport and identity-only projection create no fresh activation, observable value effect or cache entry. A NeedCell's at-most-once VALUE completion (NEED-02) is never the zero-argument property cache (NEED-10); Q-37 outermost ownership, CACHE-PUB-1, re-entrant reads and the host/native non-publication exclusions are unchanged.

**The consumer-role matrix.** Each consumer asks for exactly one observation of the binding the name resolved to:

| Consumer (examples) | Observation | Effects and caching |
|---|---|---|
| Plain binding, parameter transport, forwarding, alias hop, collector-slice opening | TRANSPORT (the cell itself) | none; NEED-01/07/08 |
| Invoking slot: a user call's callee `f(args)` through a parameter, `map`/`filter`/`reduce` callbacks, loop steps, `R.Algorithm` callee | CALLABLE projection, then an explicit invocation | projection demands nothing of the projected cell (a runtime route may demand others); the invocation is fresh |
| Value position: operators, value `==`/`!=`, root rows, builtin value slots, selection, `if` result | VALUE | a named zero-supply-accepting property reads/publishes its entry; a parameter reads its cell's one completed VALUE |
| Bare read of an argument-requiring callable in a value position | VALUE demand → that callable's ordinary rejection | unless the front end lifted it (formula, Q-03/X-02) |
| Explicit `F(args)`, `F()` | INVOCATION with the written supply | fresh; CACHE-PUB-1 may establish an EMPTY entry for an eligible zero-supply call |
| `A = F` / `A = { F }` / `A = F + 1` / `A(p) = F` / `A(p) = F(p)` | formation (CDO-R7), decided statically | no evaluation at formation |

**Boundary cases**, each pinned by the suites named below:

* With `F = tick()`: `F, F(), F + 0, F == 1, F` is `(1, 2, 1, true, 1)` — the bare read publishes, `F()` is fresh and never replaces the entry, arithmetic and comparison read the entry.
* `Bad = 1 / 0` / `Ignore(f) = 0` / `Ignore(Bad)` is `0` (transport never forces); `Read(f) = f + 1` / `Read(Bad)` fails with `DivisionByZero` (a VALUE consumer).
* `Square(x) = x * x` / `Apply(f) = f(3)`: `Apply(Square)` is 9; `Apply(Square())` and `Apply(Square(2))` are `NotAnAlgorithm` and never evaluate the supplied call; `Read(Square())` is `Square`'s `ArityMismatch` — the explicit empty supply, never a partial application.
* `Only(*xs) = tick()`: `Only, Only(), Only, Only(9)` is `(1, 2, 1, 3)`; `Head(x, *rest) = x` / `Head` is `ArityMismatch` (minimum 1).
* `Seven = 7` / `Apply0(f) = f()`: `Apply0(Seven)` is 7 (a written reference has CALLABLE whatever it computes), `Apply0(7)` and `Apply0((Seven, Seven))` are `NotAnAlgorithm` (a literal and a capture have none), and `Apply1(f) = f(1)` / `Apply1(Seven)` is `Seven`'s `ArityMismatch`.
* With `F = tick()`, `A = F`, `B = { F }`, `C = F + 0`: `A(), B(), C(), F` is `(1, 2, 1, 1)` — `A()` is F's fresh call establishing F's empty entry, `B()` forwards freshly, the formula reads F's entry.
* `F(p) = p * 10` / `D(p) = F` / `E(q) = F(q)`: `D(2), E(3)` is `(20, 30)`, and `D(q) = F` is `UnforwardableParameter`; `Sub(y, x) = y - x` / `G(x, y) = Sub` / `G(10, 3)` is -7 while `Sub(x, y)` written explicitly is 7.

Implementation map (the rules use the existing mechanisms, with no CDO-specific resolver): binding selection is shared through `Evaluator.LookupLexicalRaw` (`LookupLexical` / `LookupLexicalResolvedAlgorithm` normalize CALLABLE, `LookupLexicalForValue` normalizes the VALUE terminal without initiating CALLABLE projection) and `ElaboratedScopeLookup.SelectOwnedDeclaration`; Lean mirrors this with `lookupLexicalPropertyRaw`, `lookupLexicalProperty` / `lookupLexical`, `lookupLexicalValueProperty` and `selectOwnedDeclaration`. Pinned by `ConsumerDirectedObservationTests` (the boundary cases above, six routes, tick/trace observations) beside the detailed suites `LookupTwinEquivalenceTests`, `ResultValueBoundaryTests`, `ForwardedCallableChannelTests`, `ZeroArgumentDemandArityTests`, `ZeroArgumentReferenceLiftingTests`, `TickBuiltinTests`, `ExplicitCallPublicationTests`, `WholeAlgorithmTransportTests`, `CallableAliasBindingIndirectionTests`, `AliasAndBareForwardingTests`, `RuntimeAliasPublicationTests`, and Lean `CoreTests/ModelC.lean`, `ValueDemand.lean`, `NameOwnership.lean`, `AliasForwarding.lean`, `PropertyCachePublication.lean`, `KatLangArityLaws/WholeAlgorithmTransport.lean`, `PropertyInvocationLaws.lean`.

## Ownership-first lookup

**Summary.** The rules of this section in dense form, with their implementation anchors and pinning tests; the full statement follows.

- Ownership-first lookup must agree across the evaluator, elaboration, parameter detection, and semantic tooling. The evaluator's value-position `LookupLexical` and algorithm-position `LookupLexicalResolvedAlgorithm` are ONE implementation (`LookupTwinEquivalenceTests`); the evaluator's chain and `ElaboratedScopeLookup` (shared by `ParameterDetector` and `Semantics/`) must select the SAME declaration, because the detector's verdict rewrites the program (`LookupCoherenceTests`). Inline block and module heads remain separate providers at each written target, including dotted paths (the dedup key reads `AstHelpers.OpenTargetHead`; Lean `Expr.openTargetHead`). Open targets count once per semantic PROVIDER — the declaration in its declaring scope, never spelling or position (Q-19 D-I; `OpenProviderIdentity`, `Evaluator.ResolveAllOpens`, Lean `resolveAllOpens`; `Evaluator.OpenTargetDedupKey` is only a pre-resolution optimization) — in BOTH C# lookups. The whole model is SIX ordered rules — owner walk (parameter before property per level, prelude outermost), opens only after the whole walk (per level; two providers select nothing — a WRITTEN name there is the front end's `AmbiguousOpen`, Q-29 A-U), promotion only after both, structural-first dot edges, static `open`, identity never spelling — stated once in [`ownership-and-lookup.md` § The resolution model in one place]; `NameResolutionAuditTests` pins the cross-layer matrix. [`ownership-and-lookup.md` § Ownership-first lookup]

Ownership-first lookup is fundamental. Keep lookup behavior aligned across evaluator, parser/front-end elaboration, parameter detection, and semantic tooling. The evaluator's two lookup spellings — `LookupLexical` (reached by a bare name in VALUE position, `X`; returns owner+binding for the zero-arg property cache) and `LookupLexicalResolvedAlgorithm` (reached from ALGORITHM position: a callee `X()` or a dot-call target `X.m`) — are ONE implementation since M8+M9: the algorithm spelling is the projection of the binding-carrying chain (mirroring Lean, where `lookupLexical` projects `lookupLexicalProperty`), so ownership-first, open dedup, ambiguity, scope-level precedence, and prelude fallback exist once per engine; `LookupTwinEquivalenceTests` keeps both spellings observable so an independent fast path cannot silently regrow. Beyond that there are TWO C# lookup implementations — the evaluator's chain and `ElaboratedScopeLookup` (shared by `ParameterDetector` and `Semantics/`) — and they must select the SAME declaration, not merely both resolve: the detector's verdict rewrites the program (an unresolvable name becomes an implicit parameter), so a front-end disagreement changes what the evaluator runs. `LookupCoherenceTests` pins that relation with unique per-declaration sentinels; the `open`/visibility family in `SemanticExplorerCases.lean` pins the Lean/C# side. `open` targets count once per semantic PROVIDER (Q-19 D-I, § Open provider identity): `open A, A`, `open A, (A)` and `open Sub, Lib.Sub` for one declaration are ONE provider, not an ambiguity, while two declarations or two written blocks stay two however equal; bounded `Evaluator.OpenExprName` text is presentation only and never decides identity, and the complete-spelling key `Evaluator.OpenTargetDedupKey` survives only as a pre-resolution optimization (one spelling at one level resolves one target) — that rule lives in Lean `resolveAllOpens` and must be mirrored by BOTH C# implementations.

## The owner walk

**Summary.** The rules of this section in dense form, with their implementation anchors and pinning tests; the full statement follows.

- The OWNER WALK is the front-end half of ownership-first, with `ElaboratedScopeLookup.SelectOwnedDeclaration` its ONE implementation (Lean `selectOwnedDeclaration`): search outward by owning scope over the NAME-RESOLUTION parameters a scope binds (written, inferred, branch binders — never one automatic forwarding added, Q-04) and the properties it declares; the first owner declaring the name decides, so a captured ancestor parameter beats a property of any farther owner, opens are consulted only after the whole walk, the prelude only as the outermost property level, and ownership never changes promotion (`IsBoundName`). Properties matching parameters of the same or an enclosing algorithm are declaration errors (`ParameterPropertyCollisionValidator`), except that the never-called root's completed signature is checked against the root's OWN declarations only (an unresolved root name is `UnresolvedImplicitParams` at the first root output row). The owner map is `ParameterOwnership` (name → owning level, never a depth); `ShouldRewriteAsParam`, `ResolveReceiverNameProvider`, and `ComputeVisibleSymbols` all go through the walk. `ParameterOwnershipTests`, `LookupCoherenceTests`, the `ownership-*` spec cases. [`ownership-and-lookup.md` § The owner walk]

The OWNER WALK is the front-end half of ownership-first, and `ElaboratedScopeLookup.SelectOwnedDeclaration` is its ONE implementation (Lean: `selectOwnedDeclaration` / `elaboratesToParameter`, stated beside `shouldTreatAsImplicitParam` because `ScopeCtx` carries properties but no parameters): search outward by owning scope over the two kinds of OWNED declaration — the parameter bindings a scope binds (written, inferred, or a branch body's pattern binders) and the properties it declares — and the first owner that declares the name decides, a parameter beating a property of the SAME owner in an invalid recovery tree. Properties matching parameters of the same or any enclosing lexical algorithm are declaration errors, checked by `ParameterPropertyCollisionValidator` after automatic parameter forwarding, forwarded parameters included (Lean: `conflictingOwnedNames` / `validOwnedDeclarations`) — with ONE root exemption: the root program is never called, so its completed signature (names it could not resolve, or names forwarding lifted into it) is checked against the root's OWN declarations only and never blamed on a property nested in a deeper owner; such a name surfaces as the root's `UnresolvedImplicitParams` evaluation error, positioned at the first output row of the root by the ordinary missing-arguments span rule — or at the member token when that ONE name came from a missing member on a statically known receiver (diagnostics-only; see § Dot-call resolution and missing members) — (`Lib = { public Q = 1 }` beside the root row `Q + 1` is a missing `open Lib`/`Lib.Q`, not a conflict in `Lib`; pinned by `ParameterPropertyCollisionTests.RootPhantomParameter_*`). Consequences that must hold together: a captured ancestor parameter beats a property of any FARTHER owner (the root's and the prelude's alike, so `F(pi) = { pi + 1 }` binds the parameter), a nearer property beats an outer parameter only in invalid recovery source, the nearest of several enclosing parameters wins, and a direct reference and one from a nested body always agree. `open` and the prelude keep their SEPARATE later policy: opens are consulted only after the whole owner walk (`LookupLexicalPropertyMatches`), so an owned parameter beats an inner `open` exactly as an ancestor-owned property does, and the prelude participates only as the outermost property level. Ownership is NOT the promotion question — `IsBoundName` still stops promotion at any visible property or opened name, unchanged. The owner map is `ParameterOwnership` (name → owning level, nearest wins by construction; never a counted depth), threaded through detection beside the scope chain — detection runs before automatic parameter forwarding, so it holds name-resolution parameters only, and the collision validator, which sees forwarded ones, takes a shared implicit-signature template as ONE layer owned by its level (FE-3, never a shared owner); the detector's parameter classification (`ShouldRewriteAsParam`) and receiver classification (`ResolveReceiverNameProvider`) must both go through the shared walk, and the editor's scope visibility is its enumeration form — derived per frame as persistent layers (parameters before the level's own properties, opens after every direct name) and pinned against the eager chain walk `ComputeEagerReferenceSymbols` (FE-4b; see [`editor-semantics.md` § Scope visibility and module provenance]). Pinned by `ParameterOwnershipTests`, `LookupCoherenceTests` (the `ownership.*` cases), and the `ownership-*` `LanguageSpecCorpus` cases.

## Open, exposure, and accessibility (K1-08)

- `open Name` may target a lexically visible private head, but open-provided names and dotted open steps select PUBLIC members (`NotPublicProperty` otherwise), while structural dot access selects DECLARED members, private included. ## Static-open ownership (SYN-03 / F2)

- STATIC-OPEN OWNERSHIP (SYN-03 / F2): `open` resolves statically, but its target's HEAD name is classified by the ONE owner walk (`ParameterDetector.ClassifyOpenTargetHeads`); when the nearest binding is a parameter of any kind, the head elaborates to `Expr.Param` — never an open form (`IsCoreOpenForm` / Lean `Expr.openForm?`; evaluation yields `BadOpenForm`) — the front end reports `DiagnosticCode.OpenTargetIsParameter` at the head without searching farther outward, and the rejected target provides no names; the root's phantom signature is not a callable binding for this decision (`ParameterOwnership.CallableBindings`). The dependency summary is expanded through each declaring ancestor once. Re-expanding it can duplicate provider identity levels and lose captured requirements. A qualified open can also carry a path back through its own intermediate owner; repeated local-path equations close by set-union idempotence, with the declaring algorithm, summary-map snapshot and bound-owner exclusions kept distinct. No incomplete result enters the completed-summary memo. `ModuleLawPostCommitReviewTests` pins nested qualified paths, captured values, exposure and declaration permutations.

STATIC-OPEN OWNERSHIP (SYN-03 / F2): `open` is resolved statically — it never opens a runtime value, and there is no dynamic `open` — but lexical ownership still applies to the target's HEAD name (`Lib` in `open Lib` / `open Lib.Sub`), which parameter detection classifies through the ONE owner walk (`ElaboratedScopeLookup.SelectOwnedDeclaration`, called from `ParameterDetector.ClassifyOpenTargetHeads`) exactly like every other bare-name occurrence. ## Static open-target validity (audit #8)

Every `open` target must RESOLVE, whether or not any name is ever looked up through it: a written target whose name head no enclosing declaration or prelude member provides (an open head resolves through the direct chain — the evaluator's `lookupLexicalDirect` — never through another open), or whose dotted step — from a name head or from an INLINE head alike, a written `{ ... }` block or a loaded module (`open { ... }.S`, `open load('url').S`) — names a member the receiver lacks, declares privately (open paths select public members), or declares only inside conditional branches (a family exposes no members), is the front-end error `DiagnosticCode.UnresolvedOpenTarget` (host family `KatLangErrorCode.UnresolvedOpenTarget`) at the target, reported by `OpenProviderValidator` beside the provider rule and worded after the step that fails. A DEFERRED UNIT IS JUDGED BY THE SAME RULE WHEN IT MATERIALIZES (MOD-10; November 17 2026). A UNIT COMPLETES THE FACTS OF EVERY CONTEXT IT PUBLISHED ITSELF (`StaticStructureOperation.CompleteLookups`; November 17 2026). BUILTIN CALLABLES ARE ORDINARY PRELUDE BINDINGS, and IDENTITY — never spelling, never arity — decides semantics (SYN-05). Lexical resolution selects exactly one callable without considering the argument count; the resolved callable then determines its signature and behavior: `resolve name -> select ONE identity -> assemble the ordinary argument supply -> bind against THAT signature -> invoke`. KatLang has no overloading by arity, so a nearer property or parameter named `if`, `count`, or `sum` shadows the prelude binding COMPLETELY — `if(x) = x + 1` makes `if(1, 2, 3)` an arity error against `if(x)`, never a fallback to builtin `if/3` — and a bound parameter may carry any callable under a builtin's name (`Apply(if, x) = if(x)`). - A DOT EXPRESSION HAS ONE CALLABLE IDENTITY (Q-18 C-B3, decided October 5 2026) in every algorithm-capable position — supplied argument, forwarded parameter, builtin callback, loop step and CALLEE — decided by the ONE projection `Evaluator.ProjectDotPathCallable` (supplied cells, `ResolveCallee` for the callee, and the sequence optimizer's recognition alike; Lean `projectNeedStructuralMember`, with `resolveCalleeAlg` in callee position): an argumentless structural path carries its member's own callable with aliases normalized and members of members kept (`Apply(Lib.F, 5)` and `(Lib.F)(5)` are `Lib.F(5)`), and every other dot expression — a fallback result, an intrinsic `.string`, an argument-bearing edge — is a calculation VALUE with none (Model C, NEED-06: `Twice(10.Sub(1))` and `(5.Inc)()` are `NotAnAlgorithm`, the callee worded "a computed value, not a callable"), except the META-S3-1 `.Algorithm` intrinsic, whose identity is the RUNTIME projection of the receiver reference's captured callee in every one of those positions. Parentheses never change identity: `(Box.G)(2)` ≡ `Box.G(2)` (one frame naming `Box.G`), and `(Box.V)()` is the fresh call `Box.V()`, never reading or replacing `Box.V`'s entry, while an owning success may establish an empty entry (CACHE-PUB-1). The internal `ResolveDotCallAlgorithm` / Lean `resolveAlg .dotMember` wrapper survives only as the CARRIER of a dot result used as a receiver, never a program-visible callable (the former DOT-09 callee wrapper identity is gone). Qualified canonical Math function references (`map(Math.Abs)`, `reduce(xs, Math.Pow, initial)`, `(Math.Abs)(-3)`) are therefore ORDINARY structural member references — the prelude `Math` module's member IS the native wrapper the lowercase alias and the opened canonical name reach — so no Math-specific resolution exists (`TryResolveQualifiedMathNativeReference` is DELETED; a user `Math = { public Abs(x) = 100 }` gives 100 in every position). The front-end Math value-ROLE contract (a Math argument is a VALUE role; since Q-15 no closed-list diagnostic attaches to it) is the CONSUMER's and follows identity: every spelling the resolver resolves to the member — the alias, `Math.X` and the `open Math` name — by its resolved algorithm (`LiftingCalleeKind.StrictValue`, `ImplicitArgumentResolver.PreludeContext.IsStrictValue`), a MUST-selected dot fallback as the call it is (`A.sin` ≡ `sin(A)`, classified as that call by `FormulaLiftingRoles.EdgeKind`), and a callable ALIAS of a member by its normalized target (`A = abs`: a closed `K(z) = A(Inc)` is the same run-time zero-argument demand as `K(z) = abs(Inc)`, `ClosedListValueDemand_FollowsTheAliasTargetAtRuntime`; the former static trigger `ResolvesToStrictValueMathMember` was deleted with Q-15 — a host operation's arguments are values); lifting a BARE Math function is identity-keyed like every lift (the unified formula-lifting law: the alias, `Math.X` and the opened name lift alike), and so is FWD-02's lone-row eligibility (the alias, `Math.X` and the opened name are callable-alias targets alike). Alias and canonical member stay distinct BINDINGS (own cache entries; `P(pi, Pi)` rejects under `open Math`). Host operations are prelude members in EVERY layer — detection, open validation, exposure (`PropertyExposureResolver.Resolve(..., hostOperations)`), and the editor (`ParseResult.HostOperations`). **Math members are recognized by what a name resolves to.** A Math FUNCTION member has three spellings — the qualified `Math.Sin`, the prelude alias `sin`, and the canonical `Sin` an `open Math` provides — and one registry descriptor (`MathMemberDescriptor`). The front end's registry-proven value-demand contract (a Math member's arguments are VALUE positions, so in an inferring formula a referenced callable that requires supplied arguments lifts its implicit parameters — one that works with no arguments is read as a cached value instead, Q-03 — while under a closed list that cannot supply them the reference stays bare and is its run-time zero-argument demand, Q-15; until Q-15, 2026-10-02, such a closed list was diagnosed) belongs to the CONSUMER, so it applies to every spelling that resolves to the member and to none that does not: the resolver resolves every spelling (owner walk → prelude → opens → structural dot paths, through aliases) and classifies the member it reaches by IDENTITY as `LiftingCalleeKind.StrictValue` (`ImplicitArgumentResolver.PreludeContext.IsStrictValue`), so a user-defined `Math` or `sin` never acquires the role (the former spelling-and-shape classifiers in `AstHelpers` and the detector's per-name stamp on opened Math names lost their last reader with B3-5★ and were deleted on 2026-11-14). Dotted-call equivalence carries the contract through fallback: a dot edge whose lexical fallback MUST be selected (a non-`string` edge whose `ElaboratedMissSelection` is `Always`) on a Math member is the call `x(receiver, args)`, so `A.sin` lifts `A` exactly as `sin(A)` does and `2.pow(A)` as `pow(2, A)` — the unified formula-lifting roles classify the edge as that call (`FormulaLiftingRoles.EdgeKind`, shared by the resolver's signature analysis and rewrite; the former dedicated `AstHelpers.HasRegistryProvenStrictValueFallback` / `IsStrictValueMathMember` had no remaining consumer and were deleted with Q-18); a fallback that is only possibly selected keeps its receiver and arguments neutral. FWD-02's LONE-ROW alias eligibility is identity-keyed too since October 1 2026 (the alias, `Math.X` and the opened name are callable-alias targets alike; formerly route-based, an opened name excluded), and a callable ALIAS of a member carries the consumer contract by its normalized target: with `A = abs`, `A(Inc)`, `Inc.A` and a dotted alias member's call `Lib.A(Inc)` give `Inc` the VALUE role exactly as `abs(Inc)` does, so a closed `K(z) = A(Inc)` is the same run-time zero-argument demand as `K(z) = abs(Inc)` (since Q-15, 2026-10-02; until then both were the same front-end diagnostic, triggered through the deleted `ImplicitArgumentResolver.ResolvesToStrictValueMathMember`). A host operation's arguments are VALUE positions for lifting exactly like a Math member's: the resolver classifies both as one callee kind (`LiftingCalleeKind.StrictValue`, every argument a value role); before Q-15 (2026-10-02) only the Math positions also carried the closed-list diagnostic. At run time the grouped callee IS the member (Q-18 C-B3: a dot expression has one callable identity), so `(Math.Abs)(A)` is `Math.Abs(A)` in every respect — no Math-specific resolution exists (the qualified-native gate `TryResolveQualifiedMathNativeReference` is deleted), and a user-defined `Math = { public Abs(x) = 100 }` gives 100 for `(Math.Abs)(3)`, `Math.Abs(3)` and `map([1], Math.Abs)` alike. User callables keep neutral arguments.

**Identity of the three spellings as bindings.** The alias and the canonical member are DISTINCT property bindings that share one algorithm (the alias property's value IS the member's algorithm object, so dispatch and signatures cannot drift): the zero-argument cache keeps one entry per binding, and repeated-name callable identity (declaration + declaring scope chain + activations, Lean `sameRepeatedCallableIdentity`) sees the alias wired under the prelude and the opened member wired under `Math`, so `P(f, f) = f` binds `P(pi, pi)` and, under `open Math`, `P(Pi, Pi)`, but rejects `P(pi, Pi)`. A qualified `Math.Pi` is an argumentless structural path, so on the algorithm channel it IS the `Math` module's `Pi` member — the very binding `open Math` provides (Q-18 C-B3): under `open Math`, `P(Pi, Math.Pi)` binds one identity, while `P(pi, Math.Pi)` rejects exactly like `P(pi, Pi)`. Math functions are compared by the same identity: under the group-aware NEED-04 (`call-by-need.md` § NEED-04) two references to one function match without any VALUE demand (`P(f, f) = f(0)` / `P(sin, sin)` is `sin(0)`, while `P(sin, cos)` is two identities), and only a plain value beside a function demands the function's VALUE — which a function that needs an argument does not have.

**Host operations are prelude members in every layer.** A run's `HostOperations` extend the prelude the evaluator resolves against, and every front-end layer must see the same prelude: parameter detection and open validation already did; exposure analysis (`PropertyExposureResolver.Resolve`, whose recorded chain also serves deferred-region materialization) and the editor model (`SemanticModelBuilder.Build(ParseResult)`, through the host configuration the parse result carries, `ParseResult.HostOperations`) now do too. Because the prelude precedes every open, an operation named like an opened library's member is what a bare reference selects: charging the library member made a self-contained property local-only (`Outer.Inner` refused), and the editor named the library member the evaluator never reads. Completion lists the operations as prelude names (`SemanticModel.PreludeSymbols`). Pinned by `NameResolutionAuditTests`.

## The `load` directive and a bare `load` (MOD-07, RES-06; X-36 / Q-62, October 31 2026)

**Only the CALL form is special.** A written call `load(...)` — `Expr.Call(Expr.Resolve("load"), args)`, recognized by shape and spelling (`AstHelpers.TryGetUnresolvedLoadArguments`), after the parser's ordinary grouping normalization — is the static module directive, whatever binding a nearer scope gives the name: `load(x) = x + 1` then `load(2)`, and `F(load) = load(2)`, are directive sites with the directive's own diagnostics (`LoadElaborationUnavailable` without a downloader, `InvalidLoadDirective` for a computed URL, a wrong argument count or a runtime position). This is the deliberate spelling exception RES-06 lists; it does not extend to a dot edge (`M.load(...)` is an ordinary member call), to a call through another spelling, or to a callee that merely RESOLVES to something named `load`.

**A bare `load` is an ordinary reference.** The semantic prelude declares a signature-only `load` placeholder so that parameter detection never infers the directive's name as a parameter; the runtime prelude has no `load` and no loader value exists. A written bare `load` whose Q1 binding is that registry placeholder — selected by provenance (the prelude level's own declaration; a host operation can never be named `load`, `HostOperations.ReservedPreludeNames`), never by spelling — and that no open supplies (Q1's `OpenedBinding` projection is a confirmed miss; the runtime consults the opens because its prelude lacks the name) therefore denotes nothing: it is the front-end error `UnboundLoadReference` at the occurrence, wherever it is written and whether or not evaluation would demand it — `X = load`, a root `load`, `load + 1`, `(load)`, `F(load)` with an ignored argument, an unused declaration, a dot edge whose fallback is certainly selected (`5.load`, Q-75's MUST obligation) — instead of the former run-time `UnknownName`. Parameter detection reports it in its per-occurrence rewrite walk beside `AmbiguousOpen` (`ParameterDetector.ReportUnboundLoadReference`); the directive's own callee, a MAY or never-selected fallback, declaration headers, member names and literal text are not value references and are never reported. Rejecting the name neither infers a `load` parameter nor changes any signature.

The check observes each use before consulting the rewrite memo, with a separate per-region set keeping one diagnostic per shared name node. A directive callee or unused fallback visited first therefore cannot hide a later value use. When implicit-argument resolution turns a provisional MAY fallback into MUST, the existing deferred-check mechanism reports the unbound name at the reserved diagnostic position; a fallback that remains MAY stays a runtime question.

**The placeholder is no open provider.** An open target's direct lookup resolves as at run time, so it never selects the semantic prelude's signature-only placeholder (`BuiltinRegistry.IsSemanticPreludeOnlyName`, by registry provenance): `open load`, and `open A, B` with `A = { public load = 1 }` / `B = load`, are `UnresolvedOpenTarget`, as for any other name only an open provides, and no message names the placeholder's parameter (`OpenSignatureOnlyPlaceholderTests`).

**A real binding named `load` is ordinary.** A property, a parameter, or an opened public member named `load` binds the bare name exactly like any other: `load(x) = x + 1` then `map([1, 2], load)` is `[2, 3]` and `F(f) = f(5)` / `F(load)` is `6`; `load = 3` / `load + 1` is `4`; an alias `A = load` of a user callable calls through `A`; `open M` with `public load` selects `M.load`, `open M, M` counts one provider, and two different providers keep their existing (run-time) ambiguity result rather than this diagnostic. This repair decides nothing about prohibiting or warning on such bindings (the remaining part of Q-62): they are neither banned nor warned about, and `load` is not a keyword.

**Phases.** The check runs in every elaborated unit's detection: the main document (a required eager error is a `ParseFailure` before evaluator entry — no output, effects, draws or charges), every loaded module and inline/open target (module content is positioned at its import site), and a selected deferred unit at its materialization boundary (reported through that boundary's `EvalFailure` provenance before its continuation is frozen). A provisional elaboration (a missing module) withholds it like every pass diagnostic, and a never-selected deferred unit is never judged. The check reads authoritative static facts only — no evaluation, demand, CALLABLE projection or acquisition — so a downloader changes nothing for an isolated bare reference. A host-built AST that skipped source processing keeps the evaluator's defensive `UnknownName`. C#-only: Lean models neither source loading nor this front-end phase. Pinned by `UnboundLoadReferenceTests`.

## Zero-argument value demand follows actual call arity (September 2026)

**Summary.** The rules of this section in dense form, with their implementation anchors and pinning tests; the full statement follows.

- ZERO-ARGUMENT VALUE DEMAND FOLLOWS ACTUAL CALL ARITY (September 2026): a callable may satisfy a zero-argument value demand IF AND ONLY IF an ordinary call supplying ZERO arguments can bind it (`Evaluator.AcceptsZeroSuppliedArguments` / Lean `Algorithm.acceptsZeroSuppliedArguments`), never because its declared parameter list is empty. The rule is the binder's own, factored out as `ParameterPattern.MinimumSuppliedSlots` / `minimumSuppliedSlots`, which the binder's count `needMinimumSuppliedSlots` EQUALS on every signature the X-02 gate admits (theorems `binder_minimum_is_the_signature_minimum`, `zero_argument_acceptance_is_the_binder_gate`, `family_zero_argument_acceptance_is_the_dispatch_gate`): every top-level pattern consumes ONE supplied slot whatever it contains, and a COLLECTING capture at that level consumes NONE. So `Only(*xs) = xs` is a valid value expression (`Only` and `Only()` both give `[]`), while `Head(x, *rest)`, `Tail(*rest, z)`, `P((x, *rest))` and `P((x, y))` still require a supplied value — a structural pattern binds ONE supplied value of its own kind, it never accepts none — and a clause family accepts only when a branch's top-level pattern has arity zero (the family dispatcher `selectNeedFamilyBranch`'s own gate). The REJECTION reports that true minimum (`Head` is 1, `P((x, y))` is 1), never the flattened declared capture count; a builtin is deliberately not decided by the law and keeps `EvalBuiltinValueCounted`'s own rejection (the very error `sum()` reports). Eligibility is ALL that changed: the accepted demand evaluates through the ONE funnel `EvalZeroArgumentDemandOutputCounted` / `evalZeroArgumentDemandOutputCounted` (no pattern → its output as before; a pattern list → the ordinary binder against the EMPTY supply; a family → ordinary zero-argument dispatch), so bare `Only` takes the ordinary property-demand/cache path while `Only()` stays fresh and may establish an empty entry under CACHE-PUB-1, callback and other algorithm-valued slots still receive the algorithm (`map(A, Only)` is unchanged) — a callable FORWARDED through a parameter too: an invoking builtin slot (filter/map/reduce callbacks, loop steps) takes the parameter's algorithm-channel binding — its cell's CALLABLE projection (Lean `projectNeedCallable`, C# `NeedCell.ProjectCallable`) — without an ADDITIONAL value demand; plain binding has no VALUE effects, while value slots, `reduce`'s `initial` included, read the bound value — value-context LIFTING reads the same rule since Q-03 (the next item), and laziness, charges, cancellation and the optimizer are unchanged. `ZeroArgumentDemandArityTests`, `LazySlotZeroArgumentDemandTests`, `ForwardedCallableChannelTests`, `CoreTests/ValueDemand.lean`, the `zero_argument_*` / `minimum_supplied_slots_*` laws in `KatLangArityLaws.lean`, the `zero-argument-demand-follows-actual-call-arity` spec case. [`ownership-and-lookup.md` § Builtin identity and the zero-argument value demand]
- IMPLICIT LIFTING FOLLOWS ZERO-ARGUMENT ACCEPTANCE (Q-03, September 28 2026): if a callable works with no arguments, using its name alone reads its cached value, even if it declares optional or collecting parameters; `A()` evaluates it again. The front end lifts a bare value-position reference into an implicit forwarding call ONLY when its callee REQUIRES supplied arguments — ONE rule, `ParameterPattern.AcceptsZeroSuppliedSlots`, read by `Evaluator.AcceptsZeroSuppliedArguments` and by the resolver's `RequiresSuppliedArguments` (via `CallableSignature.AcceptsZeroSuppliedArguments`) at every liftable arm and at root-row preservation; Lean specification `liftsBareValueReference` with the definitional identity `lifts_bare_value_reference_iff_not_cacheable` (a specification law, not a proof of the C# resolver) — never because its signature merely declares a parameter. So a collecting-only `Roll(*xs)` in ANY expression position (operator or comparison operand, list element, selection receiver, spread operand, strict Math argument, Math dot fallback receiver, a block or callback body that uses it, under a closed list) stays the cached zero-argument demand: `Roll == Roll` is `true`, `first(Pair)` and `Pair[0]` read one evaluation, a formula chain evaluates its base once. A body whose ONE row is the bare name is NOT such a position: it is a callable alias or bare forwarding (FWD-02, § Callable aliases and bare forwarding, superseding Q-03's former "an alias is a zero-parameter property holding its value" clause) — `Alias = Cnt` IS Cnt's callable and, read bare, is Cnt's own cached zero-supply demand under CNT's entry (M4★ OD-E: no alias owns an entry), and a closed `A(p) = Cnt` that forwards nothing to it reads Cnt's cached value; in a formula, by-shape forwarding reaches only a grouped stream `H((*xs))`, and an owner that lifts from such a callee requires arguments itself unless enclosing parameter bindings already supply them (Q-04, § Automatic parameter forwarding preserves existing bindings); a callable that requires an argument (`Inc(x)`, `Head(x, *rest)`, `P((*xs))`) lifts and forwards exactly as before, and explicit calls stay fresh. `ZeroArgumentReferenceLiftingTests`, `CoreTests/PropertyCacheConsumers.lean`, the `zero-argument-callable-name-is-read-not-lifted` spec case. [`ownership-and-lookup.md` § Zero-argument value demand follows actual call arity]

A callable may satisfy a ZERO-ARGUMENT VALUE DEMAND **if and only if an ordinary call supplying zero arguments can bind it** (C# `Evaluator.AcceptsZeroSuppliedArguments`, Lean `Algorithm.acceptsZeroSuppliedArguments`). Eligibility is arity, never parameter-list emptiness. Before this rule the law rejected a demand whenever the callable declared any parameter, so `Only(*xs) = xs` — whose ordinary call `Only()` is perfectly legal and yields `[]` — could not be read as a value at all, and the rejection reported the flattened declared capture count (`Head(x, *rest)` claimed two parameters where its own call reports one required item).

**The rule is the binder's own.** `ParameterPattern.MinimumSuppliedSlots` / `ParameterPattern.minimumSuppliedSlots` states the arity check the binder performs. C# writes it once (`PatternLevelArity`) and every gate of `BindNeedPatterns` reads it. Lean's `bindNeedPatterns` reads the binder-level twin `needMinimumSuppliedSlots`, which `binder_minimum_is_the_signature_minimum` proves equal on every level with at most one collector. The rule: every top-level pattern consumes exactly ONE supplied slot whatever it contains — a structural group, sequence or list, is one slot the binder opens afterwards — and a COLLECTING capture at that level consumes NONE, because it collects whatever is left after the fixed prefix and suffix bind (an empty leftover is the exact empty list). A clause family decides by its own dispatch rule instead: it accepts zero supplied arguments exactly when some branch's top-level pattern has arity zero, which is the branch the family dispatcher (`selectNeedFamilyBranch` / `BindNeedFamilySupply`) selects for an empty supply (a flat multi-binder core equivalent always has at least two parameters, so it never accepts). A BUILTIN is deliberately not decided by the law at all: `zeroArgumentDemandError?` passes it through so `EvalBuiltinValueCounted` / `evalBuiltinValueCounted` raises the builtin's own rejection, which is the very message `sum()` produces.

Consequently:

* `Only(*xs) = xs` is eligible: `Only`, `(Only)`, `((Only))`, `if(true, Only, 0)`, `count(Only)`, `Only.count`, `Obj.M`, a fixed user parameter that reads its argument, a root output row — the direct value demands produce the collected empty list, exactly as `Only()` does; `count(Only)` and `Only.count` consume that value and return `0`.
* `Head(x, *rest)`, `Tail(*rest, z)`, `Mid(x, *rest, z)`, `Pair(x, y)`, `P((x, y))`, `P((x, *rest))`, `P((*xs))`, `P([*xs])` and `G((a, b), *rest)` are not: each requires at least one supplied value — a structural pattern binds ONE supplied value of its own kind (`P((*xs))` a sequence, `P([*xs])` a list), it never accepts none.
* The rejection reports the TRUE minimum supplied count (`Head` 1, `Mid` 2, `P((x, y))` 1, `G((a, b), *rest)` 1) in the ordinary structured `ArityMismatch` at the demand site, so the demand and its ordinary zero-argument call can no longer claim different numbers. The demand law reads that rule directly and deliberately does NOT consult `CallableArityFacts`; since the F4 correction the facts state the same per-level rule (`G((a, b), *rest)` is min 1, unbounded max — see `CallableArityFactsPerLevelTests`), so the two can no longer report different minimums.

**Eligibility is all that changed.** An accepted demand evaluates through the ONE funnel `EvalZeroArgumentDemandOutputCounted` / `evalZeroArgumentDemandOutputCounted` (with its value projection): a callable declaring no top-level pattern is its output exactly as before, a pattern list that accepts the empty supply is bound by the ORDINARY binder against that empty supply — so the collecting parameter holds `[]` while the body runs and the callee's names shadow every inherited tier — value and need — as a written call's do — and a zero-accepting family dispatches through ordinary conditional dispatch. The funnel's common arm is a bare delegation to the very core the demand sites called before, and the binding arm's locals live in a separate non-inlined frame, because nested blocks and property reads recurse through it inside the calibrated 1 MiB stack envelopes.

Everything else is untouched:

* **Cache policy.** A bare property-style demand still takes the run cache (`isCacheableZeroArgPropertyAlgorithm` now reads the same acceptance rule, so a newly eligible property is on the SAME path an ordinary zero-parameter property is on), and `Only()` remains a fresh invocation: it never reads or replaces an established entry, but its owning success may establish an empty one (CACHE-PUB-1). Builtin VALUE slots — `count(Only)` and the dotted `Only.count` alike — read the same entry (since September 27 2026 a builtin argument that names a property resolves on its value channel to the ordinary property read; how a property value is consumed does not affect caching — see `evaluator-and-hosting.md` § Zero-argument property cache).
* **The algorithm channel.** A callback, a higher-order argument and a loop step still receive the callable: `map((1, 2), Only)` is `[[1], [2]]`, never `[]`. So does a callable FORWARDED through a parameter: a user call binds `Apply(Only, xs)`'s parameter on both channels (the value `[]` and the algorithm `Only`), and a builtin slot that INVOKES its argument — the `filter` predicate, the `map` mapper, the `reduce` reducer, a `while`/`repeat` step — invokes the ALGORITHM-channel binding — the cell's CALLABLE projection (Lean `projectNeedCallable`, C# `NeedCell.ProjectCallable`) — so `Apply(f, xs) = xs.map(f)` selects the same callable as `xs.map(Only)`, from a nested block capturing the parameter too; plain binding performs no VALUE evaluation, and invoking-slot projection obtains the independent callable identity without forcing. Executed VALUE slots are demanded in the builtin's established order after the cardinality check, each demand finishing before the next begins; explicit spread arguments were already evaluated during supply formation, before any VALUE demand (Model C, `call-by-need.md` NEED-05). Collecting-only callables and zero-arity families in CALLBACK slots remain unevaluated.
* **Value-context lifting reads the SAME rule (Q-03, decided September 28 2026).** *If a callable works with no arguments, using its name alone reads its cached value, even if it declares optional or collecting parameters; `A()` evaluates it again.* The front end's decision to lift a referenced callable's parameters into the enclosing signature — in any VALUE position of the unified formula-lifting law (§ The unified formula-lifting law): an operand, a list or capture element, a selection receiver or selector slot, a spread operand, a builtin value slot, a Math, host or family argument, a fallback dot receiver, a block or callback body that uses it in an expression — happens BEFORE the law, and it asks this law's question: a callable that accepts zero supplied arguments is NEVER lifted, because declaring a parameter does not by itself make a bare reference a call. Its reference stays this demand, read through the cache, in every position. ONE predicate serves both halves: `ParameterPattern.AcceptsZeroSuppliedSlots` (`MinimumSuppliedSlots` is zero), read by `Evaluator.AcceptsZeroSuppliedArguments` for a user algorithm and by the resolver's `RequiresSuppliedArguments` (over `CallableSignature.AcceptsZeroSuppliedArguments`) for every value-role reference whatever its category, and at root-row preservation; Lean states it as the specification predicate `liftsBareValueReference`, with the definitional identity `lifts_bare_value_reference_iff_not_cacheable` (lifting and cache eligibility are complements; a specification law, not a proof of the C# resolver). Before the decision the lift judged "declares any parameter", so `Only + 1`, `[Only]` or `abs(Only)` turned a collecting-only `Only` into the fresh call `Only(xs*)`, lifted a collecting `*xs` into the enclosing owner (which at the root could only forward an empty supply), and bypassed the entry its neutral positions read: `Roll == Roll` was `false`, `first(Pair)` and `Pair[0]` read different evaluations, and a formula chain re-ran its base 2^k times (PV-03). A callable that REQUIRES a supplied argument (`Inc(x)`, `Head(x, *rest)`, `P((*xs))`) is lifted and forwarded exactly as before, so a lifted FIXED root parameter still leaves an argument nobody can supply. Consequences: a body whose ONE row is the bare name is NOT a value position but a callable alias or bare forwarding (§ Callable aliases and bare forwarding; decided September 29 2026, superseding Q-03's former alias clause, under which `Alias = Cnt` was a zero-parameter property holding Cnt's value): `Alias = Cnt` IS Cnt's callable — read bare, it is Cnt's own zero-supply demand under CNT's entry (M4★ OD-E: no alias owns an entry), so `Alias` and `Cnt` share one evaluation — and with `Cnt(*xs)`, `G(*xs) = Cnt` forwards G's same-named collector, `Cnt(xs*)`, while `G(p) = Cnt`, which forwards nothing to it, reads Cnt's cached value; in a formula, forwarding by shape reaches only a grouped stream `H((*xs))` or `H([*xs])`; a closed parameter list never blocks such a reference (formerly PV-27: the closed-list strict-value diagnostic, itself removed by Q-15, reported it); and because an owner lifts only from callees that require arguments, an implicitly lifted signature requires arguments itself — unless enclosing parameter bindings already supply the required ones (Q-04: the formula `H = [Head][0]` inside `F(x)` forwards only `*rest`, so `H` accepts zero arguments and is then read like any such callable). Explicit calls, with or without arguments, stay fresh. ## Automatic parameter forwarding preserves existing bindings (Q-04, September 2026)

**Summary.** The rules of this section in dense form, with their implementation anchors and pinning tests; the full statement follows.

- AUTOMATIC PARAMETER FORWARDING MUST NOT CHANGE WHAT AN EXISTING NAME REFERS TO (Q-04, decided September 28 2026): automatic forwarding reuses parameter bindings only — properties, opened names, module members and builtins are never forwarded as parameters. Name resolution (`ParameterDetector`) decides every written name FIRST; forwarding (`ImplicitArgumentResolver`) then supplies each callee parameter a lifted FORMULA reference needs (a body whose one row is the bare callee is a callable alias, which reuses nothing, or bare forwarding, which reuses the same bindings by name but never adds one — FWD-02) from the binding a written parameter reference of that name already denotes at the referencing body: its own written or inferred parameter, else the nearest ENCLOSING parameter binding — an ancestor's captured parameter, a clause-branch binder, the root's inferred names — that the owner walk reaches before any same-named property (`ImplicitArgumentResolver.ForwardableParameters`, part of the resolver's region-memo key; Lean `forwardingSource`), and a reused binding's KIND decides a re-spread (FWD-02). THE LAW (the owner's decision of constitution open question Q-04, option (a), September 28 2026): **automatic parameter forwarding must not change what an existing name refers to.** Its boundary: **automatic forwarding reuses parameter bindings only — own written or inferred parameters, and accessible captured parameters of enclosing owners, clause-branch binders included. Properties, opened names, module members and prelude builtins are never forwarded as parameters.**

Two operations answer two different questions, and the second never feeds back into the first:

* **Name resolution** — *what does this written identifier denote?* — is `ParameterDetector` (the six rules of § The resolution model in one place). It decides every written name, promotes names nothing binds, and reports undeclared ones in closed bodies. Its verdicts are final.
* **Automatic parameter forwarding** — *which EXISTING parameter binding can satisfy this callee parameter?* — is `ImplicitArgumentResolver`. When a lifted reference in a FORMULA (a bare value-position reference, inside an expression, to a callable that requires supplied arguments, § Zero-argument value demand — a body whose ONE row is the bare callee is a callable alias or bare forwarding instead, § Callable aliases and bare forwarding) needs a callee parameter `n` — formula lifting is BY BINDING NAME, however many times the callee names `n` (§ Formula lifting is by binding name) — its argument is the binding a WRITTEN parameter reference of `n` would denote at the referencing body: the body's own written or inferred parameter; otherwise the nearest enclosing parameter binding the owner walk reaches before any same-named property — an ancestor's written or inferred parameter, a clause-branch binder, the never-called root's inferred names (`ImplicitArgumentResolver.ForwardableParameters`: per level, the enclosing name-resolution parameters minus every name the level declares as a property, persistent and keyed into the resolver's region memo by canonical content). Only when neither exists does an INFERRING body receive a new parameter `n`: appended after its own names (PAR-05), keeping the callee's pattern shape and kind, and marked as a FORWARDED parameter (`Algorithm.User.ForwardingParameterStart`, `NameResolutionParameterPatterns` is the prefix before it). A CLOSED body — a written parameter list or a branch pattern — receives nothing: the reference stays the zero-argument demand (a Math position remains an ordinary runtime zero-argument demand, per Model-C Q-15), and a closed body's lone bare row — bare forwarding — reuses the same bindings by name and is rejected (`UnforwardableParameter`) rather than adding one. Opens never take part: they are not owner levels, so an opened `n` leaves the walk undecided and the body gets a forwarded parameter.

A forwarded parameter is an ordinary parameter for every CALLER — arity, order, binding, activation, exposure — and a same-named property of its owner or of a body nested in it is still `ParameterPropertyCollision` (Lean `OwnerLevel.forwarded` is part of `conflictingOwnedNames`). But it is never what a written name denotes: the owner walk, open-head classification, Grace eligibility, the editor's scope visibility (`SemanticModelBuilder.CreateScope` declares only the name-resolution prefix) and the evaluator's reads of written names never see it — a written `Param` node is owned by a name-resolution parameter at or below the forwarding owner (the reuse rule guarantees no nearer forwarded parameter of that name exists), and a written `Resolve` is a property lookup. So nothing is re-selected after lifting: the former `ParameterDetector.CompleteOwnership` pass, which re-ran the owner walk against the completed signatures and made every same-named written reference denote a lifted parameter, is deleted, together with its synthesized-call origins, signature-preserving re-resolution, and Grace revalidation. A synthesized argument is a spanless `Param` read (or `name*` when a collecting destination meets a collecting SOURCE binding — the reused enclosing binding's kind counts, FWD-02), and a callee group is rebuilt as its own structural kind from the bindings its captures stand for (§ Callable aliases and bare forwarding; forwarding preserves bindings and structural kind), so the callee receives exactly the binding an existing written reference already denotes.

Consequences, all pinned:

* `A = y + 1` / `F(y) = { G = y * 1000 + A ⏎ H(y) = G ⏎ H(100) }` / `F(3)` is `3004`, exactly the inlined `G = y * 1000 + (y + 1)`: G reuses F's `y` and takes no parameter, so H's unrelated `y` cannot reach it. Before the decision G received its own `y`, completion made the written `y` follow it, and the program gave `100101` (PV-01). Extracting a sub-expression into a property therefore never changes the binding of a name that was already resolvable.
* A helper that reuses its owner's parameter is an ordinary zero-parameter property — local-only, one evaluation per activation of its owner (PROP-08) — so a neutral `if` argument reads it (`Report(width, height) = { Doubled = Area * 2 ⏎ if(width > 1, Doubled, 0) }` is 24, formerly `ArityMismatch`), and so do callback and loop-step blocks (`map([1, 2], { A + e })` inside `F(n)` binds only `e`).
* A same-named PROPERTY is never forwarded: `v = 99` / `Need(v) = v` / `Outer = Need + 1` still infers `Outer(v)` (`Outer(7)` is 8), so an unrelated property elsewhere can never turn a parameterized formula into a zero-parameter one. A written reference to the property is never rebound either: in `Outer = { Inner = v ⏎ Inner + Need }` Inner's `v` stays 99 (`Outer(7)` is 106, formerly 14). The same holds for an opened member (formerly `ownership-later-lifted-parameter-beats-inner-open`, now `forwarded-parameter-leaves-an-opened-reference`) and a builtin (`NeedMin(min) = min + 1` / `Safe = NeedMin + min((3, 4))` / `Safe(10)` is 14: the written `min(...)` still calls the builtin, formerly `NotAnAlgorithm`), while parameters named like builtins stay parameters to forward (`Clamp(x, min, max)` / `Safe = Clamp + 0`).
* A formula under a closed parameter list forwards an accessible enclosing parameter too: `A = y + 1` / `G = { F(x) = A + 0 ⏎ F(1) + y }` / `G(10)` is 21, with or without a strict Math wrapper (K1-04 had pinned the refusal, which the decision supersedes; the strict and the ordinary formula positions still agree). The LONE row `F(x) = A` is not a formula but bare forwarding (FWD-02), which reuses the same enclosing `y` by name and leaves F's own `x` unused, so the same program with `F(x) = A` is 21 as well.
* A forwarded parameter gives no meaning to a written name nothing declares: `Need(v) = v` / `Outer = { F(0) = 0 ⏎ F(n) = v ⏎ F(1) + Need }` is `UndeclaredIdentifier` in the branch body (formerly completion rescued it with Outer's forwarded `v`).
* Explicit shadowing is untouched: in `Outer(y) = { Inner(y) = A * 2 ⏎ Inner(10) + y }`, A's `y` inside Inner is Inner's own (`Outer(3)` is 25). A NEARER owner decides: under `Outer(y) = { Mid(y) = { Inner = A ⏎ Inner } … }` the alias Inner is A's callable (A's `y`), and Mid's lone row forwards Mid's own `y` to it, never Outer's.
* Aliases are NOT formulas (FWD-02, decided September 29 2026, superseding "aliases are formulas too"): inside `F(x)`, the bare `H = Head` with `Head(x, *rest)` is a callable alias of Head — Head's own `(x, *rest)` — and ignores F's `x` (`H(10, 20)` is 11), while the formula `H = [Head][0]` reuses F's `x` and forwards only `*rest`, so it accepts zero arguments (it is then read, never lifted, Q-03; `H(10, 20)` inside `F(4)` is 6). ## Formula lifting is by binding name (September 2026)

**Summary.** The rules of this section in dense form, with their implementation anchors and pinning tests; the full statement follows.

- FORMULA LIFTING IS BY BINDING NAME, regardless of how many times that name occurs in a callee's parameter patterns (decided September 29 2026, reversing the same day's Q-72 refusal; narrowed the same day to FORMULAS by FWD-02): when a formula USES a callee inside an expression, a caller owns ONE binding per name, so lifting gives the caller one parameter per binding NAME — PAR-05's first-occurrence order, the ONE merge (`ImplicitArgumentResolver.AppendMissingPatterns`) skipping every capture, group items included, whose name an earlier capture or a reused binding already binds — and the synthesized call (`BuildImplicitCallArguments`) supplies that one binding to EVERY occurrence. So `P(x, x) = x` / `D = [P][0]` is `D(x) = [P(x, x)][0]` exactly as `F(x)`, `G(x)`, `H = F + G` is `H(x) = F(x) + G(x)`; `P((x, a), x)` lifts `(x, a)`, `P(x, (x, a))` lifts `x, a` and `P((x, x))` lifts `x` (a sequence group left with ONE binder IS that binder — never the invalid singleton `(x)`), `P(x, [x, a])` lifts `x, [a]` (a list group keeps its kind) — never a formula signature that repeats a name — and a closed list that declares the name forwards its own binding (`Q(x) = P + 0` is `Q(x) = P(x, x) + 0`). The bare lone row is not a formula: `Some = P` is a callable alias — P's callable with P's own `(x, x)` (the former alias-signature deduplication and the exact-alias wrapper are superseded) — and `Q(x) = P` is bare forwarding, which reuses Q's one binding `x` by name for both occurrences, `P(x, x)` (FWD-02) — the same call a formula builds, but under a closed list that never gains a parameter. There is no repeated-name exception anywhere in formula lifting: lifting and neutral positions, the closed-list gate, FWD-02's re-spread by the SOURCE binding's kind, and Q-03's reads are the general rules. Q-05 is untouched: the direct `P(7, 8)` supplies independent arguments and fails, while a formula feeds one complete binding (the value and callable of ONE argument) to every occurrence, so nothing is spliced: a callable-bearing binding matches itself by identity and fails only where a body reads its VALUE, and a value-only binding agrees with itself or is its own failure (group-aware NEED-04). Formula lifting is the one place a callee's binder names reach a caller's SIGNATURE (bare forwarding reads them only to select EXISTING bindings, and an explicit call never reads them) — a deliberate by-name design, not an encapsulation defect. Lean models no signature construction (`forwardingSource` decides per name). `ImplicitForwardingByBindingNameTests` (per-shape laws: one binding per name, equivalence with the explicit same-binding call, rename-apart; every formula position against the explicit call; no inferred signature repeats a name — a callable alias has no signature of its own), the `implicit-forwarding-is-by-binding-name` and `repeated-name-wrapper-keeps-independent-arguments` spec cases. THE RULE (decided September 29 2026, reversing the Q-72 refusal of the same day; narrowed to formulas by the alias and bare-forwarding rules, next section): **formula lifting is by binding name, regardless of how many times that name occurs in a callee's parameter patterns.** A caller owns ONE binding for a given parameter name; when a formula USES a callee — in an operand, a list element, a selection receiver, a strict Math argument, a callback body, beside other dependencies — and the callee uses that name in several parameter positions, the lifted call supplies the caller's one binding to every occurrence. It is the composition rule formulas already follow across callees, applied without exception within one callee:

* `F(x) = x + 1` / `G(x) = x * 2` / `H = F + G` is `H(x) = F(x) + G(x)` (`H(3)` is 10) — one name shared by two callees;
* `P(x, x) = x` / `Twice = P * 2` is `Twice(x) = P(x, x) * 2` (`Twice(7)` is 14; `Twice(7, 7)` is an arity error, because Twice has one parameter) — one name used twice by one callee.

The language does not distinguish the two cases. ONE merge builds the lifted signature: the callee captures are walked left to right and a capture is skipped when an earlier capture — the owner's own, an earlier dependency's, an earlier one of the same pattern, inside a group too — or a reused enclosing binding (Q-04, previous section) already binds its NAME (`ImplicitArgumentResolver.AppendMissingPatterns` / `MissingCapturePattern`, PAR-05's first-occurrence order); a group keeps its KIND for the names that are new there — a sequence group left with ONE non-collecting binder IS that binder (the singleton `(x)` is not a pattern), a list group keeps its brackets (`[a]` is the one-element pattern), and a group left with no new binder contributes nothing. So with `D = [P][0]`, `P(x, x, x)` lifts `x`; `P((x, a), x)` lifts `(x, a)`; `P(x, (x, a))` lifts `x, a`; `P(x, [x, a])` lifts `x, [a]`; `P((x, y), (z, x))` lifts `(x, y), z`; `P((x, x))` lifts `x`; `P([x, x])` lifts `[x]`; `P(x, (x, *rest))` lifts `x, (*rest)`; `P(x, *rest, x)` lifts `x, *rest` — never a formula signature that repeats a name, and never one parameter per occurrence. ONE builder makes the synthesized call (`BuildImplicitCallArguments`): the callee's own patterns rebuilt from the caller's bindings (`P(x, x)`, `P((x, a), x)`, `P(x, [x, a])`, `P(x, rest*, x)` — each group rebuilt as its own kind, next section), so every occurrence of a name reads that one binding, and a collector is re-spread exactly when its SOURCE binding collects (FWD-02), never because a name repeats. A closed list or branch pattern that declares the name forwards its own binding into a formula (`Q(x) = P + 0` is `Q(x) = P(x, x) + 0`); one that does not follows the ordinary closed-list rule (`Q(y) = P + y` keeps `P` the zero-argument demand, in a Math position too — since Q-15 no front-end report names the missing `x`). Which positions lift and which callables lift are the unified formula-lifting law's (next section) — value positions lift and callable positions (`Apply(P)`, callees, callbacks, loop steps) keep the reference, for every category of callable, opened and structural members and clause families included — and a bare ROOT row is its callable's own zero-argument demand; none of these general rules has a repeated-name case.

**A body whose ONE row is the bare callee is not a formula.** `Some = P` is a callable alias of P — a call through it is P's own call, with two independent arguments, which must be equal — and `Q(x) = P` is bare forwarding (next section): Q's one binding `x` reaches both occurrences by name, `P(x, x)`, the same call the formula `Q(x) = P + 0` builds, under a closed list that never gains a parameter. The alias-signature deduplication this section formerly stated (`Some = P` as `Some(x) = P(x, x)`, recorded by the Q-72 reversal and the review that followed it) is superseded, and so is the exact-alias wrapper that replaced it (binding indirection, October 1 2026).

The relation to Q-05 (`sequences-lists-and-calls.md` § Collecting parameter lists, deconstruction, and callbacks: REPEATED NAMES ARE CONSTRAINTS, NOT MERGES) is exact: **a repeated name constrains independently supplied arguments; when a formula supplies the same caller binding to several occurrences, each occurrence receives that same complete binding, and no synthetic value/callable merge occurs.** The direct `P(7, 8)` — and the alias `Some(7, 8)` — write two arguments, and they must agree. `Twice(v)` supplies its one argument as ONE cell, evaluated at most once (Q-01), and each of P's slots reads that cell: a value-only argument agrees with itself by construction or is its own failure, and a callable-bearing one matches itself by identity, failing only where a body reads its VALUE (group-aware NEED-04), exactly as through the written `Same(x) = P(x, x)`. That equivalence is the pinned metamorphic law: formula lifting is observationally the explicit call that writes the same caller binding into every matching callee slot.

A group that dedupes down to one name keeps the law of its own kind. With `P((x, x)) = x` and `Some = [P][0]`, Some takes the bare binding `x` and calls `P((x, x))`, so `Some(v)` is the written `Some(x) = [P((x, x))][0]` for every `v`: `Some(7)` is `7`, `Some([7])` is `[7]`, `Some((7, 8))` is `(7, 8)` — each occurrence receives the whole binding, and the pair `(v, v)` is always a sequence. With `P([x, x]) = x` and `Some = [P][0]`, Some takes the one-element list pattern `[x]` and calls `P([x, x])`: `Some([7])` is `7`, `Some([[7]])` is `[7]`, while `Some(7)` and `Some((7, 8))` are the kind mismatch and `Some([7, 8])` the list arity error of the written `Some([x]) = [P([x, x])][0]`. A further formula forwards each surviving group as the same kind again (`Next = [Some][0]`). `RepeatedNameInsideOneSequenceGroup_LiftsTheBareBinding`, `RepeatedNameInsideOneListGroup_KeepsTheOneElementList` and `AnotherFormulaOverASurvivingGroup_RebuildsItAsTheSameKind` pin these observations against the written formulas; Lean's `CoreTests/RepeatedNameConstraints.lean` evaluates the corresponding elaborated trees.

THE LAW (decided September 30 2026; constitution Q-11, Q-12 and Q-13 collapse, FOR FORMULAS, into this one rule, while the lone-row alias and bare-forwarding rules stay FWD-02's, next sections): **a formula lifts a reference exactly when the reference's ROLE is a value use and the callable it RESOLVES to has a lifting signature that requires supplied arguments.** The two facts are independent — every observed lifting decision factors as role × signature (the re-investigation of September 30 measured 0 of 144 role/signature cells breaking the product) — and each has ONE implementation. No callable CATEGORY is an exception: once a callable has a lifting signature — a user algorithm, a builtin, a Math member, a host operation, an opened or dotted member, a nameable clause family alike — a formula lifts it by this one rule. Formula lifting is one of FOUR distinct mechanisms, and the other three are unchanged: the callable alias and bare forwarding (a body whose one row is the bare callee, FWD-02) and the explicit call (its written arguments, whatever the callee's names).

**The role is what the immediate consumer does with the slot** (C# `FormulaLiftingRoles`; Lean `LiftingRole`, `LiftingCalleeKind`, `liftingSlotRole`, `builtinLiftingSlotRole`). A VALUE role: an operand of a unary, binary, logical or comparison operator; a selection receiver or selector slot (postfix selection `receiver[s1, …, sn]`); a spread operand; a list or capture element; an output row or a deconstruction's right-hand side; the receiver of an intrinsic `.string` (a structural miss — a `.string` edge that selects a declared member navigates its receiver, Q-17 S-C); and every argument slot whose callee demands its value — a builtin's collection, value and whole-number controls and surplus positions (static roles: at run time, under Model C, cardinality is checked before any slot is demanded, so a surplus slot is never demanded — formerly it was value-evaluated before the arity verdict, PV-05; `if` takes three values; `repeat`'s count is a value), a Math member's and a host operation's arguments, and a clause family's arguments (a static role retained by NEED-05; at run time a family demands only what its patterns inspect or its selected body consumes, PAT-07 and NEED-04). A CALLABLE role: a call's callee; a builtin callback (`map`, `filter` and `reduce` steps) and a loop step; a whole argument of a user callable (its binder decides at run time, and a plain capture keeps both channels — call arguments stay neutral, sub-choice A1); an argument of a callee known only at run time (a parameter, an unresolved name, a computed value); and the receiver of a dot edge that NAVIGATES a structural member or whose dispatch only the runtime receiver decides. A dot edge whose lexical fallback is selected IS the call `F(receiver, args)`: its receiver is slot 0 and its written arguments slots 1.. of the fallback callee, so `R.F(args)` and `F(R, args)` infer alike. No role depends on how many arguments a call supplies. The role is RECURSIVE — a compound expression in any slot is examined and its own children take the roles of THEIR consumers (`Id(Inc)` keeps `Inc`, `Id(Inc + 0)` lifts it) — and BLIND TO LAZINESS: an `if` branch is a value position whether or not a run selects it, exactly as a free name written there becomes a parameter, and lifting never changes which branch a run evaluates. After a spread slot a builtin's positions are known only at run time, so a later position is a value only when every declared position of that builtin is one. The resolver's signature analysis (through ONE role walk, `ImplicitArgumentResolver.WalkLiftingRoles`, B3-5★) and its rewrite read the SAME classifier, and the rewrite checks that it lifted exactly the callees the selected signature was composed from, in the composed order (`RequireSelectedComposition`), so what a formula's equation records, what it lifts and how it is rewritten cannot drift.

**The signature is what the resolved callable contributes** (C# `ImplicitArgumentResolver.TryResolveLiftable`; Lean `Algorithm.liftingSignature?`, `builtinLiftingSignature`, `familyLiftingSignature?`) — ONE identity-keyed source, never the route that reached the callable. The reference is resolved in the language's own order — the owner walk over the document's properties, then the prelude (the builtins, the Math module and its aliases, the run's host operations; `load` is a front-end directive and has none), then the opens level by level (one public provider selects, two select nothing) — and a structural dot path `R.M` by its member. A user algorithm contributes its FINAL parameter patterns — an open body of this resolution its SELECTED signature (B3-5★, § Signature selection below), a closed body its written list, a body an earlier operation completed its published one; a callable alias contributes its NORMALIZED TARGET's signature (lifting looks through aliases, so an alias has no signature, kind or role of its own); a builtin its callable interface, `BuiltinDescriptor.PlainSignature` (the registry's parameter names; a loop's `meta step` gives a caller an ordinary binding); a Math member or host operation its declared parameters; an opened or dotted member its own signature, by the same rule. A CLAUSE FAMILY contributes one whole-value slot per top-level position (its common arity, PAT-03), each named by its clauses: a clause that binds a PLAIN parameter at a position votes that name — a literal, a structural pattern and a binderless group vote nothing, being dispatch detail rather than leaves of the signature — every vote for a position must agree, every position needs one, and the names of different positions must be distinct (by-name lifting would otherwise feed one binding to independent positions: `P(a, 0)` / `P(0, a)` is not `P(a, a)`). A family whose clauses fail any of these has NO lifting signature and no name is ever invented: it stays explicitly callable, and an INFERRING formula that would lift it is the front-end error `DiagnosticCode.UnliftableClauseFamily` at the reference, naming the position and why (`S(1) = 1` / `S(-1) = -1` / `G = S + 0`). A closed list or branch pattern forwards only same-named existing bindings (PAR-04) and such a family names nothing, so there the reference keeps its ordinary zero-argument demand and runtime check, like every blocked reference. Diagnostic reasons cached by callable identity contain no occurrence name: `UnliftableClauseFamily` names the current reference, including when several bindings share one family AST. Each unliftable-family reference reports once per rewrite region, using reference identity independently of rewrite sharing. A reference to nothing static — a parameter, an unresolved name, an ambiguous open, a runtime receiver's member — has no lifting signature.

**Everything else is unchanged, and composes with the law.** Q-03: a callable whose signature accepts zero supplied arguments is never lifted, whatever its category — it is read through the cache. Q-04: forwarding reuses existing parameter bindings by name; a property, an opened name or a builtin is never forwarded as a SOURCE (the law widens which CALLEES lift, never what supplies them). PAR-04: closed lists gain no forwarded name. Model-C Q-15 leaves every blocked reference as an ordinary runtime zero-argument demand, including Math; an unused argument or unselected branch never reaches it. Directly written undeclared names remain front-end errors. No strict-value diagnostic observation or lazy-depth replay remains. PAR-05: first-occurrence order, one parameter per binding name. X-02: the composed signature must be one a programmer could write (next section). FWD-02: a body whose ONE row is the bare callee is a callable alias or bare forwarding, never a formula — and since aliases became binding indirection (October 1 2026) its eligibility is identity-keyed like lifting: a builtin, a host operation, an opened or dotted member and a clause family are alias targets like every parameterized callable, so `C = count` is a callable alias of `count` while the formula `C = count + 0` is `C(collection)`. THE ROOT CLAUSE: a bare ROOT output row naming a callable that requires supplied arguments is never lifted into the never-called root, whatever the callable's category, so evaluation reports that callable's own zero-argument rejection at the reference (`abs`, `Math.Random`, `count`, `Lib.Inc` and a family alone at the root are their own arity or branch errors; formerly the two Math spellings lifted there and reported the root's `UnresolvedImplicitParams`), while a root FORMULA lifts like any other (`abs + 0` needs the root's `x`). The clause keeps the ROW unlifted, never a block written in it: in `{ public K = if(true, 5, Inc) ⏎ 0 }.K` the block is a body of its own, elaborated like every other (`K` lifts to `K(x)`), and only the row stays `K`'s own zero-argument demand — the named-holder law: `{ M }.K` at the root behaves exactly like `Lib = { M }` followed by `Lib.K`, with the same front-end codes, the same evaluation outcome and the same callable blamed (S-10 F1: the block was formerly left unelaborated, so such a row could print a value, blame an inner callee, or lose a front-end error; `RootRowBlockHeadTests`, the `root-row-block-head-*` spec cases).

**Every read sees a FINAL signature.** Lifting reads the selected signature of what a reference resolves to, decided for every open body of the operation before anything is rewritten, so no read waits on, orders or processes another body (§ Signature selection, next section).

**The calls lifting writes count toward the structural ceiling** (2026-11-26). A lifted reference becomes a call whose argument rebuilds each structural parameter pattern of its callee, two units per pattern level at the reference (bare forwarding writes the same call), so a shallow formula naming a callee with a deep pattern elaborates to a deep tree: with a 148-level pattern in `F`, `G = F + 0` passes the written-tree gate and elaborates past `EvaluationLimits.MaxSupportedAstDepth`, whether or not `G` is ever called. The front end's elaboration gate judges the elaborated tree, so such a program is `AstDepthLimitExceeded` at the reference, at parse time ([`evaluator-and-hosting.md` § Structural depth and parser budgets], `ElaboratedTreeDepthGateTests`). The written call `G(t) = F(t) + 0` passes the structure whole as one argument and stays shallow.

Consequences, all pinned: `Total = count + 0` is `Total(collection) = count(collection) + 0`; `Next = Lib.Inc + 0` and `{ open Lib ⏎ Inc + 0 }` take `x`; `Fam = E + 1` with `E(0) = 100` / `E(n) = n` is `Fam(n) = E(n) + 1`; `G = if + 0` is `G(condition, whenTrue, whenFalse)`, `G = repeat + 0` is `G(step, count)` (META-S3-3: the lifted `step` is an ordinary binding that transports its cell into `repeat`'s META slot, CR-1), and a host `trace(x)` makes `G = trace + 0` take `x`; `[Inc, Inc * 2]`, `(Inc, 0)`, `Inc.string`, `Inc.count`, `take([1, 2, 3], Inc)`, `abs(Inc)` and `E(Inc)` lift, while `Apply(Inc)`, `map([1, 2], Inc)`, `repeat(Inc(0), 2)` and `f(Inc)` keep `Inc`; `G = if(c, 1, Bad)` is `G(c, x)` and still evaluates `Bad` only when `c` is false; a formula's lifted calls evaluate, charge, draw random numbers and call host operations exactly as the explicit calls it abbreviates, and extracting a helper formula (`H = F + 1`, `G = H * 2`) agrees with inlining it (`G = (F + 1) * 2`). Formerly builtin value slots, capture elements, nested argument expressions and the `.string` receiver were not lifting positions (Q-11), and builtins, host operations, opened and dotted members (Q-12) and clause families (Q-13) never lifted, so extracting or inlining a helper formula could change a program's signature; the runtime zero-argument demand of such positions is now pinned under a closed list (`Probe(u) = if(true, Inc, 0)`).

## Signature selection (B3-5★, November 2026; owner direction 2026-11-05: X-04 = plain A-agree with R1 origins, CG4 = A-agree)

**Summary.** The rules of this section in dense form, with their implementation anchors and pinning tests; the full statement follows.

- B3-5★ SIGNATURE SELECTION (November 2026; owner direction 2026-11-05: X-04 = plain A-agree with R1 origins, CG4 = A-agree): implicit-argument resolution has two phases. ANALYSIS records one equation per written open body per declaring context (D1a) through the ONE formula-lifting role walk (`WalkLiftingRoles`) and the static callable identity (`ResolveStaticCallable`: every reference row followed to its Q3 endpoint); SELECTION (`SignatureSelector`, rule G6) decides every inferred signature — and through it every `.Algorithm` link's class, a calculation exactly when its signature is nonempty — JOINTLY: a cyclic component by the closed gate, then simultaneous rounds from it until the full ordered signature state stabilizes (no uniqueness search, no withdrawal refusal), three-valued groundedness, a dependency-first local pass, then joint regions over dependency cones (components, and the classification search that finds a table's rows without reading every vector, are optimizations only); the REWRITE then processes declarations in their elaborated order over the selected signatures and never recomposes one or collects its lifted dependencies again (`SelectedLifting`; `RequireSelectedComposition` checks by reference that the rewritten rows lift exactly the composed callees, each callee's first lift in the composed order with the composed signature, from the rewrite's own role-walk-ordered lift log `OpenBodyLiftLog`), and every body the analysis recorded must have been rewritten (THE REACH INVARIANT, `RequireEveryAnalyzedBodyRewritten`). No read observes a provisional signature, so declaration order is unobservable (only the ORDER of diagnostics follows the rewrite's traversal); there is no processing order, sibling-order channel, on-demand processing or demand budget. A group without a unique grounded answer is refused on A1's recovery route as `SelfDependentInferredParameters`, worded by its category: a recursive inference that does not settle (a repeated state with period above one; `F = if(c, x, F + 1)` completes as `F(x)`), two grounded readings, none, only self-supporting ones, or an undetermined (U1) one; a reader of a refused group is not reported again. Selection work and storage are charged to the static ledger (exhaustion is `StaticStructureLimitExceeded`, never an inference rule). Every capture records a determined origin or one generated cycle origin (R1, carried by the capture record, never a side table; a descriptor is never reported as a source declaration; it can name a group with no source, when a callee stopped lifting during the rounds). X-02 validity is judged on the settled state: a flag a later round clears refuses nothing, and a flag the settled state keeps is the definition's error. `RecursiveParameterInferenceTests`, `CycleOriginConsumerTests`, `RecursiveInferenceLifecycleTests`, `RecursiveOriginOracleTests`, `SignatureSelectionTests`, `SignatureSelectionReviewRegressionTests` (the independent whole-system G6 oracle), `SiblingDependencyCycleTests`. Lifting reads the FINAL signature of what a reference resolves to, and an open body's final signature can depend on other open bodies' — so implicit-argument resolution decides every inferred signature of an operation BEFORE it rewrites anything, and no read ever observes a provisional one. It has two phases. The ANALYSIS walks exactly what the rewrite will walk (`ImplicitArgumentResolver.SignatureAnalysis.cs`; enforced by THE REACH INVARIANT, `RequireEveryAnalyzedBodyRewritten`: when the resolution completes, every body the analysis recorded has been rewritten or served from another context's processing, else an internal failure — S-10 F1 was a block in a preserved root row that the analysis recorded and the rewrite skipped) and records one EQUATION per written open body per declaring context (D1a: a nested helper's reads belong to the helper, never to its owner) — the body's own patterns and its value-role references in written order, each with its static callee identity (`ResolveStaticCallable`: every reference row followed to its Q3 endpoint, so an alias and its target are one callee) and, for a read a link's class decides, that `.Algorithm` link as its GUARD — and it writes nothing the rewrite reads. The SELECTION (`SignatureSelector`, rule G6, `SignatureSelection.cs`) then decides every equation's signature JOINTLY, and through it every link's class (a calculation exactly when its selected signature is nonempty, META-S3-2): under a classification of the links, the active reads are evaluated dependency-first (Φ_B); a cyclic component is evaluated with every member read as declaring nothing — the CLOSED GATE — and when no read inside the cycle then lifts, that is the cycle's one non-lifting meaning, otherwise the cycle is a GENUINE LIFTING CYCLE, completed SIMULTANEOUSLY (§ Recursive parameter inference below); a cycle that does not settle has no meaning, nor has any body that reads it; a classification is consistent when every link evaluates to its class and every body has a meaning, and grounded when every nonempty set of its calculation links is refuted (three-valued: a counterfactual without meaning is undetermined, U1). The unique grounded consistent classification is selected; otherwise the group is REFUSED on A1's recovery route as `DiagnosticCode.SelfDependentInferredParameters`, at each body that failed on its own and worded by its category — a recursive inference that does not settle, two grounded readings, none, only self-supporting readings, or an undetermined one — while a body that failed only because it reads a refused group is not reported again. The REWRITE then processes declarations in their elaborated order over the selected signatures and never recomposes one (`SelectedLifting`; `RequireSelectedComposition` checks, by reference and in O(recorded rewrite DAG + dependencies), that the rewritten rows lift exactly the callees the composition read, each callee's first lift in the composed order with the composed signature — a difference is an internal defect, never a program's error).

There is no processing order, sibling-order channel, on-demand processing, demand-depth budget or soft preference any more; formerly the resolver processed a level's properties in dependency order and a sibling cycle — or a read no channel edge ordered — kept declaration order observable (its tests were deleted with that machinery). A component's table is found by the CLASSIFICATION SEARCH (`ClassificationSearch`, an optimization too): one reading per partial classification, split only where it consults a class that its own facts do not already force, so the rows are exactly those of evaluating every classification while a ring of n links costs 4n − 5 states for n ≥ 2 instead of 2^(n+1) − 1, and references to callees that cannot lift are classified once per table; 2^62 or more classifications of one table stay refused by the fixed limit. A later unit inherits the projections a unit made before sealing; what a sealed table projects afterwards is its readers' cache, neither inherited nor charged. ## Recursive parameter inference (X-04 plain A-agree, R1 origins; owner direction 2026-11-05)

THE PRINCIPLE: **implicit parameter inference uses the same signature-composition rules for ordinary and recursive dependencies. Recursive groups are completed simultaneously from their initial known facts. When the full ordered signature state stabilizes, the reached signatures define the result.**

1. **One composition law.** A member's signature is composed exactly as any open body's: own parameters first, then lifted callees in written reference order, with the existing duplicate precedence, alias-endpoint deduplication, Q-04 filtering, group shapes, grouped-collector forwarding, META lifting and X-02 recovery. Cyclic completion adds no second law.
2. **Defined initialization.** Round one is the closed gate: reads inside the component see no parameter, while own patterns and every fixed lower or external fact are included. A closed gate that lifts nothing is the answer.
3. **Simultaneous rounds.** Otherwise every member is recomposed from the PRECEDING round's facts, never from a partly updated neighbour. Lower and external facts stay fixed during one component's rounds.
4. **The reached result is authoritative.** Rounds stop when two successive rounds have the same full ordered structural state: every member's pattern tree (kinds, grouping, names, order) and its X-02 flag. Another structural fixed point of the same equations creates no ambiguity by itself, and a parameter or requirement that appears and later disappears during the rounds refuses nothing. Competing `.Algorithm` classifications still go through rule G6, which sees one reading per vector.
5. **Order invariance.** Processing order, declaration order that preserves bindings, allocation identity and scheduling select nothing. WRITTEN REFERENCE ORDER stays meaningful, because the composition law gives it meaning: `A = if(tick() > 3, x + y, B + 1)` / `B = A + z` is `A(x, y, z)` and `B(z, x, y)`.
6. **Precise failures.** A state that repeats an earlier one with period greater than one proves the group does not settle; it is refused as `SelfDependentInferredParameters`, worded as a recursive inference that does not settle. Exhausting the static ledger is `StaticStructureLimitExceeded` and cancellation is the operation's cancellation; neither is ever reported as non-settling. Inference never evaluates a user expression, `tick()`, a callback or any runtime effect.
7. **Written lists are authoritative.** A written parameter list is final as written; rounds never change it, and it remains the way to choose an order the rounds did not reach.
8. **Faithful origins (R1).** Every capture records where it came from. Follow the FIRST PROVIDER of its name: an own capture or a fixed callee's record determines the origin, and a chain inherits its end. A chain that closes on itself has no derivable single origin, and no invariant rule can invent one (the rotation `A = B + P` / `B = A + Q` is its own image when `A`,`B` and `P`,`Q` are swapped), so its nodes, and every node whose chain enters it, share ONE GENERATED CYCLE ORIGIN: the cycle's members, named within the innermost body declaring them all, and the source origins reachable from it through every active, lifted, non-inert provider. One such source collapses to that source; an earlier cycle origin contributes its own sources; none at all is possible, and then the origin names the group alone. Origins describe the FINAL provider graph, not the history of the rounds: a callee can bring a name into a cycle and then stop lifting, for example when an enclosing binding filters its callee down to a lone collector, which accepts zero arguments. The members keep the name from each other, because the settled state is authoritative, and the callee that first brought it is no longer a provider. Such a group has a shared origin with no source: it is not a missing origin, and no source is invented for it. A reader and a later unit inherit it unchanged. The cycle origin is a set: rendering order means nothing, and it is never reported as a source declaration.
9. **Validity belongs to the settled state.** The law of the next section, that an inferred signature must be one a programmer could write, judges the COMPLETED signature. A round is a step of the computation: when its composition breaks the rule, its fact is the recovered list with the X-02 flag set, the next round reads that list, and the flag compares as part of the state. A flag a later round clears refuses nothing, and the settled list has passed the same validator as a written head. A flag the settled state keeps is the definition's front-end error, and the program never runs. There is no refusal of an intermediate state and no weaker validator for a settled one.

The promise is limited on purpose. Not every recursive program is accepted. Completing a signature evaluates nothing, so a completed recursion can still fail or run forever when used. A completed answer need not be the only structural fixed point: `E(e) = e * 10` / `F = if(tick() > 2, 0, F + G + E)` / `G = p + F + 0` / `F(1, 2)` reaches `F(e, p)` and 24, while the equally consistent written `F(p, e) = …` gives 42. Rounds are bounded by the static ledger, not by a language-wide polynomial law.

Completed examples: `F = if(tick() > 3, x, F + 1)` / `F(10)` is `F(x)` and 13; `A = if(tick() > 3, x, B + 1)` / `B = A + 1` / `A(10)` is 16 in both orders; `A = if(x <= 0, 0, B)` / `B = if(x <= 0, A, A(x - 1)) + 1` / `A(3)` is 3. Oscillation is refused: `X(x) = x` / `Y(y) = y` / `A = B + X` / `B = A + Y` alternates between two orders. CG4 stays a contradiction: no coinductive reading is added.

Written reference order also decides validity. With `C1(a, *p) = a` and `C2(b, *q) = b`, `A = if(tick() > 2, 0, B + C1 + C2)` / `B = A + 0` is valid: `A`'s first round breaks the collector rule, `B` picks up the recovered list, and reading `B` first gives `A` a plain `q` before `C2`'s `*q` arrives, so the settled `A(a, *p, b, q)` is writable and `A(1, 2, 3, 4, 5)` is 10, as it is when that list is written out. `A = if(tick() > 2, 0, C1 + C2 + B)` rebuilds both collectors in every round, so it settles with the violation and is the definition's `InvalidCollectingBinding`. Rounds and complete witnesses: `static-structure-resolver-2026-10.md` § 10.1.

**Compatibility consequence (C2 accepted 2026-11-05).** Previously accepted code can be refused when recursive inference makes an additional `.Algorithm` alias classification meaningful: in the C2 fixture, `N = o + L2.repeat(N)` excluded one reading under B but now completes as `N(o)`, leaving two grounded readings. The compiler reports `SelfDependentInferredParameters` with the ambiguity wording rather than choosing one. Writing `K(p) = L2.repeat(Cq) + P` and `M(p) = L1.repeat(Cq) + P` makes the complete fixture compile cleanly; writing only N's list does not. This witness is not a characterization of every compatibility break or a rarity theorem. Agreement on facts B defined, wherever both rules accept, does not guarantee whole-program acceptance. The exact tested fixtures, evidence and separate owner decision are recorded in `artifacts/validation/a-agree-r1-production/c2-closeout/decision.md`; the owner explicitly accepted this consequence on 2026-11-05, closing C2 acknowledgment, with rootless origins, intermediate collector recovery and release authorization excluded.

**Mechanism.** `SignatureSelector.Complete` runs the rounds and `ImplicitArgumentResolver.SealCompletion` (`ImplicitArgumentResolver.CycleOrigins.cs`) prepares each completed component inside the selection: it builds final pattern lists from the first-provider law and recomposes every member from those FINAL lists, checking structure and origin content, so the rewrite's by-reference `RequireSelectedComposition` holds. The carrier is the capture record (FE-3): a determined capture holds its origin's record, or a view of it with `ParameterDeclaration.OriginalDeclaration` when the kinds differ (a META source stays an ordinary capture, a recovered collector stays plain), and a cycle capture is a generated record whose `ImplicitParameterProvenance.CycleOrigin` holds the members and sources, so a single-origin accessor cannot pick a root. Shared templates intern by exact record, so two owners with different origins never share a list. No side table exists: origins reach the tree only through the operation's existing publication, so cancellation, refusal or exhaustion publishes none. Diagnostics read notes (`ImplicitParameterProvenance.CollectFrom`), and editors read `PropertyParameterInfo.OriginSpans` and `HasSharedCycleOrigin`. Those two are read together: `HasSharedCycleOrigin` with empty `OriginSpans` is a recorded group whose sources have no location here or that has none, which reports distinguish by naming the sources or by saying that no source declaration supplies the name.

The witness: `C1(a, *p) = a` / `C2(b, *q) = b` / `K = C1 + C2` would infer `K(a, *p, b, *q)` — two distinct collectors at one level, which no parser accepts. The same rule holds across every category the unified law lifts. No builtin collects since META-S3-3, so a loop adds no collector: `K = while + repeat` is `K(step, count)`, and `C1 + while` is the valid `K(a, *p, step)`. Recovery is the parser's for a written head — the first collector of each level stays and a later one becomes fixed (`ParameterPattern.KeepFirstCollectingCapturePerLevel`) — so the recovered tree carries only valid signatures and the editor model builds. A deferred module region's provisional body is judged when it materializes, not by the evaluator gate at the start of the run (a name its module supplies reads as undeclared there — evaluator-and-hosting.md § Source loading and deferred modules). ## Whole-algorithm transport: transparent references and forwarding carriers (M4★, ALIAS-UNIFY-1, October 2026)

**Summary.** The rules of this section in dense form, with their implementation anchors and pinning tests; the full statement follows.

* **Classification** (`ImplicitArgumentResolver.TryCompleteLoneCalleeRow`, after inference; `RuntimeAliasRow` for runtime rows). * **Structural forwarding carrier.** Its STRUCTURE is its own — its declaration, its declaring activation, its own declarations as its ONLY members (no inheritance: `D = { B }` / `D.Q` takes the ordinary miss route — the extension fallback where a lexical name is visible, otherwise its existing inference or error), its own public declarations for `open`. An own-member hit never resolves or executes the unused forwarding target. THE RULES (decided September 29–30 2026; aliases as BINDING INDIRECTION decided October 1 2026, superseding the exact-alias wrapper; FWD-02 owns them). **A body whose ONE written row is a bare reference is a CALLABLE ALIAS when its body is open — since M4★ whatever the target's arity, a zero-parameter target included (§ Whole-algorithm transport) — and BARE FORWARDING when its parameter list is written and the target declares parameterized callable structure: an alias is a second name for the target's callable itself; bare forwarding reuses already-existing compatible bindings BY NAME — it never renames a binding, never adds one to the closed list, never matches by position, and never converts an incompatible top-level parameter pattern because nested leaf names coincide. An explicit call means exactly what is written. Formula lifting is a separate, by-name inference mechanism.** Six forms are distinguished by what is written, never by compiler internals:

| You write | Meaning |
|---|---|
| `A = F` | a CALLABLE ALIAS of `F`: `A`'s callable IS `F`'s (since M4★ a transparent reference: every observation is `F`'s) |
| `A(p) = F` | BARE FORWARDING: reuse `A`'s existing compatible binding named `p` for `F`'s parameter `p`; infer nothing, rename nothing |
| `A(p) = F(p)` | an EXPLICIT CALL: the written arguments; the caller's and the callee's parameter names need not match |
| `A = F(p)` | a FORMULA whose parameter `p` is the free name written in it |
| `A = F + 1` | FORMULA LIFTING: `F`'s required parameter names become `A`'s inferred parameters, by name |
| `A(p) = F + 1` | a formula under a CLOSED list: it may use existing bindings (its own `p`, Q-04's enclosing ones), never add one |

**Do not equate `A(p) = F` with `A(p) = F(p)`.** With `Sub(y, x) = y - x`, `G(x, y) = Sub` hands G's `y` to Sub's `y` and G's `x` to Sub's `x`, so `G(10, 3)` is -7, while `G(x, y) = Sub(x, y)` passes its arguments in the written order and gives 7. The two agree only when the names do.

* **An existing binding is forwarded unchanged.** A fixed binding is supplied as its whole value — never opened, never wrapped — and a collecting binding that is re-spread supplies exactly its collected items: in bare forwarding and a formula when BOTH the destination capture and the SOURCE binding collect (FWD-02's source-kind rule). ## Grace (F10, Q-16 G-O)

**Summary.** The rules of this section in dense form, with their implementation anchors and pinning tests; the full statement follows.

- Grace `~` is a front-end parameter-order annotation on exactly one DIRECTLY attached bare-name occurrence (`~x` / `x~`; a detached marker is `InvalidGraceMarker` recovering to the plain name; attached runs use ordinary weight arithmetic), stripped before evaluation. GRACE IS OWNER-LOCAL AND REQUIRES AN OWN INFERRED PARAMETER (F10; Q-16 G-O, decided 2026-10-07): a marker belongs to the innermost algorithm owner — the root, a property body, a brace block in any position, a clause-branch body — whose written rows (`AstHelpers.WrittenRows`: output rows and hoisted deconstruction right-hand sides) contain the occurrence, and it is valid exactly when that occurrence becomes one of the owner's OWN inferred parameters. Eligibility, never movement (Q-16(1) E): a saturated marker — a single own parameter, a name already at its boundary, excess weight, a tie, a cancelled weight, the own/lifted boundary (`A = p - q` / `F = A - z~` is `F(z, p, q)`) — is valid; a FIXED binding (an explicit parameter or clause binder, a captured parameter, a visible property, a builtin, an opened name, a structural dot member, `.string`) has no inferred parameter to weight and is `DiagnosticCode.InvalidGraceMarker`, as is every marker on a CLOSED level (an explicit parameter list; a clause branch's own rows, deconstruction right-hand sides included, PV-49). A branch is closed at its OWN level only (Q-16(2) O): an algorithm nested in it is an ordinary owner with its own Grace in every spelling (`F(0) = Apply({ y - ~x })` ≡ the named `B = y - ~x`), never adding a parameter to the branch, and a branch binder it captures is an enclosing parameter. The ONE authority is the parameter detector's per-owner rewrite pass (`ParameterDetector.ReportIneffectiveGrace`, policies `ImplicitSignature` / `ClosedExplicitList` / `ClosedBranch`, once per occurrence per region); the parser keeps Grace SYNTAX only (attachment, one bare name, compound operands, clause-head patterns, open targets), so a load-bearing branch's own-level verdict comes when that deferred unit is selected (MOD-10). GRACE MOVEMENT (X-49, decided 2026-10-08; `GraceMovement`, applied by Q7 alone, `StaticStructureQueries.Inputs`, which sums the weights with each shared node's exact occurrence multiplicity — detection's free-name walk sums none): each marker requests one adjacent exchange; every name with postfix (positive) weight takes ONE turn, from the last-occurring, THEN every name with prefix (negative) weight, from the first-occurring (the turn order comes from first-occurrence identities and initial weights); a mover passes its neighbour unless that neighbour moves the same way with at least as much REMAINING weight (strict, current weights, compared before the step), a passed name keeps its weight, weight a name cannot use at an end or a block STAYS and keeps blocking, and weights are exact unbounded integers (`System.Numerics.BigInteger`; no saturation); no name crosses the own/lifted boundary. So `K = s * 100 + ~x * 10 + ~y` is `K(x, y, s)`, `Z = s~ * 100 + x~ * 10 + y` is `Z(y, s, x)`, `K = a * 100 + b~ * 10 + ~~c` is `K(c, a, b)`, `K = a~ * 100 + b * 10 + ~c` is `K(b, c, a)` and `F = ~a * 100 + b * 10 + ~~c` is `F(a, c, b)`. A graced name inside redundant parentheses is the graced name (`(~a).V` is `~a.V`, `(~a)(b)` is `~a(b)`): the group is erased whatever the marker's weight, so Grace can never change selection. `GraceOwnershipSemanticsTests`, `GraceEffectivenessTests`, `GraceMovementLawTests`, `lean/CoreTests/GraceMovement.lean` (a standalone model; no evaluator change), the `grace-*` spec cases. [`ownership-and-lookup.md` § Grace]
- Grace composes with ordinary dot syntax: `a~.t(args)` is postfix Grace on the bare receiver occurrence followed by ordinary `.t`, while `a.~t(args)` is ordinary dot with prefix Grace on the participating fallback/member occurrence `t`. Base DotCall occurrence order is receiver, participating fallback, then arguments, so `a.t` infers `(a, t)` and both graced two-name forms infer `(t, a)` through the ONE general Grace reordering law. Postfix Grace on a compound receiver (including a second `~.` in a chain) rejects through the one-name eligibility rule; prefix member Grace remains eligible because it decorates the bare member occurrence. Parameter detection consumes Grace, all forms elaborate to the SAME ordinary structural-first `DotCall`, and Grace never changes executable selection.
- Implicit-parameter order: a level's OWN inferred names follow first semantic source occurrence plus the ordinary Grace arithmetic (Grace reorders only this own-name list), and the names formula lifting forwards to its callees FOLLOW them, never interleaved (PAR-05: `A = x - y` / `F = A - z` infers `F(z, x, y)`). A DotCall contributes its receiver occurrences, then its member's stored lexical-fallback occurrence when fallback MAY be selected, then written argument occurrences; thus `K = a.t(b)` infers `(a, t, b)`, while the direct call `K = t(a)` independently infers `(t, a)`. Grace `~` is a front-end parameter-order annotation on exactly one bare name occurrence (`~x` / `x~`), written DIRECTLY attached to that name (marker attachment law: `~ x` and `x ~` are `InvalidGraceMarker` attachment errors that recover to the plain name with no weight; `~~x` and `~x~` are attached runs); it is not a general expression operator, the markers on that occurrence — and on repeated occurrences of one name in one owner — add up as ordinary weights, and elaboration strips it before evaluation.

GRACE IS OWNER-LOCAL AND REQUIRES AN OWN INFERRED PARAMETER (Q-16 G-O, decided 2026-10-07; F10). Grace belongs to its OWNER: the innermost algorithm-level scope — the root, a property body, a brace block in any expression position, a clause-branch body — whose written rows (`AstHelpers.WrittenRows`: output rows and hoisted deconstruction right-hand sides, through every transparent construct) contain the marked occurrence. A nested brace block or property is an owner of its own whatever encloses it, and deconstruction hoisting never moves an occurrence to another owner. SATURATION IS NEVER AN ERROR (Q-16(1) E: eligibility, not movement): a single own inferred parameter (`F = ~x + 1`), a name already at the boundary it points to, excess weight, a neighbour moving the same way with at least as much remaining weight, a cancelled weight (`~x~`; `~x` with `x~`) and the own/lifted boundary (`A = p - q` / `F = A - z~` infers `F(z, p, q)`) are valid, and a cancelled marker is still validated for its binding. Grace never changes resolution, selection, values, callability or evaluation. The ORDER is the movement law below. A graced name inside REDUNDANT PARENTHESES is the graced name (PARENTHESES GROUP SYNTAX, September 2026): `(~a).V` is `~a.V` — the ordinary structural-first dot edge on `a` with `a` moved earlier, so a bound algorithm's own `V` is read and a number falls back to the lexical `V` exactly as `a.V` and `(a).V` do — and `(~a)(b)` is the call `~a(b)`; the parser's `IsRedundantGrouping` never looks at the inner kind, so the group is erased whatever the marker's weight and Grace can never change selection (`OutputBundleSplitTests`, the `grace-in-redundant-group-is-grace-on-the-name` spec case).

GRACE MOVEMENT (X-49, decided 2026-10-08; `GraceMovement`, applied by Q7, `StaticStructureQueries.Inputs`, once per inferring owner, whose signature the detector takes). The owner's OWN inferred names start in first semantic occurrence (PAR-05), each with its exact summed weight as its REMAINING weight: prefix −1 and postfix +1 per marker, summed over every eligible occurrence, opposite markers cancelling before anything moves, as unbounded integers (`System.Numerics.BigInteger` — never an int saturation, wrap or clamp; Q7 counts a shared node with its exact occurrence multiplicity, so a shared subtree weighs what its duplicated tree weighs; the detector's free-name walk sums no weight). Movement runs in exactly two passes, with the schedule fixed by the first-occurrence identities and their INITIAL weights — never by current positions, spellings or dictionary order: (1) every name with a POSITIVE weight takes one turn, from the LAST-occurring to the first-occurring; (2) then every name with a NEGATIVE weight, from the FIRST-occurring to the last-occurring; a zero-weight name takes no turn. In its turn a name requests one adjacent exchange per unit — with the next name for a positive weight, the previous for a negative one — and each exchange moves its remaining weight one unit toward zero. A step is impossible, and the turn ends, at the end of the own list or when the neighbour moves the same way with at least as much REMAINING weight — rightward `remaining(q) >= remaining(p)`, leftward `remaining(q) <= remaining(p)` — compared on CURRENT remaining weights before the step (the patent's strict comparison); an unmarked neighbour or one moving the other way never blocks. A passed name keeps its remaining weight. Weight a name cannot use — at an end or against such a neighbour — STAYS with it and keeps blocking later movers that push the same way no harder: `F = ~a * 100 + b * 10 + ~~c` is `F(a, c, b)` (a keeps −1 at the front; c passes b and then cannot pass a, whose remaining weight equals its own), and `SumOfParams = a~~ + b~` is `SumOfParams(b, a)`. The forwarded tail is appended afterwards (PAR-05, PAR-07), so no name crosses the own/lifted boundary. Each turn makes at most n − 1 exchanges, so at most n(n − 1) in all whatever the weights. Why this order: running rightward movers first and from the end, then leftward movers from the front, means the mover nearer its destination moves first, so no movement is lost because a same-direction blocker had not moved yet; a rightward and a leftward mover can only meet when the rightward one is written first, so the passes resolve every meeting in source order. An equivalent reading, used only to explain and to cross-check (equal on the investigation's 208,196 states, not proved): turns in first-occurrence order, where a mover blocked by a same-direction neighbour that has not moved yet lets it move first. Examples: `K = s * 100 + ~x * 10 + ~y` is `K(x, y, s)`; `Z = s~ * 100 + x~ * 10 + y` is `Z(y, s, x)`; `K = a * 100 + b~ * 10 + ~~c` is `K(c, a, b)`, as without `b~` (before X-49 a position cursor skipped the displaced `c` and gave `K(a, c, b)`); `K = a~ * 100 + b * 10 + ~c` is `K(b, c, a)` (prefix-first movement would give `(c, a, b)`); `K = ~a * 100 + ~b * 10 + c` is `K(a, b, c)`; `K = a~ * 1000 + b~ * 100 + c~ * 10 + d` is `K(d, a, b, c)`; `K = a * 1000 + ~b * 100 + ~c * 10 + ~d` is `K(b, c, d, a)`; `K = a + b~ + c~ + d~ + ~e` is `K(e, a, b, c, d)`. GUARANTEED: first-occurrence order without effective markers; a lone marked name moves exactly its weight, stopping at the end; own-direction monotonicity (one more postfix marker never moves a name earlier, one more prefix marker never later, and the name never overtakes in the wrong direction a name it was behind); equal accumulated weights keep their first-occurrence relative order; every marked name takes its turn, and every leftover is held by an end or a same-direction neighbour with at least as much remaining weight; a contiguous equal-weight run moves as a unit in either direction when every parameter outside that run has zero weight; prefix-only markings (one per earlier-written name that must end up after it) and postfix-only markings (one per later-written name that must end up before it) give exactly the intended order; saturation is never an error; the order depends only on own first-occurrence positions and total weights, in every owner and spelling. NOT guaranteed: contiguity of an equal-weight run when other parameters also move (`K = a~ * 1000 + b~ * 100 + ~c * 10 + ~d` takes `(c, a, d, b)` and `K(1, 2, 3, 4)` is `2413`; both `(a, b)` and `(c, d)` are split); mirror symmetry (`a + b~ + ~c` is `(c, a, b)`, `c~ + ~b + a` is `(b, c, a)`); independence (a marker on one name may change how two others end up); displacement bounded by a name's own markers (others may carry it, as `e` above); a move never undone (a strictly stronger same-direction mover may pass it back: `a + ~b + ~~c` is `(c, b, a)`); "desired position minus written position" as a recipe. Equal accumulated weights preserve their original relative order. A contiguous equal-weight run moves as a unit when every parameter outside that run has zero weight. Other moving parameters can split the run while preserving its relative order. `GraceMovementLawTests` (the canonical examples on six routes, the patent's FIG. 6, 7, 9–12 and 14, every state of 1–5 names with weights −3…3 against an independent oracle, monotonicity, equal weights, final-state blocking, groups, recipes, residual weights, aggregation, exact large weights and shared DAGs, owners, lifted tails, renaming, explicit-list twins), `lean/CoreTests/GraceMovement.lean` (a standalone model whose `#guard` table the C# suite also checks), the `grace-front-first-movement` spec case.

## Parameter channels and shadowing

**Summary.** The rules of this section in dense form, with their implementation anchors and pinning tests; the full statement follows.

- A user call binds each parameter on the value channel, the algorithm channel, or both, and the callee evaluates in the CALLER's environments extended with its own bindings; a BOUND PARAMETER OWNS ITS NAME ON EVERY CHANNEL — every binding site in both engines and the async twin shadows the callee's parameter names out of every inherited tier (the Model-C need-cell tier and the value tier; the algorithm-channel and counted tiers, which no production binding site wrote after Model C, were retired on 2026-10-13) through ONE helper (`ShadowInheritedParameterEnvironments` with `ShadowValEnv`; Lean `EvalCtx.bindParameters` with `ValEnv.shadow`), so a name read in value position demands its own supplied cell — a cell whose VALUE demand failed reports that failure, never a re-evaluation (`sequences-lists-and-calls.md` § At-most-once argument value evaluation) —, a name whose binding has no callable identity read in call position fails as not callable, and neither ever reaches a same-named caller binding. CAPTURED READS ARE LEXICAL-ONLY (EXPORTED-DETACHED, November 2026; Lean-first): a read of a parameter the head does not bind itself goes through the ACTIVATION of its lexical owner (the nearest enclosing level binding the name), and when that owner has no usable activation — a static owner reached by navigation from outside its call, or an activation DETACHED inside an exported evaluation — the name is lexically OWNED and UNAVAILABLE at the site, and EVERY EXECUTED OPERATION on the written occurrence is refused with the structured `UnknownName(name)` at that occurrence: its VALUE read, its CALLABLE projection and so a call through it (`y(5)` — never `NotAnAlgorithm`, which stays the report of an AVAILABLE value-only cell), and its direct TRANSPORT as a supplied argument, callee, link receiver, spread operand or alias row, which fails WHILE THE SUPPLY IS FORMED whether or not the receiver demands it (`Ignore(y)` with `Ignore(z) = 42` is refused; a computation that merely contains the parameter, `F(y + 1)`, stays a suspended cell; an available cell transports lazily); the inherited tiers are consulted only for a name NO lexical level binds (a builtin wrapper's argument, a host-built free parameter), so a wrong exposure flag or a host-built static owner can no longer read a dynamically live caller's binding (`H(y) = G.F(1)` formerly read `H`'s `y` from inside `G`). A probe that only SELECTS a binding never executes such an operation: the front-end promotion probe asks whether a name resolves, never whether its binding is callable (Lean `shouldTreatAsImplicitParam` over `lookupLexicalPropertyRaw`). No planned-loop exception exists: a fully planned round runs no generic evaluation under its unactivated head, and a partially planned round enters the step with a real activation (`DetachedPlannedLoopModeTests`) (`Evaluator.CapturedParameterActivation` with `ParameterActivation.IsUnavailable`, `UnboundParameter`, `ResolveNeedParameterAlgorithm`, `SupplyCell` with `NeedCell.Refused` reported by `FormNeedSupply`; Lean `capturedParameter`, whose lookup `capturedParameterActivation?` is the refusal; `KatLangArityLaws/DetachedEvaluation.lean`; `DetachedExportedEvaluationTests`, HP-18 of `HostParentDifferentialCorpus`). [`ownership-and-lookup.md` § Parameter channels and shadowing]

A bound name has one shared NeedCell carrying independent VALUE completion and optional CALLABLE identity. Every explicit call, callback, branch activation and loop step shadows that name on all inherited channels, and retained owner activations preserve captured parameter cells. A value read forces that cell; a call-position lookup projects its callable identity without VALUE evaluation. Transport preserves the exact address, original provenance and caller environment. Invoking the callable is fresh; it does not replace a completed VALUE success or failure. The older value environment remains only for already-produced data and supported host/optimizer contexts (the counted and algorithm-channel environments, which no production binding site wrote after Model C, were retired on 2026-10-13); new argument acquisition uses NeedEnv. See `call-by-need.md` NEED-06 and NEED-10.

CAPTURED READS ARE LEXICAL-ONLY (EXPORTED-DETACHED, November 2026; Lean-first). A read of a parameter the head does not bind itself finds its binding in ONE of three ways, decided by the reading context's lexical chain alone (Lean `capturedParameter`; C# `Evaluator.CapturedParameterActivation`):
* OWN — the head binds the name, or NO level of its lexical chain binds it (a builtin wrapper's argument, a host-built free parameter): the read uses the context's own tiers.
* ACTIVATION — the nearest enclosing level binding the name is activated, and that activation is not detached: the read uses its snapshot. This is the retained owner activation of the first paragraph.
* UNAVAILABLE — that level exists but has no activation (a STATIC owner, reached by navigation from outside its call), or its activation is DETACHED inside an exported evaluation — an enclosing call of the binding being evaluated, recorded before the evaluation started; the activation behind a callable another computation returned is not ([`evaluator-and-hosting.md` § Detached evaluation of exported properties]): the name is lexically OWNED and UNAVAILABLE at the site, and EVERY EXECUTED OPERATION on the written occurrence is refused with the structured `UnknownName(name)`, positioned at the occurrence (owner decision of the 2026-11-21 follow-up, superseding the first form of the rule, in which only the value read failed):
  * the VALUE read (`P = y * 10`);
  * the CALLABLE projection, and so a call through the name (`P = y(5) + 0`): the refusal names the parameter, never a missing callable capability — `NotAnAlgorithm` stays the report of an AVAILABLE cell that holds a value only;
  * the DIRECT TRANSPORT of the parameter as a supplied argument, a callee, an `.Algorithm` link's receiver, a spread operand or a transparent reference's row: the supply fails WHILE IT IS FORMED, whether or not the receiver would ever demand it (`P = Ignore(y) + 0` with `Ignore(z) = 42` is refused, where it formerly returned `42`). Only the parameter itself is transported; a computation that merely contains it (`F(y + 1)`) stays a suspended cell and is refused when it is demanded (call by need is unchanged);
  * the lookup of the cell the parameter would hold (the dot-only `string` intrinsic's receiver, a publication origin).

  The other two cases are untouched: an absent lexical owner keeps the context lookup on every channel, and an available cell transports lazily (nothing is demanded or allocated).

Formerly the third case read the context's INHERITED tiers — whatever a dynamically live caller had bound under the same name. That was dynamic scoping, reachable whenever a member was (wrongly) accessible outside its owner: with `G(y)` holding a member `F` that reads `y`, `H(y) = G.F(1)` computed with `H`'s `y`. It is now a refusal on every route, cached and uncached, synchronous and asynchronous, planned and generic; the inherited tiers are never read for a name whose lexical owner has no usable activation. No exception is needed for planned loops (the audit's context-binding marker for the planned iteration head is NOT implemented; owner decision of the 2026-11-21 follow-up made it conditional on evidence, which `DetachedPlannedLoopModeTests` gives for both modes): a FULLY planned round reads the frame's slots and the cells its planner found, and runs no generic evaluation under its unactivated head, so no captured parameter is ever looked up through it; a PARTIALLY planned round — one that evaluates a row generically — enters the step with its own activation every round; and the planner treats an unavailable parameter as unplannable (`ParameterNeedCell` finds no cell), which leaves the row to the generic evaluation inside the planned loop and its refusal. Host-built trees: a host level that lists a name among its `ScopeCtx.Parameters` is that name's lexical owner and is never activated, so a property that reads the name through it finds no binding (formerly it read its consumer's same-named binding; `HostParentDifferentialCorpus` HP-18c). A TRANSPARENT REFERENCE whose row is the parameter (`A = y`) owns no entry and no cell of its own — its binding cell IS the parameter's cell, found from the reading context — so a falsely exported one shares nothing across calls: read inside a call it is that call's parameter, and read from outside its owner it is the refusal above. THE FRONT-END PROMOTION PROBE asks whether a name RESOLVES, never whether the binding it selects is callable (Lean `shouldTreatAsImplicitParam` over the raw selection `lookupLexicalPropertyRaw`): chasing a parameter-row alias at a static site is the refusal of the ROW's parameter, which must not be read as "the probed name does not resolve". Lean `capturedParameter`, whose lookup `capturedParameterActivation?` is the refusal for `.unavailable`, read by `parameterContext`, `projectParameterWith`, `supplyNeed`, `parameterNeedAddress?`; laws `unavailable_lookup_refused`, `detached_param_read_refused`, `static_owner_read_refused`, `unavailable_transport_refused`, `unavailable_projection_refused`, `unavailable_cell_lookup_refused`, `unavailable_spread_refused`, `unavailable_alias_row_refused`, `own_transport_uses_the_context`, `available_transport_is_lazy`, `captured_read_is_lexical` (`KatLangArityLaws/DetachedEvaluation.lean`); C# `ParameterActivation.Unbound` / `UnboundDetached` (`IsUnavailable`), `Evaluator.UnboundParameter` / `UnavailableParameterRefusal`, `ResolveNeedParameterAlgorithm`, `SupplyCell` with `NeedCell.Refused` (reported by `FormNeedSupply`); `DetachedExportedEvaluationTests` (the callee and transport witnesses with their controls, positions and publication counts, on the optimized, generic and async routes), the HP-18l…u cases of `HostParentDifferentialCorpus` (against Lean), `FrontEndElaborationBoundaryTests`.
