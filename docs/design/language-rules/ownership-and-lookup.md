# Ownership, lookup, and binding rules

The full statement of the rules that AGENTS.md carries in compact form — consequences, examples, the implementation map, and the pinning tests — moved here verbatim from AGENTS.md in September 2026. These rules are as binding as AGENTS.md; the compact bullet there points at the section here. Keep both in step: a rule change edits the compact bullet and the section together.

## The resolution model in one place

Every layer — the evaluator (sync, async, planned), parameter detection, implicit-argument resolution and its sibling-order channel, exposure/dependency analysis, open validation, and the editor model — answers "what does this occurrence denote?" by the same ordered rules (name-resolution audit #8, September 2026):

1. **Owner walk.** Search outward by owning scope — the occurrence's body, each enclosing algorithm or branch body, the root, and the prelude as the outermost property level (builtins, `Math`, the Math aliases, and a run's host operations). At each level a PARAMETER binding (written, inferred, collecting, grouped, or a branch binder — never one that automatic parameter forwarding added, see § Automatic parameter forwarding preserves existing bindings) is asked before the level's PROPERTIES (any visibility); the first level that declares the name decides. A property may not share a name with a parameter of its own or an enclosing algorithm (declaration error), so the tie rule only matters in recovery trees.
2. **Opens, only after the whole walk.** If no level declares the name, the `open` providers are consulted level by level, innermost first; a level's named targets deduplicate first-occurrence-wins by their spelling (inline blocks never), each provides only its PUBLIC members, and the first level at which any target provides the name decides — one provider selects its member, two or more are `ambiguousOpen` and select NOTHING. An open therefore never overrides anything owned, a builtin or host operation included.
3. **Promotion, only after both.** A name nothing declares or provides becomes an implicit parameter of the innermost algorithm without a written parameter list; under a closed list or in a branch body it is an error.
4. **Structural first on dot edges.** `R.M` looks `M` up among the receiver's DECLARED members (any visibility) first, at every level of a chain; only a structural miss falls back to the lexical callable `M` of rule 1–3, as the ordinary call `M(R, args)`. A declared but inaccessible member is its own error, never a fallback.
5. **`open` is static.** A target's head is an ordinary occurrence (a parameter-owned head is an error, never a farther declaration); a target must resolve — head through the direct chain (never another open), dotted steps through public declared members — and must need no call.
6. **Identity decides, spelling never.** The selected declaration carries its identity to every consumer: value and algorithm positions are one decision projected onto two channels; builtin behavior (laziness of `if`, optimizer fusion, the Math value-demand contract) follows the resolved identity; a user `Alias = A` is a new declaration, while forwarding the same bound callable keeps its identity; accessibility is checked on the selected member afterwards and never changes the selection.

**Automatic parameter forwarding changes none of these answers** (Q-04, decided September 28 2026). It runs after the six rules have decided every written name, reuses the PARAMETER bindings they select to supply a lifted callee's inputs, and adds a parameter only for a name no parameter binding supplies — a forwarded parameter that no written name ever denotes. There is no second round of selection after forwarding.

The sections below state each rule in full.

## Ownership-first lookup

Ownership-first lookup is fundamental. Keep lookup behavior aligned across evaluator, parser/front-end elaboration, parameter detection, and semantic tooling. The evaluator's two lookup spellings — `LookupLexical` (reached by a bare name in VALUE position, `X`; returns owner+binding for the zero-arg property cache) and `LookupLexicalResolvedAlgorithm` (reached from ALGORITHM position: a callee `X()` or a dot-call target `X.m`) — are ONE implementation since M8+M9: the algorithm spelling is the projection of the binding-carrying chain (mirroring Lean, where `lookupLexical` projects `lookupLexicalProperty`), so ownership-first, open dedup, ambiguity, scope-level precedence, and prelude fallback exist once per engine; `LookupTwinEquivalenceTests` keeps both spellings observable so an independent fast path cannot silently regrow. Beyond that there are TWO C# lookup implementations — the evaluator's chain and `ElaboratedScopeLookup` (shared by `ParameterDetector` and `Semantics/`) — and they must select the SAME declaration, not merely both resolve: the detector's verdict rewrites the program (an unresolvable name becomes an implicit parameter), so a front-end disagreement changes what the evaluator runs. `LookupCoherenceTests` pins that relation with unique per-declaration sentinels; the `open`/visibility family in `SemanticExplorerCases.lean` pins the Lean/C# side. Named `open` targets deduplicate first-occurrence-wins by their COMPLETE spelling through `Evaluator.OpenTargetDedupKey`; bounded `Evaluator.OpenExprName` text is presentation only and never decides identity (inline blocks get positional keys and never dedup), so `open A, A` is ONE provider, not an ambiguity — that rule lives in Lean `resolveAllOpens` and must be mirrored by BOTH C# implementations.

## The owner walk

The OWNER WALK is the front-end half of ownership-first, and `ElaboratedScopeLookup.SelectOwnedDeclaration` is its ONE implementation (Lean: `selectOwnedDeclaration` / `elaboratesToParameter`, stated beside `shouldTreatAsImplicitParam` because `ScopeCtx` carries properties but no parameters): search outward by owning scope over the two kinds of OWNED declaration — the parameter bindings a scope binds (written, inferred, or a branch body's pattern binders) and the properties it declares — and the first owner that declares the name decides, a parameter beating a property of the SAME owner in an invalid recovery tree. Properties matching parameters of the same or any enclosing lexical algorithm are declaration errors, checked by `ParameterPropertyCollisionValidator` after automatic parameter forwarding, forwarded parameters included (Lean: `conflictingOwnedNames` / `validOwnedDeclarations`) — with ONE root exemption: the root program is never called, so its completed signature (names it could not resolve, or names forwarding lifted into it) is checked against the root's OWN declarations only and never blamed on a property nested in a deeper owner; such a name surfaces as the root's `UnresolvedImplicitParams` evaluation error, positioned at the first output row of the root by the ordinary missing-arguments span rule — or at the member token when that ONE name came from a missing member on a statically known receiver (diagnostics-only; see the dot-call bullet) — (`Lib = { public Q = 1 }` beside the root row `Q + 1` is a missing `open Lib`/`Lib.Q`, not a conflict in `Lib`; pinned by `ParameterPropertyCollisionTests.RootPhantomParameter_*`). Consequences that must hold together: a captured ancestor parameter beats a property of any FARTHER owner (the root's and the prelude's alike, so `F(pi) = { pi + 1 }` binds the parameter), a nearer property beats an outer parameter only in invalid recovery source, the nearest of several enclosing parameters wins, and a direct reference and one from a nested body always agree. `open` and the prelude keep their SEPARATE later policy: opens are consulted only after the whole owner walk (`LookupLexicalPropertyMatches`), so an owned parameter beats an inner `open` exactly as an ancestor-owned property does, and the prelude participates only as the outermost property level. Ownership is NOT the promotion question — `IsBoundName` still stops promotion at any visible property or opened name, unchanged. The owner map is `ParameterOwnership` (name → owning level, nearest wins by construction; never a counted depth), threaded through detection beside the scope chain — detection runs before automatic parameter forwarding, so it holds name-resolution parameters only, and the collision validator, which sees forwarded ones, takes a shared implicit-signature template as ONE layer owned by its level (FE-3, never a shared owner); the detector's parameter classification (`ShouldRewriteAsParam`) and receiver classification (`ResolveReceiverNameProvider`) must both go through the shared walk, and the editor's scope visibility is its enumeration form — derived per frame as persistent layers (parameters before the level's own properties, opens after every direct name) and pinned against the eager chain walk `ComputeEagerReferenceSymbols` (FE-4b; see [`editor-semantics.md` § Scope visibility and module provenance]). Pinned by `ParameterOwnershipTests`, `LookupCoherenceTests` (the `ownership.*` cases), and the `ownership-*` `LanguageSpecCorpus` cases.

## Open, exposure, and accessibility (K1-08)

`open Name` may target a lexically visible private head, but open-provided names and dotted open steps select PUBLIC members (a private step reports `NotPublicProperty` before any capture check); structural dot access selects DECLARED members including private ones. SELECTION NEVER DEPENDS ON EXPOSURE (K1-08): a public captured member participates in precedence and ambiguity, and the unique selected member is checked afterwards by `Evaluator.IsAccessibleFrom` / Lean `memberAccessible?`. Capture requirements retain the exact semantic owner, including transitive requirements across shadowing: `Property.RequiredAncestorParameters` / `.localCapturedAncestorParams names` supply diagnostic names, while internal `CaptureRequirements` / Lean `PropDef.requiredOwnerDepths` retain owner positions relative to the declaring scope. Host-built trees without owner metadata use the nearest binder of each supplied name. Both elaborated lists have immutable backing that properties may SHARE (FE-4a; [`evaluator-and-hosting.md` § Shared-DAG guarantee]): the exposure pass decides requirement identity by name AND owning scope — same-named parameters of different owners stay different requirements — and only then projects each property's final set into its lists, whose content is the whole meaning (names; owner depths relative to the property's OWN declaring scope), so two properties with equal contents may share backing without merging declarations, owners, or activations. Distinct nonempty wrappers preserve the existing reference-based list fields in generated Property equality and hashing; collection reference identity is not semantic requirement identity. Accessibility requires the matching declaration AND activation in the site's lexical chain, including already captured ancestor activations of a static nested provider. Runtime declaration tokens distinguish clause families and distinct algorithms even when they share names, properties, opens, or output nodes; activation tokens distinguish successive calls. Both are FIELDS of the runtime model, never a side table (Lean: `Algorithm.declarationId`, `ScopeCtx.declarationId`/`activation`, `EvalCtx.headScope`): `Algorithm.Declaration` is minted once per constructed `User`/`Conditional` and carried by every record copy — a `with` copy is a view of the same written declaration, whether the evaluator, the front end, or a host made it — while a `ParameterActivation` is minted per parameterized body entry or clause match, compared by reference, and carried by the activated `ScopeCtx` (`ScopeCtx.Owner`/`Activation`; the entered body's is `EvalCtx.HeadScope`, cleared by every push). A host-constructed scope has no owner, so it establishes identity only by being the same object. A conditional publishes its matched binders on its family scope. Parameter reads use the owning activation's value, algorithm, and counted channels, never a shadowing caller's binding. Compile-time branch analysis may share equivalent relative binder/open contexts without merging runtime families. Structural paths and open-provided names carry transitive capture requirements through `PendingReference`, preserving per-activation caching — a BARE opened name read by a sibling property is settled by the same one settlement (`PendingResolution.ResolveVisibleName`: the declaring chain's own properties first, then the declaring level's and its ancestors' opens), so `Y = X` beside `open Lib` with a capturing `Lib.X` is local-only exactly like `Y = Lib.X` and `Y = { open Lib  X }` (final audit, September 2026: it was classified Exported and the run cache leaked the first activation's value). An escaping reference carries an UNRESOLVED open candidate (the opener's target head was not the opener's own property) outward level by level, and the level that DECLARES the head settles it there — `PropertyDependencyGraphBuilder.AddEscaping` through the ONE local-head settlement `TryResolveLocalHeadCandidate`, the same one `MakeOpenCandidates` applies when the opener declares the head — because the evaluator resolves the target from the opener's direct chain outward and the nearest declaration wins; a head declared BETWEEN the opener and the settling level used to be carried past its declaration, so `Outer(p) = { Mid = { Lib = { public X = p }  Inner = { open Lib  X }  Inner }  Mid }` classified `Mid` exported and `Outer(1), Outer(2)` displayed `1 1` from the run cache (final hostile pass; `LocalMemberAccessTests.OpenTargetHeadDeclaredBetweenTheOpenerAndTheSettlingLevel_*`, spec case `ownership-open-head-between-opener-and-settling-level-charges-the-capture`). An OPEN PROVIDER must have zero effective call parameters, cannot be a clause family, and cannot be a prelude builtin — bare or as the HEAD of a dotted target (`open count.X` is refused like `open count`, never left to promote the opener's names to implicit parameters): `OpenProviderValidator` runs after signature completion and both evaluators reject the final provider with `IllegalInOpen` — the validator refuses a builtin head (`open count`) eagerly, in the same rule as a parameterized provider, matching the evaluator's and Lean's refusal by kind. Exported-property cache identity remains separate from runtime accessibility identity. Intermediate owners in `Lib.Sub` are static navigation, so parameterized or inferred-parameter intermediates are allowed if every selected edge is accessible and the final provider needs no call. A family exposes no branch members structurally (`LocalOnlyConditionalAlgorithm`), while a self-contained branch-local provider works inside the branch and nested bodies. Classification cannot invalidate selection, so no outer re-elaboration/recheck exists; the local dependency-summary fixed point remains. Pinned by `LocalMemberAccessTests`, `ZeroArgPropertyCacheScopeTests`, `FrontEndDagComplexityTests`, the exposure lookup cases, and independent `CoreTests/NameOwnership.lean` guards.

## Static-open ownership (SYN-03 / F2)

STATIC-OPEN OWNERSHIP (SYN-03 / F2): `open` is resolved statically — it never opens a runtime value, and there is no dynamic `open` — but lexical ownership still applies to the target's HEAD name (`Lib` in `open Lib` / `open Lib.Sub`), which parameter detection classifies through the ONE owner walk (`ElaboratedScopeLookup.SelectOwnedDeclaration`, called from `ParameterDetector.ClassifyOpenTargetHeads`) exactly like every other bare-name occurrence. If the nearest binding is a parameter — explicit, inferred, collecting, grouped, a branch binder, or any of these captured from an enclosing owner (never one automatic forwarding added) — that parameter owns the name; a parameter cannot be opened, so the head elaborates to `Expr.Param` (not an open form in either engine: `IsCoreOpenForm` / Lean `Expr.openForm?`, so evaluating any such tree yields `BadOpenForm`) and the front end reports `DiagnosticCode.OpenTargetIsParameter` at the head's span. It NEVER searches farther outward: adding or removing a farther same-named declaration (a root property, an enclosing property, an opened or module-provided member) changes neither the verdict nor the report, so `F(Lib) = { open Lib … }` is rejected with or without a root `Lib`. The rejected target provides no names (the same recovery rule as a rejected capture target), so the closed-list check and inference see nothing through it, and the editor classifies the head as the parameter reference it is (`OccurrenceKind.OpenTargetReference` with the parameter's declaration — never a farther property's). The never-called program root's phantom signature is NOT a callable binding for this decision (`ParameterOwnership.CallableBindings`, the F1 exemption): a nested `open Q` beside an unresolved root row `Q.X` stays a static lookup and evaluation reports the unresolved root input. Lean states the rule as `elaborateOpenHead` beside `elaboratesToParameter`; pinned by `StaticOpenOwnershipTests`, the `ownership-open-*` `LanguageSpecCorpus` cases, `LookupCoherenceTests.ownership.parameterOwnedOpenHeadResolvesToTheParameter`, and the F2 guards in `CoreTests/NameOwnership.lean`.

## Static open-target validity (audit #8)

Every `open` target must RESOLVE, whether or not any name is ever looked up through it: a written target whose name head no enclosing declaration or prelude member provides (an open head resolves through the direct chain — the evaluator's `lookupLexicalDirect` — never through another open), or whose dotted step — from a name head or from an INLINE head alike, a written `{ ... }` block or a loaded module (`open { ... }.S`, `open load('url').S`) — names a member the receiver lacks, declares privately (open paths select public members), or declares only inside conditional branches (a family exposes no members), is the front-end error `DiagnosticCode.UnresolvedOpenTarget` (host family `KatLangErrorCode.UnresolvedOpenTarget`) at the target, reported by `OpenProviderValidator` beside the provider rule and worded after the step that fails. Every static consumer reads the SAME decomposition of a target into its head and dotted steps (`AstHelpers.OpenTargetHead`): the parser's form check (a head that is not a name, a block, or a `load` module is `BadOpenForm` at the head — see [`syntax.md` § The `open` declaration]), the static resolution (`ElaboratedScopeLookup.ResolveOpenTarget`) and its diagnostic, parameter detection's head classification, and dependency/exposure analysis, which settles an inline-headed provider at its own open level exactly as the evaluator reads it (`PropertyDependencyGraphBuilder.TryChargeInlineOpenProvider`: the block is wired to the prelude, so only its own requirement names survive). Before constitution PV-11 (September 29 2026) the diagnostic described name-headed paths only, so `A = { open { public X = 1 }.Nope  X }` ran with `X` promoted to `A`'s parameter and `open load('url').Shwn` did the same while `Lib = load('url')` / `open Lib.Shwn` was refused; and dependency analysis charged a VALID block-headed provider as providing nothing, so a name it provided escaped to an enclosing `open` and a property reading it was classified local-only (`Outer.Y` refused where the bare-block and name-headed spellings read 5) or missed an `ambiguousOpen` (`OpenTargetHeadValidityTests`). Before this rule the front end silently dropped such a target (`ElaboratedPropertyScope.GetResolvedOpenProviders` omits it), so its names were promoted to implicit parameters, while both evaluators — which resolve ALL of a level's opens as soon as a lookup consults that level (Lean `resolveAllOpens`) — failed only if some lookup happened to reach it: `open Lib, Nope` with `X` from `Lib` was accepted by the front end and refused at runtime, and `A = { open Nope  X }` ran with `X` as an implicit parameter. Lean's surface spec refuses to promote through most failing opens too (`shouldTreatAsImplicitParam` propagates every lookup error except `unknownName`, which it cannot tell apart from the probed name's own absence — an unknown open head included); the front end now refuses every such target directly, so no accepted program reaches that distinction. A parameter-owned head keeps `OpenTargetIsParameter`, a builtin head or provider `IllegalInOpen`, and an illegal target shape the parser's `BadOpenForm`; a local-only captured step stays the evaluator's per-site accessibility question. Like `IllegalInOpen`, the report is per WRITTEN target (each is a site the author fixes). Pinned by `NameResolutionAuditTests`, `LookupCoherenceTests` (`providers.*`), and `DiagnosticCodeTests`.

## Open ambiguity in dependency analysis (audit #8)

Named open targets deduplicate by their complete name path. An inline block or module head keeps a separate provider for each written target, including dotted paths such as `open { ... }.S` and `open load('url').S`. The shared `Evaluator.OpenTargetDedupKey` reads `AstHelpers.OpenTargetHead` (Lean `Expr.openTargetHead` in `resolveAllOpens`), so diagnostic abbreviations such as `{...}.S` never merge distinct inline providers. This rule is shared by runtime lookup, static lookup, and dependency analysis. `OpenTargetHeadValidityTests`, `CoreTests/NameOwnership.lean`, and the `inline-headed-open-paths-keep-distinct-providers` spec case pin ambiguity, missing/private members of the first provider, and named-path controls.

Exposure/dependency analysis charges exactly the declaration the evaluator reads, and an ambiguous open reads NONE: the settlement of an escaping reference (`PropertyExposureResolver.PendingResolution.Resolve`) consults the escaped levels' providers and then the owning level's and its ancestors' opens ONE LEVEL AT A TIME — each carried `OpenCandidate` records its opener level (`ProviderLevel`) — and the first level at which any target publicly provides the head decides: a sole provider charges its member's requirements, two or more charge nothing (the evaluator's `ambiguousOpen`). Taking the first-listed provider made the verdict depend on target order: with `A.X` capturing `p` and `B.X` self-contained, `public Y = { open A, B  X }` was classified local-only and `Outer.Y` refused with `LocalOnlyProperty`, while `open B, A` reached the true `AmbiguousOpen`. Pinned by `NameResolutionAuditTests`.

## Dot-call resolution and missing members (G-24)

Dot-call uses structural lookup first and lexical fallback second, at EVERY level of a chain: a receiver that is itself an argumentless, non-`string` dot edge is NAVIGATED through its declared structural members before either channel of the outer edge is consulted (`resolveDotReceiver` / `ResolveDotReceiver`, the ONE receiver-position resolution shared by the sync evaluator, the async twin, and the sequence optimizer's shadow check), so `Lib.Sub.Q` reads `Sub`'s own `Q` before any lexical `Q(x)` and `A.B.C.D` traverses every level; a declared intermediate member that is inaccessible from the site (a local-only member outside its owner's activation — the member-accessibility law of K1-08 applied at every level, so selection never depends on exposure) or a conditional-branch intermediate member is that edge's `LocalOnlyProperty` error, never a fallback (private members stay reachable); a receiver without the member, an argument-bearing edge (`Lib.Sub().Q`), and the `.string` intrinsic are values, so the chain continues by extension fallback (`3.A.B` is `B(A(3))`; dot-call passes the receiver as the ordinary leading argument of that call — `sequences-lists-and-calls.md` § The dot-call receiver). Navigation is identity-only (no intermediate edge is evaluated) and the higher-order channel is untouched: `resolveAlg`/`ResolveAlg` still lifts every general argumentless dot expression to its zero-parameter wrapper identity. The front end mirrors the same rule through the ONE compositional static classification `AstHelpers.ResolveStaticStructuralMemberProvider` (detector receiver classification, editor dot-member resolution, and the scope-free dependency view; `StaticStructuralMemberProviderKind.KnownFailure` marks a statically failing intermediate edge, selection `Never`). Structural lookup, receiver injection, fallback order, and diagnostics must stay consistent across Lean and C#; pinned by `ChainedDotStructuralPrecedenceTests`, CoreTests `chained*`, and the `dot-chain-*` `LanguageSpecCorpus` cases. A MISSING MEMBER ON A STATICALLY KNOWN RECEIVER (G-24) is never a resolution or validity question: a known receiver (`Math`, a block, a module) that lacks the member falls back lexically exactly like any receiver, an unresolved fallback name is inferred as an implicit parameter exactly like a bare name, and a visible lexical callable of that name is a VALID fallback (`Ceiling(a, b) = b * 2` makes `Math.Ceiling(2.1)` the call `Ceiling(Math, 2.1)`, i.e. `4.2`). Static receiver knowledge is used ONLY for diagnostics: the detector's occurrence recorder stamps `ImplicitParameterProvenance.DotMemberOrigin` at promotion and a diagnostic-only walk after exposure completion discards receiver claims/hints invalidated by provider changes (the receiver described exactly as the evaluator's dot-call context describes it), the report leads with the shared `Property 'X' was not found on `R`` clause plus the fallback explanation, a member-bearing receiver's suggestion comes from its OWN declared member surface only (`NameSuggestions` member-typo policy: wider length-scaled threshold, initial-letter safeguard (a unique one-edit correction may change the initial on names of at least five characters), no lexical name offered in its place — `Math.Min` never suggests `min`; a memberless receiver keeps the ordinary lexical policy), and a single such unresolved parameter is positioned at the member token when it belongs to the current source (an imported module keeps the local demand span). No layer may branch on the receiver's spelling (SYN-05). Pinned by `ReceiverAwareMissingMemberDiagnosticsTests` and the `dot-fallback-on-known-receiver-stays-valid` `LanguageSpecCorpus` case. ATTACHMENT (invalid-state §3.4): a provenance note is ONE object per promotion — the moment one detection run over one body, in one front-end context, first promotes the name — and every record that stands for that promotion references the same object: the inferred capture (`CaptureParameterPattern.InferredProvenance`, the first carrier), the declarations flattened from it, every caller signature implicit argument resolution lifts that capture INSTANCE into, the dot edge whose fallback occurrence caused the promotion (`Expr.DotCall.InferredFallbackProvenance`, stamped by the detector's `RewriteDotCall`), and the note lists the evaluator snapshots onto `ArityMismatch`/`UnresolvedImplicitParams`. Each carrier holds the reference in a private equality-transparent `RuntimeStateSlot<T>` field behind an internal init-only property, so the SYNTHESIZED copy constructor propagates it through every `with` (the resolver's and exposure's edge rewrites, the evaluator's span-attaching error copies) with no registration step and no hand-written copy constructor, while record equality, hashing, and printing never see it. The finalizer mutates the note in place BECAUSE it is shared — its verdict (forget the receiver claim, restrict the suggestion, forget the origin position inside a module) must reach every lifted caller without rewriting an executable node — and it is the only mutator, running before its tree is published (inside the synchronous pipeline, or inside a deferred region's gated materialization over notes that materialization minted), so evaluation only reads. The suggestion itself is DEFERRED (FE-1): a promotion captures only its immutable canonical candidate context (a `SuggestionQuery` from the detection run's `SuggestionContexts` — never a scope chain, which stays confined to its front-end operation), and the note computes the suggestion on its FIRST READ, when a diagnostic renders it, as that query's result with the finalizer's confirmed receivers applied in order (a forgotten claim drops it for good), publishing the pure value atomically — so a read never changes what the note says, and a program that renders no suggestion compares no candidate (`DeferredSuggestionProtocolTests`, `SuggestionContextDifferentialTests`). Nothing forks a note: a body elaborated again in another context (a module spliced under a second owner, a shared host subtree under two owners, a materialized branch, a re-detected tree) is a new promotion with a new note, which is why independent contexts reach independent verdicts, while two references under ONE owner share one elaboration and one note. Pinned by `ImplicitParameterProvenanceAttachmentTests`.

## Builtin identity and the zero-argument value demand (SYN-05)

BUILTIN CALLABLES ARE ORDINARY PRELUDE BINDINGS, and IDENTITY — never spelling, never arity — decides semantics (SYN-05). Lexical resolution selects exactly one callable without considering the argument count; the resolved callable then determines its signature and behavior: `resolve name -> select ONE identity -> assemble the ordinary argument supply -> bind against THAT signature -> invoke`. KatLang has no overloading by arity, so a nearer property or parameter named `if`, `count`, or `sum` shadows the prelude binding COMPLETELY — `if(x) = x + 1` makes `if(1, 2, 3)` an arity error against `if(x)`, never a fallback to builtin `if/3` — and a bound parameter may carry any callable under a builtin's name (`Apply(if, x) = if(x)`). There is NO reserved-name mechanism, in either engine: do not add `ReservedNameValidator`, a `BuiltinDescriptor.IsReservedName` flag, reserved-name tables, `ReservedName` diagnostics, or grammar productions excluding builtin names from binding identifiers. (`BuiltinRegistry`'s reserved-name check and `HostOperations.ReservedPreludeNames` are unrelated: they govern who may BUILD the prelude — a Math alias or a host operation may not collide with a builtin — not what source may declare.) Consequently NO layer may branch on a callee's written spelling: the parser is purely syntactic about calls (it never counts arguments from a callee name, so a wrong-arity builtin call is an ordinary evaluation-time `ArityMismatch` against the resolved signature, and is inert in an unevaluated property exactly like `count(1, 2, 3)`), and a builtin recognizer such as the loop optimizer's `if` planning may use the spelling only as a lookup KEY taken from registry metadata (`Evaluator.BuiltinDisplayName`) before confirming `Evaluator.ResolvesToBuiltinAlgorithm`. Lean already models exactly this — `preludeAlg` declares `if` with one ordinary `publicProp`, and `NameOwnership` treats the prelude as the outermost property level of the owner walk — so a spelling gate anywhere in C# is a divergence from the authoritative model. Builtin `if`'s ONE intrinsic behavior is its invocation (`if(condition, whenTrue, whenFalse)`: evaluate the condition, then only the selected branch); that laziness belongs to the resolved builtin, disappears when the name is shadowed, and never applies retroactively to a value the caller already built (`if(true, Risky*)` evaluates all of `Risky` under the ordinary `expression -> value -> supply` rule). A builtin VALUE slot demands its SELECTED argument through the ONE zero-argument value-demand law (C# `ZeroArgumentValueDemandRejection`/`ZeroArgumentValueDemandError`, Lean `zeroArgumentDemandError?` — the factored rejection half of the value-position `Param`/`Resolve`/block arms): a resolved callable that cannot accept zero supplied arguments is the ordinary arity rejection at the argument's reference and its body is never entered (under a closed list, `Probe(u) = if(true, Inc, 0)` with `Inc(x) = x + 1` is "Property 'Inc' expects 1 parameter…", never `Unknown name: x`; a body that would not read its parameter is rejected all the same — in an inferring formula the value slot lifts the reference instead, § The unified formula-lifting law), a conditional is `ConditionalValueAccessError`, a written block `UnresolvedImplicitParams`; an UNSELECTED slot is never demanded; CALLBACK slots that supply arguments (`map`/`filter`/`reduce` steps, loop steps) never consult it; `reduce`'s initial accumulator keeps its dedicated hint but decides through the shared rejection law and retains the demanded family's name. Collection arguments and fixed VALUE/whole-number controls consult the same law after ordinary fixed-arity binding, and DEMAND an accepted item as soon as the descriptor identifies its VALUE slot during left-to-right call-item assembly, before later argument effects, so a collecting-only callback argument is never eagerly evaluated (`DemandSequenceBuiltinCallItemValue` / `demandSequenceBuiltinCallItemValue`, then `SequenceBuiltinValueDemandError` / `sequenceBuiltinValueDemandError?`); call-item and suffix preparation preserve the written source without demanding callback positions. Every builtin VALUE slot (`if` condition/branches, `while`/`repeat` initial state, the `repeat` count, `atoms`, `range` — `EvalResolvedArgumentCounted`, Lean `evalArgumentValueCounted` over `ResolvedArgumentAlgorithm.Source`/`source?`) and the ordinary-dot `.string` receiver (`EvalDotStringReceiverAlgOutput`) go through it; pinned by `LazySlotZeroArgumentDemandTests`, `CoreTests/ValueDemand.lean`, and the `lazy-slot-demand-*` `LanguageSpecCorpus` cases. Pinned by `BuiltinCallableIdentityTests`, `IfBuiltinArityPayloadTests`, the `builtin-callable-is-an-ordinary-prelude-binding` / `no-arity-based-callable-selection` / `if-*` `LanguageSpecCorpus` cases, and `CoreTests/NameOwnership.lean`. NOTE: `load` is NOT covered by this rule — it is still recognized by raw spelling (`AstHelpers.TryGetUnresolvedLoadArguments`) as a front-end/module directive; that asymmetry is deliberate-for-now and is not a licence to re-privilege a callable's spelling.

## Math members, host operations, and the prelude in every layer (audit #8)

**Math members are recognized by what a name resolves to.** A Math FUNCTION member has three spellings — the qualified `Math.Sin`, the prelude alias `sin`, and the canonical `Sin` an `open Math` provides — and one registry descriptor (`MathCallableFacts`). The front end's registry-proven value-demand contract (a Math member's arguments are strict value positions, so a referenced callable that requires supplied arguments lifts its implicit parameters — one that works with no arguments is read as a cached value instead, Q-03 — and a closed list that cannot supply them is diagnosed) belongs to the CONSUMER, so it applies to every spelling that resolves to the member and to none that does not (`AstHelpers.TryGetRegistryProvenMathCalleeFacts`): the qualified and alias spellings are recognized by shape (the prelude is reached before any open, so a caller's shadow predicate is all ownership needs), and the opened spelling by the identity verdict parameter detection stamps on the name (`Expr.Resolve.ElaboratedMathMember`, set only when the owner walk leaves the name to the opens and exactly one open provides it from the prelude's own `Math`). Dotted-call equivalence carries the contract through fallback: a dot edge whose lexical fallback MUST be selected (`ElaboratedFallbackSelection == Always`) on a Math member is the call `x(receiver, args)`, so `A.sin` lifts `A` exactly as `sin(A)` does and `2.pow(A)` as `pow(2, A)` (`AstHelpers.HasRegistryProvenStrictValueFallback`, shared by the resolver's rewrite and dependency collection and by the sibling-order channel); a fallback that is only possibly selected keeps its receiver and arguments neutral. Before, `open Math` + `F = Sin(A)` and `F = A.sin` elaborated `F` without `A`'s parameter (a runtime arity error) while `sin(A)` lifted it, and a closed `F(x) = Sin(A)` or `F(x) = A.sin` escaped the front-end diagnostic (`ClosedListStrictValueDiagnosticTests` had pinned the dot receiver as never lifting — a measured scope boundary of the then-behavior, now the direct call's rule). LIFTING a Math function referenced bare as a value follows the unified formula-lifting law (§ The unified formula-lifting law, September 30 2026): the lifting signature is keyed by the resolved member, never by the route, so the alias `sin`, the qualified `Math.Sin` and the opened `Sin` lift alike (formerly the lift was route-based and the opened `Sin`, like every opened callable, was never forwarded). Only FWD-02's LONE-ROW alias eligibility stays route-based (`AstHelpers.TryGetRegistryProvenMathAliasFacts`: the alias and `Math.X` are alias targets, an opened name is not). The qualified native reference is also the callee in an ordinary call such as `(Math.Abs)(A)`: the callee stays in algorithm position, its own parameters are supplied by the call, and the same strict contract lifts A's dependencies and diagnoses blocked forwarding. User callables keep neutral arguments.

**Identity of the three spellings as bindings.** The alias and the canonical member are DISTINCT property bindings that share one algorithm (the alias property's value IS the member's algorithm object, so dispatch and signatures cannot drift): the zero-argument cache keeps one entry per binding, and repeated-name callable identity (declaration + declaring scope chain + activations, Lean `sameRepeatedCallableIdentity`) sees the alias wired under the prelude and the opened member wired under `Math`, so `P(f, f) = f` binds `P(pi, pi)` and, under `open Math`, `P(Pi, Pi)`, but rejects `P(pi, Pi)`. A qualified `Math.Pi` is a dot RESULT and, like every argumentless dot expression, a fresh zero-parameter wrapper on the algorithm channel (only qualified Math FUNCTIONS resolve to the member itself there, `TryResolveQualifiedMathNativeReference`), so it matches nothing but itself forwarded. Math functions cannot be compared this way at all: they carry no value, and repeated callables must.

**Host operations are prelude members in every layer.** A run's `HostOperations` extend the prelude the evaluator resolves against, and every front-end layer must see the same prelude: parameter detection and open validation already did; exposure analysis (`PropertyExposureResolver.Resolve`, whose recorded chain also serves deferred-region materialization) and the editor model (`SemanticModelBuilder.Build(ParseResult)`, through the host configuration the parse result carries, `ParseResult.HostOperations`) now do too. Because the prelude precedes every open, an operation named like an opened library's member is what a bare reference selects: charging the library member made a self-contained property local-only (`Outer.Inner` refused), and the editor named the library member the evaluator never reads. Completion lists the operations as prelude names (`SemanticModel.PreludeSymbols`). Pinned by `NameResolutionAuditTests`.

## Zero-argument value demand follows actual call arity (September 2026)

A callable may satisfy a ZERO-ARGUMENT VALUE DEMAND **if and only if an ordinary call supplying zero arguments can bind it** (C# `Evaluator.AcceptsZeroSuppliedArguments`, Lean `Algorithm.acceptsZeroSuppliedArguments`). Eligibility is arity, never parameter-list emptiness. Before this rule the law rejected a demand whenever the callable declared any parameter, so `Only(*xs) = xs` — whose ordinary call `Only()` is perfectly legal and yields `[]` — could not be read as a value at all, and the rejection reported the flattened declared capture count (`Head(x, *rest)` claimed two parameters where its own call reports one required item).

**The rule is the binder's own.** `ParameterPattern.MinimumSuppliedSlots` / `ParameterPattern.minimumSuppliedSlots` states the arity check `BindParameterPatternList` / `bindParameterPatternList` performs, and those binders now read it rather than re-deriving it: every top-level pattern consumes exactly ONE supplied slot whatever it contains — a structural group, sequence or list, is one slot the binder opens afterwards — and a COLLECTING capture at that level consumes NONE, because it collects whatever is left after the fixed prefix and suffix bind (an empty leftover is the exact empty list). A clause family decides by its own dispatch rule instead: it accepts zero supplied arguments exactly when some branch's top-level pattern has arity zero, which is the branch `matchCallBranches` selects for an empty argument list (a flat multi-binder core equivalent always has at least two parameters, so it never accepts). A BUILTIN is deliberately not decided by the law at all: `zeroArgumentDemandError?` passes it through so `EvalBuiltinValueCounted` / `evalBuiltinValueCounted` raises the builtin's own rejection, which is the very message `sum()` produces.

Consequently:

* `Only(*xs) = xs` is eligible: `Only`, `(Only)`, `((Only))`, `if(true, Only, 0)`, `count(Only)`, `Only.count`, `Obj.M`, a fixed user parameter that reads its argument, a root output row — the direct value demands produce the collected empty list, exactly as `Only()` does; `count(Only)` and `Only.count` consume that value and return `0`.
* `Head(x, *rest)`, `Tail(*rest, z)`, `Mid(x, *rest, z)`, `Pair(x, y)`, `P((x, y))`, `P((x, *rest))`, `P((*xs))`, `P([*xs])` and `G((a, b), *rest)` are not: each requires at least one supplied value — a structural pattern binds ONE supplied value of its own kind (`P((*xs))` a sequence, `P([*xs])` a list), it never accepts none.
* The rejection reports the TRUE minimum supplied count (`Head` 1, `Mid` 2, `P((x, y))` 1, `G((a, b), *rest)` 1) in the ordinary structured `ArityMismatch` at the demand site, so the demand and its ordinary zero-argument call can no longer claim different numbers. The demand law reads that rule directly and deliberately does NOT consult `CallableArityFacts`; since the F4 correction the facts state the same per-level rule (`G((a, b), *rest)` is min 1, unbounded max — see `CallableArityFactsPerLevelTests`), so the two can no longer report different minimums.

**Eligibility is all that changed.** An accepted demand evaluates through the ONE funnel `EvalZeroArgumentDemandOutputCounted` / `evalZeroArgumentDemandOutputCounted` (with its value projection): a callable declaring no top-level pattern is its output exactly as before, a pattern list that accepts the empty supply is bound by the ORDINARY binder against that empty supply — so the collecting parameter holds `[]` while the body runs and the callee's names shadow all three inherited tiers as a written call's do — and a zero-accepting family dispatches through ordinary conditional dispatch. The funnel's common arm is a bare delegation to the very core the demand sites called before, and the binding arm's locals live in a separate non-inlined frame, because nested blocks and property reads recurse through it inside the calibrated 1 MiB stack envelopes.

Everything else is untouched:

* **Cache policy.** A bare property-style demand still takes the run cache (`isCacheableZeroArgPropertyAlgorithm` now reads the same acceptance rule, so a newly eligible property is on the SAME path an ordinary zero-parameter property is on), and `Only()` keeps its established direct-call bypass. Builtin VALUE slots — `count(Only)` and the dotted `Only.count` alike — read the same entry (since September 27 2026 a builtin argument that names a property resolves on its value channel to the ordinary property read; how a property value is consumed does not affect caching — see `evaluator-and-hosting.md` § Zero-argument property cache).
* **The algorithm channel.** A callback, a higher-order argument and a loop step still receive the callable: `map((1, 2), Only)` is `[[1], [2]]`, never `[]`. So does a callable FORWARDED through a parameter: a user call binds `Apply(Only, xs)`'s parameter on both channels (the value `[]` and the algorithm `Only`), and a builtin slot that INVOKES its argument — the `filter` predicate, the `map` mapper, the `reduce` reducer, a `while`/`repeat` step — invokes the ALGORITHM-channel binding (`ResolvedArgumentAlgorithm.invoked` / `InvokedAlgorithm`), so `Apply(f, xs) = xs.map(f)` selects the same callable as `xs.map(Only)`, from a nested block capturing the parameter too; ordinary eager parameter binding can already have evaluated `Only()` to establish the value channel, and callable-slot selection adds NO further value demand; every VALUE slot (the collection, loop initial state, `if` branches, `reduce`'s `initial`) reads the bound value and never re-runs the body, and a parameter bound on the value channel only has no callable to invoke. The descriptor identifies VALUE slots during left-to-right assembly: demand finishes before the next argument is evaluated. Collecting-only callables and zero-arity families in CALLBACK slots remain unevaluated.
* **Value-context lifting reads the SAME rule (Q-03, decided September 28 2026).** *If a callable works with no arguments, using its name alone reads its cached value, even if it declares optional or collecting parameters; `A()` evaluates it again.* The front end's decision to lift a referenced callable's parameters into the enclosing signature — in any VALUE position of the unified formula-lifting law (§ The unified formula-lifting law): an operand, a list or capture element, an index target, a spread operand, a builtin value slot, a Math, host or family argument, a fallback dot receiver, a block or callback body that uses it in an expression — happens BEFORE the law, and it asks this law's question: a callable that accepts zero supplied arguments is NEVER lifted, because declaring a parameter does not by itself make a bare reference a call. Its reference stays this demand, read through the cache, in every position. ONE predicate serves both halves: `ParameterPattern.AcceptsZeroSuppliedSlots` (`MinimumSuppliedSlots` is zero), read by `Evaluator.AcceptsZeroSuppliedArguments` for a user algorithm and by the resolver's `RequiresSuppliedArguments` (over `CallableSignature.AcceptsZeroSuppliedArguments`) for every value-role reference whatever its category, and at root-row preservation; Lean states it as `liftsBareValueReference`, with the law `bare_reference_lifts_iff_not_cacheable` (lifting and cache eligibility are complements). Before the decision the lift judged "declares any parameter", so `Only + 1`, `[Only]` or `abs(Only)` turned a collecting-only `Only` into the fresh call `Only(xs*)`, lifted a collecting `*xs` into the enclosing owner (which at the root could only forward an empty supply), and bypassed the entry its neutral positions read: `Roll == Roll` was `false`, `first(Pair)` and `Pair:0` read different evaluations, and a formula chain re-ran its base 2^k times (PV-03). A callable that REQUIRES a supplied argument (`Inc(x)`, `Head(x, *rest)`, `P((*xs))`) is lifted and forwarded exactly as before, so a lifted FIXED root parameter still leaves an argument nobody can supply. Consequences: a body whose ONE row is the bare name is NOT a value position but an exact alias or bare forwarding (§ The alias and bare-forwarding rules; decided September 29 2026, superseding Q-03's former alias clause, under which `Alias = Cnt` was a zero-parameter property holding Cnt's value): `Alias = Cnt` keeps Cnt's collecting signature — read bare, it is its OWN cached zero-argument value, one evaluation for the alias's binding — and with `Cnt(*xs)`, `G(*xs) = Cnt` forwards G's same-named collector, `Cnt(xs*)`, while `G(p) = Cnt`, which forwards nothing to it, reads Cnt's cached value; in a formula, forwarding by shape reaches only a grouped stream `H((*xs))` or `H([*xs])`; a closed parameter list never blocks such a reference, so the closed-list strict-value diagnostic never reports it (formerly PV-27); and because an owner lifts only from callees that require arguments, an implicitly lifted signature requires arguments itself — unless enclosing parameter bindings already supply the required ones (Q-04: the formula `H = [Head]:0` inside `F(x)` forwards only `*rest`, so `H` accepts zero arguments and is then read like any such callable). Explicit calls, with or without arguments, stay fresh. Pinned by `ZeroArgumentReferenceLiftingTests` (every consumer position against the zero-parameter property, host and seeded-random counts on six routes), `ZeroArgumentDemandArityTests.ValueContextLifting_FollowsZeroArgumentAcceptance`, Lean `CoreTests/PropertyCacheConsumers.lean`, and the `zero-argument-callable-name-is-read-not-lifted` spec case.
* **Laziness, charges, cancellation, optimizer.** An unselected builtin slot is still never demanded, the depth-only argument charge is unchanged, and the loop planner never plans a callable with an explicit parameter list as a temp (such a step falls back to the generic strategy).

Pinned by `ZeroArgumentDemandArityTests` (the metamorphic law over the signature families, host-built signatures, parentheses transparency, the algorithm channel, cache and host/random execution counts, genuine async suspension, cancellation, and the reported minimums), `LazySlotZeroArgumentDemandTests`, `ForwardedCallableChannelTests` (the forwarded algorithm channel), `AlgorithmParameterNamesTests`, `CoreTests/ValueDemand.lean`, the `minimum_supplied_slots_*` / `zero_argument_*` / `collector_binder_empty_supply_*` laws in `KatLangArityLaws.lean`, and the canonical `zero-argument-demand-follows-actual-call-arity` and `forwarded-callable-keeps-its-algorithm-channel` `LanguageSpecCorpus` cases.

## Automatic parameter forwarding preserves existing bindings (Q-04, September 2026)

THE LAW (the owner's decision of constitution open question Q-04, option (a), September 28 2026): **automatic parameter forwarding must not change what an existing name refers to.** Its boundary: **automatic forwarding reuses parameter bindings only — own written or inferred parameters, and accessible captured parameters of enclosing owners, clause-branch binders included. Properties, opened names, module members and prelude builtins are never forwarded as parameters.**

Two operations answer two different questions, and the second never feeds back into the first:

* **Name resolution** — *what does this written identifier denote?* — is `ParameterDetector` (the six rules of § The resolution model in one place). It decides every written name, promotes names nothing binds, and reports undeclared ones in closed bodies. Its verdicts are final.
* **Automatic parameter forwarding** — *which EXISTING parameter binding can satisfy this callee parameter?* — is `ImplicitArgumentResolver`. When a lifted reference in a FORMULA (a bare value-position reference, inside an expression, to a callable that requires supplied arguments, § Zero-argument value demand — a body whose ONE row is the bare callee is an exact alias or bare forwarding instead, § The alias and bare-forwarding rules) needs a callee parameter `n` — formula lifting is BY BINDING NAME, however many times the callee names `n` (§ Formula lifting is by binding name) — its argument is the binding a WRITTEN parameter reference of `n` would denote at the referencing body: the body's own written or inferred parameter; otherwise the nearest enclosing parameter binding the owner walk reaches before any same-named property — an ancestor's written or inferred parameter, a clause-branch binder, the never-called root's inferred names (`ImplicitArgumentResolver.ForwardableParameters`: per level, the enclosing name-resolution parameters minus every name the level declares as a property, persistent and keyed into the resolver's region memo by canonical content). Only when neither exists does an INFERRING body receive a new parameter `n`: appended after its own names (PAR-05), keeping the callee's pattern shape and kind, and marked as a FORWARDED parameter (`Algorithm.User.ForwardingParameterStart`, `NameResolutionParameterPatterns` is the prefix before it). A CLOSED body — a written parameter list or a branch pattern — receives nothing: the reference stays the zero-argument demand (a registry-strict Math position is the closed-list diagnostic, `ReportBlockedStrictValueForwarding`), and a closed body's lone bare row — bare forwarding — reuses the same bindings by name and is rejected (`UnforwardableParameter`) rather than adding one. Opens never take part: they are not owner levels, so an opened `n` leaves the walk undecided and the body gets a forwarded parameter.

A forwarded parameter is an ordinary parameter for every CALLER — arity, order, binding, activation, exposure — and a same-named property of its owner or of a body nested in it is still `ParameterPropertyCollision` (Lean `OwnerLevel.forwarded` is part of `conflictingOwnedNames`). But it is never what a written name denotes: the owner walk, open-head classification, Grace effectiveness, the editor's scope visibility (`SemanticModelBuilder.CreateScope` declares only the name-resolution prefix) and the evaluator's reads of written names never see it — a written `Param` node is owned by a name-resolution parameter at or below the forwarding owner (the reuse rule guarantees no nearer forwarded parameter of that name exists), and a written `Resolve` is a property lookup. So nothing is re-selected after lifting: the former `ParameterDetector.CompleteOwnership` pass, which re-ran the owner walk against the completed signatures and made every same-named written reference denote a lifted parameter, is deleted, together with its synthesized-call origins, signature-preserving re-resolution, and Grace revalidation. A synthesized argument is a spanless `Param` read (or `name*` when a collecting destination meets a collecting SOURCE binding — the reused enclosing binding's kind counts, FWD-02), and a callee group is rebuilt as its own structural kind from the bindings its captures stand for (§ The alias and bare-forwarding rules; forwarding preserves bindings and structural kind), so the callee receives exactly the binding an existing written reference already denotes.

Consequences, all pinned:

* `A = y + 1` / `F(y) = { G = y * 1000 + A ⏎ H(y) = G ⏎ H(100) }` / `F(3)` is `3004`, exactly the inlined `G = y * 1000 + (y + 1)`: G reuses F's `y` and takes no parameter, so H's unrelated `y` cannot reach it. Before the decision G received its own `y`, completion made the written `y` follow it, and the program gave `100101` (PV-01). Extracting a sub-expression into a property therefore never changes the binding of a name that was already resolvable.
* A helper that reuses its owner's parameter is an ordinary zero-parameter property — local-only, one evaluation per activation of its owner (PROP-08) — so a neutral `if` argument reads it (`Report(width, height) = { Doubled = Area * 2 ⏎ if(width > 1, Doubled, 0) }` is 24, formerly `ArityMismatch`), and so do callback and loop-step blocks (`map([1, 2], { A + e })` inside `F(n)` binds only `e`).
* A same-named PROPERTY is never forwarded: `v = 99` / `Need(v) = v` / `Outer = Need + 1` still infers `Outer(v)` (`Outer(7)` is 8), so an unrelated property elsewhere can never turn a parameterized formula into a zero-parameter one. A written reference to the property is never rebound either: in `Outer = { Inner = v ⏎ Inner + Need }` Inner's `v` stays 99 (`Outer(7)` is 106, formerly 14). The same holds for an opened member (formerly `ownership-later-lifted-parameter-beats-inner-open`, now `forwarded-parameter-leaves-an-opened-reference`) and a builtin (`NeedMin(min) = min + 1` / `Safe = NeedMin + min((3, 4))` / `Safe(10)` is 14: the written `min(...)` still calls the builtin, formerly `NotAnAlgorithm`), while parameters named like builtins stay parameters to forward (`Clamp(x, min, max)` / `Safe = Clamp + 0`).
* A formula under a closed parameter list forwards an accessible enclosing parameter too: `A = y + 1` / `G = { F(x) = A + 0 ⏎ F(1) + y }` / `G(10)` is 21, with or without a strict Math wrapper (K1-04 had pinned the refusal, which the decision supersedes; the strict and the ordinary formula positions still agree). The LONE row `F(x) = A` is not a formula but bare forwarding (FWD-02), which reuses the same enclosing `y` by name and leaves F's own `x` unused, so the same program with `F(x) = A` is 21 as well.
* A forwarded parameter gives no meaning to a written name nothing declares: `Need(v) = v` / `Outer = { F(0) = 0 ⏎ F(n) = v ⏎ F(1) + Need }` is `UndeclaredIdentifier` in the branch body (formerly completion rescued it with Outer's forwarded `v`).
* Explicit shadowing is untouched: in `Outer(y) = { Inner(y) = A * 2 ⏎ Inner(10) + y }`, A's `y` inside Inner is Inner's own (`Outer(3)` is 25). A NEARER owner decides: under `Outer(y) = { Mid(y) = { Inner = A ⏎ Inner } … }` the alias Inner inherits A's `y`, and Mid's lone row forwards Mid's own `y` to it, never Outer's.
* Aliases are NOT formulas (FWD-02, decided September 29 2026, superseding "aliases are formulas too"): inside `F(x)`, the bare `H = Head` with `Head(x, *rest)` is an exact alias that inherits `(x, *rest)` and ignores F's `x` (`H(10, 20)` is 11), while the formula `H = [Head]:0` reuses F's `x` and forwards only `*rest`, so it accepts zero arguments (it is then read, never lifted, Q-03; `H(10, 20)` inside `F(4)` is 6). A grouped callee pattern keeps its reused capture in a formula (`P((a, b))` inside `F(a)`: `G = P + 0` takes only `b` — a sequence group left with one binder IS that binder, the invalid singleton `(b)` is never manufactured — and calls `P((a, b))` with F's `a`, so `G(5)` inside `F(10)` is 15).
* A shared (DAG) body reached under owners with different parameter names is rewritten once per distinct set of forwardable bindings (the region-memo key); deferred branch regions carry the bindings in their resolver context.

Lean states the rule as `forwardingSource` (beside `liftsBareValueReference`) over the name-resolution owner chain, with the proved laws `forwarding_reuses_exactly_the_written_parameter_binding`, `forwarding_never_supplies_a_property`, `forwarding_never_supplies_an_undeclared_name`, `fresh_forwarded_parameter_only_without_a_parameter_binding`, `forwarded_parameter_changes_no_written_binding` and `forwarded_parameter_still_conflicts_with_a_same_named_property` (`KatLangArityLaws.lean`), and `CoreTests/ForwardingBindings.lean` evaluates the decided and the superseded elaborations side by side. Pinned in C# by `AutomaticForwardingBindingTests` (six routes and host-call counts, the elaborated tree, the editor model, and generated added-dependency and extraction metamorphic families), `OwnershipConformanceTests` (mask bit 4 = forwarded, against `CoreTests/NameOwnership.lean`), and the `forwarding-reuses-a-captured-ancestor-parameter`, `forwarding-never-supplies-a-property-an-open-or-a-builtin`, `forwarded-parameter-leaves-an-opened-reference` and `forwarded-parameter-names-nothing-in-a-closed-body` `LanguageSpecCorpus` cases.

## Formula lifting is by binding name (September 2026)

THE RULE (decided September 29 2026, reversing the Q-72 refusal of the same day; narrowed to formulas by the alias and bare-forwarding rules, next section): **formula lifting is by binding name, regardless of how many times that name occurs in a callee's parameter patterns.** A caller owns ONE binding for a given parameter name; when a formula USES a callee — in an operand, a list element, an index target, a strict Math argument, a callback body, beside other dependencies — and the callee uses that name in several parameter positions, the lifted call supplies the caller's one binding to every occurrence. It is the composition rule formulas already follow across callees, applied without exception within one callee:

* `F(x) = x + 1` / `G(x) = x * 2` / `H = F + G` is `H(x) = F(x) + G(x)` (`H(3)` is 10) — one name shared by two callees;
* `P(x, x) = x` / `Twice = P * 2` is `Twice(x) = P(x, x) * 2` (`Twice(7)` is 14; `Twice(7, 7)` is an arity error, because Twice has one parameter) — one name used twice by one callee.

The language does not distinguish the two cases. ONE merge builds the lifted signature: the callee captures are walked left to right and a capture is skipped when an earlier capture — the owner's own, an earlier dependency's, an earlier one of the same pattern, inside a group too — or a reused enclosing binding (Q-04, previous section) already binds its NAME (`ImplicitArgumentResolver.AppendMissingPatterns` / `MissingCapturePattern`, PAR-05's first-occurrence order); a group keeps its KIND for the names that are new there — a sequence group left with ONE non-collecting binder IS that binder (the singleton `(x)` is not a pattern), a list group keeps its brackets (`[a]` is the one-element pattern), and a group left with no new binder contributes nothing. So with `D = [P]:0`, `P(x, x, x)` lifts `x`; `P((x, a), x)` lifts `(x, a)`; `P(x, (x, a))` lifts `x, a`; `P(x, [x, a])` lifts `x, [a]`; `P((x, y), (z, x))` lifts `(x, y), z`; `P((x, x))` lifts `x`; `P([x, x])` lifts `[x]`; `P(x, (x, *rest))` lifts `x, (*rest)`; `P(x, *rest, x)` lifts `x, *rest` — never a formula signature that repeats a name, and never one parameter per occurrence. ONE builder makes the synthesized call (`BuildImplicitCallArguments`): the callee's own patterns rebuilt from the caller's bindings (`P(x, x)`, `P((x, a), x)`, `P(x, [x, a])`, `P(x, rest*, x)` — each group rebuilt as its own kind, next section), so every occurrence of a name reads that one binding, and a collector is re-spread exactly when its SOURCE binding collects (FWD-02), never because a name repeats. A closed list or branch pattern that declares the name forwards its own binding into a formula (`Q(x) = P + 0` is `Q(x) = P(x, x) + 0`); one that does not follows the ordinary closed-list rule (`Q(y) = P + y` keeps `P` the zero-argument demand, and a strict Math position names the missing `x` once). Which positions lift and which callables lift are the unified formula-lifting law's (next section) — value positions lift and callable positions (`Apply(P)`, callees, callbacks, loop steps) keep the reference, for every category of callable, opened and structural members and clause families included — and a bare ROOT row is its callable's own zero-argument demand; none of these general rules has a repeated-name case.

**A body whose ONE row is the bare callee is not a formula.** `Some = P` is an exact alias that inherits `P(x, x)` verbatim — two independent arguments, which must be equal — and `Q(x) = P` is bare forwarding (next section): Q's one binding `x` reaches both occurrences by name, `P(x, x)`, the same call the formula `Q(x) = P + 0` builds, under a closed list that never gains a parameter. The alias-signature deduplication this section formerly stated (`Some = P` as `Some(x) = P(x, x)`, recorded by the Q-72 reversal and the review that followed it) is superseded.

The relation to Q-05 (`sequences-lists-and-calls.md` § Collecting parameter lists, deconstruction, and callbacks: REPEATED NAMES ARE CONSTRAINTS, NOT MERGES) is exact: **a repeated name constrains independently supplied arguments; when a formula supplies the same caller binding to several occurrences, each occurrence receives that same complete binding, and no synthetic value/callable merge occurs.** The direct `P(7, 8)` — and the alias `Some(7, 8)` — write two arguments, and they must agree. `Twice(v)` evaluates its one argument once and binds it — the value and callable of that ONE argument, or its recorded failure (Q-01) — and each of P's slots reads that binding: the occurrences agree by construction on a value, and a callable-only or failed argument is its own failure, exactly as through the written `Same(x) = P(x, x)`. That equivalence is the pinned metamorphic law: formula lifting is observationally the explicit call that writes the same caller binding into every matching callee slot.

A group that dedupes down to one name keeps the law of its own kind. With `P((x, x)) = x` and `Some = [P]:0`, Some takes the bare binding `x` and calls `P((x, x))`, so `Some(v)` is the written `Some(x) = [P((x, x))]:0` for every `v`: `Some(7)` is `7`, `Some([7])` is `[7]`, `Some((7, 8))` is `(7, 8)` — each occurrence receives the whole binding, and the pair `(v, v)` is always a sequence. With `P([x, x]) = x` and `Some = [P]:0`, Some takes the one-element list pattern `[x]` and calls `P([x, x])`: `Some([7])` is `7`, `Some([[7]])` is `[7]`, while `Some(7)` and `Some((7, 8))` are the kind mismatch and `Some([7, 8])` the list arity error of the written `Some([x]) = [P([x, x])]:0`. A further formula forwards each surviving group as the same kind again (`Next = [Some]:0`). `RepeatedNameInsideOneSequenceGroup_LiftsTheBareBinding`, `RepeatedNameInsideOneListGroup_KeepsTheOneElementList` and `AnotherFormulaOverASurvivingGroup_RebuildsItAsTheSameKind` pin these observations against the written formulas; Lean's `CoreTests/RepeatedNameConstraints.lean` evaluates the corresponding elaborated trees.

History: the Q-72 decision (September 29 2026) had refused such a reference with a front-end error, reasoning that forwarding by name collapses independent occurrences into one input. It was reversed the same day: a caller binding forwarded to several slots is one input deliberately supplied to each — the reading formulas already give `H = F + G` — and only independently supplied arguments are constrained. The refusal, its diagnostic, its signature query and report memo, and its Lean specification are removed. FWD-02 (next section) later took the lone-row forms out of formula lifting — an open lone row is an exact alias and a closed one bare forwarding — so lifting a callee's names into a SIGNATURE concerns formulas only.

Lean models no signature construction: `forwardingSource` decides per NAME, which is exactly this rule, and `CoreTests/RepeatedNameConstraints.lean` evaluates the lifted elaborations (`Lifted(x) = [P(x, x)]:0`, a nested group, a collector) beside the exact aliases, the explicit calls and the Q-05 guards (bare forwarding's are in `CoreTests/AliasForwarding.lean`); the Lean programs of the `implicit-forwarding-is-by-binding-name` and `repeated-name-wrapper-keeps-independent-arguments` spec cases are derived from the C# elaboration. Pinned in C# by `ImplicitForwardingByBindingNameTests` — per generated shape: one caller binding per name, equivalence with the explicit same-binding call on satisfying, traced, failing and callable-only arguments, and rename-apart; every formula position (operators, comparisons, unary, lists, index target and selector, row spread, strict Math argument and dot-fallback receiver, deconstruction, blocks and nested properties that use the callee, a closed list and a branch pattern that bind the name, sibling formulas, a loop step, a callback) against the explicit call on six routes with host-call logs and seeded random draws; closed lists; module text; and an invariant over the whole executable specification that no inferred signature repeats a name, an exact alias's inherited signature excepted — and by `RepeatedNameAdversarialReviewTests`.

## The unified formula-lifting law (September 30 2026)

THE LAW (decided September 30 2026; constitution Q-11, Q-12 and Q-13 collapse, FOR FORMULAS, into this one rule, while the lone-row alias and bare-forwarding rules stay FWD-02's, next sections): **a formula lifts a reference exactly when the reference's ROLE is a value use and the callable it RESOLVES to has a lifting signature that requires supplied arguments.** The two facts are independent — every observed lifting decision factors as role × signature (the re-investigation of September 30 measured 0 of 144 role/signature cells breaking the product) — and each has ONE implementation. No callable CATEGORY is an exception: once a callable has a lifting signature — a user algorithm, a builtin, a Math member, a host operation, an opened or dotted member, a nameable clause family alike — a formula lifts it by this one rule. Formula lifting is one of FOUR distinct mechanisms, and the other three are unchanged: the exact alias and bare forwarding (a body whose one row is the bare callee, FWD-02) and the explicit call (its written arguments, whatever the callee's names).

**The role is what the immediate consumer does with the slot** (C# `FormulaLiftingRoles`; Lean `LiftingRole`, `LiftingCalleeKind`, `liftingSlotRole`, `builtinLiftingSlotRole`). A VALUE role: an operand of a unary, binary, logical or comparison operator; an index target or index part; a spread operand; a list or capture element; an output row or a deconstruction's right-hand side; the `.string` receiver; and every argument slot whose callee demands its value — a builtin's collection, value and whole-number controls and surplus positions (a surplus slot is value-evaluated before the arity verdict, PV-05; `if` takes three values; a loop's count and initial state are values), a Math member's and a host operation's arguments, and a clause family's arguments (every argument is value-demanded before a clause is tried, PAT-07). A CALLABLE role: a call's callee; a builtin callback (`map`, `filter` and `reduce` steps) and a loop step; a whole argument of a user callable (its binder decides at run time, and a plain capture keeps both channels — call arguments stay neutral, sub-choice A1); an argument of a callee known only at run time (a parameter, an unresolved name, a computed value); and the receiver of a dot edge that NAVIGATES a structural member or whose dispatch only the runtime receiver decides. A dot edge whose lexical fallback is selected IS the call `F(receiver, args)`: its receiver is slot 0 and its written arguments slots 1.. of the fallback callee, so `R.F(args)` and `F(R, args)` infer alike. No role depends on how many arguments a call supplies. The role is RECURSIVE — a compound expression in any slot is examined and its own children take the roles of THEIR consumers (`Id(Inc)` keeps `Inc`, `Id(Inc + 0)` lifts it) — and BLIND TO LAZINESS: an `if` branch is a value position whether or not a run selects it, exactly as a free name written there becomes a parameter, and lifting never changes which branch a run evaluates. After a spread slot a builtin's positions are known only at run time, so a later position is a value only when every declared position of that builtin is one. The resolver's dependency collection and rewrite and the sibling-order channel (`PropertyDependencyGraphBuilder`) read the SAME classifier, so what a formula lifts, how it is rewritten, and which sibling must be processed first cannot drift.

**The signature is what the resolved callable contributes** (C# `ImplicitArgumentResolver.TryResolveLiftable`; Lean `Algorithm.liftingSignature?`, `builtinLiftingSignature`, `familyLiftingSignature?`) — ONE identity-keyed source, never the route that reached the callable. The reference is resolved in the language's own order — the owner walk over the document's properties, then the prelude (the builtins, the Math module and its aliases, the run's host operations; `load` is a front-end directive and has none), then the opens level by level (one public provider selects, two select nothing) — and a structural dot path `R.M` by its member. A user algorithm contributes its parameter patterns as processed (an exact alias's inherited ones included); a builtin its callable interface, `BuiltinDescriptor.ToolingPlainSignature` (the registry's parameter names, a loop's variadic initial state as `*init`); a Math member or host operation its declared parameters; an opened or dotted member its own signature, read from its processed provider. A CLAUSE FAMILY contributes one whole-value slot per top-level position (its common arity, PAT-03), each named by its clauses: a clause that binds a PLAIN parameter at a position votes that name — a literal, a structural pattern and a binderless group vote nothing, being dispatch detail rather than leaves of the signature — every vote for a position must agree, every position needs one, and the names of different positions must be distinct (by-name lifting would otherwise feed one binding to independent positions: `P(a, 0)` / `P(0, a)` is not `P(a, a)`). A family whose clauses fail any of these has NO lifting signature and no name is ever invented: it stays explicitly callable, and an INFERRING formula that would lift it is the front-end error `DiagnosticCode.UnliftableClauseFamily` at the reference, naming the position and why (`S(1) = 1` / `S(-1) = -1` / `G = S + 0`). A closed list or branch pattern forwards only same-named existing bindings (PAR-04) and such a family names nothing, so there the reference keeps its ordinary zero-argument demand and runtime check, like every blocked reference. Diagnostic reasons cached by callable identity contain no occurrence name: `UnliftableClauseFamily` names the current reference, including when several bindings share one family AST. Each reference reports once per rewrite region, even when strict/eager diagnostic observation revisits a shared node. A reference to nothing static — a parameter, an unresolved name, an ambiguous open, a runtime receiver's member — has no lifting signature.

**Everything else is unchanged, and composes with the law.** Q-03: a callable whose signature accepts zero supplied arguments is never lifted, whatever its category — it is read through the cache. Q-04: forwarding reuses existing parameter bindings by name; a property, an opened name or a builtin is never forwarded as a SOURCE (the law widens which CALLEES lift, never what supplies them). PAR-04: a closed list or branch pattern receives nothing new, and a registry-strict Math position it blocks is the closed-list diagnostic — Q-15's trigger is unchanged; the law only widens which references that trigger meets (`F(x) = Math.Abs(count)`, and `Id(Math.Abs(A))` nested in a neutral argument). Laziness, which the role table ignores, still bounds that DIAGNOSTIC: a demand a run may never make is no statically impossible demand, so beneath a LAZY slot — a branch of `if`, direct or dotted (`FormulaLiftingRoles.IsLazySlot`) — the refused lift is left to the runtime (`K(y) = if(false, abs(A), 0)` is `0`, while the eager condition `if(abs(A) > 0, 1, 2)` is diagnosed); a shared host node reached both lazily and eagerly reports once, whichever reach comes first (`ResolverWalkMemos.LazyDepth` / `LazilyRewritten`). PAR-05: first-occurrence order, one parameter per binding name. X-02: the composed signature must be one a programmer could write (next section). FWD-02: a body whose ONE row is the bare callee is an exact alias or bare forwarding, never a formula, and FWD-02's target eligibility is untouched — a non-Math builtin, a host operation, an opened or dotted member and a clause family are still no alias targets, so `C = count` stays a zero-parameter property while the formula `C = count + 0` is `C(collection)`. THE ROOT CLAUSE: a bare ROOT output row naming a callable that requires supplied arguments is never lifted into the never-called root, whatever the callable's category, so evaluation reports that callable's own zero-argument rejection at the reference (`abs`, `Math.Random`, `count`, `Lib.Inc` and a family alone at the root are their own arity or branch errors; formerly the two Math spellings lifted there and reported the root's `UnresolvedImplicitParams`), while a root FORMULA lifts like any other (`abs + 0` needs the root's `x`).

**Every read sees the signature its turn gives (processing order).** Lifting reads the PROCESSED signature of what a reference resolves to, so the resolver processes a level's properties in dependency order (`PropertyDependencyGraph`, `ImplicitArgumentResolver.PropertyLoop`). The reads the sibling-order channel classifies — with THE role classifier — are hard edges; the reads it can only anticipate (a nested body's `open` whose head is a sibling; a bare sibling argument of a callee the channel cannot classify, whose role only the rewrite knows) are SOFT preferences, honored among the properties the hard edges leave ready, so they never block the order. A read that nevertheless reaches a pending property processes it ON DEMAND (`PropertyLoop.EnsureOnDemand`) together with its pending hard-dependency closure, dependencies first — the order its turn would have had — and never ahead of a dependency still in progress. The members of a SIBLING CYCLE — closed by hard edges, soft preferences, or both (`PropertyDependencyGraph.CyclicIndices`) — and every property that hard-depends on one are never processed early: a cycle keeps its processing-order fallback, as every sibling cycle always has (a member processed first reads the others' unprocessed signatures). Two siblings that `open` each other therefore form a cycle, and a member read before its provider's turn does not yet carry the parameters its own lifting adds (its written and detected ones it always carries); outside cycles, declaration order is unobservable. On-demand processing — the one place two rewrites stack — stays within the structural depth budget (`ImplicitArgumentResolver.DemandDepthBudget`: the live depth plus ten units per active demand must leave room for the demanded property's structural height under `EvaluationLimits.MaxSupportedAstDepth`; beyond it `DiagnosticCode.AstDepthLimitExceeded` at the demanded property, deterministic and never a host stack overflow). With the soft preferences no known program reaches on-demand processing at all — the whole test suite and the re-investigation corpus make none — so it is the safety net for a read no channel edge anticipates. HOSTILE REVIEW (September 30 2026): the first implementation processed a demanded sibling in the middle of the one reading it whenever the two formed no HARD cycle, one inside the next: a reverse-declared chain of 300 siblings reading each other through nested `open`s overflowed the host stack, and a demanded sibling that read the one in progress got its unprocessed signature — `Y = { open X ⏎ A = Q + 1 ⏎ Inc + 0 }` / `X = { public Q = 5 ⏎ Z = Y + 0 ⏎ public W = Z * 2 ⏎ 0 }` / `X.W(7)` lost `Y`'s lifted `x` from `Z` and `W` (an ArityMismatch where HEAD gives 16), and adding an unrelated read could change another member's signature. Pinned by `PropertyProcessingOrderTests` (the order, the cycle set, the closure, the in-progress and cycle refusals, the budget) and `UnifiedFormulaLiftingTests` § 9.

Consequences, all pinned: `Total = count + 0` is `Total(collection) = count(collection) + 0`; `Next = Lib.Inc + 0` and `{ open Lib ⏎ Inc + 0 }` take `x`; `Fam = E + 1` with `E(0) = 100` / `E(n) = n` is `Fam(n) = E(n) + 1`; `G = if + 0` is `G(condition, whenTrue, whenFalse)`, `G = repeat + 0` is `G(step, count, *init)`, and a host `trace(x)` makes `G = trace + 0` take `x`; `[Inc, Inc * 2]`, `(Inc, 0)`, `Inc.string`, `Inc.count`, `take([1, 2, 3], Inc)`, `abs(Inc)` and `E(Inc)` lift, while `Apply(Inc)`, `map([1, 2], Inc)`, `repeat(Inc, 2, 0)` and `f(Inc)` keep `Inc`; `G = if(c, 1, Bad)` is `G(c, x)` and still evaluates `Bad` only when `c` is false; a formula's lifted calls evaluate, charge, draw random numbers and call host operations exactly as the explicit calls it abbreviates, and extracting a helper formula (`H = F + 1`, `G = H * 2`) agrees with inlining it (`G = (F + 1) * 2`). Formerly builtin value slots, capture elements, nested argument expressions and the `.string` receiver were not lifting positions (Q-11), and builtins, host operations, opened and dotted members (Q-12) and clause families (Q-13) never lifted, so extracting or inlining a helper formula could change a program's signature; the runtime zero-argument demand of such positions is now pinned under a closed list (`Probe(u) = if(true, Inc, 0)`).

Lean states the role table and the lifting signatures, with the laws `family_arguments_are_value_slots`, `strict_value_arguments_are_value_slots`, `user_and_dynamic_arguments_stay_neutral`, `builtin_slot_roles_follow_the_registry`, `unknown_builtin_position_is_a_value_only_when_every_slot_is`, the `family_*` naming laws, `builtin_reference_lifts_and_is_never_cacheable` and `nameable_family_reference_lifts` (`KatLangArityLaws.lean`) and the guards of `CoreTests/ForwardingBindings.lean` § 3; Lean models no signature construction, so the spec and explorer programs are derived from the C# elaboration. Pinned in C# by `UnifiedFormulaLiftingTests` (the role matrix, the category matrix, family naming and the unnameable diagnostic, laziness, the explicit-call and extraction metamorphic laws, effects and seeded random draws, X-02 across categories, the root clause, closed lists, and FWD-02's unchanged eligibility — six routes with host-call logs), `LazySlotZeroArgumentDemandTests` (the runtime demand under a closed list), the `formula-lifting-is-one-law-for-every-callable`, `formula-lifting-follows-the-consumers-role` and `unliftable-clause-family` `LanguageSpecCorpus` cases, and the `formulaLifting*` semantic-explorer specials.

## Inferred signatures are held to the rules of written ones (X-02, September 30 2026)

THE LAW (decided September 30 2026, X-02): **a signature the front end infers must be one a programmer could write.** Formula lifting composes an owner's signature from its callees' contracts; a composition no source may declare is the DEFINITION's front-end error, reported when the definition is elaborated — never a later call's failure and never a host exception. ONE validator decides validity everywhere (C# `ParameterPattern.FindSignatureViolation`, Lean `ParameterPattern.signatureViolation?`): the parser's rules for a written head, the resolver's check of an inferred one (composed from shared template facts, `ImplicitSignatureTemplate.TemplateFacts.SignatureViolation`, so FE-3 sharing stays linear), and — for the collector rule — the pre-evaluation validation of a host-built tree. Its rules, in the parser's order: no one-item sequence pattern (the singleton rule), at most ONE collecting parameter per pattern level (VAR-02), and no repeated name that includes a collector (a repeated fixed name stays a Q-05 constraint).

The witness: `C1(a, *p) = a` / `C2(b, *q) = b` / `K = C1 + C2` would infer `K(a, *p, b, *q)` — two distinct collectors at one level, which no parser accepts. Before the rule the front end inferred it silently: `K(1, 2)` threw the binding planner's `InvalidOperationException` out of `KatLangEngine.Run` on every route, a bare read misreported "expects 3 parameters", and the editor model threw while building the signature. Now it is `DiagnosticCode.InvalidCollectingBinding` at the second callee's reference, naming both collectors and the callees that need them ("Formula lifting cannot complete this definition's signature: it would need the collecting parameters '*p' (needed by 'C1') and '*q' (needed by 'C2') at the same pattern level … Call 'C2' with explicit arguments, or declare this definition's parameters explicitly."). A collecting NAME shared by two callees is ONE binding (`C(n, *xs)` twice is `K(n, *xs)`; `K = while + repeat` is `K(step, *init, count)`), collectors in their own groups are legal (`(a, *p)` beside `*q`), and a collector-only callee is never lifted at all (Q-03), so it never composes one. The same rule holds across every category the unified law lifts (`C1 + while` is rejected). Recovery is the parser's for a written head — the first collector of each level stays and a later one becomes fixed (`ParameterPattern.KeepFirstCollectingCapturePerLevel`) — so the recovered tree carries only valid signatures and the editor model builds. A host-built tree with two collecting captures at one level is `IllegalInEval` before evaluation in both engines (`PreEvaluationAstViolation.MultipleCollectingCaptures`, Lean `Algorithm.hasMultipleCollectingCaptures`): a deliberate host-AST compatibility change, since C# formerly threw the planner's exception for a top-level pair and both engines bound a nested second collector as a suffix pattern.

Lean laws `x02_distinct_top_level_collectors_are_an_invalid_signature`, `shared_collecting_name_is_one_valid_binding`, `collectors_in_their_own_groups_are_valid`, `nested_level_with_two_collectors_is_invalid`, `repeated_name_with_a_collector_is_invalid_while_fixed_repeats_are_constraints` and `valid_signature_has_at_most_one_top_level_collector` (`KatLangArityLaws.lean`) and the guards of `CoreTests/StructuralPatterns.lean` § 10. Pinned in C# by `InferredSignatureValidityTests` (every lifting position, six routes and both engine entry points without a host exception, the recovered tree and the editor model, the validator against the parser for written heads, template-fact composition, and the host-built pre-evaluation rule), `UnifiedFormulaLiftingTests.DistinctCollectors_FromAnyCategory_AreTheDefinitionsFrontEndError`, and `PatternBindingErrorPrecedenceTests.SecondCollectingCapture_IsIllegalBeforeEvaluation`.

## The alias and bare-forwarding rules; forwarding preserves bindings and structural kind (FWD-02, September 2026)

THE RULES (decided September 29–30 2026; FWD-02 owns them). **A body whose ONE written row is a bare reference to a callable that declares parameters is an exact alias when its body is open, and BARE FORWARDING when its parameter list is written: bare forwarding reuses already-existing compatible bindings BY NAME — it never renames a binding, never adds one to the closed list, never matches by position, and never converts an incompatible top-level parameter pattern because nested leaf names coincide. An explicit call means exactly what is written. Formula lifting is a separate, by-name inference mechanism.** Six forms are distinguished by what is written, never by compiler internals:

| You write | Meaning |
|---|---|
| `A = F` | an EXACT ALIAS of `F`: `F`'s callable contract, verbatim |
| `A(p) = F` | BARE FORWARDING: reuse `A`'s existing compatible binding named `p` for `F`'s parameter `p`; infer nothing, rename nothing |
| `A(p) = F(p)` | an EXPLICIT CALL: the written arguments; the caller's and the callee's parameter names need not match |
| `A = F(p)` | a FORMULA whose parameter `p` is the free name written in it |
| `A = F + 1` | FORMULA LIFTING: `F`'s required parameter names become `A`'s inferred parameters, by name |
| `A(p) = F + 1` | a formula under a CLOSED list: it may use existing bindings (its own `p`, Q-04's enclosing ones), never add one |

**Do not equate `A(p) = F` with `A(p) = F(p)`.** With `Sub(y, x) = y - x`, `G(x, y) = Sub` hands G's `y` to Sub's `y` and G's `x` to Sub's `x`, so `G(10, 3)` is -7, while `G(x, y) = Sub(x, y)` passes its arguments in the written order and gives 7. The two agree only when the names do.

* **Exact alias.** An open body with no parameter of its own (`A = F`, `A = { local declarations ⏎ F }`, an inline block `{ F }`) takes `F`'s parameter patterns VERBATIM as its signature — arity, structural kinds, collectors, repeated names, binderless groups — and calls `F` with those patterns rebuilt (`ImplicitArgumentResolver.TryCompleteLoneCalleeRow`, `BuildSourceArguments`; the signature is interned as one shared template, FE-3). Binding a supply against the copied patterns and rebuilding reproduces exactly the values `F`'s own patterns bind from it, so `A(S)` behaves as `F(S)` for every supply: the same success or failure, value, structure, effects, random draws and errors (modulo the alias's own evaluation frame and the name in its signature display). `P(x, x) = x` / `A = P` takes two independent arguments that must be equal (Q-05); `E((), []) = 1` / `A = E` keeps its two binderless structural parameters; chains (`B = A`, `C = B`) inherit the same signature at every level. Every inherited parameter is FORWARDED (`ForwardingParameterStart` is 0): no written name denotes it and no enclosing binding is reused, so a local alias inside `Outer(x)` never reads Outer's `x` (§ Automatic parameter forwarding). Its NAMES are the callee's private binder names, so they are ENCAPSULATED: they collide with no property the alias or a body nested in it declares (`Algorithm.User.InheritsCalleeSignature`, read by `ParameterPropertyCollisionValidator`). Renaming the callee's binders renames the alias's inherited parameters with them — naturally, since the alias IS the callee's contract. Alias transparency is OBSERVATIONAL call and signature equivalence, not binding identity: `A` read bare is a property binding of its own, with its own zero-parameter cache entry (§ Builtin identity and the zero-argument value demand; cache identity follows binding identity). The editor shows the inherited signature (`G = Add` displays `G((a, b))`) and creates no site for it.
* **Bare forwarding.** A written parameter list (`G(params) = F`) or a clause branch (`G(head) = F`) keeps its own CLOSED signature, and each of `F`'s top-level parameter patterns is supplied from an EXISTING binding (`BareForwardingArgument`; Lean `bareForwardingArgument` / `bareForwardingRow`):
  * a callee CAPTURE `n` is supplied by the body's own TOP-LEVEL capture `n`; when the body binds no `n` at all, by the enclosing parameter binding a written `n` would denote there (Q-04: an ancestor's parameter, a clause binder, the root's inferred names — never a property, an opened name or a builtin); a body that binds `n` only INSIDE one of its structural patterns holds an element, never a whole-value parameter, so that capture is unforwardable;
  * a callee STRUCTURAL parameter is supplied only by one of the body's own top-level patterns with the SAME contract — kind, shape, names and collectors (C# `ParameterPattern.ContractComparer` structural equality, Lean `ParameterPattern.sameContract`) — rebuilt as itself; enclosing bindings are plain named values and never supply one, and a structural pattern is never assembled from same-named leaves;
  * a collector that nothing of its name supplies receives no argument (a collector accepts none); any other parameter nothing supplies is UNFORWARDABLE: the front-end error `DiagnosticCode.UnforwardableParameter` (public `KatLangErrorCode.UnforwardableParameter`), reported once per callee parameter at the bare reference — at the import site inside module text, re-issued per family for a shared branch body — with the row left as written, never an evaluator arity message.

  So: `F(p) = p * 2` / `A(p) = F` is `F(p)` (10 for `A(5)`); `F(q) = q * 2` / `A(p) = F` is rejected — A's `p` is never renamed to `q`, whatever the arity; `F(p, q) = p + q` / `A(p) = F` is rejected — an explicit list is closed, so `q` is never inferred (write `A(p, q) = F` or `A(p) = F(p, 10)`); `F(p)` / `A(p, unused) = F` forwards `p` and leaves `unused` unused; `F = 10` / `A(p) = F` is 10 (a callee that declares nothing is not a target at all); `Single([x]) = x` / `G(x) = Single` is rejected — G's whole `x` never becomes Single's `[x]` because the leaf names coincide — while `G(x) = Single(x)` is the explicit call (`G([7])` is 7) and `G([x]) = Single` forwards the same pattern (`G([7])` is 7); `Add((x, y)) = x + y` / `G(x, y) = Add` is rejected — nothing manufactures the pair — while `G((x, y)) = Add` forwards it; `F([a, b])` / `A([x, y]) = F` is rejected — positions inside a pattern are never renamed either. Only the SOURCE binding's kind decides a re-spread: a collecting source into a collecting destination of the same name re-spreads exactly its items (`G(*xs) = F` with `F(*xs)` is `F(xs*)`, FWD-01's `spread (collect S) = S`), while a fixed source reaches a collector as ONE item (`G(xs) = F` with `F(*xs)`: `G((1, 2))` collects `[(1, 2)]`) and a collected list reaches a fixed parameter WHOLE (`G(*xs) = F` with `F(xs)`). Repeated callee names follow the same rule: `P(x, x) = x` / `Q(x) = P` hands Q's ONE binding `x` to both occurrences, `P(x, x)` — the call a formula builds too; the two slots are then ordinary arguments reading one binding, which Q-05 compares and never merges. A branch head offers its binders and its literal-free top-level items (`G(n) = F` with `F(n)` forwards the binder; `G(0) = F` with `F(v)` is rejected, since the pattern binds no `v`). When every callee parameter is an unsupplied collector, nothing is forwarded and the row stays the bare name — Q-03's cached read, never an invented call (`F(*xs) = xs` / `A(p) = F` reads F's own `[]`).
* **Explicit call.** `A(p) = F(p)` is an ordinary written call and never reaches the rule: its arguments are exactly the written expressions, whatever `F` calls its parameters. It is deliberately NOT the same thing as the bare row.
* **Written-call formula.** `G = F(exprs)` is an ordinary formula: its parameters are the free names WRITTEN in `exprs`, in first-appearance order with the ordinary Grace arithmetic, so `G = Add((x, y))` is exactly `G(x, y) = Add((x, y))` whatever `Add` calls its binders, and `G = Single([x])` takes one parameter `x`.
* **Eligibility** (`DeclaresParameters`, Lean `aliasesLoneBareReference`): the row names the callable ITSELF, so the rules read the callee's DECLARED signature, not zero-argument acceptance. A callable that also works with no arguments (`Only(*xs)`) is aliased and forwarded like any other — superseding Q-03's former alias clause — while a bare reference in every OTHER position keeps Q-03's cached value read, so `A = Only` read bare is its own zero-argument value. The targets covered are lexically visible user properties, the Math aliases and the bare `Math.X` shape; a Math function is forwarded by its registry signature's parameter names — `sqrt(x)`, `pow(x, y)`, `round(value, digits)`, `randomInt(start, end)` — the names formula lifting gives it too, so `R(x) = sqrt` forwards and `R(value) = sqrt` is rejected. NOT covered, each keeping its prior behavior — this eligibility is route-based and unchanged by the unified formula-lifting law, which lifts every one of these (a callable parameter excepted) when a FORMULA uses it: a clause family (no parameter-pattern signature, PV-14), an opened member, a structural member reached with a dot (`A = Lib.X`), a callable parameter, and non-Math builtins and host operations (PV-26). The ROOT's rows are never completed (the root is never called). A deconstruction declaration's right-hand side is a WRITTEN row of its body (`AstHelpers.WrittenRows`; its free names are the body's own parameters), so a body with a deconstruction beside the bare callee has two written rows and is a formula (`A = { a, b = 1, 2 ⏎ P }` with `P(x, x)` is `A(x)`) — a documented boundary, not an alias — while ordinary property declarations beside the row keep it an alias (`A = { k = 1 ⏎ F }`).
* **Formulas keep formula lifting.** A body that USES a callee inside an expression is formula lifting, by binding name (§ Formula lifting is by binding name), with Q-04's reuse of enclosing parameter bindings. An OPEN formula infers what bare forwarding refuses to add (`F(q) = q * 2` / `A = F + 1` is `A(q)`); a CLOSED formula adds nothing either: `F(q) = q * 2` / `A(p) = F + 1` keeps `F` the zero-argument demand — accepted by the front end in this non-strict position and the runtime arity error `F` expects 1 (a strict Math position is the closed-list diagnostic; that front-end/runtime asymmetry is Q-15's) — never a renamed `p`, while `F(p) = p * 2` / `A(p) = F + 1` reuses `p` (`A(5)` is 11). By-shape forwarding (`H((*xs))` fed from a caller's single top-level stream) belongs to formulas only; a lone row never forwards by shape. Formula lifting is the one place a callee's binder names reach a caller's SIGNATURE (`H = [F]:0` infers F's `x`; renaming it renames H's parameter). That is the deliberate distinction of this section: formula lifting infers dependencies by name, bare forwarding reuses existing bindings by name, an explicit call maps written arguments.

**Renaming the callee's parameters** affects each form as its mechanism says, and the tests pin all four: an ALIAS inherits the new names; BARE FORWARDING may become unforwardable (intended — `A(x) = F` depends on `F`'s name `x`); an EXPLICIT CALL is unaffected (`A(p) = F(p)`, `G = Add((x, y))`); FORMULA LIFTING lifts the new name.

**Every synthesized call forwards existing bindings unchanged and rebuilds each structural pattern as its own kind** (FWD-02 with the structural-pattern model):

* **An existing binding is forwarded unchanged.** A fixed binding is supplied as its whole value — never opened, never wrapped — and a collecting binding that is re-spread supplies exactly its collected items: in an alias whenever the inherited capture collects, and in bare forwarding and a formula when BOTH the destination capture and the SOURCE binding collect (FWD-02's source-kind rule). This holds whatever route supplies the binding: the owner's own parameter, a closed list's own binding, a reused enclosing binding (Q-04), and a name an earlier capture already bound (by binding name).
* **A rebuilt structural pattern keeps its kind.** A SEQUENCE group is rebuilt as a sequence — the written capture `(a, b)`, `()` for the empty group, or the one lone non-spread item itself where the group reduces to it (the written `C((xs))` IS `C(xs)`, so the invalid singleton is never manufactured) — and a LIST group as a list literal `[a, b]`, `[]`, `[x]`, `[items*]` (`ImplicitArgumentResolver.BuildPatternArgument` / `BuildSequenceArgument`, Lean `ParameterPattern.sourceArguments` / `sequenceArgument`). Nesting keeps every level's kind.

Consequently every synthesized call is exactly the call a programmer would write. In a formula, a caller's collecting stream is re-spread into the group it came from, by name or by shape (`Use(*items) = [LC]:0` with `LC([*xs]) = xs` calls `LC([items*])`), and a group that holds no new binder contributes nothing to the lifted signature while the call rebuilds it as the empty structure of its own kind (`L = [E]` with `E((), []) = 1` takes no parameter and holds `[E((), [])]`, while the alias `A = E` keeps both groups as parameters). There is no kind conversion anywhere.

A conditional branch body's resolver region is keyed by the branch's closed binder specification (`FrontEndRegionKeys.ClosedBranchSpecification`, literal-blind), except that a body SHAPED like bare forwarding — one bare written row, `ImplicitArgumentResolver.HasLoneBareRowShape` — is keyed by its head's value-blind structure (`BareForwardingBranchHead`: binders, groups and literal POSITIONS, never literal values), since what bare forwarding offers depends on which items hold literals but never on their values: K literal branches sharing such a body share one region, while a wide shared body keeps one region (FE-1).

## Grace (F10)

Grace `~` is a front-end parameter-order annotation on exactly one bare name occurrence (`~x` / `x~`), written DIRECTLY attached to that name (marker attachment law: `~ x` and `x ~` are `InvalidGraceMarker` attachment errors that recover to the plain name with no weight; `~~x` and `~x~` are attached runs); it is not a general expression operator, repeated markers on that occurrence use ordinary weight arithmetic, and elaboration strips it before evaluation. GRACE MUST BE EFFECTIVE (F10): the marker is meaningful only on a FREE bare-name occurrence that implicit-signature collection promotes to a parameter of the enclosing algorithm — the one place its weight is consumed. On an occurrence whose binding is already fixed — an explicit parameter, a captured parameter of an enclosing algorithm, a visible property, a builtin, an opened name, a dot member that always resolves structurally (or the `.string` intrinsic), and ANY occurrence under a closed explicit parameter list — it is the front-end error `DiagnosticCode.InvalidGraceMarker` ("Grace has no effect on 'x' because …"), reported by `ParameterDetector.ReportIneffectiveGrace` from the REWRITE pass (once per occurrence per region through a diagnostic visit set), never a silent no-op; the reason comes from the same owner walk the editor resolves with, and conditional branch bodies keep the parser's own rejection (`GraceEffectPolicy.NotReported`) — a branch infers nothing, so the parser rejects every marker in every row the branch WRITES (`AstHelpers.WrittenRows`: its output rows and its hoisted deconstruction right-hand sides, exactly the rows the detector's branch region rewrites; before constitution PV-49 the scan read the output rows only, so `F(n) = { a, b = (~n, 1)  a + b }` in a family ran silently — `ConditionalBranchDeconstructionGraceTests`). Pinned by `GraceEffectivenessTests` and the `grace-on-bound-name-rejected` / `grace-under-explicit-list-rejected` `LanguageSpecCorpus` cases. A graced name inside REDUNDANT PARENTHESES is the graced name (PARENTHESES GROUP SYNTAX, September 2026): `(~a).V` is `~a.V` — the ordinary structural-first dot edge on `a` with `a` moved earlier, so a bound algorithm's own `V` is read and a number falls back to the lexical `V` exactly as `a.V` and `(a).V` do — and `(~a)(b)` is the call `~a(b)`; the parser's `IsRedundantGrouping` never looks at the inner kind, so the group is erased whatever the marker's weight and Grace can never change selection (`OutputBundleSplitTests`, the `grace-in-redundant-group-is-grace-on-the-name` spec case).

## Parameter channels and shadowing

A user call binds each parameter on the value channel, the algorithm channel, or both, and the callee then evaluates in the CALLER's environments extended with its own bindings — that inheritance is what lets a nested property read an ancestor-owned parameter and a nested call invoke an ancestor-owned callable. A BOUND PARAMETER OWNS ITS NAME ON EVERY CHANNEL: every binding site — user calls (flat fixed, patterned, item-supply/collecting), clause-family binders, sequence-builtin callbacks, and generic and planned loop steps, in both engines and in the async twin — shadows the callee's parameter names out of ALL THREE inherited tiers: the value environment (`ShadowValEnv` / Lean `ValEnv.shadow`), the counted callback-parameter environment (`ShadowCountedParamEnv` / `CountedParamEnv.shadow`), and the algorithm environment (`ShadowAlgEnv` / `AlgEnv.shadow`). The two context tiers are shadowed by ONE shared helper — C# `ShadowInheritedParameterEnvironments`, Lean `EvalCtx.bindParameters` — and a new binding path must go through it rather than filter one tier ad hoc. Consequences: a parameter bound ONLY on the algorithm channel (a higher-order argument, or any argument whose value evaluation failed) read in value position reaches its algorithm binding — which reports the failure its argument slot's one value evaluation established (the zero-argument demand's arity error for a parameterized callable, the conditional value-access error for a clause family, the argument's own error otherwise), never a re-evaluation of the algorithm (sequences-lists-and-calls.md § At-most-once argument value evaluation) — never a same-named caller value; and a parameter bound ONLY on the value channel read in call position (`f(2)`, the lexical dot-call fallback `2.f`, forwarding through `Pass(f)`) fails as not-callable exactly like the standalone program, never invoking a same-named caller callable. Lookup never falls through to a caller binding merely because the inner binding is unusable in the requested position — this is lexical name shadowing, not overload resolution across channels — while names the callee does not bind stay visible (`Inner(x) = f(x)` inside `Apply(f)` still calls the received `f`). Without this, a callee silently computed with an unrelated caller value or callable, and which caller parameter names collide with a callee's became observable.
