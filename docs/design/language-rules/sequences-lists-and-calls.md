# Sequence, list, spread, and call rules

The full statement of the rules that AGENTS.md indexes in compact form — consequences, examples, the implementation map, and the pinning tests. The detail moved here verbatim from AGENTS.md in September 2026; in November 2026 the dense statements AGENTS.md still carried moved here too, as the **Summary** list that opens a section. ## Output bundles, capture, and algorithm identity

**Summary.** The rules of this section in dense form, with their implementation anchors and pinning tests; the full statement follows.

- Algorithm output is written as expression rows: every non-definition expression row in an algorithm body contributes to that algorithm's output, and output rows may be interleaved with property definitions. There is no output keyword; `Output` and `output` are ordinary identifiers.
- `Expr.SequenceConstruct` / `.sequenceConstruct` is an INTERNAL sequence-join node, not the AST representation of written parenthesized sequence values (those parse to `Expr.Capture` / `.capture` bundles; `()` to the empty-sequence node). Its evaluation drops non-spread `()` leaves (a spread leaf contributes exactly its spread items, like a spread row), so routing surface syntax through it would violate visible-empty semantics — the parser must never produce it (guarded by `SequenceConstructContainmentTests`, CoreTests internal-node guards, and the semantic explorer's internal-node cases; see `docs/design/sequence-boundary-audit-2026-07.md` §7).
- Brace algorithms parse to `Expr.AlgorithmExpr` / `.algorithmExpr` (algorithm identity); a surviving parenthesized group parses to `Expr.Capture` / `.capture` over an `OutputBundle` — ordered written slots with NO lexical ownership, consumed by the receiver. Capture is not algorithm identity (`Apply((Inc, Dec))` errors, `(Obj*).V` falls back, `open (M, N)` is `BadOpenForm`), while every `AlgorithmExpr` provides its algorithm on the higher-order channel whatever its parameter count — and a REDUNDANT group is not a capture at all (`Apply((Increment))` is `Apply(Increment)`, `(Obj).V` is `Obj.V`, `open (M)` is `open M`; see `syntax.md` § Parentheses group syntax). `Expr.Call.Args` is an `OutputBundle` and `Expr.DotCall.Args` an optional one (`null` = property-style access), evaluated in the CALLER's context; there is no transparent Args algorithm and no `IsParametrized` mode bit — every `Algorithm.User` owns a scope (parser entry points `ParseScopedAlgorithm` / `ParseParenthesizedBodyParts`). Value-context lifting is a consumer property decided by the ONE role classifier of the unified formula-lifting law (`FormulaLiftingRoles`, `ownership-and-lookup.md` § The unified formula-lifting law): builtin value slots and Math, host and family arguments lift, a user callable's whole argument stays neutral, and a closed list leaves blocked lifting as runtime zero-argument demand (Model-C Q-15). [`sequences-lists-and-calls.md` § Output bundles, capture, and algorithm identity]

Brace algorithms are `Expr.AlgorithmExpr` / `.algorithmExpr` and carry algorithm identity and lexical scope. A surviving parenthesized group is `Expr.Capture` / `.capture` over an `OutputBundle`, with no algorithm identity, members or lexical ownership. `Apply((Inc, Dec))` therefore reports absence of a callable; no synthetic output thunk supplies identity. Redundant grouping is erased by the parser, so `Apply((Inc))` is `Apply(Inc)` and `(Obj).V` is `Obj.V`. Genuine capture and spread targets are invalid `open` forms.

Every brace algorithm has an independent CALLABLE channel, whatever its parameter count. Call arguments are `OutputBundle` slots in the caller's context. Each ordinary slot becomes a suspended cell; a capture or list, if demanded, evaluates its elements eagerly and constructs an ordinary value. No Args algorithm or call-site slot reinterpretation exists. Formula lifting follows its immediate consumer role as specified in `ownership-and-lookup.md`. A closed parameter list blocks adding forwarded names and leaves an ordinary runtime zero-argument demand; it introduces no Q-15 strict-Math diagnostic. See `call-by-need.md` for the complete demand laws.

## Value boundaries

**Summary.** The rules of this section in dense form, with their implementation anchors and pinning tests; the full statement follows.

- A property/call/builtin RESULT boundary returns ONE value with count `Result.valueCount` (0 for `()`, otherwise 1; a list counts 1): a multi-output body is one sequence value to its caller and only an explicit spread opens it (or the spread the front end inserts at an eligible call to a marked declaration, `A(x, y)* = …`), and redundant unary sequence structure normalizes during construction. The re-count helper `reCountValueBoundary` / `ReCountValueBoundary` applies at user/conditional calls, structural zero-arg dot access, and higher-order callback items; collection-producing builtins and collecting bindings materialize ONE exact list (`makeCollectionListResult`; a collector cell materializes through it on its VALUE demand, Lean `demandNeed` / C# `CollectorCell`). SELECTION IS A VALUE BOUNDARY (September 2026): `A[i]`, `first(A)`, and `last(A)` CHOOSE a value and never open it — `Result.select?` / `Result.Index` return the stored element of the target's position view and the `.index` arm of `evalCounted` (C# the Index case of `EvalExpressionSpineCounted` and its async twin), `evalFirstCounted`/`evalLastCounted`, and `countedSequenceCallbackItem` all emit `(selected, Result.valueCount selected)`; so a selected sequence or list is ONE value at every receiver (`Coll(A[0], 3)` collects `[(1, 2), 3]`, a lone root row `A[0]` is one row, a loop-step row one slot, `map(A, Id)` maps a nested pair to itself), a selected `()` re-counts to zero values whatever route selected it (so `(first(((), 1)))*.Coll` is `[]`, while the unspread `first(((), 1)).Coll` passes the one value `()` — one argument, collected as `[()]`), a selected `[]` stays one exact list (`[[]]`), the origin is forgotten (`X = A[0]` agrees with `A[0]` everywhere — selection chooses a value; later collector behavior depends only on that value and whether it was spread, never on selection provenance: `A[0].Coll` is `[(1, 2)]` exactly like `V.Coll` on a property holding the pair), and only the spread marker opens a selection, one boundary (`A[0]*.Coll` is `[1, 2]`). The three-part motto: SELECTION CHOOSES A VALUE, DOT-CALL PASSES A VALUE, SPREAD OPENS A VALUE. Over a value in hand, `first(v) ≡ v[0]` and `last(v) ≡ v[count(v) - 1]` for EVERY value, failures included — laws, never rewrites (`first(Data())` and `Data()[0]` each demand `Data()` once) — so an empty value names no position and `first(())`, `last([])` and `().first` are `BadIndex` exactly like `()[0]` (Q-27, Q-81; Lean `first_is_selection_at_zero`/`last_is_selection_at_count_minus_one` and the total `first_is_select_zero_total`/`last_is_select_last_total`; `SelectionValueBoundaryTests`; CoreTests `SelectionValueBoundary`); there is no selected-content projection or live selection count anywhere. A completed `while`/`repeat` is a value boundary too (Q-26; § Loops: patterns bind, rows produce, spread opens). A `map`/`reduce` CALLBACK RESULT is one too (Q-25, October 2026): a transform or step returns its ORDINARY call result — several rows are ONE sequence value, `()` and `[]` are ordinary values, `map` stores the result whole as one element and `reduce` passes it whole as the next accumulator, never spread and never checked for cardinality or emptiness; an output-less callback is still `MissingOutput` and `filter` keeps its Boolean contract (`CallbackResultBoundaryTests`, CoreTests `CallbackResultBoundary`). NOT value boundaries: root/body output accumulation and a loop step's own row supply (the loop protocol). [`sequences-lists-and-calls.md` § Value boundaries]
- `arity` means the structural count of top-level output slots. The `ArityMismatch` error family reports a supply/output CARDINALITY failure (and NEED-04's unequal repeated value), never a value of the wrong kind, a missing callable, or an empty selection (Q-27).
- `count` means the number of evaluated top-level values after sequence values are opened by the consuming operation.
- Do not treat `arity` and `count` as interchangeable.

A property/call/builtin RESULT boundary is a value boundary: it always returns ONE value, with emitted count `Result.valueCount` (0 for the empty sequence value, otherwise 1 — a list value always counts 1, including `[]`). A multi-output body/collection is observed by the caller as one sequence value; only an explicit caller-site spread (`expr*`), or an eligible call to a marked declaration (§ Declaration-level output spreading: the front end inserts that very spread), spreads it back into the surrounding item supply (spread reads the value via `spreadItems` — the spread view that also opens one list boundary — not the emitted count; `toItems` is the non-spread item view and keeps lists opaque). Redundant unary sequence structure is normalized during ordinary value construction, including `(())` and `((()))` to `()`. The shared helper is `reCountValueBoundary` (Lean) / `ReCountValueBoundary` (C#); it re-counts the value boundary without rebuilding the value and is applied at user/conditional calls (`evalUserCallCounted`, `evalConditionalCallCounted`), structural dot zero-arg access (`evalDotCallCounted`), and higher-order callback items (`countedSequenceCallbackItem` / `CountedSequenceCallbackItem`). SELECTION IS A VALUE BOUNDARY (September 2026; the bracket spelling and variadic form since October 2026, § Variadic postfix selection): `A[i]`, `first(A)`, and `last(A)` CHOOSE a value and never open it — the `.index` arm of `evalCounted` (C# the Index case of `EvalExpressionSpineCounted` and its async twin), `evalFirstCounted`/`evalLastCounted`, and the callback item all emit `(selected, Result.valueCount selected)` for one selected value, so a selected sequence or list is ONE value everywhere (`Coll(A[0], 3)` collects `[(1, 2), 3]`, a lone root row `A[0]` is one row, a loop-step row `A[0]` is one state slot, `map(A, Id)` with `Id(x) = x` maps a nested pair to itself), a selected `()` re-counts to zero values whatever route selected it (so it spreads to nothing — `(first(((), 1)))*.Coll` is `[]` — while passed unspread it is ONE argument value: `first(((), 1)).Coll` is `Coll(first(((), 1)))`, which the exact collector law collects as `[()]`, like `E.Coll` / `Coll(E)` for `E = ()`), a selected `[]` stays one exact list (`[[]]`), and the selected value's origin is forgotten (`X = A[0]` then `X.Coll` agrees with `A[0].Coll`, and both agree with `V.Coll` for a property `V` holding the same value — selection chooses a value; later collector behavior depends only on that value and whether it was spread, never on selection provenance, so `A[0].Coll` with `A = ((1, 2), 3)` is `[(1, 2)]` under the exact collector law described under Collecting parameters). Only the spread marker opens a selected value, one boundary (`(A[0])*.Coll` is `[1, 2]`; `A[0]*` is the same select-then-spread). Over a value in hand, `first(v) ≡ v[0]` and `last(v) ≡ v[count(v) - 1]` for EVERY value, failures included (Q-27, October 5 2026) — laws, never rewrites of effectful expressions (§ Variadic postfix selection (C)): an empty value names no position, so `first(())`, `first([])`, `last(())`, `last([])` and `().first` are `BadIndex` exactly like `()[0]` and `[][0]` (Lean `first_is_selection_at_zero` / `last_is_selection_at_count_minus_one`, the older `first_is_select_zero` / `last_is_select_last` and the total `first_is_select_zero_total` / `last_is_select_last_total`, with `first_empty_is_badIndex` / `last_empty_is_badIndex`; C# `SelectionValueBoundaryTests`; CoreTests `SelectionValueBoundary`; `evaluator-and-hosting.md` § The evaluation-error taxonomy). There is no selected-content projection and no live selection count anywhere: `Result.select?` / `Result.Index` return the stored element (`select_is_stored_element`), and `projectionItems` / `ProjectionItems` is only the TARGET's position view. Collection-producing builtins (`order`, `orderDesc`, `distinct`, `take`, `skip`, `filter`, `map`, `range`, `atoms`) materialize ONE exact list value with count 1 via `makeCollectionListResult` / `MakeCollectionListResult` and need no re-count. Collecting bindings likewise produce one exact list value with count 1 — since Model C a collector cell whose VALUE demand materializes its slice through `makeCollectionListResult` / `MakeCollectionListResult` (`demandNeed`, `CollectorCell`; formerly `collectSegment` / `CollectSegment`) — and need no re-count or raw-supply storage. Lexical zero-arg property access and `if` already re-counted this way; the reduce initial accumulator is likewise reified as ONE accumulator value (`reCountValueBoundary`) before reduction, so an empty reduction returns it as ONE value and every reducer step receives it as one ordinary argument. A completed `while`/`repeat` is a value boundary too (Q-26, October 2026): `loopResultCounted` / `MakeCheckedLoopStateResult` re-count the captured final state, so a non-spread loop is ONE item at every receiver (§ Loops). NOT value boundaries (must keep their multi-item counts): root/body output accumulation (`evalAlgOutputCountedCore`) and a loop step's own row supply (`evalAlgOutputSlots`, the loop's iteration protocol). A `map`/`reduce` CALLBACK RESULT is a value boundary like every call result (Q-25, October 2026; § Callback results): a transform or step returns its ordinary call result, ONE value, and the former strict single-value callback contract is gone. Scalar/reduction builtins already return one value and are unchanged.

## Variadic postfix selection

**Summary.** The rules of this section in dense form, with their implementation anchors and pinning tests; the full statement follows.

- VARIADIC POSTFIX SELECTION (Q-81, decided October 2026, resolving Q-52; Lean and C# together, replacing the colon form): `receiver[s1, …, sn]`. PARENTHESES INVOKE A COMPUTATION; POSTFIX BRACKETS SELECT FROM A VALUE; selection never changes how its receiver obtains that value. ONE node `Expr.Index(Target, Selectors)` / Lean `.index target selectors` (the written selector slots). Evaluation — Lean the `.index` arm of `evalCounted` instantiating the TOTAL core `selectPosition` / `selectWith` / `selectionResult` (defined above the evaluator core), C# the Index case of `EvalExpressionSpineCounted` and its async twin (`AdvanceSelection`, `SelectPosition`, `CompleteSelection`): (1) the receiver is demanded ONCE through its ordinary value path (`Data` the cached read, `Data()` fresh, never reading the cache, establishing it only when empty — CACHE-PUB-1); (2) the selector supply is FORMED like a call's (Model C) — explicit spreads run now (`FormSpreadSupplySlot`), ordinary selectors stay suspended; (3) the supplied selectors are demanded, validated and selected LEFT TO RIGHT, the first failure ending the selection (a non-number `TypeMismatch`, a number naming no position `BadIndex`, positioned at its own selector slot); (4) zero selections give `()`, one the selected value itself, several ONE sequence of the selected values kept whole (`MakeCheckedSequenceCapture` / `combineOutputSlots`; a selected `()` or `[]` stays an element; no selector count survives). So `[10, 20][99, 1 / 0]` is `BadIndex` and `[10, 20][99, (1 / 0)*]` is `DivisionByZero`. `count`, `first`, `last` and selection share ONE immediate positional view (`Result.projectionItems`): a string is ONE position (`count('abc')` is 1, `''[0]` is `''`, `'abc'[1]` is `BadIndex`), and a scalar selects itself at 0. SYNTAX: a `[` on the receiver's SAME physical line (spaces and tabs allowed) opens the selector list — the list literal's expression list (commas select siblings, newlines separate slots once open, whole-slot spreads, chained brackets descend); a `[` on a later line begins a new list literal; `A*[0]` stays multiplication (`(A*)[0]` captures then selects); a selection has no callable identity and is never a call target; `[]` never resolves a user-visible name. THE COLON IS RETIRED: `expr:sel` is `DiagnosticCode.RetiredColonSelection` (public `KatLangErrorCode.RetiredColonSelection`), recovered as the selection it meant. `VariadicSelectionSemanticsTests`, `VariadicSelectionDemandTests`, `PostfixSelectionSyntaxTests`, `EvaluatorIndexingTests`, `CoreTests/VariadicSelection.lean`, the `## Variadic postfix selection` laws in `KatLangArityLaws.lean`, the `variadic-selection-*` spec cases. [`sequences-lists-and-calls.md` § Variadic postfix selection; `syntax.md` § Postfix selection]

VARIADIC POSTFIX SELECTION (owner-approved October 2026; it replaces and retires the colon form `receiver:selector`). `receiver[s1, …, sn]` selects zero or more positions of ONE receiver value. The rule has six parts.

**(A) Invocation and selection are different operations.** PARENTHESES INVOKE A COMPUTATION; POSTFIX BRACKETS SELECT FROM A VALUE; SELECTION DOES NOT CHANGE HOW ITS RECEIVER OBTAINS THAT VALUE. `Data` is the ordinary cached zero-argument property read and `Data()` a fresh invocation that never reads or replaces the property's cache entry (one that finds the entry empty establishes it — CACHE-PUB-1, 2026-10-22) (§ Zero-argument property cache in `evaluator-and-hosting.md`); so `Data[indices]` consumes the ordinary read and `Data()[indices]` consumes ONE fresh invocation result. Grouping stays transparent: `Data[0]`, `(Data)[0]` and `((Data))[0]` are one node. A selection has no CALLABLE identity (`resolveAlg` / `ResolveAlg` report `NotAnAlgorithm("index expression")`), so `Data[0](1)` is the SYN-07A separator error and `Data[0].F` is the extension call `F(Data[0])`; selection never makes a computed value callable.

**(B) Counting and selection share ONE immediate positional view.** KatLang's `count` counts values (elements), not the internal components of those values. A list or sequence exposes its immediate elements, never recursively flattened; a number, a Boolean or a string exposes ITSELF as one element (position `0`) — the empty string `''` included, which is one scalar value, not an empty collection; an empty list or empty sequence has no positions. Counting a list of strings counts its strings, never their characters, and selecting from a string never extracts characters, code units, code points or graphemes: `count('abc')` and `count('')` are `1`, `'abc'[0]` and `first('abc')` are `'abc'`, `''[0]` is `''`, `'abc'[1]` is `BadIndex`, `count([['a', 'b']])` is `1`. The view is `Result.projectionItems` / `Result.ProjectionItems`, which EQUALS the post-binding collection view `count`, `first` and `last` read (`builtinCollectionItems` / `BuiltinCollectionItems`; Lean theorem `positional_view_is_shared`). This view is distinct from argument cardinality, emitted-value count, explicit-spread supply and the structural-pattern views; their agreement on counting and selection does not authorize merging helpers that deliberately keep different boundaries.

**(C) The selection laws.** For the same already evaluated receiver value `v`, `first(v)` and `v[0]` — and `last(v)` and `v[count(v) - 1]` — have the same result and the same error (`BadIndex` when `v` has no positions; for `last` the index is then `-1`). These are semantic equivalences over a value in hand, NOT unrestricted rewrites of effectful expressions and not promises of identical resource use: `last(BuildData())` invokes once, `BuildData()[count(BuildData()) - 1]` twice. Builtin identity resolution and shadowing are unchanged (no spelling recognition implements the laws). Lean: `first_is_selection_at_zero`, `last_is_selection_at_count_minus_one`, `count_is_the_number_of_positions` (and the older `first_is_select_zero_total` / `last_is_select_last_total`).

**(D) Values are preserved and only the result grouping is normalized.** One immediate element per supplied index, in supplied order, repetitions repeating stored values, each element whole; the selected values are captured by ordinary normalization of the RESULT GROUPING only (`combineOutputSlots` / `MakeCheckedSequenceCapture`, the capture loop results use): zero selections are the successful empty sequence `()`, one is the selected value itself, several are ONE sequence of the selected values. `Data[]` is `()` (emitted count 0, never a missing output, never the receiver, never `[]`); `Data[2, 0, 2]` is `(30, 10, 30)` for `Data = [10, 20, 30]`; `Nested[2, 3]` is `((), [])` and `Nested[0, 1]` is `((10, 20), [30, 40])` for `Nested = [(10, 20), [30, 40], (), []]` — no flattening, no dropped `()`, no list wrapping, no hidden selection-count metadata. BRACKETS SOLVE THE INVOCATION AMBIGUITY; THEY DO NOT REMOVE THE ORDINARY CONSEQUENCES OF SINGLETON NORMALIZATION: with `Data = [(10, 20), 30]`, `Data[0]` is `(10, 20)` and `[Data[0]*]` is `[10, 20]`, never `[(10, 20)]`; an exact one-per-index list is written explicitly (`Indexes.map{Data[i]}`). A multi-selection is one sequence VALUE, never an argument supply: `Add(Data[0, 1])` is an arity error and `Add(Data[0, 1]*)` supplies two arguments. Surrounding output and count behavior is the ordinary value boundary's.

**(E) Operational order — when the selection expression is demanded:** (1) the receiver is demanded ONCE through its ordinary value path, and its failure propagates even for an empty selector supply — unless it is a RETAINED COLLECTOR (NEED-07, `call-by-need.md`), whose slice is obtained with no VALUE demand; (2) the selector supply is formed exactly like a call's (Model C, `formNeedSupply` / the ONE spread-slot formation `FormSpreadSupplySlot`): explicit spread slots run during formation, in written order — a collecting parameter's slice, direct or through a transparent reference (NEED-07), is transported unforced — and ordinary non-spread selectors stay suspended. Transport of an unavailable parameter fails at its written slot during formation. (3) the supplied indices are demanded, validated (`selectPosition` / `SelectPosition`: a non-number selector VALUE is `TypeMismatch`; a negative, fractional, non-finite, beyond-host or past-the-view number is `BadIndex`) and selected LEFT TO RIGHT, the first failure ending the selection with no later ordinary selector demanded; (4) the selected values are normalized (D). Over a retained collector step (3) validates each position BEFORE demanding its one element (Lean `selectViewWith` over `retainedSourced`), so a position's first demand follows selector order and repeated positions reuse the one cell outcome; steps (2), (4), the selector categories and the result grouping are unchanged. Formation completes before any selector is validated, so `[10, 20][99, 1 / 0]` is `BadIndex` (the later ordinary selector is never demanded) while `[10, 20][99, (1 / 0)*]` is `DivisionByZero` (the spread runs during formation) — a consequence of the established supply rule, not a selection-specific order. Caller environments, need-cell sharing and the error categories are the ordinary ones; the rule applies when the selection is demanded, never to unused expressions. Lean: the `.index` arm of `evalCounted` over the TOTAL core `selectWith` (laws `selectWith_runs_as_its_trace`, `selectWith_stops_at_first_failure`, `selectWith_pure_preserves_order_and_repetition`, `selection_of_*`, `selected_empty_values_stay_elements`, `single_selection_keeps_no_wrapper`); C#: the Index case of `Evaluator.EvalExpressionSpineCounted` and its async twin through the shared `AdvanceSelection` / `SelectPosition` / `CompleteSelection` (an ordinary slot is demanded as a machine child at its turn — observably its private suspended cell's first demand — and a spread-formed cell is demanded directly; one machine transition, hence one budget/cancellation checkpoint, per supplied selector; a selector failure is positioned at its written slot).

**(F) Syntax and migration boundaries.** Postfix `[` takes zero or more selectors, explicit spreads included (`Data[Indexes*]`; a collection-valued selector is ONE supplied value — `Data[(0, 1)]`, `Data[[0, 1]]` and `Data[()]` are `TypeMismatch`, while `Data[[0, 1]*]` supplies two indices and `Data[[]*]` and `Data[()*]` none). Same-line spaces and tabs before `[` are allowed (`Data [0]`, `Grid [0] [1]`); the `[` must be on the same physical line as the receiver's final token (`Data` newline `[0, 1]` is two rows; `Grid[0]` newline `[1]` is no chain), and once open the selector list may span lines with the ordinary expression-list rules. Commas select siblings (`Grid[0, 1]` is `([10, 20], [30, 40])`), chained brackets descend (`Grid[0][1]` is `20`), and selection is a postfix form with the old `:`'s precedence (`-A[0]` is `-(A[0])`, `A[0] ^ 2` is `(A[0]) ^ 2`, `BuildData(n)[0].sum` selects then calls). The star disambiguation is unchanged: `A*[0]` is the multiplication `A * [0]`; capture-then-select is `(A*)[0]` and select-then-spread `A[0]*`. The colon form is retired: a same-line `expr:selector` is `DiagnosticCode.RetiredColonSelection` (public `KatLangErrorCode.RetiredColonSelection`), recovered as the selection it meant, and a `:`-led line reports the same code; `:` is not syntax. No types, slicing, negative-from-end indexing, string-character indexing, multidimensional coordinates, mutation or user-defined indexing protocol are introduced, and `[]` never resolves a user-visible `at` name.

## Spread semantics

**Summary.** The rules of this section in dense form, with their implementation anchors and pinning tests; the full statement follows.

- Spread preserves failures from its operand's dependencies, arguments and constructed elements, including their category, cause and blame. Only the directly demanded computation's own missing output becomes `SpreadMissingOutput`, retaining its useful demand context (X-29 / Q-36, owner decision 2026-10-24). [`sequences-lists-and-calls.md` § Spread semantics]
- A spread spreads ONE item-producing boundary of its evaluated operand into the surrounding item supply — it creates no value; the RECEIVER decides what the items become (capture materializes a sequence, a collecting binding collects a list, fixed bindings and calls take items individually, root output emits rows). Sequence and list values supply their items; any other value supplies itself. A comma is REQUIRED between a spread and a following item on the SAME line (`A*, B`), because `A* B` multiplies; at the end of a line an attached `A*` already completes its item, so `A*` newline `B` is two items (issue #183), while a detached `A *` newline `B` multiplies; `f((A*, B))` passes a spread plus a value as ONE argument. [`sequences-lists-and-calls.md` § Spread semantics]

A spread expression spreads ONE item-producing boundary of the evaluated operand, contributing its items to the surrounding item supply — it does not create, return, or emit a sequence or list value by itself; the RECEIVER decides what the supplied items become (capture materializes a canonical sequence, a collecting binding collects an exact list, fixed bindings receive items individually, calls receive separate argument slots, root output emits rows). Sequence values and exact list values supply their contained items; other values follow the total item-view rule (an atom or string supplies itself as one item). A comma is REQUIRED between a spread and a following supplied item on the SAME line (`A*, B`), because `A* B` is the multiplication `A * B`; a same-line closing delimiter or fluent receiver boundary may follow a spread without a comma, and so may the end of the physical line after an ATTACHED star (issue #183): `A*` newline `B` is two items wherever a newline separates slots, EOF and a later-line closer end the spread too, while the DETACHED `A *` newline `B` is the multiplication `A * B` (`A* ; B` is invalid semicolon syntax; to pass a spread plus another value as ONE sequence-value argument, write `f((A*, B))`). In a call, evaluating the spread operand is part of assembling the supply, for EVERY callee — a user callable, a clause family, and a builtin alike: if it succeeds, the spread supplies exactly its items; if it fails, that failure (whatever its kind — `SpreadMissingOutput` for the operand's OWN missing output, the preserved failure otherwise, below) is the call's failure, raised before the arity check, before clause selection or binding, and before any later slot — a failed spread never becomes a supplied item (§ Collection builtins, PV-20).

SPREAD FAILURE ORIGIN (X-29 / Q-36, owner decision 2026-10-24; Lean and C# together). Spread preserves failures originating within its operand's dependencies or arguments, including their category, cause and blame; only the operand's OWN missing output becomes `SpreadMissingOutput`, at the operand, retaining its useful property, call and argument context. The OWN missing output is the output check of the computation the operand directly denotes or invokes — `{}*`, `G*` and `G()*` with `G = { public X = 1 }`, and through a parameter or alias, which denote the supplied computation, `P({})` with `P(x) = x*`. A missing output met INSIDE the operand's evaluation is NESTED and keeps its category (`MissingOutput`), its context frames (property, parameter, call, written-argument blame F5) and its source location: a dependency (`H = G + 1` / `H*`, `H()*`, `P(H)`), an argument (`F({})*` keeps exactly the report of `F({})`), a written output row of the operand body (`{ G }*`, and the carrier `A = { G }` / `A*` — while the transparent reference `A = G` reads G itself, so `A*` is G's OWN missing output, `SpreadMissingOutput`, M4★), a constructed value or operator operand (`(G, 1)*`, `[G]*`, `(G + 1)*`), a collector list element (`C(*xs) = xs*` / `C(G)`, also after forwarding the whole collector), a builtin's argument or callback, an argument a pattern or clause inspects, and a dot intrinsic's receiver (`G.string*`). The spread then adds one frame, `while evaluating spread operand H` (`SpreadOperandContext`), never a claim that the operand lacks output; every other failure — an inner spread's own `SpreadMissingOutput` included — is the operand's own and passes unchanged. Empty values and supplies are not missing output (`()*`, `[]*`, `{ []* }*`). The origin is part of the COMPLETED failure (Lean `MissingOutputOrigin`, C# `EvalError.MissingOutput.IsNested`): the demanded computation's output check raises it own, and a subordinate computation's failure is nested in its consumer's outcome (Lean `withNestedMissingOutput` at the row loops, the operator/constructor/selection arms, `applyBuiltinCounted`, the user and family binders and the intrinsic receivers; C# `NestMissingOutput` at their twins, the fused sequence pipeline and the deconstruction right-hand side included), so it survives every memo — a property's cached outcome, a need cell's completed outcome — for every consumer, and the decision (`spreadOperandFailure` / `SpreadOperandFailure`) reads that outcome and evaluates nothing. Pinned by `SpreadFailureOriginTests`, `BuiltinArgumentRoleTests.FailedSpread_PropagatesItsOwnFailure`, Lean `CoreTests/SpreadFailureOrigin.lean`, the explorer `spread*` specials and spec case `spread-preserves-nested-missing-output`. *(Until 2026-10-24 any `MissingOutput` raised anywhere in the operand, however deep and under any frames, was rewritten to `SpreadMissingOutput` and its inner frames dropped.)*

ARGUMENT VIEW SPREAD (CallReference S2): in an argument or selector supply, a spread whose last star opens an argument view (`F(R.Arguments*)`) contributes the captured call's ORIGINAL argument cells — undemanded, callable arguments still callable, values shared with the original call — instead of opened items; a star that would open a view into VALUES (any spread in a value position such as `[R.Arguments*]`, or an inner star of `F(R.Arguments**)`) is `TypeMismatch`. Every other spread is unchanged (`call-by-need.md` § Argument views, CR-11).

## Declaration-level output spreading (the static form, November 2026)

**Summary.** The rules of this section in dense form, with their implementation anchors and pinning tests; the full statement follows.

- DECLARATION-LEVEL OUTPUT SPREADING (static form, November 2026; C# front end only, like Grace): a postfix `*` DIRECTLY attached to a declaration's name or parameter list's `)` (`A* = x, y`, `A(x, y)* = x, y`; `public`, nested, every clause of a family or none) changes no algorithm; implicit-argument resolution spreads every ELIGIBLE CALL — written, lifted or bare-forwarded; `N(args)`, `Path.N(args)`, an extension call `x.N(args)` — whose callee resolves statically through TRANSPARENT aliases to a marked declaration (the existing static receiver reading `ReadDeclaration`, Q3: never through carriers or runtime references, never a new chase), inserting the existing `Expr.SequenceSpread` (`InsertedFor`, diagnostics only) exactly where a written `*` spreads: whole rows, whole argument slots of any callee (no exemption: `if`, `repeat`, `while`, builtins), whole selector slots, list and multi-slot group elements, a written `*`'s operand (`A(1, 2)**`), and an extension edge's receiver (`A(1, 2).F(3)` is `F(A(1, 2)*, 3)`); operands, selection and intrinsic receivers, callees, reads (a bare `P`), parameters, runtime-target aliases, `.Algorithm` link bodies, `R.Algorithm(…)`/`R.Invoke()`, callbacks and loop iterations never spread. Every decision reads the pass's WRITTEN input (a dot edge's detector stamp, never a MAY resolution later refines). D1: a WRITTEN marked call as the receiver of an extension edge makes the edge the lowered call from PARAMETER DETECTION on — `H = A(x, y).F(3)` infers `H(F, x, y)`, as `A(x, y)*.F(3)` and `F(A(x, y), 3)` do; Q7 orders the names and the detector builds the call from ONE reading (`StaticStructureQueries.LoweredReceiver`), and resolution never decides it again (the receiver-first order of every other dot edge is unchanged). D2: a slot the pass spreads — a written marked call, or a bare reference to a marked declaration that formula lifting turns into a call — makes later positions unknown to the formula-lifting roles exactly as a written `*` does; roles and spread slots are decided TOGETHER, left to right, BEFORE signature selection, from static facts (`ArgumentRolesWithSpreads`, read by the one role walk and the rewrite, which checks every prediction: `RequirePredictedLift`): a final signature, or own parameters that require an argument, decide the lift; a body with no own required parameter and no potentially liftable value-role reference in its rows is a read (callable slots and final zero-supply signatures cannot lift; an open body a row names can lift only through a required parameter of its own or, recursively, through its own rows, so a group that reads only itself cannot); anything else is a selection result and is the front-end error `OutputSpreadReferenceNeedsCall` exactly where a later builtin slot's role depends on it (`reduce(P, Add, Inc)` with `P* = Q[0]` and `Q(x) = [[x]]`: write `P(…)` or `{ P }`). So lifting a marked callee equals its explicit call, and a marked program IS its explicit-`*` counterpart, a lifted call's counterpart writing `*` after the bare reference (the oracle; `DeclarationOutputSpreadingTests` compares Lean encodings), so evaluation, Model C, caching, the optimizer and Lean's core are unchanged; only a program whose admission met a marker examines a call (`AdmittedWithOutputSpreadMarkers`, carried into a deferred unit's materialization). Errors: `DetachedOutputSpreadMarker`, `RepeatedOutputSpreadMarker`, `OutputSpreadMarkerOnAlias` (transparent or runtime-target alias, module holder, an `.Algorithm` link that stays a calculation), `MixedOutputSpreadMarkers`, `OutputSpreadMarkerOnDeconstructionTarget`, `OutputSpreadReferenceNeedsCall` (D2); a call's own arity error, or a META refusal only the inserted spread can explain, gains a C#-only note naming the marked declaration (`EvalError.OutputSpreadNotes`, attached at every call dispatch, invocation plans included). Accepted consequences (marked arguments always run; `first(A(1, 2))` is an arity error while `A(1, 2)[0]` works; a marked step needs an unmarked wrapper; parentheses cannot opt out, `{ … }`/`[ … ]`/a property can) are stated there. [`sequences-lists-and-calls.md` § Declaration-level output spreading; `syntax.md` § The declaration-level output-spreading marker]

A declaration written with a postfix `*` after its name or parameter list (`A* = x, y`, `A(x, y)* = x, y`; the syntax: [`syntax.md` § The declaration-level output-spreading marker]) changes no algorithm: its parameters, inference, body and result value stay the same. It changes how CALLS to it are elaborated: implicit-argument resolution rewrites every eligible call into the existing spread expression, as if `*` were written after it (`Expr.SequenceSpread` with the diagnostic-only `InsertedFor`). With `A(x, y)* = x, y` and `Add(x, y) = x + y`, `Add(A(1, 2))` elaborates to `Add(A(1, 2)*)` and is 3, and `[A(3, 4)]` is `[A(3, 4)*]`, `[3, 4]`. It is compile-time shorthand: after elaboration a marked program IS the program with `*` written at those calls, so evaluation, Model C demand, caching, the optimizer and Lean's core are unchanged. THE ORACLE: for every program P with markers, elaborating P gives the tree that elaborating P′ — P with the markers removed and `*` written after each eligible call — gives, spans and marker metadata aside (`DeclarationOutputSpreadingTests` compares the Lean encodings). That includes which references formula lifting turns into calls and the order of inferred parameters. For a call that formula lifting creates, the counterpart writes `*` after the bare reference (`reduce(P*, Add, Inc)`), and formula lifting's own law holds for marked callees too: a lifted reference elaborates exactly as its explicit call. The oracle has no exception (owner decisions D1 and D2, 2026-11-14, below).

**R1 Eligible call.** A call `N(args)`, `Path.N(args)` or `(Path.N)(args)`, and an extension call `x.N(args)` / `x.N` (the call `N(x, args)`, DOT-03) — written, or synthesized by implicit-argument resolution (formula lifting, bare forwarding) — whose callee the front end resolves at compile time (owner walk, prelude, `open`, static member path, loaded module member), through transparent aliases, to a marked declaration. The callee is read as every static callee of the pass is (`ImplicitArgumentResolver.ResolveStaticCallable`'s first step) and followed to its STRUCTURAL identity by the existing static receiver reading (`ReadDeclaration`: Q3's target walk with B3-5★'s selected `.Algorithm` link classes) — the endpoint a transparent reference denotes, a carrier itself, no static identity for a runtime reference — so no new alias chase exists; the invocation projection (`StaticInvocationTarget`) is NOT used, since it continues through carriers. An `.Algorithm` link body is never an eligible callee, whatever its selected class (the reading before selection, so the B3-5★ analysis and the rewrite agree). Every decision reads the WRITTEN input of the pass — for a dot edge the detector's stamped verdict, never a MAY verdict resolution later refines — so an extension call is eligible only when detection already certainly selects its fallback. Only a program whose admission met a marker examines any call (`StaticStructureOperation.AdmittedWithOutputSpreadMarkers`), so every other program elaborates exactly as before.

**R2 Eligible position.** Exactly where a written `*` is legal and spreads (`ImplicitArgumentResolver.SpreadIfMarked`, the one insertion): a whole output row (root, algorithm body, clause branch, block, deconstruction right-hand side, a bare-forwarding body's forwarded call); a whole argument slot of any callee (user algorithm, clause family, builtin including `if`, `repeat` and `while`, Math member, host operation, dot-edge arguments), with no exemptions; a whole selector slot (`L[A(0, 1)]`); a list element, or an element of a multi-slot group; the operand of a written `*` (`A(1, 2)*` becomes `A(1, 2)**`, the chained-spread law, never recursive); and the receiver of an extension-call edge, lowered as the parser lowers a written `R*.F(args)`: `A(1, 2).F(3)` is `F(A(1, 2)*, 3)` (D1, below). Everywhere else the call is its ordinary single value: operator and comparison operands, `not` and unary minus, selection receivers (`A(1, 2)[0]`), receivers of intrinsic edges (`.string`, `.Invoke`, `.Arguments`, `.Algorithm`), and callees. Edge kinds come from the existing dot-edge decision (`FormulaLiftingRoles.EdgeKind` over the detector's stamp), never a spelling check. ARGUMENT ROLES: a slot the pass will spread — a written marked call, or a bare reference to a marked declaration that formula lifting turns into a call — makes the positions after it unknown to the formula-lifting roles exactly as a written `*` does (D2, below), so `H(x) = reduce(P(), Add, Inc)` with a marked `P` leaves `Inc` unlifted, as `reduce(P()*, Add, Inc)` does.

**D1 A marked extension edge is the lowered call from parameter detection on** (owner decision, 2026-11-14). `A(x, y).F(3)`, with `A` marked and `.F` an extension edge (its lexical fallback certainly selected, no intrinsic), is `F(A(x, y)*, 3)` for EVERY front-end decision, the order of inferred names included — exactly what the parser produces for the written `A(x, y)*.F(3)`. So `H = A(x, y).F(3)` infers `H(F, x, y)`, like `A(x, y)*.F(3)` and the marked written call `F(A(x, y), 3)`; with `Add3(a, b, c) = a + b + c`, `H(Add3, 1, 2)` is 6. The receiver-first order of dot edges (`a.t(b)` infers `(a, t, b)`; `ownership-and-lookup.md` § Grace, the dot-edge occurrence order) is unchanged: under R2 a marked extension edge is no dot edge, and `A*.F` is `F(A*)` including implicit callable-parameter detection, with no spread-specific inference exception. It is decided ONCE, where names are ordered: `StaticStructureQueries.LoweredReceiver` composes two existing readings — the edge's miss verdict (Q5) and the receiver call's callee through Q1's binding and Q3's target walk (through transparent references, a carrier itself, no static identity for a runtime reference) — with no signature selection and no new query kind. Q7 (`Inputs`, `OccurrenceOrder`) orders the edge's names by it (only where the member is an inferred name, the one case an order can change; while a fact is undecided it answers only if both readings give one order); the detector's collection walk reads it; and the detector's rewrite BUILDS the call (`ParameterDetector.RewriteLoweredReceiver`): the callee is the edge's own lexical fallback, whose member token keeps its span and its editor site; the receiver stands in a front-end spread (`InsertedFor`, the receiver's span, no marker span, no site); the call spans the edge. Implicit-argument resolution receives the call and decides nothing about it. The receiver may be `N(args)`, `(Path.N)(args)`, `Path.N(args)`, a parenthesized call, a call through a transparent alias, or itself an extension call to a marked declaration (`4.Dup.F` with `Dup(v)* = v, v` is `F(Dup(4)*)`); in a chain `A(x, y).F(3).G(4)` the inner edge is the call and the outer edge keeps its own receiver-first order (`H(F, x, y, G)`, as `A(x, y)*.F(3).G(4)`). A receiver that is a BARE reference formula lifting calls (`P.reduce(Add, 10)`) is lowered by resolution (`LowerLiftedMarkedReceiver`): it holds no inferred name, so no order depends on it.

**D2 A call formula lifting creates for a marked declaration counts as a spread for the roles of the later argument slots** (owner decision, 2026-11-14), exactly like a written one. With `P(x)* = [x]`, `Add(a, b) = a + b` and `Inc(x) = x + 1`, all three of `H = reduce(P, Add, Inc)` (marked), `H = reduce(P(x), Add, Inc)` (marked) and `H = reduce(P*, Add, Inc)` (unmarked `P`) elaborate to `reduce(P(x)*, Add, Inc)`: `Inc` is not lifted, and each fails with the same `ArityMismatch` (`reduce` has no initial value). Roles and spread slots are decided TOGETHER, left to right, each slot's role read at the position state the earlier slots left, BEFORE signature selection (`ImplicitArgumentResolver.ArgumentRolesWithSpreads`; the ONE decision the B3-5★ signature analysis, the rewrite and `CertainMissDecidesALift` read). Whether a bare value-role reference to a marked declaration becomes a call is read from static facts (`StaticLiftOf`): LIFTED when its callee's own parameters (the written list, or the names parameter detection inferred for it) already require a supplied argument; DECIDED BY ITS SIGNATURE when that is final (a registry member, a clause family, a closed list, an earlier completion; inside a closed body the existing closed-list gate applies); NOT LIFTED — a read: no spread (R3) and no role change — when it has no required parameter of its own and its rows hold no potentially liftable VALUE-role reference, so nothing in its body can be lifted. POTENTIALLY LIFTABLE IS DECIDED RECURSIVELY (follow-up of 2026-11-14: the implementation corrected to this rule, no new rule): a value-role reference can lift when its callee, read through Q3 in that body's own context, is a final signature that requires a supplied argument, an open body of this resolution with a required parameter of its own (written, or inferred by parameter detection), or an open body of this resolution whose own rows hold such a reference, by the same rule in THAT body's context; a runtime fact (an `.Algorithm` link) and an undecided dot route stay conservative and keep counting as liftable. The verdict is reachability over contextual bodies (`HoldsALiftableReference`: one memo per resolution, charged to the static ledger, reading no selected signature and no analysis order). It is sound because selection can give a body a required parameter only from an own inferred name, from a lifted reference to a callee that requires arguments, or from a link class it decides: a body that reaches none of them gains none, and a group of open bodies that read only each other reaches none. So with `Q = [[1, 2], 3]` and `P* = Q[0]`, `H = reduce(P, Add, Inc)` is a READ of `P`: it is accepted and elaborates exactly as the unmarked program, `H(x)`, and `H(-3)` is `1` (the earlier any-open-dependency reading refused it). The same formula-lifting role walk excludes callback and neutral user-argument references, and a reference with a final zero-supply signature cannot lift either: `Values(*xs) = [1, 2]` / `P* = [Values*]` and `P* = map([1, 2], Inc)` are reads, so neither changes the later roles in `reduce(P, Add, Inc)`. Each reference is resolved in the marked body's own context, with the result cached per contextual body, never per shared syntax node alone. EVERY OTHER CASE IS A SELECTION RESULT: a marked declaration whose required parameters could come only from formula lifting, such as `P* = Q[0]` over `Q(x) = [[x]]`. It is the front-end error `OutputSpreadReferenceNeedsCall` at the bare reference — "`P` is declared with `*`, and only parameter inference decides whether `P` is called here, which also decides how the later arguments are treated. Write `P(…)` to call it (its result is spread), or `{ P }` to read it without arguments as one value." — the two spellings are two programs, and the message names both (through an alias both use the written name); but ONLY when the elaboration depends on it: a later slot has a different role at a known and at an unknown position (`FormulaLiftingRoles.SlotRole`: after a spread a builtin slot is a value only when every declared slot is, so `reduce`'s initial value and a surplus slot of `map` or `filter` qualify, `if` never does, and a callback slot is callable at both), AND that slot holds a bare reference the value role could lift. `H = reduce(P, Add, Inc)` is the error; `reduce(P, Add, 0)`, `count(P)`, `if(…)`, a user callee, and a later reference neither role lifts are not, and there the reference is spread if selection lifted it. The rewrite checks each prediction against the call it built and fails loudly on a mismatch (`RequirePredictedLift`, the mirror of `RequireSelectedComposition`). A REFUSED MARKER DECIDES NOTHING AT ITS USES (follow-up of 2026-11-14): no use of a declaration whose marker the front end refuses gets `OutputSpreadReferenceNeedsCall`; one problem gives one diagnostic. Where the refusal is known before the roles are decided the declaration is unmarked there too: the parser drops a module holder's marker and stores none for a deconstruction target; a transparent alias is read through to its target (only the target's marker counts), but its own refused marker suppresses the needs-call report at its uses even when that target is validly marked (an unmarked alias keeps the target's use-site obligation); an unbraced `.Algorithm` link and a parameter row have no static structure to carry one. Where only selection reveals it — a braced body the rewrite makes a runtime-target alias, such as `P* = { Link }` over a `Link = Mk.Algorithm` whose `Mk` takes nothing — the use-site report is suppressed (`ReportOutputSpreadReferenceNeedsCall` asks `IsRuntimeTargetEndpoint` of the reference's invocation endpoint, the selected class the rewrite forms the alias from): the refusal at the declaration is the one diagnostic, and such a program never runs. With `Mk = [7]`, `P* = { Mk.Algorithm }` is now a certain read by the recursive rule, so its use never asks. A detached or repeated marker is a misspelled marker that STANDS, and a clause family with mixed markers recovers marked (a family's signature is final, so it is never a selection result): a use-site report there is genuine. Pinned by `DeclarationOutputSpreadingTests` (`LiftedMarkedCall_IsItsExplicitCall_AndTheUnmarkedExplicitSpread`, `BareReferenceThatIsRead_NeverSpreads_AndChangesNoRole`, the `SelectionDependentReference_*` theories, `MarkedExtensionEdge_IsTheLoweredCall_FromParameterDetectionOn`; for the follow-up `CertainRead_IsAccepted_AsItsUnmarkedCounterpart`, `ReferenceThatCanLift_StaysASelectionResult`, `GeneratedDependencyShapes_AreReadOrReported_ExactlyAsReachabilityDecides`, `SelectionDependentReference_NamesBothSpellings_AndBothAreAccepted`, `RefusedMarker_IsTheOneDiagnostic_AndItsUsesGetNone`, `MisspelledMarker_Stands_SoItsUseSiteReportIsGenuine`) and the spec cases `output-spread-receiver-edge-is-the-lowered-call`, `output-spread-lifted-call-ends-known-positions`, `output-spread-reference-needs-call`, `output-spread-reference-certainly-read`.

**R3 Not eligible, by design.** Calls through a parameter (`f(1, 2)`); runtime-target aliases (enclosing-parameter rows, `.Algorithm` links, parameter-rooted member paths, and aliases of these); `R.Algorithm(…)`; `R.Invoke()`; invocations a builtin performs (callbacks, loop iterations); and reads. A read is not a call (CDO-1): a bare `P` or `V` never spreads, even when `P` is a marked zero-parameter declaration.

**R4 Where the marker may be written.** Allowed: an algorithm with written or inferred parameters; a zero-parameter declaration (then only explicit calls `P()` spread); a structural forwarding carrier (`B* = { A }`); nested and `public` declarations; a clause family, on every clause or on none. Not allowed (`DiagnosticCode.OutputSpreadMarkerOnAlias`, reported where the alias is formed, with a marked-wrapper suggestion `B(x, y)* = A(x, y)`): a transparent alias (`B* = A`), a runtime-target alias, an `.Algorithm` link that stays a calculation (`A* = Mk.Algorithm`), and a module holder (`M* = load('url')`); and a deconstruction target (`a*, b = …`). An alias of a marked declaration inherits the marker (R1). Carriers, explicit wrappers (`W(x, y) = A(x, y)`) and bare-forwarding bodies (`G(x, y) = A`) are declarations of their own: calls to them spread only if they are marked, while a marked call written inside them spreads where it stands.

**R6 Timing.** Exactly the explicit `*`'s: a marked call in an argument or selector slot is evaluated once, while the supply is formed, before the arity check, whether or not the callee uses it. Caching is unchanged: `P()` stays a fresh call, `P` the cached read. **R7 No opt-out syntax**: parentheses stay transparent (`(A(1, 2))` is `A(1, 2)` and spreads); to keep one value, write `{ A(1, 2) }`, `[A(1, 2)]` (a list) or a property (`V = A(1, 2)`, then `V`).

ACCEPTED CONSEQUENCES (documented, not defects): the same algorithm behaves differently by route — `Add(A(1, 2))` is 3, but `Apply(f) = Add(f(1, 2))` / `Apply(A)` is an arity error; explicit wrappers and stored results lose the marker, aliases keep it. Marked calls in arguments always run, even when unused (`FirstOf(5, D(1, 0))` with `D(x, y)* = x / y, y` is `DivisionByZero`). A marked algorithm cannot be a loop step or a `meta` argument directly — `Fib(0, 1).repeat(10)` is `repeat(Fib(0, 1)*, 10)`, an arity error; the workaround is an unmarked wrapper `F(a, b) = Fib(a, b)`, whose row spreads (`F(0, 1).repeat(10)` is `(55, 89)`); there is no exemption for `meta` parameters. Item positions and value positions differ: `A(1, 2)[0]` is 1, while `first(A(1, 2))`, `A(1, 2).first`, `count(A(1, 2))`, `sum(A(1, 2))` and `if(true, A(1, 2), 0)` are arity errors. Marking a public declaration changes every caller, including code that imports it. Lifted calls spread like written ones (`S = [A]` / `S(1, 2)` is `[1, 2]`; `C = count(A)` / `C(1, 2)` is an arity error). The rule lives only in the C# front end (like Grace): Lean sees the inserted spreads and does not check where they were inserted.

DIAGNOSTICS. When a call fails with its OWN cardinality error or META refusal and some of its argument slots are inserted spreads, the error carries one note per slot (`EvalError.OutputSpreadNotes`, C# wording only; kind, payload, code and span unchanged), rendered after the message: "`Fib(0, 1)` supplies 2 arguments here because `Fib` is declared with `*` (line 1). To pass its output as one value, write `{ Fib(0, 1) }`." The count is stated when the call has exactly one spread slot; a module's declaration has no line. A META refusal is noted only when the refused cell provably came from the inserted spread: the refusal has no written occurrence (META-DIAG-2 positions every written argument's refusal at it) and the inserted spread is the call's only spread slot — so `C(5, P())` with `C(meta op, x)` blames `5`, never `P()`. Attached at every call dispatch before the call's frame (`Evaluator.WithOutputSpreadNotes`: the call funnel, the written-callee and `.Algorithm`-callee dispatches, dot edges, and invocation plans, sync and async), on the error path only. Pinned by `DeclarationOutputSpreadingTests`, the `output-spread-*` spec cases, `DiagnosticCodeTests`.

## Call argument assembly and written-slot reification

**Summary.** The rules of this section in dense form, with their implementation anchors and pinning tests; the full statement follows.

- Call argument-slot assembly (supply FORMATION) is SHARED by every callable shape (`FormNeedSupply` / Lean `formNeedSupply`): the written slots are formed left to right — each non-spread slot into ONE suspended supply cell that is evaluated AT MOST ONCE, on its first VALUE demand, and never if nothing demands it (`call-by-need.md`; NEED-01..03), each arbitrary spread slot evaluated during formation and spread one boundary into ordinary slots BEFORE arity checking, clause selection, or pattern binding (a known collector slice transfers its cells unforced, written directly or, A-2, as a name or accessible member path that reaches the collector's parameter row through transparent references only, or through a parameter holding such a reference: `Pass(A)` stays ONE ordinary argument and only a later explicit `v*` opens the slice; selecting a member never crosses its receiver's output, and braces, calculations, calls of a member and parameter-headed paths stay arbitrary: `Evaluator.WrittenCollectorSlice`, Lean `EvalBody.transparentCollectorSlice?`, NEED-07) — every non-spread slot reifies to ONE value, and every non-spread slot — a capture, a block, a name, a call, a literal alike — is evaluated, when demanded, through the ONE `EvalCounted` / `evalCounted` (no callee shape receives a second, written-slot view of a slot; a patterned callee opens the slot's VALUE). FORMATION IS SHARED, DEMAND IS NOT (X-18, closed 2026-10-10): which formed cells a callee demands, and in what order, is its own — a user callee's inspecting patterns and the consumers its body executes, a builtin's argument roles (BUILTIN ARGUMENT ROLES, § Collection builtins; `if` demands its condition, then only the selected branch) — so no rule makes every callee evaluate every argument, or evaluate its arguments in written order. WRITTEN-SLOT REIFICATION holds wherever the grammar defines one value per slot (list elements, sequence-value pattern items, the reduce initial accumulator); root/body rows and loop-step outputs keep multi-item emission. [`sequences-lists-and-calls.md` § Call argument assembly and written-slot reification]

Resolution selects one callable identity before supply formation. Non-spread written arguments become suspended cells without VALUE evaluation or callable probing. A written parameter reference transfers the exact existing cell. Explicit arbitrary spreads evaluate and open one value during supply formation; known collector slices, written directly, through a name or member path of transparent references, or through a parameter holding such a reference as one ordinary argument (`Pass(A)` with `Pass(v) = Coll(v*)`; NEED-07), transfer element addresses. That argument stays one supplied cell until the explicit spread runs. Supply cardinality is checked before ordinary arguments are demanded.

FORMATION IS SHARED, DEMAND IS NOT (X-18, closed by the owner on 2026-10-10, confirming the Model-C law). Every callee category forms its supply as above; which formed cells it then demands, and in what order, is the callee's own. A user callee demands through its inspecting patterns (NEED-04) and the consumers its body executes; a builtin through its argument roles (§ Collection builtins — `if` demands its condition, then only the selected branch); a callback or loop step is projected for its CALLABLE identity only when it is invoked, never VALUE-demanded (NEED-06). **Summary.** The rules of this section in dense form, with their implementation anchors and pinning tests; the full statement follows.

STRUCTURAL PATTERN DELIMITERS SELECT THE VALUE KIND THEY DESTRUCTURE (September 29 2026; an INTENTIONAL pre-release valid-source semantic change, Lean and C# changed together). KatLang has two collection kinds (§ Lists), and each has its own pattern language, with the delimiter that constructs the kind:

| Pattern | Matches |
| --- | --- |
| `x` | any one value, bound whole |
| `()` | the empty sequence value only |
| `(x, y)` | a sequence value of exactly two elements |
| `(x, *rest)` | a sequence value of at least one element; `rest` collects the others as an exact list |
| `(*xs)` | any sequence value; `xs` is the exact list of its elements |
| `[]` | the empty list only |
| `[x]` | a list of exactly one element |
| `[x, y]` | a list of exactly two elements |
| `[*xs]` | any list, of any cardinality — 0, 1 and N alike |

THE KIND LAW. A sequence pattern `(p1, …, pn)` opens a SEQUENCE value and nothing else (Lean `Result.sequencePatternItems?`, C# `Result.SequencePatternItems`); a list pattern `[p1, …, pn]` opens a LIST value and nothing else (`Result.listPatternItems?` / `ListPatternItems`). There is no cross-kind matching (`FirstPair((x, y))` rejects `[10, 20]`, `PairSum([x, y])` rejects `(10, 20)`), no scalar-as-one-item fallback (`(x, *rest)` rejects `7`; before this law a scalar was a one-item supply at every pattern level), and no implicit list↔sequence conversion in any layer. A bare binder is the ONLY pattern that takes a value whole. Nesting preserves kinds at every level: `F(([x, y], z)) = x + y + z` takes a sequence whose first element is a two-element list (`F(([10, 20], 30))` is 60), `G([(x, y), z])` a list whose first element is a pair, and each level is checked against its own delimiter.

THE SINGLETON RULE. A sequence pattern with exactly ONE non-collecting item — `(x)`, `((x))`, `(([x]))`, `(((x, y)))`, `(((true)))`, at any depth — is INVALID: a sequence value never has exactly one element (`(7)` IS `7`, normalization), so the pattern describes a boundary no value has. The parser reports `DiagnosticCode.SingletonSequencePattern` (`Parser.SingletonSequencePatternDiagnostic`, the wording of Lean `singletonSequencePatternMessage`) at the group, in parameter lists and clause heads alike, and never rewrites `F((x))` to `F(x)`; a host-built tree carrying one is refused before evaluation (Lean `validateExplicitParamOutputInvariant` → `illegalInEval`; C# `PreEvaluationAstViolation.SingletonSequencePattern`), so no layer gives the pattern a meaning the surface refuses it. The collector-only `(*xs)` is not a singleton (it matches every sequence, `()` included), and lists have the one-element pattern `[x]` because a one-element list is a value. `()` and `[]` are distinct patterns, exactly as `()` and `[]` are distinct values.

OUTER ARITY IS NOT STRUCTURAL SHAPE. Every top-level pattern consumes ONE argument whatever it destructures (`ParameterPattern.minimumSuppliedSlots`), so `F((x, y))` and `F([x, y])` are one-parameter callables and `F(1, 2)` is their arity error; the pattern then opens that one value.

FAILURES USE EXISTING CATEGORIES, and ordinary binders and clause families apply the SAME law. In an ordinary definition (and a callback, loop step, or zero-argument demand, which bind through the same binder) a value of the wrong kind fails the binding with `TypeMismatch` from ONE constructor (Lean `structuralPatternKindMismatch`, C# `Evaluator.StructuralPatternKindMismatch`), naming the written pattern and the value received ("sequence pattern `(x, y)` expects a sequence value, but received numeric value 7"), and a value of the right kind with the wrong number of elements is the group's `ArityMismatch` ("Sequence pattern `(x, y)` expects 2 elements, but received 3 elements.", "at least" for a pattern with a collector; the list form says "List pattern"). In a clause family neither is raised: a clause whose pattern does not match — wrong kind, wrong length, unequal literal — is skipped, and a call no clause matches is `NoMatchingBranch`. Single-clause classification is the same for both kinds (PAT-01: one literal-free binder/group clause is an ordinary algorithm, whether its groups are sequence or list patterns), and duplicate-clause detection is kind-aware (`F((a, b))` and `F([a, b])` are different heads, `F([]) = 0` beside `F(()) = 1` is not a duplicate).

ASSIGNMENT DECONSTRUCTION IS NOT A WRITTEN PATTERN. `x, *y, z = RHS` is the UNPACKING receiver: it opens a lone sequence OR lone list right-hand side one level and matches the flat targets against the items (§ Collecting parameter lists, deconstruction, and callbacks). It is modeled as its own construct — Lean `ParameterPattern.unpacking`, C# `UnpackingParameterPattern`, ONE node shared by every target's helper — so the kind law stays exact for every written pattern while deconstruction's values, errors and linear cost are unchanged; a right-hand side without output is its own `MissingOutput`. There is no bracketed deconstruction target, and none is added for symmetry.

Pins: `BuiltinArgumentRoleTests`, `ModelCProductionTests`, `CoreTests.BuiltinArgumentRoles` and `CoreTests.ModelC`.

## Callback results

**Summary.** The rules of this section in dense form, with their implementation anchors and pinning tests; the full statement follows.

- Q-25's `map` unfolding equation compares RESULT VALUES for pure, deterministic, total computations: a mapped position reads its source position before its transform runs, when that position is read (lazy collections, issue #204), while expanded Model-C calls follow ordinary demand order and can skip unused computations. `reduce` preserves each complete ordinary call result as the next accumulator, and its unfolding `reduce([a, b], R, i)` = `R(b, R(a, i))` holds for the DEMAND of its accumulators too (§ Lazy `reduce` accumulators); only the elements differ, a fold computing its whole collection first. Effects, random draws, failures and resource budgets keep those established rules. [`sequences-lists-and-calls.md` § Callback results]

A CALLBACK RETURNS ITS ORDINARY CALL RESULT (HO-03; Q-25, owner decision of October 10 2026, Option B). A `map` transform or `reduce` step is invoked exactly as the direct call over the values the operation supplies (the callback law, § Collecting parameter lists, deconstruction, and callbacks), and what it returns is that call's result — the ONE value the call boundary delivers (§ Value boundaries; VAL-06): several written rows (or a spread row's several items) arrive as ONE sequence value, `()` and `[]` are ordinary values, and nothing is spread. `map` stores each result whole as ONE element of its list; `reduce` passes each result whole as the next accumulator, and its own result is the final accumulator (which steps run at all is decided by demand: § Lazy `reduce` accumulators). There is no cardinality check and no non-empty check on a callback result, so:

* For pure, deterministic, total computations, `map(L, F)` has the same result value as `[F(L[0]), F(L[1]), …]`, and `reduce([a, b], R, i)` has the same result value as `R(b, R(a, i))`. Every callable category uses the ordinary callback result: a user algorithm, a clause family (its selected clause's ordinary call, PAT-11), an alias, a Math member and a host operation alike.
* Wrappers are invisible: with `D(x) = x, x`, `G(x) = D(x)` and `H(x) = (x, x)`, `[1].map(D)`, `[1].map(G)` and `[1].map(H)` are all `[(1, 1)]`, exactly `[D(1)]`.
* The identity map reproduces every list: `map([(), 1, [], 2], Id)` with `Id(x) = x` is `[(), 1, [], 2]`.
* Every value is a legitimate accumulator: `R(x, acc) = x, acc` gives `reduce([1, 2], R, 0)` = `(2, (1, 0))` (one sequence value per step, nested, never spread), and `R(x, acc) = acc` over the initial `()` gives `()`.
* A reduce RESULT is a value boundary like every builtin result: its emitted count is `Result.valueCount` of its value (0 exactly for `()`).

`()` is an ordinary element and an ordinary accumulator — it never means "skip this element" or "keep the previous state"; use `filter` to omit elements. A callback body with an unintended extra row is VALID and produces a sequence value the author did not mean, exactly as the same body called directly would.

Owner clarification (2026-10-10, as amended by issue #203 in November 2026): the `map` unfolding equation compares result values for pure, deterministic, total computations; it does not guarantee identical effect ordering, argument demand, random draws, resource consumption or error timing. A mapped position reads its source position before its transform runs (§ Lazy collections and pipelines, issue #204); expanded calls can ignore indexed arguments. With `L = [tick(), tick()]` and `F(x) = tick()`, `map(L, F)` is `[2, 4]`, while `[F(L[0]), F(L[1])]` is `[1, 2]`. For `reduce` the equation is stronger since November 2026: `reduce([a, b], R, i)` is `R(b, R(a, i))` in value AND in the demand of its accumulators (§ Lazy `reduce` accumulators), so with `R(x, acc) = x`, `reduce([1, 2], R, 1 / 0)` and `R(2, R(1, 1 / 0))` are both `2` (the fold failed until November 2026), and with `R(x, acc) = tick() * x + acc` the fold and the nested expression are both `4` (the fold was `5`). Only the ELEMENTS still differ: a fold computes its whole collection first, the written nest evaluates each element where its call demands it (`[tick(), tick()].reduce(Sub, 0)` is `1` and `Sub(tick(), Sub(tick(), 0))` is `-1` with `Sub(x, acc) = x - acc`). Pins: `CallbackResultBoundaryTests.Independent_Reduce*` / `Independent_Map*`, `LazyReduceAccumulatorTests`, canonical cases `reduce-accumulators-are-evaluated-on-demand`, `reduce-demands-only-the-steps-it-needs`, `reduce-effects-follow-accumulator-demand`, `reduce-empty-collection-demands-initial-once`, `map-demands-collection-before-transforms` and `expanded-map-calls-may-skip-indexed-arguments`.

Failures of the invocation propagate unchanged: an output-less callback is still `MissingOutput` (VAL-05; never `()`), a callback's cardinality error keeps its plain `ArityMismatch` shape (the C# drivers' `variadicArityStyle` shapes only that diagnostic; ordinary calls report the variadic form), and errors, spans, demand order, effects, seeded draws and budget charges are the direct call's. Unchanged consumers: `filter` reads its predicate's VALUE and keeps its Boolean contract (`booleanRequiredMessage`), a loop step's ROWS are still its next state (§ Loops), Q-23 step dispatch, Model-C demand, clause-family selection and every pattern.

HISTORY (superseded). #135 (July 2026) required a transform or step to EMIT exactly one top-level value that is not `()`, judged by the callback's RAW emitted count before any re-count (Lean `expectSingleValueWith` / `expectSingleAccumulator` / `expectSingleMappedElement`, C# `ExpectSingleEmittedValue` and its two wrappers; the errors "map transform must return a single element" / "reduce step must return a single accumulator value"), and D1 (October 9 2026) made a clause family obey the same raw count. Q-25 replaced the law because, after ordinary calls became value boundaries, retaining the raw-output callback restriction broke compositionality, identity mapping and wrapper equivalence: `[1].map(D)` failed while `[1].map(G)` and `[1].map(H)` succeeded with the same value, `map([(), 1], Id)` failed on its own element, and no reduce step could return `()`. The checks are deleted, the callback drivers always re-count at the call boundary (Lean `evalNeedUserSupply` / `evalNeedFamilySupply`, C# `EvalNeedUserSupply*` / `EvalNeedFamilySupply*`), and the former `recount` flag survives in C# only as the separated diagnostic style. Pins: `CallbackResultBoundaryTests`, `ClauseFamilyCallbackCardinalityTests`, `ClauseFamilyCallbackCardinalityBoundaryTests`, `CoreTests/CallbackResultBoundary.lean`, `CoreTests/FamilyCallbackCardinality.lean`, the spec cases `callback-result-is-the-ordinary-call-result`, `map-identity-preserves-empty-elements`, `reduce-accumulator-may-be-empty`, `clause-family-multirow-callback-is-one-value` and `clause-family-multirow-reduce-step-is-one-value`.

## Lazy `reduce` accumulators

**Summary.** The rules of this section in dense form, with their implementation anchors and pinning tests; the full statement follows.

- LAZY `reduce` ACCUMULATORS (issue #203, November 2026; Lean first): `reduce` forms its supply and checks its arity through the ordinary call path, demands its collection as an ordinary whole value, then — EMPTY: demands `initial` once and returns it, the reducer never projected; NONEMPTY: projects the reducer and demands ONLY THE LAST STEP. Each invoked step is the ordinary `reducer(element, accumulator)` over its already evaluated element and ONE DEFERRED accumulator cell, whose demand runs the preceding step or evaluates `initial`. A demanded accumulator memoizes its value or ordinary failure (forwarding never evaluates it; reads and pattern inspections share its completion), a reducer that ignores its accumulator skips every step only it would reach (`Pick(item, acc) = item`: `reduce([1, 2], Pick, 1 / 0)` is `2`), and effects follow actual demand (`R(item, acc) = tick() * item + acc`: `reduce([1, 2], R, 0)` is `4`). Each accumulator is ONE slot at the ordinary counted value boundary, demanded through the existing binder and argument roles (a plain binder does not demand it; an inspecting pattern, a clause head, a strict builtin or host reducer do). Synthetic accumulator cells are VALUE-only: no CALLABLE identity, no invocation plan (a `meta` parameter refuses them), no retained slice; `initial` is never replayed and reports through the existing initial-accumulator path; a failure gains ONE reduce step frame however many accumulators its demand crossed. Lean: the DEFERRED control (`SequenceBuiltinSuffixArgDescriptor.deferred`) and the deferred application `NeedSuspension.applied`, chained by `EvalBody.evalReduceCounted`. C#: `Evaluator.ReduceFold` (one entry with an `asynchronous` flag; the general route uses a plain synchronous step and callback dispatch, and each accumulator demand restores the host context of the step that requested it). C#-only host policy: a suspended step is a FOLD CONTINUATION accounted apart from call depth (`EvaluationBudget.EnterFoldContinuation`: every step runs at the fold's own depth, genuine recursion inside a reducer still counts), kept on the heap as a segment of its fold's trampoline (`FoldTrampoline`: a drain loop starts each demanded segment and resumes each waiting step from its own frame, so a fold runs on the demanding thread with the native stack of one step; the synchronous evaluator keeps at most `HostStackAllowance` continuations on the host stack and pumps the rest through the async twins on the calling thread — no other thread, no thread-pool hop, no wait for either); a reducer that LEADS WITH ITS ACCUMULATOR (`acc + x`) takes the STREAMED route (`ReduceFold.Stream`): the same value, effects, ordinary failures and total charges with no step suspended, chosen from the reducer's structure alone (a step's expression work before its accumulator read is charged when its body runs, so a step limit that runs out inside the fold stops after more completed steps than the nested order would). Never reintroduce the eager loop, a per-level error frame, callable or plan identity on an accumulator cell, or a route choice that reads values, limits or configuration. [`sequences-lists-and-calls.md` § Lazy `reduce` accumulators; `evaluator-and-hosting.md` § Limits observe a run]

`reduce` EVALUATES ITS ACCUMULATORS ON DEMAND (issue #203, November 2026; Lean and C# together, Lean first; it replaces the operational paragraph of the owner clarification of 2026-10-10 under § Callback results). THE RULE: `reduce(collection, reducer, initial)` forms its supply and checks its three-argument arity through the ordinary call path, demands its `collection` as an ordinary whole value (the existing top-level item order and collection validation), and then:

* for an EMPTY collection, demands `initial` once and returns its value at the ordinary value boundary; the reducer is never projected;
* for a NONEMPTY collection, resolves the reducer through the ordinary callback projection and demands ONLY THE LAST STEP. The fold associates as a left fold — `reduce([a, b], R, i)` is `R(b, R(a, i))` — and each invoked step is the ordinary invocation `reducer(element, accumulator)` over its ALREADY EVALUATED element (one Ready value, exactly as collected) and ONE DEFERRED accumulator. Demanding that accumulator runs the preceding step, or evaluates `initial`.

So `reduce([a, b], R, i)` is `R(b, R(a, i))` in value AND in the demand of its accumulators (the elements differ: a fold evaluates its whole collection first, the written nest evaluates each element where its call demands it):

* a reducer that ignores its accumulator skips every step that only that accumulator would have reached, and the initial expression with them: with `Pick(item, acc) = item`, `reduce([1, 2], Pick, 1 / 0)` is `2`, and only the final `Pick` call executes; with `R(item, acc) = if(item == 1, 1 / 0, item)`, `reduce([1, 2], R, 0)` is `2`;
* a demanded accumulator is evaluated ONCE: each accumulator is a need cell that memoizes its counted value or its ordinary failure; forwarding passes the cell without evaluating it, and reads and pattern inspections share its completion (`R(item, acc) = tick() + acc + acc` over `[1, 2]` from `tick()` is `17`: one draw for the start, one per step);
* effects follow actual demand: with `R(item, acc) = tick() * item + acc`, `reduce([1, 2], R, 0)` in a fresh run is `4`, because the step for `2` draws `1` first (until November 2026 it was `5`);
* a demanded `initial` fails where it is demanded: with `Add(item, acc) = item + acc`, `reduce([1, 2], Add, 1 / 0)` is `DivisionByZero`, and so is `reduce([], Add, 1 / 0)`;
* a failure of an element is the collection's: `reduce([1 / 0, 2], Pick, 0)` is `DivisionByZero` before any step.

THE ACCUMULATOR SLOT. Each accumulator occupies ONE slot at the ordinary counted value boundary — the initial value, each completed reducer result and the fold result alike — so an empty sequence, a list or a multirow result is one accumulator with its ordinary value shape (§ Callback results is unchanged). The slot is demanded through the existing binder and argument roles: a plain binder does not demand it (only the body's read does), an inspecting pattern (`R(item, (a, b))`) and a clause head (`R(item, 0)`) demand it during binding and dispatch, a strict builtin (`Math.Pow`) or a host operation demands it as its ordinary argument.

SYNTHETIC ACCUMULATOR CELLS ARE VALUE-ONLY. An accumulator cell is a calculation, never the written argument: it has no CALLABLE identity (`Call(item, acc) = acc(item)` with `reduce([1], Call, Inc)` is `NotAnAlgorithm`, while `Call(1, Inc)` is `2`), it is no invocation plan (a `meta` parameter refuses it with the ordinary META refusal, where the direct call `R(1, F(5))` captures the written call), and it retains no collector slice (`count(acc)` over a collector passed as `initial` materializes the whole exact list). The start is a NEW cell over the ORIGINAL `initial` computation: that computation is demanded through the value-slot law — at most once, never replayed — and its callable identity, retained slice and written-call plan stay behind. A demanded initial failure is reported through the existing initial-accumulator path (`reduceInitialRejection` / `ReduceInitialRejection`: `reduce([1, 2], Add, Inc)` still reports the reducer written where the initial accumulator belongs, now when a step demands the start). A WRITTEN SPREAD is supply formation and runs whether or not the slot it supplies is demanded (`reduce([1, 2], Pick, One*)` evaluates `One`).

FAILURES. A demanded step's failure keeps its own source position and structured error and is the fold's failure; the fold adds ONE reduce step frame around the demand of its last step, however many accumulators that demand crosses (never one frame per fold level). A resource limit or a cancellation a demanded step reaches is terminal for the run exactly as before; a skipped step reaches none.

BUDGETS AND STACKS (C#-only host policy; no Lean counterpart). An executed step charges one invocation and its own work, at the existing chokepoints; a skipped step charges nothing. A step suspended while its accumulator is evaluated is a fold CONTINUATION, accounted separately from call nesting (`EvaluationBudget.EnterFoldContinuation`): every step of a fold runs at the depth the fold began at, so a fold over any admitted collection stays within `MaxDepth` exactly when one step does, while genuine recursion inside a reducer (a reducer that calls itself, a fold started inside a reducer) still counts from that depth and reaches the same ceiling. A fold whose reducer uses every accumulator holds one suspended step per element, and it keeps them on the heap (single-thread fold progress, November 2026; `Evaluation/FoldTrampoline.cs`, [`evaluator-and-hosting.md` § Limits observe a run]): each accumulator's computation is a SEGMENT of the fold's trampoline, whose drain loop starts a demanded segment and resumes a waiting step from its own frame, never nested in the step that completes, so the fold keeps the native stack of one step however long it is and runs on the thread that demands it — with no other thread, no thread-pool hop and no blocking wait, on a single-threaded host such as a browser worker too. The asynchronous twins send every accumulator demand through the trampoline. The synchronous evaluator keeps a short chain on the host stack (at most `FoldTrampoline.HostStackAllowance` continuations per thread, each a plain synchronous step and the accumulator demand's context boundary) and continues a longer one on the heap through the asynchronous twins, pumped on the calling thread. Evaluator awaits in a segment capture the private ready queue, including under a custom host task scheduler, except where a pump resumes a step's frames inline in its own completion cascade ([`evaluator-and-hosting.md` § Limits observe a run], INLINE RESUMPTIONS). Synchronous host callbacks keep the ambient values and flow state of their own step across its accumulator read. A segment is exactly the computation the demanding step would run in place, started at its demand and finished before it resumes, so values, effects and their order, random draws, charges, limit verdicts and `DemandCycle` are those of the nested evaluation. Such a fold costs time and memory proportional to its length where the former loop held one step: its suspended steps are heap state (measurements: [`evaluator-and-hosting.md` § Limits observe a run], COST).

THE STREAMED ROUTE (C#-only implementation optimization; no Lean counterpart; `Evaluator.ReduceFold.Stream`). A reducer that LEADS WITH ITS ACCUMULATOR — a user algorithm without `open` whose head is two plain, differently named parameters and whose first output row reaches the read of its second parameter before anything observable, through operands the evaluator takes left to right past number or Boolean literals and the element's own read (`acc + x`, `{x + total}`, `acc * 10 + item`, `acc < item`; `LeadsWithItsAccumulator`) — demands every accumulator of its fold, each before anything else its step does. The nested evaluation of such a fold is therefore fully determined: every step is entered, last step first, with no effect but its invocation charge; the start is evaluated; every step completes, first step first. The streamed route performs exactly that sequence without suspending a step: the invocation charges of all steps, last step first, then each body in order over a completed accumulator (the start's own deferred cell for the first step, so the first step's leading read is what evaluates `initial`). Value, effects and their order, ordinary failures with their positions, and the budget charges of a completed run are those of the nested evaluation (`StreamedReduceFoldEquivalenceTests` compares the two on every route, and under every step limit of its three-element folds, through `ReduceFoldTestSeam`), and the fold costs what the former loop cost however long it is. ONE DIFFERENCE, which only a run that a step limit stops INSIDE such a fold can observe: the nested evaluation charges the expression work a step does before its accumulator read on the way down, before the first step completes, while the streamed route charges it when that step's body runs — the same total, charged later. A `MaxSteps` budget that runs out inside the fold therefore lets the streamed fold complete more steps before it stops: one more step of budget per 4,096 expression checkpoints the nested descent would have charged ahead (measured: `R(item, acc) = acc + trace(item)` over `range(1, 20000)` under `MaxSteps = 20020` makes 20 host calls on the streamed route and 6 on the general one). The verdict is `EvaluationStepLimitExceeded` at the same consumed total either way, the limit law is untouched (a run that completes is the run without the limit), and Q-09b's agreement between strategies holds, because the route is chosen from the reducer's structure alone: the generic, optimized and asynchronous strategies all take the streamed route for such a reducer and stop at the same point. Every other reducer — one that calls, selects, inspects a pattern or computes with its element before it reads the accumulator, a clause family, a builtin, a host operation — takes the general route above. For a very long collection prefer an accumulator-led reducer, or a dedicated builtin (`sum`, `min`, `max`, `count`).

## Lazy collections and pipelines

**Summary.** The rules of this section in dense form, with their implementation anchors and pinning tests; the full statement follows.

- LAZY COLLECTIONS AND PIPELINES (issue #204, November 2026; Lean first): a list is a finite collection of POSITIONS, each read by one VALUE demand shared per position per list INSTANCE. A list literal captures one deferred VALUE computation per ordinary written element in its own environment (an explicit spread, and a declaration-level output spread, is formed with the list; its cardinality is known when it is built); `map` preserves positions, reads the SOURCE position first and then projects its mapper on first use (`first(map([1 / 0], 7))` is `DivisionByZero`, `count(map([1 / 0, 2], 7))` is `2`); `filter` discovers its matches in source order, keeps the accepted positions and its scan frontier, never inspects a candidate twice and memoizes an ordinary failure at its frontier; `take` validates its count before any position and is a prefix sharing its source's state. Consumers read what they need: `count` the cardinality, `first`/`last`/selection the positions they name in written order, a list pattern or unpacking the kind and cardinality before any field (names and collecting bindings bind the original positions as VALUES), an explicit spread and the strict collection builtins one level in order (`reduce` obtains the complete collection first), evaluator equality / `contains` / `distinct` / repeated names / `atoms` the whole value in operand order, and the RUN RESULT is assembled first and then materialized left to right, depth first, while the run is active (a host argument where the operation is called). So `[10, 1 / 0][0]` is `10`, `[1, 2].map{if(n == 1, 10, 1 / 0)}.first` is `10`, `[1, 0].filter{1 / n > 0}.take(1)` is `[1]`; with `L = [tick(), tick(), tick()]` the rows `L[2, 0, 2], L[0], tick()` are `(1, 2, 1)`, `2`, `3`, and with `L = [tick()]` the rows `L, tick()` are `[2]`, `1`. A value that holds itself through a deferred position (`L = [L]`) is a `DemandCycle` when it is read whole. Diagnostics never force an untouched element (`<deferred>`); a passive property observation shows a concrete form the run built or, for a list of settled cardinality, the memoized values of every position it read (one by one or through a completed scan), and is `Withheld` otherwise. Lean: `Result.deferred` / `Result.pendingList`, § "Lazy collections" of `KatLang.lean`, the internal builtins `mappedBuiltin` / `keptBuiltin` / `takenBuiltin` / `materializedBuiltin` as deferred applications, `NeedCapabilities.positions` / `.whole`, `evalRunValue`. C#: `Evaluator.LazyLists.cs` (`LazyList`, `ForcePosition`, `ForceLevel`, `MaterializeValue`, `StageSite`). Rules: `docs/design/language-rules/sequences-lists-and-calls.md` § Lazy collections and pipelines. Pins: `LazyCollectionTests`, `CoreTests/LazyCollections.lean`, spec cases `lazy-*`.

LISTS AND THEIR PIPELINES ARE EVALUATED ON DEMAND (issue #204, November 2026; Lean and C# together, Lean first). A list is a FINITE collection of POSITIONS; a position is found before it is read, and reading it is one VALUE demand that every reader of that list instance shares. The four views every consumer uses are:

* KNOWN CARDINALITY — a list literal, a `map` and a `take` over known positions have all their positions from the start, so `count`, bounds checks and pattern cardinality read no element;
* POSITION DISCOVERY — a `filter` (and every stage over one) finds its positions by scanning its source in order, only as far as the consumer asks;
* INDEXED VALUE DEMAND — the VALUE of the one position selected, memoized per position per list instance;
* MATERIALIZATION — one level (explicit spread, the strict collection builtins) or the whole value (evaluator equality, `atoms`, the run result, a host-operation argument), read left to right and depth first.

So `[10, 1 / 0][0]` is `10`, `[1, 2].map{if(n == 1, 10, 1 / 0)}.first` is `10`, and `[1, 0].filter{1 / n > 0}.take(1)` is `[1]`.

CONSTRUCTION. A list literal captures ONE DEFERRED VALUE COMPUTATION per ordinary written element, in the literal's own environment (a parameter element is the parameter's own computation, so both share one completion), and evaluates nothing. An EXPLICIT SPREAD element is formed while the literal is built — its operand evaluated, the level it opens read, its items supplied as values — and so is a declaration-level output spread (`[P, P()]` with `P* = …` forms `P()` with the list). A number, string or Boolean literal and `()` are their values. The cardinality is therefore known when the literal is built. A literal without a deferred element is an ordinary concrete list.

SHARING AND ORDER. Each position is computed at most once per LIST INSTANCE and memoizes its value or its ordinary failure; two evaluations of one literal build two instances that share nothing. Effects follow the order in which positions are read: with `L = [tick(), tick(), tick()]`, the rows `L[2, 0, 2], L[0], tick()` are `(1, 2, 1)`, `2`, `3`; with `L = [tick()]`, the rows `L, tick()` are `[2]`, `1` (the run's output is assembled first and read afterwards).

`map` PRESERVES POSITIONS: position `i` of `map(c, f)` is `f` applied to position `i` of `c`, whatever `c`'s cardinality or discovery state. Building the stage reads nothing and projects nothing. The first read of a position reads the SOURCE position first, THEN projects the mapper (the callback slot's ordinary projection, on first use), then makes the ordinary callback call; its whole result is the position's value (HO-03). So `first(map([1 / 0], 7))` is `DivisionByZero`, `count(map([1 / 0, 2], 7))` is `2`, and `map([1], 7)` fails `NotAnAlgorithm` only when the position is read. A source known to be empty maps to `[]`.

`filter` DISCOVERS ITS MATCHES in source order. It keeps the positions accepted so far and its scan FRONTIER; a later discovery resumes after the candidates already inspected, so a candidate — accepted or rejected — is never inspected twice. Inspecting a candidate reads its VALUE, projects the predicate on first use and invokes it with the candidate's source index. An ordinary failure is memoized AT THE FRONTIER: every later discovery that reaches that candidate reports it again, while the positions accepted before it stay readable (`F = [1, 0, 2].filter{1 / x > 0}`: `F.first` and `F.take(1)` are `1` and `[1]`, `F.count` is `DivisionByZero`). An empty or unread stage never projects its callback. A predicate that needs the scan it is part of is a demand cycle.

`take` VALIDATES ITS COUNT BEFORE ANY POSITION and returns a PREFIX that shares its source's positions and discovery state: a non-positive count is `[]` and reads nothing, and a full prefix inspects no further candidate.

CONSUMERS READ WHAT THEY NEED:

* `first` reads position zero, `last` discovers the final position and reads it, `count` needs the cardinality only;
* postfix selection validates each selector and reads the position it names, in written order, checking bounds against the known cardinality (or discovering up to that position); a repeated selector reads the position's completed value;
* a list pattern and the unpacking receiver of a deconstruction check the KIND and the CARDINALITY before any field, then bind names and collecting bindings to the ORIGINAL positions (a value, with no callable identity, plan or slice of the element's computation). A scalar literal rejects a list by kind without scanning it; the empty-list pattern may need discovery; a sequence pattern rejects any list by kind. A literal or nested field is read in the ordinary inspection order;
* an EXPLICIT SPREAD reads the level it opens, in order, and contributes Ready VALUE slots; the items' own contents stay as they are;
* every other collection builtin (`sum`, `min`, `max`, `avg`, `order`, `orderDesc`, `skip`, `distinct`, `contains`, `reduce`) reads its collection's positions in order when it binds it; `reduce` obtains the complete collection first and keeps its lazy accumulators (§ Lazy `reduce` accumulators);
* EVALUATOR EQUALITY (`==`, `!=`, `contains`, `distinct`, a repeated name's agreement) compares WHOLE values: both operands are materialized, in operand order, before the comparison;
* `atoms` reads the whole value;
* THE RUN RESULT is assembled first and then materialized left to right, depth first, while the run is active — a host never receives a list evaluated on demand, and an element that fails there fails the run. A host-operation argument is materialized where the operation is called.

A LIST CAN HOLD ITSELF through a deferred position (`L = [L]`: building `L` reads nothing, `L.count` is `1`). Reading such a value whole reaches a list it is already inside, which is a demand cycle of the value, reported as `DemandCycle`, never an unbounded materialization; a position whose computation reads itself (`L = [L[0]]`) is the ordinary demand cycle of its cell.

DIAGNOSTICS NEVER FORCE AN UNTOUCHED ELEMENT. A diagnostic names a list by what is known without reading it: a deferred position is shown as `<deferred>` (`a list value with 2 elements: [1, <deferred>]`), a list whose positions are found by discovery as `[<deferred>...]` / `a list value whose elements are not yet evaluated`. A failure keeps its own source position and structured error. C# reports a deferred `map` / `filter` step under the frame and the position of the written call that BUILT its stage, followed by the frames of the consumer that demanded it (`while evaluating call to count: while evaluating call to filter: …`); the Lean model's errors carry no written-call frame for a deferred step (documented divergence, diagnostics only).

PASSIVE PROPERTY OBSERVATIONS read nothing: an observed value that holds a list evaluated on demand is shown as a concrete form of what the run has read of it, with the lists inside resolved the same way — its whole form; the one-level form of a consumer that read every position; or, when the run SETTLED its cardinality and the VALUE of every position has completed successfully, a new list of those memoized values, however the positions were read (selected one at a time in any order, or judged by a completed `filter` scan, whose verdicts read every candidate: `F = [a, b, c].filter{…}` observed after `F.count` shows its matches). The observation is `Withheld` when the run read some list of it too little: its cardinality unsettled (a scan that found what its readers asked for but was never asked past it, even when its last candidate was judged), or a position never read, still in flight, or failed (a list that was only counted, or read at some of its positions) — or when those forms and positions lead back to a list the snapshot is already inside (`L = [L]` after `L.skip(1)`: the one-level form of `L` holds `L` again, so it has no finite concrete form; `L = [L, x]` after `L[0]` and `L[1]` likewise; the run still completes with its ordinary output). Taking the snapshot demands no cell, discovers or reserves nothing, charges nothing and observes no cancellation; a structure several observations reach is walked once and shared. Observations are reported in publication order, and a list is published when it is BUILT, before anything reads it.

BUDGETS (C#-only host policy; no Lean counterpart). A list of known cardinality reserves its positions when it is built (the reservation the eager list made); a scan reserves its accepted positions when it completes, and a stage whose positions are discovered reserves them when its first concrete form is built. An executed callback charges one invocation and its own work when its position is read; an unread position charges nothing. Whole-value reads are iterative (no native recursion per nesting level) and observe cancellation. A scan's completion reservation, when refused, is positioned at the call that built the `filter` stage, on every evaluation strategy.

STACKED STAGES AND RUNAWAY RESULTS (C#-only host policy). A pipeline can be stacked at run time — a loop that maps its own list every round builds one stage per round. Asking such a list for its cardinality asks the list that finds its positions directly, however many `map` and `take` stages lie between; reading a position through stacked `map` stages reads the stages DEEPEST FIRST (the order the nested reads take, so effects, values and failures are unchanged) without one native call chain per stage. Stacked `filter` scans are discovered without one native call per scan: a scan whose source has no position at its frontier asks the scan below (through any `map` and `take` stages, for exactly one more position), and one frame drives the whole chain — the scan above waits on an explicit list while the scan below runs the iterations its own discovery would run, so the verdict order (Lean's `LazyList.discover`), the cached accepted and rejected prefixes, the positions readable before a later ordinary failure, the failure's blame, the budget, cancellation and in-flight joins are those of the nested calls, on both routes and at any height (`FilteredList.DiscoverScans`). A STAGE RELEASES WHAT ONLY ITS STEPS READ: a `map` stage whose positions are all found and all resolved (a value or the failure its cell keeps), and a `filter` scan that has judged every candidate its source will ever have, run no further step, so they let go of their source, the root that found their positions, the callback and the environment of the call that built them, and keep their cells; a loop that composes a new stage every round and reads it keeps only the last round's stage reachable, while a stage with an unread position keeps what that position's step needs. The position and verdict cells hold one computation object each (`NeedComputation`), not two delegates. A RESULT THAT KEEPS BUILDING LISTS WHILE IT IS READ WHOLE IS BOUNDED LIKE RECURSION: with `F(x) = [x].map(F)`, `F(1)` returns at once and so does every callback, so no call ever nests — but reading the result whole would read forever. The lists built while a position of a generation-`g` list is read whole are generation `g + 1`, and a list of generation `MaxDepth` is not read: the run ends with `EvaluationDepthExceeded`, the failure the same program had while `map` ran its callback itself. A structure of any depth that was built before it is read (by calls, by a loop) is generation 0 throughout and is never refused; `F(1).count` is `1`.
