# Sequence, list, spread, and call rules

The full statement of the rules that AGENTS.md carries in compact form — consequences, examples, the implementation map, and the pinning tests — moved here verbatim from AGENTS.md in September 2026. These rules are as binding as AGENTS.md; the compact bullet there points at the section here. Keep both in step: a rule change edits the compact bullet and the section together.

## Output bundles, capture, and algorithm identity

Brace algorithms are `Expr.AlgorithmExpr` / `.algorithmExpr` and carry algorithm identity and lexical scope. A surviving parenthesized group is `Expr.Capture` / `.capture` over an `OutputBundle`, with no algorithm identity, members or lexical ownership. `Apply((Inc, Dec))` therefore reports absence of a callable; no synthetic output thunk supplies identity. Redundant grouping is erased by the parser, so `Apply((Inc))` is `Apply(Inc)` and `(Obj).V` is `Obj.V`. Genuine capture and spread targets are invalid `open` forms.

Every brace algorithm has an independent CALLABLE channel, whatever its parameter count. Call arguments are `OutputBundle` slots in the caller's context. Each ordinary slot becomes a suspended cell; a capture or list, if demanded, evaluates its elements eagerly and constructs an ordinary value. No Args algorithm or call-site slot reinterpretation exists. Formula lifting follows its immediate consumer role as specified in `ownership-and-lookup.md`. A closed parameter list blocks adding forwarded names and leaves an ordinary runtime zero-argument demand; it introduces no Q-15 strict-Math diagnostic. See `call-by-need.md` for the complete demand laws.

## Value boundaries

A property/call/builtin RESULT boundary is a value boundary: it always returns ONE value, with emitted count `Result.valueCount` (0 for the empty sequence value, otherwise 1 — a list value always counts 1, including `[]`). A multi-output body/collection is observed by the caller as one sequence value; only an explicit caller-site spread (`expr*`) spreads it back into the surrounding item supply (spread reads the value via `spreadItems` — the spread view that also opens one list boundary — not the emitted count; `toItems` is the non-spread item view and keeps lists opaque). Redundant unary sequence structure is normalized during ordinary value construction, including `(())` and `((()))` to `()`. The shared helper is `reCountValueBoundary` (Lean) / `ReCountValueBoundary` (C#); it re-counts the value boundary without rebuilding the value and is applied at user/conditional calls (`evalUserCallCounted`, `evalConditionalCallCounted`), structural dot zero-arg access (`evalDotCallCounted`), and higher-order callback items (`countedSequenceCallbackItem` / `CountedSequenceCallbackItem`). SELECTION IS A VALUE BOUNDARY (September 2026; the bracket spelling and variadic form since October 2026, § Variadic postfix selection): `A[i]`, `first(A)`, and `last(A)` CHOOSE a value and never open it — the `.index` arm of `evalCounted` (C# the Index case of `EvalExpressionSpineCounted` and its async twin), `evalFirstCounted`/`evalLastCounted`, and the callback item all emit `(selected, Result.valueCount selected)` for one selected value, so a selected sequence or list is ONE value everywhere (`Coll(A[0], 3)` collects `[(1, 2), 3]`, a lone root row `A[0]` is one row, a loop-step row `A[0]` is one state slot, `map(A, Id)` with `Id(x) = x` maps a nested pair to itself), a selected `()` re-counts to zero values whatever route selected it (so it spreads to nothing — `(first(((), 1)))*.Coll` is `[]` — while passed unspread it is ONE argument value: `first(((), 1)).Coll` is `Coll(first(((), 1)))`, which the exact collector law collects as `[()]`, like `E.Coll` / `Coll(E)` for `E = ()`), a selected `[]` stays one exact list (`[[]]`), and the selected value's origin is forgotten (`X = A[0]` then `X.Coll` agrees with `A[0].Coll`, and both agree with `V.Coll` for a property `V` holding the same value — selection chooses a value; later collector behavior depends only on that value and whether it was spread, never on selection provenance, so `A[0].Coll` with `A = ((1, 2), 3)` is `[(1, 2)]` under the exact collector law described under Collecting parameters). Only the spread marker opens a selected value, one boundary (`(A[0])*.Coll` is `[1, 2]`; `A[0]*` is the same select-then-spread). Over a value in hand, `first(v) ≡ v[0]` and `last(v) ≡ v[count(v) - 1]` for EVERY value, failures included (Q-27, October 5 2026) — laws, never rewrites of effectful expressions (§ Variadic postfix selection (C)): an empty value names no position, so `first(())`, `first([])`, `last(())`, `last([])` and `().first` are `BadIndex` exactly like `()[0]` and `[][0]` (Lean `first_is_selection_at_zero` / `last_is_selection_at_count_minus_one`, the older `first_is_select_zero` / `last_is_select_last` and the total `first_is_select_zero_total` / `last_is_select_last_total`, with `first_empty_is_badIndex` / `last_empty_is_badIndex`; C# `SelectionValueBoundaryTests`; CoreTests `SelectionValueBoundary`; `evaluator-and-hosting.md` § The evaluation-error taxonomy). There is no selected-content projection and no live selection count anywhere: `Result.select?` / `Result.Index` return the stored element (`select_is_stored_element`), and `projectionItems` / `ProjectionItems` is only the TARGET's position view. Collection-producing builtins (`order`, `orderDesc`, `distinct`, `take`, `skip`, `filter`, `map`, `range`, `atoms`) materialize ONE exact list value with count 1 via `makeCollectionListResult` / `MakeCollectionListResult` and need no re-count. Collecting bindings likewise produce one exact list value with count 1 — since Model C a collector cell whose VALUE demand materializes its slice through `makeCollectionListResult` / `MakeCollectionListResult` (`demandNeed`, `CollectorCell`; formerly `collectSegment` / `CollectSegment`) — and need no re-count or raw-supply storage. Lexical zero-arg property access and `if` already re-counted this way; the reduce initial accumulator is likewise reified as ONE accumulator value (`reCountValueBoundary`) before reduction, so an empty reduction returns it as ONE value and every reducer step receives it as one ordinary argument. A completed `while`/`repeat` is a value boundary too (Q-26, October 2026): `loopResultCounted` / `MakeCheckedLoopStateResult` re-count the captured final state, so a non-spread loop is ONE item at every receiver (§ Loops). NOT value boundaries (must keep their multi-item counts): root/body output accumulation (`evalAlgOutputCountedCore`) and a loop step's own row supply (`evalAlgOutputSlots`, the loop's iteration protocol). A `map`/`reduce` CALLBACK RESULT is a value boundary like every call result (Q-25, October 2026; § Callback results): a transform or step returns its ordinary call result, ONE value, and the former strict single-value callback contract is gone. Scalar/reduction builtins already return one value and are unchanged.

## Variadic postfix selection

VARIADIC POSTFIX SELECTION (owner-approved October 2026; it replaces and retires the colon form `receiver:selector`). `receiver[s1, …, sn]` selects zero or more positions of ONE receiver value. The rule has six parts.

**(A) Invocation and selection are different operations.** PARENTHESES INVOKE A COMPUTATION; POSTFIX BRACKETS SELECT FROM A VALUE; SELECTION DOES NOT CHANGE HOW ITS RECEIVER OBTAINS THAT VALUE. `Data` is the ordinary cached zero-argument property read and `Data()` a fresh invocation that never reads or replaces the property's cache entry (one that finds the entry empty establishes it — CACHE-PUB-1, 2026-10-22) (§ Zero-argument property cache in `evaluator-and-hosting.md`); so `Data[indices]` consumes the ordinary read and `Data()[indices]` consumes ONE fresh invocation result. Grouping stays transparent: `Data[0]`, `(Data)[0]` and `((Data))[0]` are one node. A selection has no CALLABLE identity (`resolveAlg` / `ResolveAlg` report `NotAnAlgorithm("index expression")`), so `Data[0](1)` is the SYN-07A separator error and `Data[0].F` is the extension call `F(Data[0])`; selection never makes a computed value callable.

**(B) Counting and selection share ONE immediate positional view.** KatLang's `count` counts values (elements), not the internal components of those values. A list or sequence exposes its immediate elements, never recursively flattened; a number, a Boolean or a string exposes ITSELF as one element (position `0`) — the empty string `''` included, which is one scalar value, not an empty collection; an empty list or empty sequence has no positions. Counting a list of strings counts its strings, never their characters, and selecting from a string never extracts characters, code units, code points or graphemes: `count('abc')` and `count('')` are `1`, `'abc'[0]` and `first('abc')` are `'abc'`, `''[0]` is `''`, `'abc'[1]` is `BadIndex`, `count([['a', 'b']])` is `1`. The view is `Result.projectionItems` / `Result.ProjectionItems`, which EQUALS the post-binding collection view `count`, `first` and `last` read (`builtinCollectionItems` / `BuiltinCollectionItems`; Lean theorem `positional_view_is_shared`). This view is distinct from argument cardinality, emitted-value count, explicit-spread supply and the structural-pattern views; their agreement on counting and selection does not authorize merging helpers that deliberately keep different boundaries.

**(C) The selection laws.** For the same already evaluated receiver value `v`, `first(v)` and `v[0]` — and `last(v)` and `v[count(v) - 1]` — have the same result and the same error (`BadIndex` when `v` has no positions; for `last` the index is then `-1`). These are semantic equivalences over a value in hand, NOT unrestricted rewrites of effectful expressions and not promises of identical resource use: `last(BuildData())` invokes once, `BuildData()[count(BuildData()) - 1]` twice. Builtin identity resolution and shadowing are unchanged (no spelling recognition implements the laws). Lean: `first_is_selection_at_zero`, `last_is_selection_at_count_minus_one`, `count_is_the_number_of_positions` (and the older `first_is_select_zero_total` / `last_is_select_last_total`).

**(D) Values are preserved and only the result grouping is normalized.** One immediate element per supplied index, in supplied order, repetitions repeating stored values, each element whole; the selected values are captured by ordinary normalization of the RESULT GROUPING only (`combineOutputSlots` / `MakeCheckedSequenceCapture`, the capture loop results use): zero selections are the successful empty sequence `()`, one is the selected value itself, several are ONE sequence of the selected values. `Data[]` is `()` (emitted count 0, never a missing output, never the receiver, never `[]`); `Data[2, 0, 2]` is `(30, 10, 30)` for `Data = [10, 20, 30]`; `Nested[2, 3]` is `((), [])` and `Nested[0, 1]` is `((10, 20), [30, 40])` for `Nested = [(10, 20), [30, 40], (), []]` — no flattening, no dropped `()`, no list wrapping, no hidden selection-count metadata. BRACKETS SOLVE THE INVOCATION AMBIGUITY; THEY DO NOT REMOVE THE ORDINARY CONSEQUENCES OF SINGLETON NORMALIZATION: with `Data = [(10, 20), 30]`, `Data[0]` is `(10, 20)` and `[Data[0]*]` is `[10, 20]`, never `[(10, 20)]`; an exact one-per-index list is written explicitly (`Indexes.map{Data[i]}`). A multi-selection is one sequence VALUE, never an argument supply: `Add(Data[0, 1])` is an arity error and `Add(Data[0, 1]*)` supplies two arguments. Surrounding output and count behavior is the ordinary value boundary's.

**(E) Operational order — when the selection expression is demanded:** (1) the receiver is demanded ONCE through its ordinary value path, and its failure propagates even for an empty selector supply; (2) the selector supply is formed exactly like a call's (Model C, `formNeedSupply` / the ONE spread-slot formation `FormSpreadSupplySlot`): explicit spread slots run during formation, in written order — a collecting parameter's slice is transported unforced — and ordinary non-spread selectors stay suspended; (3) the supplied indices are demanded, validated (`selectPosition` / `SelectPosition`: a non-number selector VALUE is `TypeMismatch`; a negative, fractional, non-finite, beyond-host or past-the-view number is `BadIndex`) and selected LEFT TO RIGHT, the first failure ending the selection with no later ordinary selector demanded; (4) the selected values are normalized (D). Formation completes before any selector is validated, so `[10, 20][99, 1 / 0]` is `BadIndex` (the later ordinary selector is never demanded) while `[10, 20][99, (1 / 0)*]` is `DivisionByZero` (the spread runs during formation) — a consequence of the established supply rule, not a selection-specific order. Caller environments, need-cell sharing and the error categories are the ordinary ones; the rule applies when the selection is demanded, never to unused expressions. Lean: the `.index` arm of `evalCounted` over the TOTAL core `selectWith` (laws `selectWith_runs_as_its_trace`, `selectWith_stops_at_first_failure`, `selectWith_pure_preserves_order_and_repetition`, `selection_of_*`, `selected_empty_values_stay_elements`, `single_selection_keeps_no_wrapper`); C#: the Index case of `Evaluator.EvalExpressionSpineCounted` and its async twin through the shared `AdvanceSelection` / `SelectPosition` / `CompleteSelection` (an ordinary slot is demanded as a machine child at its turn — observably its private suspended cell's first demand — and a spread-formed cell is demanded directly; one machine transition, hence one budget/cancellation checkpoint, per supplied selector; a selector failure is positioned at its written slot).

**(F) Syntax and migration boundaries.** Postfix `[` takes zero or more selectors, explicit spreads included (`Data[Indexes*]`; a collection-valued selector is ONE supplied value — `Data[(0, 1)]`, `Data[[0, 1]]` and `Data[()]` are `TypeMismatch`, while `Data[[0, 1]*]` supplies two indices and `Data[[]*]` and `Data[()*]` none). Same-line spaces and tabs before `[` are allowed (`Data [0]`, `Grid [0] [1]`); the `[` must be on the same physical line as the receiver's final token (`Data` newline `[0, 1]` is two rows; `Grid[0]` newline `[1]` is no chain), and once open the selector list may span lines with the ordinary expression-list rules. Commas select siblings (`Grid[0, 1]` is `([10, 20], [30, 40])`), chained brackets descend (`Grid[0][1]` is `20`), and selection is a postfix form with the old `:`'s precedence (`-A[0]` is `-(A[0])`, `A[0] ^ 2` is `(A[0]) ^ 2`, `BuildData(n)[0].sum` selects then calls). The star disambiguation is unchanged: `A*[0]` is the multiplication `A * [0]`; capture-then-select is `(A*)[0]` and select-then-spread `A[0]*`. The colon form is retired: a same-line `expr:selector` is `DiagnosticCode.RetiredColonSelection` (public `KatLangErrorCode.RetiredColonSelection`), recovered as the selection it meant, and a `:`-led line reports the same code; `:` is not syntax (a `:` that begins an interpolation hole or follows the hole's completed expression stays `InvalidInterpolationHole` (a `:` where the hole's expression still needs an operand, `"{a + :0}"`, is that operand's own `RetiredColonSelection`, and the hole adds no second report)). No types, slicing, negative-from-end indexing, string-character indexing, multidimensional coordinates, mutation or user-defined indexing protocol are introduced, and `[]` never resolves a user-visible `at` name.

Pinned by `VariadicSelectionSemanticsTests`, `VariadicSelectionDemandTests`, `PostfixSelectionSyntaxTests`, `SelectionValueBoundaryTests`, `EvaluatorIndexingTests`, the `variadic-selection-*` LanguageSpec cases, Lean `CoreTests/VariadicSelection.lean` and the selection laws in `KatLangArityLaws.lean` § Variadic postfix selection.

## Spread semantics

A spread expression spreads ONE item-producing boundary of the evaluated operand, contributing its items to the surrounding item supply — it does not create, return, or emit a sequence or list value by itself; the RECEIVER decides what the supplied items become (capture materializes a canonical sequence, a collecting binding collects an exact list, fixed bindings receive items individually, calls receive separate argument slots, root output emits rows). Sequence values and exact list values supply their contained items; other values follow the total item-view rule (an atom or string supplies itself as one item). A comma is REQUIRED between a spread and a following supplied item on the SAME line (`A*, B`), because `A* B` is the multiplication `A * B`; a same-line closing delimiter or fluent receiver boundary may follow a spread without a comma, and so may the end of the physical line after an ATTACHED star (issue #183): `A*` newline `B` is two items wherever a newline separates slots, EOF and a later-line closer end the spread too, while the DETACHED `A *` newline `B` is the multiplication `A * B` (`A* ; B` is invalid semicolon syntax; to pass a spread plus another value as ONE sequence-value argument, write `f((A*, B))`). In a call, evaluating the spread operand is part of assembling the supply, for EVERY callee — a user callable, a clause family, and a builtin alike: if it succeeds, the spread supplies exactly its items; if it fails, that failure (whatever its kind, `SpreadMissingOutput` for a missing output) is the call's failure, raised before the arity check, before clause selection or binding, and before any later slot — a failed spread never becomes a supplied item (§ Collection builtins, PV-20).

ARGUMENT VIEW SPREAD (CallReference S2): in an argument or selector supply, a spread whose last star opens an argument view (`F(R.Arguments*)`) contributes the captured call's ORIGINAL argument cells — undemanded, callable arguments still callable, values shared with the original call — instead of opened items; a star that would open a view into VALUES (any spread in a value position such as `[R.Arguments*]`, or an inner star of `F(R.Arguments**)`) is `TypeMismatch`. Every other spread is unchanged (`call-by-need.md` § Argument views, CR-11).

## Call argument assembly and written-slot reification

Resolution selects one callable identity before supply formation. Non-spread written arguments become suspended cells without VALUE evaluation or callable probing. A written parameter reference transfers the exact existing cell. Explicit arbitrary spreads evaluate and open one value during supply formation; known collector slices transfer element addresses. Supply cardinality is checked before ordinary arguments are demanded.

FORMATION IS SHARED, DEMAND IS NOT (X-18, closed by the owner on 2026-10-10, confirming the Model-C law). Every callee category forms its supply as above; which formed cells it then demands, and in what order, is the callee's own. A user callee demands through its inspecting patterns (NEED-04) and the consumers its body executes; a builtin through its argument roles (§ Collection builtins — `if` demands its condition, then only the selected branch); a callback or loop step is projected for its CALLABLE identity only when it is invoked, never VALUE-demanded (NEED-06). So no callee evaluates every argument as such, and no rule orders argument evaluation by written position: the order of first demands decides argument effects, random draws and failures (NEED-03), and an explicit spread has already run at formation, before any ordinary argument and whatever the callee selects. `Keep(x) = 42` / `Keep(1 / 0)` is `42`; `F(x, y) = y + x` / `F(1 / 0, 'a' + 1)` is `TypeMismatch` (`y` is demanded first); `count(1 / 0, 2)` is `ArityMismatch` (cardinality first); `if(false, 1 / 0, 42)` is `42`, while `if(false, (1 / 0)*, 42)` is `DivisionByZero`; `range(1 / 0, (1 + 'a')*)` is `TypeMismatch` (the later-written spread is formed before `range` demands its start). The pre-Model-C description of call assembly as one eager, written-order evaluation of every slot, shared by every callee, is superseded history (CALL-02, CALL-03; NEED-01..07).

One supplied item is one value whatever its kind. An interpolation hole is one written value too (STR-02): its expression yields ONE value, converted whole to its structural text — a multi-row block or property in a hole is one sequence value, shown `(a, b)` — and a hole is no item-supply receiver, so a bare spread there is `MisplacedSpread` while `"{(xs*)}"` captures the items as one sequence value. `F(S)`, `F((S))`, `F(((1, 2)))`, `F({S})` and `F((S*))` have the same value boundary when their values agree. A structural pattern demands its one parent cell and opens the resulting whole eager value one level. Neither a binder nor an adapter reconstructs a data Result as an algorithm. Ready cells carry already-produced data without inventing CALLABLE identity. `FormNeedSupply` / `formNeedSupply`, `BindNeedPatterns` / `bindNeedPatterns` are the common formation and binding path.

## At-most-once argument value evaluation

Model-C replaces eager acquisition with at-most-once first demand. A plain binder attaches its supplied cell without forcing. The first VALUE demand evaluates the original expression in its retained caller environment, stores the full counted success or ordinary failure, and every later demand observes that completion. A failed computation cannot heal. An unused cell performs no expression work, effects, random draw or suspension.

CALLABLE projection is independent and pure: it obtains the resolved identity and retained owner without a preliminary VALUE demand. Actual invocation is fresh with normal arguments and charges. A VALUE failure does not destroy independent identity, while terminal run state prevents further semantic work on either channel. Scalars, captures and computed/selected values gain no callable thunk.

Memoization belongs to one supplied computation. A bare property inside a demanded cell still uses the separate per-run property cache; an explicit `Z()` is fresh once per cell, and two independently supplied `Z()` cells remain independent. Failed properties are not globally cached. Cell and slice transport, completion joins and memo observation add no semantic step or invocation depth. See `call-by-need.md` NEED-01..10; pins include `NeedCellTests`, `ModelCProductionTests`, `CoreTests.ModelC`, and `ArgumentValueOutcomeTests`.

## Arity error payloads

Flat fixed arity errors report the complete inputs to the selected binder, never the residual tails after consuming a prefix. The cardinality check comes before any demand, and its payload is the selected signature's minimum and the complete supply count (Lean `bindNeedLevel`, C# `NeedCallArityError`; formerly Lean `bindParams` and C# `BindParams`, which checked the two lengths before zipping): `Add(x, y)` called as `Add((1, 2))`, `(1, 2).Add`, or `map([(1, 2)], Add)` reports `(expected 2, actual 1)`; a three-parameter callable supplied two values reports `(3, 2)`. Since Model C every supplied slot is one cell, so a slot that would be satisfied only on the algorithm channel counts like any other: `F(x, y) = x(y)` / `F(Inc)` reports `(2, 1)` in both engines (CALL-04; until then such a slot was excluded from the value binder's inputs, giving `(1, 0)`). Successful bindings and the PAT-10 inspection order are unchanged. The production `bindNeedLevel` rejection is a theorem since October 2026 (`binder_rejects_unaccepted_supply_before_any_effect`, reached at a call through `call_binder_rejects_unaccepted_supply_before_any_effect`, in `KatLangArityLaws.lean`: at the top level of a call, after supply formation, for EVERY pair of need channels an unaccepted count is exactly this `arityMismatch` with the run state unchanged — the binder demands, projects and allocates nothing; FORMAL-07), and is also pinned by `#guard`s (CoreTests `ModelC`: `F(x, y) = x(y)` / `F(Inc)` is `arityMismatch 2 1`; CoreTests `CollectingParameters`); CoreTests `ExplicitValueOpening` and `CFullHostileReviewTests` pin ordinary/callback parity executably (since Model C a callback and a direct call reach the one need binder `bindNeedPatterns` / `BindNeedPatterns`; that agreement is not a theorem, Q-66).

## Lists

Square brackets construct list values (`Result.listValue` / `Expr.ListLiteral`), a second collection kind beside sequence values: sequence normalization never applies to list structure (`[7] != 7`, `[] != ()`), while parentheses around a list stay redundant sequence grouping (`([1, 2]) == [1, 2]`). `[` begins a NEW list expression at the start of an expression or slot and on a later physical line; a same-line `[` after a completed expression is postfix selection instead (§ Variadic postfix selection: `A[1]` and `A [1]` select from A, while `A, [1]` and `A` newline `[1]` stay the two-slot list; `[` is never a call delimiter), and bracket content is a pure expression list (spread elements insert their item supply; declarations are illegal inside brackets). Spread uses `Result.spreadItems` / `SpreadItems` (opens one sequence OR list boundary). Postfix selection reads its RECEIVER's positions through the position view `Result.projectionItems` / `ProjectionItems` (`[1, 2, 3][0]` is 1 under the same zero-based index rules as sequence selection), while the selected ELEMENT is returned exactly as stored and never opened — a selected list is one opaque list (`[[1, 2], [3, 4]][0]` is `[1, 2]`), a selected sequence value one sequence value (`[(1, 2), (3, 4)][0]` is the one value `(1, 2)`); chaining selects one level at a time (see the selection rule under Value boundaries). Every other NON-spread consumer keeps lists opaque via `toItems` (a list is one item for value boundaries and call binding — calls never open lists, or sequences, implicitly). Deconstruction's unpacking receiver (Lean `ParameterPattern.unpacking`, C# `UnpackingParameterPattern`, opening through `Result.spreadItems` / `SpreadItems`) opens a lone sequence OR lone list (`x, y, z = [1, 2, 3]`), while a written structural pattern opens only its own kind (§ Structural patterns); collecting bindings collect exact lists (see the collecting-binding rule below). The post-binding builtin collection view opens a BOUND list exactly like a bound sequence value (`count([1, 2, 3])` is 3, `A.take(1)` works on a list property; the opening is never recursive — a nested list stays one opaque item; spread supplies ordinary argument slots, so `count([1, 2, 3]*)` is an arity error under the fixed `count(collection)` signature). The `atoms` builtin recursively collects numeric atoms through BOTH sequence and list boundaries (depth-first, left to right; strings contribute none) via its own dedicated collector `Result.languageAtoms` / `LanguageAtoms` and materializes them as ONE exact list through `makeCollectionListResult` (`atoms(7)` is `[7]`, `atoms([1, [2]])` is `[1, 2]`, `atoms('text')` is `[]` — the result kind never depends on the input). Truth is deliberately SEPARATE from every atom view: since first-class Booleans (September 2026) a condition is decided by `Result.asBool?`/`AsBool` alone — only a Boolean value qualifies — so lists have no truth value (`if([1], a, b)` stays invalid), numbers have none either, and the atoms traversal can never leak into `if` (see [`evaluator-and-hosting.md` § Boolean values]). Host-boundary flattening (`runFlat` / `Result.hostAtoms`, C# `RunFlat`/`EvaluateToAtoms` via `ToHostAtoms`) opens list boundaries; the non-spread `toItems` view stays list-opaque, and Boolean values have no host numeric projection at all. Receiver theorems: `receivers_agree_outside_lone_structure` (on supplies outside the `loneStructure` shape), `receivers_never_same_on_lone_structure` with its `receivers_never_same_on_lone_seq` / `receivers_never_same_on_lone_list` instances (a lone argument that is a sequence or a list never opens at a call, for ANY pattern list — values stay values — so call binding and deconstruction never coincide on it), and the concrete `lone_collecting_disagrees_on_lone_structure` in `lean/CoreArityAlgebraProofs.lean`; for the production Model-C binder, `nested_unpack_level_is_bind_need_level` (`lean/KatLangArityLaws.lean`) proves that the unpacking receiver binds the demanded value's one-level items (`Result.spreadItems`, which opens a list exactly as a sequence: `spreadItems_listValue`) through the ordinary `bindNeedLevel`, while a call's lone collector allocates its one supplied cell whole (`lone_collector_collects_every_supplied_cell`); end to end over the real evaluator the list-side receivers are pinned by `#guard`s (CoreTests `CollectingBindings`, and `ExplicitValueOpening`'s `deconstructionOpensExplicitly`). The CoreArityAlgebra paper artifact now models `Val.list` and `collect` (the pre-list sequence-only extraction is preserved at the pinned paper tag).

## Structural patterns

STRUCTURAL PATTERN DELIMITERS SELECT THE VALUE KIND THEY DESTRUCTURE (September 29 2026; an INTENTIONAL pre-release valid-source semantic change, Lean and C# changed together). KatLang has two collection kinds (§ Lists), and each has its own pattern language, with the delimiter that constructs the kind:

| Pattern | Matches |
| --- | --- |
| `x` | any one value, bound whole |
| `()` | the empty sequence value only |
| `(x, y)` | a sequence value of exactly two elements |
| `(x, *rest)` | a sequence value of at least one element; `rest` collects the others as an exact list |
| `(*xs)` | any sequence value; `xs` is the exact list of its elements |
| `[]` | the empty list only |
| `[x]` | a list of exactly one element |
| `[x, y]` | a list of exactly two elements |
| `[*xs]` | any list, of any cardinality — 0, 1 and N alike |

THE KIND LAW. A sequence pattern `(p1, …, pn)` opens a SEQUENCE value and nothing else (Lean `Result.sequencePatternItems?`, C# `Result.SequencePatternItems`); a list pattern `[p1, …, pn]` opens a LIST value and nothing else (`Result.listPatternItems?` / `ListPatternItems`). There is no cross-kind matching (`FirstPair((x, y))` rejects `[10, 20]`, `PairSum([x, y])` rejects `(10, 20)`), no scalar-as-one-item fallback (`(x, *rest)` rejects `7`; before this law a scalar was a one-item supply at every pattern level), and no implicit list↔sequence conversion in any layer. A bare binder is the ONLY pattern that takes a value whole. Nesting preserves kinds at every level: `F(([x, y], z)) = x + y + z` takes a sequence whose first element is a two-element list (`F(([10, 20], 30))` is 60), `G([(x, y), z])` a list whose first element is a pair, and each level is checked against its own delimiter.

THE SINGLETON RULE. A sequence pattern with exactly ONE non-collecting item — `(x)`, `((x))`, `(([x]))`, `(((x, y)))`, `(((true)))`, at any depth — is INVALID: a sequence value never has exactly one element (`(7)` IS `7`, normalization), so the pattern describes a boundary no value has. The parser reports `DiagnosticCode.SingletonSequencePattern` (`Parser.SingletonSequencePatternDiagnostic`, the wording of Lean `singletonSequencePatternMessage`) at the group, in parameter lists and clause heads alike, and never rewrites `F((x))` to `F(x)`; a host-built tree carrying one is refused before evaluation (Lean `validateExplicitParamOutputInvariant` → `illegalInEval`; C# `PreEvaluationAstViolation.SingletonSequencePattern`), so no layer gives the pattern a meaning the surface refuses it. The collector-only `(*xs)` is not a singleton (it matches every sequence, `()` included), and lists have the one-element pattern `[x]` because a one-element list is a value. `()` and `[]` are distinct patterns, exactly as `()` and `[]` are distinct values.

OUTER ARITY IS NOT STRUCTURAL SHAPE. Every top-level pattern consumes ONE argument whatever it destructures (`ParameterPattern.minimumSuppliedSlots`), so `F((x, y))` and `F([x, y])` are one-parameter callables and `F(1, 2)` is their arity error; the pattern then opens that one value.

FAILURES USE EXISTING CATEGORIES, and ordinary binders and clause families apply the SAME law. In an ordinary definition (and a callback, loop step, or zero-argument demand, which bind through the same binder) a value of the wrong kind fails the binding with `TypeMismatch` from ONE constructor (Lean `structuralPatternKindMismatch`, C# `Evaluator.StructuralPatternKindMismatch`), naming the written pattern and the value received ("sequence pattern `(x, y)` expects a sequence value, but received numeric value 7"), and a value of the right kind with the wrong number of elements is the group's `ArityMismatch` ("Sequence pattern `(x, y)` expects 2 elements, but received 3 elements.", "at least" for a pattern with a collector; the list form says "List pattern"). In a clause family neither is raised: a clause whose pattern does not match — wrong kind, wrong length, unequal literal — is skipped, and a call no clause matches is `NoMatchingBranch`. Single-clause classification is the same for both kinds (PAT-01: one literal-free binder/group clause is an ordinary algorithm, whether its groups are sequence or list patterns), and duplicate-clause detection is kind-aware (`F((a, b))` and `F([a, b])` are different heads, `F([]) = 0` beside `F(()) = 1` is not a duplicate).

ASSIGNMENT DECONSTRUCTION IS NOT A WRITTEN PATTERN. `x, *y, z = RHS` is the UNPACKING receiver: it opens a lone sequence OR lone list right-hand side one level and matches the flat targets against the items (§ Collecting parameter lists, deconstruction, and callbacks). It is modeled as its own construct — Lean `ParameterPattern.unpacking`, C# `UnpackingParameterPattern`, ONE node shared by every target's helper — so the kind law stays exact for every written pattern while deconstruction's values, errors and linear cost are unchanged; a right-hand side without output is its own `MissingOutput`. There is no bracketed deconstruction target, and none is added for symmetry.

## Collecting parameters

A top-level collector consumes zero or more supplied slots, after fixed prefix and suffix allocation. It binds a cell representing the exact allocated slice. Binding and slice opening perform no VALUE demand. A collector's first ordinary VALUE demand forces every element left to right and constructs ONE exact eager list (`[]` for no items), preserving nested and empty values as elements. `xs.count`, `xs.first`, `sum(xs)` and selection receive that entire list; there is no prefix-only materialization or shape-only count. The completed list is memoized.

A structural pattern consumes one argument and opens only its own kind: sequence patterns open sequences, list patterns open lists. Its collector collects opened Ready elements as an exact list. No lone structured argument is implicitly expanded at a call boundary. Explicit `E*` alone opens a supply. See NEED-07 and NEED-FWD in `call-by-need.md`.

## Collecting parameter lists, deconstruction, and callbacks

Deconstruction-target explicit calls (Q-38, owner decision 2026-10-13): `a()` freshly invokes the target’s projection wrapper, which reads the separately cached shared right-hand side. It never requests a fresh RHS evaluation; a first call of a target can cause the RHS’s first VALUE demand. Successful RHS values retain the ordinary exported/run or local/activation cache identity and Q-37 publication law. C# may reuse its shared binding; Lean can bind the same cached source again. `DeconstructionExplicitCallDecisionTests` pins scalar/list sources, effects, owner activations and seeded draws across all six routes.

One inspecting binder (`bindNeedPatterns`; C# `BindNeedPatterns`, which runs the top-level cardinality gate, and `BindAcceptedNeedPatterns`, which binds after a caller's own gate) serves ordinary calls, conditional clauses, callbacks, generic loop steps and zero-supply demand. Top-level cardinality is checked first, exactly once: by the binder's gate, or by the caller. An ordinary call or callback, a user loop step and a deconstruction report the rejection in their own diagnostic shape; a clause family's driver checks each clause, where a refused count is that clause's non-match. Patterns then traverse in written left-to-right order, recursively within structural patterns. A unique plain name stores its cell without forcing. A literal forces its cell when reached. A structural pattern forces its whole parent value before opening Ready children. A collector binds a slice without materializing it.

Every occurrence of a repeated name forces its own cell when reached. Compare the full counted values and independently available callable identities immediately against the previous contribution. A conflict terminates that attempt before later patterns are inspected. Ordinary conflicts are binding errors; a family's successful incompatible values are a non-match, but an evaluation failure aborts dispatch. Successful contributions retain one complete compatible cell with the richest available channel (VALUE + CALLABLE outranks VALUE only, in either order); among equally rich contributions the FIRST in written traversal order — left to right, depth first — is retained, its complete value with its exact Decimal128 representation (Q-28, N-F, decided 2026-10-07): with `P(x, x) = x.string`, `P(1.5, 1.50)` is `'1.5'` and `P(1.50, 1.5)` is `'1.50'`, while `A = 1.50` makes `P(1.5, A)` and `P(A, 1.5)` both `'1.50'`. On success it preserves the bound VALUE up to `==`, callable identity and channel availability; among equally rich compatible contributions, the first in written traversal order supplies the retained representation. Failure reporting follows ordinary binding order (NEED-04, PAT-10, Q-27): when different incompatibilities coexist, permutation may change the error category, blamed contribution, payload, message or span, although every permutation still fails. No representative is synthesized, canonicalized or merged leaf-wise from several arguments, and no value/callable chimera is constructed. This supersedes the historical range-wide and prefix/suffix merge order.

Families share ONE supply across ordered clause attempts. No candidate forces all arguments in advance. If no head accepts the supply count, report arity before ordinary demand; otherwise try clauses and enter only the first successful body. Assignment deconstruction still demands its whole right-hand-side value, uses the explicit unpacking pattern, and shares the binding result across target helpers. Callback elements and reducer accumulators are ordinary Ready arguments, one slot per item; no row convention, fake algorithm or distinct callback binder exists.

## The dot-call receiver

DOT-CALL PASSES A VALUE. SPREAD OPENS A VALUE. (September 2026 — this replaces the former "receiver segment" rule, under which a written group receiver fed a collecting parameter its raw rows and a named `()` receiver supplied zero items.) ## Collection builtins

Collection builtins are ordinary FIXED-ARITY callables that receive exactly ONE fixed `collection` parameter followed by fixed control parameters: `count(collection)`, `sum(collection)`, `first/last/min/max/avg/order/orderDesc/distinct(collection)`, `take/skip(collection, count)`, `contains(collection, item)`, `map(collection, mapper)`, `filter(collection, predicate)`, `reduce(collection, reducer, initial)`. An unspread sequence or list value is ONE argument at this call boundary like at every other call boundary, and NOTHING is opened before binding — `count(1, 2, 3)`, `count()`, `sum(A*, B*)`, `take((1, 2, 3))` (missing count), `take([1, 2, 3]*, 2)`, and `distinct((), ())` are ordinary arity errors (spread only supplies ordinary argument slots that obey the same fixed arity; re-group to pass spread items as one collection: `sum((A*, B*))`). The bound collection value is interpreted through the POST-BINDING one-level collection view (`builtinCollectionItems` / `BuiltinCollectionItems`): a lone sequence OR exact list opens one outer boundary and any other value is a one-element collection — `count((1, 2, 3))`, `count([1, 2, 3])`, and `Values.count` are 3, `count(7)` is 1, `count(())`/`count([])` are 0, and opening is never recursive (`count((1, [2], 3))` is 3, `count(([], []))` is 2). Item shape/empty policies apply to the viewed items (`sum` numeric constraint, `first` non-empty), each reporting the contract it names (Q-27): a non-numeric element is `TypeMismatch`, an empty `first`/`last` has no position to select (`BadIndex`, `RequireSelectablePosition`) and an empty `min`/`max`/`avg` is outside its domain (`IllegalInEval`, `RequireAnyItem`) — never an arity error, because the argument count is correct. Collection-producing builtins (`filter`, `map`, `order`, `orderDesc`, `distinct`, `take`, `skip`, `range`) materialize their kept/projected items as ONE list via `makeCollectionListResult` / `MakeCollectionListResult`: zero items form `[]`, a single kept item forms `[item]` (never erased, so `take(((1, 2), (3, 4)), 1)` is `[(1, 2)]` and `distinct(((), ()))` is `[()]`), and nested sequence/list elements stay exact — the result kind never depends on the input kind, and only an explicit `spread` re-spreads the list into the arity layer. Canonical arity capture (`combineOutputSlots`, ordinary construction) and spread are UNCHANGED by this model, and collecting binding produces the SAME exact-list kind (the collector cell's materialization; `collectSegment` is its value-level definition) — collecting parameters remain a general arity mechanism for user-defined callables, and passing a collected list to a builtin unspread passes it as the one collection argument (`Qmean(*args) = args.sum / args.count` works because the post-binding collection view opens the bound list; `map(values*, f)` inside a body is an arity error — write `map(values, f)`). Callback/builtin execution stays a separate runtime-owned phase after binding. For collection builtins the receiver fills the fixed `collection` parameter (`A.take(2)` is `take(A, 2)`, `A.count` is `count(A)`), with no builtin-specific receiver placement, through the same call funnel every written call uses (see § The dot-call receiver): the dotted and written spellings agree on binding, error kind, and the zero-argument value demand of a bare named receiver.

No builtin metadata or dot-level adapter may implicitly expand a receiver. Only an explicit spread supplies separate arguments; the builtin collection view applies after ordinary binding.

ARGUMENT VIEWS (CallReference S2, 2026-10-17): a call reference's lazy argument view `R.Arguments` is no collection value. Bound as the WHOLE collection, `count` reads the number of the captured call's effective supplied arguments without demanding any, and `first`/`last` select (and demand) only the first/last argument; every other collection builtin, and `atoms`, refuses a view (`TypeMismatch`) rather than reading it as a one-element collection or materializing it. ## Callback results

A CALLBACK RETURNS ITS ORDINARY CALL RESULT (HO-03; Q-25, owner decision of October 10 2026, Option B). A `map` transform or `reduce` step is invoked exactly as the direct call over the values the operation supplies (the callback law, § Collecting parameter lists, deconstruction, and callbacks), and what it returns is that call's result — the ONE value the call boundary delivers (§ Value boundaries; VAL-06): several written rows (or a spread row's several items) arrive as ONE sequence value, `()` and `[]` are ordinary values, and nothing is spread. `map` stores each result whole as ONE element of its list; `reduce` passes each result whole as the next accumulator, and its own result is the final accumulator. There is no cardinality check and no non-empty check on a callback result, so:

* For pure, deterministic, total computations, `map(L, F)` has the same result value as `[F(L[0]), F(L[1]), …]`, and `reduce([a, b], R, i)` has the same result value as `R(b, R(a, i))`. Every callable category uses the ordinary callback result: a user algorithm, a clause family (its selected clause's ordinary call, PAT-11), an alias, a Math member and a host operation alike.
* Wrappers are invisible: with `D(x) = x, x`, `G(x) = D(x)` and `H(x) = (x, x)`, `[1].map(D)`, `[1].map(G)` and `[1].map(H)` are all `[(1, 1)]`, exactly `[D(1)]`.
* The identity map reproduces every list: `map([(), 1, [], 2], Id)` with `Id(x) = x` is `[(), 1, [], 2]`.
* Every value is a legitimate accumulator: `R(x, acc) = x, acc` gives `reduce([1, 2], R, 0)` = `(2, (1, 0))` (one sequence value per step, nested, never spread), and `R(x, acc) = acc` over the initial `()` gives `()`.
* A reduce RESULT is a value boundary like every builtin result: its emitted count is `Result.valueCount` of its value (0 exactly for `()`).

`()` is an ordinary element and an ordinary accumulator — it never means "skip this element" or "keep the previous state"; use `filter` to omit elements. A callback body with an unintended extra row is VALID and produces a sequence value the author did not mean, exactly as the same body called directly would.

Owner clarification (2026-10-10): both unfolding equations compare result values for pure, deterministic, total computations. They do not guarantee identical effect ordering, argument demand, random draws, resource consumption or error timing. Operationally, `reduce` evaluates its initial value once, processes collection elements from left to right, invokes each step using the current accumulator, and preserves the complete ordinary call result as the next accumulator. Nested ordinary calls follow Model-C demand order: an unused inner accumulator can remain unevaluated, and a demanded inner call can run after an outer effect. With `R(x, acc) = x`, `reduce([1, 2], R, 1 / 0)` fails, while `R(2, R(1, 1 / 0))` returns `2`. With `R(x, acc) = tick() * x + acc` and a host `tick()` returning successive integers starting at one, the fold returns `5` and the nested expression `4`. Map demands its collection before the transforms; expanded calls can ignore indexed arguments. With `L = [tick(), tick()]` and `F(x) = tick()`, `map(L, F)` is `[3, 4]`, while `[F(L[0]), F(L[1])]` is `[1, 2]`. Option B and the existing demand, effect, error and resource rules are unchanged. Pins: `CallbackResultBoundaryTests.Independent_Reduce*` / `Independent_Map*`, canonical cases `reduce-demands-initial-before-iteration`, `nested-reducer-calls-may-skip-unused-initial`, `map-demands-collection-before-transforms` and `expanded-map-calls-may-skip-indexed-arguments`.

Failures of the invocation propagate unchanged: an output-less callback is still `MissingOutput` (VAL-05; never `()`), a callback's cardinality error keeps its plain `ArityMismatch` shape (the C# drivers' `variadicArityStyle` shapes only that diagnostic; ordinary calls report the variadic form), and errors, spans, demand order, effects, seeded draws and budget charges are the direct call's. Q-25 replaced the law because, after ordinary calls became value boundaries, retaining the raw-output callback restriction broke compositionality, identity mapping and wrapper equivalence: `[1].map(D)` failed while `[1].map(G)` and `[1].map(H)` succeeded with the same value, `map([(), 1], Id)` failed on its own element, and no reduce step could return `()`. The checks are deleted, the callback drivers always re-count at the call boundary (Lean `evalNeedUserSupply` / `evalNeedFamilySupply`, C# `EvalNeedUserSupply*` / `EvalNeedFamilySupply*`), and the former `recount` flag survives in C# only as the separated diagnostic style. Pins: `CallbackResultBoundaryTests`, `ClauseFamilyCallbackCardinalityTests`, `ClauseFamilyCallbackCardinalityBoundaryTests`, `CoreTests/CallbackResultBoundary.lean`, `CoreTests/FamilyCallbackCardinality.lean`, the spec cases `callback-result-is-the-ordinary-call-result`, `map-identity-preserves-empty-elements`, `reduce-accumulator-may-be-empty`, `clause-family-multirow-callback-is-one-value` and `clause-family-multirow-reduce-step-is-one-value`.

## Loops: patterns bind, rows produce, spread opens

THE LOOP INTERFACE (META-S3-3, owner decisions D1/D2/D6/D7, OD-1 and RP-1 of October 2026; Lean and C# changed together; it replaced `while(step, *init)` and `repeat(step, count, *init)` with no compatibility form). The loops are ORDINARY fixed-arity builtins whose step is a genuine META parameter: `while(meta step)` and `repeat(meta step, count)`, one registry signature (Lean `builtinSignature`, C# `BuiltinDescriptor.PlainSignature`) read by the arity gate, the binder, formula lifting, forwarding, the semantic model and diagnostics. A call `while(Step(0))` / `Step(0).while` / `Step(0).while()` and `repeat(Inc(0), 5)` / `Inc(0).repeat(5)` is formed by the ordinary supply former (an explicit spread in the OUTER argument list opens there, as for every builtin), passes the exact arity gate (`while` 1, `repeat` 2; anything else is `ArityMismatch` against `while(meta step)` / `repeat(meta step, count)` before any demand — the retired `while(Step, 0)` and `Step.repeat(3, 0)` included), and then binds through THE ONE inspecting binder like any META algorithm: a builtin whose signature declares a META parameter binds its supplied cells with `bindNeedPatterns` / `BindAcceptedNeedPatterns` over that signature, whose META arm captures the supplied call inertly (`NeedPlan.reference` / `ReferenceAdapterCell`; nothing evaluated). The captured call is never dispatched: its plan's canonical callee cell (CR-13) is the step, projected only when an iteration runs, and its ONE sticky supply (CR-9, the argument view's preparation — the captured call's ORIGINAL argument cells, never re-formed) is the initial state. Plain and dot spellings are the ordinary call rules (DOT-01..09): a structural member, a lexical declaration, a parameter or an alias named `while`/`repeat` is selected by ordinary lookup exactly as for any name. Consequences, each decided: a value, a property read (`Start = Step(0)` / `Start.while`: no implicit provenance, D6), a bare callable (`while(Step)`) or member path without an argument list (`Box.S.while`), an existing call reference are the ordinary META refusal, while since META-S3-4 every WRITTEN invocation is a step — a member or module call (`Box.S(0).while`, `Math.Abs(-3).repeat(2)`), a grouped member callee (`(Box.S)(0).while`), an extension call (`5.Add(1).repeat(1)` steps `Add` from the state `(5, 1)`) and a rebuilt projection (`op.Algorithm(op.Arguments*).while`) — and an anonymous block is named to be called (`Inc = { x + 1 }` / `Inc(0).repeat(3)`) (`call-by-need.md` § Generalized capture); `W(step) = while(step)` forwards the original call (CR-3) while `W(meta step) = while(step)` hands on a captured reference, which META refuses (CR-4); `Start()` is a fresh explicit call, captured like any call. The loops iterate a STATE — an ordered list of slots — and three concerns stay separate, none changing the others: the step's parameter PATTERNS bind the incoming state, the step's ROWS produce the next state, and the explicit SPREAD MARKER decides where a value boundary is opened.

* **Initial state.** Each EFFECTIVE supplied cell of the captured call is one state slot: a non-spread argument is one slot whatever its value (`Id(P).repeat(2)` with `P = 0, 1` is one slot holding `(0, 1)`), an explicit spread written inside the captured call supplies its items (`Fib(P*).repeat(10)`) (LOOP-01). ZERO slots are the ordinary empty state (OD-1): `Z = false` / `Z().while` and `Z().repeat(0)` are `()`, a collecting step binds an empty slice, and a step that needs a parameter fails through its own binding; a zero-state step that keeps returning `true` loops until MaxSteps, cancellation or the host's limits end it, like any non-terminating loop. Preparing the captured supply demands no argument VALUE; only explicit spreads written inside the captured call run. `repeat`'s count is the outer call's own VALUE argument: RP-1 — after the inert capture, `repeat` prepares the captured supply FIRST and only then demands and validates the count once (`Inc([1][5]*).repeat(1 / 0)` is `BadIndex`; `Inc(1 / 0).repeat(-1)` is the count's `IllegalInEval`, the non-spread cell staying unevaluated), the order the retired `repeat(Inc, 1 / 0, [1][5]*)` had (Lean `metaRepeatSetup`, laws `repeat_setup_order` / `repeat_setup_failure_skips_count`).
* **The step is an ordinary callable (Q-23, owner decision of October 2026).** A loop step is an ordinary callable invoked over the current state supply: ANY callable is eligible, and when an iteration runs, the current state cells — an already formed Model-C supply, never re-opened, re-counted or demanded by the loop — are supplied to it through its OWN ordinary invocation (Lean `runNeedStepSlots`, C# `InvokeLoopStepSupply`, shared by `EvalNeedLoop` and the generic continuation `RunReadyNeedStepSlots`): a user algorithm (also a block, a Math member and a host operation) through its parameter patterns as below; a clause family through the ORDINARY family dispatcher (Lean `selectNeedFamilyBranch`, C# `BindNeedFamilySupply` — family cardinality, clause order, inspecting patterns where a successful mismatch tries the next clause and a runtime failure aborts dispatch, `NoMatchingBranch` when nothing matches, deferred selected-branch materialization); a builtin through its ordinary argument roles (`applyBuiltinCountedResolved` / `ApplyBuiltinCountedResolved` over need-backed arguments — value, control, lazy and callback slots exactly as in a call); an alias as its target. Eligibility never depends on the callable's category or runtime representation, the number of family clauses, the spelling (alias, dot, forwarded, opened, qualified, structural path) or planner support. Eligible is not successful: a step whose ordinary invocation rejects the state fails with that ordinary failure (a family's arity, `NoMatchingBranch` — never loop termination; only `while`'s flag ends a loop — or a builtin's own arity or role error), reported under the step's own call frame inside the loop's frame. A captured callee with no CALLABLE identity — a value supplied for the parameter whose call is captured, `Run(f) = repeat(f(0), 1)` / `Run(5)` — is still no step (NEED-06): the iteration that needs it reports `NotAnAlgorithm` described as the "repeat step" or "while step" (Q-06, through `ProjectLoopStep` → `ProjectInvokingSlot`), never demanding the value; a value written as the META argument itself never reaches the loop (META refusal, above). A genuinely zero-parameter callable IS a step, and it cannot bind a non-empty state: the loop-state `ArityMismatch` ("the loop found no step parameter to bind it to"). Until Q-06 (October 5 2026) the value step was that same loop-state `ArityMismatch`. Projection happens only when an iteration runs, so a zero-iteration `repeat` never projects or validates its step (LOOP-05), and invoking a step charges no invocation depth (loop-step invocations are outside the depth protocol for every callable shape) and nothing beyond the loop's one step per iteration and the callable's own work. Before Q-23 the loop bound the state against the step's STORED parameter-pattern list, which is empty for a builtin and a family, so both were rejected as if they declared no parameters — an implementation omission of the original user-only binder, never a design rule. Pins: `LoopStepCallableDispatchTests` (six routes: the callable-category matrix, η, alias and forwarding transparency, Model-C demand, randomness, cancellation, Q-09 budget parity, planner interaction, source admission), `CoreTests/LoopSteps.lean`, the `loop-step-*` spec cases and `loopStep*` explorer specials.
* **Binding — patterns bind.** A user step's parameter patterns — or the selected clause head of a family step — bind the incoming state through the ONE inspecting binder (`bindNeedPatterns` / `BindNeedPatterns`), exactly as the direct call `Step(s1, …, sk)` binds k supplied items: fixed names bind positionally, a repeated name compares its occurrences (NEED-04), a collector binds an exact slice, a structural sequence or list pattern opens its own kind. Patterns constrain the INCOMING state only. A mismatch is the binder's own failure — a user step's cardinality mismatch is the loop-state `ArityMismatch` (`LoopStateBindingContext`), a family's the family's ordinary arity failure, a repeated-name conflict the ordinary `BadArity`, a wrong structural kind `TypeMismatch`.
* **Production — rows produce.** The step's emitted ROW SUPPLY is the next state (Lean `evalAlgOutputSlots` via `runNeedStepSlots` for `repeat`, `whileVerdictSlots` via `runNeedWhileRound` for `while`, both through the ONE dispatcher `runNeedStepWith` and the ONE row rule `OutputRows.items` / `formOutputRow`; C# `EvalAlgOutputSlots` / `EvalWhileVerdictSlots` and their `// MIRROR OF` twins, sharing `AddOutputRowItems`, reached through `InvokeLoopStepSupply` by `EvalNeedLoop` and by `RunReadyNeedStepSlots`, the generic continuation after a planned handover): the output rows of a user step or of the selected family clause are evaluated once each — left to right for `repeat`, condition first for `while` (next bullet) — under the bindings of the state that entered the iteration; each NON-spread row supplies exactly ONE slot — its value, whether `()` (a visible slot), a sequence, a list, a selection, a call or property result, or a completed loop — and each spread row `e*` supplies its spread items, possibly none. A builtin step has no written rows: its ONE result value is ONE non-spread row (Lean `loopStepBuiltinRows`), so a `()` result is one visible `()` slot and a collection result one slot holding the collection — exactly the row its one-row wrapper `W(p…) = builtin(p…)` writes, never the result's emitted count. No pattern category repacks that supply: the row supply takes no pattern-derived argument. Q-24 retired LOOP-04's packing of a pattern-bound step's top-level spread row into one slot (a `;`-era leftover, af92bad #99, widened to repeated names by a predicate swap, e054a6f #121), together with the pattern-category predicates and the generic step's binding-shape selection that existed only to compute its flag. Consequences: `Dup(x, x) = { x + 1, x + 1 }` and `Dup(x, x) = { (x + 1, x + 1)* }` form the same two-slot state, and `Dup(1, 1).repeat(2)` is `(3, 3)` for both; with diverging rows `x + 1, x + 2` one iteration gives `(2, 3)` and the NEXT binding is the repeated-name `BadArity`, exactly the direct call `Dup(2, 3)`'s; a structural step's one-value row `Step((a, b)) = (b, a + b)` is one slot its pattern re-binds, while `(b, a + b)*` supplies two items the one-pattern head cannot re-bind. To keep a structured value as ONE slot, write one value: a capture `P((*h), n) = (h*), n + 1` or an exact list `Grow([*h], n) = [h*, n], n + 1` (the history idiom `(history*, Next)` of the canonical Yellowstone program).
* **The `while` flag — condition first (LOOP-06; LOOP-CF1, owner decision of October 17 2026, Lean and C# together, no compatibility mode).** The continuation flag is the LAST EFFECTIVE item of that row supply, and a `while` round reads it FIRST: it forms the rows from the last row backwards, each one complete ordinary formation, until a row supplies an item; that row's last item is the flag (`WhileRound.discover`). A trailing spread row that supplies nothing is formed (effects included) and passed over. The flag must be a Boolean (`WhileRound.flag` / `ContinuationFlag`; otherwise `TypeMismatch`, reported before any earlier row is formed and positioned at the written row that supplied the flag — `Evaluator.ContinuationFlagOfRow`, the narrowest truthful location, since a call or spread row's items carry no provenance of their own; a spanless host-built row or an atomic builtin step leaves the inner error unpositioned, so the established enclosing-span fallback applies when available); no row supplying an item is the missing-flag `BadArity`. `false` returns the state that ENTERED the round without forming the remaining earlier rows — on the first round the original initial cells (zero accepted transitions), still subject to the final materialization below; `true` forms the remaining rows LEFT TO RIGHT and the supply without its last item is the next state, a one-item supply being both flag and state. Every row is formed at most once, in the one step activation, so the flag row and the transition rows share parameter cells and local-property caches. Protection is ROW-GRANULAR: a call or spread inside one row (`Step(x) = Pack(x)*`, a builtin or host step) is one ordinary value formed left to right, and whatever the flag row needs runs first by call-by-need (`10 / (x - 1), 10 / (x - 1) > 0` still divides by zero at `x = 1`). The order is a LANGUAGE rule, not an optimization: effects, host calls, seeded random draws and lazy initial-cell demands of the flag row precede the transition rows'; condition-first effects are not a subset of the retired step-first ones (`S(x) = 1 / 0, mark(false)` now returns `1`), an old success can fail (`S(x) = 1 / (1 - pulse()), pulse() == 0`), and budgets follow the new demand order identically on every strategy (Q-09b). The planned loop evaluates its continuation plan first and refuses a spread continuation row (fail closed, "loop plan spread continuation row"). * **The result — spread opens.** A completed loop is ONE value — the canonical capture of its final slots: `()` for zero slots, the slot itself for one, a sequence for several — with emitted count `Result.valueCount`, exactly like every builtin and call result (Lean `loopResultCounted`; C# `MakeCheckedLoopStateResult` through `ReCountValueBoundary`, the ONE construction site for the generic sync and async loops, the planned frame and every handover). A non-spread loop expression is therefore ONE item at every receiver: a root row (`Fibonacci(0, 1).repeat(10)` is the one row `(55, 89)`, formerly two rows), beside other rows (`Fibonacci(0, 1).repeat(10), 7` is two rows with emitted count 2, formerly 3), in a body, a capture or a list, as a loop-step row (one next-state slot — the former SUP-01 exception that spliced a nested loop row's k slots is gone; write `repeat(Inner(a, b), 2)*` to supply them, exactly as `Inner(a, b)*` would), and as a callback body (one value, like a helper returning it — the callback's ordinary call result, § Callback results). Only `L*` opens it. The slot count is not observable outside the loop: a one-slot state holding `(20, 30)` and the two-slot state `20, 30` complete to the same value and count, differing only in the loop's own next binding.
* **One iteration equals the direct call.** For a `repeat` step, `repeat(S(s…), 1)` equals `S(s…)` in value AND emitted count, whatever the step's head (LOOP-07); iterating is not nesting calls — `repeat(S(s…), 2)` is `S(S(s…))` when the first iteration supplies exactly one item (`Pair(x) = (x, x)`, `W(x) = [x, x]`) and `S(S(s…)*)` when it supplies zero or several (`Fib(a, b) = b, a + b`).
