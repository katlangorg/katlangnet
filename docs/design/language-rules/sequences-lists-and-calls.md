# Sequence, list, spread, and call rules

The full statement of the rules that AGENTS.md carries in compact form — consequences, examples, the implementation map, and the pinning tests — moved here verbatim from AGENTS.md in September 2026. These rules are as binding as AGENTS.md; the compact bullet there points at the section here. Keep both in step: a rule change edits the compact bullet and the section together.

## Output bundles, capture, and algorithm identity

OutputBundle split: brace algorithms parse to `Expr.AlgorithmExpr` / `.algorithmExpr` (algorithm identity: scope, parameters, properties, `open`, namespace interpretation), while surviving parenthesized groups parse to `Expr.Capture` / `.capture` over an `OutputBundle` (ordered written expression slots with NO lexical ownership — the receiver decides consumption). `Algorithm.User.Output` is an `OutputBundle`. CAPTURE IS NOT ALGORITHM IDENTITY: the algorithm channel sees only a zero-parameter output thunk over a capture's bundle, so a genuine capture suppresses callable identity (`Apply((Inc, Dec))` is an arity error on the thunk), a capture receiver exposes no structural members (`(Obj*).V` and `(Obj, Obj).V` fall back lexically; `Obj.V` navigates), and a capture is NOT an openable target (`open (M, N)` and `open (M*)` are targeted parse errors — the evaluator's open resolution equally rejects capture targets with `BadOpenForm`, mirroring spread). A REDUNDANT group is not a capture (PARENTHESES GROUP SYNTAX, `syntax.md`): `Apply((Increment))` is `Apply(Increment)`, `(Obj).V` is `Obj.V`, `open (M)` is `open M` — the parser erases every group of one non-spread slot before any of these laws apply. ALGORITHMEXPR IDENTITY IS STRUCTURAL: every `Expr.AlgorithmExpr` provides its contained algorithm on the higher-order channel regardless of parameter/declaration/output count — `Call0({42})` invokes the brace algorithm exactly like the named zero-parameter `Call0(Const)` — while the value channel reifies written slots independently (builtin argument adapters keep the one-slot value boundary for zero-declaration blocks: `repeat(step, n, {1, 2})` still supplies ONE initial state slot). Value-context implicit lifting (`ProcessValueDemandingArgumentBundle`) is a consumer property: Math member arguments are registry-provably strict-value and lift like every ordinary value position, while ordinary call arguments stay neutral to preserve higher-order references. When such a strict-value position REFUSES to lift because the enclosing CLOSED explicit parameter list cannot supply the referenced callable's implicit parameters (`ClosedListBlocksLifting`), the front end DIAGNOSES it (`ReportBlockedStrictValueForwarding`, reusing `DiagnosticCode.UndeclaredIdentifier` — the same closed-list rule as a directly written undeclared identifier, one indirection out, and equally reachability-independent): the value is required, nothing later can supply it, so the program is rejected naming the reference and its missing parameters, never the consuming member or the consumer's own declared argument names. The blamed names come from `MissingClosedListForwardingNames`, the ONLY implementation of the closed-list gate (`ClosedListBlocksLifting` blocks exactly when it is non-empty; gate and report read it through the region's `ResolverWalkMemos.MissingForwardingNames`, computed once per callee), so availability and blame cannot drift. The rule fires ONLY on that conjunction: positions the resolver never lifts in any caller (a capture, a Math call in a NEUTRAL argument slot, a dot-call receiver) are excluded because the closed list is not what blocks them, arbitrary user callees are never analyzed for strictness, and the strict-value flag is threaded beside `inCallPosition` WITHOUT becoming a memo key (it changes no rewrite). `Expr.Call.Args` is an `OutputBundle` and `Expr.DotCall.Args` an optional one: call/dot-call argument lists are ordered bundles of the ORIGINAL written argument expressions, evaluated transparently in the CALLER's lexical context — no transparent Args Algorithm exists anywhere in a parsed tree, and free names inside argument slots belong to the enclosing algorithm. `DotCall.Args = null` (no argument-list syntax, property-style access) stays distinct from an explicit empty list. There is NO transparent-vs-scoped Algorithm mode bit (no `IsParametrized`): every `Algorithm.User` is a scope-owning algorithm, transparent syntax is carried structurally by OutputBundle-bearing nodes (`Capture`, `ListLiteral`, `Call.Args`, `DotCall.Args`), and the parser's two body contexts are the named entry points `ParseScopedAlgorithm` (braces/trailing-brace arguments; `ParseRootAlgorithm` shares the scoped lowering) and `ParseParenthesizedBodyParts` (groups and call argument lists, which lower to capture/bundle — or to one recovery `AlgorithmExpr` when illegal declarations were retained for recovery).

## Value boundaries

A property/call/builtin RESULT boundary is a value boundary: it always returns ONE value, with emitted count `Result.valueCount` (0 for the empty sequence value, otherwise 1 — a list value always counts 1, including `[]`). A multi-output body/collection is observed by the caller as one sequence value; only an explicit caller-site spread (`expr*`) spreads it back into the surrounding item supply (spread reads the value via `spreadItems` — the spread view that also opens one list boundary — not the emitted count; `toItems` is the non-spread item view and keeps lists opaque). Redundant unary sequence structure is normalized during ordinary value construction, including `(())` and `((()))` to `()`. The shared helper is `reCountValueBoundary` (Lean) / `ReCountValueBoundary` (C#); it re-counts the value boundary without rebuilding the value and is applied at user/conditional calls (`evalUserCallCounted`, `evalConditionalCallCounted`), structural dot zero-arg access (`evalDotCallCounted`), and higher-order callback items (`countedSequenceCallbackItem` / `CountedSequenceCallbackItem`). SELECTION IS A VALUE BOUNDARY (September 2026): `A:i`, `first(A)`, and `last(A)` CHOOSE a value and never open it — the `.index` arm of `evalCounted` (C# the Index case of `EvalExpressionSpineCounted` and its async twin), `evalFirstCounted`/`evalLastCounted`, and the callback item all emit `(selected, Result.valueCount selected)`, so a selected sequence or list is ONE value everywhere (`Coll(A:0, 3)` collects `[(1, 2), 3]`, a lone root row `A:0` is one row, a loop-step row `A:0` is one state slot, `map(A, Id)` with `Id(x) = x` maps a nested pair to itself), a selected `()` re-counts to zero values whatever route selected it (so it spreads to nothing — `(first(((), 1)))*.Coll` is `[]` — while passed unspread it is ONE argument value: `first(((), 1)).Coll` is `Coll(first(((), 1)))`, which the exact collector law collects as `[()]`, like `E.Coll` / `Coll(E)` for `E = ()`), a selected `[]` stays one exact list (`[[]]`), and the selected value's origin is forgotten (`X = A:0` then `X.Coll` agrees with `A:0.Coll`, and both agree with `V.Coll` for a property `V` holding the same value — selection chooses a value; later collector behavior depends only on that value and whether it was spread, never on selection provenance, so `A:0.Coll` with `A = ((1, 2), 3)` is `[(1, 2)]` under the exact collector law described under Collecting parameters). Only the spread marker opens a selected value, one boundary (`(A:0)*.Coll` is `[1, 2]`; `A:0*` is the same select-then-spread). `first(A) ≡ A:0` and `last(A) ≡ A:(A.count - 1)` wherever the selection is valid (Lean `first_is_select_zero` / `last_is_select_last`; C# `SelectionValueBoundaryTests`; CoreTests `SelectionValueBoundary`). There is no selected-content projection and no live selection count anywhere: `Result.select?` / `Result.Index` return the stored element (`select_is_stored_element`), and `projectionItems` / `ProjectionItems` is only the TARGET's position view. Collection-producing builtins (`order`, `orderDesc`, `distinct`, `take`, `skip`, `filter`, `map`, `range`, `atoms`) materialize ONE exact list value with count 1 via `makeCollectionListResult` / `MakeCollectionListResult` and need no re-count. Collecting bindings likewise store one exact list value with count 1 (`collectSegment` / `CollectSegment`) and need no re-count or raw-supply storage. Lexical zero-arg property access and `if` already re-counted this way; the reduce initial accumulator is likewise reified as ONE accumulator value (`reCountValueBoundary`) before reduction, so an empty reduction returns it as ONE value and every reducer step receives it as one ordinary argument. NOT value boundaries (must keep their multi-item counts): root/body output accumulation (`evalAlgOutputCountedCore`), `while`/`repeat` multi-slot loop state, and the strict single-value `map`/`reduce` callback contract. Scalar/reduction builtins already return one value and are unchanged.

## Spread semantics

A spread expression spreads ONE item-producing boundary of the evaluated operand, contributing its items to the surrounding item supply — it does not create, return, or emit a sequence or list value by itself; the RECEIVER decides what the supplied items become (capture materializes a canonical sequence, a collecting binding collects an exact list, fixed bindings receive items individually, calls receive separate argument slots, root output emits rows). Sequence values and exact list values supply their contained items; other values follow the total item-view rule (an atom or string supplies itself as one item). A comma is REQUIRED between a spread and a following supplied item, on the same line or the next (`A*, B`, or the trailing `A*,` newline `B`), because `A* B` and `A*` newline `B` are both the multiplication `A * B`; only a declaration head, a closing delimiter, or end of input may follow a spread without a comma (`A* ; B` is invalid semicolon syntax; to pass a spread plus another value as ONE sequence-value argument, write `f((A*, B))`). In a call, evaluating the spread operand is part of assembling the supply, for EVERY callee — a user callable, a clause family, and a builtin alike: if it succeeds, the spread supplies exactly its items; if it fails, that failure (whatever its kind, `SpreadMissingOutput` for a missing output) is the call's failure, raised before the arity check, before clause selection or binding, and before any later slot — a failed spread never becomes a supplied item (§ Collection builtins, PV-20).

## Call argument assembly and written-slot reification

Call argument-slot assembly is SHARED by every callable shape — flat fixed, flat/mixed variadic, patterned (repeated-name / structural patterns), and multi-clause conditional (`BuildCallArgumentInputs` in C#, `collectVariadicCallItems` in Lean): each written slot is evaluated EXACTLY ONCE, left to right, and never again through the parameter it binds (§ At-most-once argument value evaluation); every non-spread slot is reified as exactly ONE argument value — ONE supplied item, whatever the value; and every explicit spread slot spreads exactly one value boundary into ordinary argument slots, items that no binder reopens, BEFORE any arity checking, clause selection, or pattern binding. VALUES STAY VALUES (September 2026): a supplied item carries no record of how it was written — the former `SupplyOrigin` slot mark and its one collector reading are deleted — because no binder reinterprets one item as several (see Collecting parameters), and no `CountedResult` carries provenance. Every non-spread slot — a capture, a brace block, a name, a call, a selection, a literal alike — is evaluated through the ONE `EvalCounted` / `evalCounted` at its value boundary, and NO callee shape receives a second, written-slot view of a slot (PARENTHESES GROUP SYNTAX, September 2026): a patterned callee's structural pattern opens the slot's VALUE one level when it is of the pattern's own kind (`GetStructuralPatternItems` / the `.sequenceValue` and `.listValue` arms of `bindParameterPattern`, over `Result.sequencePatternItems?` / `listPatternItems?`), so `F((1, 2))`, `F(S)`, `F(((1, 2)))`, `F({S})`, and `F((S*))` bind the same value; the former `explicitItems?` / `ExplicitSequenceValueItems` view and `evalVariadicCallItemPrepared` / `PrepareCallArgumentEvaluation` are deleted (the `PreparedAlgorithmOutput` slot list remains the loop machinery's state-slot view only). Caller-side spread therefore has identical meaning for every callee representation: `F(A*)` supplies A's spread items as slots whether `F` is flat, patterned, or a clause family (clause selection happens after spreading, so a literal clause such as `F(0, 0)` can win on a spread `(0, 0)` and a one-argument catch-all can never absorb a spread pair). WRITTEN-SLOT REIFICATION is the same rule at every syntax form whose grammar defines one value per written slot — list-literal elements, written sequence-value pattern argument items (`evalExplicitSequenceValueExprSlots` / `EvalExplicitSequenceValueExprSlots`), and the reduce initial accumulator (reified via `reCountValueBoundary` before reduction): a non-spread expression whose counted supply emitted several items (a multi-slot loop result) still contributes ONE value, and a selection is already one value (`S = ((1, 2), (3, 4))` makes `[S:0, 5]` the list `[(1, 2), 5]`; only `[(S:0)*, 5]` splices). Root/body output rows and loop step outputs are NOT written value slots — they keep their multi-item emission semantics (with one documented receiver-specific exception: a sequence-value-PATTERNED loop step's output keeps a top-level spread expression as ONE packed next-state slot, preserving structured state boundaries in both directions — see `docs/design/sequence-boundary-audit-2026-07.md`).

## At-most-once argument value evaluation

AT-MOST-ONCE ARGUMENT VALUE EVALUATION (Q-01 / PV-04, September 2026) is the normative statement of how a call's written slots and the parameters they bind relate; every other rule that mentions a parameter's value refers here. Within one call, a written argument slot is evaluated AT MOST ONCE for its value. If that evaluation succeeds, that is its value. If it fails with an ordinary error, that is its failure. If it reaches a resource limit, the call and the run end there: a resource limit is never a slot's outcome (RESOURCE LIMITS ARE TERMINAL, evaluator-and-hosting.md § Resource limits are terminal for the run). Reading the bound parameter never causes the argument expression to execute again: argument evaluation uses the proper semantic route ONCE (a named property through its ordinary property access and cache, a written block through its own evaluation, a dot expression through ordinary dot resolution), and every parameter read reuses the outcome it established. The outcome is immutable for the lifetime of the call activation, so a failure cannot heal, an argument's effects and random draws are never repeated by reading the parameter again, and every read of one parameter in one activation observes the same value or the same failure.

The two channels stay distinct. A slot that resolves to an algorithm (a name, a brace block, a dot expression, a parameter already bound to one) also binds that algorithm on the ALGORITHM channel, and an ORDINARY failure of the slot's value evaluation is RETAINED rather than raised (an argument nobody demands is not an error: `F(x, y) = x` called as `F(1, Bad)` is `1`; a slot with no algorithm channel fails the call at assembly, and so does a slot whose evaluation reaches a resource limit — `Evaluator.IsDeferrableEvaluationFailure`, before any later slot is evaluated). The retained failure is recorded beside the algorithm channel — Lean `AlgBinding.valueFailure?`, C# the `ValueError` element of an `AlgEnv` entry, both built by the ONE `slotAlgorithmBinding` / `SlotAlgorithmBinding` every user-call binder uses — and it IS the parameter's value outcome: the `.param` arm of `evalCounted` / `EvalParamCounted` reports it and never evaluates the algorithm; a builtin VALUE slot reads such a parameter through the ordinary parameter read (`resolveArgAlgExpr` / `ResolveArgAlgsWithSequenceSpread`, which treat a parameter with an established value outcome — value or failure — like a value-bound one, the named algorithm riding along only for invoking slots and the zero-argument law); the `.string` receiver reports it before judging the algorithm (`parameterValueFailure?` / `ParameterValueFailure`, value first, exactly as the read orders the tiers); and forwarding the parameter carries the outcome into the next call's slot without re-evaluating the source. Possessing an algorithm channel never licenses recomputing a value the slot has already established: INVOKING the algorithm (`f(x)`, `f()`, a callback or loop-step slot, structural member access `o.X`) is an ordinary invocation with the existing higher-order semantics — an explicit call is fresh, the `A` versus `A()` rule — and it never repairs or replaces the recorded value outcome (`B = if(tick() < 2, 1 / 0, tick())` with `ThenRead(f) = f(), f` called as `ThenRead(B)` runs `f()` afresh and still fails reading `f`).

The sticky failure belongs to the SLOT of one call activation, not to the property the slot named: a failed property evaluation is never cached (evaluator-and-hosting.md § Zero-argument property cache), so a separate later demand of the property — another slot, a root row, a read inside the callee — is an ordinary property demand. With `B` as above, `Ignore(x) = 0` called as `Ignore(B), B, B` gives `(0, 3, 3)`: the slot failed at `tick#1`, and the root reads evaluate `B` afresh and cache its first success. A successful slot of a named property reads the property's cache entry like any other value read (`P, Pair(P), P` draws once). What changed (September 2026): before this rule a flat fixed or normal-capture binder DROPPED a non-limit slot failure and every value read re-ran the raw argument algorithm outside the property cache — `Bad = trace(1) / 0` with `F(v) = v` traced twice, `Pair(B)` gave `(3, 5)` (one parameter, two values), and a seeded failing selection healed into a value (`F(Pick)` gave `10` where `Pick` alone is `BadIndex`); forwarding multiplied the retries. Diagnostic consequence: a NAMED argument's recorded failure keeps the report its evaluation made (`F(a) = sum(a)` called as `F(NoOut)` reports "Property 'NoOut' has no defined output", as `sum(NoOut)` does), while an unnamed written argument read through a parameter keeps the parameter blame (evaluator-and-hosting.md § Blame for an output-less written argument); a callable argument read as a value reports the zero-argument failure of the written argument (`Plus(f, x) = f + x` called as `Plus({x + 1}, 5)` is `UnresolvedImplicitParams`, what `{x + 1}` itself raises). Out of scope at first: the builtin argument adapter's own slots (a builtin callback slot's value evaluation during assembly, `reduce`'s `initial` handled as an algorithm control, a failed spread counted as an argument — PV-19, PV-05, PV-20). They were repaired on September 29 2026 (§ Collection builtins: BUILTIN CALL ASSEMBLY RESPECTS ARGUMENT ROLES): a builtin value slot establishes its outcome once exactly like a user argument slot, and a callback slot is never value-evaluated. The repeated-name verdict, out of scope here, was decided the next day (Q-05, § Collecting parameter lists, deconstruction, and callbacks: REPEATED NAMES ARE CONSTRAINTS, NOT MERGES): every occurrence supplies its own value, so a failed contribution's recorded failure now propagates instead of the other occurrence's value binding; it reuses this rule's recorded outcome and evaluates nothing again. Resource-limit absorption in undemanded slots (Q-02), out of scope here at first, was decided in the same month: a limit is terminal at assembly, never a recorded slot outcome (evaluator-and-hosting.md § Resource limits are terminal for the run). Pinned by Lean `CoreTests/ArgumentValueOutcome.lean` (binding-context counts: no read, forward or builtin slot re-evaluates a failed slot; a recorded failure never becomes the value its algorithm would compute), the laws `failed_slot_binds_its_failure_beside_the_algorithm_channel` / `valued_slot_binds_its_value_and_no_failure` (`KatLangArityLaws.lean`), the Lean-guarded canonical spec case `argument-value-outcome-is-final` (its Lean program derived from the parsed AST), and C# `ArgumentValueOutcomeTests` (the canonical `trace`/`tick`/seeded reproducers, named-property and owner-activation cache semantics, explicit calls, higher-order preservation, every binding shape and consumer, and the four laws as metamorphic relations — reads are observationally inert, a failure never becomes a value, a value never changes between reads, at most one evaluation per slot — on the sync and async engines, the async twin, the generic and optimized evaluators, and the forced twin).

A retained parameter failure also precedes a builtin VALUE slot's callable-signature classification. For example, `G(v) = sum(v)` called as `G({x + 1})` reports the slot's original `UnresolvedImplicitParams`, as a direct read of `v` does; `if`, collection controls, loop controls and `reduce`'s initial value preserve it too. They do not replace it with a fresh arity rejection or a reduce-initial hint. The original argument's error payload, property context and span are retained. This priority concerns an already-bound user parameter and does not change the builtin adapters' own retention policy.

## Arity error payloads

Flat fixed arity errors report the complete inputs to the selected binder, never the residual tails after consuming a prefix. Lean `bindParams` and C# `BindParams` check the two lengths before zipping: `Add(x, y)` called as `Add((1, 2))`, `(1, 2).Add`, or `map([(1, 2)], Add)` reports `(expected 2, actual 1)`; a three-parameter callable supplied two values reports `(3, 2)`. In the ordinary dual-channel path, parameters already satisfied only on the algorithm channel are excluded from the value binder's inputs. This closes the previously documented Lean/C# payload gap. Successful bindings, evaluation order, and D1 precedence are unchanged. The theorem `flat_binding_arity_reports_complete_supply` proves the full-length rejection; CoreTests `ExplicitValueOpening` and `CFullHostileReviewTests` pin ordinary/callback parity and the real counted binder.

## Lists

Square brackets construct list values (`Result.listValue` / `Expr.ListLiteral`), a second collection kind beside sequence values: sequence normalization never applies to list structure (`[7] != 7`, `[] != ()`), while parentheses around a list stay redundant sequence grouping (`([1, 2]) == [1, 2]`). `[` always begins a NEW expression (never a call/indexing delimiter; `A[1]` is a second same-line item after `A` and is the SYN-07A separator error, while `A, [1]` is the two-slot list), and bracket content is a pure expression list (spread elements insert their item supply; declarations are illegal inside brackets). Spread uses `Result.spreadItems` / `SpreadItems` (opens one sequence OR list boundary). Indexing `:` reads its TARGET's positions through the position view `Result.projectionItems` / `ProjectionItems` (`[1, 2, 3]:0` is 1 under the same zero-based index rules as sequence selection), while the selected ELEMENT is returned exactly as stored and never opened — a selected list is one opaque list (`[[1, 2], [3, 4]]:0` is `[1, 2]`), a selected sequence value one sequence value (`[(1, 2), (3, 4)]:0` is the one value `(1, 2)`); chaining selects one level at a time (see the selection rule under Value boundaries). Every other NON-spread consumer keeps lists opaque via `toItems` (a list is one item for value boundaries and call binding — calls never open lists, or sequences, implicitly). Deconstruction's unpacking receiver (Lean `ParameterPattern.unpacking`, C# `UnpackingParameterPattern`, opening through `Result.spreadItems` / `SpreadItems`) opens a lone sequence OR lone list (`x, y, z = [1, 2, 3]`), while a written structural pattern opens only its own kind (§ Structural patterns); collecting bindings collect exact lists (see the collecting-binding rule below). The post-binding builtin collection view opens a BOUND list exactly like a bound sequence value (`count([1, 2, 3])` is 3, `A.take(1)` works on a list property; the opening is never recursive — a nested list stays one opaque item; spread supplies ordinary argument slots, so `count([1, 2, 3]*)` is an arity error under the fixed `count(collection)` signature). The `atoms` builtin recursively collects numeric atoms through BOTH sequence and list boundaries (depth-first, left to right; strings contribute none) via its own dedicated collector `Result.languageAtoms` / `LanguageAtoms` and materializes them as ONE exact list through `makeCollectionListResult` (`atoms(7)` is `[7]`, `atoms([1, [2]])` is `[1, 2]`, `atoms('text')` is `[]` — the result kind never depends on the input). Truth is deliberately SEPARATE from every atom view: since first-class Booleans (September 2026) a condition is decided by `Result.asBool?`/`AsBool` alone — only a Boolean value qualifies — so lists have no truth value (`if([1], a, b)` stays invalid), numbers have none either, and the atoms traversal can never leak into `if` (see [`evaluator-and-hosting.md` § Boolean values]). Host-boundary flattening (`runFlat` / `Result.hostAtoms`, C# `RunFlat`/`EvaluateToAtoms` via `ToHostAtoms`) opens list boundaries; the non-spread `toItems` view stays list-opaque, and Boolean values have no host numeric projection at all. Receiver theorems: `receivers_agree_outside_lone_structure` (on supplies outside the `loneStructure` shape), `receivers_never_same_on_lone_structure` with its `receivers_never_same_on_lone_seq` / `receivers_never_same_on_lone_list` instances (a lone argument that is a sequence or a list never opens at a call, for ANY pattern list — values stay values — so call binding and deconstruction never coincide on it), and the concrete `lone_collecting_disagrees_on_lone_structure` in `lean/CoreArityAlgebraProofs.lean`; list-side receiver behavior over the real model is proven by the list bridge laws in `lean/KatLangArityLaws.lean` (e.g. `deconstruct_fixed_single_list_opens`, `lone_collecting_list_call_and_deconstruct_differ`). The CoreArityAlgebra paper artifact now models `Val.list` and `collect` (the pre-list sequence-only extraction is preserved at the pinned paper tag).

## Structural patterns

STRUCTURAL PATTERN DELIMITERS SELECT THE VALUE KIND THEY DESTRUCTURE (September 29 2026; an INTENTIONAL pre-release valid-source semantic change, Lean and C# changed together). KatLang has two collection kinds (§ Lists), and each has its own pattern language, with the delimiter that constructs the kind:

| Pattern | Matches |
| --- | --- |
| `x` | any one value, bound whole |
| `()` | the empty sequence value only |
| `(x, y)` | a sequence value of exactly two elements |
| `(x, *rest)` | a sequence value of at least one element; `rest` collects the others as an exact list |
| `(*xs)` | any sequence value; `xs` is the exact list of its elements |
| `[]` | the empty list only |
| `[x]` | a list of exactly one element |
| `[x, y]` | a list of exactly two elements |
| `[*xs]` | any list, of any cardinality — 0, 1 and N alike |

THE KIND LAW. A sequence pattern `(p1, …, pn)` opens a SEQUENCE value and nothing else (Lean `Result.sequencePatternItems?`, C# `Result.SequencePatternItems`); a list pattern `[p1, …, pn]` opens a LIST value and nothing else (`Result.listPatternItems?` / `ListPatternItems`). There is no cross-kind matching (`FirstPair((x, y))` rejects `[10, 20]`, `PairSum([x, y])` rejects `(10, 20)`), no scalar-as-one-item fallback (`(x, *rest)` rejects `7`; before this law a scalar was a one-item supply at every pattern level), and no implicit list↔sequence conversion in any layer. A bare binder is the ONLY pattern that takes a value whole. Nesting preserves kinds at every level: `F(([x, y], z)) = x + y + z` takes a sequence whose first element is a two-element list (`F(([10, 20], 30))` is 60), `G([(x, y), z])` a list whose first element is a pair, and each level is checked against its own delimiter.

THE SINGLETON RULE. A sequence pattern with exactly ONE non-collecting item — `(x)`, `((x))`, `(([x]))`, `(((x, y)))`, `(((true)))`, at any depth — is INVALID: a sequence value never has exactly one element (`(7)` IS `7`, normalization), so the pattern describes a boundary no value has. The parser reports `DiagnosticCode.SingletonSequencePattern` (`Parser.SingletonSequencePatternDiagnostic`, the wording of Lean `singletonSequencePatternMessage`) at the group, in parameter lists and clause heads alike, and never rewrites `F((x))` to `F(x)`; a host-built tree carrying one is refused before evaluation (Lean `validateExplicitParamOutputInvariant` → `illegalInEval`; C# `PreEvaluationAstViolation.SingletonSequencePattern`), so no layer gives the pattern a meaning the surface refuses it. The collector-only `(*xs)` is not a singleton (it matches every sequence, `()` included), and lists have the one-element pattern `[x]` because a one-element list is a value. `()` and `[]` are distinct patterns, exactly as `()` and `[]` are distinct values.

OUTER ARITY IS NOT STRUCTURAL SHAPE. Every top-level pattern consumes ONE argument whatever it destructures (`ParameterPattern.minimumSuppliedSlots`), so `F((x, y))` and `F([x, y])` are one-parameter callables and `F(1, 2)` is their arity error; the pattern then opens that one value.

FAILURES USE EXISTING CATEGORIES, and ordinary binders and clause families apply the SAME law. In an ordinary definition (and a callback, loop step, or zero-argument demand, which bind through the same binder) a value of the wrong kind fails the binding with `TypeMismatch` from ONE constructor (Lean `structuralPatternKindMismatch`, C# `Evaluator.StructuralPatternKindMismatch`), naming the written pattern and the value received ("sequence pattern `(x, y)` expects a sequence value, but received numeric value 7"), and a value of the right kind with the wrong number of elements is the group's `ArityMismatch` ("Sequence pattern `(x, y)` expects 2 elements, but received 3 elements.", "at least" for a pattern with a collector; the list form says "List pattern"). In a clause family neither is raised: a clause whose pattern does not match — wrong kind, wrong length, unequal literal — is skipped, and a call no clause matches is `NoMatchingBranch`. Single-clause classification is the same for both kinds (PAT-01: one literal-free binder/group clause is an ordinary algorithm, whether its groups are sequence or list patterns), and duplicate-clause detection is kind-aware (`F((a, b))` and `F([a, b])` are different heads, `F([]) = 0` beside `F(()) = 1` is not a duplicate).

ASSIGNMENT DECONSTRUCTION IS NOT A WRITTEN PATTERN. `x, *y, z = RHS` is the UNPACKING receiver: it opens a lone sequence OR lone list right-hand side one level and matches the flat targets against the items (§ Collecting parameter lists, deconstruction, and callbacks). It is modeled as its own construct — Lean `ParameterPattern.unpacking`, C# `UnpackingParameterPattern`, ONE node shared by every target's helper — so the kind law stays exact for every written pattern while deconstruction's values, errors and linear cost are unchanged; a right-hand side without output is its own `MissingOutput`. There is no bracketed deconstruction target, and none is added for symmetry.

## Collecting parameters

VALUES STAY VALUES — THE EXACT COLLECTOR LAW (September 2026; supersedes the former collector supply-boundary law). Values stay values across ordinary boundaries. A non-spread argument supplies exactly ONE item — its value, whatever it is (a scalar, a string, a Boolean, a sequence, a list, `()`, `[]`) and whatever produced it (a literal, a written group, a property, a call result, an `if`, a selection, a brace block, a captured spread `(A*)`, a dot-call receiver). The explicit spread `v*` converts a value into an item supply, opening exactly one sequence OR list boundary (`spreadItems`), and a spread-produced item is never reopened. Fixed parameters receive their allocated items unchanged. A collecting parameter collects EXACTLY the items allocated to it — after fixed prefix/suffix allocation, never at a fixed position — as ONE exact list with emitted count 1 (`collectSegment` / `CollectSegment`, called by `bindParameterPatternList` / `bindCountedParameterPatternList` and the C# `BindParameterPatternList` / `BindCountedParameterPatternList` on the segment they allocate). Structural patterns (`(a, b)`, `(*xs)`, `[a, b]`, `[*xs]`, each opening only its own kind — § Structural patterns), assignment deconstruction, and a builtin's own post-binding collection view are the explicit openers; no collector, callback, reducer, dot-call, selection, alias, or forwarding mechanism silently spreads a value on the programmer's behalf. Consequently no supplied item records how it was written: the former slot provenance (`SupplyOrigin.writtenSlot` / `finalItem`), its one reader `collectorSupply` / `CollectorSupply`, and the algebra's `Origin` / `CallSupply` / `fuseCollectorSegment` are DELETED and must not be reintroduced, and no parser mechanism (parenthesis preservation in particular) decides collector behavior.

A collector therefore counts ARGUMENTS while a fixed parameter reads a value's contents: `Cnt(*xs) = xs.count` gives `Cnt((10, 7))` 1 and `Cnt((10, 7)*)` 2, while `CntValue(x) = x.count` gives `CntValue((10, 7))` 2. A user-defined top-level collecting parameter collects exactly the argument slots actually supplied: `Name(*values) = body` with `Name(A)` binds `values = [A]` for a stored sequence and a stored list alike, `Name(A*)` collects A's spread items, and `Name()` collects `[]` — `F(A)` and `F(A*)` coincide only for a scalar atom, string, or Boolean argument (spread is total: `7*` supplies `7` itself) and differ for every sequence- or list-valued argument (`F((1, 2))` is `[(1, 2)]` while `F((1, 2)*)` is `[1, 2]`; `F([1, 2])` is `[[1, 2]]` while `F([1, 2]*)` is `[1, 2]`). A lone `*values` is the degenerate lone-collecting-binding case of this model. Forwarding is ordinary list spread — `Forward(*items) = Target(items*)` (equally the fluent `items*.Target`) re-supplies exactly the collected items (`spread(collect(S)) = S`, so `Forward((), [], (1, 2), [()]*)` reaches `Target` as the same four items), and passing the collected list unspread passes one list argument; there is no hidden raw-supply metadata, no receiver segment, and no arbitrary-expression `CountedResult` provenance (a `variadicSupplyEnv`/`VariadicStreamEnv` or a `CollectingSegmentEmittedCount` must never be reintroduced). ## Collecting parameter lists, deconstruction, and callbacks

A parameter list with two or more captures that contains one collecting parameter binds the supplied call argument supply: fixed captures bind from the front and back FIRST, and the single movable collecting parameter then collects the matched middle segment (possibly zero) EXACTLY — every remaining argument is one collected item, a lone remaining sequence value included (`F(x, *rest)` on `F(1, (2, 3))` binds `rest = [(2, 3)]`, on `F(1, (2, 3), 4)` `rest = [(2, 3), 4]`, on `F(1, (2, 3)*)` `rest = [2, 3]`; `F(*xs, z)` on `F((1, 2), 3)` binds `xs = [(1, 2)]`, on `F((1, 2), 3, 4)` `xs = [(1, 2), 3]`, on `F([(1, 2)]*, 3)` `xs = [(1, 2)]`; `F(x, *middle, z)` on `F(0, (1, 2), 3)` binds `middle = [(1, 2)]`, on `F(0, (1, 2), 3, 4)` `middle = [(1, 2), 3]`); a fixed position never opens a sequence or list argument (`F((1, 2))` with `F(x, *rest)` binds `x` to the whole pair and `rest = []`; `F(x, *middle, z)` on `F((1, 2))` is an arity error — arity counts supplied slots, never a sequence's elements). Assignment deconstruction, by contrast, is an unpacking receiver (Python-style): `x, *y, z = RHS` opens one lone sequence- or list-valued shared right-hand-side value and matches its items element-by-element, so `x, y, z = A` splits a stored sequence value or exact list value `A`. A written spread RHS is first captured into that shared value; it usually presents the same immediate items, but a singleton list whose lone element is itself a sequence or list can open one level further after singleton capture (for example, bare `x, y = [(1, 2)]` fails while `x, y = ([(1, 2)]*)` succeeds — the closing `)` makes `*` a spread marker; without it, an operand-like following row can make the trailing star multiplication and continue the line-bounded definition body). The collecting target then collects its middle items into an exact list (`x, *rest = [1, 2, 3]` binds `rest = [2, 3]`; `x, *rest = 1` binds `rest = []`); those items are pattern-opened items, collected exactly like any other supplied items, so a sequence-valued item among them is never reopened (`x, *y, z = (1, (2, 3), 4)` binds `y = [(2, 3)]`, `*all = (1, (2, 3))` binds `[1, (2, 3)]`). Deconstruction keeps its own one-level opening rule and does not use the call collector's segment abstraction. This unpacking is deconstruction-specific and does NOT change calls — `F(A)` still passes `A` as one argument (a fixed parameter binds it whole; a lone collector collects it as one item) and needs `F(A*)` to spread it into items. The shared front/collecting/back matcher is `bindParameterPatternList` (Lean) / `BindParameterPatternList` in C#); every collecting-binding materialization funnels through `collectSegment` (Lean) / `CollectSegment` (C#) — the plain and counted pattern binders plus the flat-collecting loop path all call it, always producing one exact list with emitted count 1. Item-supply call routing is `Algorithm.usesItemSupplyBinding` / `IsDeconstructionUserCallShape`. Assignment deconstruction is parser-elaborated so the right-hand side is evaluated once into a shared property and each target binds through an inline helper whose one parameter is the dedicated unpacking receiver (`UnpackingParameterPattern`, Lean `ParameterPattern.unpacking` — ONE receiver node shared by every target's helper, so the elaboration stays linear in the number of targets) that opens that single shared value through `spreadItems`; the receiver demands the value, so a right-hand side without output is its own `MissingOutput`, never a spread failure. The right-hand side is WRITTEN as an expression of the enclosing body and the front end elaborates it that way (`Algorithm.User.IsAssignmentDeconstructionSource`): its free names are the enclosing algorithm's implicit parameters (ordered by first written occurrence together with that body's rows, and read back through the inherited value environment), its bare sibling references lift in the enclosing algorithm's context, it obeys the enclosing closed-input rule (an undeclared name in a right-hand side under an explicit parameter list or a branch pattern is a front-end error), and the hoisted source never acquires parameters of its own — it stays the zero-parameter property the shared bind evaluates once, and its synthetic name never appears in a diagnostic (a body `a, b = x, 10` makes `x` a parameter of the enclosing algorithm, exactly as a written row `x + 10` would). A WRITTEN `(x, *y, z)` sequence pattern (or `[x, *y, z]` list pattern) opens one received value of its own kind for parameter/callback-position destructuring (§ Structural patterns). THE CALLBACK LAW (September 2026). A callback element is ONE ordinary argument: `map` and `filter` bind each element exactly as the direct call `F(element)`, and `reduce` binds each step exactly as the ordinary two-argument call `F(element, accumulator)` — through the ONE ordinary counted binder (`evalUserCallbackCallCounted` → `bindCountedParameterPatternList`; C# `EvalResolvedCallbackCallCountedCore` and its async twin → `BindCountedParameterPatternList`; a single-clause family through `flatBinderUserEquivalent?` / `TryGetFlatBinderUserEquivalent`, a multi-clause family through the ordinary branch matcher over the same supply). PATTERN-LIST BINDING FAILURE ORDER AND ORDER-INDEPENDENT REPEATED NAMES (September 2026, D1). REPEATED NAMES ARE CONSTRAINTS, NOT MERGES (Q-05, September 29 2026): a repeated name is a compatibility constraint over INDEPENDENTLY supplied arguments, so every contribution must supply its OWN value. A top-level capture whose name repeats at its pattern level needs its slot's value when it binds (Lean `bindParameterPattern` through `ParameterPattern.repeatsAtLevel`, C# `BindParameterPattern` through `RepeatsAtLevel`), exactly as a nested group needs the value it opens, so a valueless contribution is a BINDING failure reported with the slot's own recorded outcome (the at-most-once value evaluation already happened at assembly; nothing is evaluated again) before its range's repeated-name verdict (the prefix, suffix and collector retain D1's order): a callable-only argument (`Inc(y) = y + 1` passed bare) reports its own value demand — the arity rejection `Property 'Inc' expects 1 parameter` — and a failed one its own failure (`Q(x, x) = x` called as `Q(Bad, 7)` or `Q(7, Bad)` with `Bad = 1 / 0` is the division by zero; with two failed arguments the first in evaluation order is reported). Another occurrence never supplies a value in place of a missing or failed one, a failure never becomes a match, and no binding pairs one argument's value with another argument's algorithm. The verdict depends only on the multiset of contributions, never on argument order or merge grouping: with `A = 5` and `B = 2 + 3`, `P(f, f, f)` rejects `(A, 5, B)` in every permutation (two callables) and binds `(A, A, 5)` in every permutation, while `(Inc, 5, A)` is Inc's own failure wherever Inc stands. A name that repeats within the prefix but is ALSO bound on the other side of the collector is decided at the cross merge, with every contribution bound. Between DIFFERENT names the merge order decides which failure is reported: the innermost merge first (the name completing furthest right), and within one merge an unequal value before a callable-identity conflict (`P(x, x, f, f)` with `P(1, 2, A, B)` is the type mismatch, `P(f, f, x, x)` with `P(A, B, 1, 2)` the arity error); a valueless contribution precedes both (`P(x, x, f, f)` with `P(1, 2, Inc, Inc)` is Inc's own failure). Clause families already required every argument's value before any clause is tried and bind values only (PAT-07), so they are unchanged. Formula lifting supplies no independent arguments: it is by binding name (ownership-and-lookup.md § Formula lifting is by binding name), so `D = [P]:0` with `P(x, x)` is `D(x) = [P(x, x)]:0` — one caller binding, received complete by both occurrences, exactly as through the written `Same(x) = P(x, x)` — while the direct `P(7, 8)`, an explicit call with two parameters of its own, `Both(a, b) = P(a, b)`, and the exact alias `Some = P` (which inherits `P(x, x)` verbatim, FWD-02) supply independent arguments that must agree. A conflict INSIDE a nested group is part of binding that group. Keeping the first compatible entry is only a storage choice; it gives no positional precedence to a callable. Genuine aliases of the same declaration and captured activation remain compatible. ## The dot-call receiver

DOT-CALL PASSES A VALUE. SPREAD OPENS A VALUE. (September 2026 — this replaces the former "receiver segment" rule, under which a written group receiver fed a collecting parameter its raw rows and a named `()` receiver supplied zero items.) Dot resolution has three classes — a STRUCTURAL MEMBER (`Obj.X` calls Obj's own `X`, no receiver is injected), the `.string` INTRINSIC, and EXTENSION FALLBACK — and for extension fallback dot syntax injects the receiver as an ORDINARY leading argument and never opens it: `R.F(args)` is exactly `F(R, args)`, and `R*.F(args)` is exactly `F(R*, args)`, in value, emitted count, argument cardinality, binding (fixed, collecting, prefix/collector/suffix, patterned, clause family), evaluation order and count (the receiver is evaluated exactly once, before the written arguments), error kind, cache, randomness, and host effects, on the sync, async, generic, and optimized paths. Consequences: the receiver's item count never satisfies arity (`(1, 2).Add` with `Add(x, y)` is an arity error; `(1, 2)*.Add` is `Add(1, 2)`); a FIXED parameter binds it whole; a collecting parameter collects it as ONE item (the exact collector law, see Collecting parameters) exactly as it collects the written argument — dot-call is ordinary receiver injection, and the collector law explains fluent collection behavior — with `Coll(*xs) = xs`: `().Coll` is `[()]`, `1.Coll` is `[1]`, `(1, 2).Coll` is `[(1, 2)]`, `((1, 2), 3).Coll` is `[((1, 2), 3)]`, `[].Coll` is `[[]]`, `[1, 2].Coll` is `[[1, 2]]`, `{1, 2}.Coll` is `[(1, 2)]`, `((1, 2)).Coll` is `[(1, 2)]`, `(1, 2).Coll(3)` is `[(1, 2), 3]`, `().Coll(3)` is `[(), 3]`, `(1, 2, 3).Mean` and `[1, 2, 3].Mean` hand `sum` one non-numeric element, `(1, 2, 3).Scale(10)` with `Scale(*values, factor)` binds `values = [(1, 2, 3)]` after the suffix takes 10, and a capture of a spread `(A*).Coll` is `Coll((A*))`, one value collected whole — while only the spread forms hand over the receiver's items, through exactly one boundary: `()*.Coll` is `[]`, `(1, 2)*.Coll` is `[1, 2]`, `[]*.Coll` is `[]`, `[1, 2]*.Coll` is `[1, 2]`, `[(1, 2)]*.Coll` is `[(1, 2)]`, `(1, 2, 3)*.Mean` and `[1, 2, 3]*.Mean` average the items. The receiver's ORIGIN never matters (a literal, a property, a call result, an `if`, a selection `A:0` / `first(A)` / `last(A)`), a list, a nested sequence): `X = A:0` then `X.Coll` agrees with `A:0.Coll` and with `Coll(A:0)`. A `()` value's `valueCount` of zero is a fact about the value boundary, NEVER an implicit zero-argument supply (`One(a) = 1` binds `().One`, and `().Coll` collects the one visible `()`); only `()*` supplies nothing. A builtin callee binds the receiver as its ordinary `collection` / value argument through the ONE call funnel, so the dotted spelling has exactly the plain call's binding, error, and value-demand behavior: a bare named receiver of a builtin value slot (`A.count`, `A.sum`, `A.take(2)`) is judged by the zero-argument value-demand law and READ through the zero-argument property cache exactly like `count(A)`, and redundant grouping `(A).count` / `count((A))` is the same read — the former receiver-only cache reuse was an asymmetry and stays removed, and since September 27 2026 BOTH spellings read the cache, because how a property value is consumed does not affect caching (`evaluator-and-hosting.md` § Zero-argument property cache).

## Collection builtins

Collection builtins are ordinary FIXED-ARITY callables that receive exactly ONE fixed `collection` parameter followed by fixed control parameters: `count(collection)`, `sum(collection)`, `first/last/min/max/avg/order/orderDesc/distinct(collection)`, `take/skip(collection, count)`, `contains(collection, item)`, `map(collection, mapper)`, `filter(collection, predicate)`, `reduce(collection, reducer, initial)`. An unspread sequence or list value is ONE argument at this call boundary like at every other call boundary, and NOTHING is opened before binding — `count(1, 2, 3)`, `count()`, `sum(A*, B*)`, `take((1, 2, 3))` (missing count), `take([1, 2, 3]*, 2)`, and `distinct((), ())` are ordinary arity errors (spread only supplies ordinary argument slots that obey the same fixed arity; re-group to pass spread items as one collection: `sum((A*, B*))`). The bound collection value is interpreted through the POST-BINDING one-level collection view (`builtinCollectionItems` / `BuiltinCollectionItems`): a lone sequence OR exact list opens one outer boundary and any other value is a one-element collection — `count((1, 2, 3))`, `count([1, 2, 3])`, and `Values.count` are 3, `count(7)` is 1, `count(())`/`count([])` are 0, and opening is never recursive (`count((1, [2], 3))` is 3, `count(([], []))` is 2). Item shape/empty policies apply to the viewed items (`sum` numeric constraint, `first` non-empty). Collection-producing builtins (`filter`, `map`, `order`, `orderDesc`, `distinct`, `take`, `skip`, `range`) materialize their kept/projected items as ONE list via `makeCollectionListResult` / `MakeCollectionListResult`: zero items form `[]`, a single kept item forms `[item]` (never erased, so `take(((1, 2), (3, 4)), 1)` is `[(1, 2)]` and `distinct(((), ()))` is `[()]`), and nested sequence/list elements stay exact — the result kind never depends on the input kind, and only an explicit `spread` re-spreads the list into the arity layer. Canonical arity capture (`combineOutputSlots`, ordinary construction) and spread are UNCHANGED by this model, and collecting binding produces the SAME exact-list kind (`collectSegment`) — collecting parameters remain a general arity mechanism for user-defined callables, and passing a collected list to a builtin unspread passes it as the one collection argument (`Qmean(*args) = args.sum / args.count` works because the post-binding collection view opens the bound list; `map(values*, f)` inside a body is an arity error — write `map(values, f)`). Callback/builtin execution stays a separate runtime-owned phase after binding. For collection builtins the receiver fills the fixed `collection` parameter (`A.take(2)` is `take(A, 2)`, `A.count` is `count(A)`), with no builtin-specific receiver placement, through the same call funnel every written call uses (see § The dot-call receiver): the dotted and written spellings agree on binding, error kind, and the zero-argument value demand of a bare named receiver.

No builtin metadata or dot-level adapter may implicitly expand a receiver. Only an explicit spread supplies separate arguments; the builtin collection view applies after ordinary binding.

BUILTIN CALL ASSEMBLY RESPECTS ARGUMENT ROLES (PV-05 / PV-19 / PV-20 of the semantic-constitution audit, September 29 2026; observable semantics, Lean and C# changed together). A collection builtin's argument adapter (Lean `collectSequenceCallableCallItems`, C# `BuildCallableCallItems` and its async twin) takes the written slots left to right and handles each by the ROLE its position has in the builtin's metadata (`SequenceBuiltinMetadata.slotRole` / `SlotRole`): the `collection` and every value or whole-number control (`contains`'s `item`, `take`/`skip`'s `count`, `reduce`'s `initial`) are VALUE slots, every algorithm control (the `filter` predicate, the `map` mapper, the `reduce` reducer) is a CALLBACK slot, and a position past the fixed signature is SURPLUS. A spread slot is not a position: it is supply assembly, and each of its items takes the role of the position it lands on.
- A VALUE slot is demanded ONCE, at assembly and in written order. Its outcome is final for the call: a value, or an ORDINARY failure retained until binding reads the slot (so the call still reports its arity first — `count(1 / 0, 2)` is `ArityMismatch`) — and nothing evaluates the slot again. `reduce`'s `initial` is such a slot (HO-04): `reduce([], {x + y}, 10 / randomInt(0, 2))` is `DivisionByZero` after ONE evaluation for every seed that draws 0 first, where it used to evaluate the failed initial again and could return 10; `reduce([], Add, trace(1) / 0)` traces once, and nested failing initials evaluate the innermost failure once instead of 2^n times. A callable that cannot supply a zero-argument value is rejected there without running, and only that REJECTION keeps reduce's dedicated accumulator hint when the callable declares parameters (`reduce(xs, Add, Inc)`; Lean `reduceInitialRejection`, C# `ReduceInitialRejection`).
- A CALLBACK slot carries its algorithm channel and the callable it names, and the builtin INVOKES it per element; supplying it evaluates nothing (CALL-03). An unused callback therefore has no effect, draws no random number, cannot fail, and cannot recurse: with `A = tick()`, `map([], A)` is `[]` with no tick, exactly as `repeat(A, 0, 5)` never runs `A`; `L = L + 1` / `map([], L)` is `[]`; `E = ()` / `D = E.filter(D)` / `D.count` is 0. A zero-parameter callable invoked with an element is the binder's ordinary arity error, raised before its body could run (`map([1], A)`). The fused filter-count pipeline shares the rule: its predicate preparation (`PrepareFilterPredicateArgument`) evaluates nothing, so a failed source is the pipeline's verdict with no predicate outcome before or after it.
- A SPREAD slot's operand is evaluated at once, and its failure — of any kind — is the call's failure, raised before the arity check and before any later slot (§ Spread semantics): `take(Bad*)` is `Bad`'s own failure (formerly the arity error "called with 1 argument"), `map([], Bad*)` and `reduce([], Bad*, 0)` fail (formerly `[]` and `0`), and `count(1, {}*)` is `SpreadMissingOutput`. Because an earlier value slot's ORDINARY failure is retained rather than raised, a later failed spread is the first RAISED failure (`take(Bad, BadType*)` is the `TypeMismatch`).
- A SURPLUS slot keeps the value slot's eager evaluation (an ordinary failure retained, never demanded through the zero-argument law), so a wrong-arity call still reports its verdict after every written item was prepared (`count(trace(1), trace(2))` traces both); a callback position before it is still skipped (`map(trace(1), trace(2), trace(3))` traces 1 and 3).
Resource limits stay terminal everywhere in the adapter (evaluator-and-hosting.md § Resource limits are terminal for the run). Laziness elsewhere is unchanged: the non-collection builtins keep their own adapter (spread slots forced first, non-spread slots demanded by the builtin), and user calls still evaluate every written slot at assembly (§ Call argument assembly and written-slot reification). Pinned by Lean `CoreTests/BuiltinArgumentRoles.lean` (binding-context counts: one evaluation per value slot, none for an unused callback, a failed spread's own failure) and the slot-role laws in `KatLangArityLaws.lean` (`collection_position_is_a_value_slot`, `control_position_role_follows_its_kind`, `position_past_the_signature_is_surplus`, `reduce_initial_is_a_value_slot`, `callback_control_binds_only_the_algorithm_channel`, `value_control_reports_its_recorded_failure`), the `builtin-call-assembly-respects-argument-roles` spec case, and C# `BuiltinArgumentRoleTests` (six execution routes: effects, seeded random streams, recursion, every failure kind, and the value-slot, callback, and spread equivalences).
