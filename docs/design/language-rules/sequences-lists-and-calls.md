# Sequence, list, spread, and call rules

The full statement of the rules that AGENTS.md carries in compact form — consequences, examples, the implementation map, and the pinning tests — moved here verbatim from AGENTS.md in September 2026. These rules are as binding as AGENTS.md; the compact bullet there points at the section here. Keep both in step: a rule change edits the compact bullet and the section together.

## Output bundles, capture, and algorithm identity

OutputBundle split: brace algorithms parse to `Expr.AlgorithmExpr` / `.algorithmExpr` (algorithm identity: scope, parameters, properties, `open`, namespace interpretation), while surviving parenthesized groups parse to `Expr.Capture` / `.capture` over an `OutputBundle` (ordered written expression slots with NO lexical ownership — the receiver decides consumption). `Algorithm.User.Output` is an `OutputBundle`. CAPTURE IS NOT ALGORITHM IDENTITY: the algorithm channel sees only a zero-parameter output thunk over a capture's bundle, so a genuine capture suppresses callable identity (`Apply((Inc, Dec))` is an arity error on the thunk), a capture receiver exposes no structural members (`(Obj*).V` and `(Obj, Obj).V` fall back lexically; `Obj.V` navigates), and a capture is NOT an openable target (`open (M, N)` and `open (M*)` are targeted parse errors — the evaluator's open resolution equally rejects capture targets with `BadOpenForm`, mirroring spread). A REDUNDANT group is not a capture (PARENTHESES GROUP SYNTAX, `syntax.md`): `Apply((Increment))` is `Apply(Increment)`, `(Obj).V` is `Obj.V`, `open (M)` is `open M` — the parser erases every group of one non-spread slot before any of these laws apply. ALGORITHMEXPR IDENTITY IS STRUCTURAL: every `Expr.AlgorithmExpr` provides its contained algorithm on the higher-order channel regardless of parameter/declaration/output count — `Call0({42})` invokes the brace algorithm exactly like the named zero-parameter `Call0(Const)` — while the value channel reifies written slots independently (builtin argument adapters keep the one-slot value boundary for zero-declaration blocks: `repeat(step, n, {1, 2})` still supplies ONE initial state slot). Value-context implicit lifting (`ProcessValueDemandingArgumentBundle`) is a consumer property: Math member arguments are registry-provably strict-value and lift like every ordinary value position, while ordinary call arguments stay neutral to preserve higher-order references. When such a strict-value position REFUSES to lift because the enclosing CLOSED explicit parameter list cannot supply the referenced callable's implicit parameters (`ClosedListBlocksLifting`), the front end DIAGNOSES it (`ReportBlockedStrictValueForwarding`, reusing `DiagnosticCode.UndeclaredIdentifier` — the same closed-list rule as a directly written undeclared identifier, one indirection out, and equally reachability-independent): the value is required, nothing later can supply it, so the program is rejected naming the reference and its missing parameters, never the consuming member or the consumer's own declared argument names. The blamed names come from `MissingClosedListForwardingNames`, the ONLY implementation of `CanBuildImplicitCallArgumentsFromExistingParameters`, so availability and blame cannot drift. The rule fires ONLY on that conjunction: positions the resolver never lifts in any caller (a capture, a Math call in a NEUTRAL argument slot, a dot-call receiver) are excluded because the closed list is not what blocks them, arbitrary user callees are never analyzed for strictness, and the strict-value flag is threaded beside `inCallPosition` WITHOUT becoming a memo key (it changes no rewrite). `Expr.Call.Args` is an `OutputBundle` and `Expr.DotCall.Args` an optional one: call/dot-call argument lists are ordered bundles of the ORIGINAL written argument expressions, evaluated transparently in the CALLER's lexical context — no transparent Args Algorithm exists anywhere in a parsed tree, and free names inside argument slots belong to the enclosing algorithm. `DotCall.Args = null` (no argument-list syntax, property-style access) stays distinct from an explicit empty list. There is NO transparent-vs-scoped Algorithm mode bit (no `IsParametrized`): every `Algorithm.User` is a scope-owning algorithm, transparent syntax is carried structurally by OutputBundle-bearing nodes (`Capture`, `ListLiteral`, `Call.Args`, `DotCall.Args`), and the parser's two body contexts are the named entry points `ParseScopedAlgorithm` (braces/trailing-brace arguments; `ParseRootAlgorithm` shares the scoped lowering) and `ParseParenthesizedBodyParts` (groups and call argument lists, which lower to capture/bundle — or to one recovery `AlgorithmExpr` when illegal declarations were retained for recovery).

## Value boundaries

A property/call/builtin RESULT boundary is a value boundary: it always returns ONE value, with emitted count `Result.valueCount` (0 for the empty sequence value, otherwise 1 — a list value always counts 1, including `[]`). A multi-output body/collection is observed by the caller as one sequence value; only an explicit caller-site spread (`expr*`) spreads it back into the surrounding item supply (spread reads the value via `spreadItems` — the spread view that also opens one list boundary — not the emitted count; `toItems` is the non-spread item view and keeps lists opaque). Redundant unary sequence structure is normalized during ordinary value construction, including `(())` and `((()))` to `()`. The shared helper is `reCountValueBoundary` (Lean) / `ReCountValueBoundary` (C#); it re-counts the value boundary without rebuilding the value and is applied at user/conditional calls (`evalUserCallCounted`, `evalConditionalCallCounted`), structural dot zero-arg access (`evalDotCallCounted`), and higher-order callback items (`countedSequenceCallbackItem` / `CountedSequenceCallbackItem`). SELECTION IS A VALUE BOUNDARY (September 2026): `A:i`, `first(A)`, and `last(A)` CHOOSE a value and never open it — the `.index` arm of `evalCounted` (C# the Index case of `EvalExpressionSpineCounted` and its async twin), `evalFirstCounted`/`evalLastCounted`, and the callback item all emit `(selected, Result.valueCount selected)`, so a selected sequence or list is ONE value everywhere (`Coll(A:0, 3)` collects `[(1, 2), 3]`, a lone root row `A:0` is one row, a loop-step row `A:0` is one state slot, `map(A, Id)` with `Id(x) = x` maps a nested pair to itself), a selected `()` re-counts to zero values whatever route selected it (so it spreads to nothing — `(first(((), 1)))*.Coll` is `[]` — while passed unspread it is ONE written argument value: `first(((), 1)).Coll` is `Coll(first(((), 1)))` — one slot for arity, which the collector supply-boundary law then opens to nothing, `[]`, like `E.Coll` / `Coll(E)` for `E = ()`), a selected `[]` stays one exact list (`[[]]`), and the selected value's origin is forgotten (`X = A:0` then `X.Coll` agrees with `A:0.Coll`, and both agree with `V.Coll` for a property `V` holding the same value — selection chooses a value; later collector behavior depends only on that value and how it entered the call supply, not on selection provenance, so `A:0.Coll` with `A = ((1, 2), 3)` is `[1, 2]` under the collector law described under Collecting parameters). Only the spread marker opens a selected value, one boundary (`(A:0)*.Coll` is `[1, 2]`; `A:0*` is the same select-then-spread). `first(A) ≡ A:0` and `last(A) ≡ A:(A.count - 1)` wherever the selection is valid (Lean `first_is_select_zero` / `last_is_select_last`; C# `SelectionValueBoundaryTests`; CoreTests `SelectionValueBoundary`). There is no selected-content projection and no live selection count anywhere: `Result.select?` / `Result.Index` return the stored element (`select_is_stored_element`), and `projectionItems` / `ProjectionItems` is only the TARGET's position view. Collection-producing builtins (`order`, `orderDesc`, `distinct`, `take`, `skip`, `filter`, `map`, `range`, `atoms`) materialize ONE exact list value with count 1 via `makeCollectionListResult` / `MakeCollectionListResult` and need no re-count. Collecting bindings likewise store one exact list value with count 1 (`collectSegment` / `CollectSegment`) and need no re-count or raw-supply storage. Lexical zero-arg property access and `if` already re-counted this way; the reduce initial accumulator is likewise reified as one written accumulator slot (`reCountValueBoundary`) before reduction, so an empty reduction returns it as ONE value. NOT value boundaries (must keep their multi-item counts): root/body output accumulation (`evalAlgOutputCountedCore`), `while`/`repeat` multi-slot loop state, and the strict single-value `map`/`reduce` callback contract. Scalar/reduction builtins already return one value and are unchanged.

## Spread semantics

A spread expression spreads ONE item-producing boundary of the evaluated operand, contributing its items to the surrounding item supply — it does not create, return, or emit a sequence or list value by itself; the RECEIVER decides what the supplied items become (capture materializes a canonical sequence, a collecting binding collects an exact list, fixed bindings receive items individually, calls receive separate argument slots, root output emits rows). Sequence values and exact list values supply their contained items; other values follow the total item-view rule (an atom or string supplies itself as one item). A comma is REQUIRED between a spread and a following supplied item, on the same line or the next (`A*, B`, or the trailing `A*,` newline `B`), because `A* B` and `A*` newline `B` are both the multiplication `A * B`; only a declaration head, a closing delimiter, or end of input may follow a spread without a comma (`A* ; B` is invalid semicolon syntax; to pass a spread plus another value as ONE sequence-value argument, write `f((A*, B))`).

## Call argument assembly and written-slot reification

Call argument-slot assembly is SHARED by every callable shape — flat fixed, flat/mixed variadic, patterned (repeated-name / sequence-value patterns), and multi-clause conditional (`BuildCallArgumentInputs` in C#, `collectVariadicCallItems` in Lean): each written slot is evaluated EXACTLY ONCE, left to right; every non-spread slot is reified as exactly ONE argument value and MARKED as a written slot (`SupplyOrigin.writtenSlot` / `SupplyOrigin.WrittenSlot`; callback supply construction also marks whole callback items written); and every explicit spread slot spreads exactly one value boundary into ordinary argument slots — FINAL items (`SupplyOrigin.finalItem`) — BEFORE any arity checking, clause selection, or pattern binding. The mark is slot provenance for the collector supply-boundary law (see Collecting parameters) and nothing else: no consumer other than the collecting binder reads it, and no `CountedResult` carries provenance. Every non-spread slot — a capture, a brace block, a name, a call, a selection, a literal alike — is evaluated through the ONE `EvalCounted` / `evalCounted` at its value boundary, and NO callee shape receives a second, written-slot view of a slot (PARENTHESES GROUP SYNTAX, September 2026): a patterned callee's sequence-value pattern opens the slot's VALUE one level (`GetSequenceValuePatternItems` / the `.sequenceValue` arm of `bindParameterPattern`, over `Result.structureItems?`), so `F((1, 2))`, `F(S)`, `F(((1, 2)))`, `F({S})`, and `F((S*))` bind the same value; the former `explicitItems?` / `ExplicitSequenceValueItems` view and `evalVariadicCallItemPrepared` / `PrepareCallArgumentEvaluation` are deleted (the `PreparedAlgorithmOutput` slot list remains the loop machinery's state-slot view only). Caller-side spread therefore has identical meaning for every callee representation: `F(A*)` supplies A's spread items as slots whether `F` is flat, patterned, or a clause family (clause selection happens after spreading, so a literal clause such as `F(0, 0)` can win on a spread `(0, 0)` and a one-argument catch-all can never absorb a spread pair). WRITTEN-SLOT REIFICATION is the same rule at every syntax form whose grammar defines one value per written slot — list-literal elements, written sequence-value pattern argument items (`evalExplicitSequenceValueExprSlots` / `EvalExplicitSequenceValueExprSlots`), and the reduce initial accumulator (reified via `reCountValueBoundary` before reduction): a non-spread expression whose counted supply emitted several items (a multi-slot loop result) still contributes ONE value, and a selection is already one value (`S = ((1, 2), (3, 4))` makes `[S:0, 5]` the list `[(1, 2), 5]`; only `[(S:0)*, 5]` splices). Root/body output rows and loop step outputs are NOT written value slots — they keep their multi-item emission semantics (with one documented receiver-specific exception: a sequence-value-PATTERNED loop step's output keeps a top-level spread expression as ONE packed next-state slot, preserving structured state boundaries in both directions — see the loop-step notes in `tutorial.md` and `docs/design/sequence-boundary-audit-2026-07.md`).

## Lists

Square brackets construct list values (`Result.listValue` / `Expr.ListLiteral`), a second collection kind beside sequence values: sequence normalization never applies to list structure (`[7] != 7`, `[] != ()`), while parentheses around a list stay redundant sequence grouping (`([1, 2]) == [1, 2]`). `[` always begins a NEW expression (never a call/indexing delimiter; `A[1]` is a second same-line item after `A` and is the SYN-07A separator error, while `A, [1]` is the two-slot list), and bracket content is a pure expression list (spread elements insert their item supply; declarations are illegal inside brackets). Spread uses `Result.spreadItems` / `SpreadItems` (opens one sequence OR list boundary). Indexing `:` reads its TARGET's positions through the position view `Result.projectionItems` / `ProjectionItems` (`[1, 2, 3]:0` is 1 under the same zero-based index rules as sequence selection), while the selected ELEMENT is returned exactly as stored and never opened — a selected list is one opaque list (`[[1, 2], [3, 4]]:0` is `[1, 2]`), a selected sequence value one sequence value (`[(1, 2), (3, 4)]:0` is the one value `(1, 2)`); chaining selects one level at a time (see the selection rule under Value boundaries). Every other NON-spread consumer keeps lists opaque via `toItems` (a list is one item for value boundaries and call binding — calls never open lists implicitly). Deconstruction's `Result.structureItems?` / `StructureItems` opens a lone sequence OR lone list (`x, y, z = [1, 2, 3]`); collecting bindings collect exact lists (see the collecting-binding rule below). The post-binding builtin collection view opens a BOUND list exactly like a bound sequence value (`count([1, 2, 3])` is 3, `A.take(1)` works on a list property; the opening is never recursive — a nested list stays one opaque item; spread supplies ordinary argument slots, so `count([1, 2, 3]*)` is an arity error under the fixed `count(collection)` signature). The `atoms` builtin recursively collects numeric atoms through BOTH sequence and list boundaries (depth-first, left to right; strings contribute none) via its own dedicated collector `Result.languageAtoms` / `LanguageAtoms` and materializes them as ONE exact list through `makeCollectionListResult` (`atoms(7)` is `[7]`, `atoms([1, [2]])` is `[1, 2]`, `atoms('text')` is `[]` — the result kind never depends on the input). Truth is deliberately SEPARATE from every atom view: since first-class Booleans (September 2026) a condition is decided by `Result.asBool?`/`AsBool` alone — only a Boolean value qualifies — so lists have no truth value (`if([1], a, b)` stays invalid), numbers have none either, and the atoms traversal can never leak into `if` (see [`evaluator-and-hosting.md` § Boolean values]). Multi-clause conditional sequence-value patterns still match sequence values only (list patterns are deferred, so a list argument takes the fallback clause — except a SINGLETON pattern `(x)`, which matches any one argument whole via the scalar one-item rule, binding `x` to the entire list). Host-boundary flattening (`runFlat` / `Result.hostAtoms`, C# `RunFlat`/`EvaluateToAtoms` via `ToHostAtoms`) opens list boundaries; the non-spread `toItems` view stays list-opaque, and Boolean values have no host numeric projection at all. Receiver theorems: `receivers_agree_outside_lone_structure` (on final supplies outside the `loneStructure` shape), `receivers_never_same_on_lone_list` (a lone written LIST never opens at a call, for any pattern list), `receivers_never_same_on_lone_seq_with_fixed` (a lone written SEQUENCE never coincides for any pattern list with a fixed position), `receivers_agree_on_lone_seq_lone_collecting` (the lone collecting pattern is exactly where call and deconstruction coincide on a lone written sequence — the collector supply-boundary law), and the concrete `lone_collecting_disagrees_on_lone_list` in `lean/CoreArityAlgebraProofs.lean`; list-side receiver behavior over the real model is proven by the list bridge laws in `lean/KatLangArityLaws.lean` (e.g. `deconstruct_fixed_single_list_opens`, `lone_collecting_list_call_and_deconstruct_differ`). The CoreArityAlgebra paper artifact now models `Val.list` and `collect` (the pre-list sequence-only extraction is preserved at the pinned paper tag).

## Collecting parameters

THE COLLECTOR SUPPLY-BOUNDARY LAW (September 2026). A collecting parameter consumes its allocated argument supply. Multiple supplied items are collected exactly. If its entire segment is one lone non-spread sequence value, that sequence may provide the collector's whole supply, opening exactly one level. Lists remain exact. Items already produced by explicit spread are final supplied items. The rule applies to the SEGMENT allocated to the collector after fixed prefix/suffix allocation (never to a fixed position), and it reads ONLY slot provenance: a non-spread written slot (`SupplyOrigin.writtenSlot` / `SupplyOrigin.WrittenSlot`, marked by call-item assembly — a literal, a written group, a property, a call result, an `if`, a selection, a brace block, and a captured spread `(A*)` are written slots alike) versus a final item (`SupplyOrigin.finalItem` / `FinalItem`: an item an explicit spread produced, a pattern-opened item, a flat-callback row slot, a loop state slot, or a reducer accumulator slot). It never reads result provenance, never opens more than one level, and never opens a list. The ONE implementation is `collectorSupply` (Lean) / `CollectorSupply` (C#) — `[(sequenceValue items, writtenSlot)] → items`, every other segment its values as supplied — called by `bindParameterPatternList` and `bindCountedParameterPatternList` (`BindParameterPatternList` / `BindCountedParameterPatternList`) on the segment they allocate; no other binder and no parser mechanism (parenthesis preservation in particular) implements it, and `collectSegment` / `CollectSegment` still materializes the result as ONE exact list with emitted count 1.

With `Coll(*xs) = xs`: `Coll()` is `[]`, `Coll(1)` `[1]`, `Coll(1, 2)` `[1, 2]`, `Coll(())` `[]`, `Coll((1, 2))` `[1, 2]`, `Coll(((), 3))` `[(), 3]`, `Coll(((1, 2), 3))` `[(1, 2), 3]` (one level, never recursive), `Coll((), 3)` `[(), 3]`, `Coll((1, 2), 3)` `[(1, 2), 3]`, `Coll([])` `[[]]`, `Coll([1, 2])` `[[1, 2]]`, `Coll((1, 2)*)` `[1, 2]`, `Coll([(1, 2)]*)` `[(1, 2)]`, `Coll([()]*)` `[()]`, `Coll([]*)` `[]`, `Coll((1, 2)*, 3)` `[1, 2, 3]`; `Coll(((1, 2)))` is `Coll((1, 2))` (redundant grouping normalizes first). A user-defined top-level collecting parameter therefore collects the argument slots actually supplied, read through this law: `Name(*values) = body` with `Name(A)` binds `values` to `A`'s items for a stored SEQUENCE `A` and to `[A]` for a stored LIST, `Name(A*)` collects A's spread items, and `Name()` collects `[]` — `F(A)` and `F(A*)` coincide for scalars and sequence values and differ for every list-valued argument (`F([1, 2])` is `[[1, 2]]`, `F([1, 2]*)` is `[1, 2]`). For a scalar atom or string argument the two calls coincide because spread is total (`7*` supplies `7` itself). A lone `*values` is the degenerate lone-collecting-binding case of this model. Forwarding is ordinary list spread — `Forward(*items) = Target(items*)` (equally the fluent `items*.Target`) re-supplies exactly the collected items as final slots (`spread(collect(xs)) = xs`), and passing the collected list unspread passes one list argument; there is no hidden raw-supply metadata, no receiver segment, and no arbitrary-expression `CountedResult` provenance (a `variadicSupplyEnv`/`VariadicStreamEnv` or a `CollectingSegmentEmittedCount` must never be reintroduced) — the slot mark is the whole of the origin information the rule needs. LAWS (`lean/KatLangArityLaws.lean`): `collector_many_items_are_exact`, `collector_lone_scalar_is_exact`, `collector_lone_sequence_opens_once`, `collector_lone_empty_sequence_is_empty_supply`, `collector_lone_list_is_exact`, `collector_explicit_spread_item_is_final`, `collector_opening_is_non_recursive`, `selection_origin_does_not_change_collector_binding`, `dot_call_uses_same_collector_binding_as_plain_call`, the `collector_binder_*` binder-path laws; the paper algebra `CoreArityAlgebra.collectorSupply` / `fuseCollectorSegment` / `bindArgs : List Pat → CallSupply → Option Env` with `Origin` / `written` / `final`. PINS: `CollectorSupplyBoundaryTests` (the required table in both spellings, origin independence, mixed signatures, arity, nested patterns, callbacks, fusion, loops, deconstruction, builtins, a genuinely suspended async run), CoreTests `CollectorSupplyBoundary`, the LanguageSpec cases `variadic-grouped-and-spread` / `mixed-front-back-family` / `supply-vs-value-patterns` / `callback-variadic-collects` / `dot-receiver-passes-a-value` / `selection-forms-agree`, the ArityDifferential laws `COLLECTOR_LONE_WRITTEN_SEQUENCE_OPENS_ONE_LEVEL` / `COLLECTOR_EXPLICIT_SPREAD_ITEM_IS_FINAL`, and the CountedMatrix `collect/*`, `args/*`, `dot/*` cases.

## Collecting parameter lists, deconstruction, and callbacks

A parameter list with two or more captures that contains one collecting parameter binds the supplied call argument supply: fixed captures bind from the front and back FIRST, and the single movable collecting parameter then consumes the matched middle segment (possibly zero) by the collector supply-boundary law — several remaining slots are collected exactly, a lone remaining written sequence value opens one level (`F(x, *rest)` on `F(1, (2, 3))` binds `rest = [2, 3]`, on `F(1, (2, 3), 4)` `rest = [(2, 3), 4]`; `F(*xs, z)` on `F((1, 2), 3)` binds `xs = [1, 2]`, on `F((1, 2), 3, 4)` `xs = [(1, 2), 3]`, on `F([(1, 2)]*, 3)` `xs = [(1, 2)]`; `F(x, *middle, z)` on `F(0, (1, 2), 3)` binds `middle = [1, 2]`, on `F(0, (1, 2), 3, 4)` `middle = [(1, 2), 3]`); a fixed position never opens a sequence or list argument (`F((1, 2))` with `F(x, *rest)` binds `x` to the whole pair and `rest = []`; `F(x, *middle, z)` on `F((1, 2))` is an arity error — arity counts supplied slots, never a sequence's elements). Assignment deconstruction, by contrast, is an unpacking receiver (Python-style): `x, *y, z = RHS` opens one lone sequence- or list-valued shared right-hand-side value and matches its items element-by-element, so `x, y, z = A` splits a stored sequence value or exact list value `A`. A written spread RHS is first captured into that shared value; it usually presents the same immediate items, but a singleton list whose lone element is itself a sequence or list can open one level further after singleton capture (for example, bare `x, y = [(1, 2)]` fails while `x, y = ([(1, 2)]*)` succeeds — the closing `)` makes `*` a spread marker; without it, an operand-like following row can make the trailing star multiplication and continue the line-bounded definition body). The collecting target then collects its middle items into an exact list (`x, *rest = [1, 2, 3]` binds `rest = [2, 3]`; `x, *rest = 1` binds `rest = []`); those items are pattern-opened — FINAL — so the collector supply-boundary law never reopens a sequence-valued item among them (`x, *y, z = (1, (2, 3), 4)` binds `y = [(2, 3)]`, `*all = (1, (2, 3))` binds `[1, (2, 3)]`). Deconstruction keeps its own one-level opening rule and does not use the call collector's segment abstraction. This unpacking is deconstruction-specific and does NOT change calls — `F(A)` still passes `A` as one argument (a fixed parameter binds it whole; a lone collector applies the collector law) and needs `F(A*)` to spread it into final items. The shared front/collecting/back matcher is `bindParameterPatternList` (Lean) / `BindParameterPatternList` in C#); every collecting-binding materialization funnels through `collectSegment` (Lean) / `CollectSegment` (C#) — the plain and counted pattern binders plus the flat-collecting loop path all call it, always producing one exact list with emitted count 1. Item-supply call routing is `Algorithm.usesItemSupplyBinding` / `IsDeconstructionUserCallShape`. Assignment deconstruction is parser-elaborated so the right-hand side is evaluated once into a shared property and each target binds through an inline sequence-value parameter pattern (`SequenceValueParameterPattern`) that opens that single shared value. The right-hand side is WRITTEN as an expression of the enclosing body and the front end elaborates it that way (`Algorithm.User.IsAssignmentDeconstructionSource`): its free names are the enclosing algorithm's implicit parameters (ordered by first written occurrence together with that body's rows, and read back through the inherited value environment), its bare sibling references lift in the enclosing algorithm's context, it obeys the enclosing closed-input rule (an undeclared name in a right-hand side under an explicit parameter list or a branch pattern is a front-end error), and the hoisted source never acquires parameters of its own — it stays the zero-parameter property the shared bind evaluates once, and its synthetic name never appears in a diagnostic (a body `a, b = x, 10` makes `x` a parameter of the enclosing algorithm, exactly as a written row `x + 10` would). The same `(x, *y, z)` sequence-value parameter pattern opens one received value for parameter/callback-position destructuring. Flat callbacks with a top-level collecting parameter bind through the shared binder too (`bindCountedCallbackParameterPatternList` / `BindCountedCallbackParameterPatternList`), and the collector supply-boundary law applies through it by the ordinary callback binder: a WHOLE iterated element is one WRITTEN slot of the callback call, so a single-collecting callback keeps a scalar or list element as ONE collected slot (`[7].map(Collect)` binds `items = [7]`; `[[1, 2]].map(Collect)` binds `[[1, 2]]`) and opens a sequence element one level (`[(1, 2)].map(Collect)` binds `items = [1, 2]`; `[()].map(Collect)` binds `[]`; `[((1, 2), 3)].map(Collect)` binds `[(1, 2), 3]`), while a multi-parameter flat callee first opens a lone SEQUENCE-valued element into row slots — FINAL items (the flat-callback row convention; exact-LIST elements stay opaque and arity-error in flat binding — the nested `F((x, *y, z))` pattern form is the tool that opens BOTH kinds, and pattern-opened items are final too) and then allocates prefix/collecting/suffix (`Rows.map(F)` with `F(x, *y, z)` on sequence row `(1, 2, 3, 4)` binds `y = [2, 3]`, agreeing with the nested form on sequence rows only; a nested pair among the row slots stays one collected item — `[(1, (2, 3), 4)].map(F)` binds `y = [(2, 3)]`). The reducer's accumulator slots are final as well (an accumulator-side collector `Acc(x, *acc)` collects the accumulator's own one-level `toItems` slots exactly: `reduce([9], Acc, ((1, 2), 3))` is `[(1, 2), 3]`), and so are loop state slots: a loop step is never called with written arguments, so `repeat(Step, 1, (1, 2))` with `Step(*xs) = xs.count` is 1 with optimizations enabled or disabled; collecting step signatures explicitly decline planning, while eligible fixed-signature planned loops can invoke collectors in their bodies and temporary properties — loop slot production is unchanged and the decision lives in the binder abstraction, not in loop code. A callback binds every value it supplies through the ORDINARY call's nested-pattern rules (S3, September 2026): both binders open a sequence-value pattern's value through the ONE rule `Result.sequenceValuePatternItems` / `SequenceValuePatternItems` — a sequence or list value opens one level, and any other value (a number, string, or Boolean) is the scalar one-item supply at every pattern level and for every group size — so `map([7], P)` with `P((x, *rest))` binds `x = 7, rest = []` exactly like `P(7)`, `P((x, y))` rejects the scalar with the same nested-group arity mismatch in both, and each value a reducer receives binds like the same value in an ordinary call with the same supply — `R(element, accumulator)`, or, for a reducer with a top-level collecting accumulator parameter, the element followed by the accumulator's one-level slots (the reducer's own accumulator-slot convention above: `R((a, *r), *acc)` over `reduce([7], R, (1, 2))` binds `a = 7, r = [], acc = [1, 2]` like `R(7, 1, 2)`). The callback operation still decides how many values it supplies, in what shape, and how often it invokes (never for an empty collection); the binding rule for each supplied value is never its own. For a clause-family callback the no-match error names the callback role (`No matching branch for 'map transform'`), not the family — a pre-existing, Lean-aligned label; branch selection itself is the ordinary matcher. The front-end implicit-argument resolver synthesizes forwarding spread only when BOTH the destination capture is collecting AND the source binding of that name is a collecting binding: `Use(items) = Target` with collecting `Target(*items)` elaborates to `Target(items)` (one written argument, bound by the collector law like the written call: `Use([1, 2])` is `[[1, 2]]`, `Use((1, 2))` is `[1, 2]`), a caller collecting parameter `Use(*items) = Target` (collecting `Target`) elaborates to `Target(items*)`, and a collected-list source forwarded into a FIXED destination parameter passes the collected list as one argument (a fixed destination never re-spreads the list).

PATTERN-LIST BINDING FAILURE ORDER AND ORDER-INDEPENDENT REPEATED NAMES (September 2026, D1). Every binder (ordinary calls, callbacks, loop state, the zero-argument demand's empty supply) follows Lean's `bindParameterPatternList` / `bindCountedParameterPatternList`. First the arity check. Then, without a collecting capture, EVERY pattern binds left to right before any repeated name is decided (`bindPairs`), so a later pattern's binding failure — a nested group's arity mismatch, or an argument's retained value error that a pattern needs — outranks a repeated-name conflict (`P(x, x, (a, b))` called as `P(1, 2, Bad)` with `Bad = 1 / 0` is the division by zero, not the unequal `x`). With a collecting capture the fixed prefix binds and settles its own repeated names first, then the suffix does the same, then the collector's values are collected — a callable there is the collector's type mismatch — and materialized, and only then are the names shared across the collector decided (`P(x, x, *rest, (a, b))` with `P(1, 2, Bad)` is the prefix's unequal `x`; `P(x, *rest, x)` with `P(1, Bad, 2)` is the collected argument's division by zero). A repeated name is decided ONCE per pattern level, at the merge where its LAST contribution joins, and it binds iff every PAIR of its contributions is compatible — equal values, equal complete counted pairs (value and emitted count), and two algorithm-channel bindings only when each carries a value and they share one callable identity (declaration and captured lexical activations), because repeated-bind equality compares values and an algorithm-only argument (`Inc(y) = y + 1` passed bare) has none. The verdict depends only on the multiset of contributions, never on argument order or merge grouping: with `A = 5`, `P(f, f, f)` rejects `(Inc, 5, A)` in every permutation and binds `(A, A, 5)` in every permutation, and unequal values (`BadArity`) outrank an algorithm-only repeat (`TypeMismatch`) whatever the order. The same compatibility rule applies to one, two, and N occurrences (`P(f, f)` with `P(5, Inc)` binds the value 5 with the algorithm `Inc`; `P(Inc, A)` is the type mismatch). A name that repeats within the prefix but is ALSO bound on the other side of the collector is decided at the cross merge, with every contribution bound. Between DIFFERENT names the merge order decides which failure is reported: the innermost merge first (the name completing furthest right), and within one merge an unequal value before an algorithm-channel conflict (`P(x, x, f, f)` with `P(1, 2, Inc, Inc)` is the type mismatch, `P(f, f, x, x)` with `P(Inc, Inc, 1, 2)` the arity error). A conflict INSIDE a nested group is part of binding that group. The first collecting capture of a level is its collector; in the callback, loop, and zero-argument binders a second one (a host-built shape the parser rejects) is an ordinary suffix pattern that fails to bind, while an ordinary call with such a signature is refused earlier by its binding plan. A successful binding is permutation-invariant in its COMPLETE contents: channel availability, values, emitted counts, and callable identity. Keeping the first compatible entry is only a storage choice; it gives no positional precedence to a callable. Genuine aliases of the same declaration and captured activation remain compatible. Distinct callables now reject even for two occurrences with equal values: with `A(*xs) = 5`, `B(*xs) = 5 + xs.count`, and `P(f, f) = f(1)`, both `P(A, B)` and `P(B, A)` are type errors. This deliberately tightens the former two-occurrence rule. Runtime dot-result wrappers receive fresh identities; forwarding one wrapper preserves it. Pinned by `PatternBindingErrorPrecedenceTests`, the precedence and order-independence guards in `CoreTests/HigherOrderCalls.lean`, the laws `repeated_name_failure_is_permutation_invariant` and `repeated_name_complete_binding_is_permutation_invariant` (the actual merged environments, including absent channels and full counted pairs), and the `binding-failure-outranks-repeated-name-conflict` / `collecting-pattern-list-merges-after-the-collector` / `repeated-name-binding-is-order-independent` spec cases.

## The dot-call receiver

DOT-CALL PASSES A VALUE. SPREAD OPENS A VALUE. (September 2026 — this replaces the former "receiver segment" rule, under which a written group receiver fed a collecting parameter its raw rows and a named `()` receiver supplied zero items.) Dot resolution has three classes — a STRUCTURAL MEMBER (`Obj.X` calls Obj's own `X`, no receiver is injected), the `.string` INTRINSIC, and EXTENSION FALLBACK — and for extension fallback dot syntax injects the receiver as an ORDINARY leading argument and never opens it: `R.F(args)` is exactly `F(R, args)`, and `R*.F(args)` is exactly `F(R*, args)`, in value, emitted count, argument cardinality, binding (fixed, collecting, prefix/collector/suffix, patterned, clause family), evaluation order and count (the receiver is evaluated exactly once, before the written arguments), error kind, cache, randomness, and host effects, on the sync, async, generic, and optimized paths. Consequences: the receiver's item count never satisfies arity (`(1, 2).Add` with `Add(x, y)` is an arity error; `(1, 2)*.Add` is `Add(1, 2)`); a FIXED parameter binds it whole; a collecting parameter binds it through the collector supply-boundary law (see Collecting parameters) exactly as it binds the written argument — dot-call is ordinary receiver injection, and the collector rule explains fluent collection behavior — with `Coll(*xs) = xs`: `().Coll` is `[]`, `1.Coll` is `[1]`, `(1, 2).Coll` is `[1, 2]`, `((1, 2), 3).Coll` is `[(1, 2), 3]`, `[].Coll` is `[[]]`, `[1, 2].Coll` is `[[1, 2]]`, `{1, 2}.Coll` is `[1, 2]`, `((1, 2)).Coll` is `[1, 2]`, `(1, 2).Coll(3)` is `[(1, 2), 3]`, `().Coll(3)` is `[(), 3]`, `(1, 2, 3).Mean` averages the items, `(1, 2, 3).Scale(10)` with `Scale(*values, factor)` binds `values = [1, 2, 3]` after the suffix takes 10, and a capture of a spread `(A*).Coll` is `Coll((A*))`, one written value (which opens one level when it is a sequence) — while the spread forms hand over FINAL items through exactly one boundary: `()*.Coll` is `[]`, `(1, 2)*.Coll` is `[1, 2]`, `[]*.Coll` is `[]`, `[1, 2]*.Coll` is `[1, 2]`, `[(1, 2)]*.Coll` is `[(1, 2)]`, `(1, 2, 3)*.Mean` averages the items. The receiver's ORIGIN never matters (a literal, a property, a call result, an `if`, a selection `A:0` / `first(A)` / `last(A)`), a list, a nested sequence): `X = A:0` then `X.Coll` agrees with `A:0.Coll` and with `Coll(A:0)`. A `()` value's `valueCount` of zero is a fact about the value boundary, NEVER an implicit zero-argument supply (`One(a) = 1` binds `().One`); that a lone written `()` collects to `[]` is the collector law reading its segment, not a missing argument. A builtin callee binds the receiver as its ordinary `collection` / value argument through the ONE call funnel, so the dotted spelling has exactly the plain call's binding, error, and value-demand behavior: a bare named receiver of a builtin value slot (`A.count`, `A.sum`, `A.take(2)`) is demanded through the zero-argument value-demand law exactly like `count(A)` and neither reads nor stores the zero-argument property cache, and redundant grouping `(A).count` / `count((A))` makes the same direct demand; a real property body `V = A` still reads A through the cache — the former receiver-only cache reuse (observable for random- and host-backed properties, and as a materialization difference) is REMOVED, and closing the builtin-slot cache gap for BOTH spellings remains the documented open design question in `evaluator-and-hosting.md`.

IMPLEMENTATION: Lean `prepareLexicalDotCallArgs receiver extraArgs = [receiver] ++ extraArgs` → `callLexicalWithReceiverCounted` → the ONE `evalResolvedCallCounted` funnel (user, conditional, and builtin callees; builtin arguments through `resolveArgAlgsWithSequenceSpread`); C# `BuildLexicalReceiverCallArgs` → `CallLexicalWithReceiverCounted` / `CallLexicalFallbackCalleeWithReceiverCounted` → `EvalResolvedCallCounted` and their `// MIRROR OF` async twins; the sequence-pipeline optimizer's `filter`→`count` receiver adapter binds the receiver through the same builtin argument funnel (`ResolveArgAlgsWithSequenceSpread` + `BindSequenceBuiltinCollectionArgument`) and declines a spread receiver. ## Collection builtins

Collection builtins are ordinary FIXED-ARITY callables that receive exactly ONE fixed `collection` parameter followed by fixed control parameters: `count(collection)`, `sum(collection)`, `first/last/min/max/avg/order/orderDesc/distinct(collection)`, `take/skip(collection, count)`, `contains(collection, item)`, `map(collection, mapper)`, `filter(collection, predicate)`, `reduce(collection, reducer, initial)`. An unspread sequence or list value is ONE argument at this call boundary like at every other call boundary, and NOTHING is opened before binding — `count(1, 2, 3)`, `count()`, `sum(A*, B*)`, `take((1, 2, 3))` (missing count), `take([1, 2, 3]*, 2)`, and `distinct((), ())` are ordinary arity errors (spread only supplies ordinary argument slots that obey the same fixed arity; re-group to pass spread items as one collection: `sum((A*, B*))`). The bound collection value is interpreted through the POST-BINDING one-level collection view (`builtinCollectionItems` / `BuiltinCollectionItems`): a lone sequence OR exact list opens one outer boundary and any other value is a one-element collection — `count((1, 2, 3))`, `count([1, 2, 3])`, and `Values.count` are 3, `count(7)` is 1, `count(())`/`count([])` are 0, and opening is never recursive (`count((1, [2], 3))` is 3, `count(([], []))` is 2). Item shape/empty policies apply to the viewed items (`sum` numeric constraint, `first` non-empty). Collection-producing builtins (`filter`, `map`, `order`, `orderDesc`, `distinct`, `take`, `skip`, `range`) materialize their kept/projected items as ONE list via `makeCollectionListResult` / `MakeCollectionListResult`: zero items form `[]`, a single kept item forms `[item]` (never erased, so `take(((1, 2), (3, 4)), 1)` is `[(1, 2)]` and `distinct(((), ()))` is `[()]`), and nested sequence/list elements stay exact — the result kind never depends on the input kind, and only an explicit `spread` re-spreads the list into the arity layer. Canonical arity capture (`combineOutputSlots`, ordinary construction) and spread are UNCHANGED by this model, and collecting binding produces the SAME exact-list kind (`collectSegment`) — collecting parameters remain a general arity mechanism for user-defined callables, and passing a collected list to a builtin unspread passes it as the one collection argument (`Qmean(*args) = args.sum / args.count` works because the post-binding collection view opens the bound list; `map(values*, f)` inside a body is an arity error — write `map(values, f)`). Callback/builtin execution stays a separate runtime-owned phase after binding. For collection builtins the receiver fills the fixed `collection` parameter (`A.take(2)` is `take(A, 2)`, `A.count` is `count(A)`), with no builtin-specific receiver placement, through the same call funnel every written call uses (see § The dot-call receiver): the dotted and written spellings agree on binding, error kind, and the zero-argument value demand of a bare named receiver.

No builtin metadata or dot-level adapter may implicitly expand a receiver. Only an explicit spread supplies separate arguments; the builtin collection view applies after ordinary binding.
