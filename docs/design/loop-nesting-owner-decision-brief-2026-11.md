# Bounding nested async loop steps

**Owner decision requested, November 27, 2026.** Adopt a separate run-scoped limit on simultaneously active loops. I recommend a default of **1,024**, a hard ceiling of **4,096**, and a distinct resource-limit error. Count a loop once across all its rounds, including any time it waits for a fold accumulator. This would bound retained loop activations on both evaluator routes and let a host configure ordinary call depth independently. The owner can adopt this policy independently of the earlier stack-safety repair.

Q-39 is open. The November 21 adversarial performance audit at `8947d21e` requested an owner decision on finding 1, recommendation 3. At the reviewed checkout, `8aac1808`, the rule still explicitly leaves loop nesting undecided. The Constitution also cites Q-39 in LOOP-08 and RUN-03. This brief proposes C# host policy. Lean models the unlimited evaluation, and its proof fuel has no correspondence to host `MaxSteps`. None of these repairs releases an outer loop still awaiting an inner one. A sync evaluator can stop earlier at the host-stack backstop. An async twin can keep accumulating loop state through either explicit hops or genuine suspension. A finite step budget can eventually stop it, but controls cumulative work. ## Compatibility and the choice of bound

An activation starts when a `while` or positive-count `repeat` passes loop admission and ends when that `EvalNeedLoop` returns. It covers step projection, the generic or planned body, handover and final state demand. A million sequential rounds of one loop require a single admission. The cap covers admitted loop steps. A zero-round repeat and a new entry waiting for its pre-admission hop have yet to run a step.

A lazy `reduce` makes the distinction between **logical depth** and **live activations** observable. In the 300-element fold probe, the reducer demanded its accumulator from inside its loop. With observation alone, 300 loops were open at once. Resetting the loop count to the fold's starting level made the reported peak one, with 300 fold continuations still suspended. Both executions returned 45,450. A strict cap of 128 refused the same fold, while two 300-element controls that held at most one loop completed. This was observed on generic, planned and twin routes. The fold resets ordinary **call depth** by design. It never releases a waiting loop by resetting an integer. A fold without overlapping loops can still be as long as its admitted collection. [Fold accounting](../../dotnet/src/KatLang/Evaluator.ReduceFold.cs) · [Lazy reduce contract](language-rules/sequences-lists-and-calls.md#lazy-reduce-accumulators)

| Design | Compatibility, counters and refusal |
| --- | --- |
| **A. Charge each active loop one ordinary depth level** | Uses the existing depth ceiling and `EvaluationDepthExceeded` (23). Loops compete with calls. In the corpus, `PeakDepth` changed for 122 programs, including 104 conformance cases or probes. Six extra programs changed outcome. The shared entry preserved route parity in the recorded fields. Ordinary fold-depth resets leave suspended loop activations outside this bound. |
| **B′. Separate count using `EffectiveMaxDepth` and code 23** | A strict count caps active loops at 128 or a host's lower setting, without charging call depth. No new public API. Previously completing loops may fail after a host lowers its call-depth setting, even with headroom in the call budget. At 128 the 300-loop fold fails with code 23 despite each reducer step fitting the call limit. This changes the meaning of the documented fold guarantee. Resetting the count at each fold preserves that guarantee but only bounds nesting within each continuation. |
| **B. Separate count, limit and failure code (recommended)** | A strict `MaxLoopNesting` caps active loops independently of call depth. It can preserve the 300-loop fold at the default and report a specific reason at a lower limit. Costs a new public option, error variant and stable code. The depth and step counters retain their existing meanings. |
| **Cap nested async stack hops** | The refusal would depend on route and available native stack. A measured genuinely suspending chain had zero explicit hops while retaining just as many loop activations as its hopping counterpart. A hop cap cannot enforce the proposed bound. |
| **Keep the present rule** | Preserves all existing outcomes. A host can choose a finite `MaxSteps` or request cancellation. Neither provides an independent ceiling on the number of loops waiting under default settings. |

**Why 1,024 and 4,096?** The default accommodates the observed 300-loop fold and the existing 400-level terminating process test on routes with headroom. A host or test can select a higher limit, up to 4,096, to accommodate the existing 2,000-level termination and failure-unwind checks. A 128 default is also viable if the owner accepts earlier refusal of those terminating programs. In one measured twin shape, refusal at 1,024 took 14.4 MiB of total allocation and refusal at 4,096 took 57.8 MiB. These samples help choose a starting ceiling. They establish no upper bound in bytes, native frames or diagnostic frames for arbitrary programs. A synchronous route can reach its physical stack limit first at any of these settings.

## What hosts would observe under B

| Situation | Proposed behavior |
| --- | --- |
| Ordinary and terminating loops | Up to the effective limit `N`, a run with headroom retains its value or original failure, effect order and resource counters. If a terminating program actually needs loop `N + 1`, it receives the nesting refusal before that step is projected or run. Sibling loops reuse the released slot. A lower limit may deliberately change a previously successful run. |
| Hops, suspension and strategy | Hold the same activation across a stack hop, incomplete await, fold accumulator demand and planned-to-generic handover. Each new public run owns its budget. The twin's scheduling changes no logical charge. A physical backstop can still report `EvaluationStackExhausted` (30) first, as allowed by Q-09a. |
| Long runs with finite `MaxSteps` | Keep one step charge per executed round and all existing call and bulk-work charges. Once the step chokepoint refuses, retain `EvaluationStepLimitExceeded` (24). If the next loop is refused first, retain the nesting error without charging a step. Merely using the last permitted step does not report an error at loop admission. |
| Depth, peaks and cleanup | Keep `CurrentDepth`, `PeakDepth`, consumed steps, checkpoints and materialization counters identical on a common executed prefix. Return active loop and call counts to their entry values on every exit, including cancellation. Peak counters retain their high-water marks. Iterations, hops and handovers add no nesting level. |
| Failure contract | Propose `EvalError.EvaluationLoopNestingExceeded(Limit)` mapped to a distinct stable `KatLangErrorCode.EvaluationLoopNestingExceeded` (93 is available at the reviewed revision). Mark it as a terminal resource refusal, carry the **effective** limit and use the ordinary resource-limit source-span convention. Preserve code 23 for actual depth and the existing lazy-read generation rule. The prototype reused code 23, so it provides no verification of the proposed public code or message. |

**Cancellation and host faults.** On an otherwise admissible loop with headroom, preserve today's observation points. On an actual nesting refusal, consult `CheckContinuation()` before retaining the new resource error. In a twin boundary, an already retained host exception wins, followed by required-source cancellation, the run token and a retained terminal failure in the existing order. `HostTermination` travels by value and receives no context frames. The entry closes the boundary in a `finally` and rethrows the retained exception. The internal marker must never be passed to `RetainTerminal`, which accepts resource limits only. A refused descent cannot absorb a host failure or allow later effects. These ordering claims about production use the current code. The proposed refusal has no production implementation or direct marker-collision test. ## Evidence for the decision

The following are recorded Windows x64 Release observations from the investigation at `8aac1808`. The reviewer independently inspected the source, logs and corpus results. Elapsed time and memory are samples from one machine. The probe divides byte counts by 1,048,576.

| Observation | Recorded result |
| --- | --- |
| Synchronous host-stack backstop | Across the measured generic/planned and repeat/while shapes, the deepest observed levels were 37–71 on a 1 MiB thread, 349–663 on 8 MiB and 705–1,338 on 16 MiB. There is no portable nesting threshold in these figures. |
| Twin memory and cancellation | In one shape, sampled live heap rose from 9.2 MiB at 1,000 levels to 898.9 MiB at 100,000. Cancellation returned with the run token at all four measured depths. The return took about 15–471 ms and allocated 0.1–4.6 MiB after cancellation. |
| Finite fuel | At `MaxSteps = 1,000,000`, one run reached 499,024 levels, sampled about 4,525 MiB of managed heap and returned code 24. Call depth returned to zero. |
| Hops and failures | The two 20,000-level shapes took 571 and zero explicit hops respectively. Both retained about 186 MiB. An ordinary failure at 64,000 levels returned with 128,002 context frames. The measured prototype nesting refusals carried zero context frames. |
| Tight boundary and fuel order | With the separate counter set to 128, a finite 128-loop input succeeded on all three routes with adequate stack. Entry 129 in the separate repeat probe refused at 258 consumed steps, `PeakDepth = 2`. With a 256-step budget the twin returned code 24. At 258 the nesting check refused before another round charge. The prototype used code 23 for this refusal. |
| Fold compatibility | The same independent-counter prototype with a cap of 128 refused the 300-overlapping-loop fold at 257 steps and `PeakDepth = 1`. The version that reset at each continuation completed in 600 steps and reported loop peak one. The no-cap, no-reset control measured peak 300. |

**Corpus comparison.** Of the parsed feature sources, probes and 20 added programs, 2,433 ran on each of the generic sync, plan-enabled sync and counted twin routes (7,299 rows). Another 89 inputs had front-end errors and did not execute. The instrumented no-policy build matched the recorded baseline fields. The strict counter at 128 changed the outcome summary and steps of two added programs and changed no recorded `PeakDepth`. Among conformance inputs, 112 exercised a loop and the greatest observed nesting was two. The 300-element fold was a separate experiment. With the proposed independent option, reducing `MaxDepth` would not implicitly reduce the loop allowance.

The harness recorded a truncated rendering of the value and its emitted count, or the terminal error type, public code and number of context frames. It recorded steps and current/peak depth, plus the prototype's loop observations. The three routes agreed on the recorded fields. Complete nested values, error payloads and spans, ordered effects, expression checkpoints, materialization totals and post-exception budget state were outside that comparison. The final scratch probe also registered an async host operation in some sync attempts, which the sync entry rejected during setup. Those rows supply no loop evidence. The earlier sync-only samples and the host-operation-free corpus supply the synchronous observations above. No full implementation of option B, platform comparison or combined marker/refusal test was run.

## Acceptance criteria if the owner approves B

1. Admit one loop only when a round will run, after the existing hop/backstop and before step projection. Hold a balanced scope until all work in that invocation completes. Do not reset it on a fold continuation. A refused entry leaves the count, peaks and cumulative budgets as they were. Use 1,024 when unset, reject zero or negative settings, and clamp positive settings above 4,096 to 4,096. Pin the effective limit in the failure payload.
2. Pin a terminating chain at `N − 1`, `N` and `N + 1` with adequate stack on the generic, plan-enabled and twin routes. Exercise both loop forms, sequential and zero-round repeats, real suspension, a hop and a planned handover. Verify value and emitted count, ordered effects, failure code/payload/span, current and peak counters and identical fuel at the common prefix. Keep an independent small-stack process check for code 30.
3. Test the 300-element fold at limits 1,024 and 128. Require the successful value and peak 300 in the former, the new nesting error in the latter, and success at 128 for the controls that keep only one loop active. Check independently varying `MaxDepth` and `MaxLoopNesting`. A long fold with no overlapping loops preserves its one-step call-depth behavior.
4. At a configured loop limit of 128, preserve the 256/258-step ordering above. Use a retained budget reference to check cleanup after success, ordinary failure, resource refusal, host fault and cancellation. Pin active counts at zero on return, the peak reached, and a fresh run's initial state. At a full counter, exercise a previously retained terminal, the original host exception and same-token cancellation. Check both the internal marker and the public rethrow, including identity and absence of later effects.
5. Preserve the existing termination-transport and failure-scaling gates, including genuine suspension and exception/frame counts. Set an explicit higher loop allowance for the existing deep cases where needed. Keep separate coverage of the default refusal.
