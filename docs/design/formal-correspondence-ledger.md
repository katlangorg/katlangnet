# Formal correspondence ledger

The one tracked status of what is proved, about what. Older labels (R4, R6, CF-4, R7, FG-H1) are kept only where they name a
live claim. A theorem name is not a proof of a broader claim, and a stale paragraph is not evidence that a theorem is missing:
read the statement. No other document restates a row's status: it links here.

The dated change log and the former E-18 row are in git, last present in commit `fa6287b8` (`git show fa6287b8:docs/design/formal-correspondence-ledger.md`).

**Evidence categories.** *Production Lean*: a kernel theorem about the definitions of `lean/KatLang.lean`, with its production
instance discharged. *Conditional*: a kernel theorem whose named premises are not all discharged for production. *Reference
kernel*: a kernel theorem about `KatLangArityLaws/SignatureCompletion.lean`, a front-end model, not the evaluator and not C#.
*Guard*: an executable Lean check. *C# differential*: native code compared with Lean on a stated finite corpus. *C# test*:
native tests with no Lean counterpart. *Source*: inspection only. *Open*: well specified and unproved. § E-18 also uses
*Static model*: a kernel theorem, or a kernel-checked verdict, about `KatLangArityLaws/NavigationSourceDomain.lean`, a static
selection model of member exposure; like the reference kernel it is a model, not the evaluator and not C#.

**The boundary.** A Lean theorem is about Lean. Agreement with C# is finite executable evidence. There is NO machine-checked
bridge from any C# source to any Lean term in this repository: no extraction, no formal C# semantics, no translator. Every row
that reaches C# is therefore tested correspondence over a trusted boundary. Universal verification of the C# compiler and
runtime is not established and is not claimed by anything here.

**FD-F1: the by-shape supply (settled by the language rule).** At the reference to `Get` in `Use` (line 2, level 2 of
`spec/forwarding-single-collector-by-shape`), the callee requests `xs`. C# supplies `.ownParameter "items"` and emits
`Get([items*])`; both evaluators return `2` on that tree. This is the language's rule, not a disagreement about behavior:
`lean/KatLang.lean` § Implicit argument resolution states that a bare helper reference whose helper's one group holds a lone
collector uses "a containing algorithm's single top-level variadic supply by shape rather than by capture-name equality",
`AGENTS.md` and `language-rules/ownership-and-lookup.md` state the same for formulas, the canonical spec case is hand-written,
and the reference kernel models the premise (`canForwardStream`). What has no by-shape arm is the specification FUNCTION:
`forwardingSource` decides by name from the owner chain alone, so `forwardingSource chain false "xs"` is `.unavailable`.
Each by-shape occurrence therefore carries two guards — the read C# emitted, `forwardingSource chain false "items" ==
.ownParameter`, and the function's by-name answer for the callee's name — and `ByShapeSupplies_AreExactlyTheReviewedOccurrences`
pins every occurrence. The witnesses add the sequence group `Sum((*xs))`, the alpha-rename and the declaration-reorder (seven
occurrences in all), and `by-shape-supply-under-one-name`, where caller and callee spell the collector alike and the two
rules give one answer. Whether Lean should gain a by-shape specification function is an owner decision.

```katlang
Get([*xs]) = xs.count
Use(*items) = [Get][0]
Use(3, 4)
```
