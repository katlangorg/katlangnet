# Testing and validation

The complete test-writing rules and the local validation procedure of this repository. `AGENTS.md` (§ Testing and § Validation) states the rules every agent applies on every task and points here for the procedure, the commands and the tables. The two must agree: change them together.

## Writing tests

- Prefer minimal, semantics-preserving, reviewable changes.
- Add or update focused tests near the changed layer.
- Include negative coverage when failure modes are meaningful.
- Test design, adversarial coverage, failure analysis, and validation execution all belong to the primary agent; a subagent is for a bulky self-contained investigation only, never for running tests (see § Validation).
- If a change crosses parser, evaluator, semantics, or docs boundaries, cover the affected layers in the same task when feasible.
- **A source-based evaluator test must PARSE CLEANLY, and must assert the error TYPE, not merely that something failed.** `Parser.Parse(source).Root` silently discards diagnostics, so a test whose source the parser rejects still evaluates the recovery tree and can pass for an unrelated reason — that is how a `NotPublicProperty` regression passed without ever reaching the branch, and how 41 `EvaluatorTests` came to run on illegal source. Use `SourceProvenance.ParseValid(...)` (or `EvaluatorTestSupport.ParseValidRoot`) for ordinary source semantics; `SourceProvenance.ExpectFrontEndError(...)` when the parser/elaborator is the subject; `SourceProvenance.ParseAllowingDiagnostics(...)` only where malformed source is the point (recovery, fuzz, editor tooling). Never assert an evaluator outcome on a source you have not shown to be legal.
- **A strict allocation assertion (exactly zero bytes, an exact count, or two equal counts) is a `*_GcIsolatedChild` test** (`dotnet/tests/KatLang.Tests/Infrastructure/GcIsolatedAllocation.cs`): during a background GC, `GC.GetAllocatedBytesForCurrentThread` can report up to one allocation quantum (~8 KB) for an allocation-free window (dotnet/runtime#134724). Such tests therefore run in one child test host per assembly with `DOTNET_gcConcurrent=0`, and the pinned `GcIsolatedAllocationTests` (core) and `CliGcIsolatedAllocationTests` inventories require each to complete there. Coarse bounds and ratios stay in-process; warm up before the window and keep assertions outside it. A gen-2 collection under high memory pressure can trim `ArrayPool`, including during a blocking collection in the child. A later rent in the measured window can then allocate a replacement buffer. Long strings and large number formatting can need substantial refills (32,832 bytes for a 6,178-character number). Allow for one refill of the workload and, for in-process bounds, the ~8 KB counter quantum. Document the arithmetic when sizing the bound.
- **Before writing a source test for an evaluator branch, check the branch is surface-reachable at all.** Front-end elaboration can make it dead: clause-family elaboration turns every single-clause binder form into an `Algorithm.User`, so the flat-binder arm of `ConditionalValueAccessError` cannot be reached from any written program, and implicit-parameter promotion hides the dotted-`open` visibility checks. A source test for such a branch passes while the branch stays dead — pin these from a prebuilt AST instead (`EvaluatorDefensiveBranchTests`).

## Validation

Local test execution is OPT-IN. After implementation, review the diff and whitespace, but do not automatically run tests, probe executables, `validate-all.ps1`, `check-cancellation-token-order.ps1`, regeneration tests, or Lean builds that execute semantic guards. Run local tests only when the user explicitly requests them; an implementation or fix request alone is not such a request. Build-only compilation is allowed. Report tests as not run locally rather than implying that CI passed or asking for permission to run them.

`.github/workflows/validate.yml` is the default .NET + Lean validation path for pull requests and pushes to `main`; its .NET job runs the fast test tier, the slow tier runs nightly, and a release runs both (Test tiers below). When local validation IS requested, scope follows REGRESSION RISK, never line count, file count, or file extension alone. The alignment manifest and language rules decide which semantic edits a change needs; the levels below select the requested local checks. They do not authorize automatic test execution.

### Candidate and level

- Assess the COMPLETE candidate: the relevant commits plus staged, unstaged, untracked, deleted, and renamed files. A clean working tree is not evidence that a committed candidate needs no tests. Preserve unrelated work and account for it when it affects the candidate or the test results.
- Classify by semantic impact, dependency reach, and changed contracts. Start at V1 unless the change is clearly V0, then apply the V2/V3 triggers; when the impact cannot be confidently bounded, choose V3. Record the level and a one-line reason before validation starts; the level may be raised on evidence, never lowered. The level is also the execution plan: V0–V2 run only what their row names, and the `validate-all.ps1` phases belong to V3 alone — if the candidate warrants a phase, record V3; running one at V1/V2 is a misclassification, not extra diligence.

| Level | Appropriate scope | Scope when local validation is requested |
| --- | --- | --- |
| V0 — trivial | Instruction/prose edits, comments, or formatting proven not to affect execution or mechanically checked content | Review the diff, whitespace (`git diff --check`), and the references/consistency of the text. No build or runtime suite for a genuinely documentation-only change. |
| V1 — focused | Small, isolated, behavior-preserving refactor or test change with a well-understood dependency boundary | Build the affected project/test dependency closure; run the directly related tests with verified filters. |
| V2 — affected | Bounded subsystem behavior change; a limited shared helper, API, or diagnostic contract change; neighboring consumers affected | Focused tests plus the neighboring/affected suites, the affected project builds, and the applicable parity/artifact/Lean checks — never the full solution suite or a `validate-all.ps1` phase. |
| V3 — full | Fundamental behavior, broadly shared infrastructure, cross-cutting changes, or uncertain impact | One fast-tier .NET phase, one class-filtered run of the slow tests of every touched area (Test tiers below), and all seven canonical Lean targets once. Regression and mode-parity tests run within that suite, without a second full-suite pass. |

When local validation is requested, V3 is the required scope for changes to parser/grammar behavior or AST structure; elaboration; lexical ownership/name resolution; parameter binding or implicit lifting; Grace; sequence/list/spread/collect/arity semantics; the evaluator core; the optimizer/planned execution; sync/async/cancellation behavior; core loading/module semantics; caching/exposure; Decimal128/numeric semantics; Lean/C# correspondence; and widely reused infrastructure or build/toolchain changes with broad impact. The triggers concern the behavior or machinery changed: a comment fix inside `Parser.cs` is not V3, a one-line ownership fix is; a formatting-only string-construction refactor may be V1 when the output contract is demonstrably unchanged; updating expected semantic results never makes a semantic change test-only. V2 covers bounded production-behavior changes, shared consumers, and API/diagnostic contracts without a V3 trigger — an isolated CLI presentation change needs no evaluator-wide validation, a change to shared loading or cancellation does. Executable documentation is not prose: tutorial result claims, spec-linked examples, generated prompt blocks, and the EBNF keep their verification tests (coverage map below) even when only text files changed, so such a change is neither automatically V0 nor V3; changed language MEANING is still V3 plus the semantic-update process.

### Lean validation

- V3 always runs all seven Lean targets, even when no `.lean` file changed — a C#-only optimizer, async, or ownership change is V3, and `SemanticExplorerCases`/`LanguageSpecCases` are how Lean/C# correspondence is checked.
- V1/V2: build the affected Lean targets and the dependent artifact/parity checks whenever Lean code, proofs, guards, imports, or generated Lean content changes or is affected; a meaningful Lean-only change never gets zero Lean validation, and unclear dependency reach means V3. Pure Lean comments may be V0; regenerating an artifact without a content change is not itself a semantic change.

### Commands

The command that runs both phases, from the repo root (V3 adds the class-filtered slow run of the touched areas between the .NET and the Lean phase; § Test tiers):

```powershell
pwsh -NoProfile -File ./scripts/validate-all.ps1 -Phase All
```

The .NET phase builds [the full solution](../dotnet/KatLang.slnx), including the benchmark and demo projects. It then runs the selected test tier with `--no-build` and finishes with `git diff --check`. The [standalone build script](../scripts/build-standalone-tools.ps1) compiles the fuzz harness separately. The Lean phase builds the seven targets listed below.

`-Phase` accepts only `All` (the default), `DotNet`, and `Lean`, and the .NET phase takes one `-Tier`: `Fast` (the default), `Slow`, or `Full` (Test tiers below); the script has no focused or level switch and does not detect risk. Completing `-Phase DotNet` and then `-Phase Lean`, one after the other, against the same unchanged candidate satisfies V3 together with the touched areas' slow tests — do not rerun `All` merely to repeat completed work, and never run the two phases side by side — while a partial phase alone is never full validation. A phase already runs every focused suite of its tier, so it is never preceded, accompanied, or followed by a separate filtered pass over the same candidate, except the one class-filtered run of the touched areas' slow tests that V3 adds. Each phase fingerprints the staged, unstaged, and untracked state and fails if validation changes it; a checkout may start dirty, but validation must leave it exactly as it started.

SINGLE-PASS VALIDATION: run the ordinary .NET suite once per unchanged candidate. Do not launch a second whole-suite forced invocation-plan run, even for META/need-binding changes. Dedicated tests compare ordinary and planned routes through the per-run `InvocationPlanTestSeam`; keep their value/effect/charge/diagnostic assertions. The script removes an inherited `KATLANG_FORCE_INVOCATION_PLANS` flag so it cannot silently change the normal run.

NO LOCAL NORMAL-RUN DEADLINE: let local builds, tests and probe children finish. Do not wrap validation in a 900-second/15-minute supervisor, kill it because elapsed time increased, or restart it as batches after a timeout. Report progress without terminating or duplicating the run. Keep explicit user cancellation and tests that intentionally exercise cancellation/deadlock behavior distinct from a suite/probe deadline. Historical B3 bounded-run approvals document past evidence only; they are not the current validation procedure. GitHub Actions validation jobs deliberately use 60 minutes for .NET and 40 minutes for Lean in both validation and release workflows. These CI limits do not impose a local suite or probe deadline.

Manual .NET fallback (equivalent to the fast-tier phase, including the independent full-solution build; `--filter "Tier=Slow"` gives the slow tier and no filter the full tier):

```powershell
dotnet build .\dotnet\KatLang.slnx -p:UseSharedCompilation=false
dotnet test .\dotnet\KatLang.slnx -p:UseSharedCompilation=false --no-build --filter "Tier!=Slow"
git diff --check
```

Manual Lean fallback (all seven targets, as V3 runs them; a V1/V2 change that affects Lean builds only the affected targets and their dependent checks, § Lean validation):

```powershell
Push-Location .\lean
lake build CoreTests
lake build KatLangArityLaws
lake build AstDemo
lake build CoreArityAlgebra
lake build CoreArityAlgebraProofs
lake build SemanticExplorerCases
lake build LanguageSpecCases
Pop-Location
```

Lean CoreTests use `#guard` for semantic assertions, so a failing assertion fails `lake build CoreTests`. Remaining `#eval` lines are demo/inspection output only.

Focused V1/V2 runs build the affected projects, then filter, for example:

```powershell
dotnet build ./dotnet/tests/KatLang.Tests/KatLang.Tests.csproj -p:UseSharedCompilation=false
dotnet test ./dotnet/tests/KatLang.Tests/KatLang.Tests.csproj -p:UseSharedCompilation=false --no-build --filter "FullyQualifiedName~SameLineSeparatorTests"
```

Filters must name real test classes/namespaces (check the inventory: the class in `LanguageSpec/GeneratorSpecTests.cs` is `LanguageSpecArtifactsGeneratorPromptTests`), and the summary must show the intended tests discovered AND executed — zero matching tests is not a pass whatever the exit code. Use `--no-build` only after a successful, current build of the same projects/configuration/framework and inputs. Verification outside the script keeps its guarantees: neutralize inherited `KATLANG_REGENERATE_*` flags for the verification process only (a child `pwsh -NoProfile` whose environment is discarded, never the caller's lasting environment), snapshot `git status --porcelain=v1 --untracked-files=all` plus the index and worktree diffs before and after, and report an unexpected mutation with its evidence instead of undoing it. Keep terminal output minimal; save complete stdout/stderr under the ignored `artifacts/validation/` directory or a temporary directory, preserving the command's real exit code when redirecting or piping (`$LASTEXITCODE` after the native command in pwsh, `pipefail`/`PIPESTATUS` in bash). Missing required tooling (SDK, `lake`, a runner) is BLOCKED/incomplete validation, never a pass and never a silently lower level.

### Test tiers

The .NET suite has two tiers (owner decisions 6 and 7, 2026-11-20). A test tagged `[Trait("Tier", "Slow")]` is in the SLOW tier, which runs nightly (`.github/workflows/slow-tier-nightly.yml`) and before every release; every other test is in the FAST tier, which `validate.yml` runs on every pull request and push. `validate-all.ps1 -Tier Fast` (the default) runs `--filter "Tier!=Slow"`, `-Tier Slow` runs `--filter "Tier=Slow"`, and `-Tier Full` runs every test; the record names the tier, its filter and the executed count, and a tier that executes nothing fails the phase.

- `SlowTierInventoryTests` pins every Slow test with its category, its reason and its per-pull-request slice, so adding or removing a tag updates that inventory in the same diff. A slice is a separate, untagged test in the same class whose cases are a strict subset of the slow test's; a theory slice repeats rows of its slow theory. Tags go on test methods only, never on a class or a shared base class. Only harness self-checks, Debug copies of stress probes whose Release copy runs in the stack-suite job, exhaustive scans, full-size stack or memory checks, old-versus-new algorithm checks and further corpus variants may move, and a test that is the only per-pull-request coverage of a rule stays.
- Local V3 (decision 7(a)): the fast-tier `-Phase DotNet`, then ONE class-filtered run of the slow tests of every area the candidate touches (the slow-tier bullet of the coverage map in `AGENTS.md` § Validation names them; for example `--filter "Tier=Slow&(FullyQualifiedName~KatLang.Tests.StrategyNeutralBudgetParityTests.|FullyQualifiedName~KatLang.Tests.Q09IndependentHostileReviewTests.)"`), then `-Phase Lean`. The slow tier runs nightly and the full tier before every release; run the full tier locally when a change concerns the tiers themselves.
- A change to the tiers proves itself: a fast run plus a slow run equals one full run, test name for test name, and every slice is a strict subset of its slow test.

### Regenerating generated artifacts

Generated artifacts are never edited by hand and never rewritten by a verification run. For a test-generated artifact, regeneration is one deliberate, targeted `dotnet test` run with the artifact's flag set to `1`: the run WRITES the artifact and then FAILS BY DESIGN (also when nothing changed), so it can never pass as verification — review the diff, clear the flag, and run the normal verification at the level the underlying change requires (an intentional language-behavior change is V3).

### Execution discipline

Validation is executed by the primary agent, in ONE execution stream: never two of `dotnet build`, `dotnet test`, `lake build`, a `validate-all.ps1` phase, or a regeneration run in flight at once — concurrent `dotnet test` invocations lock `KatLang.Tests.dll` (MSB3027), a phase fingerprints the tree while it runs, and a second run of the same suite over an unchanged candidate is pure duplication. Every command's full output goes to a log file (the ignored `artifacts/validation/` directory or a temporary directory) and only its summary lines — result totals, failure identities, exit code — are read back, never the whole log.

- ONE plan per candidate, chosen before anything runs: at V1/V2 the focused and affected suites, most informative first, and nothing beyond them; at V3 the phases and the touched areas' slow tests only. When explicitly requested, development checks while editing stay minimal — the test class being written, `scripts/check-cancellation-token-order.ps1` after a signature change (`AGENTS.md` § C# implementation rules), the one previously failing check after a repair, the Lean target that compiles the edited file, a regeneration run — because the plan runs everything else exactly once; a pre-validation sweep of neighboring suites runs every test twice.
- One command at a time, waited to completion: a `--no-build` run only after the build's exit code is in hand, `lake build` never beside a `dotnet` command, the .NET phase and then the Lean phase, never side by side. A requested `validate-all.ps1` phase may outlive a tool response window; wait for the same process to complete without an execution deadline or a restart. Do not edit the checkout while it runs. Read only bounded progress output when needed.
- On a failure, capture the command, the failure identity, and the evidence; decide what it means; repair; rerun only the failing check; then complete the plan for the FINAL candidate. Reuse earlier results only while their inputs, dependencies, configuration, and environment still apply (later prose-only edits do not by themselves invalidate runtime results). When a failure suggests wider regression, or the diff reveals a V3 trigger the classification missed, raise the scope one level at a time — never as a precaution — and a full phase replaces the remaining focused plan instead of adding to it. Do not rerun an unchanged failure repeatedly, and do not launch every suite to diagnose a missing SDK.
- Never claim validation from a partial run, a stale build, an unexecuted command, a zero-test filter, or an assumption that CI will pass, and do not label a failure pre-existing or flaky without evidence. Report what ran, the counts, the failures, what was omitted and why, and the log paths.

### Subagents

Do not delegate test execution. Measured in September 2026, a validation worker spent 30–50 requests to run two or three commands — about ten times the cost of running them inline — could not work in parallel with a tree that must stay frozen, and shared no prompt cache with the primary agent (caches are model-scoped and prefix-exact). A subagent is for a BULKY, SELF-CONTAINED INVESTIGATION whose intermediate reading would otherwise flood the primary context — a failure hunt across many files, an inventory, a cross-file audit. Give it the cheapest model that can do the job, a bounded brief with an explicit stopping point, and ask for `file:line` facts; code the primary agent will edit or reason about it reads itself, in bounded ranges. Never spawn one for a single known file, and never let one edit, regenerate, or validate.
