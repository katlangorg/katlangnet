# KatLang C# Benchmarks

This folder holds KatLang C# performance scenarios for evaluator cache and optimizer comparisons. The benchmark set is intentionally small and deterministic so later evaluator changes can be compared without changing language semantics.

## Run

```powershell
dotnet run -c Release --project benchmarks/KatLang.Benchmarks/KatLang.Benchmarks.csproj
```

Useful filters:

```powershell
dotnet run -c Release --project benchmarks/KatLang.Benchmarks/KatLang.Benchmarks.csproj -- --filter *ParseAndEvaluate*
dotnet run -c Release --project benchmarks/KatLang.Benchmarks/KatLang.Benchmarks.csproj -- --filter *PreparedEvaluation*
dotnet run -c Release --project benchmarks/KatLang.Benchmarks/KatLang.Benchmarks.csproj -- --filter *GcdWhileLoop*
dotnet run -c Release --project benchmarks/KatLang.Benchmarks/KatLang.Benchmarks.csproj -- --filter *LoopStage2*
dotnet run -c Release --project benchmarks/KatLang.Benchmarks/KatLang.Benchmarks.csproj -- --filter *SequencePipelineStage2*
dotnet run -c Release --project benchmarks/KatLang.Benchmarks/KatLang.Benchmarks.csproj -- --filter *SequencePipelineDispatch*
dotnet run -c Release --project benchmarks/KatLang.Benchmarks/KatLang.Benchmarks.csproj -- --filter *SequencePipelineLargeList* *SequencePipelineRepeated*
dotnet run -c Release --project benchmarks/KatLang.Benchmarks/KatLang.Benchmarks.csproj -- --filter *SequenceBuiltinLargeList*
dotnet run -c Release --project benchmarks/KatLang.Benchmarks/KatLang.Benchmarks.csproj -- --filter *PerSitePlanRetention*
dotnet run -c Release --project benchmarks/KatLang.Benchmarks/KatLang.Benchmarks.csproj -- --filter *OutputFormattingBenchmarks*
dotnet run -c Release --project benchmarks/KatLang.Benchmarks/KatLang.Benchmarks.csproj -- --filter *SemanticQueryBenchmarks*
dotnet run -c Release --project benchmarks/KatLang.Benchmarks/KatLang.Benchmarks.csproj -- --loop-stats
dotnet run -c Release --project benchmarks/KatLang.Benchmarks/KatLang.Benchmarks.csproj -- --sequence-stats
```

The run is unambiguous from the main checkout even when git-ignored copies of `KatLang.Benchmarks.csproj` exist (under `artifacts/`, `.claude/worktrees/`, or a scratch export). BenchmarkDotNet 0.14.0 would otherwise search the whole repository for a project of that name and report every benchmark as `NA` ("Found more than one matching project file"). The build records its own project path in the assembly, and `PinnedProjectToolchain` makes every job — `[SimpleJob]` attributes and command-line jobs such as `--job dry` alike — build exactly that project; the summary's job names show `Toolchain=CsProj (pinned project)`. Do not delete other people's scratch copies or worktrees to work around a benchmark run. The pinned toolchain targets `net11.0` only, so `--runtimes` is not supported.

Compare timings only against a same-build control — a control workload or mode measured in the same build and run (for example each `PerSitePlanRetention` workload against its loop-free control); across a code change compare those same-build ratios, never raw timings: timings can move 7–15% between builds with byte-identical allocation (JIT/layout effects).

BenchmarkDotNet writes summaries under `BenchmarkDotNet.Artifacts/results/`.

## Exit Code

BenchmarkDotNet never fails the process itself: a benchmark whose build fails or that throws becomes an `NA` row, and a rejected configuration returns no summary at all. The host sets the exit code instead, and prints one line `KatLang.Benchmarks: <reason> Exit code <n>.` whenever it has something to report (on the error stream when the code is nonzero).

| Exit code | Meaning |
| --- | --- |
| `0` | At least one benchmark case produced a successful report, or nothing was asked to run: `--help`, `--version`, `--info`, `--list`, and the diagnostic runners (`--cache-stats`, `--loop-stats`, `--sequence-stats`, `--async-stack-capacity`). |
| `1` | Benchmarks were selected but none produced a successful report (every row is `NA`, for example after a build failure or when every benchmark throws), or BenchmarkDotNet reported a critical validation error. |
| `2` | A run was requested and nothing ran: the filter matched nothing, nothing was selected at the interactive prompt (for example no `--filter` and no console input), or BenchmarkDotNet rejected the arguments. |

A successful report is a case whose build and every launch succeeded and that holds a result measurement. Exit code 0 means "at least one result", not "every result": when only some cases fail, the host still exits 0 and prints `warning: N of M benchmark case(s) produced no successful report (NA).`, so read the summary before citing a number. Never treat an `NA` row as data. Read the exit code of the benchmark process itself (`$LASTEXITCODE` after `dotnet run` in PowerShell, `$?` or `PIPESTATUS` in bash), not that of a pipeline it feeds. The decision is the pure function `BenchmarkHostExit.Decide`, pinned by `BenchmarkHostExitTests` in `dotnet/tests/KatLang.Tests`.

Informational requests in BenchmarkDotNet response files (`@path/to/options.rsp`) follow the same exit-code rules as direct arguments, including `--help` and `--version`. A missing response file or rejected arguments still exit 2.

Any other exit code is a crash, not a result: an exception that escapes BenchmarkDotNet ends the process with the runtime's unhandled-exception code (`0xE0434352` on Windows, which Git Bash reports as 127). One case is known in BenchmarkDotNet 0.14.0: adding `--job dry` to a run of `PerSitePlanRetentionBenchmarks` throws `ArgumentException: values can't be empty` from the rank column while the summary table is built, after the benchmarks themselves ran. The other six classes with `[RankColumn]` were not tried and are expected to fail the same way. Run such a class with its own job (omit `--job`). `SequencePipelineLargeListBenchmarks`, `SequencePipelineRepeatedBenchmarks` and `SequenceBuiltinLargeListBenchmarks` have no rank column, so they also run under `--job dry`.

## What Is Measured

- `ParseAndEvaluateBenchmarks` measures `KatLangEngine.EvaluateToAtoms(source)`, so parse, front-end elaboration, and evaluation are all included.
- `PreparedEvaluationBenchmarks` parses and elaborates each checked-in scenario once outside the timed benchmark and then measures `Evaluator.RunFlat(new Expr.AlgorithmExpr(root))`.
- The baseline method in each class is `RepeatedZeroArgPropertyReuse`, so BenchmarkDotNet's ratio columns compare the other scenarios against that same repeated zero-arg property reuse scenario for each benchmark mode.
- `LoopMode=Generic` disables the internal optimized loop path; `LoopMode=Optimized` enables it. This makes loop-heavy scenarios compare before/after behavior without changing KatLang source semantics.
- `SequencePipelineMode=Generic` disables sequence filter-count fusion; `SequencePipelineMode=Optimized` enables Stage S2 direct range iteration while keeping loop optimization enabled in the sequence pipeline benchmarks.
- `SequencePipelineLargeListBenchmarks` and `SequencePipelineRepeatedBenchmarks` (2026-11-16) compare filter→count fusion ON (`Optimized`) and OFF (`Generic`) on prepared roots with the loop optimizer on, where the generic composition builds lists of 100,000 items: one `count(filter(range(1, 100000), Pos))` with the cheap predicate `Pos(n) = n > 0` (16 operations per iteration), the 2026-11-14 audit program `map(range(1, 20), K).sum` with 20 such pipelines, and, as the short-range control, 2,000 pipelines of 1,000 items with the same 2,000,000 predicate calls (one operation per iteration). Read the `Gen1`/`Gen2` columns beside the time: the generic path's lists of that size and the survival of their items cost collections that the fused path does not have, and the gain is GC-driven. Each method runs its two modes back to back, `Generic` first; set `KATLANG_BENCH_SEQUENCE_MODE_ORDER=OptimizedFirst` for the opposite order, and alternate the two orders across runs (ABBA). Check with `--sequence-stats` that `Optimized` fuses every pipeline and `Generic` none. `PropertyFilterCount100k` (2026-11-18) is the same 100,000-item pipeline over a property source, `R.filter(Pos).count` with `R = range(1, 100000)`: it is no written range, so `Optimized` fuses it through the dot-receiver adapter (`--sequence-stats` reports a direct-range fallback, "source is not builtin range"). Filter: `--filter *SequencePipelineLargeList* *SequencePipelineRepeated*`.
- `SequenceBuiltinLargeListBenchmarks` (2026-11-17) measures the generic collection builtins over a 100,000-item `range`, one method each: `take`, `skip` (50,000 items kept), `distinct`, `order`, `orderDesc`, `sum`, `avg`, `min`, `max`, and `range(1, 100000).map(Inc).sum`. None of them is fused, so the production configuration is measured without a mode parameter. Every run also builds its source range (about 4 MB of list slots and numbers), so compare each method's `Allocated` column with the `RangeCount100k` control, which only builds and counts that source. The list builders allocate their exact result array once and hand it over, and the numeric builtins read the numbers through a view of the validated items, so `sum`, `avg`, `min` and `max` allocate no more than the control. Compare a method's time with `RangeCount100k` in the SAME build, not with an older build: measured on 2026-11-17 (four alternating runs), removing the numeric builtins' 1.6 MB `List<Decimal128>` per run made `sum`/`avg`/`min`/`max` 24–35% slower in mean time, although the builtins' own work became faster (a direct 100,000-item `sum` call went from 2.2 to 1.7 ms) and they run 250 fewer Gen2 collections per 1,000 operations. The old list's large-object garbage set a GC rhythm that made the source range cheaper to build: the old `Sum100k` ran 0.5 ms below its own `RangeCount100k` control, and adding a dummy 1.6 MB large-object allocation per run to the control made the control itself about 15% faster. `Atoms100k` and `RetainedTake100k` (2026-11-18) add `range(1, 100000).atoms.count` and a 50,000-item `take` of a retained collector holding 100,000 cells (`Prefix(*xs) = take(xs, 50000).count` applied to `range(1, 100000)*`, NEED-07). Since 2026-11-21 `order` and `orderDesc` sort dense whole numbers (every value a whole number in `int` range, spanning no more integers than there are items) with a counting sort, so `Order100k` and `OrderDesc100k` measure that path; `OrderFraction100k` (`range(100000, 1).map(Eighth).order.first` with `Eighth(n) = n / 8`) exercises the comparison sort on fractional inputs. `MapSum100k` also maps 100,000 items, using an ascending range and the `Inc` callback. Filter: `--filter *SequenceBuiltinLargeList*`.
- `SequencePipelineDispatchBenchmarks` measures the sequence-pipeline PROBE cost on calls and dot-calls that are never candidates (M15): `Optimized` is the fusion-enabled recognition-miss path, `Generic` is the fusion-disabled bail path, and the generic loop strategy is pinned so every iteration crosses the expression dispatch that hosts the probe. Allocated bytes/op is the primary metric.
- `PerSitePlanRetentionBenchmarks` measures J7 per-site plan retention (2026-11-09) on prepared roots with both optimizations enabled: the S1 workload `Id(count(filter(range(1, 20000), IsEven)))` in a loop-only program (an added `Unused(s) = s.while`) against the same program without the loop (the loop-free control, which never retains plans), and the P1 loop `S(x) = Id(Id(Id(x + 1))), x < 1000` / `S(0).while` against a loop-free control making the same nested calls once per item of a 1000-item `map`. Before per-site retention the S1 loop program planned the supplied pipeline and ran it generically, and the P1 loop formed 2001 plans; now the first fuses like its control and the second forms one plan. Time and allocated bytes/op are the metrics; compare each workload with its control. Filter: `--filter *PerSitePlanRetention*`.
- The same class measures builtin-aware transport (0eed993a, 2026-11-10) with two more pairs. `IfCalleeLoop1000` calls `F(x) = if(x > 0, x, 0)` with the supplied `G(n)` once per transition of a 1000-transition loop, and `CountCalleeLoop1000` calls `F(xs) = count(xs)` with the supplied `range(1, 3)`. The callee hands its parameter only to a value-only builtin, so the supplied call is not a plan and the run forms one plan, the loop step. Each stands beside a planned baseline, `IfCalleePlannedBaseline1000` / `CountCalleePlannedBaseline1000`: the same program plus an unread local property `Keep = Pass(x)` in `F`. That property transports the parameter to a user callable, so the supplied call stays a plan (1001 plans per run), and because it is never read, the evaluation steps and checkpoints are identical. Compare each workload with its planned baseline, not with a loop-free control: the difference is the cost of the retained plans. A baseline that reaches the builtin through an alias (`Choose = if`) also keeps the plan but allocates about 400 B more per call for reasons unrelated to plan retention, so it is not used. Measured once at dbd2e8fd (2026-11-11, the class's own short job): 4.90 MB against 5.12 MB per run for `if` (230,592 B, 232 B per retained plan) and 4.80 MB against 4.91 MB for `count` (119,880 B, 120 B per retained plan). The mean times of each pair differed by 2–3% in the baseline's favour, inside the build-to-build noise described above, so that run shows the gain in allocation only.
- `EvaluatorIdentityStateBenchmarks` measures the evaluator's declaration / activation / scope-owner bookkeeping (invalid-state audit §3.1, September 2026) on twelve prepared shapes — a parameterized call, three nested calls, an exported property cache hit, a local-only property read, `M.A`, a captured-ancestor read from a nested call, recursion to depth 40, a clause-family call, a recursive clause family (`Fib(15)`, the run-local family-preparation memo's hot path), a two-parameter call (`Add(a, b) = a + b`, the binder's flat unique-name path), a user call whose body is one builtin call (`Abs(x) = if(x < 0, -x, x)`, the builtin argument supply), and a callback shape (`range(1, 201).map(Inc)`, one callback invocation per item) — with per-run time, allocated bytes, and Gen0 pressure; divide by `UnitsPerRun` for per-operation numbers (201 normally, including the two-parameter, builtin-call and callback shapes; 804 calls for the nested shape, 41 calls for recursion, 1,973 family calls for the recursive family). Sources live in `EvaluatorIdentityStateScenarios` (the same class a paired Stopwatch harness can compile in). Filter: `--filter *EvaluatorIdentityState*`. `ParameterActivationCaptureBenchmarks` separately checks narrow-to-wide signature scaling (`--filter *ParameterActivationCapture*`); the wide path must deduplicate in linear time.
- `OutputFormattingBenchmarks` measures `OutputFormatter.Format` on values evaluated once in setup. `FlatList` holds 20,000 integers. `NestedLists` holds 4,000 three-level lists, and `SmallNested` uses the first three as a one-line control. `Numbers64` and `Numbers65` each hold 2,000 numbers. Their canonical texts (`1e63` and `1e64`) fall on either side of the renderer’s 64-code-unit stack buffer. Setup checks the list result, the boundary lengths, and each formatter’s display limit. Run `--filter *OutputFormattingBenchmarks*` for all modes, or `--filter *OutputFormattingBenchmarks*Numbers64*` for one value.
  - On Windows x64 at `54f62307`, `NestedLists` allocated about 2.77 MB per call under `readable` and `concise`, and 1.00 MB under `exact`. Writing inline items from their measured text and sharing a traversal stack brought the layouts to 1.06 MB. The longer layout output accounts for about 56 KB of the remaining difference on CRLF. Width-only lookahead counts characters without copying them.
  - In the November 21 comparison, `SmallNested` fell from 1,512 B to 1,312 B under both layouts. Flat and boundary layouts allocated about 260 B more per rendering for the width probe at the root. Use each run’s `exact` result as the timing control.
  - On November 22 (against `81564d8c`), a layout measurement that does not fit keeps its walk, so a nested value’s leading text is no longer measured again at every level. Before, at zero indentation, 20,000 nested lists under a 10,000-unit line took about 3 s, and now take about 50 ms. The layouts allocate 112 B more for `SmallNested` (1,424 B), 416 B more for `NestedLists`, and 264–290 B more for the flat and boundary values. Over three alternating rounds `NestedLists` stayed within 2% of the baseline, beside an unchanged `exact` control. These benchmarks keep the default indentation, so the deterministic growth checks are in `LayoutMeasurementReuseTests`.
- `SemanticQueryBenchmarks` (2026-11-18; name-query shapes and index build 2026-11-20) measures the editor semantic model on generated documents of 129, 1,281 and 12,801 lines (`Size` = `small`, `medium`, `large`; `SemanticQueryScenarios` repeats one block with a library, aliases, an opening body, a clause family, an implicit-parameter formula, nested bodies and a callback row): `Parse` (`Parser.Parse`), `Build` (`SemanticModelBuilder.Build` of the parsed document), and query kinds as fixed batches reported per query (`OperationsPerInvoke`): `Hover` (`FindPropertyAt` plus the display signature) and `Definition` (`FindResolutionAt`) at 4,096 identifier sites, `Completion` (`GetVisibleSymbolsAt`) at 256, and 64 name queries, each `FindResolutions` plus `FindDeclarations` of one name. `Names` queries declared names spread over the document. By result shape, `NamesEmpty` queries absent names, `NamesSparse` names declared once with at most four sites, `NamesDuplicate` the names every block declares again (their results grow with the document), and `NamesDense` the name `v`, 7 of every 8 sites of `SemanticQueryScenarios.DenseSource`, a document of the same length. Hover and definition binary-search the identifier sites, and completion binary-searches the scope regions. The name queries read a name index that the model builds on their first call. `Rewrap` puts the built model's parts in a new model, which has no name index, and `RewrapAndIndex` adds the first name queries. The difference estimates the cost of building both indexes. Each retains one 8-byte key per named item, plus fixed object and array overhead. On the 2026-11-20 `large` run, each query pair took 35 ns for `NamesEmpty`, 60 ns for `NamesSparse`, 2.3 µs for `NamesDuplicate`, and 0.24 ms for `NamesDense`. Dividing each time by `Rewrap` in the same build, the former filter took about 4,200, 2,000, 57 and 5 times as long, respectively. An empty pair went from 337 B to zero. A dense pair allocated about 819 KB in both builds. Building both indexes on the mixed document cost 1.7 ms and 288 KB, about twelve former empty query pairs and 2.2% of the 12.8 MB retained model. Each query builds its own listing’s index on first use. Filter: `--filter *SemanticQueryBenchmarks*`.

## Planned-loop numeric temporaries (KL-01)

The November 21, 2026 experiment compared eager boxing at `6e99edc9` with a prototype that kept arithmetic-only local temporaries unboxed. The prototype classified reads during plan preparation and stored one Boolean per temporary. Results below are for .NET 11 Release on Windows x64. Each case runs `repeat(Step(0, 0), N)` with `T = a + 1` where used. The three-temp case adds `U = T * 2` and `V = U - T`.

| Use and step output rows | Planned B/iteration, eager → prototype | Generic B/iteration, both builds | Steps/iteration | Expression checkpoints/iteration |
| --- | ---: | ---: | ---: | ---: |
| Arithmetic only • `T + 0, b + T` | 96 → 64 | 2,618.87 | 3 | 18 |
| Three arithmetic temps • `T + 0, b + V` | 160 → 64 | 4,625.23 | 6.01 | 30 |
| Inline control • `a + 1 + 0, b + (a + 1)` | 64 → 64 | 1,552.00 | 1 | 20 |
| Escaping • `T, T` | 32 → 32 | 2,282.87 | 3 | 8 |
| Mixed • `T, b + T` | 64 → 64 | 2,434.87 | 3 | 13 |
| Conditional • `if(T > 0, T, 0), b + T` | 88 → 88 | 4,201.23 | 4 | 20 |
| Equality • `T + 0, b + if(T == T, 1, 0)` | 120 → 120 | 4,385.23 | 4.01 | 25 |
| Independent equal results • `a + 1, a + 1` | 64 → 64 | 1,456.00 | 1 | 12 |

The harness parsed each program before measuring. It subtracted current-thread allocations for 1,000 iterations from allocations for 101,000, divided by 100,000 and took the median of five samples after two warmups per size. Separate observed runs verified the planned path, final values and work counters. Both strategies and builds agreed on values and charged the work shown. The `square-free-count-local-temp-loop` scenario allocated 228,099,656 bytes per run with eager boxing, 237,894,128 with a first prototype using a hash set, and 215,174,128 with the Boolean-array prototype.

For timing, each round used the median of 15 runs of 200,000 iterations. Dividing each planned time by the inline control in the same build and taking the median ratio across three rounds gave **1.00 → 1.06** for one arithmetic temp and **1.70 → 1.77** for three. With tiering disabled the ratios were **0.93 → 0.90** and **1.53 → 1.47**. The prototype saved 32 bytes per arithmetic-only temporary per iteration. The timing comparisons changed direction with tiering, so the planner keeps the single boxing rule for established results.

## Cache-Sensitive Notes

- The most cache-sensitive scenarios are `RepeatedZeroArgPropertyReuse`, `ScalarHelperSumCalls`, and `PropertyRichSharedSubcomputations` because they intentionally re-read the same zero-arg properties or call through helpers that close over them.
- `NestedPropertyChains` intentionally measures one-hop dot access. Multi-hop dot chains (`Lib.Sub.Q`, navigated structurally at every level) are legal KatLang; to measure them, add a new scenario instead of mutating this baseline.
- `SequenceHeavyBuiltins` is a useful control case: if it changes a lot without the property-heavy scenarios moving, the hotspot is more likely callback dispatch or sequence traversal than property reuse.
- `RealisticWhileCalculation` is the end-to-end sanity check. It mixes multiple evaluator features and is the best quick regression scan after any future performance work.
