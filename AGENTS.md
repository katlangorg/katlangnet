# KatLang Agent Instructions

## Project Overview

- These instructions are for Codex and other AI coding agents working in this repository.
- `AGENTS.md` is the canonical shared agent-instructions file for this repo.
- KatLang's authoritative language model is `lean/KatLang.lean`.
- The C# implementation in `src/KatLang/` must stay semantically aligned with Lean.
- If Lean and C# are both wrong for the same bug, fix both together when feasible.
- Keep this file operational and concise.

## Core Architecture

- `lean/KatLang.lean`: source of truth for AST shape, evaluation rules, and invariants.
- `lean/CoreTests.lean`, `lean/AstDemo.lean`: Lean-side regression and AST compatibility checks.
- `lean/CoreArityAlgebra.lean`, `lean/CoreArityAlgebraProofs.lean`, `lean/CoreArityAlgebra.md`: isolated paper-facing extraction of KatLang's arity algebra; it must stay faithful to `lean/KatLang.lean` but is not authoritative semantics.
- `src/KatLang/`: C# AST, parser, front-end elaboration, evaluator, diagnostics, and public API.
- `src/KatLang/Semantics/`: editor-facing semantic tooling only; it is not the evaluator and not the normative semantics layer.
- `tests/KatLang.Tests/`: parser, evaluator, elaboration, semantics, and integration regression coverage.
- `tutorial.md`, `KatLang.ebnf`, and generator prompt/agent files must stay aligned with real language behavior.
- `docs/design/language-rules/`: the full statement of every compact rule in this file (consequences, examples, implementation map, pinning tests), as binding as this file; its `README.md` says which file to read before touching which subsystem.

## Language Semantics And Design Rules

A bracketed pointer such as [`syntax.md` § The spread marker] names the section of `docs/design/language-rules/` that holds the full rule; read it before changing that rule's implementation, and change both together.

- Lean 4 wins over implementation convenience, performance, or stylistic preference.
- `lean/CoreArityAlgebra.lean` defines the algebra. `lean/CoreArityAlgebraProofs.lean` proves the small laws and executable checks. If either diverges from `lean/KatLang.lean`, fix the artifact or explicitly change the authoritative model first.
- If Lean is ambiguous for a requested behavior change, stop and clarify before implementing.
- Do not invent syntax or semantics that are not in Lean unless the task explicitly includes the Lean change.
- Do not add new operators, convenience syntax, implicit coercions, hidden fallbacks, or AST simplifications that erase Lean distinctions.
- Preserve structural distinctions in the AST and runtime model. In particular, `.dotCall` and `open` are language-level constructs, not incidental parser sugar.
- `Expr.SequenceConstruct` / `.sequenceConstruct` is an INTERNAL sequence-join node, not the AST representation of written parenthesized sequence values (those parse to `Expr.Capture` / `.capture` bundles; `()` to the empty-sequence node). Its evaluation drops `()` leaves, so routing surface syntax through it would violate visible-empty semantics — the parser must never produce it (guarded by `SequenceConstructContainmentTests`, CoreTests internal-node guards, and the semantic explorer's internal-node cases; see `docs/design/sequence-boundary-audit-2026-07.md` §7).
- Brace algorithms parse to `Expr.AlgorithmExpr` / `.algorithmExpr` (algorithm identity); a surviving parenthesized group parses to `Expr.Capture` / `.capture` over an `OutputBundle` — ordered written slots with NO lexical ownership, consumed by the receiver. Capture is not algorithm identity (`Apply((Increment))` errors, `(Obj).V` fails, `open (M)` is `BadOpenForm`), while every `AlgorithmExpr` provides its algorithm on the higher-order channel whatever its parameter count. `Expr.Call.Args` is an `OutputBundle` and `Expr.DotCall.Args` an optional one (`null` = property-style access), evaluated in the CALLER's context; there is no transparent Args algorithm and no `IsParametrized` mode bit — every `Algorithm.User` owns a scope (parser entry points `ParseScopedAlgorithm` / `ParseParenthesizedBodyParts`). Value-context lifting (`ProcessValueDemandingArgumentBundle`) is a consumer property: registry-strict Math positions lift, call arguments stay neutral, and a strict-value position blocked by a CLOSED parameter list is diagnosed (`ReportBlockedStrictValueForwarding`, blame from `MissingClosedListForwardingNames`). [`sequences-lists-and-calls.md` § Output bundles, capture, and algorithm identity]
- Strict-value diagnostic OBSERVATION is independent of rewrite memoization: a per-region reference-identity visit set lets a shared node reached neutral-first and strict-later report exactly once without changing the `(node, inCallPosition)` rewrite key or output sharing. Diagnostic presence and multiplicity must not depend on host-DAG traversal order.
- Algorithm output is written as expression rows: every non-definition expression row in an algorithm body contributes to that algorithm's output, and output rows may be interleaved with property definitions. There is no output keyword; `Output` and `output` are ordinary identifiers.
- Delimiter model: `(...)` groups sequences/expressions and delimits call arguments, `[...]` constructs lists, and only `{...}` (and the root) creates an algorithm-level scope: `open`, property/clause definitions, and deconstruction bindings are parser-rejected inside parentheses with a targeted diagnostic pointing at `{ ... }`, while brace blocks work in any expression position without leaking. Unmatched root `)` / `}` tokens recover in the same scope (later declarations retained, the parse stays erroneous), and recovery never consumes a closer an ENCLOSING construct is still waiting for (`Parser.IsOwedCloser`; every nested body loop ends at such a closer — `RootStrayCloserRecoveryTests`, including the exhaustive delimiter-soup sweep). An expression unwrapped from redundant grouping keeps the group's FULL extent as its `Span` (`Parser.WithGroupExtent`; `GroupedExpressionSpanTests`), and every unary operand rejection carries the unary expression's span from the ONE `Evaluator.ApplyUnaryOperator` (`UnaryBadAritySpanTests`). [`syntax.md` § Delimiters, grouping extent, and unary spans]
- BUILTIN CALLABLES ARE ORDINARY PRELUDE BINDINGS (SYN-05): resolution selects ONE identity without looking at the argument count, and that identity decides signature and behavior (`resolve → select ONE identity → assemble the ordinary supply → bind against THAT signature → invoke`); a nearer property or parameter named `if`, `count`, or `sum` shadows the prelude COMPLETELY, and NO layer branches on a callee's spelling — no reserved-name mechanism of any kind, no argument counting from a callee name in the parser (a wrong-arity builtin call is an evaluation-time `ArityMismatch`), and a recognizer may use spelling only as a registry-metadata key (`Evaluator.BuiltinDisplayName`) before confirming `Evaluator.ResolvesToBuiltinAlgorithm`; builtin `if`'s laziness belongs to the resolved builtin. Every builtin VALUE slot demands its selected argument through the ONE zero-argument value-demand law (`ZeroArgumentValueDemandRejection` / Lean `zeroArgumentDemandError?`; `SequenceBuiltinValueDemandError` for collection arguments and fixed controls): a parameterized algorithm is its ordinary arity rejection, a conditional `ConditionalValueAccessError`, a written block `UnresolvedImplicitParams`; unselected and callback slots are never demanded. (`load` alone is still recognized by spelling — deliberate.) `BuiltinCallableIdentityTests`, `LazySlotZeroArgumentDemandTests`, `CoreTests/NameOwnership.lean`, `CoreTests/ValueDemand.lean`. [`ownership-and-lookup.md` § Builtin identity and the zero-argument value demand]
- Ownership-first lookup must agree across the evaluator, elaboration, parameter detection, and semantic tooling. The evaluator's value-position `LookupLexical` and algorithm-position `LookupLexicalResolvedAlgorithm` are ONE implementation (`LookupTwinEquivalenceTests`); the evaluator's chain and `ElaboratedScopeLookup` (shared by `ParameterDetector` and `Semantics/`) must select the SAME declaration, because the detector's verdict rewrites the program (`LookupCoherenceTests`). Named `open` targets dedup first-occurrence-wins (`Evaluator.OpenExprName`, Lean `resolveAllOpens`) in BOTH C# lookups. [`ownership-and-lookup.md` § Ownership-first lookup]
- The OWNER WALK is the front-end half of ownership-first, with `ElaboratedScopeLookup.SelectOwnedDeclaration` its ONE implementation (Lean `selectOwnedDeclaration`): search outward by owning scope over the parameters a scope binds and the properties it declares; the first owner declaring the name decides, so a captured ancestor parameter beats a property of any farther owner, opens are consulted only after the whole walk, the prelude only as the outermost property level, and ownership never changes promotion (`IsBoundName`). Properties matching parameters of the same or an enclosing algorithm are declaration errors (`ParameterPropertyCollisionValidator`), except that the never-called root's completed signature is checked against the root's OWN declarations only (an unresolved root name is `UnresolvedImplicitParams` at the first root output row). The owner map is `ParameterOwnership` (name → owning level, never a depth); `ShouldRewriteAsParam`, `ResolveReceiverNameProvider`, and `ComputeVisibleSymbols` all go through the walk. `ParameterOwnershipTests`, `LookupCoherenceTests`, the `ownership-*` spec cases. [`ownership-and-lookup.md` § The owner walk]
- Complete owner signatures include later implicit forwarding captures. After lifting, `ParameterDetector.CompleteOwnership` reselects bindings using the existing owner walk while preserving inferred lists, pattern shapes, provenance, and Grace order. If a binding or deferred owner context changes, restore synthesized-call source origins and rebuild forwarding/closed-input diagnostics with signatures fixed before exposure; never turn an obsolete implicit call into a written call of the newly selected parameter. `OwnershipConformanceTests` connects real owner/binder identities to the independent hand-written Lean table in `CoreTests/NameOwnership.lean`; generated elaborated-AST evaluation alone is not classification conformance.
- `open Name` may target a lexically visible private head, but open-provided names and dotted open steps select PUBLIC members (`NotPublicProperty` otherwise), while structural dot access selects DECLARED members, private included. SELECTION NEVER DEPENDS ON EXPOSURE (K1-08): selection by visibility first, then ONE accessibility check of the unique selected member (`Evaluator.IsAccessibleFrom` / Lean `memberAccessible?`) requiring the declaration AND its activation in the site's lexical chain; capture requirements retain the exact semantic owner through shadowing (`Property.RequiredAncestorParameters`, `CaptureRequirements` / `PropDef.requiredOwnerDepths`, `PendingReference`); declaration tokens distinguish same-named algorithms and clause families, activation tokens distinguish calls. An OPEN PROVIDER needs zero effective call parameters and can be neither a clause family nor a prelude builtin, bare or as the head of a dotted target (`OpenProviderValidator`; `IllegalInOpen`, refused eagerly by the front end and by kind at open resolution), a family exposes no branch members structurally, and classification never invalidates selection, so there is no recheck round. `LocalMemberAccessTests`, `ZeroArgPropertyCacheScopeTests`, `CoreTests/NameOwnership.lean`. [`ownership-and-lookup.md` § Open, exposure, and accessibility]
- STATIC-OPEN OWNERSHIP (SYN-03 / F2): `open` resolves statically, but its target's HEAD name is classified by the ONE owner walk (`ParameterDetector.ClassifyOpenTargetHeads`); when the nearest binding is a parameter of any kind, the head elaborates to `Expr.Param` — never an open form (`IsCoreOpenForm` / Lean `Expr.openForm?`; evaluation yields `BadOpenForm`) — the front end reports `DiagnosticCode.OpenTargetIsParameter` at the head without searching farther outward, and the rejected target provides no names; the root's phantom signature is not a callable binding for this decision (`ParameterOwnership.CallableBindings`). Lean `elaborateOpenHead`; `StaticOpenOwnershipTests`, the `ownership-open-*` spec cases. [`ownership-and-lookup.md` § Static-open ownership]
- `open` is a declaration, not an output expression: ONE comma-separated target list per algorithm (`open A, B, C`; string targets in single quotes), parsed by a dedicated comma-list parser into resolve / argumentless dot-call / block / string-load targets; the first target must start on the `open` line; a comma or a leading `.` continues the list across lines but a plain newline never does (`open Math` newline `Math.Pi` is an open plus a row); `;` and a bare same-line second target are missing-comma diagnostics; `open A*` parses to a spread and is rejected as not an open form. [`syntax.md` § The `open` declaration]
- `open 'url'` is front-end sugar for load elaboration, not a core AST construct.
- Dot-call uses structural lookup first and lexical fallback second at EVERY level of a chain: an argumentless non-`string` receiver is NAVIGATED through its exported structural members before the outer edge is resolved (`resolveDotReceiver` / `ResolveDotReceiver`, the ONE receiver resolution shared by the sync evaluator, the async twin, and the sequence optimizer, mirrored statically by `AstHelpers.ResolveStaticStructuralMemberProvider`); a local-only or branch intermediate is that edge's `LocalOnlyProperty` error; a receiver without the member, an argument-bearing edge, or `.string` is a value, so the chain continues by extension fallback (`3.A.B` is `B(A(3))`); navigation is identity-only and the higher-order channel is untouched. A MISSING MEMBER ON A STATICALLY KNOWN RECEIVER (G-24) falls back lexically like any receiver — a visible lexical callable is a VALID fallback, an unresolved name becomes an implicit parameter — and static receiver knowledge serves diagnostics ONLY (`ImplicitParameterProvenance.DotMemberOrigin`, member-surface suggestions, member-token positioning); no layer branches on the receiver's spelling. `ChainedDotStructuralPrecedenceTests`, `ReceiverAwareMissingMemberDiagnosticsTests`, the `dot-chain-*` spec cases. [`ownership-and-lookup.md` § Dot-call resolution and missing members]
- Grace `~` is a front-end parameter-order annotation on exactly one DIRECTLY attached bare-name occurrence (`~x` / `x~`; a detached marker is `InvalidGraceMarker` recovering to the plain name; attached runs use ordinary weight arithmetic), stripped before evaluation. GRACE MUST BE EFFECTIVE (F10): on any occurrence whose binding is already fixed — an explicit or captured parameter, a visible property, a builtin, an opened name, a structural dot member, anything under a closed explicit parameter list — it is `DiagnosticCode.InvalidGraceMarker` from `ParameterDetector.ReportIneffectiveGrace` (once per occurrence per region; run-local `GraceOrigins` revalidates through ownership completion), never a silent no-op. A graced name inside redundant parentheses keeps the plain name's CAPTURE boundary (`(~a).V` is `(a).V`, never `a.V`). `GraceEffectivenessTests`, the `grace-*` spec cases. [`ownership-and-lookup.md` § Grace]
- Grace composes with ordinary dot syntax: `a~.t(args)` is postfix Grace on the bare receiver occurrence followed by ordinary `.t`, while `a.~t(args)` is ordinary dot with prefix Grace on the participating fallback/member occurrence `t`. Base DotCall occurrence order is receiver, participating fallback, then arguments, so `a.t` infers `(a, t)` and both graced two-name forms infer `(t, a)` through the ONE general Grace reordering law. Postfix Grace on a compound receiver (including a second `~.` in a chain) rejects through the one-name eligibility rule; prefix member Grace remains eligible because it decorates the bare member occurrence. Parameter detection consumes Grace, all forms elaborate to the SAME ordinary structural-first `DotCall`, and Grace never changes executable selection.
- Implicit-parameter order follows first semantic source occurrence plus the ordinary Grace arithmetic. A DotCall contributes its receiver occurrences, then its member's stored lexical-fallback occurrence when fallback MAY be selected, then written argument occurrences; thus `K = a.t(b)` infers `(a, t, b)`, while the direct call `K = t(a)` independently infers `(t, a)`. Runtime fallback assembly as `t(a, b)` does not determine the enclosing signature order.
- A user call binds each parameter on the value channel, the algorithm channel, or both, and the callee evaluates in the CALLER's environments extended with its own bindings; a BOUND PARAMETER OWNS ITS NAME ON EVERY CHANNEL — every binding site in both engines and the async twin shadows the callee's parameter names out of all three inherited tiers (value, counted, algorithm) through ONE helper (`ShadowInheritedParameterEnvironments` with `ShadowValEnv`; Lean `EvalCtx.bindParameters` with `ValEnv.shadow`), so a name bound only on the algorithm channel read in value position gets the value-demand outcome, a name bound only on the value channel read in call position fails as not callable, and neither ever reaches a same-named caller binding. [`ownership-and-lookup.md` § Parameter channels and shadowing]
- Ordinary lexical dot-call injects the receiver as ONE leading argument SEGMENT — `A.B(C, D)` allocates like `B(A, C, D)`: the receiver's item count never satisfies arity, a FIXED parameter allocated the segment binds its one captured value, and only a flat TOP-LEVEL collecting parameter consumes the segment's supply (a written group/brace receiver supplies its raw rows, a NAMED property receiver one item); assembly never inspects the callee or pre-expands the receiver (`ParameterPatternInput.CollectingSegmentEmittedCount` / Lean `collectingSegmentCount?` is ephemeral). Direct calls are unchanged. [`sequences-lists-and-calls.md` § The receiver segment]

## Lean/C# Alignment

Before editing, classify the change with `src/KatLang/SEMANTIC-ALIGNMENT.md`; its "Lean update required?" column is authoritative. Observable semantics require Lean consideration and usually Lean updates plus parity tests; C# implementation/tooling-only changes need C# tests only; optimization-only changes leave Lean untouched but need equivalence tests against the generic path; diagnostic wording-only changes need no Lean when the structured error kind/payload is unchanged; grammar or AST changes usually need Lean review; numeric changes route by tier (the numeric bullet below). This decides the required semantic EDITS only — validation scope is decided by the risk level in `Validation`: a C#-only optimizer, async, or ownership change that needs no Lean edit is still V3 when it touches a V3 trigger, so all seven Lean targets run with no `.lean` change, and an unchanged `.lean` file is no evidence that C# is still aligned. When semantics change, update every affected layer in the same task: Lean, C# parser/elaboration/evaluator, `src/KatLang/Semantics/`, tests and the canonical corpus, `KatLang.ebnf`, `tutorial.md`, and the generator guidance.

- `Parser.Parse(...)` and `ParseResult` are elaborated front-end outputs, not raw syntax trees.
- The raw syntax boundary is `Parser.ParseSyntax(...)`.
- `FrontEndPipeline.Process(...)` / `ProcessAsync(...)` are the explicit C# front-end paths for elaboration passes such as load elaboration, parameter detection, implicit argument resolution, and property exposure resolution.
- The individual elaboration passes are INTERNAL stages: `ParameterDetector`, `ImplicitArgumentResolver`, `PropertyExposureResolver`, `FrontEndPipeline`, `Parser.ParseSyntax`, and `ModuleLoader` are not host API, and hosts cannot compose partial elaboration (a Detect→Resolve tree without exposure resolution leaves every `Property.Exposure` at `Exported`, which the evaluator trusts). Supported layers: `Parser.Parse`/`ParseAsync` and `KatLangEngine` (complete pipeline), `SemanticModelBuilder` over `ParseResult`, and `Evaluator.Run*` over host-built ASTs (as-is, preflight only, no elaboration). Do not re-publicize a stage or add a partial facade. Pinned by `FrontEndElaborationBoundaryTests` and `PublicElaborationSurfaceTests`. [`evaluator-and-hosting.md` § Elaboration boundary]
- Default parse/run entry points reject unresolved `load`; SOURCE LOADING IS ASYNC-ONLY through the one downloader contract `RunOptions.DownloadCode : Func<string, CancellationToken, ValueTask<string>>` — the ONLY transport (no ambient HTTP downloader; `AllowedHosts` fails closed on blank or null entries), awaited inside `ModuleLoader.ElaborateAsync` — so `KatLangEngine.RunAsync` and `Parser.ParseAsync(source, options)` are the elaboration-enabled entry points and the sync ones reject a downloader-configured options object with `InvalidOperationException`, never a sync-over-async bridge. Load-bearing spines take the `// MIRROR OF` async loader twins; a branch body owning an unresolved load is a DEFERRED region (`DeferredModuleRegion.MaterializeAsync`, fetched only when evaluation selects the branch, cancelled when its last consumer leaves); residual stack exhaustion is `ModuleElaborationStackExhausted`. `ModuleLoaderAsyncTests`, `docs/design/async-evaluation-2026-08.md`. [`evaluator-and-hosting.md` § Source loading and deferred modules]
- Structural AST depth is a C#-only host-safety policy: every entry point that hands an AST to recursive consumers runs the iterative `AstStructuralPreflight` FIRST (two tiers — `EvaluationLimits.MaxSupportedAstDepth` for fat-frame consumers, `AstStructuralPreflight.RawSyntaxMaxAstDepth` for raw-syntax passes and the module loader, whose nested loads count cumulatively), a new `Expr` variant joins its child enumeration and the fail-loud `AstWalker.VisitExpr`, pure-expression spines stay ITERATIVE in `Eval`/`EvalCounted` (`EvalExpressionSpineCounted`), diagnostic rendering is iterative and output-bounded (`ExprNameRenderer`), and the PARSER budget is ONE cumulative weighted counter (`Parser.MaxNestingDepth`; a nested module parse starts with the loader's live debt) — never a mechanism with its own budget or reset; lookahead is linear total work; an `AstWalker` subclass using neither declaration hook opts out of the per-declaration loop (`VisitsExplicitParameterDeclarations => false`). No Lean counterpart. [`evaluator-and-hosting.md` § Structural depth and parser budgets]
- Host ASTs may contain SHARED acyclic subtrees (cycles are preflight-rejected) and module elaboration splices one cached module algorithm at every load site, so every front-end pass is DAG-SAFE: a run-local reference-identity memo per constant-context region bounds work by distinct reachable nodes × distinct semantic regions, output preserves sharing within a context, and traversal-path multiplicity affects neither results, nor diagnostics, nor asymptotic work (deliberate exceptions: diagnostic multiplicity within one diagnostic context, load-site identity within one loader context, a sibling CYCLE resolving by declaration order, the loader splitting by depth near the ceiling). Sibling-dependency edges are COMPLETE, so declaration order is unobservable; the `ModuleLoader` memo checks live INSIDE the calibrated frames. `FrontEndDagComplexityTests`, `AstGraphFuzzTests`. [`evaluator-and-hosting.md` § Shared-DAG guarantee]
- EVERY hand-written `Expr` traversal is exhaustiveness-enforced: no `_ => expr` / `default: break` arm may absorb an unknown variant — the front-end walks (`ParameterDetector`, `ImplicitArgumentResolver`, `PropertyExposureResolver.RewriteExpr`, `PropertyDependencyGraphBuilder`, `ModuleLoader.ProcessExpr` and its async twin) enumerate their leaves explicitly and THROW `InvalidOperationException` on an unhandled variant, and both counted dispatches (`EvalCounted` / `EvalCountedAsync`) enumerate their sync-delegable leaves (Num, StringLiteral, Grace; `NativeCall` is NOT one). Adding an `Expr` variant requires, in the same change: `AstStructuralPreflight`, `AstWalker.VisitExpr`, every traversal switch, both counted dispatches, and the pinned tables in `AstWalkerExhaustivenessTests`, `FrontEndTraversalExhaustivenessTests`, and `AsyncEvaluation/AsyncDispatchExhaustivenessTests`. [`evaluator-and-hosting.md` § Traversal exhaustiveness]
- Runtime evaluator budgets are OPERATION-LOCAL: dynamic depth is the only balanced protocol (`EvaluationBudget.TryEnterInvocation` / `TryEnterArgumentEvaluation`, released exactly once by `ExitInvocation`, fail-loud on underflow), steps, items, and string units are CUMULATIVE and never refunded, and a REJECTED enter mutates no counter. Host cancellation (`RunOptions.EvaluationCancellationToken`) lives ON the run-scoped budget: every chokepoint observes the token BEFORE any counter mutation (`EvaluationBudget.ObserveCancellation`), the optimized loop observes once per iteration without charging, and cancellation THROWS `OperationCanceledException` with the supplied token — never an `EvalError`. `BudgetConservationTests`, `EvaluationCancellationTests`. [`evaluator-and-hosting.md` § Budgets and cancellation]
- The ASYNC evaluation surface (`Evaluator.RunAsync`/`RunFlatAsync`, `KatLangEngine.RunAsync`) has NO Lean counterpart: the sync evaluator is the semantic oracle, a run with a sync-only cache and host-operation set executes the sync pipeline inline (never `Task.Run`), and otherwise the `async ValueTask` twins run — each marked `// MIRROR OF <sync name>` and updated in the SAME change as its counterpart (counted-family mirrors only; the twin root pins the GENERIC strategies through `ThrowIfAsyncStrategyPinningViolated`; `AsyncTwinDifferentialTests` pins outcome and counter equality). PUBLIC host operations (`HostOperations`, `RunOptions.HostOperations`) are ambient prelude properties over `Expr.NativeCall("host:" + name, params)`, so resolution, shadowing, arity, and the `A` vs `A()` cache rule are unchanged; async operations await at ONE guarded `EvalCountedAsync` case, every successful host value is normalized at the boundary (`NormalizeHostOperationValue`), sync entry points reject async configurations, and host exceptions propagate unchanged. Native wrappers read arguments through `LookupNativeArgument` — the `Expr.Param` value read — so `Expr.NativeCall` is a RECURSIVE variant with its own async twin. `Hosting/*Tests`, `docs/design/async-evaluation-2026-08.md`. [`evaluator-and-hosting.md` § Async evaluation and host operations]
- SEEDED RANDOMNESS is host/runtime evaluation configuration with NO Lean native counterpart: `Math.Random`/`random` and `Math.RandomInt`/`randomInt` consume ONE run-scoped stream — run-scoped MUTABLE state owned by `EvaluationBudget.RandomSource` (a KatLang-owned SplitMix64 source, constructed EAGERLY per run by `RandomSourceFactory.Create` from `RunOptions.RandomSeed` / the `Evaluator.Run*` `randomSeed` overloads / CLI `--seed`, or from 8 bytes of entropy when unseeded) — never static, thread-local, `AsyncLocal`, seed-keyed, or on `RunOptions`/`EvaluationLimits`/`HostOperations`; `ApplyMathNative` receives it EXPLICITLY from `ctx.Budget` in both engines. Sync/async routing and optimizer strategies must preserve draw count and order (validation precedes every draw; a seed reproduces the stream, it never memoizes), the sampling algorithms stay independent of source acquisition, `Parser.Parse*` ignore the seed, and the exact PRNG/bounded-rejection contract lives in `docs/design/seeded-randomness-2026-09.md`. `RandomSourceTests`, the `Seeded*Tests` families, `CliApplicationTests`. [`evaluator-and-hosting.md` § Seeded randomness]
- Qualified canonical Math function references (`map(Math.Abs)`, `reduce(xs, Math.Pow, initial)`) resolve to the SAME runtime native wrapper as the lowercase alias and opened canonical name. Gate this exception on both authoritative Math metadata and the resolved member's actual `Expr.NativeCall` body; every general argumentless `DotCall` keeps its Lean-modeled zero-parameter wrapper identity.
- Plain/counted evaluator ownership: where a plain/counted pair is semantically equivalent, the COUNTED implementation is canonical and the plain one is its value projection — in Lean (`eval` is the total projection of `evalCounted`, which matches every `Expr` variant with no default arm) and in C# (`ProjectCountedValue`). Never reintroduce an independent plain evaluator body, and never make a counted function delegate to a plain one; the deliberate exceptions are enumerated in `SEMANTIC-ALIGNMENT.md`. [`evaluator-and-hosting.md` § Plain/counted ownership]
- The zero-parameter property cache is observable semantics modeled in Lean: property-value `A` reuses its first successful entry and explicit `A()` neither reads nor replaces it; exported bindings use one entry per declaring scope per run across every VALUE-read spelling, user-call argument, callback, loop, and open (keys identify the declaring scope structurally — never add environment identity; builtin VALUE slots such as `sum(A)` / `if(1, A, 0)` and the `.string` receiver demand the algorithm directly and bypass the entry, the captured `(A)` reads it), local-only bindings retain all three binding contexts, planned exported temps use the run cache and local-only temps per-iteration memoization, the evaluator trusts exposure metadata, failed properties are never stored, and a re-entrant read never replaces a completed first entry. `ZeroArgPropertyCacheScopeTests`, `LeanAstEncoderTests`, CoreTests `zeroArg*`. [`evaluator-and-hosting.md` § Zero-argument property cache]
- Lean core numerics use `Int`; the C# runtime uses IEEE 754 `System.Numerics.Decimal128` end-to-end. Division/modulo by an EVALUATED zero is the Lean-modeled `divByZero` error, zero-base powers follow the manifest's domain-error policy, `div` is `Decimal128Numerics.IntegerDivide`, other arithmetic is IEEE (specials are ordinary values), structural equality uses `Decimal128.Equals` while ordering is IEEE, and only transcendental Math results and `range` bounds are quantum-canonicalized. `order` is a STABLE sort and `orderDesc` its reverse (Lean `sortIntsAsc`/`sortIntsDesc`); `Math.Ln`/`Lg`/`Log` near 1 and delegated near-1 powers take the log1p reformulation (`Decimal128Numerics.NaturalLog`, oracle-pinned); `DisplayDecimals` rounds midpoints away from zero like `Math.Round` (`ValueTextRenderer.FormatAtom`). ROUTING is two-tier per the manifest's "Core numeric semantics" row: exact-integer laws change Lean and C# together with Lean-comparable spec coverage, while Decimal128-specific behavior is a reviewed divergence pinned by C#-only spec cases with a `LeanExclusionReason` — never classify from source spelling alone. [`evaluator-and-hosting.md` § Numerics]

## Builtins And Spread Conventions

- `arity` means the structural count of top-level output slots.
- `count` means the number of evaluated top-level values after sequence values are opened by the consuming operation.
- Do not treat `arity` and `count` as interchangeable.
- Terminology: prefix `*` is the COLLECT MARKER; `*name` is a COLLECTING BINDING; in a callable declaration it forms a COLLECTING PARAMETER. Postfix `*` is the SPREAD MARKER; `value*` is a SPREAD EXPRESSION. Infix `*` multiplies. A callable with a collecting parameter may be DESCRIBED as variadic (it accepts a variable number of argument items), but "collecting parameter" is the canonical construct name — never "variadic parameter", "rest parameter", or "rest binding".
- A property/call/builtin RESULT boundary returns ONE value with count `Result.valueCount` (0 for `()`, otherwise 1; a list counts 1): a multi-output body is one sequence value to its caller and only an explicit spread opens it, and redundant unary sequence structure normalizes during construction. The re-count helper `reCountValueBoundary` / `ReCountValueBoundary` applies at user/conditional calls and structural zero-arg dot access; collection-producing builtins and collecting bindings materialize ONE exact list (`makeCollectionListResult`, `collectSegment`). NOT value boundaries: root/body output accumulation, `while`/`repeat` multi-slot state, and the single-value `map`/`reduce` callback contract. [`sequences-lists-and-calls.md` § Value boundaries]
- Comma is the explicit expression-list separator and on one physical line the ONLY one (SYN-07A): whitespace never creates a slot, so `1 2 3`, `F(1 2)`, `[1 2]`, `A[1]`, and `P = a b` are the targeted `DiagnosticCode.UnseparatedSameLineItem`, reported at the second item with ONE message naming the three repairs. ONE ownership point decides slots (`Parser.StartsNextExpressionListSlot` through `ParseExpressionListOperand`), the body loop's row check decides declarations, parameter-pattern lists use `Parser.StartsUnseparatedPatternItem`, and recovery is always a slot boundary, never a grammar hole. A newline is a separate mechanism — it separates slots at root output and inside open delimiters, ends a one-line body, and never splits a continued expression — and parsing never depends on arity, values, or types. `SameLineSeparatorTests`, the `same-line-*` spec cases. [`syntax.md` § Comma and same-line items]
- Semicolon `;` is not supported as expression syntax. It is not an alternative separator or sequence constructor. The parser reports: "Semicolon is not supported as an expression separator. Use ',' between expressions on one line (a new line separates them where the context allows it), or parentheses for one sequence value." Use commas (or separate rows) for separate slots and parentheses for one sequence-valued slot, e.g. `sum((10, 20, 30))`, `take((1, 2, 3), 2)`, and row-like values as `Reports = (row1), (row2)`.
- Postfix continuations bind on the same physical line only — a same-line `(`/`{` after a callable is a call delimiter, a newline never continues a closed expression; indexing `:`, postfix `~`, binary operators, and the postfix `*` marker are same-line only; a leading `.` is the supported chain continuation; definition bodies and open target lists are line-bounded. DECLARATION HEADS ARE LINE-LOCAL (F7) through the ONE predicate `Parser.IsHeadToken` (a simple head on one line; a clause head's name and `(` share a line, its `)` and `=` share a line), so `A` newline `= 1` keeps the first line as a closed row and reaches `Parser.StrayEqualsDiagnostic`; explicit continuation AFTER a recognized head is unchanged. `DeclarationHeadLineRuleTests`. [`syntax.md` § Line rules and declaration heads]
- The star `*` has three purely syntactic roles: prefix COLLECT MARKER in binding patterns (`*name` is the ONLY collecting-binding syntax, valid only in binding positions and DIRECTLY attached — `* items` and `**items` are targeted errors, and a prefix `*` in expression position is a diagnostic recovering to the operand), postfix SPREAD MARKER on a completed expression, and infix multiplication. `name...`, `...name`, `spread(expr)`, and `expr.spread` are NOT KatLang syntax. [`syntax.md` § Star roles]
- The spread expression has ONE spelling, the postfix `expr*`, read LAYOUT-INDEPENDENTLY (SYN-07B): the NEXT significant token decides — an operand-starting token (same line or later) makes the star multiplication; a declaration head (`Parser.StartsDeclarationAt`), comma, closing delimiter, end of input, or non-expression token makes it a spread. Attachment is a SEPARATE later check (`Parser.ParseSpreadMarkerContinuation` through the ONE helper `Parser.IsDirectlyAttached`, shared with Grace and collect markers): a spread-classified star detached from its operand is `DiagnosticCode.InvalidSpreadMarker`, never silently either operation, and neither attachment nor same-line lookahead ever goes into `IsPostfixSpreadMarkerStar`. The marker lowers to the ONE unary `Expr.SequenceSpread` (never a Call/DotCall); `value**` is `(value*)*`, never recursive flattening; a spread is legal only as a whole slot, a spread operand, or the FLUENT receiver `operand*.Member(...)` = lexical `Member(operand*, ...)` (`(A*).F` is a CAPTURE receiver instead). `StarSyntaxTests`, `MarkerAttachmentTests`. [`syntax.md` § The spread marker]
- Dotted-call equivalence is uniform through frontend elaboration: `a.F` is `F(a)`, and `A*.F` is `F(A*)`. This includes lexical resolution and implicit callable-parameter detection, so an unresolved `F` is inferred identically in both spellings; do not add fluent-call origin metadata or a spread-specific inference exception. Parenthesized `(A*).F` remains different because the parentheses make it an ordinary CAPTURE receiver — one leading segment through dot-call lookup (see the receiver-segment rule above), not a pre-lowered spread argument list.
- A spread spreads ONE item-producing boundary of its evaluated operand into the surrounding item supply — it creates no value; the RECEIVER decides what the items become (capture materializes a sequence, a collecting binding collects a list, fixed bindings and calls take items individually, root output emits rows). Sequence and list values supply their items; any other value supplies itself. A comma is REQUIRED between a spread and a following item (`A*, B`, or `A*,` newline `B`), because `A* B` and `A*` newline `B` multiply; `f((A*, B))` passes a spread plus a value as ONE argument. [`sequences-lists-and-calls.md` § Spread semantics]
- Call argument-slot assembly is SHARED by every callable shape (`BuildCallArgumentInputs` / Lean `collectVariadicCallItems`): each written slot is evaluated EXACTLY ONCE left to right, every non-spread slot reifies to ONE value, every spread slot spreads one boundary into ordinary slots BEFORE arity checking, clause selection, or pattern binding, and a patterned callee that needs both a capture's combined value and its written-slot view gets both from ONE prepared evaluation (`PreparedAlgorithmOutput`). WRITTEN-SLOT REIFICATION holds wherever the grammar defines one value per slot (list elements, sequence-value pattern items, the reduce initial accumulator); root/body rows and loop-step outputs keep multi-item emission. [`sequences-lists-and-calls.md` § Call argument assembly and written-slot reification]
- Square brackets construct list values (`Result.listValue` / `Expr.ListLiteral`), a second collection kind: normalization never applies to list structure (`[7] != 7`, `[] != ()`), `[` always begins a NEW expression, and bracket content is a pure expression list. Spread opens one sequence OR list boundary (`spreadItems`), indexing `:` projects through `projectionItems` and returns the element as stored, deconstruction's `structureItems?` opens a lone sequence or list, the post-binding builtin collection view opens a BOUND list one level, and every other non-spread consumer keeps lists opaque via `toItems` (calls never open lists implicitly). `atoms` collects numeric atoms through both boundaries (`languageAtoms`) into ONE exact list; truth testing stays sequence-only (`if([1], a, b)` is invalid); conditional sequence-value patterns match sequence values only; host flattening (`runFlat` / `hostAtoms`) opens lists. [`sequences-lists-and-calls.md` § Lists]
- Collecting binding COLLECTS one list. The three item-supply operations are distinguished by receiver purpose: `capture : Supply -> Value` (ordinary value/output capture — the normalizing `Result.normalize` boundary), `collect : Supply -> ListValue` (collecting binding / collecting parameter — `collectSegment` in Lean, `CollectSegment` in C#), and `spread : Value -> Supply` (the spread marker — `spreadItems`). Every collecting binding — single collecting parameters, mixed prefix/collecting/suffix parameter lists, and deconstruction collecting bindings — materializes exactly the assigned item slots as ONE exact list with emitted count 1: zero slots form `[]`, one slot forms `[item]` (NEVER erased, so one remaining structured row stays distinguishable from the row's elements), many form `[a, b, ...]`. Ordinary capture is unchanged (`x = 1, 2, 3` is `(1, 2, 3)`).
- A top-level collecting parameter collects the argument slots actually supplied: `Name(*values) = body` with `Name(A)` binds `values = [A]`, `Name(A*)` collects A's spread items, `Name()` collects `[]` — `F(A)` and `F(A*)` differ for every sequence-valued, list-valued, and empty argument and coincide only for scalars. Forwarding is ordinary list spread (`Forward(*items) = Target(items*)`, `spread(collect(xs)) = xs`); passing the collected list unspread passes one list argument; there is no hidden raw-supply metadata (a `variadicSupplyEnv`/`VariadicStreamEnv` must never be reintroduced). [`sequences-lists-and-calls.md` § Collecting parameters]
- A parameter list with several captures and one collecting parameter binds fixed captures front and back first, the movable collector taking the middle as one exact list; a plain call never implicitly opens a single sequence or list argument. Assignment deconstruction is the UNPACKING receiver instead: `x, *y, z = RHS` captures the right-hand side into one shared value, opens a lone sequence or list one level, and matches element-by-element; the RHS is a row of the ENCLOSING body (`Algorithm.User.IsAssignmentDeconstructionSource`) whose free names are the enclosing algorithm's implicit parameters, and its synthetic name never appears in a diagnostic. The shared matcher is `bindParameterPatternList` / `BindParameterPatternList`, every collecting materialization funnels through `collectSegment` / `CollectSegment`, flat callbacks bind through `bindCountedCallbackParameterPatternList` (a lone SEQUENCE element opens into row slots for a multi-parameter callee, LIST elements stay opaque), and the resolver synthesizes forwarding spread only when BOTH the destination and the source binding are collecting. [`sequences-lists-and-calls.md` § Collecting parameter lists, deconstruction, and callbacks]
- Collection builtins are ordinary FIXED-ARITY callables with ONE fixed `collection` parameter plus fixed controls: an unspread sequence or list is ONE argument and nothing opens before binding (`count(1, 2, 3)`, `take((1, 2, 3))`, and `count([1, 2, 3]*)` are arity errors; re-group as `sum((A*, B*))`); the bound collection is read through the POST-BINDING one-level view `builtinCollectionItems` / `BuiltinCollectionItems` (never recursive); collection-producing builtins materialize ONE exact list via `makeCollectionListResult` (a single kept item is `[item]`); a lexical dot-call receiver fills the `collection` parameter with no builtin-specific placement, and only sequence/variadic builtin dot-call paths may opt into receiver top-level expansion, explicitly in builtin metadata. [`sequences-lists-and-calls.md` § Collection builtins]

## Editor Semantics
- `src/KatLang/Semantics/` derives editor-facing meaning from parsed and elaborated ASTs.
- Build semantic models from `Parser.Parse(...)` / `ParseResult`, not from raw syntax.
- Only source-backed identifiers may produce semantic sites, resolutions, declarations, or spans. The parser's spanless recovery binder (`_error_`) declares no symbol (`SemanticModelBuilder.CreateScope`).
- Synthetic constructs must not invent source spans.
- If editor-visible behavior changes, update `src/KatLang/Semantics/` and `tests/KatLang.Tests/SemanticModelTests.cs` together.
- Preserve exact source-span invariants for hover, references, go-to-definition, classification, and callable-property metadata.
- Scope visibility is completion's semantic source: `SemanticModel.ScopeVisibilities` / `GetVisibleSymbolsAt` and `PreludeCatalog` enumerate exactly what ownership-first lookup resolves, scope regions are source-span hulls, and builtin names come from `PreludeCatalog` only. MODULE PROVENANCE is structural, decided per owner before the walk (`ModuleProvidedAlgorithmCollector`): a load-elaborated subtree (`Algorithm.User.IsModuleElaborated`) is module-provided at every depth, so the model emits NO document-owned sites for it while still building its scopes and symbols, a document reference to an imported member gets a LOCATIONLESS target (never a fabricated span), and inside a deferred module region the model performs NO module I/O and classifies unresolvable names `IdentifierClassification.DeferredModuleReference`. [`editor-semantics.md` § Scope visibility and module provenance]

## Testing Expectations

- Prefer minimal, semantics-preserving, reviewable changes.
- Add or update focused tests near the changed layer.
- Include negative coverage when failure modes are meaningful.
- Test design, adversarial coverage, failure analysis, and validation execution all belong to the primary agent; a subagent is for a bulky self-contained investigation only, never for running tests (see `Validation`).
- If a change crosses parser, evaluator, semantics, or docs boundaries, cover the affected layers in the same task when feasible.
- **A source-based evaluator test must PARSE CLEANLY, and must assert the error TYPE, not merely that something failed.** `Parser.Parse(source).Root` silently discards diagnostics, so a test whose source the parser rejects still evaluates the recovery tree and can pass for an unrelated reason — that is how a `NotPublicProperty` regression passed without ever reaching the branch, and how 41 `EvaluatorTests` came to run on illegal source. Use `SourceProvenance.ParseValid(...)` (or `EvaluatorTestSupport.ParseValidRoot`) for ordinary source semantics; `SourceProvenance.ExpectFrontEndError(...)` when the parser/elaborator is the subject; `SourceProvenance.ParseAllowingDiagnostics(...)` only where malformed source is the point (recovery, fuzz, editor tooling). Never assert an evaluator outcome on a source you have not shown to be legal.
- **Before writing a source test for an evaluator branch, check the branch is surface-reachable at all.** Front-end elaboration can make it dead: clause-family elaboration turns every single-clause binder form into an `Algorithm.User`, so the flat-binder arm of `ConditionalValueAccessError` cannot be reached from any written program, and implicit-parameter promotion hides the dotted-`open` visibility checks. A source test for such a branch passes while the branch stays dead — pin these from a prebuilt AST instead (`EvaluatorDefensiveBranchTests`).

## Coding Guidance

- Prefer small changes that fix the root semantic issue without widening scope unnecessarily.
- Do not introduce new AST shapes unless strongly justified by Lean or an existing architectural boundary.
- Reuse the owning logic instead of re-encoding the same rule across parser, elaboration, evaluator, or semantic-model code, and preserve the current parser/evaluator/tooling boundaries.
- Keep diagnostics structured, source-positioned, user-friendly, and phrased in KatLang terms.
- If a change is implementation-only optimization, say so explicitly.

## Validation

Validation scope follows REGRESSION RISK, never line count, file count, or file extension alone. The alignment manifest and the language rules decide which semantic EDITS a change needs (Lean, C#, corpus, docs); this section decides how much local validation the candidate gets and how it is executed. `.github/workflows/validate.yml` stays the full .NET + Lean backstop for pull requests and pushes to `main`: a local V0–V2 omission is a deliberate risk decision, and CI is never a reason to skip V3 locally. It IS the reason a local V1/V2 stays bounded: the backstop catches what a scoped run misses, so a V1/V2 run is never padded with a full phase "to be safe".

### Candidate and level

- Assess the COMPLETE candidate: the relevant commits plus staged, unstaged, untracked, deleted, and renamed files. A clean working tree is not evidence that a committed candidate needs no tests. Preserve unrelated work and account for it when it affects the candidate or the test results.
- Classify by semantic impact, dependency reach, and changed contracts. Start at V1 unless the change is clearly V0, then apply the V2/V3 triggers; when the impact cannot be confidently bounded, choose V3. Record the level and a one-line reason before validation starts; the level may be raised on evidence, never lowered. The level is also the execution plan: V0–V2 run only what their row names, and the full `validate-all.ps1` phases belong to V3 alone — if the candidate warrants a full phase, record V3; running one at V1/V2 is a misclassification, not extra diligence.

| Level | Appropriate scope | Required local validation |
| --- | --- | --- |
| V0 — trivial | Instruction/prose edits, comments, or formatting proven not to affect execution or mechanically checked content | Review the diff, whitespace (`git diff --check`), and the references/consistency of the text. No build or runtime suite for a genuinely documentation-only change. |
| V1 — focused | Small, isolated, behavior-preserving refactor or test change with a well-understood dependency boundary | Build the affected project/test dependency closure; run the directly related tests with verified filters. |
| V2 — affected | Bounded subsystem behavior change; a limited shared helper, API, or diagnostic contract change; neighboring consumers affected | Focused tests plus the neighboring/affected suites, the affected project builds, and the applicable parity/artifact/Lean checks — never the full solution suite or a `validate-all.ps1` phase. |
| V3 — full | Fundamental behavior, broadly shared infrastructure, cross-cutting changes, or uncertain impact | Complete local .NET validation and all seven canonical Lean targets, plus any specifically required regression/parity checks. |

V3 is MANDATORY for changes to parser/grammar behavior or AST structure; elaboration; lexical ownership/name resolution; parameter binding or implicit lifting; Grace; sequence/list/spread/collect/arity semantics; the evaluator core; the optimizer/planned execution; sync/async/cancellation behavior; core loading/module semantics; caching/exposure; Decimal128/numeric semantics; Lean/C# correspondence; and widely reused infrastructure or build/toolchain changes with broad impact. The triggers concern the behavior or machinery changed: a comment fix inside `Parser.cs` is not V3, a one-line ownership fix is; a formatting-only string-construction refactor may be V1 when the output contract is demonstrably unchanged; updating expected semantic results never makes a semantic change test-only. V2 covers bounded production-behavior changes, shared consumers, and API/diagnostic contracts without a V3 trigger — an isolated CLI presentation change needs no evaluator-wide validation, a change to shared loading or cancellation does. Executable documentation is not prose: tutorial result claims, spec-linked examples, generated prompt blocks, and the EBNF keep their verification tests (coverage map below) even when only text files changed, so such a change is neither automatically V0 nor V3; changed language MEANING is still V3 plus the semantic-update process.

### Lean validation

- V3 always runs all seven Lean targets, even when no `.lean` file changed — a C#-only optimizer, async, or ownership change is V3, and `SemanticExplorerCases`/`LanguageSpecCases` are how Lean/C# correspondence is checked.
- V1/V2: build the affected Lean targets and the dependent artifact/parity checks whenever Lean code, proofs, guards, imports, or generated Lean content changes or is affected; a meaningful Lean-only change never gets zero Lean validation, and unclear dependency reach means V3. Pure Lean comments may be V0; regenerating an artifact without a content change is not itself a semantic change.

### Commands

The normal V3 command, from the repo root:

```powershell
pwsh -NoProfile -File ./scripts/validate-all.ps1 -Phase All
```

Its .NET phase runs the FULL solution build (every project — `dotnet test` alone builds only test projects and their dependencies, so benchmark/demo compile breaks escape it), then the C# suite with `--no-build`, then `git diff --check`; its Lean phase owns the one canonical seven-target list. The script accepts only `All` (the default), `DotNet`, and `Lean`: it has no focused or level switch and does not detect risk. Completing `-Phase DotNet` and then `-Phase Lean`, one after the other, against the same unchanged candidate satisfies V3 — do not rerun `All` merely to repeat completed work, and never run the two phases side by side — while a partial phase alone is never full validation. A phase already runs every focused suite, so it is never preceded, accompanied, or followed by a separate filtered pass over the same candidate. Each phase fingerprints the staged, unstaged, and untracked state and fails if validation changes it; a checkout may start dirty, but validation must leave it exactly as it started.

Manual .NET fallback (equivalent, including the independent full-solution build):

```powershell
dotnet build .\KatLang.slnx -p:UseSharedCompilation=false
dotnet test .\KatLang.slnx -p:UseSharedCompilation=false --no-build
git diff --check
```

Manual Lean fallback (all seven targets — V3, or a V1/V2 change that affects Lean):

```powershell
Push-Location .\lean
lake build CoreTests
lake build KatLangArityLaws
lake build AstDemo
lake build CoreArityAlgebra
lake build CoreArityAlgebraProofs
lake build SemanticExplorerCases
lake build LanguageSpecCases
Pop-Location
```

Lean CoreTests use `#guard` for semantic assertions, so a failing assertion fails `lake build CoreTests`. Remaining `#eval` lines are demo/inspection output only.

Focused V1/V2 runs build the affected projects, then filter, for example:

```powershell
dotnet build ./tests/KatLang.Tests/KatLang.Tests.csproj -p:UseSharedCompilation=false
dotnet test ./tests/KatLang.Tests/KatLang.Tests.csproj -p:UseSharedCompilation=false --no-build --filter "FullyQualifiedName~SameLineSeparatorTests"
```

Filters must name real test classes/namespaces (check the inventory: the class in `LanguageSpec/GeneratorSpecTests.cs` is `LanguageSpecArtifactsGeneratorPromptTests`), and the summary must show the intended tests discovered AND executed — zero matching tests is not a pass whatever the exit code. Use `--no-build` only after a successful, current build of the same projects/configuration/framework and inputs. Verification outside the script keeps its guarantees: neutralize inherited `KATLANG_REGENERATE_*` flags for the verification process only (a child `pwsh -NoProfile` whose environment is discarded, never the caller's lasting environment), snapshot `git status --porcelain=v1 --untracked-files=all` plus the index and worktree diffs before and after, and report an unexpected mutation with its evidence instead of undoing it. Keep terminal output minimal; save complete stdout/stderr under the ignored `artifacts/validation/` directory or a temporary directory, preserving the command's real exit code when redirecting or piping (`$LASTEXITCODE` after the native command in pwsh, `pipefail`/`PIPESTATUS` in bash). Missing required tooling (SDK, `lake`, a runner) is BLOCKED/incomplete validation, never a pass and never a silently lower level.

### Regenerating generated artifacts

Generated artifacts are never edited by hand and never rewritten by a verification run. Regeneration is one deliberate, targeted `dotnet test` run with the artifact's flag set to `1`: the run WRITES the artifact and then FAILS BY DESIGN (also when nothing changed), so it can never pass as verification — review the diff, clear the flag, and run the normal verification at the level the underlying change requires (an intentional language-behavior change is V3).

| Artifact | Flag | Filter |
| --- | --- | --- |
| `lean/LanguageSpecCases.lean` plus the `=== BEGIN GENERATED: katlang-spec-examples ===` block in `.github/agents/katlang-generator.agent.md` and `experimental/prompts/katlang-generator.txt` | `KATLANG_REGENERATE_LANGUAGE_SPEC` | `--filter LanguageSpecArtifacts` |
| `lean/SemanticExplorerCases.lean` | `KATLANG_REGENERATE_SEMANTIC_EXPLORER` | `--filter SemanticExplorerLeanArtifact` |
| `tests/KatLang.Formatting.PublicApi.Tests/PublicApiBaseline.txt` | `KATLANG_REGENERATE_PUBLIC_API` | `--filter PublicApiBaseline` |

For example `$env:KATLANG_REGENERATE_LANGUAGE_SPEC = "1"; dotnet test .\KatLang.slnx --filter LanguageSpecArtifacts`. `validate-all.ps1` is observational: before it builds or tests anything it removes every `KATLANG_REGENERATE_*` variable from its own process (the whole prefix, case-insensitively; restored on exit), so an inherited flag can never make a green run rewrite a tracked artifact. The flag registry and the write-then-fail contract are `RegenerationFlags` / `ArtifactRegeneration` in `tests/KatLang.Tests/Infrastructure/ArtifactRegeneration.cs` (shared as source with the public-API test project); a new `KATLANG_REGENERATE_*` variable must be registered there — `ArtifactRegenerationPolicyTests` scans the repository for unregistered names and for tests that read a flag outside the helper.

### Execution discipline

Validation is executed by the primary agent, in ONE execution stream: never two of `dotnet build`, `dotnet test`, `lake build`, a `validate-all.ps1` phase, or a regeneration run in flight at once — concurrent `dotnet test` invocations lock `KatLang.Tests.dll` (MSB3027), a phase fingerprints the tree while it runs, and a second run of the same suite over an unchanged candidate is pure duplication. Every command's full output goes to a log file (the ignored `artifacts/validation/` directory or a temporary directory) and only its summary lines — result totals, failure identities, exit code — are read back, never the whole log.

- ONE plan per candidate, chosen before anything runs: at V1/V2 the focused and affected suites, most informative first, and nothing beyond them; at V3 the full phases only. Development checks while editing stay minimal — the test class being written, the one previously failing check after a repair, the Lean target that compiles the edited file, a regeneration run — because the plan runs everything else exactly once; a pre-validation sweep of neighboring suites runs every test twice.
- One command at a time, waited to completion: a `--no-build` run only after the build's exit code is in hand, `lake build` never beside a `dotnet` command, the .NET phase and then the Lean phase, never side by side. A `validate-all.ps1` phase exceeds the foreground time limit, so run it as ONE background command and then wait for its completion — no polling loop (every poll re-reads the whole context), no other command, and no edit to the checkout until it has finished.
- On a failure, capture the command, the failure identity, and the evidence; decide what it means; repair; rerun only the failing check; then complete the plan for the FINAL candidate. Reuse earlier results only while their inputs, dependencies, configuration, and environment still apply (later prose-only edits do not by themselves invalidate runtime results). When a failure suggests wider regression, or the diff reveals a V3 trigger the classification missed, raise the scope one level at a time — never as a precaution — and a full phase replaces the remaining focused plan instead of adding to it. Do not rerun an unchanged failure repeatedly, and do not launch every suite to diagnose a missing SDK.
- Never claim validation from a partial run, a stale build, an unexecuted command, a zero-test filter, or an assumption that CI will pass, and do not label a failure pre-existing or flaky without evidence. Report what ran, the counts, the failures, what was omitted and why, and the log paths.

### Subagents

Do not delegate test execution. Measured in September 2026, a validation worker spent 30–50 requests to run two or three commands — about ten times the cost of running them inline — could not work in parallel with a tree that must stay frozen, and shared no prompt cache with the primary agent (caches are model-scoped and prefix-exact). A subagent is for a BULKY, SELF-CONTAINED INVESTIGATION whose intermediate reading would otherwise flood the primary context — a failure hunt across many files, an inventory, a cross-file audit. Give it the cheapest model that can do the job, a bounded brief with an explicit stopping point, and ask for `file:line` facts; code the primary agent will edit or reason about it reads itself, in bounded ranges. Never spawn one for a single known file, and never let one edit, regenerate, or validate.

  the version already present in `KatLangVersion.props`. A push, merge, or tag
  never publishes a release automatically.
- The release workflow validates the exact dispatched commit, builds and runs
  the NativeAOT CLI on native Windows/Linux/macOS x64 and ARM64 runners,
  packages the tested executable with the root `LICENSE`, `NOTICE`, and

  Runtime/ILCompiler pack identities and versions come from the publish output's

  an MSBuild version override, create/move an existing version tag, or replace
  an existing release.
- Normal jobs have `contents: read`. Only the final publication job has
  `contents: write`; workflows use no user-managed secrets. External actions
  are pinned to immutable commit SHAs and `.github/dependabot.yml` proposes
  reviewable GitHub Actions pin updates.


## Public API Baseline And Release Version

- `tests/KatLang.Formatting.PublicApi.Tests/PublicApiBaseline.txt` is the checked-in, deterministic rendering of the COMPILED public surface of the `KatLang` assembly — the one assembly the NuGet package ships — reflected by `PublicApiSurfaceRenderer` in that deliberately non-friend test project: every exported type plus consumer-reachable protected nested types, with base/interfaces, generics and constraints; every consumer-visible member with parameter names, modifiers, defaults, nullable annotations and nullable-flow attributes; and every public enum member with its exact numeric value. `PublicApiBaselineTests` compares exactly and never rewrites; a difference is a NuGet surface change. Record an intentional change by regenerating it (`Regenerating generated artifacts` under `Validation`) and review the diff as the compatibility review. Regenerating the baseline never changes the release version; the focused hand-written contracts in that project (`PublicElaborationSurfaceTests`, `PublicFormatterExtensionTests`) stay beside it.
- `KatLangVersion.props` is the ONE place the release version is written. `src/KatLang/KatLang.csproj` (package and assembly version), `src/KatLang.CLI/KatLang.CLI.csproj` (which builds against the KatLang PROJECT, so it cannot lag onto a previously published package) and `tests/KatLang.CLI.Tests` (which bakes the value in as `IntendedKatLangVersion` assembly metadata — build intent, never read from the KatLang assembly under test) derive from it. `ReleaseVersionSourceTests` rejects any other version literal in an MSBuild file and any in-repository `PackageReference` to KatLang; the CLI version tests compare the loaded runtime, the CLI assembly and `--version` against the intended metadata, so a stale or mismatched artifact fails rather than passing against itself.

## Executable Language Specification

- `tests/KatLang.Tests/LanguageSpec/LanguageSpecCorpus.cs` is the canonical executable specification: named cases with stable IDs and HAND-WRITTEN canonical expectations. Never regenerate its expectations from observed behavior — a failing `LanguageSpec*` test means either fix the implementation or edit the canonical case in a reviewed diff.
- Same-program fidelity: the Lean program of every Lean-comparable case in BOTH differential corpora (`LanguageSpecCorpus` and `SemanticExplorerCorpus`, internal-node cases included) is DERIVED from the source's real elaborated AST through `tests/KatLang.Tests/LeanAstEncoder.cs` — never authored by hand and never rebuilt by test-side parser-rule templates. C#-only cases carry an explicit non-blank `LeanExclusionReason`, a hand-authored LanguageSpec Lean program requires the exceptional `LeanProgramOverride` + `LeanOverrideReason` (currently unused), and per-corpus exact-ID exclusions plus `FidelityRatchet_*` tests pin the derived-case partitions. The encoder is FAIL-LOUD: extend it deliberately (with reviewed goldens in `LeanAstEncoderTests`) rather than approximating, and expected strings in encoder tests are manually reviewed constants. See `docs/design/executable-language-spec.md` §5.
- GENERATED from it (do not edit by hand): `lean/LanguageSpecCases.lean` and the `=== BEGIN GENERATED: katlang-spec-examples ===` block in both generator files; regenerate all three together (`Regenerating generated artifacts` under `Validation`). `lean/SemanticExplorerCases.lean` is the second GENERATED Lean/C# differential corpus (from `SemanticExplorerCorpus`; see `docs/design/sequence-boundary-audit-2026-07.md`): a failing `#guard` there is a Lean/C# divergence — or a Lean-internal plain/counted mismatch — on that case; after an intentional semantics change regenerate it the same way.
- Tutorial examples marked `<!-- spec:case-id -->` are verified against the corpus (source and expected output) by `TutorialSpecTests`; when changing a linked example, update the canonical case and the tutorial together.
- EVERY tutorial fence followed by a `**Result(s):**` claim is executable documentation: `TutorialResultSweepTests` runs it through `KatLangEngine.Run` and display-matches the claim — no marker needed, so an ordinary new example enters the sweep automatically. A genuinely non-standalone example (e.g. one needing a network downloader) carries `<!-- spec:skip nonblank reason -->` before the fence; the skip inventory is exact-pinned, and result-bearing coverage is monotonic (pinned minimum baseline — removing an existing claim requires a reviewed ratchet reduction, while additions need no pin edit). The shared grammar lives in `TutorialCorpus` and fails loudly on malformed/detached claims, so a result claim can never silently drop out of verification.
- Output-only verification is not a semantic pin (SYN-12): a tutorial example can print the documented number for the wrong reason (an indented `Inner = v + 1` beneath `Outer(v) = Inner` is a ROOT property whose `v` is forwarded through the closed list, not a nested property reading the parameter of its owner). The high-risk explanations — lexical ownership, visibility/export, property-first dot-call resolution, clause-family arity, sequence-value pattern kinds, the call/value boundary, Grace order — are therefore ALSO pinned by `tests/KatLang.Tests/LanguageSpec/TutorialSemanticContractTests.cs` through the elaborated AST (`Property.Exposure`, `Params`), the semantic model (`FindResolutionAt` declaration spans), and structured `DiagnosticCode`/`KatLangErrorCode` values; extend it, and the corpus, when such an explanation changes.
- When language behavior intentionally changes, update the affected canonical cases in the same task as the Lean/C#/tutorial/generator changes.
- Maintainer guide: `docs/design/executable-language-spec.md` (partitions, counts, how to add cases, worked example).

## Do Not

- Do not silently change language semantics.
- Do not let Lean and C# diverge.
- Do not treat `AGENTS.md` as a long design essay.
- Do not let multiple agent-instruction files drift into conflicting guidance.
- Do not add convenience syntax, hidden fallbacks, or duplicated semantic logic just to make a local change easier.
- Do not report a partial, stale, zero-test, or tool-blocked run as validation, and do not lower a selected validation level silently.
- Do not run validation commands concurrently or twice: one command in flight, one plan per candidate, no pre-validation sweep, and no subagent for test execution.
- Do not let a subagent edit code, tests, expectations, or tracked artifacts, run validation, or stage, commit, reset, or discard files.
