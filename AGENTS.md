# KatLang Agent Instructions

## Project Overview

- These instructions are for Codex and other AI coding agents working in this repository.
- `AGENTS.md` is the canonical shared agent-instructions file for this repo.
- KatLang's authoritative language model is `lean/KatLang.lean`.
- The C# implementation in `src/KatLang/` must stay semantically aligned with Lean.
- If Lean and C# are both wrong for the same bug, fix both together when feasible.
- Keep this file operational and concise.

## Core Architecture

- `lean/KatLang.lean`: source of truth for AST shape, evaluation rules, and invariants.
- `lean/CoreTests.lean`, `lean/AstDemo.lean`: Lean-side regression and AST compatibility checks.
- `lean/CoreArityAlgebra.lean`, `lean/CoreArityAlgebraProofs.lean`, `lean/CoreArityAlgebra.md`: isolated paper-facing extraction of KatLang's arity algebra; it must stay faithful to `lean/KatLang.lean` but is not authoritative semantics.
- `src/KatLang/`: C# AST, parser, front-end elaboration, evaluator, diagnostics, and public API.
- `src/KatLang/Semantics/`: editor-facing semantic tooling only; it is not the evaluator and not the normative semantics layer.
- `tests/KatLang.Tests/`: parser, evaluator, elaboration, semantics, and integration regression coverage.
- `tutorial.md`, `KatLang.ebnf`, and generator prompt/agent files must stay aligned with real language behavior.

## Language Semantics And Design Rules

- Lean 4 wins over implementation convenience, performance, or stylistic preference.
- `lean/CoreArityAlgebra.lean` defines the algebra. `lean/CoreArityAlgebraProofs.lean` proves the small laws and executable checks. If either diverges from `lean/KatLang.lean`, fix the artifact or explicitly change the authoritative model first.
- If Lean is ambiguous for a requested behavior change, stop and clarify before implementing.
- Do not invent syntax or semantics that are not in Lean unless the task explicitly includes the Lean change.
- Do not add new operators, convenience syntax, implicit coercions, hidden fallbacks, or AST simplifications that erase Lean distinctions.
- Preserve structural distinctions in the AST and runtime model. In particular, `.dotCall` and `open` are language-level constructs, not incidental parser sugar.
- `Expr.SequenceConstruct` / `.sequenceConstruct` is an INTERNAL sequence-join node, not the AST representation of written parenthesized sequence values (those parse to `Expr.Capture` / `.capture` bundles; `()` to the empty-sequence node). Its evaluation drops `()` leaves, so routing surface syntax through it would violate visible-empty semantics — the parser must never produce it (guarded by `SequenceConstructContainmentTests`, CoreTests internal-node guards, and the semantic explorer's internal-node cases; see `docs/design/sequence-boundary-audit-2026-07.md` §7).
- OutputBundle split (Track A): brace algorithms parse to `Expr.AlgorithmExpr` / `.algorithmExpr` (algorithm identity: scope, parameters, properties, `open`, namespace interpretation), while surviving parenthesized groups parse to `Expr.Capture` / `.capture` over an `OutputBundle` (ordered written expression slots with NO lexical ownership — the receiver decides consumption). `Algorithm.User.Output` is an `OutputBundle`. CAPTURE IS NOT ALGORITHM IDENTITY: the algorithm channel sees only a zero-parameter output thunk over a capture's bundle, so grouping suppresses callable identity (`Apply((Increment))` stays an error), a capture receiver exposes no structural members (`(Obj).V` fails; `Obj.V` works), and a capture is NOT an openable target (`open (M)` is a targeted parse error — the evaluator's open resolution equally rejects capture targets with `BadOpenForm`, mirroring spread). ALGORITHMEXPR IDENTITY IS STRUCTURAL: every `Expr.AlgorithmExpr` provides its contained algorithm on the higher-order channel regardless of parameter/declaration/output count — `Call0({42})` invokes the brace algorithm exactly like the named zero-parameter `Call0(Const)` — while the value channel reifies written slots independently (builtin argument adapters keep the one-slot value boundary for zero-declaration blocks: `repeat(step, n, {1, 2})` still supplies ONE initial state slot). Value-context implicit lifting (`ProcessValueDemandingArgumentBundle`) is a consumer property: Math member arguments are registry-provably strict-value and lift like every ordinary value position, while ordinary call arguments stay neutral to preserve higher-order references. When such a strict-value position REFUSES to lift because the enclosing CLOSED explicit parameter list cannot supply the referenced callable's implicit parameters (`ClosedListBlocksLifting`), the front end DIAGNOSES it (`ReportBlockedStrictValueForwarding`, reusing `DiagnosticCode.UndeclaredIdentifier` — the same closed-list rule as a directly written undeclared identifier, one indirection out, and equally reachability-independent): the value is required, nothing later can supply it, so the program is rejected naming the reference and its missing parameters, never the consuming member or the consumer's own declared argument names. The blamed names come from `MissingClosedListForwardingNames`, the ONLY implementation of `CanBuildImplicitCallArgumentsFromExistingParameters`, so availability and blame cannot drift. The rule fires ONLY on that conjunction: positions the resolver never lifts in any caller (a capture, a Math call in a NEUTRAL argument slot, a dot-call receiver) are excluded because the closed list is not what blocks them, arbitrary user callees are never analyzed for strictness, and the strict-value flag is threaded beside `inCallPosition` WITHOUT becoming a memo key (it changes no rewrite). `Expr.Call.Args` is an `OutputBundle` and `Expr.DotCall.Args` an optional one (Track B): call/dot-call argument lists are ordered bundles of the ORIGINAL written argument expressions, evaluated transparently in the CALLER's lexical context — no transparent Args Algorithm exists anywhere in a parsed tree, and free names inside argument slots belong to the enclosing algorithm. `DotCall.Args = null` (no argument-list syntax, property-style access) stays distinct from an explicit empty list. There is NO transparent-vs-scoped Algorithm mode bit (Track C removed `IsParametrized` entirely): every `Algorithm.User` is a scope-owning algorithm, transparent syntax is carried structurally by OutputBundle-bearing nodes (`Capture`, `ListLiteral`, `Call.Args`, `DotCall.Args`), and the parser's two body contexts are the named entry points `ParseScopedAlgorithm` (braces/trailing-brace arguments; `ParseRootAlgorithm` shares the scoped lowering) and `ParseParenthesizedBodyParts` (groups and call argument lists, which lower to capture/bundle — or to one recovery `AlgorithmExpr` when illegal declarations were retained for recovery).
- Strict-value diagnostic OBSERVATION is independent of rewrite memoization: a per-region reference-identity visit set lets a shared node reached neutral-first and strict-later report exactly once without changing the `(node, inCallPosition)` rewrite key or output sharing. Diagnostic presence and multiplicity must not depend on host-DAG traversal order.
- Algorithm output is written as expression rows: every non-definition expression row in an algorithm body contributes to that algorithm's output, and output rows may be interleaved with property definitions. There is no output keyword; `Output` and `output` are ordinary identifiers.
- Delimiter model: `(...)` is sequence/expression grouping and call-argument syntax, `[...]` is list construction, and only `{...}` (and the root) creates an algorithm-level lexical scope. Algorithm-level declarations — `open`, property/clause definitions, deconstruction bindings — are parser-rejected inside parentheses with a targeted diagnostic pointing at `{ ... }`; brace blocks work in any expression position, including as call arguments, and their opens/local properties never leak into the surrounding scope. The parser may keep temporary Algorithm/Block structures for parenthesized sequences internally; the observable invariant is that no diagnostic-free parenthesized expression contains algorithm-level declarations. Recover unmatched root `)` / `}` tokens in the same scope, retaining later declarations and output for editor analysis; keep the parse erroneous and preserve nested delimiter ownership.
- BUILTIN CALLABLES ARE ORDINARY PRELUDE BINDINGS, and IDENTITY — never spelling, never arity — decides semantics (SYN-05). Lexical resolution selects exactly one callable without considering the argument count; the resolved callable then determines its signature and behavior: `resolve name -> select ONE identity -> assemble the ordinary argument supply -> bind against THAT signature -> invoke`. KatLang has no overloading by arity, so a nearer property or parameter named `if`, `count`, or `sum` shadows the prelude binding COMPLETELY — `if(x) = x + 1` makes `if(1, 2, 3)` an arity error against `if(x)`, never a fallback to builtin `if/3` — and a bound parameter may carry any callable under a builtin's name (`Apply(if, x) = if(x)`). There is NO reserved-name mechanism, in either engine: do not add `ReservedNameValidator`, a `BuiltinDescriptor.IsReservedName` flag, reserved-name tables, `ReservedName` diagnostics, or grammar productions excluding builtin names from binding identifiers. (`BuiltinRegistry`'s reserved-name check and `HostOperations.ReservedPreludeNames` are unrelated: they govern who may BUILD the prelude — a Math alias or a host operation may not collide with a builtin — not what source may declare.) Consequently NO layer may branch on a callee's written spelling: the parser is purely syntactic about calls (it never counts arguments from a callee name, so a wrong-arity builtin call is an ordinary evaluation-time `ArityMismatch` against the resolved signature, and is inert in an unevaluated property exactly like `count(1, 2, 3)`), and a builtin recognizer such as the loop optimizer's `if` planning may use the spelling only as a lookup KEY taken from registry metadata (`Evaluator.BuiltinDisplayName`) before confirming `Evaluator.ResolvesToBuiltinAlgorithm`. Lean already models exactly this — `preludeAlg` declares `if` with one ordinary `publicProp`, and `NameOwnership` treats the prelude as the outermost property level of the owner walk — so a spelling gate anywhere in C# is a divergence from the authoritative model. Builtin `if`'s ONE intrinsic behavior is its invocation (`if(condition, whenTrue, whenFalse)`: evaluate the condition, then only the selected branch); that laziness belongs to the resolved builtin, disappears when the name is shadowed, and never applies retroactively to a value the caller already built (`if(1, Risky*)` evaluates all of `Risky` under the ordinary `expression -> value -> supply` rule). A builtin VALUE slot demands its SELECTED argument through the ONE zero-argument value-demand law (C# `ZeroArgumentValueDemandRejection`/`ZeroArgumentValueDemandError`, Lean `zeroArgumentDemandError?` — the factored rejection half of the value-position `Param`/`Resolve`/block arms): a resolved parameterized algorithm is the ordinary arity rejection at the argument's reference and its body is never entered (`if(1, Inc, 0)` with `Inc(x) = x + 1` is "Property 'Inc' expects 1 parameter…", never `Unknown name: x`; a body that would not read its parameter is rejected all the same), a conditional is `ConditionalValueAccessError`, a written block `UnresolvedImplicitParams`; an UNSELECTED slot is never demanded; CALLBACK slots that supply arguments (`map`/`filter`/`reduce` steps, loop steps) never consult it; `reduce`'s initial accumulator keeps its dedicated hint but decides through the shared rejection law and retains the demanded family's name. Collection arguments and fixed VALUE/whole-number controls consult the same law after ordinary fixed-arity binding (`SequenceBuiltinValueDemandError` / `sequenceBuiltinValueDemandError?`); call-item and suffix preparation preserve the written source without demanding callback positions. Every builtin VALUE slot (`if` condition/branches, `while`/`repeat` initial state, the `repeat` count, `atoms`, `range` — `EvalResolvedArgumentCounted`, Lean `evalArgumentValueCounted` over `ResolvedArgumentAlgorithm.Source`/`source?`) and the ordinary-dot `.string` receiver (`EvalDotStringReceiverAlgOutput`) go through it; pinned by `LazySlotZeroArgumentDemandTests`, `CoreTests/ValueDemand.lean`, and the `lazy-slot-demand-*` `LanguageSpecCorpus` cases. Pinned by `BuiltinCallableIdentityTests`, `IfBuiltinArityPayloadTests`, the `builtin-callable-is-an-ordinary-prelude-binding` / `no-arity-based-callable-selection` / `if-*` `LanguageSpecCorpus` cases, and `CoreTests/NameOwnership.lean`. NOTE: `load` is NOT covered by this rule — it is still recognized by raw spelling (`AstHelpers.TryGetUnresolvedLoadArguments`) as a front-end/module directive; that asymmetry is deliberate-for-now and is not a licence to re-privilege a callable's spelling.
- Ownership-first lookup is fundamental. Keep lookup behavior aligned across evaluator, parser/front-end elaboration, parameter detection, and semantic tooling. The evaluator's two lookup spellings — `LookupLexical` (reached by a bare name in VALUE position, `X`; returns owner+binding for the zero-arg property cache) and `LookupLexicalResolvedAlgorithm` (reached from ALGORITHM position: a callee `X()` or a dot-call target `X.m`) — are ONE implementation since M8+M9: the algorithm spelling is the projection of the binding-carrying chain (mirroring Lean, where `lookupLexical` projects `lookupLexicalProperty`), so ownership-first, open dedup, ambiguity, scope-level precedence, and prelude fallback exist once per engine; `LookupTwinEquivalenceTests` keeps both spellings observable so an independent fast path cannot silently regrow. Beyond that there are TWO C# lookup implementations — the evaluator's chain and `ElaboratedScopeLookup` (shared by `ParameterDetector` and `Semantics/`) — and they must select the SAME declaration, not merely both resolve: the detector's verdict rewrites the program (an unresolvable name becomes an implicit parameter), so a front-end disagreement changes what the evaluator runs. `LookupCoherenceTests` pins that relation with unique per-declaration sentinels; the `open`/visibility family in `SemanticExplorerCases.lean` pins the Lean/C# side. Named `open` targets deduplicate first-occurrence-wins by `Evaluator.OpenExprName` (inline blocks get positional keys and never dedup), so `open A, A` is ONE provider, not an ambiguity — that rule lives in Lean `resolveAllOpens` and must be mirrored by BOTH C# implementations.
- The OWNER WALK is the front-end half of ownership-first, and `ElaboratedScopeLookup.SelectOwnedDeclaration` is its ONE implementation (Lean: `selectOwnedDeclaration` / `elaboratesToParameter`, stated beside `shouldTreatAsImplicitParam` because `ScopeCtx` carries properties but no parameters): search outward by owning scope over the two kinds of OWNED declaration — the parameter bindings a scope binds (written, inferred, or a branch body's pattern binders) and the properties it declares — and the first owner that declares the name decides, a parameter beating a property of the SAME owner in an invalid recovery tree. Properties matching parameters of the same or any enclosing lexical algorithm are declaration errors, checked by `ParameterPropertyCollisionValidator` after signature completion (Lean: `conflictingOwnedNames` / `validOwnedDeclarations`) — with ONE root exemption: the root program is never called, so its completed signature (names it could not resolve, or names forwarding lifted into it) is checked against the root's OWN declarations only and never blamed on a property nested in a deeper owner; such a name surfaces as the root's `UnresolvedImplicitParams` evaluation error at the reference (`Lib = { public Q = 1 }` beside the root row `Q + 1` is a missing `open Lib`/`Lib.Q`, not a conflict in `Lib`; pinned by `ParameterPropertyCollisionTests.RootPhantomParameter_*`). Consequences that must hold together: a captured ancestor parameter beats a property of any FARTHER owner (the root's and the prelude's alike, so `F(pi) = { pi + 1 }` binds the parameter), a nearer property beats an outer parameter only in invalid recovery source, the nearest of several enclosing parameters wins, and a direct reference and one from a nested body always agree. `open` and the prelude keep their SEPARATE later policy: opens are consulted only after the whole owner walk (`LookupLexicalPropertyMatches`), so an owned parameter beats an inner `open` exactly as an ancestor-owned property does, and the prelude participates only as the outermost property level. Ownership is NOT the promotion question — `IsBoundName` still stops promotion at any visible property or opened name, unchanged. The owner map is `ParameterOwnership` (name → owning level, nearest wins by construction; never a counted depth), threaded through detection beside the scope chain; the detector's parameter classification (`ShouldRewriteAsParam`) and receiver classification (`ResolveReceiverNameProvider`) must both go through the shared walk, and the editor's `ComputeVisibleSymbols` is its enumeration form. Pinned by `ParameterOwnershipTests`, `LookupCoherenceTests` (the `ownership.*` cases), and the `ownership-*` `LanguageSpecCorpus` cases.
- Complete owner signatures include later implicit forwarding captures. After lifting, `ParameterDetector.CompleteOwnership` reselects bindings using the existing owner walk while preserving inferred lists, pattern shapes, provenance, and Grace order. If a binding or deferred owner context changes, restore synthesized-call source origins and rebuild forwarding/closed-input diagnostics with signatures fixed before exposure; never turn an obsolete implicit call into a written call of the newly selected parameter. `OwnershipConformanceTests` connects real owner/binder identities to the independent hand-written Lean table in `CoreTests/NameOwnership.lean`; generated elaborated-AST evaluation alone is not classification conformance.
- `open Name` may target a lexically visible private head, but `open` only exposes public members. "Public" through `open` means public AND `PropertyExposure.Exported`: a local-only property (one whose value depends on an input only an enclosing owner's call binds — an ancestor-owned parameter, or the pattern binder of an enclosing conditional branch) is never exposed even when written `public`. Exposure is a fact about the VALUE, never about where the declaration is written: a declaration inside a conditional branch body is an ordinary declaration inside that branch (a self-contained branch-local library — declared, opened inline, or module-backed — is openable and dot-accessible by the branch body and every body nested in it), while its REACH is structural — a family exposes no structural members, so nothing declared in a branch is reachable by name from outside it (`F.Helper`, `open F.Helper`, sibling branches, the enclosing algorithm), refused with the family-level reason `LocalOnlyConditionalAlgorithm`, which classification never assigns. Structural dot access deliberately ignores `public` but not exposure, so `Lib.X` reaches a private self-contained `X` that `open Lib` would not.
- STATIC-OPEN OWNERSHIP (SYN-03 / F2): `open` is resolved statically — it never opens a runtime value, and there is no dynamic `open` — but lexical ownership still applies to the target's HEAD name (`Lib` in `open Lib` / `open Lib.Sub`), which parameter detection classifies through the ONE owner walk (`ElaboratedScopeLookup.SelectOwnedDeclaration`, called from `ParameterDetector.ClassifyOpenTargetHeads`) exactly like every other bare-name occurrence. If the nearest binding is a parameter — explicit, inferred, lifted, collecting, grouped, a branch binder, or any of these captured from an enclosing owner — that parameter owns the name; a parameter cannot be opened, so the head elaborates to `Expr.Param` (not an open form in either engine: `IsCoreOpenForm` / Lean `Expr.openForm?`, so evaluating any such tree yields `BadOpenForm`) and the front end reports `DiagnosticCode.OpenTargetIsParameter` at the head's span. It NEVER searches farther outward: adding or removing a farther same-named declaration (a root property, an enclosing property, an opened or module-provided member) changes neither the verdict nor the report, so `F(Lib) = { open Lib … }` is rejected with or without a root `Lib`. The rejected target provides no names (the same recovery rule as a rejected capture target), so the closed-list check and inference see nothing through it, and the editor classifies the head as the parameter reference it is (`OccurrenceKind.OpenTargetReference` with the parameter's declaration — never a farther property's). The never-called program root's phantom signature is NOT a callable binding for this decision (`ParameterOwnership.CallableBindings`, the F1 exemption): a nested `open Q` beside an unresolved root row `Q.X` stays a static lookup and evaluation reports the unresolved root input. Lean states the rule as `elaborateOpenHead` beside `elaboratesToParameter`; pinned by `StaticOpenOwnershipTests`, the `ownership-open-*` `LanguageSpecCorpus` cases, `LookupCoherenceTests.ownership.parameterOwnedOpenHeadResolvesToTheParameter`, and the F2 guards in `CoreTests/NameOwnership.lean`.
- `open` is a declaration/import directive, not an output expression: it takes ONE comma-separated target list (`open A, B, C`; string targets use single quotes — `open 'url', A`), parsed by a dedicated comma-list parser into individual targets (resolve, argumentless dot-call path, block, or string-load sugar). Each algorithm allows at most one `open` declaration. The first target must begin on the same physical line as `open` (`open` newline `A` is a missing-target error and `A` stays a separate row). Comma keeps its normal explicit line-continuation behavior — `open A,` newline `B` and `open A` newline `, B` both continue the list — and a leading `.` continues a dotted target (`open A` newline `.B` is `open A.B`), but a plain newline never continues `open`: `open Math` newline `Math.Pi` is an open plus a report row. `;` and a bare same-line second target are NOT open-target separators (`open A ; B` and `open A B` report a missing-comma diagnostic, never two targets). A spread-marked open target (`open A*`) parses to a spread expression and is rejected by open-form validation — spread is not an open form.
- `open 'url'` is front-end sugar for load elaboration, not a core AST construct.
- Dot-call uses structural lookup first and lexical fallback second, at EVERY level of a chain: a receiver that is itself an argumentless, non-`string` dot edge is NAVIGATED through its exported structural members before either channel of the outer edge is consulted (`resolveDotReceiver` / `ResolveDotReceiver`, the ONE receiver-position resolution shared by the sync evaluator, the async twin, and the sequence optimizer's shadow check), so `Lib.Sub.Q` reads `Sub`'s own `Q` before any lexical `Q(x)` and `A.B.C.D` traverses every level; a declared local-only or conditional-branch intermediate member is that edge's `LocalOnlyProperty` error, never a fallback (the established one-level accessibility rule; private members stay reachable); a receiver without the member, an argument-bearing edge (`Lib.Sub().Q`), and the `.string` intrinsic are values, so the chain continues by extension fallback (`3.A.B` is `B(A(3))`). Navigation is identity-only (no intermediate edge is evaluated) and the higher-order channel is untouched: `resolveAlg`/`ResolveAlg` still lifts every general argumentless dot expression to its zero-parameter wrapper identity. The front end mirrors the same rule through the ONE compositional static classification `AstHelpers.ResolveStaticStructuralMemberProvider` (detector receiver classification, editor dot-member resolution, and the scope-free dependency view; `StaticStructuralMemberProviderKind.KnownFailure` marks a statically failing intermediate edge, selection `Never`). Structural lookup, receiver injection, fallback order, and diagnostics must stay consistent across Lean and C#; pinned by `ChainedDotStructuralPrecedenceTests`, CoreTests `chained*`, and the `dot-chain-*` `LanguageSpecCorpus` cases.
- Grace `~` is a front-end parameter-order annotation on exactly one bare name occurrence (`~x` / `x~`), written DIRECTLY attached to that name (marker attachment law: `~ x` and `x ~` are `InvalidGraceMarker` attachment errors that recover to the plain name with no weight; `~~x` and `~x~` are attached runs); it is not a general expression operator, repeated markers on that occurrence use ordinary weight arithmetic, and elaboration strips it before evaluation.
- Grace composes with ordinary dot syntax: `a~.t(args)` is postfix Grace on the bare receiver occurrence followed by ordinary `.t`, while `a.~t(args)` is ordinary dot with prefix Grace on the participating fallback/member occurrence `t`. Base DotCall occurrence order is receiver, participating fallback, then arguments, so `a.t` infers `(a, t)` and both graced two-name forms infer `(t, a)` through the ONE general Grace reordering law. Postfix Grace on a compound receiver (including a second `~.` in a chain) rejects through the one-name eligibility rule; prefix member Grace remains eligible because it decorates the bare member occurrence. Parameter detection consumes Grace, all forms elaborate to the SAME ordinary structural-first `DotCall`, and Grace never changes executable selection.
- Implicit-parameter order follows first semantic source occurrence plus the ordinary Grace arithmetic. A DotCall contributes its receiver occurrences, then its member's stored lexical-fallback occurrence when fallback MAY be selected, then written argument occurrences; thus `K = a.t(b)` infers `(a, t, b)`, while the direct call `K = t(a)` independently infers `(t, a)`. Runtime fallback assembly as `t(a, b)` does not determine the enclosing signature order.
- A user call binds each parameter on the value channel, the algorithm channel, or both, and the callee then evaluates in the CALLER's environments extended with its own bindings — that inheritance is what lets a nested property read an ancestor-owned parameter and a nested call invoke an ancestor-owned callable. A BOUND PARAMETER OWNS ITS NAME ON EVERY CHANNEL: every binding site — user calls (flat fixed, patterned, item-supply/collecting), clause-family binders, sequence-builtin callbacks, and generic and planned loop steps, in both engines and in the async twin — shadows the callee's parameter names out of ALL THREE inherited tiers: the value environment (`ShadowValEnv` / Lean `ValEnv.shadow`), the counted callback-parameter environment (`ShadowCountedParamEnv` / `CountedParamEnv.shadow`), and the algorithm environment (`ShadowAlgEnv` / `AlgEnv.shadow`). The two context tiers are shadowed by ONE shared helper — C# `ShadowInheritedParameterEnvironments`, Lean `EvalCtx.bindParameters` — and a new binding path must go through it rather than filter one tier ad hoc. Consequences: a parameter bound ONLY on the algorithm channel (a higher-order argument, or any argument whose value evaluation failed) read in value position reaches its algorithm binding — the ordinary zero-argument value demand, its arity error, or the conditional value-access error — never a same-named caller value; and a parameter bound ONLY on the value channel read in call position (`f(2)`, the lexical dot-call fallback `2.f`, forwarding through `Pass(f)`) fails as not-callable exactly like the standalone program, never invoking a same-named caller callable. Lookup never falls through to a caller binding merely because the inner binding is unusable in the requested position — this is lexical name shadowing, not overload resolution across channels — while names the callee does not bind stay visible (`Inner(x) = f(x)` inside `Apply(f)` still calls the received `f`). Without this, a callee silently computed with an unrelated caller value or callable, and which caller parameter names collide with a callee's became observable.
- Ordinary lexical dot-call injects the receiver as ONE leading argument SEGMENT: `A.B(C, D)` allocates like `B(A, C, D)` — the receiver's item count never satisfies arity, fixed prefix/suffix parameters bind from the front and back first, and a FIXED parameter allocated the receiver segment binds its one captured value. The segment additionally carries its evaluated top-level supply, which exactly one consumer reads: a flat TOP-LEVEL collecting parameter allocated the segment consumes the supply items (one level, never recursive — exact lists stay opaque, nested/patterned collecting bindings are never fed the supply). A WRITTEN group/brace receiver supplies its raw row emission (`(1, 2, 3).Mean` with `Mean(*Vector)` binds `Vector = [1, 2, 3]`; `((1, 2)).Collect` keeps the extra written boundary; `().Collect` supplies zero items), while a NAMED property receiver evaluates at its value boundary and supplies one item (or zero for `()`). Receiver assembly never inspects the resolved callee and never pre-expands the receiver (`ParameterPatternInput.CollectingSegmentEmittedCount` / Lean `collectingSegmentCount?` is the ephemeral segment-supply carrier; it is data-only and never stored in environments, collected lists, or `Result`). Direct calls are unchanged: a written argument slot always reifies to ONE value, so `Mean((1, 2, 3))` still collects one grouped argument.
- Only sequence/variadic builtin dot-call paths may opt into receiver top-level expansion, and that expansion must remain explicit in builtin metadata/evaluator handling.

## Lean/C# Consistency Requirements

- `Parser.Parse(...)` and `ParseResult` are elaborated front-end outputs, not raw syntax trees.
- The raw syntax boundary is `Parser.ParseSyntax(...)`.
- `FrontEndPipeline.Process(...)` / `ProcessAsync(...)` are the explicit C# front-end paths for elaboration passes such as load elaboration, parameter detection, implicit argument resolution, and property exposure resolution.
- The individual elaboration passes are INTERNAL implementation stages (v0.8.187, M6): `ParameterDetector`, `ImplicitArgumentResolver`, `PropertyExposureResolver`, `FrontEndPipeline`, and `Parser.ParseSyntax` are not host API, and hosts must not be able to compose partial elaboration — a Detect→Resolve tree without exposure resolution leaves every `Property.Exposure` at the default `Exported`, which the evaluator trusts (pinned by `FrontEndElaborationBoundaryTests` and the non-friend `PublicElaborationSurfaceTests`). The supported public layers are `Parser.Parse`/`ParseAsync` and `KatLangEngine` (complete pipeline), `SemanticModelBuilder` over `ParseResult`, and `Evaluator.Run*` direct evaluation of host-built ASTs (as-is, preflight only, no elaboration). Do not re-publicize a stage or add a partial facade; exposure/ownership metadata is trustworthy only after the complete pipeline finishes. (`ModuleLoader` is internal too since v0.8.188 — load elaboration alone is even more incomplete: a loader-only tree has had no parameter detection, so spliced module functions cannot even bind their arguments; hosts get module loading through `Parser.ParseAsync`/`KatLangEngine.RunAsync` with `RunOptions.DownloadCode`/`AllowedHosts`.)
- Default parse/run entry points reject unresolved `load`; only elaboration-enabled paths may consume it. SOURCE LOADING IS ASYNC-ONLY: the one downloader contract is `RunOptions.DownloadCode : Func<string, CancellationToken, ValueTask<string>>` — and it is the ONLY transport: the library ships no default/ambient HTTP downloader (a `ModuleLoader` cannot be constructed without an explicit delegate; `AllowedHosts` governs load-target policy while transport behavior, redirects included, belongs to the host delegate; blank or null `AllowedHosts` entries must fail closed with `ArgumentException` at sync and async options boundaries; trim valid entries and keep loader matching fail-closed even below those boundaries) — module acquisition awaits it inside `ModuleLoader.ElaborateAsync` (an incomplete download genuinely suspends source processing and resumes it at the same point; the downloader is never replayed), and the elaboration-enabled entry points are the asynchronous ones (`KatLangEngine.RunAsync` + async conveniences, `Parser.ParseAsync(source, options)`). The synchronous source-level entry points remain for downloader-less configurations only and reject a downloader-configured options object with `InvalidOperationException` before parsing (enforced in the synchronous `FrontEndPipeline.Process(source, RunOptions?)`) — never a blocking sync-over-async bridge. Parsing and all other elaboration passes stay synchronous CPU work. ## Builtins And Spread Conventions

- `arity` means the structural count of top-level output slots.
- `count` means the number of evaluated top-level values after sequence values are opened by the consuming operation.
- Do not treat `arity` and `count` as interchangeable.
- Terminology: prefix `*` is the COLLECT MARKER; `*name` is a COLLECTING BINDING; in a callable declaration it forms a COLLECTING PARAMETER. Postfix `*` is the SPREAD MARKER; `value*` is a SPREAD EXPRESSION. Infix `*` multiplies. A callable with a collecting parameter may be DESCRIBED as variadic (it accepts a variable number of argument items), but "collecting parameter" is the canonical construct name — never "variadic parameter", "rest parameter", or "rest binding".
- A property/call/builtin RESULT boundary is a value boundary: it always returns ONE value, with emitted count `Result.valueCount` (0 for the empty sequence value, otherwise 1 — a list value always counts 1, including `[]`). A multi-output body/collection is observed by the caller as one sequence value; only an explicit caller-site spread (`expr*`) spreads it back into the surrounding item supply (spread reads the value via `spreadItems` — the spread view that also opens one list boundary — not the emitted count; `toItems` is the non-spread item view and keeps lists opaque). Redundant unary sequence structure is canonicalized during ordinary value construction, including `(())` and `((()))` to `()`. The shared helper is `reCountValueBoundary` (Lean) / `ReCountValueBoundary` (C#); it re-counts the value boundary without rebuilding the value and is applied at user/conditional calls (`evalUserCallCounted`, `evalConditionalCallCounted`) and structural dot zero-arg access (`evalDotCallCounted`). Collection-producing builtins (`order`, `orderDesc`, `distinct`, `take`, `skip`, `filter`, `map`, `range`, `atoms`) materialize ONE exact list value with count 1 via `makeCollectionListResult` / `MakeCollectionListResult` and need no re-count. Collecting bindings likewise store one exact list value with count 1 (`collectSegment` / `CollectSegment`) and need no re-count or raw-supply storage. Lexical zero-arg property access and `if` already re-counted this way; the reduce initial accumulator is likewise reified as one written accumulator slot (`reCountValueBoundary`) before reduction, so an empty reduction returns it as ONE value. NOT value boundaries (must keep their multi-item counts): root/body output accumulation (`evalAlgOutputCountedCore`), `while`/`repeat` multi-slot loop state, and the strict single-value `map`/`reduce` callback contract. Scalar/reduction builtins already return one value and are unchanged.
- Comma is the explicit expression-list separator, and on one physical line it is the ONLY separator (SYN-07A): whitespace never creates a slot boundary, so `1, 2, 3` is three slots while `1 2 3`, `F(1 2)`, `(1 2)`, `[1 2]`, `2(3)`, `A[1]`, `2m`, and `P = a b` are the targeted parse error `DiagnosticCode.UnseparatedSameLineItem` (public `KatLangErrorCode.UnseparatedSameLineItem`), reported at the first token of the second item with ONE generic message naming the three repairs (a comma between slots, an operator to continue the expression, a new line for a declaration) and never guessing intent. ONE ownership point decides slots — `Parser.StartsNextExpressionListSlot`, reached by every expression-list context through `ParseExpressionListOperand` — and the body loop's per-item row check decides declarations: `open`, property/clause definitions, deconstruction patterns, and `public …` must begin a physical line or follow the opening `{` directly (`1 P = 3`, `x = 3 y = 4`, `{ d = 2 n * d }` are the same error). Parameter-pattern lists (clause heads and nested sequence-value patterns) follow the same rule through their own ONE boundary decision — `Parser.StartsUnseparatedPatternItem`, reached through `ParsePatternItems`, over the atom grammar's starter set `CanStartPatternAtom` (a star counts only when an operand follows it — the SYN-07B classifier — so a star nothing can follow keeps its existing marker or closing-delimiter recovery) — reporting the SAME code with a pattern-worded message that names the comma as the only repair, and recovering the item as the next pattern of the SAME head: `F(a b) = a + b` recovers as `F(a, b) = a + b`, so the head's `)` and `=` are found where written and nothing leaks to the enclosing scope; a next-LINE pattern without a comma is NOT admitted (parameter lists have no newline separator) and keeps the ordinary closing-delimiter diagnostic. Recovery is a slot boundary, never a grammar hole: the second item stays the next slot of the SAME list (`P = a b` keeps `b` in P's body and leaks nothing to the enclosing scope; `F(1 2)` recovers as a two-argument call) or the declaration it spells, and recovery sites that already own a boundary (rejected Grace runs, detached markers, stray root closers, bad tokens, open-target leftovers, single-token primary recoveries) call `OwnSameLineItem` so the separator rule stays silent there — one diagnostic per malformed boundary. A newline is a separate mechanism — a body/statement/output boundary: at root output or inside an explicitly open context (`(`, `[`, `{`, an argument list) a newline between independent expressions separates slots (so `1`/`2`/`3` on three lines are three output slots and `F(` newline `1` newline `2` newline `)` is a two-argument call), but a simple one-line property body ends at the newline. Ordinary expression continuation is never a slot boundary: `F(1 -2)` is the one argument `1 - 2`. Root output consumes a bare expression list as output slots; call syntax consumes it as argument slots; parentheses materialize it as one sequence value. Parsing must not depend on callable arity, runtime values, inferred types, or any other semantic information. Pinned by `SameLineSeparatorTests` and the `same-line-*` `LanguageSpecCorpus` cases.
- Semicolon `;` is not supported as expression syntax. It is not an alternative separator or sequence constructor. The parser reports: "Semicolon is not supported as an expression separator. Use ',' between expressions on one line (a new line separates them where the context allows it), or parentheses for one sequence value." Use commas (or separate rows) for separate slots and parentheses for one sequence-valued slot, e.g. `sum((10, 20, 30))`, `take((1, 2, 3), 2)`, and row-like values as `Reports = (row1), (row2)`.
- Postfix continuations bind on the same physical line only. A `(` or `{` after a callable target on the same physical line is a call delimiter even across whitespace, while a physical newline never continues a closed expression into a call. For multiline calls, open the delimiter before the newline. Indexing `:`, postfix grace `~`, binary operators, and the postfix `*` spread marker are also same-physical-line only (a line-final `*`, spaced or not, is multiplication whose right operand continues on the next line whenever that line starts with an operand, and otherwise a spread marker that must be attached — SYN-07B and the marker attachment law, see the star rule below). A leading `.` is the supported method-chain continuation. Definition bodies and open target lists are line-bounded: a newline ends the body, so an expression on a following line — at any indentation — is a separate output row parsed by the surrounding output/algorithm context, never a body continuation. (A same-line comma, an already-open delimiter, a same-line binary operator, and a leading `.` still continue the body. Root output and algorithm/brace bodies, by contrast, keep the expression list open across newlines, so a newline there separates output slots.)
- The star `*` has three roles resolved purely syntactically: prefix COLLECT MARKER in binding patterns, postfix SPREAD MARKER on a completed expression, and infix multiplication — the marker surfaces match the semantic directions `collect : Supply -> ListValue` and `spread : Value -> Supply`. PREFIX `*name` is the ONLY collecting BINDING syntax, valid only in binding positions — explicit parameter lists (`F(*items)`, `F(first, *middle, last)`), nested sequence-value parameter patterns (`F((x, *y, z))`), and assignment deconstruction, including the single-target form `*items = RHS`. The collect marker must be DIRECTLY attached to its binding name (exact source-offset adjacency — no whitespace, comment, or newline between; `* items` is a targeted attachment error that never creates a collecting binding, and `**items` is a repeated-marker error), and exactly one marker forms a binding. Prefix `*` is NOT an expression operator: in expression position it reports a targeted collect-marker diagnostic and recovers to the following operand. The old spellings `name...`, `...name`, `spread(expr)`, and `expr.spread` are NOT KatLang syntax: there is no ellipsis token (`...` lexes as three dot tokens and fails through ordinary parsing) and `spread` is an ordinary identifier with no reserved meaning.
- The spread expression has ONE spelling: the postfix marker `expr*`, and its reading is LAYOUT-INDEPENDENT (SYN-07B): the NEXT significant token decides, never whitespace before the star, never source attachment, and never the physical newline after it. When a token that can begin a multiplication operand follows the star — on the same line or on a later one — the star is infix MULTIPLICATION (`a*b`, `a* b`, `a *b`, `a * b`, `a*` newline `b`, and `a *` newline `b` all multiply; the trailing star continues exactly like every trailing binary operator). The ONE exception is a following DECLARATION head (`Name = …`, `Name(pattern) = …`, a binding pattern, `open`, `public`, `~Name = …`), decided through the same declaration-starter relation the slot boundary uses (`Parser.StartsDeclarationAt`): a declaration head is never an operand, so `a*` newline `b = 1` is a spread row followed by a definition. The star is the SPREAD MARKER when the surrounding syntax closes the expression before any operand could follow: a comma, a closing `)`/`]`/`}`, end of input, a token that cannot start an expression (`.`, `;`, `==`, …), or a declaration head — so `F(A*)`, `[A*]`, `A*, B`, `A*,` newline `B`, and a program-final `A*` are all spreads. THE MARKER ATTACHMENT LAW is a SEPARATE, LATER check (`Parser.ParseSpreadMarkerContinuation`, after classification): every structural/annotation marker is directly attached to the syntax it modifies — collect `*name`, spread `name*`, Grace `~name` / `name~` — through the ONE attachment helper `Parser.IsDirectlyAttached` (exact source offsets; whitespace, comments, and newlines all break attachment), while ordinary operators may be spaced freely. A star classified as a spread marker but detached from its operand (`F(A *)`, `(A *)`, `A *` at end of input or before a declaration head) is the targeted parse error `DiagnosticCode.InvalidSpreadMarker` (public `KatLangErrorCode.InvalidSpreadMarker`), spanning the operand through the last star of the malformed run and recovering to the plain operand — never silently a spread, never silently a multiplication — so whitespace can only separate the valid `A*` from the rejected `A *`, never turn one valid operation into another. Likewise a detached Grace marker (`~ x`, `x ~`, `~ ~x`, `a.~ t`) is `InvalidGraceMarker` with the attachment message and recovers to the plain name with no weight, and a detached collect marker (`* items`) is the existing `InvalidCollectMarker` attachment error on every binding surface. Consequences: a spread ROW followed by another output row needs the trailing comma (`A*,` newline `B`; a bare `A*` newline `B` is `A * B`), and a DEFINITION body ending in a spread that an output row follows must be closed (`y = (A*)` capture parentheses, or `y = { A* }`), because the trailing star continues the line-bounded body across the newline like any trailing operator (`X = A*` newline `B` is `X = A * B`). The one line-dependent star is the `*`-LED LINE: a same-line star always belongs to the expression before it, so a collecting deconstruction `*r = …` starts its own line (`A* *r = 1, 2` on one line reads its second star as a further — detached — spread marker of `A` and is rejected by the attachment law). Do not put attachment or same-line-only lookahead back into the postfix star DECISION (`IsPostfixSpreadMarkerStar`), and do not add a heuristic attachment guard there (the newline-tolerant binding-pattern scan makes such guards misfire on `A*` newline `B = 5`); pinned by `StarSyntaxTests` (layout-independence section) and `MarkerAttachmentTests` (the whole marker table). The marker lowers at parse time to the ONE unary `Expr.SequenceSpread` node (Lean `sequenceSpread`) — never to a Call or DotCall — so there is a single evaluator path, no ordinary call/property value boundary is introduced, and the operand is evaluated exactly once. Chained spread is compositional: `value**` equals `(value*)*` — each extra written star spreads the value that the previous star's supply re-captures at the ordinary expression boundary (`spread` then `capture` then `spread`), so a multi-item supply is a fixed point (`[[1, 2], [3, 4]]**` supplies the two inner lists unchanged) and only a lone structured item opens one more boundary (`[[7]]**` supplies `7`); it is NEVER recursive flattening. `value**next`, `value** next`, and `value**` newline `next` are targeted errors — the second star is multiplication with a spread operand, never exponentiation. A spread expression is legal ONLY as a whole expression-list slot (root/body rows, call argument slots, group and list elements, definition body slots), as the operand of another spread, or as the FLUENT DOT-CHAIN receiver: `operand*.Member(...)` lowers at parse time to the ordinary LEXICAL call `Member(operand*, ...)` with the spread as the leading argument slot — the receiver is an item supply, not a value, so structural member lookup never applies (`x.Calculate*.Target` builds the same AST as `Target(x.Calculate*)`, and further postfix continuations chain on the call result). GROUPING THE SPREAD CHANGES THE RECEIVER, and the difference is the ordinary capture rule, not a star rule: `A*.F` keeps the spread a SUPPLY and lowers to the lexical call `F(A*)` (items become argument slots), while `(A*).F` is a CAPTURE receiver — ONE leading argument segment whose value is the captured sequence and whose raw supply is the spread items. The two coincide on a collecting callable — the fluent form through ordinary spread slots, the grouped form through the general segment rule (the allocated collector consumes the segment's supply; no callee inspection, no `(A*)`-spelling recognition) — but differ decisively at fixed arity: `A*.count` is an arity error (three argument slots) where `(A*).count` is 3, and at a fixed suffix beside a collector the grouped receiver stays one segment (`(A*).F` with `F(*mid, last)` binds `last` to the whole captured value) where the fluent form supplies separate slots. (`(A)*.F` is different again — that groups only the OPERAND, so it stays the fluent supply form.) Using a spread expression as a unary/binary operand or an indexing target/selector is a targeted parse error with unwrap recovery.
- Dotted-call equivalence is uniform through frontend elaboration: `a.F` is `F(a)`, and `A*.F` is `F(A*)`. This includes lexical resolution and implicit callable-parameter detection, so an unresolved `F` is inferred identically in both spellings; do not add fluent-call origin metadata or a spread-specific inference exception. Parenthesized `(A*).F` remains different because the parentheses make it an ordinary CAPTURE receiver — one leading segment through dot-call lookup (see the receiver-segment rule above), not a pre-lowered spread argument list.
- A spread expression spreads ONE item-producing boundary of the evaluated operand, contributing its items to the surrounding item supply — it does not create, return, or emit a sequence or list value by itself; the RECEIVER decides what the supplied items become (capture materializes a canonical sequence, a collecting binding collects an exact list, fixed bindings receive items individually, calls receive separate argument slots, root output emits rows). Sequence values and exact list values supply their contained items; other values follow the total item-view rule (an atom or string supplies itself as one item). A comma is REQUIRED between a spread and a following supplied item, on the same line or the next (`A*, B`, or the trailing `A*,` newline `B`), because `A* B` and `A*` newline `B` are both the multiplication `A * B`; only a declaration head, a closing delimiter, or end of input may follow a spread without a comma. `A* ; B` is invalid semicolon syntax.
- Call argument-slot assembly is SHARED by every callable shape — flat fixed, flat/mixed variadic, patterned (repeated-name / sequence-value patterns), and multi-clause conditional (`BuildCallArgumentInputs` in C#, `collectVariadicCallItems` in Lean): each written slot is evaluated EXACTLY ONCE, left to right; every non-spread slot is reified as exactly ONE argument value; and every explicit spread slot spreads exactly one value boundary into ordinary argument slots BEFORE any arity checking, clause selection, or pattern binding. When a patterned callee needs both the combined value of a `Capture` or zero-parameter `AlgorithmExpr` and its explicit written-slot view, BOTH are captured from the same prepared output evaluation (`PreparedAlgorithmOutput` / `evalAlgOutputPreparedCore` or the corresponding capture evaluator) — never by evaluating again or decomposing the combined value. Caller-side spread therefore has identical meaning for every callee representation: `F(A*)` supplies A's spread items as slots whether `F` is flat, patterned, or a clause family (clause selection happens after spreading, so a literal clause such as `F(0, 0)` can win on a spread `(0, 0)` and a one-argument catch-all can never absorb a spread pair). WRITTEN-SLOT REIFICATION is the same rule at every syntax form whose grammar defines one value per written slot — list-literal elements, written sequence-value pattern argument items (`evalExplicitSequenceValueExprSlots` / `EvalExplicitSequenceValueExprSlots`), and the reduce initial accumulator (reified via `reCountValueBoundary` before reduction): a non-spread expression whose counted supply emitted several items (an index projection, a loop result, a counted callback parameter) still contributes ONE value (`S = ((1, 2), (3, 4))` makes `[S:0, 5]` the list `[(1, 2), 5]`; only `[(S:0)*, 5]` splices). Root/body output rows and loop step outputs are NOT written value slots — they keep their multi-item emission semantics (with one documented receiver-specific exception: a sequence-value-PATTERNED loop step's output keeps a top-level spread expression as ONE packed next-state slot, preserving structured state boundaries in both directions — see the loop-step notes in `tutorial.md` and `docs/design/sequence-boundary-audit-2026-07.md`).
- Square brackets construct EXACT immutable list values (`Result.listValue` / `Expr.ListLiteral`), a second collection kind beside sequence values: no singleton/empty canonicalization ever applies to list structure (`[7] != 7`, `[] != ()`), while parentheses around a list stay redundant sequence grouping (`([1, 2]) == [1, 2]`). `[` always begins a NEW expression (never a call/indexing delimiter; `A[1]` is a second same-line item after `A` and is the SYN-07A separator error, while `A, [1]` is the two-slot list), and bracket content is a pure expression list (spread elements insert their item supply; declarations are illegal inside brackets). Spread uses `Result.spreadItems` / `SpreadItems` (opens one sequence OR list boundary). Indexing `:` opens its TARGET through the projection view `Result.projectionItems` / `ProjectionItems` (`[1, 2, 3]:0` is 1 under the same zero-based index rules as sequence selection), while a selected list ELEMENT is returned exactly as stored — one opaque list (`[[1, 2], [3, 4]]:0` is `[1, 2]`; chaining selects one level at a time). Every other NON-spread consumer keeps lists opaque via `toItems` (a list is one item for value boundaries and call binding — calls never open lists implicitly). Deconstruction's `Result.structureItems?` / `StructureItems` opens a lone sequence OR lone list (`x, y, z = [1, 2, 3]`); collecting bindings collect exact lists (see the collecting-binding rule below). The post-binding builtin collection view opens a BOUND list exactly like a bound sequence value (`count([1, 2, 3])` is 3, `A.take(1)` works on a list property; the opening is never recursive — a nested list stays one opaque item; spread supplies ordinary argument slots, so `count([1, 2, 3]*)` is an arity error under the fixed `count(collection)` signature). The `atoms` builtin recursively collects numeric atoms through BOTH sequence and list boundaries (depth-first, left to right; strings contribute none) via its own dedicated collector `Result.languageAtoms` / `LanguageAtoms` and materializes them as ONE exact list through `makeCollectionListResult` (`atoms(7)` is `[7]`, `atoms([1, [2]])` is `[1, 2]`, `atoms('text')` is `[]` — the result kind never depends on the input). Truth testing is deliberately SEPARATE: `truthValue?`/`TruthValue` reads the sequence-only `Result.atoms`/`ToAtoms` view, so lists still have no truth value (`if([1], a, b)` stays invalid) and the atoms traversal can never leak into `if`. Multi-clause conditional sequence-value patterns still match sequence values only (list patterns are deferred, so a list argument takes the fallback clause — except a SINGLETON pattern `(x)`, which matches any one argument whole via the scalar one-item rule, binding `x` to the entire list). Host-boundary flattening (`runFlat` / `Result.hostAtoms`, C# `RunFlat`/`EvaluateToAtoms` via `ToHostAtoms`) opens list boundaries; the truth-testing `Result.atoms`/`toItems` views stay list-opaque. Receiver theorems: `receivers_agree_outside_lone_structure` / `receivers_never_same_on_lone_structure` (unified over both structure kinds via the `loneStructure` predicate, with per-kind corollaries `receivers_never_agree_on_lone_seq` / `receivers_never_agree_on_lone_list` and the concrete `lone_collecting_disagrees_on_lone_list`) in `lean/CoreArityAlgebraProofs.lean`; list-side receiver behavior over the real model is proven by the list bridge laws in `lean/KatLangArityLaws.lean` (e.g. `deconstruct_fixed_single_list_opens`, `lone_collecting_list_call_and_deconstruct_differ`). The CoreArityAlgebra paper artifact now models `Val.list` and `collect` (the pre-list sequence-only extraction is preserved at the pinned paper tag).
- A spread expression is one whole expression-list slot. Commas separate same-line slots; after a spread, the comma is also required across a newline when another operand follows: `f(A*, B)` supplies A's spread items and then `B` as separate slots — the comma is required, because `f(A* B)` is the one-argument multiplication `f(A * B)`. To make one sequence-value argument containing a spread plus another value, write `f((A*, B))`.
- Collecting binding COLLECTS an exact immutable list. The three item-supply operations are distinguished by receiver purpose: `capture : Supply -> Value` (ordinary value/output capture — the canonicalizing `Result.normalize` boundary), `collect : Supply -> ListValue` (collecting binding / collecting parameter — `collectSegment` in Lean, `CollectSegment` in C#), and `spread : Value -> Supply` (the spread marker — `spreadItems`). Every collecting binding — single collecting parameters, mixed prefix/collecting/suffix parameter lists, and deconstruction collecting bindings — materializes exactly the assigned item slots as ONE exact list with emitted count 1: zero slots form `[]`, one slot forms `[item]` (NEVER erased, so one remaining structured row stays distinguishable from the row's elements), many form `[a, b, ...]`. Ordinary capture is unchanged (`x = 1, 2, 3` is `(1, 2, 3)`).
- A user-defined top-level collecting parameter collects the argument slots that were actually supplied to the call. `Name(*values) = body` binds `values` to the collected list; a plain `Name(A)` supplies one argument (`values = [A]`), while `Name(A*)` explicitly spreads `A` first (`values` collects A's spread items). The old single-collecting grouped/spread display coincidence is intentionally GONE: `F(A)` and `F(A*)` are observably different for every sequence-valued, list-valued, and empty argument (`F(())` collects `[()]` vs `F(()*)` collecting `[]`). For a scalar atom or string argument the two calls coincide — spread is total, so `7*` supplies `7` itself. `Name()` collects `[]`. A lone `*values` is the degenerate lone-collecting-binding case of this model. Forwarding is ordinary list spread — `Forward(*items) = Target(items*)` (equally the fluent `items*.Target`) re-supplies exactly the collected items (`spread(collect(xs)) = xs`), and passing the collected list unspread passes one list argument; there is no hidden raw-supply metadata, no `variadicSupplyEnv`/`VariadicStreamEnv`, and no provenance tracking. The front-end implicit-argument resolver synthesizes collecting-parameter forwarding as explicit spread arguments for the same reason.
- A parameter list with two or more captures that contains one collecting parameter binds the supplied function-call argument stream: fixed captures bind from the front and back, and the single movable collecting parameter collects the matched middle arguments (possibly zero) as one exact list; a plain function call does not implicitly open a single sequence or list argument. Assignment deconstruction, by contrast, is an unpacking receiver (Python-style): `x, *y, z = RHS` opens one lone sequence- or list-valued shared right-hand-side value and matches its items element-by-element, so `x, y, z = A` splits a stored sequence value or exact list value `A`. A written spread RHS is first captured into that shared value; it usually presents the same immediate items, but a singleton list whose lone element is itself a sequence or list can open one level further after singleton capture (for example, bare `x, y = [(1, 2)]` fails while `x, y = [(1, 2)]*` succeeds). The collecting target then collects its middle items into an exact list by the same rule (`x, *rest = [1, 2, 3]` binds `rest = [2, 3]`; `x, *rest = 1` binds `rest = []`). This unpacking is deconstruction-specific and does NOT change function calls — `F(A)` still passes `A` as one argument and needs `F(A*)` to spread it. The shared front/collecting/back matcher is `bindParameterPatternList` (Lean) / `BindParameterPatternList` in C#); every collecting-binding materialization funnels through `collectSegment` (Lean) / `CollectSegment` (C#) — the plain and counted pattern binders plus the flat-collecting loop path all call it, always producing one exact list with emitted count 1. Item-supply call routing is `Algorithm.usesItemSupplyBinding` / `IsDeconstructionUserCallShape`. Assignment deconstruction is parser-elaborated so the right-hand side is evaluated once into a shared property and each target binds through an inline sequence-value parameter pattern (`SequenceValueParameterPattern`) that opens that single shared value. The right-hand side is WRITTEN as an expression of the enclosing body and the front end elaborates it that way (`Algorithm.User.IsAssignmentDeconstructionSource`): its free names are the enclosing algorithm's implicit parameters (ordered by first written occurrence together with that body's rows, and read back through the inherited value environment), its bare sibling references lift in the enclosing algorithm's context, it obeys the enclosing closed-input rule (an undeclared name in a right-hand side under an explicit parameter list or a branch pattern is a front-end error), and the hoisted source never acquires parameters of its own — it stays the zero-parameter property the shared bind evaluates once, and its synthetic name never appears in a diagnostic (a body `a, b = x, 10` makes `x` a parameter of the enclosing algorithm, exactly as a written row `x + 10` would). The same `(x, *y, z)` sequence-value parameter pattern opens one received value for parameter/callback-position destructuring. Flat callbacks with a top-level collecting parameter bind through the shared binder too (`bindCountedCallbackParameterPatternList` / `BindCountedCallbackParameterPatternList`): a single-collecting callback keeps each iterated element as ONE collected slot (`[7].map(Collect)` binds `items = [7]`; `[(1, 2)].map(Collect)` binds `items = [(1, 2)]`), while a multi-parameter flat callee first opens a lone SEQUENCE-valued element into row slots (the flat-callback row convention; exact-LIST elements stay opaque and arity-error in flat binding — the nested `F((x, *y, z))` pattern form is the tool that opens BOTH kinds) and then allocates prefix/collecting/suffix (`Rows.map(F)` with `F(x, *y, z)` on sequence row `(1, 2, 3, 4)` binds `y = [2, 3]`, agreeing with the nested form on sequence rows only). Only the sequence-value pattern's scalar-element fallback stays strict (callback deconstruction for scalar elements deferred). The front-end implicit-argument resolver synthesizes forwarding spread only when BOTH the destination capture is collecting AND the source binding of that name is a collecting binding: `Use(items) = Target` with collecting `Target(*items)` elaborates to `Target(items)` (one argument; `Use([1, 2])` is `[[1, 2]]`), a caller collecting parameter `Use(*items) = Target` (collecting `Target`) elaborates to `Target(items*)`, and a collected-list source forwarded into a FIXED destination parameter passes the collected list as one argument (a fixed destination never re-spreads the list).
- Ordinary lexical dot-call injects the receiver as one leading argument segment (the receiver-segment rule above): allocation matches `B(A, C, D)`, a fixed parameter binds the receiver as one value, and only a flat top-level collecting parameter allocated the segment consumes its supply. For collection builtins the receiver fills the fixed `collection` parameter (`A.take(2)` is `take(A, 2)`, `A.count` is `count(A)`), with no builtin-specific receiver placement.
- Collection builtins are ordinary FIXED-ARITY callables that receive exactly ONE fixed `collection` parameter followed by fixed control parameters: `count(collection)`, `sum(collection)`, `first/last/min/max/avg/order/orderDesc/distinct(collection)`, `take/skip(collection, count)`, `contains(collection, item)`, `map(collection, mapper)`, `filter(collection, predicate)`, `reduce(collection, reducer, initial)`. An unspread sequence or list value is ONE argument at this call boundary like at every other call boundary, and NOTHING is opened before binding — `count(1, 2, 3)`, `count()`, `sum(A*, B*)`, `take((1, 2, 3))` (missing count), `take([1, 2, 3]*, 2)`, and `distinct((), ())` are ordinary arity errors (spread only supplies ordinary argument slots that obey the same fixed arity; re-group to pass spread items as one collection: `sum((A*, B*))`). The bound collection value is interpreted through the POST-BINDING one-level collection view (`builtinCollectionItems` / `BuiltinCollectionItems`): a lone sequence OR exact list opens one outer boundary and any other value is a one-element collection — `count((1, 2, 3))`, `count([1, 2, 3])`, and `Values.count` are 3, `count(7)` is 1, `count(())`/`count([])` are 0, and opening is never recursive (`count((1, [2], 3))` is 3, `count(([], []))` is 2). Item shape/empty policies apply to the viewed items (`sum` numeric constraint, `first` non-empty). Collection-producing builtins (`filter`, `map`, `order`, `orderDesc`, `distinct`, `take`, `skip`, `range`) materialize their kept/projected items as ONE exact immutable list via `makeCollectionListResult` / `MakeCollectionListResult`: zero items form `[]`, a single kept item forms `[item]` (never erased, so `take(((1, 2), (3, 4)), 1)` is `[(1, 2)]` and `distinct(((), ()))` is `[()]`), and nested sequence/list elements stay exact — the result kind never depends on the input kind, and only an explicit `spread` re-spreads the list into the arity layer. Canonical arity capture (`combineOutputSlots`, ordinary construction) and spread are UNCHANGED by this model, and collecting binding produces the SAME exact-list kind (`collectSegment`) — collecting parameters remain a general arity mechanism for user functions, and passing a collected list to a builtin unspread passes it as the one collection argument (`Qmean(*args) = args.sum / args.count` works because the post-binding collection view opens the bound list; `map(values*, f)` inside a body is an arity error — write `map(values, f)`). Callback/builtin execution stays a separate runtime-owned phase after binding.
- Sequence builtins and spread behavior must stay consistent across Lean and C#.
- Changes to builtins, preludes, intrinsic metadata, or sequence syntax require synchronized updates in evaluator, front-end assumptions, semantics, tests, tutorial, EBNF, and generator guidance.

## Editor Semantics
- `src/KatLang/Semantics/` derives editor-facing meaning from parsed and elaborated ASTs.
- Build semantic models from `Parser.Parse(...)` / `ParseResult`, not from raw syntax.
- Only source-backed identifiers may produce semantic sites, resolutions, declarations, or spans.
- Synthetic constructs must not invent source spans.
- If editor-visible behavior changes, update `src/KatLang/Semantics/` and `tests/KatLang.Tests/SemanticModelTests.cs` together.
- Preserve exact source-span invariants for hover, references, go-to-definition, classification, and callable-property metadata.
- Scope visibility is completion's semantic source: `SemanticModel.ScopeVisibilities` / `GetVisibleSymbolsAt` and `PreludeCatalog` must enumerate exactly what ownership-first lookup resolves — same shadowing, open dedup, same-level open ambiguity suppression, and direct-beats-open prelude precedence as `ElaboratedScopeLookup`. Scope regions are source-span hulls. MODULE PROVENANCE: a load-elaborated module subtree (`Algorithm.User.IsModuleElaborated`, set by `ModuleLoader` on the spliced root) is module-provided at EVERY nesting depth — nested algorithms, clause families, inline open-target blocks, and modules the module opens included — because its spans belong to the module's source text, so the semantic model emits NO document-owned sites for it (no scope regions, declaration occurrences, reference sites, or identifier-classification sites; every site the model lists slices the current document to the identifier written there) while still building its scopes and symbols for binding. A document reference to an imported member classifies normally (`PropertyReference`, `OpenTarget`) with a LOCATIONLESS target: `ResolvedDeclaration`, `PropertyInfo.Declaration`, parameter spans, clause-head spans, and `VisibleSymbol.Declaration` are null (the existing no-local-location convention — never a fabricated or module-relative span), and the imported `PropertyInfo` enters `PropertyInfos` only through such a document site. Provenance is STRUCTURAL, decided per owner before the walk (`ModuleProvidedAlgorithmCollector`): lookups create property symbols lazily and a body analyzed before `M = load('url')` can reach a nested module algorithm through `open M.Sub` before the walk enters the module, so the walk position alone cannot classify an owner; the region stack's inherited suppression is that set's walk-time projection and gates every site the walk creates. Host-built DAGs may share module source anchors under document-owned parents: `ModuleProvidedAlgorithmCollector` also records those spans by REFERENCE IDENTITY, and every site/metadata factory filters them (equal coordinates from distinct sources stay independent). A local property reusing an imported body keeps its own declaration but no imported parameter spans; locationless real symbols still participate in direct lookup/completion precedence. Suppression follows module provenance, never the mere presence of an `open`: document-owned inline `open { ... }` blocks, ordinary nested algorithms, and local content after an imported open keep every site (private members included), imported public names stay visible through the open, private ones never leak, and deferred module regions (B2c, below) are unaffected. Cross-file navigation into module text is not provided. Builtin names/signatures for editors come from `PreludeCatalog`, never hardcoded lists. Inside a deferred module region (B2c) the semantic model performs NO module I/O and never asserts that a module-supplied name is invalid: a name that resolves nowhere lexically under a deferred module open, a member of an unmaterialized `X = load('url')` placeholder, and an implicit parameter a nested body inferred provisionally there classify `IdentifierClassification.DeferredModuleReference` (indeterminate until the branch is selected), while names outside that lookup chain, ambiguous opens, open heads, explicit parameters, and binders keep their ordinary classification.

untracked state and fails if validation changes it; a developer checkout may
already be dirty, but validation must leave it exactly as it started.

The .NET phase runs the FULL solution build (every project — `dotnet test` alone builds only test projects and their dependencies, so benchmark/demo compile breaks escape it), the C# test suite, and `git diff --check`.

Manual .NET fallback:

```powershell
dotnet build .\KatLang.slnx -p:UseSharedCompilation=false
dotnet test .\KatLang.slnx -p:UseSharedCompilation=false --no-build
git diff --check
```

Manual Lean fallback, only when `.lean` files changed (all seven targets):

```powershell

lake build KatLangArityLaws
lake build AstDemo
lake build CoreArityAlgebra
lake build CoreArityAlgebraProofs

Pop-Location
```

Lean CoreTests now use `#guard` for semantic assertions, so a failing assertion fails `lake build CoreTests`. Remaining `#eval` lines are demo/inspection output only.

`validate-all.ps1` is a VERIFICATION command and is observational: before it builds or tests anything it removes every `KATLANG_REGENERATE_*` environment variable from its own process (the whole prefix, case-insensitively; the original values are restored on exit), so a regeneration flag inherited from the calling shell can never make a green validation run rewrite a tracked generated artifact. Regenerating a generated artifact (`lean/LanguageSpecCases.lean`, `lean/SemanticExplorerCases.lean`, the generator prompt blocks, `tests/KatLang.Formatting.PublicApi.Tests/PublicApiBaseline.txt`) is always a separate, targeted `dotnet test` run with that artifact's flag set to `1`; the run WRITES the artifact and then FAILS BY DESIGN (also when the content did not change), so it can never be mistaken for a verification — review the diff, clear the flag, and rerun the normal verification. The flag registry and the write-then-fail contract are `RegenerationFlags` / `ArtifactRegeneration` in `tests/KatLang.Tests/Infrastructure/ArtifactRegeneration.cs` (shared as source with the public-API test project); a new `KATLANG_REGENERATE_*` variable must be registered there — `ArtifactRegenerationPolicyTests` scans the repository for unregistered names and for tests that read a flag outside the helper.

## Continuous Integration And Releases

- `.github/workflows/validate.yml` is automatic for pull requests and pushes to
  `main`, and can also be dispatched manually. Its stable required-check names
  are `.NET validation` and `Lean validation`; both invoke the phase boundary
  above rather than duplicating commands in YAML.
- `.github/workflows/release.yml` is manual-only. Dispatch it from `main` with
  the version already present in `KatLangVersion.props`. A push, merge, or tag
  never publishes a release automatically.
- The release workflow validates the exact dispatched commit, builds and runs
  the NativeAOT CLI on native Windows/Linux/macOS x64 and ARM64 runners,
  packages the tested executable with the root `LICENSE`, `NOTICE`, and
  `PATENTS` files plus the exact restored RID-specific .NET runtime pack's MIT
  license and third-party notices, collects all six archives, produces
  `SHA256SUMS`, and only then creates the tag and publishes the GitHub Release.
  Runtime/ILCompiler pack identities and versions come from the publish output's
  `project.assets.json`, never from the machine-wide SDK root. The shipped
  projects currently have no external `PackageReference`; adding one requires
  explicit release-notice review and an update to the pinned CI policy. Unix
  archives store the CLI as mode `0755` and every text document as mode `0644`.
- `KatLangVersion.props` remains authoritative. Workflow code must never pass
  an MSBuild version override, create/move an existing version tag, or replace
  an existing release.
- Normal jobs have `contents: read`. Only the final publication job has
  `contents: write`; workflows use no user-managed secrets. External actions
  are pinned to immutable commit SHAs and `.github/dependabot.yml` proposes
  reviewable GitHub Actions pin updates.

`lean/SemanticExplorerCases.lean` is a GENERATED Lean/C# differential corpus — do not edit it by hand. A failing `#guard` there is a Lean/C# divergence (or a Lean-internal plain/counted evaluator mismatch) on that case. After an intentional semantics change, regenerate it with `$env:KATLANG_REGENERATE_SEMANTIC_EXPLORER = "1"; dotnet test .\KatLang.slnx --filter SemanticExplorerLeanArtifact` (writes, then fails by design), review the diff, and run Lean validation only if `.lean` files changed. See `docs/design/sequence-boundary-audit-2026-07.md`.

## Public API Baseline And Release Version

- `tests/KatLang.Formatting.PublicApi.Tests/PublicApiBaseline.txt` is the checked-in, deterministic rendering of the COMPILED public surface of the `KatLang` assembly — the one assembly the NuGet package ships — reflected by `PublicApiSurfaceRenderer` in that deliberately non-friend test project: every exported type plus consumer-reachable protected nested types, with base/interfaces, generics and constraints; every consumer-visible member with parameter names, modifiers, defaults, nullable annotations and nullable-flow attributes; and every public enum member with its exact numeric value. `PublicApiBaselineTests` compares exactly and never rewrites; a difference is a NuGet surface change. Record an intentional change with `$env:KATLANG_REGENERATE_PUBLIC_API = "1"; dotnet test .\KatLang.slnx --filter PublicApiBaseline` (writes, then fails by design), review the diff as the compatibility review, clear the flag, rerun. Regenerating the baseline never changes the release version; the focused hand-written contracts in that project (`PublicElaborationSurfaceTests`, `PublicFormatterExtensionTests`) stay beside it.
- `KatLangVersion.props` is the ONE place the release version is written. `src/KatLang/KatLang.csproj` (package and assembly version), `src/KatLang.CLI/KatLang.CLI.csproj` (which builds against the KatLang PROJECT, so it cannot lag onto a previously published package) and `tests/KatLang.CLI.Tests` (which bakes the value in as `IntendedKatLangVersion` assembly metadata — build intent, never read from the KatLang assembly under test) derive from it. `ReleaseVersionSourceTests` rejects any other version literal in an MSBuild file and any in-repository `PackageReference` to KatLang; the CLI version tests compare the loaded runtime, the CLI assembly and `--version` against the intended metadata, so a stale or mismatched artifact fails rather than passing against itself.

## Executable Language Specification

- `tests/KatLang.Tests/LanguageSpec/LanguageSpecCorpus.cs` is the canonical executable specification: named cases with stable IDs and HAND-WRITTEN canonical expectations. Never regenerate its expectations from observed behavior — a failing `LanguageSpec*` test means either fix the implementation or edit the canonical case in a reviewed diff.
- Same-program fidelity (M11): the Lean program of every Lean-comparable case in BOTH differential corpora (`LanguageSpecCorpus` and `SemanticExplorerCorpus`, internal-node cases included) is DERIVED from the source's real elaborated AST through `tests/KatLang.Tests/LeanAstEncoder.cs` — never authored by hand and never rebuilt by test-side parser-rule templates. C#-only cases carry an explicit non-blank `LeanExclusionReason`, a hand-authored LanguageSpec Lean program requires the exceptional `LeanProgramOverride` + `LeanOverrideReason` (currently unused), and per-corpus exact-ID exclusions plus `FidelityRatchet_*` tests pin the derived-case partitions. The encoder is FAIL-LOUD: extend it deliberately (with reviewed goldens in `LeanAstEncoderTests`) rather than approximating, and expected strings in encoder tests are manually reviewed constants. See `docs/design/executable-language-spec.md` §5.
- GENERATED from it (do not edit by hand): `lean/LanguageSpecCases.lean` and the `=== BEGIN GENERATED: katlang-spec-examples ===` block in `.github/agents/katlang-generator.agent.md` and `experimental/prompts/katlang-generator.txt`. Regenerate all three with `$env:KATLANG_REGENERATE_LANGUAGE_SPEC = "1"; dotnet test .\KatLang.slnx --filter LanguageSpecArtifacts` (writes, then fails by design), review the diff, and run Lean validation only if `.lean` files changed.
- Tutorial examples marked `<!-- spec:case-id -->` are verified against the corpus (source and expected output) by `TutorialSpecTests`; when changing a linked example, update the canonical case and the tutorial together.
- EVERY tutorial fence followed by a `**Result(s):**` claim is executable documentation (M13): `TutorialResultSweepTests` runs it through `KatLangEngine.Run` and display-matches the claim — no marker needed, so an ordinary new example enters the sweep automatically. A genuinely non-standalone example (e.g. one needing a network downloader) carries `<!-- spec:skip nonblank reason -->` before the fence; the skip inventory is exact-pinned, and result-bearing coverage is monotonic (pinned minimum baseline — removing an existing claim requires a reviewed ratchet reduction, while additions need no pin edit). The shared grammar lives in `TutorialCorpus` and fails loudly on malformed/detached claims, so a result claim can never silently drop out of verification.
- When language behavior intentionally changes, update the affected canonical cases in the same task as the Lean/C#/tutorial/generator changes.
- Maintainer guide: `docs/design/executable-language-spec.md` (partitions, counts, how to add cases, worked example).

## Lean/C# Semantic Alignment

Before editing, classify the change using `src/KatLang/SEMANTIC-ALIGNMENT.md`.

- Observable semantics require Lean consideration and usually Lean updates/parity tests.
- C# implementation/tooling-only changes require C# tests; Lean updates are not required.
- Optimization-only changes do not change Lean, but require equivalence tests against the generic path.
- Diagnostic wording-only changes do not require Lean if the structured error kind/payload is unchanged.
- Numeric changes split by tier (the manifest's "Core numeric semantics" row): Lean-modeled laws on the common exact integer subdomain (exact integer arithmetic/comparison, the representative truncating `div`/`mod` cases, the zero-divisor rule where applicable, `0 ^ negative-int`, structural equality, truth testing) change Lean and C# together with Lean-comparable LanguageSpec coverage. Decimal128-specific behavior (finite precision/range even for integral inputs, fractional values and quantum, NaN, ±Infinity, signed zero, overflow to infinity, gradual underflow, IEEE ordering of specials, non-exact `/`/`avg` results) is an explicit reviewed model divergence — C# tests plus a canonical C#-only LanguageSpec case with a `LeanExclusionReason`, never a fabricated Lean encoding. Do not classify from source spelling alone: "integer input" is not sufficient once a Decimal128 operation rounds or overflows.
- Grammar or AST changes usually require Lean review.

If in doubt, the manifest's "Lean update required?" column is authoritative. If Lean is silent or ambiguous, stop and ask.

## Do Not

- Do not silently change language semantics.
- Do not let Lean and C# diverge.
- Do not treat `AGENTS.md` as a long design essay.
- Do not let multiple agent-instruction files drift into conflicting guidance.
- Do not add convenience syntax, hidden fallbacks, or duplicated semantic logic just to make a local change easier.
