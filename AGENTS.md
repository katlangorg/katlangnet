# KatLang Agent Instructions

## Project Overview

- These instructions are for Codex and other AI coding agents working in this repository.
- `AGENTS.md` is the canonical shared agent-instructions file for this repo.
- KatLang's authoritative language model is `lean/KatLang.lean`.
- The C# implementation in `src/KatLang/` must stay semantically aligned with Lean.
- If Lean and C# are both wrong for the same bug, fix both together when feasible.
- Keep this file operational and concise.

## Core Architecture

- `lean/KatLang.lean`: source of truth for AST shape, evaluation rules, and invariants.
- `lean/CoreTests.lean`, `lean/AstDemo.lean`: Lean-side regression and AST compatibility checks.
- `lean/CoreArityAlgebra.lean`, `lean/CoreArityAlgebraProofs.lean`, `lean/CoreArityAlgebra.md`: isolated paper-facing extraction of KatLang's arity algebra; it must stay faithful to `lean/KatLang.lean` but is not authoritative semantics.
- `src/KatLang/`: C# AST, parser, front-end elaboration, evaluator, diagnostics, and public API.
- `src/KatLang/Semantics/`: editor-facing semantic tooling only; it is not the evaluator and not the normative semantics layer.
- `tests/KatLang.Tests/`: parser, evaluator, elaboration, semantics, and integration regression coverage.
- `tutorial.md`, `KatLang.ebnf`, and generator prompt/agent files must stay aligned with real language behavior.
- `docs/design/language-rules/`: the full statement of every compact rule in this file (consequences, examples, implementation map, pinning tests), as binding as this file; its `README.md` says which file to read before touching which subsystem.

## Language Semantics And Design Rules

A bracketed pointer such as [`syntax.md` § The spread marker] names the section of `docs/design/language-rules/` that holds the full rule; read it before changing that rule's implementation, and change both together.

- Lean 4 wins over implementation convenience, performance, or stylistic preference.
- `lean/CoreArityAlgebra.lean` defines the algebra. `lean/CoreArityAlgebraProofs.lean` proves the small laws and executable checks. If either diverges from `lean/KatLang.lean`, fix the artifact or explicitly change the authoritative model first.
- If Lean is ambiguous for a requested behavior change, stop and clarify before implementing.
- Do not invent syntax or semantics that are not in Lean unless the task explicitly includes the Lean change.
- Do not add new operators, convenience syntax, implicit coercions, hidden fallbacks, or AST simplifications that erase Lean distinctions.
- Preserve structural distinctions in the AST and runtime model. In particular, `.dotCall` and `open` are language-level constructs, not incidental parser sugar.
- `Expr.SequenceConstruct` / `.sequenceConstruct` is an INTERNAL sequence-join node, not the AST representation of written parenthesized sequence values (those parse to `Expr.Capture` / `.capture` bundles; `()` to the empty-sequence node). Its evaluation drops `()` leaves, so routing surface syntax through it would violate visible-empty semantics — the parser must never produce it (guarded by `SequenceConstructContainmentTests`, CoreTests internal-node guards, and the semantic explorer's internal-node cases; see `docs/design/sequence-boundary-audit-2026-07.md` §7).
- Brace algorithms parse to `Expr.AlgorithmExpr` / `.algorithmExpr` (algorithm identity); a surviving parenthesized group parses to `Expr.Capture` / `.capture` over an `OutputBundle` — ordered written slots with NO lexical ownership, consumed by the receiver. Capture is not algorithm identity (`Apply((Inc, Dec))` errors, `(Obj*).V` falls back, `open (M, N)` is `BadOpenForm`), while every `AlgorithmExpr` provides its algorithm on the higher-order channel whatever its parameter count — and a REDUNDANT group is not a capture at all (`Apply((Increment))` is `Apply(Increment)`, `(Obj).V` is `Obj.V`, `open (M)` is `open M`; see the parentheses bullet). `Expr.Call.Args` is an `OutputBundle` and `Expr.DotCall.Args` an optional one (`null` = property-style access), evaluated in the CALLER's context; there is no transparent Args algorithm and no `IsParametrized` mode bit — every `Algorithm.User` owns a scope (parser entry points `ParseScopedAlgorithm` / `ParseParenthesizedBodyParts`). Value-context lifting is a consumer property decided by the ONE role classifier of the unified formula-lifting law (`FormulaLiftingRoles`, bullet below): builtin value slots and Math, host and family arguments lift, a user callable's whole argument stays neutral, and a closed list leaves blocked lifting as runtime zero-argument demand (Model-C Q-15). [`sequences-lists-and-calls.md` § Output bundles, capture, and algorithm identity]
- MODEL-C CALL-BY-NEED (October 2026): one suspended/Ready NeedCell per supplied computation; plain binding, parameter transport, alias indirection and collector-slice opening do not force. First VALUE demand evaluates once in the caller environment, memoizing full counted success, ordinary failure or cancellation; overlapping demands join one flight. CALLABLE projection is independent and never forces VALUE. Inspecting patterns traverse left to right; families share one supply across attempts. Arbitrary spread forms eager Ready items; collector VALUE materializes the whole exact list. Cardinality precedes ordinary demand. Cyclic active dependencies report DemandCycle; fresh recursion obeys ordinary limits. Q-15 blocked lifting is runtime demand, while directly written undeclared names and Q-77 structural incompatibility stay static. Cell work adds no semantic charge and property caching is a separate domain. RESULTS ARE CALCULATION VALUES: inputs may expose VALUE and CALLABLE, but no result construction (output rows, `if`/clause selection, collections, selection, spread results, loop state) exports CALLABLE — projection exists only for written references, Ready data has none — and an undersupplied call is an arity error, never partial application (`ResultValueBoundaryTests`, CoreTests `ModelC`). [`call-by-need.md` § Production implementation map; § Result boundary]
- Algorithm output is written as expression rows: every non-definition expression row in an algorithm body contributes to that algorithm's output, and output rows may be interleaved with property definitions. There is no output keyword; `Output` and `output` are ordinary identifiers.
- PARENTHESES GROUP SYNTAX; THEY DO NOT INTRODUCE A SEMANTIC BOUNDARY (September 2026): a parenthesized group whose content is exactly ONE non-spread expression slot is that expression, whatever its kind — `(x)`, `((x))`, `(~x)`, `(F(1))`, `(Obj.X)`, `(A:0)`, `([1, 2])`, `({...})`, `((1, 2))`, `(())` elaborate to the very node `x`, `F(1)`, `Obj.X`, `A:0`, `[1, 2]`, `{...}`, `(1, 2)`, `()` do (`Parser.IsRedundantGrouping`, the ONE decision, which never looks at the inner kind; the unwrapped node takes the group's extent as its span except that a NAME occurrence keeps its exact identifier span for the semantic model). Consequently `E ≡ (E) ≡ ((E))` for value, emitted count, normalization, every binding (fixed, collecting, patterned, clause family), storage, caching and value demand (`(A).count` is `A.count` is `count(A)` — a direct demand; `if(true, (A), 0)` demands `A`), selection, dot-call receivers (`(Obj).V` navigates `Obj`'s member), spread (`(E)*` is `E*`), evaluation count and order, error kind, and every execution strategy — no layer may branch on a grouping that no longer exists. Only a group whose parentheses DO something survives as `Expr.Capture` / `.capture`: several slots (`(1, 2)`) or a lone spread slot (`(A*)`, `capture : Supply -> Value`), and those keep the capture laws (no algorithm identity, no structural members, not an open target). A same-line `(` after a grouped callable name is a call (`(F)(1)` is `F(1)`). PATTERN DELIMITERS ARE NOT EXPRESSION GROUPING: redundant grouping is an EXPRESSION rule and no pattern is ever unwrapped — `F((a, b))` takes ONE argument whose sequence VALUE its pattern opens one level, and a one-item sequence pattern (`F((x))`, `F(((x)))`, `F(([x]))`, `F(((x, y)))`) is the front-end error `SingletonSequencePattern`, never a spelling of `F(x)` (the structural-pattern bullet under Builtins And Spread Conventions). There is no written-slot view of an argument (`explicitItems?` / `ExplicitSequenceValueItems` are DELETED, never to return), so a CALL-SITE group is still erased: `F(S)`, `F((S))`, `F(((1, 2)))`, `F({S})`, and `F((S*))` bind the same value. Lean cannot see the parser, so the rule is pinned by the derived-AST corpora (`parentheses-group-syntax` spec case, `SemanticExplorerTests.DerivedLeanPrograms_MirrorParserParenthesisNormalization`), `RedundantParenthesesTransparencyTests` (the `E ≡ (E) ≡ ((E))` observer matrix: value, count, error kind, evaluation count/order, cache, generic/optimized/suspended-async), `OutputBundleSplitTests`, and CoreTests `CollectingParameters`/`DotCallSemantics`/`OutputBundle`. Selection chooses a value, dot-call passes a value, spread opens a value, parentheses group syntax. [`syntax.md` § Parentheses group syntax]
- Delimiter model: `(...)` groups sequences/expressions and delimits call arguments, `[...]` constructs lists, and only `{...}` (and the root) creates an algorithm-level scope: `open`, property/clause definitions, and deconstruction bindings are parser-rejected inside parentheses with a targeted diagnostic pointing at `{ ... }`, while brace blocks work in any expression position without leaking. DELIMITER OWNERSHIP (#9): a closer is never consumed as junk while a construct is open — every nested body, list, operand, and clause-head parse ends at a closer of any kind, and the innermost construct resolves it (`Parser.ExpectCloser`): its own closer is consumed, one an ENCLOSING construct is waiting for is left for that owner (`Parser.IsOwedCloser`), one nothing is waiting for closes it as the mismatched closer it is (`(1, 2]` is one diagnostic); only with no construct open is a closer a top-level stray, reported and consumed in the same root scope (`)`, `]`, `}` alike; later declarations retained, the parse stays erroneous). Every closer therefore closes at least one construct, so a malformed region whose delimiters balance by count never swallows later source (`RootStrayCloserRecoveryTests` with its exhaustive delimiter soup, `MalformedSourceRecoveryTests`). REPORTED CHARACTERS ARE INVISIBLE TO THE GRAMMAR (#9): the parser skips a character the lexer reported exactly like a comment (`Parser.IsSkippedByGrammar`), so the lexer's diagnostic is its only one (`A @= 1` is the declaration `A = 1`); one standing where the grammar needs a piece — an operand, member name, open target, pattern item, or separating comma, never a closer or `=` — is that piece, filled silently (`Parser.TakeReportedCharacterBeforeCurrent`), a skipped run fills at most one piece, and marker attachment stays exact source adjacency. A prospective clause head is itself an open construct even at the root: lookahead rejects every internal delimiter mismatch and leaves ordinary delimiter parsing to resolve it. An expression unwrapped from redundant grouping keeps the group's FULL extent as its `Span` (`Parser.WithGroupExtent`; `GroupedExpressionSpanTests`) — except a name occurrence, whose span IS the identifier the semantic model sites on — and every unary operand rejection carries the unary expression's span from the ONE `Evaluator.ApplyUnaryOperator` (`UnaryOperandSpanTests`). [`syntax.md` § Delimiters, grouping extent, and unary spans]
- BUILTIN CALLABLES ARE ORDINARY PRELUDE BINDINGS (SYN-05): resolution selects ONE identity without looking at the argument count, and that identity decides signature and behavior (`resolve → select ONE identity → assemble the ordinary supply → bind against THAT signature → invoke`); a nearer property or parameter named `if`, `count`, or `sum` shadows the prelude COMPLETELY, and NO layer branches on a callee's spelling — no reserved-name mechanism of any kind, no argument counting from a callee name in the parser (a wrong-arity builtin call is an evaluation-time `ArityMismatch`), and a recognizer may use spelling only as a registry-metadata key (`Evaluator.BuiltinDisplayName`) before confirming `Evaluator.ResolvesToBuiltinAlgorithm`; builtin `if`'s laziness belongs to the resolved builtin. Every builtin VALUE slot demands its selected argument through the ONE zero-argument value-demand law (`ZeroArgumentValueDemandRejection` / Lean `zeroArgumentDemandError?`; `DemandSequenceBuiltinCallItemValue` / `SequenceBuiltinValueDemandError` for collection arguments and fixed controls): a callable that cannot accept zero supplied arguments is its ordinary arity rejection, a conditional without a zero-arity branch `ConditionalValueAccessError`, a written block `UnresolvedImplicitParams`; unselected and callback slots are never demanded. (`load` alone is still recognized by spelling — deliberate.) `BuiltinCallableIdentityTests`, `LazySlotZeroArgumentDemandTests`, `CoreTests/NameOwnership.lean`, `CoreTests/ValueDemand.lean`. [`ownership-and-lookup.md` § Builtin identity and the zero-argument value demand]
- Ownership-first lookup must agree across the evaluator, elaboration, parameter detection, and semantic tooling. The evaluator's value-position `LookupLexical` and algorithm-position `LookupLexicalResolvedAlgorithm` are ONE implementation (`LookupTwinEquivalenceTests`); the evaluator's chain and `ElaboratedScopeLookup` (shared by `ParameterDetector` and `Semantics/`) must select the SAME declaration, because the detector's verdict rewrites the program (`LookupCoherenceTests`). Inline block and module heads remain separate providers at each written target, including dotted paths (the dedup key reads `AstHelpers.OpenTargetHead`; Lean `Expr.openTargetHead`). Named `open` targets dedup first-occurrence-wins (`Evaluator.OpenTargetDedupKey`, Lean `resolveAllOpens`; complete spelling, never bounded diagnostic text) in BOTH C# lookups. The whole model is SIX ordered rules — owner walk (parameter before property per level, prelude outermost), opens only after the whole walk (per level; two providers select nothing), promotion only after both, structural-first dot edges, static `open`, identity never spelling — stated once in [`ownership-and-lookup.md` § The resolution model in one place]; `NameResolutionAuditTests` pins the cross-layer matrix. [`ownership-and-lookup.md` § Ownership-first lookup]
- The OWNER WALK is the front-end half of ownership-first, with `ElaboratedScopeLookup.SelectOwnedDeclaration` its ONE implementation (Lean `selectOwnedDeclaration`): search outward by owning scope over the NAME-RESOLUTION parameters a scope binds (written, inferred, branch binders — never one automatic forwarding added, Q-04) and the properties it declares; the first owner declaring the name decides, so a captured ancestor parameter beats a property of any farther owner, opens are consulted only after the whole walk, the prelude only as the outermost property level, and ownership never changes promotion (`IsBoundName`). Properties matching parameters of the same or an enclosing algorithm are declaration errors (`ParameterPropertyCollisionValidator`), except that the never-called root's completed signature is checked against the root's OWN declarations only (an unresolved root name is `UnresolvedImplicitParams` at the first root output row). The owner map is `ParameterOwnership` (name → owning level, never a depth); `ShouldRewriteAsParam`, `ResolveReceiverNameProvider`, and `ComputeVisibleSymbols` all go through the walk. `ParameterOwnershipTests`, `LookupCoherenceTests`, the `ownership-*` spec cases. - ZERO-ARGUMENT VALUE DEMAND FOLLOWS ACTUAL CALL ARITY (September 2026): a callable may satisfy a zero-argument value demand IF AND ONLY IF an ordinary call supplying ZERO arguments can bind it (`Evaluator.AcceptsZeroSuppliedArguments` / Lean `Algorithm.acceptsZeroSuppliedArguments`), never because its declared parameter list is empty. The rule is the binder's own, factored out as `ParameterPattern.MinimumSuppliedSlots` / `minimumSuppliedSlots` and used by `bindNeedPatterns` itself: every top-level pattern consumes ONE supplied slot whatever it contains, and a COLLECTING capture at that level consumes NONE. So `Only(*xs) = xs` is a valid value expression (`Only` and `Only()` both give `[]`), while `Head(x, *rest)`, `Tail(*rest, z)`, `P((x, *rest))` and `P((x, y))` still require a supplied value — a structural pattern binds ONE supplied value of its own kind, it never accepts none — and a clause family accepts only when a branch's top-level pattern has arity zero (`matchCallBranches`' own rule). The REJECTION reports that true minimum (`Head` is 1, `P((x, y))` is 1), never the flattened declared capture count; a builtin is deliberately not decided by the law and keeps `EvalBuiltinValueCounted`'s own rejection (the very error `sum()` reports). Eligibility is ALL that changed: the accepted demand evaluates through the ONE funnel `EvalZeroArgumentDemandOutputCounted` / `evalZeroArgumentDemandOutputCounted` (no pattern → its output as before; a pattern list → the ordinary binder against the EMPTY supply; a family → ordinary zero-argument dispatch), so bare `Only` takes the ordinary property-demand/cache path while `Only()` keeps its established cache bypass, callback and other algorithm-valued slots still receive the algorithm (`map(A, Only)` is unchanged) — a callable FORWARDED through a parameter too: an invoking builtin slot (filter/map/reduce callbacks, loop steps) takes the parameter's algorithm-channel binding (`ResolvedArgumentAlgorithm.invoked` / `InvokedAlgorithm`) without an ADDITIONAL value demand; plain binding has no VALUE effects, while value slots, `reduce`'s `initial` included, read the bound value — value-context LIFTING reads the same rule since Q-03 (next bullet), and laziness, charges, cancellation and the optimizer are unchanged. `ZeroArgumentDemandArityTests`, `LazySlotZeroArgumentDemandTests`, `ForwardedCallableChannelTests`, `CoreTests/ValueDemand.lean`, the `zero_argument_*` / `minimum_supplied_slots_*` laws in `KatLangArityLaws.lean`, the `zero-argument-demand-follows-actual-call-arity` spec case. [`ownership-and-lookup.md` § Builtin identity and the zero-argument value demand]
- IMPLICIT LIFTING FOLLOWS ZERO-ARGUMENT ACCEPTANCE (Q-03, September 28 2026): if a callable works with no arguments, using its name alone reads its cached value, even if it declares optional or collecting parameters; `A()` evaluates it again. The front end lifts a bare value-position reference into an implicit forwarding call ONLY when its callee REQUIRES supplied arguments — ONE rule, `ParameterPattern.AcceptsZeroSuppliedSlots`, read by `Evaluator.AcceptsZeroSuppliedArguments` and by the resolver's `RequiresSuppliedArguments` (via `CallableSignature.AcceptsZeroSuppliedArguments`) at every liftable arm and at root-row preservation; Lean `liftsBareValueReference`, law `bare_reference_lifts_iff_not_cacheable` — never because its signature merely declares a parameter. So a collecting-only `Roll(*xs)` in ANY expression position (operator or comparison operand, list element, index target, spread operand, strict Math argument, Math dot fallback receiver, a block or callback body that uses it, under a closed list) stays the cached zero-argument demand: `Roll == Roll` is `true`, `first(Pair)` and `Pair:0` read one evaluation, a formula chain evaluates its base once. A body whose ONE row is the bare name is NOT such a position: it is a callable alias or bare forwarding (FWD-02 below, superseding Q-03's former "an alias is a zero-parameter property holding its value" clause) — `Alias = Cnt` IS Cnt's callable and, read bare, is Cnt's zero-supply demand under its OWN cache entry, and a closed `A(p) = Cnt` that forwards nothing to it reads Cnt's cached value; in a formula, by-shape forwarding reaches only a grouped stream `H((*xs))`, and an owner that lifts from such a callee requires arguments itself unless enclosing parameter bindings already supply them (Q-04, next bullet); a callable that requires an argument (`Inc(x)`, `Head(x, *rest)`, `P((*xs))`) lifts and forwards exactly as before, and explicit calls stay fresh. `ZeroArgumentReferenceLiftingTests`, `CoreTests/PropertyCacheConsumers.lean`, the `zero-argument-callable-name-is-read-not-lifted` spec case. [`ownership-and-lookup.md` § Zero-argument value demand follows actual call arity]
- AUTOMATIC PARAMETER FORWARDING MUST NOT CHANGE WHAT AN EXISTING NAME REFERS TO (Q-04, decided September 28 2026): automatic forwarding reuses parameter bindings only — properties, opened names, module members and builtins are never forwarded as parameters. Name resolution (`ParameterDetector`) decides every written name FIRST; forwarding (`ImplicitArgumentResolver`) then supplies each callee parameter a lifted FORMULA reference needs (a body whose one row is the bare callee is a callable alias, which reuses nothing, or bare forwarding, which reuses the same bindings by name but never adds one — FWD-02) from the binding a written parameter reference of that name already denotes at the referencing body: its own written or inferred parameter, else the nearest ENCLOSING parameter binding — an ancestor's captured parameter, a clause-branch binder, the root's inferred names — that the owner walk reaches before any same-named property (`ImplicitArgumentResolver.ForwardableParameters`, part of the resolver's region-memo key; Lean `forwardingSource`), and a reused binding's KIND decides a re-spread (FWD-02). Only a name no parameter binding supplies becomes a NEW forwarded parameter of an inferring body, appended and marked (`Algorithm.User.ForwardingParameterStart`); a closed list or branch pattern receives none (the reference stays the zero-argument demand; a strict Math position is the closed-list diagnostic). A forwarded parameter completes the signature for callers and still collides with a same-named property (`ParameterPropertyCollisionValidator`), but it is NEVER what a written name denotes — neither the owner walk, nor scope visibility, nor any evaluator read of a written name sees it — so nothing is re-selected after lifting (the former `ParameterDetector.CompleteOwnership` pass is deleted) and a name nothing declares in a closed body stays undeclared. So `A = y + 1` / `F(y) = { G = y * 1000 + A ⏎ H(y) = G ⏎ H(100) }` / `F(3)` is 3004 like the inlined helper (formerly 100101), a helper formula that reuses its owner's parameter is an ordinary zero-parameter property (local-only, one evaluation per activation) — while a bare local alias `G = A` is A's callable (and reuses no enclosing binding), and bare forwarding `F(x) = A` supplies A's `y` from the same enclosing binding by name, leaving F's own `x` unused (`A = y + 1` / `G = { F(x) = A ⏎ F(1) + y }` / `G(10)` is 21) — `v = 99` / `Need(v) = v` / `Outer = Need + 1` still gives `Outer(v)`, and in `Outer = { Inner = v ⏎ Inner + Need }` Inner's `v` stays the root property (106, formerly 14). Explicit shadowing (`Inner(y) = …`) is unchanged. `AutomaticForwardingBindingTests` (six routes, editor bindings, generated extraction and added-dependency metamorphic families), `OwnershipConformanceTests` (mask bit 4 = forwarded) with `CoreTests/NameOwnership.lean`, `CoreTests/ForwardingBindings.lean`, the `forwarding_*`/`forwarded_*` laws in `KatLangArityLaws.lean`, the `forwarding-*`/`forwarded-*` spec cases. [`ownership-and-lookup.md` § Automatic parameter forwarding preserves existing bindings]
- FORMULA LIFTING IS BY BINDING NAME, regardless of how many times that name occurs in a callee's parameter patterns (decided September 29 2026, reversing the same day's Q-72 refusal; narrowed the same day to FORMULAS by FWD-02): when a formula USES a callee inside an expression, a caller owns ONE binding per name, so lifting gives the caller one parameter per binding NAME — PAR-05's first-occurrence order, the ONE merge (`ImplicitArgumentResolver.AppendMissingPatterns`) skipping every capture, group items included, whose name an earlier capture or a reused binding already binds — and the synthesized call (`BuildImplicitCallArguments`) supplies that one binding to EVERY occurrence. So `P(x, x) = x` / `D = [P]:0` is `D(x) = [P(x, x)]:0` exactly as `F(x)`, `G(x)`, `H = F + G` is `H(x) = F(x) + G(x)`; `P((x, a), x)` lifts `(x, a)`, `P(x, (x, a))` lifts `x, a` and `P((x, x))` lifts `x` (a sequence group left with ONE binder IS that binder — never the invalid singleton `(x)`), `P(x, [x, a])` lifts `x, [a]` (a list group keeps its kind) — never a formula signature that repeats a name — and a closed list that declares the name forwards its own binding (`Q(x) = P + 0` is `Q(x) = P(x, x) + 0`). The bare lone row is not a formula: `Some = P` is a callable alias — P's callable with P's own `(x, x)` (the former alias-signature deduplication and the exact-alias wrapper are superseded) — and `Q(x) = P` is bare forwarding, which reuses Q's one binding `x` by name for both occurrences, `P(x, x)` (FWD-02) — the same call a formula builds, but under a closed list that never gains a parameter. There is no repeated-name exception anywhere in formula lifting: lifting and neutral positions, the closed-list gate, FWD-02's re-spread by the SOURCE binding's kind, and Q-03's reads are the general rules. Q-05 is untouched: the direct `P(7, 8)` supplies independent arguments and fails, while a formula feeds one complete binding (the value and callable of ONE argument) to every occurrence, so nothing is spliced and a callable-only or failed binding is its own failure. Formula lifting is the one place a callee's binder names reach a caller's SIGNATURE (bare forwarding reads them only to select EXISTING bindings, and an explicit call never reads them) — a deliberate by-name design, not an encapsulation defect. Lean models no signature construction (`forwardingSource` decides per name). `ImplicitForwardingByBindingNameTests` (per-shape laws: one binding per name, equivalence with the explicit same-binding call, rename-apart; every formula position against the explicit call; no inferred signature repeats a name — a callable alias has no signature of its own), the `implicit-forwarding-is-by-binding-name` and `repeated-name-wrapper-keeps-independent-arguments` spec cases. - THE UNIFIED FORMULA-LIFTING LAW (decided September 30 2026; constitution Q-11/Q-12/Q-13 collapse into it FOR FORMULAS, while lone rows stay FWD-02's): a formula lifts a reference exactly when its ROLE is a value use and the callable it RESOLVES to has a lifting signature that requires supplied arguments (Q-03) — two independent facts, each with ONE implementation. ROLE is the IMMEDIATE consumer's (`FormulaLiftingRoles`, Lean `liftingSlotRole`/`builtinLiftingSlotRole`), recursive and blind to laziness: operands, index parts, spread operands, list and capture elements, rows and deconstruction right-hand sides, the `.string` receiver, a builtin's collection/value/whole-number/surplus slots (all three `if` slots; a loop's count and initial state), and Math, host-operation and clause-family arguments are VALUE; a callee, a callback or loop step, a user callable's whole argument (neutral, sub-choice A1), an argument of a runtime-only callee, and a navigated or runtime-decided dot receiver are CALLABLE; a selected fallback `R.F(args)` is the call `F(R, args)` slot by slot; a nested expression takes its own consumer's role (`Id(Inc)` keeps `Inc`, `Id(Inc + 0)` lifts it); an `if` branch lifts whether or not it is selected, and evaluation stays lazy. SIGNATURE is identity-keyed (`ImplicitArgumentResolver.TryResolveLiftable`, Lean `Algorithm.liftingSignature?`), resolved owner walk → prelude → opens and THROUGH callable aliases to the normalized target (an alias has no signature, kind or role of its own: `A = abs` / `K = A(Inc)` gives `Inc` the value role `abs` gives it, X-45), never by route: a user algorithm's processed patterns, a builtin's `ToolingPlainSignature` (a loop's `*init`), a Math member's or host operation's parameters, an opened or dotted member's own, and a CLAUSE FAMILY's one whole-value slot per position named by its plain-binder clauses (literal, structural and binderless patterns vote nothing; votes must agree; positions need distinct names; Lean `familyLiftingSignature?`) — otherwise NO signature and no invented name: an INFERRING formula that would lift it is `DiagnosticCode.UnliftableClauseFamily` at the reference, while a closed list keeps its runtime demand. Unchanged and composing: Q-04 (sources are existing parameter bindings only), PAR-04 (closed lists gain nothing; Q-15 leaves blocked references as runtime demands, including Math), PAR-05, FWD-02 (lone rows; `C = count` is a callable alias of `count`, `C = count + 0` is `C(collection)`), and THE ROOT CLAUSE — a bare ROOT row naming a callable that requires arguments is its own zero-argument demand whatever the category (`abs`, `Math.Random`, `count` alone at the root: their own arity error; formerly the Math spellings lifted there). - `arity` means the structural count of top-level output slots. The `ArityMismatch` error family reports a supply/output CARDINALITY failure (and NEED-04's unequal repeated value), never a value of the wrong kind, a missing callable, or an empty selection (Q-27).
- `count` means the number of evaluated top-level values after sequence values are opened by the consuming operation.
- Do not treat `arity` and `count` as interchangeable.
- Terminology: prefix `*` is the COLLECT MARKER; `*name` is a COLLECTING BINDING; in a callable declaration it forms a COLLECTING PARAMETER. A callable with a collecting parameter may be DESCRIBED as variadic (it accepts a variable number of argument items), but "collecting parameter" is the canonical construct name — never "variadic parameter", "rest parameter", or "rest binding".
- A property/call/builtin RESULT boundary returns ONE value with count `Result.valueCount` (0 for `()`, otherwise 1; a list counts 1): a multi-output body is one sequence value to its caller and only an explicit spread opens it, and redundant unary sequence structure normalizes during construction. [`sequences-lists-and-calls.md` § Collection builtins]

- Flat fixed arity errors report the complete inputs to that binder, never residual recursive tails (`bindParams` / `BindParams` check lengths before zipping): `Add((1, 2))` and `map([(1, 2)], Add)` both report `(expected 2, actual 1)`. ## Editor Semantics
- Every front-end error blocks source-based evaluator entry, including load failures and invalid loaded source, except that a load-bearing clause branch is ONE deferred compilation unit (its written text plus the modules it loads; constitution MOD-10, Q-61): it is parsed eagerly, elaborated and validated as a whole when selected — every declaration, open targets included, whether or not anything demands it — and its errors then stop that evaluation before the branch body runs; a never-selected branch cannot fail after parsing. Do not evaluate recovery trees for additional diagnostics. [`evaluator-and-hosting.md` § Source loading and deferred modules]
- `src/KatLang/Semantics/` derives editor-facing meaning from parsed and elaborated ASTs.
- Build semantic models from `Parser.Parse(...)` / `ParseResult`, not from raw syntax — whatever the parse's configuration: a result with a missing module is a provisional elaboration the builder models (it never throws for an unresolved `load`).
- Only source-backed identifiers may produce semantic sites, resolutions, declarations, or spans. The parser's unique, unwritable, spanless recovery binders declare no symbol (`SemanticModelBuilder.CreateScope`); editor signatures show their missing slots as `?`, never internal names.
- Synthetic constructs must not invent source spans.
- If editor-visible behavior changes, update `src/KatLang/Semantics/` and `tests/KatLang.Tests/SemanticModelTests.cs` together.
- Preserve exact source-span invariants for hover, references, go-to-definition, classification, and callable-property metadata.
- Scope visibility is completion's semantic source: `SemanticModel.ScopeVisibilities` / `GetVisibleSymbolsAt` and `PreludeCatalog` enumerate exactly what ownership-first lookup resolves, scope regions are source-span hulls, and builtin names come from `PreludeCatalog` only. MODULE PROVENANCE is structural, decided per owner before the walk (`ModuleProvidedAlgorithmCollector`): a load-elaborated subtree (`Algorithm.User.IsModuleElaborated`) is module-provided at every depth, so the model emits NO document-owned sites for it while still building its scopes and symbols, a document reference to an imported member gets a LOCATIONLESS target (never a fabricated span), and inside a deferred module region the model performs NO module I/O and classifies unresolvable names `IdentifierClassification.DeferredModuleReference`. SCOPE VISIBILITY IS A VIEW, NOT A SNAPSHOT (FE-4b): each frame's visible set is a canonical immutable name-ordered tree derived from its parent's by the frame's own open, parameter, and property layers, one `VisibleSymbol` serves every scope that sees that symbol, and each `ScopeVisibility.Symbols` is a distinct read-only wrapper over the shared view (record equality unchanged); sharing never merges declaration identity or changes ordered enumeration, and explicit full enumeration stays proportional to its logical output. `ScopeVisibilityRepresentationTests` pins it against the retained eager oracle `ComputeEagerReferenceSymbols`; `Fe4bHostileReviewTests` and non-friend `ScopeVisibilityPublicContractTests` pin exact deferred-entry identity, public enumerator state, and baseline tied-span registration order. Shared symbol identity is model-local; generated record equality is not a declaration-identity comparator. [`editor-semantics.md` § Scope visibility and module provenance]

## Testing Expectations

- Prefer minimal, semantics-preserving, reviewable changes.
- Add or update focused tests near the changed layer.
- Include negative coverage when failure modes are meaningful.
- Test design, adversarial coverage, failure analysis, and validation execution all belong to the primary agent; a subagent is for a bulky self-contained investigation only, never for running tests (see `Validation`).
- If a change crosses parser, evaluator, semantics, or docs boundaries, cover the affected layers in the same task when feasible.
- **A source-based evaluator test must PARSE CLEANLY, and must assert the error TYPE, not merely that something failed.** `Parser.Parse(source).Root` silently discards diagnostics, so a test whose source the parser rejects still evaluates the recovery tree and can pass for an unrelated reason — that is how a `NotPublicProperty` regression passed without ever reaching the branch, and how 41 `EvaluatorTests` came to run on illegal source. Use `SourceProvenance.ParseValid(...)` (or `EvaluatorTestSupport.ParseValidRoot`) for ordinary source semantics; `SourceProvenance.ExpectFrontEndError(...)` when the parser/elaborator is the subject; `SourceProvenance.ParseAllowingDiagnostics(...)` only where malformed source is the point (recovery, fuzz, editor tooling). Never assert an evaluator outcome on a source you have not shown to be legal.
- **Before writing a source test for an evaluator branch, check the branch is surface-reachable at all.** Front-end elaboration can make it dead: clause-family elaboration turns every single-clause binder form into an `Algorithm.User`, so the flat-binder arm of `ConditionalValueAccessError` cannot be reached from any written program, and implicit-parameter promotion hides the dotted-`open` visibility checks. A source test for such a branch passes while the branch stays dead — pin these from a prebuilt AST instead (`EvaluatorDefensiveBranchTests`).

## Coding Guidance

- Prefer small changes that fix the root semantic issue without widening scope unnecessarily.
- Do not introduce new AST shapes unless strongly justified by Lean or an existing architectural boundary.
- Reuse the owning logic instead of re-encoding the same rule across parser, elaboration, evaluator, or semantic-model code, and preserve the current parser/evaluator/tooling boundaries.
- Keep diagnostics structured, source-positioned, user-friendly, and phrased in KatLang terms.
- If a change is implementation-only optimization, say so explicitly.

## Validation

Validation scope follows REGRESSION RISK, never line count, file count, or file extension alone. The alignment manifest and the language rules decide which semantic EDITS a change needs (Lean, C#, corpus, docs); this section decides how much local validation the candidate gets and how it is executed. `.github/workflows/validate.yml` stays the full .NET + Lean backstop for pull requests and pushes to `main`: a local V0–V2 omission is a deliberate risk decision, and CI is never a reason to skip V3 locally. It IS the reason a local V1/V2 stays bounded: the backstop catches what a scoped run misses, so a V1/V2 run is never padded with a full phase "to be safe".

### Candidate and level

- Assess the COMPLETE candidate: the relevant commits plus staged, unstaged, untracked, deleted, and renamed files. A clean working tree is not evidence that a committed candidate needs no tests. Preserve unrelated work and account for it when it affects the candidate or the test results.
- Classify by semantic impact, dependency reach, and changed contracts. Start at V1 unless the change is clearly V0, then apply the V2/V3 triggers; when the impact cannot be confidently bounded, choose V3. Record the level and a one-line reason before validation starts; the level may be raised on evidence, never lowered. The level is also the execution plan: V0–V2 run only what their row names, and the full `validate-all.ps1` phases belong to V3 alone — if the candidate warrants a full phase, record V3; running one at V1/V2 is a misclassification, not extra diligence.

| Level | Appropriate scope | Required local validation |
| --- | --- | --- |
| V0 — trivial | Instruction/prose edits, comments, or formatting proven not to affect execution or mechanically checked content | Review the diff, whitespace (`git diff --check`), and the references/consistency of the text. No build or runtime suite for a genuinely documentation-only change. |
| V1 — focused | Small, isolated, behavior-preserving refactor or test change with a well-understood dependency boundary | Build the affected project/test dependency closure; run the directly related tests with verified filters. |
| V2 — affected | Bounded subsystem behavior change; a limited shared helper, API, or diagnostic contract change; neighboring consumers affected | Focused tests plus the neighboring/affected suites, the affected project builds, and the applicable parity/artifact/Lean checks — never the full solution suite or a `validate-all.ps1` phase. |
| V3 — full | Fundamental behavior, broadly shared infrastructure, cross-cutting changes, or uncertain impact | Complete local .NET validation and all seven canonical Lean targets, plus any specifically required regression/parity checks. |

V3 is MANDATORY for changes to parser/grammar behavior or AST structure; elaboration; lexical ownership/name resolution; parameter binding or implicit lifting; Grace; sequence/list/spread/collect/arity semantics; the evaluator core; the optimizer/planned execution; sync/async/cancellation behavior; core loading/module semantics; caching/exposure; Decimal128/numeric semantics; Lean/C# correspondence; and widely reused infrastructure or build/toolchain changes with broad impact. The triggers concern the behavior or machinery changed: a comment fix inside `Parser.cs` is not V3, a one-line ownership fix is; a formatting-only string-construction refactor may be V1 when the output contract is demonstrably unchanged; updating expected semantic results never makes a semantic change test-only. V2 covers bounded production-behavior changes, shared consumers, and API/diagnostic contracts without a V3 trigger — an isolated CLI presentation change needs no evaluator-wide validation, a change to shared loading or cancellation does. Executable documentation is not prose: tutorial result claims, spec-linked examples, generated prompt blocks, and the EBNF keep their verification tests (coverage map below) even when only text files changed, so such a change is neither automatically V0 nor V3; changed language MEANING is still V3 plus the semantic-update process.

### Lean validation

- V3 always runs all seven Lean targets, even when no `.lean` file changed — a C#-only optimizer, async, or ownership change is V3, and `SemanticExplorerCases`/`LanguageSpecCases` are how Lean/C# correspondence is checked.
- V1/V2: build the affected Lean targets and the dependent artifact/parity checks whenever Lean code, proofs, guards, imports, or generated Lean content changes or is affected; a meaningful Lean-only change never gets zero Lean validation, and unclear dependency reach means V3. Pure Lean comments may be V0; regenerating an artifact without a content change is not itself a semantic change.

### Commands

The normal V3 command, from the repo root:

```powershell
pwsh -NoProfile -File ./scripts/validate-all.ps1 -Phase All
```

Its .NET phase runs the FULL solution build (every project — `dotnet test` alone builds only test projects and their dependencies, so benchmark/demo compile breaks escape it), then the C# suite with `--no-build`, then `git diff --check`; its Lean phase owns the one canonical seven-target list. The script accepts only `All` (the default), `DotNet`, and `Lean`: it has no focused or level switch and does not detect risk. Completing `-Phase DotNet` and then `-Phase Lean`, one after the other, against the same unchanged candidate satisfies V3 — do not rerun `All` merely to repeat completed work, and never run the two phases side by side — while a partial phase alone is never full validation. A phase already runs every focused suite, so it is never preceded, accompanied, or followed by a separate filtered pass over the same candidate. Each phase fingerprints the staged, unstaged, and untracked state and fails if validation changes it; a checkout may start dirty, but validation must leave it exactly as it started.

Manual .NET fallback (equivalent, including the independent full-solution build):

```powershell
dotnet build .\KatLang.slnx -p:UseSharedCompilation=false
dotnet test .\KatLang.slnx -p:UseSharedCompilation=false --no-build
git diff --check
```

Manual Lean fallback (all seven targets — V3, or a V1/V2 change that affects Lean):

```powershell
Push-Location .\lean
lake build CoreTests
lake build KatLangArityLaws
lake build AstDemo
lake build CoreArityAlgebra
lake build CoreArityAlgebraProofs
lake build SemanticExplorerCases
lake build LanguageSpecCases
Pop-Location
```

Lean CoreTests use `#guard` for semantic assertions, so a failing assertion fails `lake build CoreTests`. Remaining `#eval` lines are demo/inspection output only.

Focused V1/V2 runs build the affected projects, then filter, for example:

```powershell
dotnet build ./tests/KatLang.Tests/KatLang.Tests.csproj -p:UseSharedCompilation=false
dotnet test ./tests/KatLang.Tests/KatLang.Tests.csproj -p:UseSharedCompilation=false --no-build --filter "FullyQualifiedName~SameLineSeparatorTests"
```

Filters must name real test classes/namespaces (check the inventory: the class in `LanguageSpec/GeneratorSpecTests.cs` is `LanguageSpecArtifactsGeneratorPromptTests`), and the summary must show the intended tests discovered AND executed — zero matching tests is not a pass whatever the exit code. Use `--no-build` only after a successful, current build of the same projects/configuration/framework and inputs. Verification outside the script keeps its guarantees: neutralize inherited `KATLANG_REGENERATE_*` flags for the verification process only (a child `pwsh -NoProfile` whose environment is discarded, never the caller's lasting environment), snapshot `git status --porcelain=v1 --untracked-files=all` plus the index and worktree diffs before and after, and report an unexpected mutation with its evidence instead of undoing it. Keep terminal output minimal; save complete stdout/stderr under the ignored `artifacts/validation/` directory or a temporary directory, preserving the command's real exit code when redirecting or piping (`$LASTEXITCODE` after the native command in pwsh, `pipefail`/`PIPESTATUS` in bash). Missing required tooling (SDK, `lake`, a runner) is BLOCKED/incomplete validation, never a pass and never a silently lower level.

### Regenerating generated artifacts

Generated artifacts are never edited by hand and never rewritten by a verification run. Regeneration is one deliberate, targeted `dotnet test` run with the artifact's flag set to `1`: the run WRITES the artifact and then FAILS BY DESIGN (also when nothing changed), so it can never pass as verification — review the diff, clear the flag, and run the normal verification at the level the underlying change requires (an intentional language-behavior change is V3).

| Artifact | Flag | Filter |
| --- | --- | --- |
| `lean/LanguageSpecCases.lean` plus the `=== BEGIN GENERATED: katlang-spec-examples ===` block in `.github/agents/katlang-generator.agent.md` and `experimental/prompts/katlang-generator.txt` | `KATLANG_REGENERATE_LANGUAGE_SPEC` | `--filter LanguageSpecArtifacts` |
| `lean/SemanticExplorerCases.lean` | `KATLANG_REGENERATE_SEMANTIC_EXPLORER` | `--filter SemanticExplorerLeanArtifact` |
| `tests/KatLang.Formatting.PublicApi.Tests/PublicApiBaseline.txt` | `KATLANG_REGENERATE_PUBLIC_API` | `--filter PublicApiBaseline` |

For example `$env:KATLANG_REGENERATE_LANGUAGE_SPEC = "1"; dotnet test .\KatLang.slnx --filter LanguageSpecArtifacts`. `validate-all.ps1` is observational: before it builds or tests anything it removes every `KATLANG_REGENERATE_*` variable from its own process (the whole prefix, case-insensitively; restored on exit), so an inherited flag can never make a green run rewrite a tracked artifact. The flag registry and the write-then-fail contract are `RegenerationFlags` / `ArtifactRegeneration` in `tests/KatLang.Tests/Infrastructure/ArtifactRegeneration.cs` (shared as source with the public-API test project); a new `KATLANG_REGENERATE_*` variable must be registered there — `ArtifactRegenerationPolicyTests` scans the repository for unregistered names and for tests that read a flag outside the helper.

### Execution discipline

Validation is executed by the primary agent, in ONE execution stream: never two of `dotnet build`, `dotnet test`, `lake build`, a `validate-all.ps1` phase, or a regeneration run in flight at once — concurrent `dotnet test` invocations lock `KatLang.Tests.dll` (MSB3027), a phase fingerprints the tree while it runs, and a second run of the same suite over an unchanged candidate is pure duplication. Every command's full output goes to a log file (the ignored `artifacts/validation/` directory or a temporary directory) and only its summary lines — result totals, failure identities, exit code — are read back, never the whole log.

- ONE plan per candidate, chosen before anything runs: at V1/V2 the focused and affected suites, most informative first, and nothing beyond them; at V3 the full phases only. Development checks while editing stay minimal — the test class being written, the one previously failing check after a repair, the Lean target that compiles the edited file, a regeneration run — because the plan runs everything else exactly once; a pre-validation sweep of neighboring suites runs every test twice.
- One command at a time, waited to completion: a `--no-build` run only after the build's exit code is in hand, `lake build` never beside a `dotnet` command, the .NET phase and then the Lean phase, never side by side. A `validate-all.ps1` phase exceeds the foreground time limit, so run it as ONE background command and then wait for its completion — no polling loop (every poll re-reads the whole context), no other command, and no edit to the checkout until it has finished.
- On a failure, capture the command, the failure identity, and the evidence; decide what it means; repair; rerun only the failing check; then complete the plan for the FINAL candidate. Reuse earlier results only while their inputs, dependencies, configuration, and environment still apply (later prose-only edits do not by themselves invalidate runtime results). When a failure suggests wider regression, or the diff reveals a V3 trigger the classification missed, raise the scope one level at a time — never as a precaution — and a full phase replaces the remaining focused plan instead of adding to it. Do not rerun an unchanged failure repeatedly, and do not launch every suite to diagnose a missing SDK.
- Never claim validation from a partial run, a stale build, an unexecuted command, a zero-test filter, or an assumption that CI will pass, and do not label a failure pre-existing or flaky without evidence. Report what ran, the counts, the failures, what was omitted and why, and the log paths.

### Subagents

Do not delegate test execution. Measured in September 2026, a validation worker spent 30–50 requests to run two or three commands — about ten times the cost of running them inline — could not work in parallel with a tree that must stay frozen, and shared no prompt cache with the primary agent (caches are model-scoped and prefix-exact). A subagent is for a BULKY, SELF-CONTAINED INVESTIGATION whose intermediate reading would otherwise flood the primary context — a failure hunt across many files, an inventory, a cross-file audit. Give it the cheapest model that can do the job, a bounded brief with an explicit stopping point, and ask for `file:line` facts; code the primary agent will edit or reason about it reads itself, in bounded ranges. Never spawn one for a single known file, and never let one edit, regenerate, or validate.

- The release workflow validates the exact dispatched commit, builds and runs
  the NativeAOT CLI on native Windows/Linux/macOS x64 and ARM64 runners,
  packages the tested executable with the root `LICENSE`, `NOTICE`, and

- Normal jobs have `contents: read`. Only the final publication job has

## Public API Baseline And Release Version

- `tests/KatLang.Formatting.PublicApi.Tests/PublicApiBaseline.txt` is the checked-in, deterministic rendering of the COMPILED public surface of the `KatLang` assembly — the one assembly the NuGet package ships — reflected by `PublicApiSurfaceRenderer` in that deliberately non-friend test project: every exported type plus consumer-reachable protected nested types, with base/interfaces, generics and constraints; every consumer-visible member with parameter names, modifiers, defaults, nullable annotations and nullable-flow attributes; and every public enum member with its exact numeric value. `PublicApiBaselineTests` compares exactly and never rewrites; a difference is a NuGet surface change. Record an intentional change by regenerating it (`Regenerating generated artifacts` under `Validation`) and review the diff as the compatibility review. Regenerating the baseline never changes the release version; the focused hand-written contracts in that project (`PublicElaborationSurfaceTests`, `PublicFormatterExtensionTests`, `HostApiContractTests`) stay beside it.
- The public surface is LAYERED and deliberate (September 2026 public API audit): the primary host API (`KatLangEngine`, `RunOptions`, `RunResult`, `Result`, `KatLangError`/`KatLangErrorCode`), host extensibility (`HostOperation`/`HostOperations`, `OutputFormatter`/`BoundedOutputWriter`), analysis (`Parser`, `Lexer`/`Token`, `Semantics`), and the low-level `Evaluator` over the Lean-shaped AST — which evaluates a host-built `Expr` as-is and is never a source runner. Implementation machinery stays internal and is pinned so by name in `HostApiContractTests` (a baseline regeneration cannot bless re-exposing it): the signature and binding planners (`Signatures/`), the evaluator's value views on `Result` (spread/structure/selection/value-count views, `Normalize`, the UNBOUNDED atom projections — hosts use the bounded `RunResult.Success.Atoms` / `Evaluator.RunFlat`), `SemanticModel` construction, message builders, and compatibility shims. Source, evaluator, and configuration entry points validate their direct CLR arguments (host-built AST payloads remain an advanced caller contract) (`ArgumentNullException`, never a `NullReferenceException`); async entry points deliver every exception through the returned task; each `Evaluator` entry family has exactly one overload per arity (no positional-`null` ambiguity). `RunResult` variants and `ParseResult` are library-produced records with internal constructors and get-only payloads; hosts read/deconstruct them and construct `Result` values for host callbacks. `RunFlat`/`RunFlatAsync` accept host operations through the same bounded projection as their ordinary forms. The package ships its XML documentation — any documentation diagnostic that means a comment is wrong (unresolvable or ambiguous cref, bad param/paramref) is a build error, so docs cannot name a removed API — and is `IsAotCompatible` (trim/AOT analyzers on every build).
- `KatLangVersion.props` is the ONE place the release version is written. `src/KatLang/KatLang.csproj` (package and assembly version), `src/KatLang.CLI/KatLang.CLI.csproj` (which builds against the KatLang PROJECT, so it cannot lag onto a previously published package) and `tests/KatLang.CLI.Tests` (which bakes the value in as `IntendedKatLangVersion` assembly metadata — build intent, never read from the KatLang assembly under test) derive from it. `ReleaseVersionSourceTests` rejects any other version literal in an MSBuild file and any in-repository `PackageReference` to KatLang; the CLI version tests compare the loaded runtime, the CLI assembly and `--version` against the intended metadata, so a stale or mismatched artifact fails rather than passing against itself.

## Executable Language Specification

- `tests/KatLang.Tests/LanguageSpec/LanguageSpecCorpus.cs` is the canonical executable specification: named cases with stable IDs and HAND-WRITTEN canonical expectations. Never regenerate its expectations from observed behavior — a failing `LanguageSpec*` test means either fix the implementation or edit the canonical case in a reviewed diff.
- Same-program fidelity: the Lean program of every Lean-comparable case in BOTH differential corpora (`LanguageSpecCorpus` and `SemanticExplorerCorpus`, internal-node cases included) is DERIVED from the source's real elaborated AST through `tests/KatLang.Tests/LeanAstEncoder.cs` — never authored by hand and never rebuilt by test-side parser-rule templates. C#-only cases carry an explicit non-blank `LeanExclusionReason`, a hand-authored LanguageSpec Lean program requires the exceptional `LeanProgramOverride` + `LeanOverrideReason` (currently unused), and per-corpus exact-ID exclusions plus `FidelityRatchet_*` tests pin the derived-case partitions. The encoder is FAIL-LOUD: extend it deliberately (with reviewed goldens in `LeanAstEncoderTests`) rather than approximating, and expected strings in encoder tests are manually reviewed constants. See `docs/design/executable-language-spec.md` §5.
- GENERATED from it (do not edit by hand): `lean/LanguageSpecCases.lean` and the `=== BEGIN GENERATED: katlang-spec-examples ===` block in both generator files; regenerate all three together (`Regenerating generated artifacts` under `Validation`). `lean/SemanticExplorerCases.lean` is the second GENERATED Lean/C# differential corpus (from `SemanticExplorerCorpus`; see `docs/design/sequence-boundary-audit-2026-07.md`): a failing `#guard` there is a Lean/C# divergence — or a Lean-internal plain/counted mismatch — on that case; after an intentional semantics change regenerate it the same way.
- Tutorial examples marked `<!-- spec:case-id -->` are verified against the corpus (source and expected output) by `TutorialSpecTests`; when changing a linked example, update the canonical case and the tutorial together.
- EVERY tutorial fence followed by a `**Result(s):**` claim is executable documentation: `TutorialResultSweepTests` runs it through `KatLangEngine.Run` and display-matches the claim — no marker needed, so an ordinary new example enters the sweep automatically. A genuinely non-standalone example (e.g. one needing a network downloader) carries `<!-- spec:skip nonblank reason -->` before the fence; the skip inventory is exact-pinned, and result-bearing coverage is monotonic (pinned minimum baseline — removing an existing claim requires a reviewed ratchet reduction, while additions need no pin edit). The shared grammar lives in `TutorialCorpus` and fails loudly on malformed/detached claims, so a result claim can never silently drop out of verification.
- Output-only verification is not a semantic pin (SYN-12): a tutorial example can print the documented number for the wrong reason (an indented `Inner = v + 1` beneath `Outer(v) = Inner` is a ROOT property whose `v` is forwarded through the closed list, not a nested property reading the parameter of its owner). The high-risk explanations — lexical ownership, visibility/export, property-first dot-call resolution, clause-family arity, sequence-value pattern kinds, the call/value boundary, Grace order — are therefore ALSO pinned by `tests/KatLang.Tests/LanguageSpec/TutorialSemanticContractTests.cs` through the elaborated AST (`Property.Exposure`, `Params`), the semantic model (`FindResolutionAt` declaration spans), and structured `DiagnosticCode`/`KatLangErrorCode` values; extend it, and the corpus, when such an explanation changes.
- When language behavior intentionally changes, update the affected canonical cases in the same task as the Lean/C#/tutorial/generator changes.
- Maintainer guide: `docs/design/executable-language-spec.md` (partitions, counts, how to add cases, worked example).
