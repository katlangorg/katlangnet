# KatLang Agent Instructions

## Project Overview

- These instructions are for Codex and other AI coding agents working in this repository.
- `AGENTS.md` is the canonical shared agent-instructions file for this repo.
- KatLang's authoritative language model is `lean/KatLang.lean`.
- The C# implementation in `src/KatLang/` must stay semantically aligned with Lean.
- If Lean and C# are both wrong for the same bug, fix both together when feasible.
- Keep this file operational and concise.

## Core Architecture

- `lean/KatLang.lean`: source of truth for AST shape, evaluation rules, and invariants.
- `lean/CoreTests.lean`, `lean/AstDemo.lean`: Lean-side regression and AST compatibility checks.
- `lean/CoreArityAlgebra.lean`, `lean/CoreArityAlgebraProofs.lean`, `lean/CoreArityAlgebra.md`: isolated paper-facing extraction of KatLang's arity algebra; it must stay faithful to `lean/KatLang.lean` but is not authoritative semantics.
- `src/KatLang/`: C# AST, parser, front-end elaboration, evaluator, diagnostics, and public API.
- `src/KatLang/Semantics/`: editor-facing semantic tooling only; it is not the evaluator and not the normative semantics layer.
- `tests/KatLang.Tests/`: parser, evaluator, elaboration, semantics, and integration regression coverage.
- `tutorial.md`, `KatLang.ebnf`, and generator prompt/agent files must stay aligned with real language behavior.

## Language Semantics And Design Rules

- Lean 4 wins over implementation convenience, performance, or stylistic preference.
- `lean/CoreArityAlgebra.lean` defines the algebra. `lean/CoreArityAlgebraProofs.lean` proves the small laws and executable checks. If either diverges from `lean/KatLang.lean`, fix the artifact or explicitly change the authoritative model first.
- If Lean is ambiguous for a requested behavior change, stop and clarify before implementing.
- Do not invent syntax or semantics that are not in Lean unless the task explicitly includes the Lean change.
- Do not add new operators, convenience syntax, implicit coercions, hidden fallbacks, or AST simplifications that erase Lean distinctions.
- Preserve structural distinctions in the AST and runtime model. In particular, `.dotCall` and `open` are language-level constructs, not incidental parser sugar.
- `Expr.SequenceConstruct` / `.sequenceConstruct` is an INTERNAL sequence-join node, not the AST representation of written parenthesized sequence values (those parse to `Expr.Capture` / `.capture` bundles; `()` to the empty-sequence node). Its evaluation drops `()` leaves, so routing surface syntax through it would violate visible-empty semantics — the parser must never produce it (guarded by `SequenceConstructContainmentTests`, CoreTests internal-node guards, and the semantic explorer's internal-node cases; see `docs/design/sequence-boundary-audit-2026-07.md` §7).
- OutputBundle split (Track A): brace algorithms parse to `Expr.AlgorithmExpr` / `.algorithmExpr` (algorithm identity: scope, parameters, properties, `open`, namespace interpretation), while surviving parenthesized groups parse to `Expr.Capture` / `.capture` over an `OutputBundle` (ordered written expression slots with NO lexical ownership — the receiver decides consumption). `Algorithm.User.Output` is an `OutputBundle`. CAPTURE IS NOT ALGORITHM IDENTITY: the algorithm channel sees only a zero-parameter output thunk over a capture's bundle, so grouping suppresses callable identity (`Apply((Increment))` stays an error), a capture receiver exposes no structural members (`(Obj).V` fails; `Obj.V` works), and a capture is NOT an openable target (`open (M)` is a targeted parse error — the evaluator's open resolution equally rejects capture targets with `BadOpenForm`, mirroring spread). ALGORITHMEXPR IDENTITY IS STRUCTURAL: every `Expr.AlgorithmExpr` provides its contained algorithm on the higher-order channel regardless of parameter/declaration/output count — `Call0({42})` invokes the brace algorithm exactly like the named zero-parameter `Call0(Const)` — while the value channel reifies written slots independently (builtin argument adapters keep the one-slot value boundary for zero-declaration blocks: `repeat(step, n, {1, 2})` still supplies ONE initial state slot). Value-context implicit lifting (`ProcessValueDemandingArgumentBundle`) is a consumer property: Math member arguments are registry-provably strict-value and lift like every ordinary value position, while ordinary call arguments stay neutral to preserve higher-order references. `Expr.Call.Args` is an `OutputBundle` and `Expr.DotCall.Args` an optional one (Track B): call/dot-call argument lists are ordered bundles of the ORIGINAL written argument expressions, evaluated transparently in the CALLER's lexical context — no transparent Args Algorithm exists anywhere in a parsed tree, and free names inside argument slots belong to the enclosing algorithm. `DotCall.Args = null` (no argument-list syntax, property-style access) stays distinct from an explicit empty list. There is NO transparent-vs-scoped Algorithm mode bit (Track C removed `IsParametrized` entirely): every `Algorithm.User` is a scope-owning algorithm, transparent syntax is carried structurally by OutputBundle-bearing nodes (`Capture`, `ListLiteral`, `Call.Args`, `DotCall.Args`), and the parser's two body contexts are the named entry points `ParseScopedAlgorithm` (root/braces/trailing-brace arguments) and `ParseParenthesizedBodyParts` (groups and call argument lists, which lower to capture/bundle — or to one recovery `AlgorithmExpr` when illegal declarations were retained for recovery).
- Algorithm output is written as expression rows: every non-definition expression row in an algorithm body contributes to that algorithm's output, and output rows may be interleaved with property definitions. There is no output keyword; `Output` and `output` are ordinary identifiers.
- Delimiter model: `(...)` is sequence/expression grouping and call-argument syntax, `[...]` is list construction, and only `{...}` (and the root) creates an algorithm-level lexical scope. Algorithm-level declarations — `open`, property/clause definitions, deconstruction bindings — are parser-rejected inside parentheses with a targeted diagnostic pointing at `{ ... }`; brace blocks work in any expression position, including as call arguments, and their opens/local properties never leak into the surrounding scope. The parser may keep temporary Algorithm/Block structures for parenthesized sequences internally; the observable invariant is that no diagnostic-free parenthesized expression contains algorithm-level declarations.
- Ownership-first lookup is fundamental. Keep lookup behavior aligned across evaluator, parser/front-end elaboration, parameter detection, and semantic tooling. The evaluator's two lookup spellings — `LookupLexical` (reached by a bare name in VALUE position, `X`; returns owner+binding for the zero-arg property cache) and `LookupLexicalResolvedAlgorithm` (reached from ALGORITHM position: a callee `X()` or a dot-call target `X.m`) — are ONE implementation since M8+M9: the algorithm spelling is the projection of the binding-carrying chain (mirroring Lean, where `lookupLexical` projects `lookupLexicalProperty`), so ownership-first, open dedup, ambiguity, scope-level precedence, and prelude fallback exist once per engine; `LookupTwinEquivalenceTests` keeps both spellings observable so an independent fast path cannot silently regrow. Beyond that there are TWO C# lookup implementations — the evaluator's chain and `ElaboratedScopeLookup` (shared by `ParameterDetector` and `Semantics/`) — and they must select the SAME declaration, not merely both resolve: the detector's verdict rewrites the program (an unresolvable name becomes an implicit parameter), so a front-end disagreement changes what the evaluator runs. `LookupCoherenceTests` pins that relation with unique per-declaration sentinels; the `open`/visibility family in `SemanticExplorerCases.lean` pins the Lean/C# side. Named `open` targets deduplicate first-occurrence-wins by `Evaluator.OpenExprName` (inline blocks get positional keys and never dedup), so `open A, A` is ONE provider, not an ambiguity — that rule lives in Lean `resolveAllOpens` and must be mirrored by BOTH C# implementations.
- `open Name` may target a lexically visible private head, but `open` only exposes public members. "Public" through `open` means public AND `PropertyExposure.Exported`: a local-only property (one capturing ancestor-owned parameters, or defined inside a conditional clause body) is never exposed even when written `public`. Structural dot access deliberately ignores both, so `Lib.X` reaches a private `X` that `open Lib` would not.
- `open` is a declaration/import directive, not an output expression: it takes ONE comma-separated target list (`open A, B, C`; string targets use single quotes — `open 'url', A`), parsed by a dedicated comma-list parser into individual targets (resolve, argumentless dot-call path, block, or string-load sugar). Each algorithm allows at most one `open` declaration. The first target must begin on the same physical line as `open` (`open` newline `A` is a missing-target error and `A` stays a separate row). Comma keeps its normal explicit line-continuation behavior — `open A,` newline `B` and `open A` newline `, B` both continue the list — and a leading `.` continues a dotted target (`open A` newline `.B` is `open A.B`), but a plain newline never continues `open`: `open Math` newline `Math.Pi` is an open plus a report row. `;` and same-line adjacency are NOT open-target separators (`open A ; B` and `open A B` report a missing-comma diagnostic, never two targets). A spread-marked open target (`open A*`) parses to a spread expression and is rejected by open-form validation — spread is not an open form.
- `open 'url'` is front-end sugar for load elaboration, not a core AST construct.
- Dot-call uses structural lookup first and lexical fallback second. Structural lookup, receiver injection, fallback order, and diagnostics must stay consistent across Lean and C#.
- Grace `~` is a front-end parameter-order annotation on exactly one bare name occurrence (`~x` / `x~`); it is not a general expression operator, repeated markers on that occurrence use ordinary weight arithmetic, and elaboration strips it before evaluation.
- Grace composes with ordinary dot syntax: `a~.t(args)` is postfix Grace on the bare receiver occurrence followed by ordinary `.t`, while `a.~t(args)` is ordinary dot with prefix Grace on the participating fallback/member occurrence `t`. Base DotCall occurrence order is receiver, participating fallback, then arguments, so `a.t` infers `(a, t)` and both graced two-name forms infer `(t, a)` through the ONE general Grace reordering law. Postfix Grace on a compound receiver (including a second `~.` in a chain) rejects through the one-name eligibility rule; prefix member Grace remains eligible because it decorates the bare member occurrence. Parameter detection consumes Grace, all forms elaborate to the SAME ordinary structural-first `DotCall`, and Grace never changes executable selection.
- Implicit-parameter order follows first semantic source occurrence plus the ordinary Grace arithmetic. A DotCall contributes its receiver occurrences, then its member's stored lexical-fallback occurrence when fallback MAY be selected, then written argument occurrences; thus `K = a.t(b)` infers `(a, t, b)`, while the direct call `K = t(a)` independently infers `(t, a)`. Runtime fallback assembly as `t(a, b)` does not determine the enclosing signature order.
- Ordinary lexical dot-call injects the receiver as ONE leading argument SEGMENT: `A.B(C, D)` allocates like `B(A, C, D)` — the receiver's item count never satisfies arity, fixed prefix/suffix parameters bind from the front and back first, and a FIXED parameter allocated the receiver segment binds its one captured value. The segment additionally carries its evaluated top-level supply, which exactly one consumer reads: a flat TOP-LEVEL collecting parameter allocated the segment consumes the supply items (one level, never recursive — exact lists stay opaque, nested/patterned collecting bindings are never fed the supply). A WRITTEN group/brace receiver supplies its raw row emission (`(1, 2, 3).Mean` with `Mean(*Vector)` binds `Vector = [1, 2, 3]`; `((1, 2)).Collect` keeps the extra written boundary; `().Collect` supplies zero items), while a NAMED property receiver evaluates at its value boundary and supplies one item (or zero for `()`). Receiver assembly never inspects the resolved callee and never pre-expands the receiver (`ParameterPatternInput.CollectingSegmentEmittedCount` / Lean `collectingSegmentCount?` is the ephemeral segment-supply carrier; it is data-only and never stored in environments, collected lists, or `Result`). Direct calls are unchanged: a written argument slot always reifies to ONE value, so `Mean((1, 2, 3))` still collects one grouped argument.
- Only sequence/variadic builtin dot-call paths may opt into receiver top-level expansion, and that expansion must remain explicit in builtin metadata/evaluator handling.

## Lean/C# Consistency Requirements

- `Parser.Parse(...)` and `ParseResult` are elaborated front-end outputs, not raw syntax trees.
- The raw syntax boundary is `Parser.ParseSyntax(...)`.
- `FrontEndPipeline.Process(...)` / `ProcessAsync(...)` are the explicit C# front-end paths for elaboration passes such as load elaboration, parameter detection, implicit argument resolution, and property exposure resolution.
- The individual elaboration passes are INTERNAL implementation stages (v0.8.187, M6): `ParameterDetector`, `ImplicitArgumentResolver`, `PropertyExposureResolver`, `FrontEndPipeline`, and `Parser.ParseSyntax` are not host API, and hosts must not be able to compose partial elaboration — a Detect→Resolve tree without exposure resolution leaves every `Property.Exposure` at the default `Exported`, which the evaluator trusts (pinned by `FrontEndElaborationBoundaryTests` and the non-friend `PublicElaborationSurfaceTests`). The supported public layers are `Parser.Parse`/`ParseAsync` and `KatLangEngine` (complete pipeline), `SemanticModelBuilder` over `ParseResult`, and `Evaluator.Run*` direct evaluation of host-built ASTs (as-is, preflight only, no elaboration). Do not re-publicize a stage or add a partial facade; exposure/ownership metadata is trustworthy only after the complete pipeline finishes. (`ModuleLoader` is internal too since v0.8.188 — load elaboration alone is even more incomplete: a loader-only tree has had no parameter detection, so spliced module functions cannot even bind their arguments; hosts get module loading through `Parser.ParseAsync`/`KatLangEngine.RunAsync` with `RunOptions.DownloadCode`/`AllowedHosts`.)
- Default parse/run entry points reject unresolved `load`; only elaboration-enabled paths may consume it. SOURCE LOADING IS ASYNC-ONLY: the one downloader contract is `RunOptions.DownloadCode : Func<string, CancellationToken, ValueTask<string>>` — and it is the ONLY transport: the library ships no default/ambient HTTP downloader (a `ModuleLoader` cannot be constructed without an explicit delegate; `AllowedHosts` governs load-target policy while transport behavior, redirects included, belongs to the host delegate) — module acquisition awaits it inside `ModuleLoader.ElaborateAsync` (an incomplete download genuinely suspends source processing and resumes it at the same point; the downloader is never replayed), and the elaboration-enabled entry points are the asynchronous ones (`KatLangEngine.RunAsync` + async conveniences, `Parser.ParseAsync(source, options)`). The synchronous source-level entry points remain for downloader-less configurations only and reject a downloader-configured options object with `InvalidOperationException` before parsing (enforced in the synchronous `FrontEndPipeline.Process(source, RunOptions?)`) — never a blocking sync-over-async bridge. Parsing and all other elaboration passes stay synchronous CPU work. Loader traversal is routed: load-free subtrees take the calibrated synchronous walk unchanged; load-bearing spines (marked by a linear pre-scan) take `// MIRROR OF`-tagged async twins; the scan and both walks carry a per-level stack-reserve backstop that turns residual exhaustion into the structured `ModuleElaborationStackExhausted` diagnostic. Downloader error semantics are unchanged (thrown or faulted-awaitable exceptions → `load: failed to fetch` unless the source-processing token is cancelled, which stays authoritative). See `docs/design/async-evaluation-2026-08.md` (Phase 4 section) and `ModuleLoaderAsyncTests`.
- Structural AST depth is a C#-only host-safety policy: every entry point that hands a preconstructed or parsed AST to recursive consumers (evaluator `Run*`, `ParseSyntax`, front-end elaboration, the standalone `ParameterDetector.Detect` / `ImplicitArgumentResolver.Resolve` / `ModuleLoader.Elaborate` boundaries, `SemanticModelBuilder`) must run the iterative `AstStructuralPreflight` FIRST, and a new AST node variant must be added to its child enumeration (it fails loudly on unknown kinds; the base-declared `Algorithm` collections are enumerated uniformly for every subtype). The shared `AstWalker.VisitExpr` switch is fail-loud for the same reason — an unhandled variant would be silently skipped by every walker subclass — and `AstWalkerExhaustivenessTests` pins that its sample table covers every declared `Expr` variant. Two non-raisable tiers: fat-frame consumers (evaluation, front-end elaboration incl. the standalone detector/resolver entry points, semantic modeling) use `EvaluationLimits.MaxSupportedAstDepth`; the small-framed walker-class raw-syntax passes and the measured module-loader traversal use `AstStructuralPreflight.RawSyntaxMaxAstDepth` (the loader also bounds nested module loads CUMULATIVELY against that ceiling — a load site's own traversal depth counts against the module it loads). `MaxAstDepth` may only lower the evaluation tier. Pure-expression spines (unary/binary/index/list and the sequence joins) must stay ITERATIVE in `Eval`/`EvalCounted` (`EvalExpressionSpineCounted`) — the ceiling assumes they consume no proportional stack, and the 384 KiB-thread subprocess pin enforces it. Diagnostic expression-name rendering must stay ITERATIVE and OUTPUT-BOUNDED (`ExprNameRenderer`): the evaluator gates accept arbitrarily long internal join/spread chains, so no diagnostic/optimizer path may render an expression recursively. PARSER recursion budgets are CUMULATIVE across grammar mechanisms: `Parser.MaxNestingDepth` is one weighted per-parse counter that never resets inside a nested container/chain/pattern/call (heavy productions carry calibrated surcharges), its per-shape capacities are proven on 1 MiB threads with ≥2x margin, and a nested module's parse starts with the loader's live-frame stack debt (`Parser.ParseSyntax(source, initialNestingDebt)`) — never add a parser mechanism with its own independent budget or reset. This is distinct from runtime `MaxDepth` and has no Lean counterpart.
- Host ASTs may legally contain SHARED acyclic subtrees (a node referenced from several parents; cycles stay preflight-rejected), and module elaboration itself splices one cached module algorithm at every load site of the same URL. The front-end passes (`ParameterDetector`, `ImplicitArgumentResolver`, `PropertyExposureResolver`, `PropertyDependencyGraphBuilder`, `ModuleLoader` incl. its load-bearing pre-scan, plus the `LoadElaborationGuard`/`FinalPropertyExposure` helper walks) are DAG-SAFE: every walk carries a run-local REFERENCE-IDENTITY memo per constant-context region, so work is bounded by distinct reachable nodes rather than root-to-node paths wherever semantics permit, and rewritten output preserves sharing within one context. Semantics stay tree-equivalent (grace weights accumulate per semantic occurrence through memoized ordered weight effects); the deliberate per-NODE behaviors are diagnostic multiplicity within one diagnostic context and load-site identity within one constant loader context. Load-bearing loader keys include effective live traversal depth because near-ceiling admission is path-sensitive; the same node reached at two such depths intentionally splits. The `ModuleLoader` memo checks live INSIDE the calibrated walk frames — never add a wrapper method or extra async state machine to its recursion spine. A new memoized traversal must keep its explicit variant switch (the memo wrapper adds no dispatch); pinned by `FrontEndDagComplexityTests` and the `AstGraphFuzzTests` front-end shared-vs-cloned campaign. Known residuals (see `SEMANTIC-ALIGNMENT.md`): the resolver's property loop reprocesses shared property VALUES (its signature map mutates between properties), and `Semantics/SemanticModelBuilder` remains per-path.
- EVERY hand-written `Expr` traversal is exhaustiveness-enforced: no silent `_ => expr` / `_ => null` / `default: break` arm may absorb an unknown variant. The front-end rewriting/collection walks (`ParameterDetector` — ProcessOpenExpr, RewriteBinderRefs, CollectFreeParams, RewriteParams, ProcessExpr, FindResolveSpan; `ImplicitArgumentResolver` — ProcessOpenExpr, CollectImplicitDeps, RewriteImplicitCalls, ProcessExprNested; `PropertyExposureResolver.RewriteExpr`; `PropertyDependencyGraphBuilder` — CollectSummarySeed, CollectSiblingDependencyIndices; `ModuleLoader.ProcessExpr` + its async twin) enumerate their intentional leaves explicitly and THROW `InvalidOperationException` on an unhandled variant, and both counted evaluator dispatches (`EvalCounted` / `EvalCountedAsync`) enumerate their sync-delegable leaves (Num, StringLiteral, synchronous NativeCall, Grace) the same way so a new recursive variant can never silently bypass the async twin family. ADDING AN `Expr` VARIANT therefore requires, in the same change: `AstStructuralPreflight` child enumeration, `AstWalker.VisitExpr`, every traversal switch above (classify it: recursive case or intentional leaf), both counted dispatches, and the mechanically pinned classifications in `AstWalkerExhaustivenessTests`, `FrontEndTraversalExhaustivenessTests` (reflection-complete sample table + per-traversal dispatch matrix), and `AsyncEvaluation/AsyncDispatchExhaustivenessTests` (reflection-complete async-dispatch policy table + per-recursive-variant async-seam routing) — those suites fail on any current variant a targeted traversal cannot dispatch, so a missing case is a test failure naming the traversal and variant, never a silent skip.
- Runtime evaluator budgets are OPERATION-LOCAL. Dynamic depth is the only balanced protocol (`EvaluationBudget.TryEnterInvocation` / `TryEnterArgumentEvaluation`, released by `ExitInvocation`); steps, materialized items, and materialized string units are CUMULATIVE and are never refunded by a failure. Two rules hold for every admitted level: a REJECTED enter mutates no counter — not depth, not peak, and not the invocation's own step, because that invocation did not happen (charging it let a lower `MaxDepth` flip an unrelated `MaxSteps` verdict, since a resource-limit failure of a parameter's eager value evaluation is retained on the algorithm binding and the run can continue) — and an ADMITTED level is released exactly once from a `finally`, on success, structured failure, and exceptional unwind. Rejected cumulative work likewise cannot advance auxiliary admission state: in particular, a rejected bulk expression-work step leaves its 4096-checkpoint batch at the boundary so retained errors cannot admit work past an exhausted step budget. `ExitInvocation` is fail-loud on underflow, like `SourceProcessingBudget.ExitModule`: a double release is as damaging as a leak and otherwise invisible. Pinned by `BudgetConservationTests`; `OperationCanceledException` unwind is exercised both by injecting it through the internal `IZeroArgPropertyResultCache` seam and by the real host token. Evaluation host cancellation (`RunOptions.EvaluationCancellationToken`, `Evaluator.Run`/`RunFlat` token overloads) lives ON the run-scoped budget: every budget chokepoint observes the token BEFORE any counter check or mutation (`EvaluationBudget.ObserveCancellation`), each entry point checks it before the structural preflight and again before completing, and the optimized loop executor observes it once per iteration (observation-only — fully-planned iterations touch no charging chokepoint, and charging there would break optimized-vs-generic accounting parity). The completion observation closes final operations that have no later charging checkpoint; `RunFlat` and the engine also observe after their bounded host-atom projection. Requested cancellation THROWS `OperationCanceledException` carrying the supplied token and must NEVER become an `EvalError` — a resource-limit-style structured error would be retained on eager parameter bindings and the cancelled run would continue. An uncancelled token changes no counter, verdict, or result; the token is separate from `SourceProcessingCancellationToken` (front-end only). Pinned by `EvaluationCancellationTests` (deterministic mid-run and completion-edge triggering via CANCELLING — not throwing — cache-seam wrappers).
- The ASYNC evaluation surface (`Evaluator.RunAsync`/`RunFlatAsync`, `KatLangEngine.RunAsync`) is a host-execution surface with NO Lean counterpart, built as a "sync-delegating async twin spine" (`Evaluator.Async.cs`): the synchronous evaluator remains the semantic oracle; engine `RunAsync` first awaits the async front end (`FrontEndPipeline.ProcessAsync` — module downloads may suspend source processing, see the source-loading bullet above), then an async entry point routes ONCE per run — a run whose zero-arg property cache is not async-capable and whose host-operation set has no asynchronous operation executes the synchronous pipeline inline and completes synchronously (never `Task.Run`, never artificial yielding), while an async-capable cache OR asynchronous host operation routes through the internal `async ValueTask` TWIN family. Every twin is marked `// MIRROR OF <sync name>` and MUST be updated in the same change as its synchronous counterpart — the twins re-implement only awaitable child-evaluation sequencing and share every non-evaluating helper. Twin rules: counted-family mirrors only (plain wrappers are counted projections — the Lean-modelled plain/counted value equivalence); the twin root context pins the GENERIC loop/sequence strategies (fail-loud guard `ThrowIfAsyncStrategyPinningViolated`); the two row-loop funnels carry a twin-only `TryEnsureSufficientExecutionStack` backstop because async frames are larger than the calibrated sync frames and structural nesting passes no invocation chokepoint; cancellation is the Phase 1 contract via the shared budget chokepoints (OCE through the returned task, never an `EvalError`). Divergence is pinned by `AsyncEvaluation/AsyncTwinDifferentialTests`: the language-spec + explorer corpora run through the twin path with outcome AND operational-counter equality against the sync generic strategies, plus a genuine-suspension pass; keep that suite green when touching either family. PUBLIC host operations (Phase 3, same version) generalize the Math-module mechanism, not a new subsystem: `HostOperation`/`HostOperations` (`RunOptions.HostOperations`, `Evaluator.Run`/`RunAsync` host-operation overloads) synthesize one ambient prelude property per operation — a parentless wrapper `Algorithm.User` whose body is `Expr.NativeCall("host:" + name, params)` (`':'` keeps host dispatch names disjoint from Math natives) — so resolution, shadowing, arity, and the `A` vs `A()` cache rule are the existing Lean-modelled rules unchanged, and the front end resolves the names through the configuration's extended signature-only semantic prelude (`ParameterDetector.DetectPrevalidated`; a referenced operation never becomes an implicit parameter). The configuration rides the run-scoped `EvaluationBudget`; sync operations dispatch in the shared `EvalNativeCall`, async operations await at ONE guarded `EvalCountedAsync` NativeCall case (invoked exactly once — suspension never replays), and every SUCCESSFUL host return value is normalized into the canonical `Result` representation at the host boundary (`NormalizeHostOperationValue` — the existing `Result.Normalize`, shared by both dispatch paths, applied BEFORE the zero-arg property cache stores the wrapper outcome; failures/cancellation untouched, identity on already-canonical values). Routing is enforced: any async-operation configuration selects the twin path with an async-capable cache (public entries construct one, internal entries fail loud), sync entry points reject async configurations with `InvalidOperationException` before evaluating, and host exceptions/faulted awaitables propagate to the host unchanged (never `EvalError`). Native-call wrapper bodies (Math members AND host operations) read their declared argument names through the shared counted-first dual-view lookup (`LookupNativeArgument`: `CountedParamEnv` first, `valEnv` fallback — the same order as `Expr.Param`), so they work DIRECTLY as flat callback and loop-step references (`map(abs)`/`map(Enrich)`) and a same-named ambient value can never be captured or forwarded to host code in place of the callback-bound argument; the rule covers Math members and host operations together (direct calls are unchanged — flat fixed binding shadows the callee's parameter names out of the counted environment). See `docs/design/async-evaluation-2026-08.md` (Phase 3 section) and `Hosting/*Tests`.
- Qualified canonical Math function references (`map(Math.Abs)`, `reduce(xs, Math.Pow, initial)`) resolve to the SAME runtime native wrapper as the lowercase alias and opened canonical name. Gate this exception on both authoritative Math metadata and the resolved member's actual `Expr.NativeCall` body; every general argumentless `DotCall` keeps its Lean-modeled zero-parameter wrapper identity.
- When semantics change, update all affected layers together: Lean, C# parser/elaboration/evaluator, `src/KatLang/Semantics/`, tests, and user-facing docs.
- Avoid duplicating semantic rules across parser, evaluator, parameter detection, and semantic model code. Reuse the owning logic when possible.
- Plain/counted evaluator ownership (M8+M9): where a plain/counted pair is semantically equivalent, the COUNTED implementation is canonical and the plain implementation is its value projection — first in Lean (`eval` is the one-line total projection of `evalCounted`, which matches every `Expr` variant explicitly with no default arm; the call/dot-call/builtin/lookup plain families are `.fst`/`.alg` projections), then mirrored in C# (`ProjectCountedValue` over the counted twins; the former independent plain call/dot-call/builtin implementations and the resolve-only lookup chain are deleted). Never reintroduce an independently implemented plain evaluator body, and never make a counted function delegate its semantics to a plain one — the deliberate exceptions (C# plain-owned leaves Num/StringLiteral/NativeCall/Grace for the M10 async leaf-delegation contract, the slot-view family, the root-program decoration pair, the opens-free direct lookup used by open resolution) are enumerated in `SEMANTIC-ALIGNMENT.md`.
- Most C# cache-like runtime machinery is implementation-only and should not be mirrored in Lean merely for performance parity. The zero-parameter property cache is the explicit exception: property-style access `A` may use the per-run cache, while explicit call `A()` bypasses that property’s cache entry. This `A` vs `A()` distinction is core KatLang semantics and is modeled in Lean.
- Lean core numeric semantics use `Int`; the C# runtime uses IEEE 754 `System.Numerics.Decimal128` (34 significant decimal digits) end-to-end — literals parse directly into it, arithmetic and every Math function compute in it natively, and there is no `decimal` or `double` stage anywhere in core numerics. Do not silently widen or reinterpret numeric behavior without checking Lean first. Division/modulo by a zero-valued divisor (the EVALUATED value — `1 / 0`, `1 / (1 - 1)`, `1 / -0`, and an underflowed-to-zero divisor all alike) stays the Lean-modeled `divByZero` error and zero to a negative integer power stays an error; everything else follows Decimal128's IEEE behavior (overflow produces a signed infinity, domain violations produce NaN, NaN/±Infinity/−0 are ordinary values). Structural value equality (`==`, `distinct`, `contains`, ValueComparer) uses `Decimal128.Equals` semantics — NaN is one value, quantum is ignored — while the ordering operators are IEEE (comparisons with NaN are false). Transcendental Math results are quantum-canonicalized (IEEE `reduce`, value-preserving) so exact results like `Math.Lg(1000)` stay `3`; ordinary arithmetic is not quantum-canonicalized, so the Decimal128 operation's result quantum remains visible (`0.5 + 0.5` displays `1.0`). Numeric-change ROUTING is two-tier — the "Core numeric semantics" row in `src/KatLang/SEMANTIC-ALIGNMENT.md` is authoritative: Lean-modeled laws on the COMMON EXACT integer subdomain change Lean and C# together with Lean-comparable LanguageSpec coverage, while finite-precision/range behavior (even when the written operands are integers) and other Decimal128-specific behavior are explicit reviewed model divergences pinned by C#-only canonical LanguageSpec cases with `LeanExclusionReason`s (never a fabricated Lean encoding).

## Builtins And Spread Conventions

- `arity` means the structural count of top-level output slots.
- `count` means the number of evaluated top-level values after sequence values are opened by the consuming operation.
- Do not treat `arity` and `count` as interchangeable.
- Terminology: prefix `*` is the COLLECT MARKER; `*name` is a COLLECTING BINDING; in a callable declaration it forms a COLLECTING PARAMETER. Postfix `*` is the SPREAD MARKER; `value*` is a SPREAD EXPRESSION. Infix `*` multiplies. A callable with a collecting parameter may be DESCRIBED as variadic (it accepts a variable number of argument items), but "collecting parameter" is the canonical construct name — never "variadic parameter", "rest parameter", or "rest binding".
- A property/call/builtin RESULT boundary is a value boundary: it always returns ONE value, with emitted count `Result.valueCount` (0 for the empty sequence value, otherwise 1 — a list value always counts 1, including `[]`). A multi-output body/collection is observed by the caller as one sequence value; only an explicit caller-site spread (`expr*`) spreads it back into the surrounding item supply (spread reads the value via `spreadItems` — the spread view that also opens one list boundary — not the emitted count; `toItems` is the non-spread item view and keeps lists opaque). Redundant unary sequence structure is canonicalized during ordinary value construction, including `(())` and `((()))` to `()`. The shared helper is `reCountValueBoundary` (Lean) / `ReCountValueBoundary` (C#); it re-counts the value boundary without rebuilding the value and is applied at user/conditional calls (`evalUserCallCounted`, `evalConditionalCallCounted`) and structural dot zero-arg access (`evalDotCallCounted`). Collection-producing builtins (`order`, `orderDesc`, `distinct`, `take`, `skip`, `filter`, `map`, `range`, `atoms`) materialize ONE exact list value with count 1 via `makeCollectionListResult` / `MakeCollectionListResult` and need no re-count. Collecting bindings likewise store one exact list value with count 1 (`collectSegment` / `CollectSegment`) and need no re-count or raw-supply storage. Lexical zero-arg property access and `if` already re-counted this way; the reduce initial accumulator is likewise reified as one written accumulator slot (`reCountValueBoundary`) before reduction, so an empty reduction returns it as ONE value. NOT value boundaries (must keep their multi-item counts): root/body output accumulation (`evalAlgOutputCountedCore`), `while`/`repeat` multi-slot loop state, and the strict single-value `map`/`reduce` callback contract. Scalar/reduction builtins already return one value and are unchanged.
- Comma is the explicit expression-list separator, and same-line adjacency is an implicit comma where an expression-list context is active, so `1, 2, 3` and `1 2 3` both produce three slots there. A newline is a separate mechanism — a body/statement/output boundary, not a global implicit comma: at root output or inside an explicitly open context it may separate slots (so `1`/`2`/`3` on three lines are three output slots), but a simple one-line property body ends at the newline. Root output consumes a bare expression list as output slots; call syntax consumes it as argument slots; parentheses materialize it as one sequence value. Parsing must not depend on callable arity, runtime values, inferred types, or any other semantic information.
- Semicolon `;` is not supported as expression syntax. It is not an alternative separator or sequence constructor. The parser reports: "Semicolon is not supported as an expression separator. Use comma or adjacency for separate expressions, or parentheses for one sequence value." Use comma/adjacency for separate slots and parentheses for one sequence-valued slot, e.g. `sum((10, 20, 30))`, `take((1, 2, 3), 2)`, and row-like values as `Reports = (row1), (row2)`.
- Postfix continuations win over adjacency on the same physical line only. A `(` or `{` after a callable target on the same physical line is a call delimiter even across whitespace, while a physical newline never continues a closed expression into a call. For multiline calls, open the delimiter before the newline. Indexing `:`, postfix grace `~`, binary operators, and the postfix `*` spread marker are also same-physical-line only (an ATTACHED line-final `*` is a spread; an unattached one is multiplication whose right operand continues on the next line). A leading `.` is the supported method-chain continuation. Definition bodies and open target lists are line-bounded: a newline ends the body, so an expression on a following line — at any indentation — is a separate output row parsed by the surrounding output/algorithm context, never a body continuation. (Same-line adjacency, an already-open delimiter, a same-line binary operator, and a leading `.` still continue the body's single expression. Root output and algorithm/brace bodies, by contrast, keep the expression list open across newlines, so a newline there separates output slots.)
- The star `*` has three roles resolved purely syntactically: prefix COLLECT MARKER in binding patterns, postfix SPREAD MARKER on a completed expression, and infix multiplication — the marker surfaces match the semantic directions `collect : Supply -> ListValue` and `spread : Value -> Supply`. PREFIX `*name` is the ONLY collecting BINDING syntax, valid only in binding positions — explicit parameter lists (`F(*items)`, `F(first, *middle, last)`), nested sequence-value parameter patterns (`F((x, *y, z))`), and assignment deconstruction, including the single-target form `*items = RHS`. The collect marker must be DIRECTLY attached to its binding name (exact source-offset adjacency — no whitespace, comment, or newline between; `* items` is a targeted attachment error that never creates a collecting binding, and `**items` is a repeated-marker error), and exactly one marker forms a binding. Prefix `*` is NOT an expression operator: in expression position it reports a targeted collect-marker diagnostic and recovers to the following operand. The old spellings `name...`, `...name`, `spread(expr)`, and `expr.spread` are NOT KatLang syntax: there is no ellipsis token (`...` lexes as three dot tokens and fails through ordinary parsing) and `spread` is an ordinary identifier with no reserved meaning.
- The spread expression has ONE spelling: the attached postfix marker `expr*`. A same-line star is the SPREAD MARKER exactly when it is DIRECTLY attached to the completed expression's last token AND no valid expression-start token follows it on the star's physical line; when a valid right operand follows, the star is infix MULTIPLICATION regardless of spacing (`a*b`, `a* b`, `a *b`, `a * b` all multiply), and an unattached line-final star is multiplication whose right operand continues on the next physical line (`a *` newline `b`). An attached line-final star is a spread (`a*` newline `b` is a spread row then a `b` row). The marker lowers at parse time to the ONE unary `Expr.SequenceSpread` node (Lean `sequenceSpread`) — never to a Call or DotCall — so there is a single evaluator path, no ordinary call/property value boundary is introduced, and the operand is evaluated exactly once. Chained spread is compositional: `value**` equals `(value*)*` — each extra written star spreads the value that the previous star's supply re-captures at the ordinary expression boundary (`spread` then `capture` then `spread`), so a multi-item supply is a fixed point (`[[1, 2], [3, 4]]**` supplies the two inner lists unchanged) and only a lone structured item opens one more boundary (`[[7]]**` supplies `7`); it is NEVER recursive flattening. `value**next` and `value** next` are targeted errors — the second star is multiplication with a spread operand, never exponentiation. A spread expression is legal ONLY as a whole expression-list slot (root/body rows, call argument slots, group and list elements, definition body slots), as the operand of another spread, or as the FLUENT DOT-CHAIN receiver: `operand*.Member(...)` lowers at parse time to the ordinary LEXICAL call `Member(operand*, ...)` with the spread as the leading argument slot — the receiver is an item supply, not a value, so structural member lookup never applies (`x.Calculate*.Target` builds the same AST as `Target(x.Calculate*)`, and further postfix continuations chain on the call result). GROUPING THE SPREAD CHANGES THE RECEIVER, and the difference is the ordinary capture rule, not a star rule: `A*.F` keeps the spread a SUPPLY and lowers to the lexical call `F(A*)` (items become argument slots), while `(A*).F` is a CAPTURE receiver — ONE leading argument segment whose value is the captured sequence and whose raw supply is the spread items. The two coincide on a collecting callable — the fluent form through ordinary spread slots, the grouped form through the general segment rule (the allocated collector consumes the segment's supply; no callee inspection, no `(A*)`-spelling recognition) — but differ decisively at fixed arity: `A*.count` is an arity error (three argument slots) where `(A*).count` is 3, and at a fixed suffix beside a collector the grouped receiver stays one segment (`(A*).F` with `F(*mid, last)` binds `last` to the whole captured value) where the fluent form supplies separate slots. (`(A)*.F` is different again — that groups only the OPERAND, so it stays the fluent supply form.) Using a spread expression as a unary/binary operand or an indexing target/selector is a targeted parse error with unwrap recovery.
- Dotted-call equivalence is uniform through frontend elaboration: `a.F` is `F(a)`, and `A*.F` is `F(A*)`. This includes lexical resolution and implicit callable-parameter detection, so an unresolved `F` is inferred identically in both spellings; do not add fluent-call origin metadata or a spread-specific inference exception. Parenthesized `(A*).F` remains different because the parentheses make it an ordinary CAPTURE receiver — one leading segment through dot-call lookup (see the receiver-segment rule above), not a pre-lowered spread argument list.
- A spread expression spreads ONE item-producing boundary of the evaluated operand, contributing its items to the surrounding item supply — it does not create, return, or emit a sequence or list value by itself; the RECEIVER decides what the supplied items become (capture materializes a canonical sequence, a collecting binding collects an exact list, fixed bindings receive items individually, calls receive separate argument slots, root output emits rows). Sequence values and exact list values supply their contained items; other values follow the total item-view rule (an atom or string supplies itself as one item). A comma is REQUIRED between a spread and a following same-line supplied item (`A*, B`), because `A* B` is the multiplication `A * B`; an attached line-final spread needs no comma before a following row (`A*` newline `B` is a spread row then a `B` row). `A* ; B` is invalid semicolon syntax.
- Call argument-slot assembly is SHARED by every callable shape — flat fixed, flat/mixed variadic, patterned (repeated-name / sequence-value patterns), and multi-clause conditional (`BuildCallArgumentInputs` in C#, `collectVariadicCallItems` in Lean): each written slot is evaluated EXACTLY ONCE, left to right; every non-spread slot is reified as exactly ONE argument value; and every explicit spread slot spreads exactly one value boundary into ordinary argument slots BEFORE any arity checking, clause selection, or pattern binding. When a patterned callee needs both the combined value of a `Capture` or zero-parameter `AlgorithmExpr` and its explicit written-slot view, BOTH are captured from the same prepared output evaluation (`PreparedAlgorithmOutput` / `evalAlgOutputPreparedCore` or the corresponding capture evaluator) — never by evaluating again or decomposing the combined value. Caller-side spread therefore has identical meaning for every callee representation: `F(A*)` supplies A's spread items as slots whether `F` is flat, patterned, or a clause family (clause selection happens after spreading, so a literal clause such as `F(0, 0)` can win on a spread `(0, 0)` and a one-argument catch-all can never absorb a spread pair). WRITTEN-SLOT REIFICATION is the same rule at every syntax form whose grammar defines one value per written slot — list-literal elements, written sequence-value pattern argument items (`evalExplicitSequenceValueExprSlots` / `EvalExplicitSequenceValueExprSlots`), and the reduce initial accumulator (reified via `reCountValueBoundary` before reduction): a non-spread expression whose counted supply emitted several items (an index projection, a loop result, a counted callback parameter) still contributes ONE value (`S = ((1, 2), (3, 4))` makes `[S:0, 5]` the list `[(1, 2), 5]`; only `[(S:0)*, 5]` splices). Root/body output rows and loop step outputs are NOT written value slots — they keep their multi-item emission semantics (with one documented receiver-specific exception: a sequence-value-PATTERNED loop step's output keeps a top-level spread expression as ONE packed next-state slot, preserving structured state boundaries in both directions — see the loop-step notes in `tutorial.md` and `docs/design/sequence-boundary-audit-2026-07.md`).
- Square brackets construct EXACT immutable list values (`Result.listValue` / `Expr.ListLiteral`), a second collection kind beside sequence values: no singleton/empty canonicalization ever applies to list structure (`[7] != 7`, `[] != ()`), while parentheses around a list stay redundant sequence grouping (`([1, 2]) == [1, 2]`). `[` always begins a NEW expression (never a call/indexing delimiter; `A[1]` is adjacency `A, [1]`), and bracket content is a pure expression list (spread elements insert their item supply; declarations are illegal inside brackets). Spread uses `Result.spreadItems` / `SpreadItems` (opens one sequence OR list boundary). Indexing `:` opens its TARGET through the projection view `Result.projectionItems` / `ProjectionItems` (`[1, 2, 3]:0` is 1 under the same zero-based index rules as sequence selection), while a selected list ELEMENT is returned exactly as stored — one opaque list (`[[1, 2], [3, 4]]:0` is `[1, 2]`; chaining selects one level at a time). Every other NON-spread consumer keeps lists opaque via `toItems` (a list is one item for value boundaries and call binding — calls never open lists implicitly). Deconstruction's `Result.structureItems?` / `StructureItems` opens a lone sequence OR lone list (`x, y, z = [1, 2, 3]`); collecting bindings collect exact lists (see the collecting-binding rule below). The post-binding builtin collection view opens a BOUND list exactly like a bound sequence value (`count([1, 2, 3])` is 3, `A.take(1)` works on a list property; the opening is never recursive — a nested list stays one opaque item; spread supplies ordinary argument slots, so `count([1, 2, 3]*)` is an arity error under the fixed `count(collection)` signature). The `atoms` builtin recursively collects numeric atoms through BOTH sequence and list boundaries (depth-first, left to right; strings contribute none) via its own dedicated collector `Result.languageAtoms` / `LanguageAtoms` and materializes them as ONE exact list through `makeCollectionListResult` (`atoms(7)` is `[7]`, `atoms([1, [2]])` is `[1, 2]`, `atoms('text')` is `[]` — the result kind never depends on the input). Truth testing is deliberately SEPARATE: `truthValue?`/`TruthValue` reads the sequence-only `Result.atoms`/`ToAtoms` view, so lists still have no truth value (`if([1], a, b)` stays invalid) and the atoms traversal can never leak into `if`. Multi-clause conditional sequence-value patterns still match sequence values only (list patterns are deferred, so a list argument takes the fallback clause — except a SINGLETON pattern `(x)`, which matches any one argument whole via the scalar one-item rule, binding `x` to the entire list). Host-boundary flattening (`runFlat` / `Result.hostAtoms`, C# `RunFlat`/`EvaluateToAtoms` via `ToHostAtoms`) opens list boundaries; the truth-testing `Result.atoms`/`toItems` views stay list-opaque. Receiver theorems: `receivers_agree_outside_lone_structure` / `receivers_never_same_on_lone_structure` (unified over both structure kinds via the `loneStructure` predicate, with per-kind corollaries `receivers_never_agree_on_lone_seq` / `receivers_never_agree_on_lone_list` and the concrete `lone_collecting_disagrees_on_lone_list`) in `lean/CoreArityAlgebraProofs.lean`; list-side receiver behavior over the real model is proven by the list bridge laws in `lean/KatLangArityLaws.lean` (e.g. `deconstruct_fixed_single_list_opens`, `lone_collecting_list_call_and_deconstruct_differ`). The CoreArityAlgebra paper artifact now models `Val.list` and `collect` (the pre-list sequence-only extraction is preserved at the pinned paper tag).
- A spread expression is one whole expression-list slot, and the comma rule is a deliberate, narrow exception to optional comma separation: `f(A*, B)` supplies A's spread items and then `B` as separate slots — the comma is required, because `f(A* B)` is the one-argument multiplication `f(A * B)`. To make one sequence-value argument containing a spread plus another value, write `f((A*, B))`.
- Collecting binding COLLECTS an exact immutable list. The three item-supply operations are distinguished by receiver purpose: `capture : Supply -> Value` (ordinary value/output capture — the canonicalizing `Result.normalize` boundary), `collect : Supply -> ListValue` (collecting binding / collecting parameter — `collectSegment` in Lean, `CollectSegment` in C#), and `spread : Value -> Supply` (the spread marker — `spreadItems`). Every collecting binding — single collecting parameters, mixed prefix/collecting/suffix parameter lists, and deconstruction collecting bindings — materializes exactly the assigned item slots as ONE exact list with emitted count 1: zero slots form `[]`, one slot forms `[item]` (NEVER erased, so one remaining structured row stays distinguishable from the row's elements), many form `[a, b, ...]`. Ordinary capture is unchanged (`x = 1, 2, 3` is `(1, 2, 3)`).
- A user-defined top-level collecting parameter collects the argument slots that were actually supplied to the call. `Name(*values) = body` binds `values` to the collected list; a plain `Name(A)` supplies one argument (`values = [A]`), while `Name(A*)` explicitly spreads `A` first (`values` collects A's spread items). The old single-collecting grouped/spread display coincidence is intentionally GONE: `F(A)` and `F(A*)` are observably different for every sequence-valued, list-valued, and empty argument (`F(())` collects `[()]` vs `F(()*)` collecting `[]`). For a scalar atom or string argument the two calls coincide — spread is total, so `7*` supplies `7` itself. `Name()` collects `[]`. A lone `*values` is the degenerate lone-collecting-binding case of this model. Forwarding is ordinary list spread — `Forward(*items) = Target(items*)` (equally the fluent `items*.Target`) re-supplies exactly the collected items (`spread(collect(xs)) = xs`), and passing the collected list unspread passes one list argument; there is no hidden raw-supply metadata, no `variadicSupplyEnv`/`VariadicStreamEnv`, and no provenance tracking. The front-end implicit-argument resolver synthesizes collecting-parameter forwarding as explicit spread arguments for the same reason.
- A parameter list with two or more captures that contains one collecting parameter binds the supplied function-call argument stream: fixed captures bind from the front and back, and the single movable collecting parameter collects the matched middle arguments (possibly zero) as one exact list; a plain function call does not implicitly open a single sequence or list argument. Assignment deconstruction, by contrast, is an unpacking receiver (Python-style): `x, *y, z = RHS` opens one lone sequence- or list-valued shared right-hand-side value and matches its items element-by-element, so `x, y, z = A` splits a stored sequence value or exact list value `A`. A written spread RHS is first captured into that shared value; it usually presents the same immediate items, but a singleton list whose lone element is itself a sequence or list can open one level further after singleton capture (for example, bare `x, y = [(1, 2)]` fails while `x, y = [(1, 2)]*` succeeds). The collecting target then collects its middle items into an exact list by the same rule (`x, *rest = [1, 2, 3]` binds `rest = [2, 3]`; `x, *rest = 1` binds `rest = []`). This unpacking is deconstruction-specific and does NOT change function calls — `F(A)` still passes `A` as one argument and needs `F(A*)` to spread it. The shared front/collecting/back matcher is `bindParameterPatternList` (Lean) / `BindParameterPatternList` in C#); every collecting-binding materialization funnels through `collectSegment` (Lean) / `CollectSegment` (C#) — the plain and counted pattern binders plus the flat-collecting loop path all call it, always producing one exact list with emitted count 1. Item-supply call routing is `Algorithm.usesItemSupplyBinding` / `IsDeconstructionUserCallShape`. Assignment deconstruction is parser-elaborated so the right-hand side is evaluated once into a shared property and each target binds through an inline sequence-value parameter pattern (`SequenceValueParameterPattern`) that opens that single shared value. The same `(x, *y, z)` sequence-value parameter pattern opens one received value for parameter/callback-position destructuring. Flat callbacks with a top-level collecting parameter bind through the shared binder too (`bindCountedCallbackParameterPatternList` / `BindCountedCallbackParameterPatternList`): a single-collecting callback keeps each iterated element as ONE collected slot (`[7].map(Collect)` binds `items = [7]`; `[(1, 2)].map(Collect)` binds `items = [(1, 2)]`), while a multi-parameter flat callee first opens a lone SEQUENCE-valued element into row slots (the flat-callback row convention; exact-LIST elements stay opaque and arity-error in flat binding — the nested `F((x, *y, z))` pattern form is the tool that opens BOTH kinds) and then allocates prefix/collecting/suffix (`Rows.map(F)` with `F(x, *y, z)` on sequence row `(1, 2, 3, 4)` binds `y = [2, 3]`, agreeing with the nested form on sequence rows only). Only the sequence-value pattern's scalar-element fallback stays strict (callback deconstruction for scalar elements deferred). The front-end implicit-argument resolver synthesizes forwarding spread only when BOTH the destination capture is collecting AND the source binding of that name is a collecting binding: `Use(items) = Target` with collecting `Target(*items)` elaborates to `Target(items)` (one argument; `Use([1, 2])` is `[[1, 2]]`), a caller collecting parameter `Use(*items) = Target` (collecting `Target`) elaborates to `Target(items*)`, and a collected-list source forwarded into a FIXED destination parameter passes the collected list as one argument (a fixed destination never re-spreads the list).
- Ordinary lexical dot-call injects the receiver as one leading argument segment (the receiver-segment rule above): allocation matches `B(A, C, D)`, a fixed parameter binds the receiver as one value, and only a flat top-level collecting parameter allocated the segment consumes its supply. For collection builtins the receiver fills the fixed `collection` parameter (`A.take(2)` is `take(A, 2)`, `A.count` is `count(A)`), with no builtin-specific receiver placement.
- Collection builtins are ordinary FIXED-ARITY callables that receive exactly ONE fixed `collection` parameter followed by fixed control parameters: `count(collection)`, `sum(collection)`, `first/last/min/max/avg/order/orderDesc/distinct(collection)`, `take/skip(collection, count)`, `contains(collection, item)`, `map(collection, mapper)`, `filter(collection, predicate)`, `reduce(collection, reducer, initial)`. An unspread sequence or list value is ONE argument at this call boundary like at every other call boundary, and NOTHING is opened before binding — `count(1, 2, 3)`, `count()`, `sum(A*, B*)`, `take((1, 2, 3))` (missing count), `take([1, 2, 3]*, 2)`, and `distinct((), ())` are ordinary arity errors (spread only supplies ordinary argument slots that obey the same fixed arity; re-group to pass spread items as one collection: `sum((A*, B*))`). The bound collection value is interpreted through the POST-BINDING one-level collection view (`builtinCollectionItems` / `BuiltinCollectionItems`): a lone sequence OR exact list opens one outer boundary and any other value is a one-element collection — `count((1, 2, 3))`, `count([1, 2, 3])`, and `Values.count` are 3, `count(7)` is 1, `count(())`/`count([])` are 0, and opening is never recursive (`count((1, [2], 3))` is 3, `count(([], []))` is 2). Item shape/empty policies apply to the viewed items (`sum` numeric constraint, `first` non-empty). Collection-producing builtins (`filter`, `map`, `order`, `orderDesc`, `distinct`, `take`, `skip`, `range`) materialize their kept/projected items as ONE exact immutable list via `makeCollectionListResult` / `MakeCollectionListResult`: zero items form `[]`, a single kept item forms `[item]` (never erased, so `take(((1, 2), (3, 4)), 1)` is `[(1, 2)]` and `distinct(((), ()))` is `[()]`), and nested sequence/list elements stay exact — the result kind never depends on the input kind, and only an explicit `spread` re-spreads the list into the arity layer. Canonical arity capture (`combineOutputSlots`, ordinary construction) and spread are UNCHANGED by this model, and collecting binding produces the SAME exact-list kind (`collectSegment`) — collecting parameters remain a general arity mechanism for user functions, and passing a collected list to a builtin unspread passes it as the one collection argument (`Qmean(*args) = args.sum / args.count` works because the post-binding collection view opens the bound list; `map(values*, f)` inside a body is an arity error — write `map(values, f)`). Callback/builtin execution stays a separate runtime-owned phase after binding.
- Sequence builtins and spread behavior must stay consistent across Lean and C#.
- Changes to builtins, preludes, intrinsic metadata, or sequence syntax require synchronized updates in evaluator, front-end assumptions, semantics, tests, tutorial, EBNF, and generator guidance.

## Editor Semantics
- `src/KatLang/Semantics/` derives editor-facing meaning from parsed and elaborated ASTs.
- Build semantic models from `Parser.Parse(...)` / `ParseResult`, not from raw syntax.
- Only source-backed identifiers may produce semantic sites, resolutions, declarations, or spans.
- Synthetic constructs must not invent source spans.
- If editor-visible behavior changes, update `src/KatLang/Semantics/` and `tests/KatLang.Tests/SemanticModelTests.cs` together.
- Preserve exact source-span invariants for hover, references, go-to-definition, classification, and callable-property metadata.
- Scope visibility is completion's semantic source: `SemanticModel.ScopeVisibilities` / `GetVisibleSymbolsAt` and `PreludeCatalog` must enumerate exactly what ownership-first lookup resolves — same shadowing, open dedup, same-level open ambiguity suppression, and direct-beats-open prelude precedence as `ElaboratedScopeLookup`. Scope regions are source-span hulls; a load-elaborated module subtree (`Algorithm.User.IsModuleElaborated`, set by `ModuleLoader`) emits no regions because its spans belong to the module's source text. Builtin names/signatures for editors come from `PreludeCatalog`, never hardcoded lists.

## Testing Expectations

- Prefer minimal, semantics-preserving, reviewable changes.
- Add or update focused tests near the changed layer.
- Include negative coverage when failure modes are meaningful.
- When changing language behavior, update Lean tests and C# tests together.
- If a change crosses parser, evaluator, semantics, or docs boundaries, cover the affected layers in the same task when feasible.
- **A source-based evaluator test must PARSE CLEANLY, and must assert the error TYPE, not merely that something failed.** `Parser.Parse(source).Root` silently discards diagnostics, so a test whose source the parser rejects still evaluates the recovery tree and can pass for an unrelated reason — that is how a `NotPublicProperty` regression passed without ever reaching the branch, and how 41 `EvaluatorTests` came to run on illegal source. Use `SourceProvenance.ParseValid(...)` (or `EvaluatorTestSupport.ParseValidRoot`) for ordinary source semantics; `SourceProvenance.ExpectFrontEndError(...)` when the parser/elaborator is the subject; `SourceProvenance.ParseAllowingDiagnostics(...)` only where malformed source is the point (recovery, fuzz, editor tooling). Never assert an evaluator outcome on a source you have not shown to be legal.
- **Before writing a source test for an evaluator branch, check the branch is surface-reachable at all.** Front-end elaboration can make it dead: clause-family elaboration turns every single-clause binder form into an `Algorithm.User`, so the flat-binder arm of `ConditionalValueAccessError` cannot be reached from any written program, and implicit-parameter promotion hides the dotted-`open` visibility checks. A source test for such a branch passes while the branch stays dead — pin these from a prebuilt AST instead (`EvaluatorDefensiveBranchTests`).

## Documentation Expectations

- Update `KatLang.ebnf` when lexer/parser grammar changes. Its identifier/keyword terminal claims are mechanically checked by `EbnfLexicalSyncTests`: changing identifier characters or the keyword set requires updating the lexer, the EBNF, and the independent contract tests together; harmless wrapping and alternative reordering are not policy changes.
- Update `tutorial.md` when user-facing behavior changes.
- Update generator-facing files when syntax, builtins, `open`/`load`, or recommended code-generation idioms change.
- In this repo that usually includes `.github/agents/katlang-generator.agent.md` and any related generator prompt assets.
- When generator guidance changes, explicitly check both `.github/agents/katlang-generator.agent.md` and `experimental/prompts/katlang-generator.txt`.

## Coding Guidance

- Prefer small changes that fix the root semantic issue without widening scope unnecessarily.
- Do not introduce new AST shapes unless strongly justified by Lean or an existing architectural boundary.
- Preserve the current parser/evaluator/tooling boundaries instead of re-encoding the same rule in multiple places.
- Keep diagnostics structured, source-positioned, user-friendly, and phrased in KatLang terms.
- If a change is implementation-only optimization, say so explicitly.

```powershell
Pop-Location
```

Lean CoreTests now use `#guard` for semantic assertions, so a failing assertion fails `lake build CoreTests`. Remaining `#eval` lines are demo/inspection output only.

`validate-all.ps1` is a VERIFICATION command and is observational: before it builds or tests anything it removes every `KATLANG_REGENERATE_*` environment variable from its own process (the whole prefix, case-insensitively; the original values are restored on exit), so a regeneration flag inherited from the calling shell can never make a green validation run rewrite a tracked generated artifact. Regenerating a generated artifact (`lean/LanguageSpecCases.lean`, `lean/SemanticExplorerCases.lean`, the generator prompt blocks, `tests/KatLang.Formatting.PublicApi.Tests/PublicApiBaseline.txt`) is always a separate, targeted `dotnet test` run with that artifact's flag set to `1`; the run WRITES the artifact and then FAILS BY DESIGN (also when the content did not change), so it can never be mistaken for a verification — review the diff, clear the flag, and rerun the normal verification. The flag registry and the write-then-fail contract are `RegenerationFlags` / `ArtifactRegeneration` in `tests/KatLang.Tests/Infrastructure/ArtifactRegeneration.cs` (shared as source with the public-API test project); a new `KATLANG_REGENERATE_*` variable must be registered there — `ArtifactRegenerationPolicyTests` scans the repository for unregistered names and for tests that read a flag outside the helper.

## Continuous Integration And Releases

- `.github/workflows/validate.yml` is automatic for pull requests and pushes to
  `main`, and can also be dispatched manually. Its stable required-check names
  are `.NET validation` and `Lean validation`; both invoke the phase boundary
  above rather than duplicating commands in YAML.
- `.github/workflows/release.yml` is manual-only. Dispatch it from `main` with
  the version already present in `KatLangVersion.props`. A push, merge, or tag
  never publishes a release automatically.
- The release workflow validates the exact dispatched commit, builds and runs
  the NativeAOT CLI on native Windows/Linux/macOS x64 and ARM64 runners,
  packages the tested executable with the root `LICENSE`, `NOTICE`, and
  `PATENTS` files, collects all six archives, produces `SHA256SUMS`, and only
  then creates the tag and publishes the GitHub Release.
- `KatLangVersion.props` remains authoritative. Workflow code must never pass
  an MSBuild version override, create/move an existing version tag, or replace
  an existing release.
- Normal jobs have `contents: read`. Only the final publication job has
  `contents: write`; workflows use no user-managed secrets. External actions
  are pinned to immutable commit SHAs and `.github/dependabot.yml` proposes
  reviewable GitHub Actions pin updates.

`lean/SemanticExplorerCases.lean` is a GENERATED Lean/C# differential corpus — do not edit it by hand. A failing `#guard` there is a Lean/C# divergence (or a Lean-internal plain/counted evaluator mismatch) on that case. After an intentional semantics change, regenerate it with `$env:KATLANG_REGENERATE_SEMANTIC_EXPLORER = "1"; dotnet test .\KatLang.slnx --filter SemanticExplorerLeanArtifact` (writes, then fails by design), review the diff, and rebuild the Lean target. See `docs/design/sequence-boundary-audit-2026-07.md`.

## Public API Baseline And Release Version

- `tests/KatLang.Formatting.PublicApi.Tests/PublicApiBaseline.txt` is the checked-in, deterministic rendering of the COMPILED public surface of the `KatLang` assembly — the one assembly the NuGet package ships — reflected by `PublicApiSurfaceRenderer` in that deliberately non-friend test project: every exported type plus consumer-reachable protected nested types, with base/interfaces, generics and constraints; every consumer-visible member with parameter names, modifiers, defaults, nullable annotations and nullable-flow attributes; and every public enum member with its exact numeric value. `PublicApiBaselineTests` compares exactly and never rewrites; a difference is a NuGet surface change. Record an intentional change with `$env:KATLANG_REGENERATE_PUBLIC_API = "1"; dotnet test .\KatLang.slnx --filter PublicApiBaseline` (writes, then fails by design), review the diff as the compatibility review, clear the flag, rerun. Regenerating the baseline never changes the release version; the focused hand-written contracts in that project (`PublicElaborationSurfaceTests`, `PublicFormatterExtensionTests`) stay beside it.
- `KatLangVersion.props` is the ONE place the release version is written. `src/KatLang/KatLang.csproj` (package and assembly version), `src/KatLang.CLI/KatLang.CLI.csproj` (which builds against the KatLang PROJECT, so it cannot lag onto a previously published package) and `tests/KatLang.CLI.Tests` (which bakes the value in as `IntendedKatLangVersion` assembly metadata — build intent, never read from the KatLang assembly under test) derive from it. `ReleaseVersionSourceTests` rejects any other version literal in an MSBuild file and any in-repository `PackageReference` to KatLang; the CLI version tests compare the loaded runtime, the CLI assembly and `--version` against the intended metadata, so a stale or mismatched artifact fails rather than passing against itself.

## Executable Language Specification

- `tests/KatLang.Tests/LanguageSpec/LanguageSpecCorpus.cs` is the canonical executable specification: named cases with stable IDs and HAND-WRITTEN canonical expectations. Never regenerate its expectations from observed behavior — a failing `LanguageSpec*` test means either fix the implementation or edit the canonical case in a reviewed diff.
- Same-program fidelity (M11): the Lean program of every Lean-comparable case in BOTH differential corpora (`LanguageSpecCorpus` and `SemanticExplorerCorpus`, internal-node cases included) is DERIVED from the source's real elaborated AST through `tests/KatLang.Tests/LeanAstEncoder.cs` — never authored by hand and never rebuilt by test-side parser-rule templates. C#-only cases carry an explicit non-blank `LeanExclusionReason`, a hand-authored LanguageSpec Lean program requires the exceptional `LeanProgramOverride` + `LeanOverrideReason` (currently unused), and per-corpus exact-ID exclusions plus `FidelityRatchet_*` tests pin the derived-case partitions. The encoder is FAIL-LOUD: extend it deliberately (with reviewed goldens in `LeanAstEncoderTests`) rather than approximating, and expected strings in encoder tests are manually reviewed constants. See `docs/design/executable-language-spec.md` §5.
- GENERATED from it (do not edit by hand): `lean/LanguageSpecCases.lean` and the `=== BEGIN GENERATED: katlang-spec-examples ===` block in `.github/agents/katlang-generator.agent.md` and `experimental/prompts/katlang-generator.txt`. Regenerate all three with `$env:KATLANG_REGENERATE_LANGUAGE_SPEC = "1"; dotnet test .\KatLang.slnx --filter LanguageSpecArtifacts` (writes, then fails by design), review the diff, then `lake build LanguageSpecCases`.
- Tutorial examples marked `<!-- spec:case-id -->` are verified against the corpus (source and expected output) by `TutorialSpecTests`; when changing a linked example, update the canonical case and the tutorial together.
- EVERY tutorial fence followed by a `**Result(s):**` claim is executable documentation (M13): `TutorialResultSweepTests` runs it through `KatLangEngine.Run` and display-matches the claim — no marker needed, so an ordinary new example enters the sweep automatically. A genuinely non-standalone example (e.g. one needing a network downloader) carries `<!-- spec:skip nonblank reason -->` before the fence; the skip inventory is exact-pinned, and result-bearing coverage is monotonic (pinned minimum baseline — removing an existing claim requires a reviewed ratchet reduction, while additions need no pin edit). The shared grammar lives in `TutorialCorpus` and fails loudly on malformed/detached claims, so a result claim can never silently drop out of verification.
- When language behavior intentionally changes, update the affected canonical cases in the same task as the Lean/C#/tutorial/generator changes.
- Maintainer guide: `docs/design/executable-language-spec.md` (partitions, counts, how to add cases, worked example).

## Lean/C# Semantic Alignment

Before editing, classify the change using `src/KatLang/SEMANTIC-ALIGNMENT.md`.

- Observable semantics require Lean consideration and usually Lean updates/parity tests.
- C# implementation/tooling-only changes require C# tests; Lean updates are not required.
- Optimization-only changes do not change Lean, but require equivalence tests against the generic path.
- Diagnostic wording-only changes do not require Lean if the structured error kind/payload is unchanged.
- Numeric changes split by tier (the manifest's "Core numeric semantics" row): Lean-modeled laws on the common exact integer subdomain (exact integer arithmetic/comparison, the representative truncating `div`/`mod` cases, the zero-divisor rule where applicable, `0 ^ negative-int`, structural equality, truth testing) change Lean and C# together with Lean-comparable LanguageSpec coverage. Decimal128-specific behavior (finite precision/range even for integral inputs, fractional values and quantum, NaN, ±Infinity, signed zero, overflow to infinity, gradual underflow, IEEE ordering of specials, non-exact `/`/`avg` results) is an explicit reviewed model divergence — C# tests plus a canonical C#-only LanguageSpec case with a `LeanExclusionReason`, never a fabricated Lean encoding. Do not classify from source spelling alone: "integer input" is not sufficient once a Decimal128 operation rounds or overflows.
- Grammar or AST changes usually require Lean review.

If in doubt, the manifest's "Lean update required?" column is authoritative. If Lean is silent or ambiguous, stop and ask.

## Do Not

- Do not silently change language semantics.
- Do not let Lean and C# diverge.
- Do not treat `AGENTS.md` as a long design essay.
- Do not let multiple agent-instruction files drift into conflicting guidance.
- Do not add convenience syntax, hidden fallbacks, or duplicated semantic logic just to make a local change easier.
