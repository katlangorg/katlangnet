## Grace + DotCall semantic laws (normative)

These laws pin the final Grace + DotCall architecture. They are stated once, here, because collapsing them into one rule (ordering inferred from fallback-call assembly, extension-specific resolution modes) is a known drift direction; the separations below are what prevent it. The manifest row "Dot member/fallback binding and Grace composition" carries the Lean/C# ownership mapping; this section is the normative statement.

### 1. Grace is frontend-only

The law: `Expr.Grace(Inner, Weight)` is a front-end parameter-ordering annotation on exactly one bare name occurrence, and nothing downstream of parameter elaboration ever observes it.

- `Expr.Grace` may exist only in the raw/frontend AST; source-valid Grace wraps a single `Expr.Resolve` occurrence.
- Prefix `~x` contributes weight −1 per marker: the inferred parameter moves one position EARLIER.
- Postfix `x~` contributes weight +1 per marker: the inferred parameter moves one position LATER.
- Repeated markers and repeated graced occurrences of the same name SUM (`~~x` is −2; `~x~` nets 0 and produces no node). The general arithmetic is `ParameterDetector.ApplyGraceReordering`: one swap per weight unit; movement stops at the parameter-list boundary or against a neighbor whose same-direction weight is equal or more extreme; excess movement is silently ignored, never an error.
- Grace applies only to a bare name/parameter occurrence, never to a compound expression (§8).
- Grace changes ONLY inferred parameter ordering (`Algorithm.User.Params`); it never changes resolution, selection, evaluation, or output.
- Grace MUST be consumed during parameter elaboration: `ParameterDetector` collects the weights and strips the wrapper, `DotCallElaborationInvariant` rejects any survivor, and an `Expr.Grace` reaching the evaluator is host-API defense only (see the defensive-branch entry below), never a language state.
- No `Expr.Grace` node and no Grace provenance flag of any kind survives into the executable AST.

Lifecycle:

```text
source
  ↓
raw AST (Parser.ParseSyntax) — may contain Expr.Grace
  ↓
ParameterDetector (CollectFreeParams) — free-name occurrences in semantic source order; Grace weights summed per name
  ↓
ApplyGraceReordering — establishes Algorithm.User.Params
  ↓
Grace stripped (occurrences rewritten to ordinary Param/Resolve; DotCallElaborationInvariant rejects survivors)
  ↓
executable AST
  ↓
Evaluator / Optimizer / Lean (Expr.dotMember) — no Grace, no Grace provenance
```

### 2. The ordinary DotCall law — the only runtime law

```text
R.F(args...)

1. evaluate R once;
2. if the resolved receiver structurally owns member F, use it;
3. otherwise resolve the stored lexical fallback F;
4. invoke the fallback as F(R, args...) — the receiver enters as ONE leading
   argument segment (receiver-segment rule; see the compositional dot-call
   collecting receiver entry below).
```

The invariant: this is the ONLY runtime DotCall law. There is no runtime "extension-dot" mode, no resolution-mode bit, and no second dispatch path for any spelling. The `.string` intrinsic and the dotted sequence-builtin views are established arms of this one law, not modes.

### 3. Four independent semantic questions

Four questions, four owners. They must not be collapsed into one rule.

1. **Fallback participation** — "Can lexical fallback be needed?" Owned by the shared classification `AstHelpers.GetLexicalFallbackSelection` (`LexicalFallbackSelection.Never / Conditional / Always`). Implicit-signature construction includes the member's fallback occurrence when selection MAY happen (`Conditional` or `Always`); exposure/dependency charging requires MUST (`Always` only). MAY and MUST are different projections of the same fact and are never interchangeable.
2. **Source occurrence ordering** — "Where does the participating free-name occurrence appear in the semantic source traversal?" For a DotCall the traversal is: receiver occurrences, then the participating member/fallback occurrence, then written argument occurrences. Implicit parameter order follows first semantic source occurrence (`ParameterDetector.CollectFreeParams`).
3. **Grace reordering** — "How does Grace modify the already-established inferred parameter order?" By the ONE ordinary prefix/postfix weight mechanism of §1, identically in every syntactic context. No construct gets its own permutation rule.
4. **Runtime dispatch** — "At execution time, does structural lookup win or is lexical fallback invoked?" Owned by `Evaluator` alone, decided per evaluation, independent of inferred parameter order and of Grace.

### 4. Source occurrence order is not fallback invocation order

Do not infer implicit parameter order from runtime lexical-fallback invocation order.

```text
a.t    has semantic source occurrence order (a, t)
```

even though the selected fallback executes conceptually as `t(a)`. Therefore:

```text
source occurrence order != fallback invocation order
```

This is a permanent architectural law, and its violation is a known regression class: question 2 of §3 is answered by the source traversal, question 4 by the runtime, and neither answers the other.

### 5. Grace + DotCall composition

There is no semantic concept of an "extension property call with Grace". The graced dot spellings compose from ordinary Grace (§1) and the ordinary DotCall (§2), and their parameter order falls out of §3. Informal names such as "extension call" in tests, fuzz families, and the patents refer to the dotted SPELLING, never to a separate semantic category.

`a.t` — base occurrence order `(a, t)`, inferred params `(a, t)`. Raw conceptual AST (`Args = null` is property-style access; `Args` omitted below):

```text
DotCall(
    Target = Resolve("a"),
    Name = "t",
    Args = null,
    LexicalFallback = Resolve("t"))
```

`a~.t` — postfix Grace on `a`, then ordinary DotCall:

```text
DotCall(
    Target = Grace(Resolve("a"), +1),
    Name = "t",
    LexicalFallback = Resolve("t"))
```

Base `(a, t)` becomes `(t, a)`: postfix Grace moves `a` one position later.

`a.~t` — ordinary DotCall with prefix Grace on the fallback/name occurrence `t`:

```text
DotCall(
    Target = Resolve("a"),
    Name = "t",
    LexicalFallback = Grace(Resolve("t"), -1))
```

Base `(a, t)` becomes `(t, a)`: prefix Grace moves `t` one position earlier.

### 6. Same executable body after elaboration

The invariant: after parameter elaboration, valid `a.t`, `a~.t`, and `a.~t` in the same lexical environment have the SAME ordinary executable DotCall body:

```text
DotCall(
    Target = Param("a"),
    Name = "t",
    LexicalFallback = Param("t"))
```

Only the enclosing `Algorithm.User.Params` may differ. Consequences:

- Grace does not bypass structural lookup.
- Grace does not force lexical fallback.
- Grace does not lower a DotCall to a direct `Call`.
- Grace does not alter `.string`.
- Grace does not alter dotted sequence-builtin semantics.
- Grace does not alter optimizer or runtime dispatch.
- Lean needs no Grace or extension runtime form: it receives `Expr.dotMember` with the elaborated fallback and the finished parameter list.

### 7. Constitutional examples

Semantic laws, not implementation tests (pinned by `GraceEligibilityTests`, `GraceDotCompositionTests`, and the LanguageSpec `grace-dot-*` cases):

```katlang
K = a.t
K(7, {x+1})
# 8
# inferred params: (a,t)
```

```katlang
K = a~.t
K({x+1}, 7)
# 8
# inferred params: (t,a)
```

```katlang
K = a.~t
K({x+1}, 7)
# 8
# inferred params: (t,a)
```

```katlang
K = (x+y)+~z
# inferred params: (x,z,y)
```

Structural-collision law: when the receiver owns the member,

```text
Obj.t
Obj~.t
Obj.~t
```

must all select the SAME structural member. Grace never converts a structural hit into a fallback call.

### 8. Grace eligibility

The law: `~x` and `x~` operate on ONE bare name occurrence. Compound Grace is unsupported — `~(x+y)`, `(x+y)~`, `f(x)~`, `x.y~`, `[x]~`, `5~` are parse errors, and no ordering semantics are ever assigned to a multi-name operand.

The compositional consequence — decided by the one-name law itself, not by any special extension-receiver rule:

- `(x+y)~.t` is INVALID: the postfix marker would decorate the compound receiver `(x+y)`.
- `(x+y).~t` is VALID: the prefix marker decorates the bare fallback/member occurrence `t`.

The dot contributes nothing to eligibility.

### 9. Do not reintroduce

- `ExtensionOnly` runtime resolution, or any extension-specific DotCall runtime mode.
- Lowering `a~.t` (or any graced dot) to a direct `t(a)` call.
- Synthetic "extension receiver Grace" injected by the parser or elaboration.
- Extension-specific parameter swapping outside the one general Grace pass.
- Parameter ordering derived from fallback call assembly (§4).
- Runtime branches keyed on whether the source spelled `~.`.
- Semantic provenance such as `IsExtensionReceiver` — unless a strictly parser/recovery-only source fact is genuinely necessary, and then it must remain a frontend syntax concern and must not create a new semantic category.

Syntax-specific parser handling for adjacency or recovery is legitimate frontend work; it never becomes a semantic mode.

## Published API compatibility corrections

- Package `0.8.159` exposed a provisional runtime-extension model through public `DotResolutionMode`, `Expr.DotCall.ResolutionMode`, `Expr.DotCall.ExtensionMarkerSpan`, `DotCallContext.IsExtension`, and the protected `AstWalker.VisitExtensionDotMarker` callback. Package `0.8.161` removes those members and `Expr.Grace.IsExtensionReceiver`: all represented source-origin state that the compositional language does not have. `a~.t` is ordinary postfix Grace on `a` followed by ordinary dot; `a.~t` is prefix Grace on the fallback occurrence `t`. Both elaborate to the same DotCall body as `a.t`, with Grace observable only through the inferred parameter list. This is an intentional source/binary compatibility break for consumers that adopted the provisional surface. Ordinary `Expr.DotCall` construction and `LexicalFallback` remain supported.
- Two OBSERVABLE language corrections ship in `0.8.161` and change results for existing programs. First, a dot member no longer silently loses to nothing: an edge whose lexical fallback may be selected contributes its callable to the enclosing implicit signature at its semantic source position (`K = a.t` is now `K(a, t)`, previously arity 1 and uncallable), and where the fallback is statically certain but unresolvable — a memberless receiver such as `Math.Rand`, `A.X` on a value property, an alias wrapper, or `(Obj).V` — the member now becomes an implicit parameter rather than an immediate unknown-member error at runtime. A CLOSED explicit parameter list is unaffected, so `Get(obj) = obj.size` keeps arity 1 and still reports the unknown member at runtime. Second, Grace never changes member selection: `Obj~.V`, `x~.string`, and `S~.count` agree with their ungraced spellings (structural member, string intrinsic, dotted builtin view) where `0.8.160` routed them to a lexical call; their inferred parameter order follows ordinary prefix/postfix Grace.

## Known gaps

- Lean semantic assertions in `lean/CoreTests.lean` use `#guard`, so regressions fail `lake build CoreTests`. Remaining `#eval` commands are demo/inspection output.
- Automated C# <-> Lean output comparison exists for a bounded generated corpus: `lean/SemanticExplorerCases.lean` (generated by `tests/KatLang.Tests/SemanticExplorerLeanArtifactTests.cs`) pins the value/receiver corpus — currently 1,559 surface cases, of which 1,528 are Lean-representable (31 are parse-level exclusions), plus 14 internal-node cases, yielding 1,542 case guards and two partition-count guards — to C#-observed raw structure, emitted count, and error category; `lake build SemanticExplorerCases` fails on any divergence, and each case also cross-checks Lean's plain (`runResult`) vs counted evaluators. - Whole-value `Result` traversals are also DAG-BOUNDED, not path-bounded, wherever a shared node can be revisited — because a value is a DAG, not a tree. An immutable child may be reached through many parents (`W = [x, x]`, `A = W.repeat(n, 1)` builds n+1 distinct nodes reachable through 2^n root-to-leaf paths in n in-budget steps), and a walk whose work is proportional to PATHS is exponential on such a value while no evaluation step budget bounds it: the blow-up happens inside ONE value-level operation, which consumes no steps. The August 2026 follow-up memoized the two walks a shared node can blow up — `Result.ValueComparer` equality and hashing (`==`/`!=`, `contains`, `distinct`, and the repeated-bind equality checks) — by REFERENCE IDENTITY, scoped to ONE top-level operation: equality expands each ordered `(leftReference, rightReference)` pair at most once, and hashing computes each node's structural hash at most once. Measured on the doubling DAG: 33,554,431 pair expansions (5.7 s) at depth 24 before, 25 (0.06 ms) after, with hashing the same; +2 depth multiplied the old work by 4 and now adds 2. Reference identity is essential and is the same discipline `AstStructuralPreflight` uses for shared expression nodes: keying either memo on value equality or on the structural hash would re-enter the walk it exists to bound. The memos are the one deliberate exception to the O(nesting depth) auxiliary-storage rule above — O(distinct nodes or pairs actually reached), never O(paths) — and are allocated lazily on the first nested descent, so flat values still allocate none and the wide-flat allocation ceilings are unaffected. Memo lifetime is exactly one call: nothing is cached on a `Result`, so a second `GetHashCode` recomputes the graph. Hashing had to become COMPOSABLE to be memoizable at all (each node mixes its kind tag, child count, and its children's hashes, instead of streaming every reachable leaf token into one accumulator in pre-order — a shape whose subtree contribution cannot be replayed without re-walking the subtree). That changes hash VALUES, which are not observable and never were: `System.HashCode` is seeded per process, so they already differed between runs, and no KatLang result depends on them (`distinct` preserves input order and uses its set only as a duplicate filter). The `Equals`/`GetHashCode` contract is preserved by construction — equal values have the same kind tag and child count and pairwise-equal children, so by induction they fold to the same hash. Equality results, error kinds, produced values, and plain/counted agreement are unchanged, so this is implementation complexity only and Lean (whose `dedupList` is a quadratic structural scan with no hashing and no complexity contract) needs no update. Regression coverage: `SharedValueGraphComplexityTests` (exact work counts through the passive `ValueTraversalObservations` observer, memo-key discrimination, hash/equality contract over shared vs rebuilt graphs, and language-level `==`/`contains`/`distinct`/repeated-name-binding cases at depth 40 under both evaluators). `Result.Normalize` was the third walk of this class and is closed by the follow-up below, as is `Evaluator.FormatResultForDiagnostic` — a different class, bounded rather than memoized, two follow-ups below — and `Evaluator.ResultToExpr`, the last memoizable walk of the class, closed by its own follow-up below. The atom views were the last walks of this class and are closed by their own follow-up below: truth testing searches for its FIRST atom instead of materializing the per-path collection, and the bounded collectors memoize atomless subgraphs — their per-path OUTPUT stays a real materialized collection charged per collected item by the collection budget, which is exactly why only zero-atom nodes may be skipped.

- Value-PRODUCING `Result` walks must be DAG-bounded in their OUTPUT as well as in their work. `Result.Normalize` was the last duplicated-work walk named above: a post-order rebuild with one frame per PATH, which on the doubling DAG cost 2^(n+1) - 1 node expansions and — worse than the scalar walks — MATERIALIZED that many fresh `Result` nodes, converting a compact DAG into the exponentially larger tree its paths spell out and handing that tree to every later operation. Each load site now charges its own traversal path depth (plus a fixed splice-frame allowance) against `ModuleLoader.MaxTraversalDepth`, judging the fetched module's tree iteratively BEFORE descending; an unsafe nesting is the structured `load: … cumulative structural depth limit` diagnostic plus the load's established placeholder, with the module's committed source reservation kept exactly like a module that fails to parse, and the base restored via `finally` on every unwind (downloader failure, cancellation, nested rejection). Cache hits splice without re-fetching, parsing, or recursively traversing the cached module, but the complete result is re-gated before the loader's elaboration boundary returns so a shallow cache entry cannot become unsafe at a deeper splice path. Nested-module PARSING is bounded by the same policy: every nested `Parser.ParseSyntax` call starts with a conservative stack debt converted from the live traversal levels, so the parser's cumulative recursion budget bounds loader frames plus parser frames together (see the parser-recursion note above for the combined proof and boundaries) — no module source accepted for parsing at any permitted load position can overflow the documented envelope.
  - Parser output remains byte-identical in raw AST, spans, and parser diagnostics for input admitted by the current parser limits. Successful deterministic behavior — results, emitted counts, and operational budgets — remains unchanged only for programs that also satisfy the applicable elaboration and evaluator structural profiles. The new host-safety policy intentionally rejects otherwise parseable unsafe shapes with controlled diagnostics; sufficiently long dot-call chains are the principal source-reachable example because each link consumes three evaluator structural units. The preflight charges nothing to any `EvaluationBudget` and holds no static state; the 64-deep module-chain maximum loads through the real loader and either completes or stops with the established invocation backstop on the smallest stacks. Lean's evaluator is a total function over an inductive type with no host stack, so no Lean update applies. The documented minimum supported execution environment — a thread stack of at least 1 MiB — is stated on the public API surface (`EvaluationLimits.MaxSupportedAstDepth`, `Evaluator.Run(Expr)`), not only in this manifest. Regression coverage: `AstStructuralDepthTests` (boundary pinning, per-shape exact values at the ceiling, error-shape/span preservation, DAG/cycle, dot-call weight boundary, entry-point matrix, config clamping, budget neutrality, concurrency, capacity-shape gating, inherited-collection and membrane boundaries, recursive-property inventory), `ExprNameRendererTests` (golden byte-identity per mode, deep-chain bounding, determinism), and `AstStructuralDepthProcessTests` (the extreme-depth rejection child plus the near-boundary child: every materially different recursive shape at max-1/max/max+1 on a dedicated 1 MiB thread, the tiny-stack iterative-spine pin, engine and front-end gate boundaries, the module-chain probe, the deep diagnostic-name probe, and the standalone front-end boundary probe — run in Debug and Release).

- Line comments are surface-lexical trivia owned by the C# lexer: a `#` outside a string literal starts a comment that ends before the next physical newline (or at end of source), with no whitespace required before the marker. The former `//` marker was removed in August 2026 with no compatibility alias, so `/` is always the division token and `//` is two division tokens. Comment tokens never reach the AST, and Lean models no surface syntax, so no Lean update applies; generated Lean corpora changed only where embedded KatLang source strings contained comment text. - **Source and module input-size limits are host runtime policy, not KatLang language semantics** (`SourceProcessingLimits`, `SourceProcessingBudget`). They bound the work and memory a run spends turning source text and imported modules into an elaborated program BEFORE evaluation; Lean models neither surface parsing nor module loading, so no Lean update applies. They are ordinary parse/front-end `Diagnostic`s (never an `EvalError`), so a violation surfaces as `RunResult.ParseFailure` and never as an evaluator error. Four always-active ceilings, each configurable only downward via `RunOptions.SourceProcessingLimits`, clamped above the supported maximum, non-positive values rejected, counters run-scoped and never static (a fresh `SourceProcessingBudget` per run; a rejected reservation leaves every counter unchanged):
  - **Per-source length** (`MaxSupportedSourceLength` = 2 MiB UTF-16 code units) applies to the main program and to each imported module, checked before tokenization. It subsumes and re-labels the former fixed 2 MiB "bytes" module-download cap (now correctly UTF-16 code units, consistent between main and module source). The probes record source/token/node/diagnostic counts and showed `frontendNodes = parserNodes` across the included shapes; observed ratios are calibration samples, not universal proof bounds. The source ceiling bounds those counts; the formerly quadratic per-construct paths (wide deconstruction and large clause families, below) are now linear, so it is a resource ceiling rather than the last line of defence against quadratic parse work. Enforced at the raw `Parser.ParseSyntax` boundary (the always-active hard ceiling, which also protects the raw-parser fuzz target) and, for a lower configured value with a richer message, in `FrontEndPipeline` (main) and `ModuleLoader` (each module). The lower-level public `Lexer.Tokenize` API remains caller-sized and linear-scan; every parser/execution path goes through the protected parser boundary.
  - **Import depth** (`MaxSupportedModuleDepth` = 64 nested loads). The module loader resolves `load` recursively, so a deep transitive chain overflowed the host stack — an uncatchable `StackOverflowException`, measured at 562 (Release) / 605 (Debug) levels on a 1 MiB Windows stack by the `module-depth-search` probe. This converts that crash into a structured diagnostic; a chain of 5000 now returns a defined error instead of terminating the process. Those crash measurements are Windows-specific; smaller-stack hosts such as WASM motivate the conservative margin, but WASM stack headroom was not measured.
  - **Aggregate source** (`MaxSupportedAggregateSourceLength` = 8 MiB) and **distinct-module count** (`MaxSupportedModuleCount` = 256), run-scoped, because a per-module ceiling alone bounds neither a wide graph of many 1 MiB modules (probe accepted 67 MB) nor thousands of tiny modules (probe accepted 5000). A repeated `load` of an already-cached URL consumes no new module slot or aggregate. Count capacity is checked before fetch; after download and the per-source check, aggregate source and module count are committed atomically before parsing. Failed downloads and rejected source/aggregate reservations are not negatively cached or charged, so they may be fetched again at another load site.
  - **Host cancellation** is configured by `RunOptions.SourceProcessingCancellationToken` and applies only while parsing and elaborating source/modules before evaluation. The ONE downloader contract, `RunOptions.DownloadCode` (`Func<string, CancellationToken, ValueTask<string>>`), receives that exact token unchanged. Cancellation is checked before and after each fetch (the post-fetch check also covers cancellation requested while a download was suspended), before parsing downloaded source, before recursive elaboration, and between the main front-end phases. An `OperationCanceledException` (including `TaskCanceledException`, whether thrown synchronously or delivered through a faulted downloader awaitable) propagates only when the configured host token is cancellation-requested, and the escaping exception always carries that exact host token even when the downloader faulted with a different cancellation token; otherwise it is an ordinary `load: failed to fetch` diagnostic (a host downloader's own timeout or transport failure surfaces as a fetch failure like any other; the library ships no downloader of its own). Cancellation unwinds import depth and in-progress state through `finally`, rolls back the cancelled module frames' aggregate/module-count reservations, and never caches a partial module. The token and all mutable loader/accounting state are run-scoped; shared `RunOptions` and concurrent runs introduce no static cancellation state. The token deliberately does not cancel arbitrary evaluator computation; evaluation remains governed by `EvaluationLimits` and cooperatively cancelled by the separate `RunOptions.EvaluationCancellationToken` (see the evaluation host-cancellation entry below). This is implementation/host-policy behavior and requires no Lean update.
  - These bound PARSING and MODULE LOADING only. The prebuilt-AST evaluator entry points bypass parsing entirely and are governed by `EvaluationLimits` alone, so the source-length policy makes no claim about hand-built ASTs. This work also required making three pre-evaluation passes linear that were quadratic in the top-level declaration count — `PropertyExposureResolver` and `ImplicitArgumentResolver` (each cloned an O(P) visible-scope map once per sibling property; now shared when a child adds nothing) and `Parser.ParseAlgorithm` (duplicate-name detection scanned the growing property list per declaration; now an O(1) name set). These are performance/robustness corrections with no semantic change, so no Lean update applies and no row above is triggered beyond this note. A subsequent correction pass additionally made the WIDE-DECONSTRUCTION elaboration linear: `x0..x{N-1} = RHS` elaborates to one shared `$deconstruct$N` source plus N target properties, each binding through a synthetic inline helper that carries the shared N-capture `SequenceValueParameterPattern`, and five O(N)-per-helper cost sites made a wide deconstruction O(N²) — the parser's `Algorithm.User` construction (`FromDeclarations` rebuild) and post-parse validation walk (`Params.Count` list materialization plus a per-parameter no-op iteration), the three front-end passes (`ParameterDetector`, `ImplicitArgumentResolver`, `PropertyExposureResolver`), and `PropertyDependencyGraphBuilder`. Each now treats the fully-formed synthetic helper as an elaboration LEAF (O(1) per helper), and the shared `AstWalker` gained an in-family `VisitsExplicitParameterDeclarations` opt-out; the elaboration, AST shape, evaluation, diagnostics, and Lean model are all unchanged (implementation-only, verified by full-suite equivalence and structural regressions). A follow-up pass then removed the two remaining per-construct quadratics, both implementation-only (no Lean update; Lean models neither surface parsing nor front-end elaboration nor the run-scoped evaluator caches): **(1) Conditional clause-family duplicate detection** was an all-pairs O(C²) scan — the parser's per-clause `branchList.Any(IsMatchEquivalent)` insert check and the runtime `Algorithm.HasDuplicateBranchPatterns` guard both compared every new/each pattern against all earlier ones. Both now index patterns in a hashed set (`Pattern.MatchEquivalenceComparer`) whose equality IS the exact `IsMatchEquivalent` and whose hash is a deterministic FNV structural fingerprint consistent with it (binder spelling and spans ignored, first-occurrence binder numbering, literals and sequence shape included), so an equivalence class lands in one bucket and any unrelated collision is resolved by the exact comparison — O(C) with branch order, the duplicate diagnostics, and their order/spans all preserved. **(2) Evaluating every target of one wide deconstruction** was O(N) targets × one full N-capture bind, and each bind was itself O(N) (the shared `BindParameterPatternList.AddBindings` rebuilt a name set and linear-scanned the accumulators per capture), i.e. effectively O(N³). The N target helpers of a deconstruction now share one identity token, and a run-scoped `IDeconstructionBindingCache` (keyed like the zero-argument property cache — group token plus value/algorithm/counted-environment identity, errors never cached) binds the group ONCE per binding context; each target projects its own slot in O(1). `AddBindings` was additionally made O(1) amortized with running name→value indexes (preserving the repeated-bind equality check exactly), so the single shared bind is itself linear. Deferred binding, per-position values across every pattern shape, written-pattern arity errors, demand-order independence, and run isolation are unchanged; the ONE intended operational change is that later targets of a group no longer repeat the full bind (the shared bind is charged once — see the operational-accounting note). A failed full bind is NOT cached (consistent with zero-argument property failures), so the failure path is a documented residual rather than a shared/linear path; ordinary output short-circuits at the first failed target, so a demanded invalid group binds once in practice. The scaling regressions read passive, SCOPE-LOCAL observation objects, never a static field: a run-scoped `EvaluationObservations` (carried through `EvalCtx`, one per observed run via the internal `Evaluator.RunCountedObserved`) counts full deconstruction binds, and an operation-scoped `PatternComparisonObservations` (passed explicitly to the match-equivalence comparer for one parse via the internal `Parser.ParseSyntax` observed overload) counts exact clause comparisons. No Phase 6 run-time or test-observation state is stored in static mutable fields; both observers are internal, excluded from every public API and language-semantic contract, start at zero by construction (no reset), keep separate and concurrent runs/parses independent, and cannot affect any evaluation or parse decision — a null observer records nothing and the production paths pass null. The clause allocation-ratio regression is design-independent (measures parse allocation) and fails under the old all-pairs implementation even though that path would bypass the observed comparer. Regression coverage: `SourceProcessingLimitsTests`, `Phase6PerformanceRegressionTests`, `WideDeconstructionScalabilityTests`, `ClauseFamilyScalabilityTests`, `DeconstructionSharedBindingTests`, `ModuleLoaderTests`; tooling: `fuzz/KatLang.ParserFuzz` `source-probe` / `module-probe` / `module-depth-search` / `eval-probe` (`eval_all_deconstruct`, `eval_clause_family`).

- **Evaluation host cancellation is host runtime policy, not KatLang language semantics** (`RunOptions.EvaluationCancellationToken`, the `Evaluator.Run`/`RunFlat` token overloads, August 2026). The token is stored on the run-scoped `EvaluationBudget` and observed via `EvaluationBudget.ObserveCancellation` at the head of every budget chokepoint — `TryEnterInvocation`, `TryEnterArgumentEvaluation`, `TryChargeStep`, `TryChargeExpressionNodeWork` (every checkpoint, not only batch boundaries), `TryReserveCollection`, `TryReserveString`, `CheckCollectionSize` — BEFORE any counter check or mutation, plus at each evaluation entry point before the structural preflight and again before completion. The completion observation closes a real last-operation gap: a final one-slot property result can return after the cache with no later collection reservation or other charging checkpoint. `RunFlat` and `KatLangEngine.Run` additionally observe after their bounded host-atom projection. The OPTIMIZED loop executor (`LoopOptimizer.TryEvaluateWhile`/`TryEvaluateRepeat`) observes once per iteration because its fully-planned iterations are the one unbounded execution shape that otherwise touches no chokepoint; that observation is observation-only and charges nothing, preserving optimized-vs-generic accounting parity. Because the chokepoints are unconditional call sites, observation does not depend on any opt-in budget being configured. Requested cancellation THROWS `OperationCanceledException` carrying the supplied token — deliberately never an `EvalError`: a resource-limit error from a parameter's eager value evaluation is RETAINED on the binding and the run continues, so a cancellation modeled as an error could be absorbed into a value and the cancelled run would keep running (pinned by `EvaluationCancellationTests.CancellationDuringEagerArgumentEvaluation_EscapesInsteadOfBeingRetained`). The pre-mutation throw makes a cancelled checkpoint non-mutating exactly like a rejected enter, so the scoped depth protocol's conservation laws are unchanged and admitted levels unwind through their ordinary `finally` releases (the OCE unwind path the conservation suite already exercised via seam injection). An uncancelled token is inert: no counter, verdict, result, or diagnostic changes (differentially pinned across programs × limits × optimizer strategies). The evaluation token is deliberately SEPARATE from `SourceProcessingCancellationToken` (front-end only, above); a host wanting one stop signal passes the same token to both. `KatLangEngine.Run`/`EvaluateToAtoms`/`EvaluateToString` thread it into the main evaluation and the additional-error evaluation for evaluable load failures; cancellation propagates and is never wrapped in a `KatLangException`, rendered into an error string, or converted into a `RunResult`. Worst-case observation latency is bounded by the densest applicable cadence: per expression-node checkpoint for pure expression work, per invocation/iteration for calls and loops, and one always-active per-collection ceiling's worth of un-checkpointed light work (≤ 100,000 items) for callback-free fused stretches, followed by the mandatory completion check. Lean models no host cancellation, so no Lean update applies. Regression coverage: `EvaluationCancellationTests` (entry-point matrix, mid-run observation through recursion/generic loops/optimized loops via the cancelling — not throwing — cache seam, deterministic final-operation cancellation, the retained-error contrast, conservation after real-token unwind, uncancelled-token differential inertness incl. budget counters, main/additional-error engine propagation and front-end separation, concurrent cancelled/uncancelled isolation) plus `BudgetConservationTests` section D for injected-OCE unwind conservation.

- **Asynchronous evaluation is a host-execution surface, not KatLang language semantics** (`Evaluator.RunAsync`/`RunFlatAsync`, `KatLangEngine.RunAsync`, the internal `*Async` twin family in `Evaluator.Async.cs`, August 2026). Lean models no host asynchrony, and no Lean update applies. The architecture is a "sync-delegating async twin spine": the SYNCHRONOUS evaluator remains the semantic oracle, and an async entry point decides ONCE per run which family drives evaluation. When no run component can complete asynchronously — the zero-argument property cache is synchronous and no asynchronous host operation is configured — the async entry executes the ordinary synchronous pipeline inline on the calling thread and returns a completed task: identical results, diagnostics, budget verdicts, counters, optimizer eligibility, and stack behavior, by identity, with no thread offloading and no artificial yielding (host scheduling stays the host's responsibility). When the cache IS async-capable or an asynchronous host operation is configured, evaluation runs through the `async ValueTask` twin family: each twin MIRRORS its synchronous counterpart's sequencing (marked `// MIRROR OF ...`; a semantics change to a mirrored method must update its twin in the same change), shares every non-evaluating helper (lookup, binders, budget chokepoints, value construction, diagnostics), awaits the cache seam at zero-argument property access, and since Phase 3 awaits asynchronous host operations at the guarded `NativeCall` site, so incomplete host work suspends and resumes the whole spine. The twin path pins the GENERIC loop/sequence strategies (the same mode configured opt-in budgets already force; limit verdicts are strategy-independent by construction) and guards structural-nesting recursion with a twin-only `TryEnsureSufficientExecutionStack` backstop at the two row-loop funnels, because the twins' async frames are larger than the calibrated synchronous frames and structural nesting passes no invocation chokepoint; like the invocation-chokepoint probe it can only stop a run EARLIER with the structured stack error, never change a completing run, and it moves no counter. Cancellation is the Phase 1 contract unchanged — the token lives on the shared `EvaluationBudget`, chokepoints are shared code, `OperationCanceledException` carrying the supplied token surfaces through the returned task and is never an `EvalError` or retained binding value. Plain/counted note: the twins are COUNTED-family mirrors; where the synchronous family used a plain-evaluation wrapper, the twin awaits the counted core and projects its value — every such synchronous wrapper is itself exactly that projection, and the plain/counted value equivalence is the Lean-modelled invariant the explorer corpus pins. Regression coverage: `AsyncEvaluation/AsyncTwinDifferentialTests` (language-spec + explorer corpora through the twin path with OUTCOME and OPERATIONAL-COUNTER equality against the sync generic strategies, plus a genuine-suspension corpus pass), `AsyncEvaluationApiTests` (public fast-path identity incl. engine projection), `AsyncSuspensionTests` (construct-family suspension, deterministic held-run incompleteness, concurrent sync/async lanes), `AsyncCancellationTests` (Phase 1 matrix on the async surface incl. cancellation while suspended), `AsyncStackDepthTests` (structured-outcome pins on 1 MiB / 384 KiB threads; the twin's reduced synchronous-completion depth capacity is characterized by the `--async-stack-capacity` diagnostic in `KatLang.Benchmarks`).

- **Public host operations are host-execution configuration, not KatLang language semantics** (`HostOperation`/`HostOperations`, `RunOptions.HostOperations`, the `Evaluator.Run`/`RunAsync` host-operation overloads, `KatLangEngine.EvaluateToAtomsAsync`/`EvaluateToStringAsync`, August 2026 — Phase 3 of the async set). A host operation is exposed to programs by generalizing the EXISTING Math-module mechanism: each operation becomes one ambient prelude property whose wrapper is a parentless `Algorithm.User` with the operation's declared parameters and a single `Expr.NativeCall` output row carrying the `host:`-prefixed dispatch name (`':'` cannot appear in an identifier, so host dispatch names can never collide with built-in native names). No AST shape, parser rule, or Lean model changes: name resolution is the ordinary prelude fallback (program-defined properties shadow operations by ownership-first lookup), the front end resolves the names through the configuration's extended SIGNATURE-ONLY semantic prelude (`ParameterDetector.DetectPrevalidated`), so a referenced operation never becomes an implicit parameter — the same name-level runtime/semantic prelude agreement Math relies on — and zero-parameter operations participate in the Lean-modeled per-run property cache with the `A` vs `A()` distinction unchanged. Dispatch is registry lookup at the shared `EvalNativeCall` site (synchronous operations, both pipelines) plus ONE new await site in the async twin's `EvalCountedAsync` for asynchronous operations — the "adding an operation class means adding an await site" extension the Phase 2 architecture was built for. The configuration rides the run-scoped `EvaluationBudget` (immutable config on the run-identity object; the hot `EvalCtx` struct is unchanged). Routing is enforced, not documented: any configuration containing an asynchronous operation selects the async twin path with an async-capable run cache (public entry points construct one; internal entries fail loud otherwise), synchronous entry points reject asynchronous configurations with `InvalidOperationException` before any evaluation, and a stray asynchronous operation reaching the synchronous `EvalNativeCall` is a fail-loud ownership violation. Contracts: delegates receive the evaluated argument `Result`s in declaration order plus the run's evaluation cancellation token (Phase 1 token identity); an incomplete awaitable suspends the spine and resumes it exactly once (no replay — pinned with deterministically gated operations); host exceptions and faulted awaitables propagate to the host unchanged (never converted to `EvalError`, mirroring the cache-seam contract), and a null result is a fail-loud host contract violation; cancellation observed after the awaited operation completes surfaces as `OperationCanceledException` with the supplied token. A SUCCESSFUL host return value is normalized into the canonical `Result` representation at the host boundary (August 2026 correction, `Evaluator.NormalizeHostOperationValue` — the existing `Result.Normalize`, shared by the synchronous dispatch and the async await site): host code may construct shapes ordinary KatLang evaluation canonicalizes during construction (a singleton transparent sequence, redundant nested empty-sequence structure), and without this boundary such raw values entered evaluation — and the zero-argument property cache — diverging from equal program-produced values at representation-sensitive rules (`Data == 1` false for a host `SequenceValue([Atom(1)])`, visible-empty counts). Normalization happens BEFORE cache insertion (the cache stores the wrapper body's evaluation outcome, which is derived from the normalized value), applies to successful values only (failures, cancellation, and diagnostics are untouched), and is identity on already-canonical values; this moves host-created values into the canonical value space the Lean model already assumes, so no Lean update applies (Lean models no host configuration). Pinned by `Hosting/HostOperationNormalizationTests`. Native-argument lookup (limitation lifted August 2026): native-call wrapper bodies (Math members and host operations) read their declared argument names counted-first with value fallback (`LookupNativeArgument` — the `Expr.Param` dual-view order), so `open Math` + `map(Abs)`, the alias `map(abs)`, and a host operation referenced DIRECTLY as a flat callback all bind the callback-bound element, and a same-named ambient value is never captured or forwarded to host code (direct calls unchanged — flat fixed binding shadows callee parameter names out of the counted environment). Lean models no `NativeCall` (documented gap); counted-first matches the modeled `Expr.Param` order, so no Lean update applies. Editor semantic models keep their static prelude and do not surface host operations yet (documented limitation). Lean models no host configuration, and an unconfigured or unused configuration changes no program's outcome (corpus-differential pinned), so no Lean update applies. Regression coverage: `Hosting/HostOperationApiTests`, `Hosting/AsyncHostOperationTests`.
- **Qualified Math native references are the C# Math-prelude part of that lift.** In algorithm position, `Math.Abs`/`Math.Pow` resolve to the same runtime native wrapper as `abs`/`pow` and opened `Abs`/`Pow`, but only when authoritative Math metadata and the resolved member's actual `Expr.NativeCall` body agree. This prevents a user-defined property named `Math` from being reinterpreted and leaves every general argumentless `DotCall` on the Lean-modeled zero-parameter-wrapper rule. Lean models neither the Math prelude nor `NativeCall`, so this is part of the documented native gap rather than a core evaluator divergence; `MathAliasResolutionTests` and the C#-excluded language-spec case pin it.

- **Individual front-end elaboration passes are internal implementation stages, not host API** (M6 architecture-review repair, v0.8.187 — an intentional breaking NuGet surface reduction; no language semantics changed). `ParameterDetector` and `ImplicitArgumentResolver` had been public since the original rewrite, but they are two stages of a three-stage finalization, and the third (`PropertyExposureResolver`) was always internal: a host composing Detect → Resolve obtained an AST whose `Property.Exposure` values were never finalized — every property kept the constructor default `Exported` — and the evaluator TRUSTS that stored flag, so the partially elaborated tree observably diverged from engine-parsed source (sharpest witness: `open` exposed a `LocalOnlyCapturedAncestorParameters` property the language hides, turning an authoritative structured failure into a success; pinned by `FrontEndElaborationBoundaryTests`). The boundary rules: (1) hosts must not compose partial elaboration stages — the passes are internal, and none of the internal stages (`PropertyExposureResolver`, `FrontEndPipeline`, `Parser.ParseSyntax`, `PropertyDependencyGraphBuilder`) may be exposed to "complete" a partial route; (2) the supported public layers perform COMPLETE elaboration — `Parser.Parse`/`Parser.ParseAsync` (structural gates + load handling + parameter detection + implicit-argument resolution + property-exposure resolution, via `FrontEndPipeline`) and `KatLangEngine.Run`/`RunAsync` (+ conveniences), with `SemanticModelBuilder` consuming elaborated `ParseResult`s; (3) exposure/ownership metadata on an AST is trustworthy only after the authoritative pipeline finishes — the `Evaluator.Run*` host-AST entry points deliberately evaluate the supplied tree AS-IS (structural preflight, no elaboration), so a host that hand-builds exposure metadata owns its correctness; (4) there is deliberately NO public "host AST → full elaboration" API — no concrete host contract required one — and if one ever becomes necessary it must be ONE coherent operation that exactly mirrors `FrontEndPipeline.FinalizeElaboration` with pinned equivalence against `Parser.Parse`, never re-exposed individual stages. The v0.8.188 follow-up closed the one residual of the same shape: `ModuleLoader` (public constructor + `ElaborateAsync`) is internal too — load elaboration alone is even MORE incomplete than the removed Detect → Resolve composition, since a loader-only tree has had no parameter detection at all (a spliced module's declared parameter references are still raw `Expr.Resolve` nodes, so its functions fail with `UnknownName` where the engine computes the value — pinned beside the exposure witnesses in `FrontEndElaborationBoundaryTests`), and hosts keep full module-loading capability through `Parser.ParseAsync`/`KatLangEngine.RunAsync` with `RunOptions.DownloadCode`/`AllowedHosts` (an in-memory downloader completes synchronously there exactly as it did on the loader). Tests, fuzzing, and benchmarks reach the internal stages through the existing `InternalsVisibleTo` friend grants; the non-friend `KatLang.Formatting.PublicApi.Tests/PublicElaborationSurfaceTests` pins the surface.

- **Source loading is ASYNC-ONLY host acquisition policy, not KatLang language semantics** (`RunOptions.DownloadCode` as `Func<string, CancellationToken, ValueTask<string>>`, `ModuleLoader.ElaborateAsync`, `FrontEndPipeline.ProcessAsync`, `Parser.ParseAsync`, August 2026 — Phase 4 of the async set). There is ONE source-loading contract: obtaining source text for `load(...)` awaits the configured downloader, an incomplete `ValueTask<string>` genuinely suspends source processing and resumes it at the same logical point (the downloader is never re-invoked after a suspension; caching still fetches each distinct successful URL once per elaboration scope), and there is no synchronous fetching path and no blocking sync-over-async bridge anywhere in the library. Parsing and every elaboration pass remain synchronous CPU work; only module acquisition awaits. The synchronous source-level entry points (`KatLangEngine.Run`/`EvaluateToAtoms`/`EvaluateToString`, `Parser.Parse(source, options)`) remain for downloader-less configurations — they cannot suspend, so a downloader-configured options object is rejected with `InvalidOperationException` before parsing (one enforcement point in the synchronous `FrontEndPipeline.Process(source, RunOptions?)`), deterministically and configuration-driven, mirroring the asynchronous host-operation routing rule; `load` syntax without a downloader keeps its established unavailability diagnostic. The asynchronous entry points are canonical for module-loading source (`KatLangEngine.RunAsync` + async conveniences, `Parser.ParseAsync`), and one run can suspend during BOTH source processing (module download) and evaluation (asynchronous host operation). Loader traversal is routed per subtree: load-free subtrees take the byte-unchanged calibrated synchronous walk, load-bearing spines take `// MIRROR OF`-tagged `async ValueTask` twins, and a linear pre-scan (superset of the rewrite walk's reach) marks the spines; scan and both walks carry a per-level stack-reserve backstop yielding one structured diagnostic (`SourceProcessingDiagnostics.ModuleElaborationStackExhausted`) instead of overflow. Error semantics are unchanged: downloader exceptions — thrown synchronously OR delivered through a faulted awaitable — remain `load: failed to fetch` diagnostics unless the host token is cancelled (host cancellation stays authoritative), and parse/elaboration failures in downloaded source keep their established diagnostics. The evaluator's synchronous primitives (`Evaluator.Run`/`RunFlat` over constructed `Expr`) are untouched. The one-contract claim is structural since v0.8.189 (M1 architecture-review completion): the library ships NO default/ambient HTTP downloader — the former internal `HttpClient` fallback (whose default redirect-following could fetch from a host the allowlist check never saw) is deleted, and every compiled `ModuleLoader` constructor requires the explicit downloader parameter while the authoritative constructor rejects null (`ArgumentNullException`, never a substituted transport), pinned by metadata-level construction-shape and friend-level runtime tests. `AllowedHosts` governs KatLang's policy for the source-written load target passed to that delegate; redirect destinations and all other transport behavior belong to the host-supplied downloader. Lean models neither surface parsing nor module loading, so no Lean update applies. Regression coverage: `ModuleLoaderAsyncTests` (genuine suspension, exactly-once fetch across suspension, nested suspension ordering, cancellation-while-suspended, faulted-awaitable diagnostics, module-load + async-host-operation composition, concurrent independent runs, tiny-thread backstop), `ModuleLoaderCancellationTests` (async contract cancellation matrix incl. sync-entry rejection), `ModuleLoaderTests` (incl. the explicit-downloader constructor contract), and the `DeepNestedModuleChains`/`NearBoundaryShapes` subprocess probes over the async loader.

- Evaluation resource limits are **host runtime policy, not KatLang language semantics**. The Lean evaluator is unbounded and models no fuel, step budget, or recursion budget; it describes the successful/error behaviour of a program *absent host resource limits*. The C# evaluator may additionally stop for depth, steps, insufficient host-stack headroom, one-collection size, cumulative materialized items, one-string size, or cumulative materialized string units; the host renderer separately represents display-length overflow, and the pre-evaluation structural preflight rejects over-deep program trees (`AstDepthLimitExceeded`). These are the nine variants classified by `EvalError.IsResourceLimit` (the structural-cycle rejection `AstCycleDetected` is malformed input, not a resource limit). This is observable OPERATIONAL behaviour but not value semantics: for every program that completes within its limits, the C# result is bit-identical to the unlimited result and to Lean, so no differential case changes. Deliberately no fuel was added to Lean — mirroring host policy in the formal model would make the specification depend on a machine property it does not describe.
  - **Depth** counts simultaneously active evaluator entries that can recursively re-enter an algorithm body. Dynamic invocations — user and conditional calls, callbacks, and zero-argument property access — charge depth plus one step at their invocation chokepoints. Re-entry outside those chokepoints charges DEPTH ONLY through `EvaluationBudget.TryEnterArgumentEvaluation`: builtin argument/control-argument bodies, sequence-builtin dotted receivers, zero-parameter `AlgEnv` thunks demanded by either `Expr.Param` evaluator twin, and a non-short-circuited ordinary-dot `string` receiver resolved through lexical `Resolve` or `AlgEnv`-bound `Param`. The last two share `EvalResolvedAlgOutputForValueDemand`. This boundary never charges a step, and every successful enter is balanced in `finally`; a rejected enter leaves depth unchanged.

    Call-argument assembly keeps the existing dual channels. An ordinary semantic value-channel error is not sticky: when the same argument has an algorithm channel, later value demand re-evaluates it through the established fallback. Only an `IsResourceLimit` failure from that eager value-channel attempt is retained beside the `AlgEnv` binding. It becomes terminal only when that parameter's value is later demanded (including as a `string` receiver); algorithm-channel lookup and forwarding ignore it, so explicit higher-order dispatch and unused resource-failing arguments are unchanged. The sticky short-circuit prevents exponential retry, while the depth-only charge bounds non-sticky recursive re-entry and lexical `A = A.string` recursion by the deterministic evaluator ceiling.

    Written/parser-bounded nodes do not acquire a separate demand charge merely because their output is evaluated: brace blocks, captures, and dot-chain wrappers used as `string` receivers remain on the written-syntax policy, and any recursive name/parameter path inside them must still cross a charged resolution or invocation chokepoint. Correcting a previously uncharged resolved value-demand re-entry can tighten the depth boundary by one level; that is intentional host-resource accounting, not a value-semantics change. Sequence-builtin dotted receivers retain the same depth-only accounting as the equivalent plain argument. The internal ceiling (`EvaluationLimits.MaxSupportedDepth` = 128, calibrated by the `eval-probe` depth probes) applies to every entry point, and `RunOptions.EvaluationLimits.MaxDepth` can only lower it. `RuntimeHelpers.TryEnsureSufficientExecutionStack` may stop earlier as a machine-dependent backstop, never later.
  - **Steps** are opt-in (no budget by default at any layer, so existing long-running programs are unaffected). One step is charged per dynamic invocation and per loop iteration, plus ONE step per 4096 expression-evaluation work checkpoints (`EvaluationBudget.TryChargeExpressionNodeWork`, recorded at the `Eval`/`EvalCounted` dispatch heads and per expression-spine machine transition). This is a cheap operational proxy rather than a literal distinct-AST-node counter. Small ordinary programs stay below the first bulk block and keep their prior exact accounting, while a sufficiently large no-invocation expression can now consume bulk steps. The charge exists because a reference-shared (DAG-shaped) host expression evaluates every occurrence: 25 shared `Binary` nodes can demand 2^24 evaluations while every per-invocation budget stays at zero, so without it the one budget documented to stop excessive computation never fired. Optimizer independence is by construction rather than parallel accounting: a run with a configured step budget takes the generic loop / sequence-pipeline paths, so a configured budget can never mean one thing under an optimization and another without it. The step budget bounds WORK, not memory; the implemented collection and string limits below bound construction separately.
  - Budget state is run-scoped (`EvaluationBudget`, created once per top-level run, shared by reference through every copied `EvalCtx`, never static). Two runs sharing one `RunOptions`/`EvaluationLimits` instance — including concurrent runs — always start with fresh counters, and a zero-argument property cache entry never carries budget state.
  - **Collection materialization** is bounded by two further limits. `MaxCollectionItems` is an ALWAYS-ACTIVE hard ceiling (`EvaluationLimits.MaxSupportedCollectionItems` = 100,000, configurable downward only) on the immediate item slots of ONE sequence or exact list created by source evaluation; unlike the step budget it cannot be opt-in, because a single compact expression (`range(1, 10000000)`) asks for one enormous allocation before any step or depth unit is charged. `MaxMaterializedItems` is an opt-in cumulative per-run total for programs that repeatedly build individually legal collections. Both are calibrated from measured cost (~190–200 bytes of peak working set per item), deliberately far below what a development machine survives, because WASM and multi-tenant server embeddings have much smaller budgets.
  - The unit is **one immediate element position stored in a newly created persistent collection**: `[]` costs 0, `[x]` costs 1, `[[1,2]]` costs one outer slot plus the two the inner list already paid, and reusing an existing child value as an outer element costs only the new outer slot. Merely opening the spread view costs nothing; each real sequence recapture the evaluator constructs from that view is charged once. Sequence CAPTURE differs from exact-list construction by singleton/empty erasure — fewer than two slots materialize no sequence storage and cost nothing (`MakeCheckedSequenceCapture`), while `[x]` really stores one slot. Atom leaves are not charged; this is a collection-materialization budget, not an object-count budget.
  - Every reservation happens BEFORE allocation (`EvaluationBudget.TryReserveCollection`, using checked arithmetic so a rejected request leaves the cumulative counter untouched). Checked evaluator helpers cover ordinary, patterned, callback, reducer, deconstruction, and loop-step collected lists (`CollectSegment`); generic and optimized final loop state; output/sequence capture; list/builtin construction; and each persistent direct nested-spread recapture. `range` computes its cardinality from its bounds with a saturating conversion and never enumerates to find out; `atoms` — the one producer whose output can far exceed its input, since `[A, A]` doubles the atom count while adding two slots — bounds the TRAVERSAL itself (`Result.TryLanguageAtoms`) rather than counting first. The public engine's host-atom projection is bounded the same way (`Result.TryToHostAtoms`), so a successful evaluation is never followed by an unbounded flattening allocation.
  - Optimizer parity for the cumulative materialization budget is by the same force-generic construction as steps: a CONFIGURED `MaxMaterializedItems` disables sequence-pipeline fusion (`CreateRootCtx`), because a fused pipeline enforces only the single-collection boundary (`EvaluationBudget.CheckCollectionSize`) and never charges the cumulative counter — leaving fusion enabled made the verdict flip when an unrelated `MaxSteps` happened to disable it. With NO cumulative budget configured, fusion stays eligible and still consumes no cumulative accounting (charging an allocation that does not happen would be precisely the double charging fusion exists to avoid), and if a pipeline is not fused after all, the generic path reserves for real, so one collection is never charged twice. Optimized LOOPS charge the cumulative counter identically on both strategies and stay eligible under a configured budget (pinned by `GenericAndOptimizedLoops_ChargeOnlyTheirFinalPersistentState`).
  - Resource errors do not accumulate call/property `WithContext` frames (`EvalError.IsResourceLimit`, honoured by both the evaluator's `WithCtx` and the sequence optimizer's): the limit is a property of the run, not of any one call on the chain, so the innermost span is preserved and the message stays a single line instead of one identical frame per active invocation. For the same reason, a resource-limit failure from eager sequence-builtin suffix-slot preparation is terminal rather than falling through to the algorithm channel and repeating the failed work. A successfully prepared value-shaped `reduce` initial accumulator is threaded into reduction and consumed exactly once; genuine callbacks and non-resource preparation failures retain the existing algorithm-channel fallback.
  - **Language strings** are bounded by `MaxStringLength` (always-active ceiling `MaxSupportedStringLength` = 1,000,000 UTF-16 code units, configurable downward) and an opt-in cumulative `MaxMaterializedStringChars`, reserved before creation at the shared `Evaluator.MakeStringResult` construction point. This is defence in depth rather than the closure of a compact-source path: **KatLang has no string concatenation operator** (`"a" + "b"` is a `TypeMismatch`), so the only producers are source literals and `.string` numeric conversion (~30 units) and a source program cannot grow a string. The ceiling does bound hand-built ASTs reaching the public `Evaluator` API, and any future concatenating operation inherits it automatically. Loop plans store raw string literal text and call the same checked helper every time the planned expression executes, so default, explicitly configured, optimized, and generic runs agree while each logical evaluation still pays its UTF-16 units. String limits therefore do not disable loop optimization.
  - **Rendered output** is bounded by `MaxDisplayLength` (always-active ceiling `MaxSupportedDisplayLength` = 1,000,000 UTF-16 code units, configurable downward). This one *does* close a real compact-source path: display flattens a value recursively, so nesting a value inside itself (`L1 = [L0, L0]`) adds two item slots and no host atoms while DOUBLING the rendered length — a nine-line program can ask for gigabytes of text while every evaluation limit sees it as tiny. Rendering uses `BoundedDisplayWriter` with an ITERATIVE traversal: it checks before every append and never builds the forbidden output, replacing a recursive `Select(...).Join(...)` that materialized every child string before the parent knew its size (and recursed once per nesting level, unbounded for host-constructed `Result` trees).
  - Units are **UTF-16 code units** everywhere (matching `string.Length`, the source-span column model, and CLR storage): a BMP character is 1, a surrogate pair is 2, and separators/delimiters count. A top-level row separator is charged by its actual `Environment.NewLine.Length`, so the returned string is within the same strict numeric limit on LF and CRLF hosts even though the row at which overflow occurs may differ.
  - **Failure surfacing**: the effective display policy is carried immutably on every `RunResult` variant (via an internal common `DisplayOptions` property), so `ToDisplayString()` and `EvaluateToString()` never return more UTF-16 units than `MaxDisplayLength`. Over-limit rendering discards the partial writer: it returns the complete display-limit message when that fits, otherwise the complete `…` marker when one unit fits, otherwise `string.Empty`. It never appends a marker to partial output or diagnostics. The structured success value and diagnostic collections remain unchanged, and rendering failure never converts `Success` into `EvalFailure`. Manually constructed results use the default hard ceiling.
  - **Dotted receivers are evaluated at most once.** `A.F(B)` has receiver-first semantics (`F(A, B)`). The sequence-builtin dot path formerly evaluated the receiver to dispatch on it, reified that result into an AST literal (`CountedArgAlgorithm` → `ResultToExpr`), and evaluated the literal again; `range(1, 10).count` therefore charged 20 materialized item slots for one ten-item collection. Carrying the counted receiver in `ResolvedArgumentAlgorithm.PreparedValue` corrected that duplicate reconstruction. Call-shaped ordinary/dotted spellings now agree on charged work; a named zero-argument property receiver retains its established property-access invocation charge, which is independent of reconstruction. A follow-up made the now-unused reification itself LAZY: the receiver argument carries only the prepared counted value (`Algorithm: null`), and `ResolveArgumentAlgorithm` / `PrepareSequenceBuiltinSuffixArg` synthesize the legacy wrapper only if an algorithm-only consumer requests the channel. The dot receiver cannot reach such a slot: fixed sequence-builtin binding always consumes it as `items[0]`, the value-only `collection` parameter. Higher-order user receivers (`Double.Apply(7)`) remain on the lexical user-call path and retain their algorithm meaning. This follow-up is an **implementation-only optimization**: it changes unmodeled host traversal/allocation, not values, raw structure, emitted counts, errors, spans, callback order, failure order, or any evaluation-budget counter. Laziness is observed only by the passive run-scoped `EvaluationObservations.CountedArgumentReificationCount` test counter (no static state and no semantic use). Regression coverage: `DottedReceiverEvaluationTests` (generic/optimized paths, receiver kinds, callbacks and failures, resource counters, zero reification, negative control, and reachable callback-produced fallback paths).
    - **Representation note:** Lean's `ResolvedArgumentAlgorithm` deliberately has a mandatory `algorithm` field and therefore constructs the counted-value wrapper eagerly. C# has a nullable algorithm channel plus `PreparedValue`, so it may carry only the prepared counted value and construct the SAME zero-parameter algorithm if that channel is later requested. The avoided traversal and AST allocation are unmodeled host-side work: they consume no evaluation steps, materialized item slots, string units, or dynamic depth. The reification counter observes that implementation fact for tests only; it is not a budget or language-semantic channel.
  - **Patterned call arguments are evaluated exactly once.** The shared call assembler had one high-severity exception: after `BuildCallArgumentInputs` / `collectVariadicCallItems` evaluated a zero-parameter parenthesized block to obtain its ordinary counted/combined argument value, patterned binding called `TryGetExplicitSequenceValueItems` / `explicitSequenceValueItems?` and evaluated the same block again to recover its written slots. The value and pattern views could therefore come from different `Math.Random(...)` draws; a successful first evaluation could be replaced by a second-pass failure; and C# charged duplicate steps and collection/string materializations. The paired correction introduces `PreparedAlgorithmOutput` in C# and Lean: one left-to-right algorithm-output pass returns the counted combined value plus the explicit evaluated slot list, and patterned ordinary/dotted calls consume both products directly. The slot list is a non-semantic view (typed read-only) over the same evaluated `Result` values, never post-value decomposition (which would lose singleton and nested structure); in C# it is the evaluation-owned accumulator itself, so the shared algorithm-output path adds no per-evaluation wrapper allocation for callers that only take the counted projection. A multi-parameter/function-valued block still falls back lazily through the dual algorithm channel; arity and binding remain after full assembly; failures retain their first-evaluation order, span, and context. Intended observable differences are exactly one nondeterministic execution, no retry/second-pass failure, and one logical set of C# operational charges. Ordinary deterministic successful programs retain their prior value, sequence/list structure, emitted count, and pattern bindings. `Math.Random` itself is unchanged. Lean changes structurally with C# even though its pure deterministic evaluator exposes the same successful values; C# operational budgets remain host policy and are not added to Lean. Regression coverage: `PatternedCallSingleEvaluationTests`, `CallArgumentAssemblyTests`, `WrittenSlotReificationTests`, `DottedReceiverEvaluationTests`, and the `preparedAlgorithmOutput*` / `sequenceValueSingletonPatternKeepsMultiEmittingWrittenSlotWhole` Lean guards.
  - **Prepared builtin callback arguments are not reconstructed.** Collection callbacks already receive evaluated `CountedResult` values. Ordinary callback value positions pass those values through `ResolvedArgumentAlgorithm.PreparedValue`, preserving emitted count while intentionally carrying no synthetic algorithm representation; `BuildCallableCallItems` consumes the prepared value directly, so there is no `Result` → `Expr` → evaluator round trip. A legacy counted-value algorithm view is reconstructed lazily only when an algorithm-only builtin position genuinely requests one. User wrappers and direct builtin callbacks therefore agree on result, error, item/string materialization, and cumulative boundaries without a cross-call cache or changed evaluation order. Regression coverage: `OperationalMetamorphicTests`.
  - **Three observation classes, and what may be compared with what.** Testing distinguishes them explicitly, because conflating them either weakens the Lean differential or wrongly demands that Lean mirror C# implementation strategy.
    - **Language-semantic** — result kind, atom/string value, sequence/list structure, emitted count, semantic error kind and stable payload, binding/branch/visibility outcome, spread-capture-collect behaviour. These are what the Lean differential corpus compares, and they must match Lean exactly.
    - **Host-policy** — every resource-limit error (depth, steps, stack backstop, per-collection size, cumulative materialized collection-item slots, per-string size, cumulative materialized string UTF-16 units, rendered-output length), optimizer selection, cache hit counts, CLR allocation, peak working set. These are C#-only and are NEVER required to match Lean; Lean models an unbounded evaluator.
    - **Operational** — evaluation steps, materialized item slots, materialized string units, peak dynamic depth, cache misses, frontend distinct-node counts. These may be compared BETWEEN C# executions, never against Lean. No exact operation counters were added to Lean to mirror C# internals.
  - The relation must match the pair. Equality is used only where the two executions are semantically expected to perform equivalent work — `count(range(1, 10))` vs `range(1, 10).count`, because the dotted form IS the ordinary receiver-first call. Where an implementation is permitted to do less, the relation is an inequality: optimized ≤ generic, cached ≤ rebuilt. Requiring equality there would forbid fusion. Harness: `OperationalMetamorphicTests`, reading the run's own `EvaluationBudget` through `Evaluator.RunCountedObserved` — run-scoped, no static counters, and observing it cannot change optimizer eligibility or re-evaluate anything.
  - **Operational counters are compared only when both executions complete.** When either side stops at a structured resource limit, semantic outcome, resource-limit kind, and structured payload remain comparable, but partial work counters are not: an aborted run's counters are the prefix recorded at the abort point, and two equivalent forms may legitimately have done different preparatory work before reaching the same limit (`reduce(R, contains, [1, 2])` materializes its initial accumulator before forcing `R`, while `R.reduce(contains, [1, 2])` prepares the receiver first and stops earlier). Ordinary, non-resource semantic failures are NOT exempt — their counters are compared exactly like a successful run's. Which side of that gate a case landed on is recorded in its fingerprint, so skipped work comparison is visible rather than silent. Coverage: `MetamorphicComparator.WorkIsComparable`, pinned by `MetamorphicPhase2FamilyTests.OperationalCounters_AreComparedUnlessAResourceLimitAbortedARun`.

A test layer that keys a fusion-dependent relation on the optimizer flag alone therefore claims the weaker relation where the stronger one holds. The metamorphic harness owns that rule in one place (`MetamorphicLimitPolicy.SequencePipelineFusionCanApply`) and derives the chain relation from it; this mirrors production execution policy and does not introduce a separate semantic rule.

C#-only (Lean models an unbounded evaluator), equivalence-tested rather than Lean-updated. It fuzzes source text rather than programs — lexer, parser, recovery, front end, diagnostics, spans and line/column reporting — over isolated surrogates, combining marks, mixed line endings, zero-width format characters, NUL, and Unicode separators. The payload is not source bytes: an isolated surrogate has NO UTF-8 form, so the fuzzer instead selects a trusted template plus a named run of code units (or, in two bounded raw modes, builds them from the payload tail), and seeds are stored as hex payloads because a seed stored as source text would be silently rewritten to U+FFFD by git, an editor, or `File.ReadAllText`. Nothing normalizes source text to NFC/NFD/NFKC/NFKD and no ill-formed surrogate is replaced before the lexer sees it. The layer reuses `FuzzInvariants`, `FrontEndInvariants` and the shared `SourceSpanValidator` rather than restating their rules, and adds the code-unit-model invariants: the token stream covers the source with strictly increasing offsets ending at the source length (forward progress, structurally rather than by wall clock), no token slice spans a line break, every token's recorded line/column equals the one recomputed from its offset by the one shared helper, token text is the exact source slice, and diagnostics are bounded both linearly in source length and per position. `Utf16LexerContractTests` pins the coordinate contract that all of this rests on and that nothing else records: code-unit indexing, 1-based lines and columns with INCLUSIVE end positions, `'\n'` as the only line break, `'\r'` transparent to both line and column (a lone CR is therefore not a line break, though it does end a string literal and a comment), Unicode separators such as U+2028/U+2029/U+0085 as whitespace that never starts a line, zero-width format characters (U+200B/U+200D/U+FEFF) as bad tokens rather than trivia, `char.IsLetter`/`char.IsDigit` applied PER CODE UNIT so a surrogate pair never forms an identifier and a non-ASCII decimal digit starts a number token that `Decimal128.TryParse` then rejects, and string literals with no escape sequences whose code units survive unchanged to the evaluated value. One harness defect was found by the smoke campaign and fixed: the per-position diagnostic bound was justified as "the parser makes forward progress" and set to 16 from templates that never nest, but diagnostics stack at one position when nested constructs are left open — `[[[[` reports once per bracket at end of file while consuming every code unit — so the bound was measuring nesting, not stalling; it is now the parser's own `MaxNestingDepth`, with forward progress established separately by the token invariants. The only `src/KatLang` change in the phase is this documentation entry.
  - **Phase 7 adds a separate editor-tooling semantic target** (`KATLANG_FUZZ_MODE=editor`, `fuzz/KatLang.ParserFuzz/Editor`, covered by `EditorFuzzHarnessTests` and `EditorReadinessTests`), also testing-only: no `src/KatLang` behaviour, public API, or Lean artifact is involved. It fuzzes the editor-facing semantic model in `src/KatLang/Semantics/` (`SemanticModelBuilder` / `SemanticModel`) — classification, position resolution (hover), symbol lookup, go-to-definition, document symbols, and signature metadata — over arbitrary and malformed source with difficult UTF-16 code units, cursor placements, and bounded edits. Lean models neither surface syntax nor editor tooling (cursors, spans, classification, completion ordering, recovery), so no Lean update applies; the oracle is layered over the real lexer, parser, front end, and `BuiltinRegistry` metadata instead. The invariants are that tooling never throws unexpectedly (a structured "no result" and the documented unresolved-`load` DECLINE are valid outcomes — the harness pre-checks `LoadElaborationGuard.TryFindFirstUnresolvedLoad` and declines exactly as a correct editor caller must, because `SemanticModelBuilder.Build` throws on an unresolved load by contract), every source-backed span is valid under the shared `SourceSpanValidator` code-unit model, every occurrence's source slice equals its reported name, a resolution's target is a same-named declaration the model lists, builtins are non-source and match the registry's fixed-arity metadata, no synthetic `$`-name or comment/string-interior identifier leaks, ordinary and dotted spellings of one callable resolve identically, and results are deterministic and isolated across requests and small edits (A/A, A/B/A, concurrent, and no stale-source leak). The payload is a frozen 13-byte template selector reusing the Phase 5 UTF-16 code-unit tables; seeds are hex payloads for the same reason the UTF-16 ones are. The reused `SemanticModel` invariants align with `SemanticModelTests`; the editor target adds no semantic rule of its own. The only `src/KatLang` change in the phase is this documentation entry.
  - **Not claimed**: this is not complete memory safety. Source-text length, per-module download size after the downloader returns, aggregate accepted module source, distinct accepted-module count, and import depth are bounded by `SourceProcessingLimits` (see the source/module input-size note above). Still out of scope here: CLR overhead variation, host-constructed `Result` objects, live-memory (as opposed to created-slot) accounting, process-wide memory shared between runs, downloader-side buffering before a returned string can be measured, network fetch attempts (failed or policy-rejected fetches are uncharged and the number of load sites is bounded only by source length), and the lower-level caller-sized `Lexer.Tokenize` API. The cumulative evaluator counter measures slots CREATED and is deliberately not a live-memory measure.

- **Output formatting is host-side plain-text presentation, not KatLang semantics** (`KatLang.Formatting`: `OutputFormatter`, `OutputFormatters` with the stable ids `exact`/`readable`/`concise`, `OutputFormattingOptions`, `StringDelimiterMode`, `BoundedOutputWriter`, plus the public root-output view `RunResult.Success.OutputRows`). Formatters render ALREADY EVALUATED results only: they never re-parse or re-evaluate, never modify/spread/flatten/collect/reorder/merge/split values, and the parser and evaluator have no knowledge of formatter modes or options. `exact` and `RunResult.ToDisplayString` share the formatter-neutral `KatLang.Rendering.ValueTextRenderer` with the canonical raw-string strategy, so they are byte-identical without making `RunResult` depend on formatting policy; `readable`/`concise` change whitespace/layout and (optionally) string QUOTING only — string content is always verbatim, and an August 2026 audit confirmed no display path ever specially handled `_` (the only underscore consumption is the lexer's number-literal digit-separator rule), a contract now pinned by `Formatting/UnderscorePreservationTests`. All formatter rendering follows the established robustness rules: iterative indexed-continuation-frame traversal (never recursion, never sibling-granular stacks), width-CAPPED inline measurement (`CappedWidthSink`) so DAG-shared values cost at most O(width) per emitted node, and the all-or-nothing `MaxDisplayLength` contract through the same `BoundedDisplayWriter`/`Finish` path (a per-call option can only LOWER the run's limit). The delimiter policy is quoting-only by contract: `concise` structural elision is decided per concrete value through one shared raw-token safety predicate (`DelimitedStringTextPolicy.IsTokenSafe`, used identically by measurement and emission), so `StringDelimiterMode.Never` does not globally disable concise layout — ambiguous raw strings retain their CONTAINING sequence's punctuation while safe raw labels still elide. The safety predicate is conservative about invisible text: Unicode Format-category characters (bidi controls, zero-width spaces, BOM/ZWNBSP, soft hyphen, word joiner) and unpaired surrogates are never safe undelimited tokens and always need delimiters (well-formed surrogate pairs such as emoji are ordinary content), and numeric-looking detection follows the lexer's digit-separator grammar (`1_000` reads as a number) while non-ASCII digits do not — pinned by `Formatting/UnicodeTokenSafetyTests`. Layout selection uses width AND structural complexity (`StructuredLayoutRenderer.RequiresStructuredLayout`): a sequence with two or more structured children lays out multiline even when its flat text fits the preferred width, a safe nested multi-pair string/value child renders as pair lines (readable) or an indented pair block (concise) rather than a flat join, and the zero-root-spacing root-block gate admits a paren-hidden block only when a nested pair block visibly anchors it — all presentation-only line grouping over the evaluated value, never dictionary/record semantics, with spread-discarded structure never reconstructed. The separate `KatLang.Formatting.PublicApi.Tests` assembly proves extension without `InternalsVisibleTo`. Lean models no rendering, so no Lean update applies.

- Open declarations inside conditional clause bodies are **BRANCH-OWNED**. An `open` written in a clause body stays on that branch body (`Conditional.Branches[i].Body.Opens`), which is the location parameter detection, implicit-argument resolution, exposure, and evaluator lookup actually resolve through. `Algorithm.ElaborateClauseGroup` therefore constructs the family with `Conditional.Opens = []`. It previously also copied `clauses[0].Body.Opens` onto the conditional, leaving clause 0's open expressions reachable by two paths; that copy was redundant (removing it changes no observable behaviour — verified by the valid-program open matrix and the full suite) but harmful, because an open target may contain a nested algorithm (notably under malformed recovery such as an unclosed `(open(...`), so the duplicate ownership let `ImplicitArgumentResolver` and `PropertyExposureResolver` rebuild the same subtree once per path and unfold a linear-size reference DAG into an exponential (2^depth) tree. Parser-level/front-end representation only: the AST inductive, clause classification, lookup order, and evaluation semantics are unchanged, and Lean does not model surface clause-family elaboration, so no Lean update applies. Regression coverage: `ClauseFamilyOpenOwnershipTests`.

- Property exposure classification (`PropertyExposure` on `Property`) is **computed by the C# front end only** (`PropertyDependencyGraphBuilder` seeds consumed by `PropertyExposureResolver`); Lean consumes `PropDef.exposure` as an INPUT field (default `.exported`) and never derives it, and the generated differential corpora emit only exported properties, so exposure-classification changes are C#-frontend scope with no Lean update. The documented rule (tutorial: a nested property that depends on parameters owned by an enclosing algorithm is local-only) is attribution by OWNERSHIP, with no exemption for where the capture is written: ancestor-parameter references inside transparent OutputBundle layers — call/dot-call argument bundles and surviving parenthesized groups — count exactly like the same reference written directly in the property body, matching `ParameterDetector`'s free-identifier transparency model (transparent bundle content owns no names). The August 2026 correction removed a seed-side fold that credited ancestor-owned names to transparent layers and thereby left `P = F(x)` / `P = (x, 1)` incorrectly `Exported` (publicly reachable via dot access and `open`/`load`) while `P = x + 1` was local-only; brace-block scope boundaries are unchanged (`Apply({y + 1})` stays exported-eligible, `Apply({x + y})` still captures `x`). Observable-behavior fix: previously mis-exported captures now classify `LocalOnlyCapturedAncestorParameters` and are hidden from the public surfaces. Regression coverage: `PropertyExposureResolverTests` (transparent-layer matrix incl. graph seeds, nested layers, dot-call args, own-parameter and brace-scope controls) and `EvaluatorTests.Eval_CapturedNestedProperty_ThroughCallArguments_DotAccess_IsLocalOnly`.

- **Name lookup has TWO C# implementations, and they must select the same declaration** (August 2026, Track 10). The evaluator resolves through `Evaluator.LookupLexical` / `LookupLexicalResolvedAlgorithm` / `ResolveAlg` (since M8+M9 the evaluator side is ONE chain: `LookupLexicalResolvedAlgorithm` is the algorithm projection of the binding-carrying `LookupLexical`, mirroring Lean's `lookupLexical` over `lookupLexicalProperty`); the front end and editor resolve through `ElaboratedScopeLookup`, which `ParameterDetector` and `Semantics/SemanticModelBuilder` share. This is not a presentation duplicate: the detector's verdict REWRITES the program (a name it finds no declaration for becomes an implicit parameter), so a front-end lookup disagreement changes what the evaluator is later asked to run. Both implementations must reproduce the same rules — ownership-first (local, then the parent chain including the builtin prelude, then opens), public-AND-exported-only exposure through `open`, first-hit-wins by scope level, unique-provider-or-nothing, and **first-occurrence-wins dedup of named open targets keyed by `Evaluator.OpenExprName`, with inline blocks keyed positionally and never deduplicated** (Lean: `resolveAllOpens`). The dedup rule was missing on the `ElaboratedScopeLookup` side until Track 10, so `open Lib, Lib` resolved at runtime but read as ambiguous in the editor. Where the two contracts differ deliberately, that difference is pinned rather than removed: the editor is error-tolerant, so an illegal open target (`open count`) fails the runtime's whole-list validation while the editor still resolves names supplied by the other, valid targets. Regression coverage: `LookupCoherenceTests` (declaration-identity relation over unique sentinels across all three views) and the `open`/visibility family in `SemanticExplorerCases.lean`.

- **Two `Result` view pairs are currently the SAME function, and that is not a licence to merge them** (August 2026, Track 11 mutation audit). `Evaluator.BuiltinCollectionItems(v)` and `v.SpreadItems()` have identical bodies (`ListValue => items, _ => ToItems()`), and `Result.TryLanguageAtoms` / `Result.TryToHostAtoms` are line-for-line identical traversals (only the `Str` arms — spelled out versus folded into `default` — and their passive test-only observation counters differ). Substituting either pair for the other is unobservable — four mutants proved it — so no test can defend the separation. They are separate BY CONTRACT: `builtinCollectionItems` and `languageAtoms` are Lean-modelled LANGUAGE semantics (Lean writes `builtinCollectionItems` with its own three arms), while `spreadItems` is the spread marker's view and `hostAtoms` is a HOST projection that may diverge whenever an embedding need changes. Deduplicating them would silently couple a language rule to a host rule. Truth testing is the one member of this family that is genuinely distinct and tested: `ToAtoms` stays list-opaque, and swapping it for `LanguageAtoms` is caught by the language-spec probes.

- **The `open` exposure filter is only observable at the AMBIGUITY boundary** (August 2026, Track 11). Dropping `IsPublic` or `Exposure == Exported` from `LookupPublicProp` / `LookupPublicPropBinding` survived the entire suite on both lookup twins, because in the obvious `open Lib` + private `X` shape the front end has already resolved `X` to nothing and promoted it to an implicit parameter — the evaluator's filter is never reached. A regression test for anything this filter decides must pair the hidden member with a VISIBLE provider of the same name (`open Pub, Lib`), so the verdict becomes "resolves to Pub's X" versus `ambiguousOpen`. Coverage: `LookupTwinEquivalenceTests` plus the `openPrivateMemberIsNotASecondProvider` / `openLocalOnlyMemberIsNotASecondProvider` explorer specials.

- **Front-end elaboration can make an evaluator branch unreachable from ordinary source, and that changes who owns the diagnosis** (August 2026, Track 12). The dotted-`open` checks in `ResolveOpenPropAccess` — `NotPublicProperty`, `UnknownProperty`, and the exposure gate — are the clearest case: written the obvious way (`open Lib.PrivateSub` then a name that member would supply), the front end resolves the target, finds nothing, and promotes the name to an IMPLICIT PARAMETER, so the user sees an arity/unresolved-implicit-parameter diagnostic and the evaluator's visibility check never runs. Open resolution is additionally LAZY: a name that resolves by ownership never consults the opens, so an illegal target in the same declaration goes unvalidated entirely. A regression for anything in this family must therefore pair the bad target with a SECOND valid provider and reference a name only that provider supplies (`open Lib.S, Pub` + `Y`). Coverage: `OpenPathResolutionBranchTests`. Before Track 12 the whole family was unprotected, and the one test named `Eval_Visibility_NotPublicPropertyOnPrivateIntermediate` was evaluating a PARSE-REJECTED source — `EvaluatorTests.EvalFull` ignores parser diagnostics, so it passed on an unrelated recovery-AST failure.

- **Plain/counted evaluator ownership: the COUNTED implementation is canonical and the plain implementation is its value projection** (August 2026, M8+M9). Where a plain/counted pair is semantically equivalent, the counted twin owns the semantics and the plain twin only discards the emitted-count metadata; C# mirrors the authoritative Lean ownership direction. In Lean, `evalCounted` matches EVERY `Expr` variant explicitly (num/stringLiteral/unary/binary included — the operator semantics live in `evalUnaryCounted`/`evalBinaryCounted`) with NO default arm delegating to `eval`, and plain `eval` is the one-line total projection `(evalCounted e).fst`; `evalUserCall`, `evalConditionalCall`, `evalResolvedCall`, `evalCallExpr`, `evalDotCall`, `applyBuiltin`, `applyBuiltinResolved`, `evalAlgOutputCore`, `evalCaptureValue`, `evalZeroArgPropertyAccess`, and `evalResolvedCallbackCall` are all `.fst` projections of their counted twins, and the ownership-first lookup chain exists once (`lookupLexicalProperty` canonical; `lookupLexical` is its `.alg` projection). In C#, `Evaluator.ProjectCountedValue` is the ONE plain-result projection helper: `EvalCallExpr`, `EvalDotCall`, the `Eval` dispatcher's Param/Resolve/composite arms (via `EvalParamCounted`/`EvalResolveCounted`/the counted spine machines), and the callback/capture/argument/algorithm-output adapters all use it; plain builtin, user-call, conditional-call, resolved-call, receiver-fallback, loop, and zero-argument-access behavior reaches those projections through the counted call/dot dispatch rather than through separate plain wrappers. `LookupLexicalResolvedAlgorithm` independently performs the analogous field projection of the binding-carrying `LookupLexical`. The former independent plain implementations (`EvalUserCall`/`EvalConditionalCall`/`EvalResolvedCall`/`CallLexicalWithReceiver` family, the plain builtin switch, and the resolve-only open-lookup chain) are DELETED. Deliberate exceptions that remain non-projected: (1) the C# plain `Eval` dispatcher still OWNS the true leaves (Num, StringLiteral, synchronous NativeCall, Grace) because the counted dispatchers' leaf-delegation group and its M10 async-exhaustiveness pins depend on that direction — for leaves, plain-vs-counted is the trivial `(value, ValueCount)` wrap; (2) the slot-view family (`EvalAlgOutputSlots`, explicit sequence-value slot walks) returns item lists, not one counted value, so it has no plain/counted pair; (3) the entry-layer root-program decoration pair (`EvalRootProgram`/`EvalRootProgramCounted`) duplicates ~10 lines of MissingOutput decoration inside the M7 run-preparation boundary and is left as-is; (4) the opens-free direct lookup family (`LookupLexicalDirect`, Lean `lookupLexicalDirect`) is a deliberately different rule for open-target resolution, not a twin. Projection does not change zero-arg property cache semantics — the cache key has always collapsed access KINDS to their access SHAPE (`ZeroArgPropertyCacheKey.FromExecution`), so plain and counted spellings shared entries before and after; only the per-kind instrumentation attribution moved onto the counted kinds. Guards: Lean CoreTests projection-parity families (builtin, dot-call, call, total-eval, lookup), the exhaustive-match compile error on a new `Expr` variant in `evalCounted`, `SemanticExplorerHarness`'s plain-vs-counted cross-check on every explorer/spec case, and the C# fail-loud `EvalCounted`/`EvalCountedAsync` defaults.

- **Some evaluator branches are host-API defense, not language semantics** (August 2026, Track 12). `Expr.Grace` reaching the `Eval` catch-all, a non-open-form or `Expr.SequenceConstruct` in `Algorithm.Opens`, and the runtime duplicate-property / missing-output prologue checks cannot arise from any legal source program — the parser or an elaboration pass removes the shape first. They are revalidated because `Evaluator.Run`/`RunCounted` accept prebuilt ASTs from hosts and internal stages. Pin these at that boundary (`EvaluatorDefensiveBranchTests`), NOT with a LanguageSpec or Lean case, which would assert behavior the language cannot express. Note that `ResolveAllOpens`'s up-front form-validation loop duplicates the per-target rejection in `ResolveAlgForOpen`: the only observable difference is ORDERING (all shapes validated before any target resolves), so a test asserting merely "a bad form is rejected" cannot detect the loop's removal.

## Process

1. Identify the semantic area you are changing.
2. Find the matching row in this manifest.
3. If Lean update is required, update Lean first or in the same change, then update C# and tests.
4. If the change is C# implementation/tooling only, C# tests are sufficient.
5. If the change is optimization-only, add or preserve equivalence tests against the generic path.
6. If unsure, stop and ask before changing observable semantics.
