## Known gaps

- Lean semantic assertions in `lean/CoreTests.lean` use `#guard`, so regressions fail `lake build CoreTests`. Remaining `#eval` commands are demo/inspection output.
- Automated C# <-> Lean output comparison exists for a bounded generated corpus: `lean/SemanticExplorerCases.lean` (generated by `tests/KatLang.Tests/SemanticExplorerLeanArtifactTests.cs`) pins the value/receiver corpus — currently 1,417 surface cases, of which 1,385 are Lean-representable (32 are parse-level exclusions), plus 13 internal-node cases, yielding 1,398 case guards and two partition-count guards (1,400 executable `#guard` directives total) — to C#-observed raw structure, emitted count, and error category; `lake build SemanticExplorerCases` fails on any divergence, and each case also cross-checks Lean's plain (`runResult`) vs counted evaluators. (The generated file's header/footer counts are authoritative if this sentence drifts.) Lean still does not parse surface KatLang — the corpus is emitted as Lean AST constructions mirroring the C# parser's elaboration. See `docs/design/sequence-boundary-audit-2026-07.md`.
- Lean currently does not model the C# `Math` runtime surface such as `Math.Random` and `Math.RandomInt`. Lean does model zero-argument property cache semantics for property-style `A` versus explicit `A()`; C# cache instrumentation and performance counters remain implementation-only.
- Conditional branch-arity validation is enforced at BOTH of Lean's documented enforcement sites (August 2026; formerly a known hand-built-AST gap). The parser still rejects mismatched clause families during clause elaboration with richer source-positioned diagnostics, and every prebuilt-AST evaluator entry point now also runs the shared pre-evaluation validation walk — `AlgorithmValidation.FindFirstPreEvaluationViolation`, the mirror of the `validateExplicitParamOutputInvariantExpr` pass Lean's `runResultM` runs before evaluation — which rejects a hand-built conditional whose branches disagree on top-level pattern arity (`EvalError.BranchArityMismatch`) or top-level output arity (`EvalError.BranchOutputArityMismatch`) BEFORE branch matching, optimizer planning, or any evaluation, even when the malformed conditional is never referenced. Payload and precedence match Lean exactly: expected comes from the first branch and actual from the first mismatching branch; an input-arity mismatch suppresses the output-arity check for the same conditional; the diagnostic name is the nearest enclosing property name with Lean's default label `conditional` for a conditional reached through expression position (property name context does not flow through expression descent); and one depth-first walk in Lean's traversal order decides precedence across violation kinds (this same walk owns the explicit-parameters-require-output invariant, so the two checks share one traversal). The parser's post-parse walk deliberately keeps the branch-arity checks off — clause elaboration already owns that rejection for surface programs, with unchanged diagnostics. Regression coverage: `ConditionalBranchArityValidationTests` (C#, including the entry-point agreement matrix and traversal-precedence pins) against the Lean CoreTests guards `branchInputArityMismatchIsRejected` / `branchOutputArityMismatchIsRejected` / `nestedUnusedConditionalIsStillValidated`.
- `Expr.SequenceConstruct` / `Expr.sequenceConstruct` is an internal sequence-join node, not the AST representation of written parenthesized sequence values (those are zero-parameter blocks). The parser and production transformations have zero origin sites for it (visitors only rebuild an existing node); the public C# AST API and Lean's `sequenceConstruct` helper remain intentional external origin mechanisms. Its value evaluation drops `()` leaves; Lean and C# agree on it (plain evaluation is the counted projection on both sides). Guarded by `SequenceConstructContainmentTests`, CoreTests `internalSequenceConstruct*` guards, and the internal-node section of the generated `SemanticExplorerCases.lean`. Compatibility note: the July 2026 audit removed an undocumented C#-only reshape of lone hand-built `SequenceConstruct` builtin arguments — surface programs are unaffected; external semantic-AST consumers now get the Lean-aligned grouped-argument behavior (authoritative details in `docs/design/sequence-boundary-audit-2026-07.md` §7).

- Whole-value `Result` traversals are ITERATIVE (explicit stack), never natively recursive, because value NESTING DEPTH is unbounded host-side: evaluation limits bound only per-collection breadth, an ordinary in-budget loop (`Wrap = [x]`, `A = Wrap.repeat(n, 0)`) builds a depth-n value in n steps, and hand-built host trees bypass the parser entirely — a recursive walk overflowed the host stack at ~3,700 nesting levels (structural `==` on the default 1 MiB Windows stack), an uncatchable `StackOverflowException` that terminates the embedding process. The August 2026 pass rewrote every remaining recursive whole-value walk with explicit stacks: `Result.ValueComparer` equality and hashing (consumed by `==`/`!=`, `contains`, `distinct`, and the repeated-bind equality checks), `Result.Normalize`, `Result.ToAtoms`, `Result.TryLanguageAtoms`, `Result.TryToHostAtoms`, `Evaluator.FormatResultForDiagnostic` (deep values rendered into diagnostic messages), and `Evaluator.ResultToExpr` (dotted-receiver/prepared-argument reification); the already-iterative bounded display renderer (`RunResult.AppendValue` / `BoundedDisplayWriter`) was converted from pending siblings to the same indexed-frame discipline. The traversal stacks hold INDEXED CONTINUATION FRAMES — one frame per open structure level carrying the collection (or collection pair) and the next child index — never one entry per pending sibling: a legal collection holds up to 100,000 items (`MaxSupportedCollectionItems`), so sibling-granular stacks scaled with BREADTH and allocated large-object-heap-sized backing arrays for wide, shallow values (~4.2 MB per wide `==` or bounded display, ~2.1 MB per wide hash, repeated by `distinct` per hashed value). The bounded renderer incurred that allocation before it could enforce even a tiny output-length limit. Auxiliary traversal storage is therefore O(nesting depth); storage for a produced value, atom collection, diagnostic string, or reified AST is required output, not traversal overhead (`Normalize`/`ResultToExpr` per-level destination arrays are the produced structure). This is implementation robustness only: traversal order, produced values, hash inputs, diagnostic text, display text, and reified ASTs are unchanged for every program that completed before, programs that previously killed the process now complete or return their ordinary structured errors, and Lean's unbounded evaluator models no host stack, so no Lean update applies. Regression coverage: `DeepValueRobustnessTests` (depth), `WideValueRobustnessTests` (breadth, including allocation ceilings on wide flat equality, hashing, and bounded display).

- **Parser recursion is bounded by ONE cumulative WEIGHTED budget that provably fits the documented ≥1 MiB thread envelope — C# host/source-processing safety policy with no Lean counterpart** (`Parser.MaxNestingDepth` = 384 parser stack units, August 2026 recalibration). The counter threads through every recursive grammar mechanism for the whole parse and NEVER resets inside a nested container, operator chain, pattern, call, or property, so composed constructs charge exactly like their frames stack; the chokepoints are `ParseExpression`/`ParseUnary`/`ParsePatternAtom` (one unit each) plus calibrated per-level surcharges for the heavy productions (parenthesized groups and brace blocks +2, call argument lists +1, and the trailing-brace call form +3, list literals +1). Units are normalized to at most ~1.25 KB of worst-case Debug parser stack, so every shape peaks at ≤ ~480 KB — under HALF the 1 MiB minimum. The prior fixed budget (580 un-weighted units) was calibrated against a roomier stack and admitted heavy shapes past a bare 1 MiB thread's native boundary (parenthesized groups and brace blocks were MEASURED to crash the process at 211-225 levels ≈ 460 units, ~4.7 KB/level; call nesting ~3.5 KB/level, list literals ~2.8 KB/level, patterns ~1.2 KB/level, prefix unary ~1 KB/level; mixed-container alternation composes additively). The new successful surface capacities — 95 group/block levels, 127 list/call levels, 382 prefix levels, and 384 pattern levels, identical in Debug and Release because the budget is deterministic — were each ALSO proven to parse on a dedicated 512 KiB thread (half the envelope, ≥2x empirical margin), and one-beyond returns the established source-positioned "nesting is too deep" diagnostic. Right-associative power consumes the same cumulative recursion budget, but its completed AST also falls under the older `MaxExpressionChainDepth` policy, so its successful maximum remains 256 operators (257 gets the chain diagnostic, while much deeper power input crosses the recursion budget before construction). NESTED-MODULE PARSING is covered by the same budget: a downloaded module's parse runs above the module loader's live traversal frames, so the loader pre-charges a conservative stack DEBT (`ModuleLoader.NestedParseStackDebt`, two units per three live traversal levels, rounded UP — modeling ~0.83 KB/level above the worst measured ~0.8 KB/level Release cost) through the internal `Parser.ParseSyntax(source, initialNestingDebt)` entry; the combined proof (loader bytes + worst-case parser bytes ≤ ~480 KB for every permitted base) holds for the whole chain, an indebted rejection surfaces on the established `load:` channel at the load site, rejected modules are fetched at most once and never cached, and cache hits skip fetch/parse/traversal but the final composed root is always re-gated. Initial debt is clamped and guarded before the first recursive production, and every heavy surcharge is released through `finally`, including on the limit exception. Iteratively parsed binary and postfix chains keep their separate per-expression AST-depth ceiling (`Parser.MaxExpressionChainDepth` = 256, unchanged — chains consume O(1) parser recursion except for the right-associative power production, and the language's established flat-chain contract is unaffected by the new budget). This is a C#-parser robustness limit only: it does not change the AST inductive, evaluation semantics, or the parse of any in-budget program (identical AST, spans, and diagnostics); lowering the extreme-nesting capacity is deliberate resource-policy narrowing in place of process termination, and Lean does not model surface parsing, so no Lean update applies. Regression coverage: `ParserNestingDepthTests` (per-shape exact boundaries, cumulative mixed-container pin), `ParserExpressionChainDepthTests`, and the `ParserRecursionBudget`/`DeepNestedModuleChains` subprocess probes in `AstStructuralDepthProcessTests` (1 MiB threads, Debug and Release); tooling: `fuzz/KatLang.ParserFuzz` depth probe.

- **Structural AST depth is bounded by a non-recursive preflight, and every accepted shape is process-safe on the documented baseline — C# host-safety policy with no Lean counterpart** (`AstStructuralPreflight` + the iterative expression-spine evaluator, August 2026). The public AST model is host-constructible, and its consumers walk it recursively on the CLR stack, so a deep host-built tree (a few hundred spine nodes on a 1 MiB stack) terminated the embedding process with an uncatchable `StackOverflowException`; `EvaluationLimits.MaxDepth` never guarded this, because it bounds DYNAMIC algorithm invocations, not static tree shape. Every evaluator entry point accepting a preconstructed AST (`Run`, `RunFlat`, counted, observed, top-level-property, optimizer-on and -off) runs an explicit-stack iterative preflight BEFORE the recursive validation walk and anything after it, rejecting over-deep trees with `EvalError.AstDepthLimitExceeded` and cyclic node graphs (constructible because record collections are `IReadOnlyList` views over caller-owned lists) with `EvalError.AstCycleDetected`; shared ACYCLIC subtrees are accepted, judged by their longest path via reference-identity memoized weighted heights (never structural equality/hashing, which would recurse), in O(nodes + edges).
  - **Safety invariant (the point of the whole mechanism):** on the documented supported execution environment — a thread stack of at least 1 MiB, the CLR/Windows default — every AST an accepted gate admits either completes or returns an established structured KatLang outcome; no accepted shape is known to overflow the process stack. This was NOT true of the first cut (which accepted depths whose evaluation was measured to crash); it is now established by construction plus measurement, per consumer class below, and proven at the exact boundaries by the near-boundary subprocess probes on dedicated 1 MiB threads in Debug and Release.
  - **Iterative expression-spine evaluation** (`Evaluator.EvalExpressionSpineCounted`): unary, binary, index-selection, and list-literal composites — the shapes whose recursive evaluation frames were measured to exhaust a 1 MiB stack WITHIN any ceiling honoring the flat-chain contract (Debug boundaries ~330-340/binary and unary, ~270-285/index, ~290-300/list; Release only ~400-600/~300-500) — now evaluate through one explicit frame stack hooked into the `Eval`/`EvalCounted` dispatch, preserving child order, error decoration (only the index expression attaches its span to child/coercion errors), spans, budget reservation points, and emitted counts exactly (the machine subsumed the former `EvalIndexSelectionCounted`/`EvalListLiteralCounted` helpers; a permanent 384 KiB-thread subprocess pin proves these paths are not depth-proportional). The internal sequence-join kinds keep their own iterative handling and weigh 0 on the evaluator gates (pinned by `Eval_SequenceSpread_LongChain_IsStackSafeForFlatAndCountedEvaluation`); a `DotCall` link weighs 3 units because its resolution machinery (pipeline planning, `ResolveAlg` descent, lexical receiver-injection fallback) is deliberately NOT rewritten and consumes several large frames per link — measured pure dot-call chains fail at ~160 links (Debug) / ~250 links (Release) on 1 MiB, and the parser admits 256-link chains, so weighting (max ~100 accepted links, ≥1.6x margin both configs) closes what was a live SOURCE-reachable crash.
  - **Two-tier ceilings, clamped inside the checker itself; `MaxAstDepth` can only lower the evaluation one.** `EvaluationLimits.MaxSupportedAstDepth` = 300 gates every FAT-FRAME consumer: evaluation, front-end ELABORATION (`FrontEndPipeline.FinalizeElaboration`, both module and non-module paths — `ParameterDetector.RewriteParams` overflows a 1 MiB thread between ~500 and ~626 composed nodes in BOTH configs, a gap the first cut left open on the non-module path), and `SemanticModelBuilder` (throws `ArgumentException`; building a 640-node spine overflows a 512 KiB thread while a 300-node one completes within it, i.e. ≥2x margin at the gate). 300 is anchored to the language's weight-one/iterative flat-chain contract (`Parser.MaxExpressionChainDepth` = 256 ⇒ ~259-node engine spines) plus elaboration slack — not to a crash boundary; dot-call links are the documented exception and consume three structural units each. The worst remaining recursive shape, nested block/algorithm bodies at 2 nodes per level, was measured safe at 240 levels (~481 nodes) on a bare 1 MiB Debug thread while the ceiling admits 150 (~55% of measured capacity; Release roughly halves usage), and nested calls stop with the established structured invocation backstop. `AstStructuralPreflight.RawSyntaxMaxAstDepth` = 640 gates only the WALKER-CLASS consumers (the `ParseSyntax` post-parse validation walk and the module loader's composed-root load-invariant walk; shared-walker boundary ~3,000-4,000 nodes, ≥4.5x margin). The deterministic parser budget now narrows the single-mechanism surface maxima to 95 group/block, 127 list/call, 382 prefix, and 384 pattern levels; power remains independently capped at 256 operators by the established expression-chain policy. Every accepted raw tree is still composition-gated at 640, and raw syntax between the raw and elaboration gates parses but front-end elaboration rejects it with one structured diagnostic citing its own limit. A per-node `TryEnsureSufficientExecutionStack` probe at the `Eval`/`EvalCounted` heads was evaluated and REJECTED: the CLR probe reserves roughly half of a 1 MiB stack and falsely rejects working programs; it remains in use only at its established dynamic-invocation chokepoints.
  - **Composition and gate placement:** before the cumulative parser budget, independent per-mechanism counters restarted inside nested containers and therefore composed into legal-looking source trees deep enough to kill the process inside `ParameterDetector`; the current single weighted counter never resets during a parse. `ParseSyntax` gates its output before its own recursive walk, the module path re-checks the composed root at the raw cap before the load-invariant walk, `FinalizeElaboration` applies the elaboration gate on BOTH paths before any elaboration pass, and the evaluator gates run before its validation walk. The pre-evaluation validation walker additionally memoizes visited nodes by reference identity (its violation is node-local, so revisits are pure waste): a compact shared DAG — 2^250 paths in ~500 nodes — previously hung that pure pass; EVALUATION of shared nodes deliberately stays per-occurrence (separate occurrences may need separate values, nondeterminism, errors, and budget charges), in the same unbudgeted-compute class as a non-terminating loop unless a step budget is configured. The public pattern conveniences `ParameterPattern.Captures` (whose recursive flatten crashed on deep host patterns), `FlattenCaptures`, `HasMultipleCollectingCapturesAtAnyLevel`, and `Pattern.BoundNames` are iterative with order/duplicates/spans preserved; remaining recursion on caller-owned data before any entry point (record structural equality, `DisplayName`, `ElaborateClauseGroup` head classification) is construction-time host recursion outside the gates, documented rather than gated.
  - **Diagnostic expression-name rendering is iterative and output-bounded** (`ExprNameRenderer`, August 2026 review repair): the former recursive `OpenExprName`/`ExprDiagnosticName` renderers were the one consumer class behind the evaluator gates that still recursed through the zero-weight internal join/spread chains (reachable through binary operand-shape contexts, call/dot-call context construction, open-form/property errors, and optimizer reason strings — a gate-accepted host AST could terminate the process while its error message was being built, and call/dot-call contexts were rendered EAGERLY even on success). One shared explicit-stack engine now renders every mode byte-identically for in-bound names, deterministically elides beyond `ExprNameRenderer.MaxRenderedNameLength` (512 UTF-16 units) with the established `…` marker, bounds total work by a processed-item cap so a hostile tree costs no more than the bounded output justifies, and never uses record equality/hashing/`ToString()` on the rendered tree. Wide list/block collections use one indexed cursor rather than pre-pushing all siblings, so the work bound applies before breadth-proportional allocation; truncation also preserves valid UTF-16 surrogate pairs. Resolved-call helpers carry a stack-only diagnostic descriptor (an existing identifier string or the original expression reference), so successful calls allocate no name string or per-call closure; only a non-resource-limit error renders the name for each diagnostic/context frame (`WithCallCtx`/`WithDotCallCtx`).
  - **Every public front-end boundary that recursively consumes host ASTs is gated** (August 2026 review repair): `ParameterDetector.Detect` (placeholder root + structured diagnostic, measured block-shape failure boundary >1,000 nodes both configs, >3.3x margin at the 300 ceiling) and `ImplicitArgumentResolver.Resolve` (`ArgumentException`, matching `SemanticModelBuilder`; measured boundary ~600-800 nodes Release, ≥2.0x margin) preflight at the shared fat-frame ceiling; the front-end pipeline calls their internal `*Prevalidated` cores behind its one common gate so elaboration's own modest depth growth is absorbed by the ceiling's margin rather than re-gated mid-pipeline. `ModuleLoader.Elaborate` preflights host roots at the raw-syntax cap (its own rebuilding traversal measured ~1,600-1,700 counted levels Debug / ~1,300-1,600 Release before overflow on 1 MiB, ≥2.0x margin at 640) and additionally bounds nested module loads CUMULATIVELY: a nested load elaborates the fetched module while every ancestor traversal frame is live, so per-module gating alone could stack a permitted 64-module chain × per-module container depth into tens of thousands of frames from pure source (deep-brace-nested `open` targets). Each load site now charges its own traversal path depth (plus a fixed splice-frame allowance) against `ModuleLoader.MaxTraversalDepth`, judging the fetched module's tree iteratively BEFORE descending; an unsafe nesting is the structured `load: … cumulative structural depth limit` diagnostic plus the load's established placeholder, with the module's committed source reservation kept exactly like a module that fails to parse, and the base restored via `finally` on every unwind (downloader failure, cancellation, nested rejection). Cache hits splice without re-fetching, parsing, or recursively traversing the cached module, but the complete result is re-gated before the public loader boundary returns so a shallow cache entry cannot become unsafe at a deeper splice path. Nested-module PARSING is bounded by the same policy: every nested `Parser.ParseSyntax` call starts with a conservative stack debt converted from the live traversal levels, so the parser's cumulative recursion budget bounds loader frames plus parser frames together (see the parser-recursion note above for the combined proof and boundaries) — no module source accepted for parsing at any permitted load position can overflow the documented envelope.

Successful deterministic behavior — results, emitted counts, and operational budgets — remains unchanged only for programs that also satisfy the applicable elaboration and evaluator structural profiles. The new host-safety policy intentionally rejects otherwise parseable unsafe shapes with controlled diagnostics; sufficiently long dot-call chains are the principal source-reachable example because each link consumes three evaluator structural units. The preflight charges nothing to any `EvaluationBudget` and holds no static state; the 64-deep module-chain maximum loads through the real loader and either completes or stops with the established invocation backstop on the smallest stacks. Lean's evaluator is a total function over an inductive type with no host stack, so no Lean update applies. - Line comments are surface-lexical trivia owned by the C# lexer: a `#` outside a string literal starts a comment that ends before the next physical newline (or at end of source), with no whitespace required before the marker. The former `//` marker was removed in August 2026 with no compatibility alias, so `/` is always the division token and `//` is two division tokens. Comment tokens never reach the AST, and Lean models no surface syntax, so no Lean update applies; generated Lean corpora changed only where embedded KatLang source strings contained comment text. Regression coverage: `CommentSyntaxTests`, plus the comment-invisibility tests in `LexerTests`, `ParserTests`, and `EvaluatorTests`.

- **Source and module input-size limits are host runtime policy, not KatLang language semantics** (`SourceProcessingLimits`, `SourceProcessingBudget`). They bound the work and memory a run spends turning source text and imported modules into an elaborated program BEFORE evaluation; Lean models neither surface parsing nor module loading, so no Lean update applies. They are ordinary parse/front-end `Diagnostic`s (never an `EvalError`), so a violation surfaces as `RunResult.ParseFailure` and never as an evaluator error. Four always-active ceilings, each configurable only downward via `RunOptions.SourceProcessingLimits`, clamped above the supported maximum, non-positive values rejected, counters run-scoped and never static (a fresh `SourceProcessingBudget` per run; a rejected reservation leaves every counter unchanged):
  - **Per-source length** (`MaxSupportedSourceLength` = 2 MiB UTF-16 code units) applies to the main program and to each imported module, checked before tokenization. It subsumes and re-labels the former fixed 2 MiB "bytes" module-download cap (now correctly UTF-16 code units, consistent between main and module source). The probes record source/token/node/diagnostic counts and showed `frontendNodes = parserNodes` across the included shapes; observed ratios are calibration samples, not universal proof bounds. The source ceiling bounds those counts; the formerly quadratic per-construct paths (wide deconstruction and large clause families, below) are now linear, so it is a resource ceiling rather than the last line of defence against quadratic parse work. Enforced at the raw `Parser.ParseSyntax` boundary (the always-active hard ceiling, which also protects the raw-parser fuzz target) and, for a lower configured value with a richer message, in `FrontEndPipeline` (main) and `ModuleLoader` (each module). The lower-level public `Lexer.Tokenize` API remains caller-sized and linear-scan; every parser/execution path goes through the protected parser boundary.
  - **Import depth** (`MaxSupportedModuleDepth` = 64 nested loads). The module loader resolves `load` recursively, so a deep transitive chain overflowed the host stack — an uncatchable `StackOverflowException`, measured at 562 (Release) / 605 (Debug) levels on a 1 MiB Windows stack by the `module-depth-search` probe. This converts that crash into a structured diagnostic; a chain of 5000 now returns a defined error instead of terminating the process. Those crash measurements are Windows-specific; smaller-stack hosts such as WASM motivate the conservative margin, but WASM stack headroom was not measured.
  - **Aggregate source** (`MaxSupportedAggregateSourceLength` = 8 MiB) and **distinct-module count** (`MaxSupportedModuleCount` = 256), run-scoped, because a per-module ceiling alone bounds neither a wide graph of many 1 MiB modules (probe accepted 67 MB) nor thousands of tiny modules (probe accepted 5000). A repeated `load` of an already-cached URL consumes no new module slot or aggregate. Count capacity is checked before fetch; after download and the per-source check, aggregate source and module count are committed atomically before parsing. Failed downloads and rejected source/aggregate reservations are not negatively cached or charged, so they may be fetched again at another load site.
  - **Host cancellation** is configured by `RunOptions.SourceProcessingCancellationToken` and applies only while parsing and elaborating source/modules before evaluation. `DownloadCodeWithCancellation` receives that exact token and deterministically takes precedence when the legacy `DownloadCode` callback is also configured; the legacy property remains source-compatible. Cancellation is checked before and after each fetch, before parsing downloaded source, before recursive elaboration, and between the main front-end phases. An `OperationCanceledException` (including `TaskCanceledException`) propagates only when the configured host token is cancellation-requested; otherwise it is an ordinary `load: failed to fetch` diagnostic, preserving the default HttpClient downloader's ten-second timeout as a fetch failure. Cancellation unwinds import depth and in-progress state through `finally`, rolls back the cancelled module frames' aggregate/module-count reservations, and never caches a partial module. The token and all mutable loader/accounting state are run-scoped; shared `RunOptions` and concurrent runs introduce no static cancellation state. The token deliberately does not cancel arbitrary evaluator computation; evaluation remains governed by `EvaluationLimits`. This is implementation/host-policy behavior and requires no Lean update.
  - These bound PARSING and MODULE LOADING only. The prebuilt-AST evaluator entry points bypass parsing entirely and are governed by `EvaluationLimits` alone, so the source-length policy makes no claim about hand-built ASTs. This work also required making three pre-evaluation passes linear that were quadratic in the top-level declaration count — `PropertyExposureResolver` and `ImplicitArgumentResolver` (each cloned an O(P) visible-scope map once per sibling property; now shared when a child adds nothing) and `Parser.ParseAlgorithm` (duplicate-name detection scanned the growing property list per declaration; now an O(1) name set). These are performance/robustness corrections with no semantic change, so no Lean update applies and no row above is triggered beyond this note. A subsequent correction pass additionally made the WIDE-DECONSTRUCTION elaboration linear: `x0..x{N-1} = RHS` elaborates to one shared `$deconstruct$N` source plus N target properties, each binding through a synthetic inline helper that carries the shared N-capture `SequenceValueParameterPattern`, and five O(N)-per-helper cost sites made a wide deconstruction O(N²) — the parser's `Algorithm.User` construction (`FromDeclarations` rebuild) and post-parse validation walk (`Params.Count` list materialization plus a per-parameter no-op iteration), the three front-end passes (`ParameterDetector`, `ImplicitArgumentResolver`, `PropertyExposureResolver`), and `PropertyDependencyGraphBuilder`. Each now treats the fully-formed synthetic helper as an elaboration LEAF (O(1) per helper), and the shared `AstWalker` gained an in-family `VisitsExplicitParameterDeclarations` opt-out; the elaboration, AST shape, evaluation, diagnostics, and Lean model are all unchanged (implementation-only, verified by full-suite equivalence and structural regressions). A follow-up pass then removed the two remaining per-construct quadratics, both implementation-only (no Lean update; Lean models neither surface parsing nor front-end elaboration nor the run-scoped evaluator caches): **(1) Conditional clause-family duplicate detection** was an all-pairs O(C²) scan — the parser's per-clause `branchList.Any(IsMatchEquivalent)` insert check and the runtime `Algorithm.HasDuplicateBranchPatterns` guard both compared every new/each pattern against all earlier ones. Both now index patterns in a hashed set (`Pattern.MatchEquivalenceComparer`) whose equality IS the exact `IsMatchEquivalent` and whose hash is a deterministic FNV structural fingerprint consistent with it (binder spelling and spans ignored, first-occurrence binder numbering, literals and sequence shape included), so an equivalence class lands in one bucket and any unrelated collision is resolved by the exact comparison — O(C) with branch order, the duplicate diagnostics, and their order/spans all preserved. **(2) Evaluating every target of one wide deconstruction** was O(N) targets × one full N-capture bind, and each bind was itself O(N) (the shared `BindParameterPatternList.AddBindings` rebuilt a name set and linear-scanned the accumulators per capture), i.e. effectively O(N³). The N target helpers of a deconstruction now share one identity token, and a run-scoped `IDeconstructionBindingCache` (keyed like the zero-argument property cache — group token plus value/algorithm/counted-environment identity, errors never cached) binds the group ONCE per binding context; each target projects its own slot in O(1). `AddBindings` was additionally made O(1) amortized with running name→value indexes (preserving the repeated-bind equality check exactly), so the single shared bind is itself linear. Deferred binding, per-position values across every pattern shape, written-pattern arity errors, demand-order independence, and run isolation are unchanged; the ONE intended operational change is that later targets of a group no longer repeat the full bind (the shared bind is charged once — see the operational-accounting note). A failed full bind is NOT cached (consistent with zero-argument property failures), so the failure path is a documented residual rather than a shared/linear path; ordinary output short-circuits at the first failed target, so a demanded invalid group binds once in practice. The scaling regressions read passive, SCOPE-LOCAL observation objects, never a static field: a run-scoped `EvaluationObservations` (carried through `EvalCtx`, one per observed run via the internal `Evaluator.RunCountedObserved`) counts full deconstruction binds, and an operation-scoped `PatternComparisonObservations` (passed explicitly to the match-equivalence comparer for one parse via the internal `Parser.ParseSyntax` observed overload) counts exact clause comparisons. No Phase 6 run-time or test-observation state is stored in static mutable fields; both observers are internal, excluded from every public API and language-semantic contract, start at zero by construction (no reset), keep separate and concurrent runs/parses independent, and cannot affect any evaluation or parse decision — a null observer records nothing and the production paths pass null. The clause allocation-ratio regression is design-independent (measures parse allocation) and fails under the old all-pairs implementation even though that path would bypass the observed comparer. Regression coverage: `SourceProcessingLimitsTests`, `Phase6PerformanceRegressionTests`, `WideDeconstructionScalabilityTests`, `ClauseFamilyScalabilityTests`, `DeconstructionSharedBindingTests`, `ModuleLoaderTests`; tooling: `fuzz/KatLang.ParserFuzz` `source-probe` / `module-probe` / `module-depth-search` / `eval-probe` (`eval_all_deconstruct`, `eval_clause_family`).

- Evaluation resource limits are **host runtime policy, not KatLang language semantics**. The Lean evaluator is unbounded and models no fuel, step budget, or recursion budget; it describes the successful/error behaviour of a program *absent host resource limits*. The C# evaluator may additionally stop for depth, steps, insufficient host-stack headroom, one-collection size, cumulative materialized items, one-string size, or cumulative materialized string units; the host renderer separately represents display-length overflow, and the pre-evaluation structural preflight rejects over-deep program trees (`AstDepthLimitExceeded`). These are the nine variants classified by `EvalError.IsResourceLimit` (the structural-cycle rejection `AstCycleDetected` is malformed input, not a resource limit). This is observable OPERATIONAL behaviour but not value semantics: for every program that completes within its limits, the C# result is bit-identical to the unlimited result and to Lean, so no differential case changes. Deliberately no fuel was added to Lean — mirroring host policy in the formal model would make the specification depend on a machine property it does not describe.
  - **Depth** counts simultaneously active *dynamic algorithm invocations* — user calls, conditional calls (clause selection plus the selected branch body count as ONE invocation), callback invocations, and zero-argument property accesses. It is charged at those five chokepoints only, never per C# helper frame, and never for parenthesized/block nesting (which the parser recursion budget already bounds). An internal ceiling (`EvaluationLimits.MaxSupportedDepth` = 128, calibrated by the `eval-probe` depth probes) applies to EVERY entry point including the parameterless `Evaluator.Run(Expr)`; `RunOptions.EvaluationLimits.MaxDepth` can only request a lower limit. A machine-dependent stack-headroom backstop (`RuntimeHelpers.TryEnsureSufficientExecutionStack`) can only stop evaluation EARLIER than the deterministic limit, so it never changes an in-headroom result.
  - **Steps** are opt-in (no budget by default at any layer, so existing long-running programs are unaffected). One step is charged per dynamic invocation and per loop iteration. Optimizer independence is by construction rather than parallel accounting: a run with a configured step budget takes the generic loop / sequence-pipeline paths, so a configured budget can never mean one thing under an optimization and another without it. The step budget bounds WORK, not memory; the implemented collection and string limits below bound construction separately.
  - Budget state is run-scoped (`EvaluationBudget`, created once per top-level run, shared by reference through every copied `EvalCtx`, never static). Two runs sharing one `RunOptions`/`EvaluationLimits` instance — including concurrent runs — always start with fresh counters, and a zero-argument property cache entry never carries budget state.
  - **Collection materialization** is bounded by two further limits. `MaxCollectionItems` is an ALWAYS-ACTIVE hard ceiling (`EvaluationLimits.MaxSupportedCollectionItems` = 100,000, configurable downward only) on the immediate item slots of ONE sequence or exact list created by source evaluation; unlike the step budget it cannot be opt-in, because a single compact expression (`range(1, 10000000)`) asks for one enormous allocation before any step or depth unit is charged. `MaxMaterializedItems` is an opt-in cumulative per-run total for programs that repeatedly build individually legal collections. Both are calibrated from measured cost (~190–200 bytes of peak working set per item), deliberately far below what a development machine survives, because WASM and multi-tenant server embeddings have much smaller budgets.
  - The unit is **one immediate element position stored in a newly created persistent collection**: `[]` costs 0, `[x]` costs 1, `[[1,2]]` costs one outer slot plus the two the inner list already paid, and reusing an existing child value as an outer element costs only the new outer slot. Merely opening the spread view costs nothing; each real sequence recapture the evaluator constructs from that view is charged once. Sequence CAPTURE differs from exact-list construction by singleton/empty erasure — fewer than two slots materialize no sequence storage and cost nothing (`MakeCheckedSequenceCapture`), while `[x]` really stores one slot. Atom leaves are not charged; this is a collection-materialization budget, not an object-count budget.
  - Every reservation happens BEFORE allocation (`EvaluationBudget.TryReserveCollection`, using checked arithmetic so a rejected request leaves the cumulative counter untouched). Checked evaluator helpers cover ordinary, patterned, callback, reducer, deconstruction, and loop-step collected lists (`CollectSegment`); generic and optimized final loop state; output/sequence capture; list/builtin construction; and each persistent direct nested-spread recapture. `range` computes its cardinality from its bounds with a saturating conversion and never enumerates to find out; `atoms` — the one producer whose output can far exceed its input, since `[A, A]` doubles the atom count while adding two slots — bounds the TRAVERSAL itself (`Result.TryLanguageAtoms`) rather than counting first. The public engine's host-atom projection is bounded the same way (`Result.TryToHostAtoms`), so a successful evaluation is never followed by an unbounded flattening allocation.
  - Optimizer parity is exact but asymmetric by design: a fused pipeline that never materializes still enforces the same single-collection boundary (`EvaluationBudget.CheckCollectionSize`) yet consumes no cumulative budget, because charging an allocation that does not happen would be precisely the double charging fusion exists to avoid. If the pipeline is not fused after all, the generic path reserves for real, so one collection is never charged twice.
  - Resource errors do not accumulate call/property `WithContext` frames (`EvalError.IsResourceLimit`, honoured by both the evaluator's `WithCtx` and the sequence optimizer's): the limit is a property of the run, not of any one call on the chain, so the innermost span is preserved and the message stays a single line instead of one identical frame per active invocation.
  - **Language strings** are bounded by `MaxStringLength` (always-active ceiling `MaxSupportedStringLength` = 1,000,000 UTF-16 code units, configurable downward) and an opt-in cumulative `MaxMaterializedStringChars`, reserved before creation at the shared `Evaluator.MakeStringResult` construction point. This is defence in depth rather than the closure of a compact-source path: **KatLang has no string concatenation operator** (`"a" + "b"` is a `TypeMismatch`), so the only producers are source literals and `.string` numeric conversion (~30 units) and a source program cannot grow a string. The ceiling does bound hand-built ASTs reaching the public `Evaluator` API, and any future concatenating operation inherits it automatically. Loop plans store raw string literal text and call the same checked helper every time the planned expression executes, so default, explicitly configured, optimized, and generic runs agree while each logical evaluation still pays its UTF-16 units. String limits therefore do not disable loop optimization.
  - **Rendered output** is bounded by `MaxDisplayLength` (always-active ceiling `MaxSupportedDisplayLength` = 1,000,000 UTF-16 code units, configurable downward). This one *does* close a real compact-source path: display flattens a value recursively, so nesting a value inside itself (`L1 = [L0, L0]`) adds two item slots and no host atoms while DOUBLING the rendered length — a nine-line program can ask for gigabytes of text while every evaluation limit sees it as tiny. Rendering uses `BoundedDisplayWriter` with an ITERATIVE traversal: it checks before every append and never builds the forbidden output, replacing a recursive `Select(...).Join(...)` that materialized every child string before the parent knew its size (and recursed once per nesting level, unbounded for host-constructed `Result` trees).
  - Units are **UTF-16 code units** everywhere (matching `string.Length`, the source-span column model, and CLR storage): a BMP character is 1, a surrogate pair is 2, and separators/delimiters count. A top-level row separator is charged by its actual `Environment.NewLine.Length`, so the returned string is within the same strict numeric limit on LF and CRLF hosts even though the row at which overflow occurs may differ.
  - **Failure surfacing**: the effective display policy is carried immutably on every `RunResult` variant (via an internal common `DisplayOptions` property), so `ToDisplayString()` and `EvaluateToString()` never return more UTF-16 units than `MaxDisplayLength`. Over-limit rendering discards the partial writer: it returns the complete display-limit message when that fits, otherwise the complete `…` marker when one unit fits, otherwise `string.Empty`. It never appends a marker to partial output or diagnostics. The structured success value and diagnostic collections remain unchanged, and rendering failure never converts `Success` into `EvalFailure`. Manually constructed results use the default hard ceiling.
  - **Dotted receivers are evaluated at most once.** `A.F(B)` has receiver-first semantics (`F(A, B)`). The sequence-builtin dot path formerly evaluated the receiver to dispatch on it, reified that result into an AST literal (`CountedArgAlgorithm` → `ResultToExpr`), and evaluated the literal again; `range(1, 10).count` therefore charged 20 materialized item slots for one ten-item collection. Carrying the counted receiver in `ResolvedArgumentAlgorithm.PreparedValue` corrected that duplicate reconstruction. Call-shaped ordinary/dotted spellings now agree on charged work; a named zero-argument property receiver retains its established property-access invocation charge, which is independent of reconstruction. A follow-up made the now-unused reification itself LAZY: the receiver argument carries only the prepared counted value (`Algorithm: null`), and `ResolveArgumentAlgorithm` / `PrepareSequenceBuiltinSuffixArg` synthesize the legacy wrapper only if an algorithm-only consumer requests the channel. The dot receiver cannot reach such a slot: fixed sequence-builtin binding always consumes it as `items[0]`, the value-only `collection` parameter. Higher-order user receivers (`Double.Apply(7)`) remain on the lexical user-call path and retain their algorithm meaning. This follow-up is an **implementation-only optimization**: it changes unmodeled host traversal/allocation, not values, raw structure, emitted counts, errors, spans, callback order, failure order, or any evaluation-budget counter. Laziness is observed only by the passive run-scoped `EvaluationObservations.CountedArgumentReificationCount` test counter (no static state and no semantic use). Regression coverage: `DottedReceiverEvaluationTests` (generic/optimized paths, receiver kinds, callbacks and failures, resource counters, zero reification, negative control, and reachable callback-produced fallback paths).
    - **Representation note:** Lean's `ResolvedArgumentAlgorithm` deliberately has a mandatory `algorithm` field and therefore constructs the counted-value wrapper eagerly. C# has a nullable algorithm channel plus `PreparedValue`, so it may carry only the prepared counted value and construct the SAME zero-parameter algorithm if that channel is later requested. The avoided traversal and AST allocation are unmodeled host-side work: they consume no evaluation steps, materialized item slots, string units, or dynamic depth. The reification counter observes that implementation fact for tests only; it is not a budget or language-semantic channel.
  - **Patterned call arguments are evaluated exactly once.** The shared call assembler had one high-severity exception: after `BuildCallArgumentInputs` / `collectVariadicCallItems` evaluated a zero-parameter parenthesized block to obtain its ordinary counted/combined argument value, patterned binding called `TryGetExplicitSequenceValueItems` / `explicitSequenceValueItems?` and evaluated the same block again to recover its written slots. The value and pattern views could therefore come from different `Math.Random(...)` draws; a successful first evaluation could be replaced by a second-pass failure; and C# charged duplicate steps and collection/string materializations. The paired correction introduces `PreparedAlgorithmOutput` in C# and Lean: one left-to-right algorithm-output pass returns the counted combined value plus the explicit evaluated slot list, and patterned ordinary/dotted calls consume both products directly. The slot list is a non-semantic view (typed read-only) over the same evaluated `Result` values, never post-value decomposition (which would lose singleton and nested structure); in C# it is the evaluation-owned accumulator itself, so the shared algorithm-output path adds no per-evaluation wrapper allocation for callers that only take the counted projection. A multi-parameter/function-valued block still falls back lazily through the dual algorithm channel; arity and binding remain after full assembly; failures retain their first-evaluation order, span, and context. Intended observable differences are exactly one nondeterministic execution, no retry/second-pass failure, and one logical set of C# operational charges. Ordinary deterministic successful programs retain their prior value, sequence/list structure, emitted count, and pattern bindings. `Math.Random` itself is unchanged. Lean changes structurally with C# even though its pure deterministic evaluator exposes the same successful values; C# operational budgets remain host policy and are not added to Lean. Regression coverage: `PatternedCallSingleEvaluationTests`, `CallArgumentAssemblyTests`, `WrittenSlotReificationTests`, `DottedReceiverEvaluationTests`, and the `preparedAlgorithmOutput*` / `sequenceValueSingletonPatternKeepsMultiEmittingWrittenSlotWhole` Lean guards.
  - **Prepared builtin callback arguments are not reconstructed.** Collection callbacks already receive evaluated `CountedResult` values. Ordinary callback value positions pass those values through `ResolvedArgumentAlgorithm.PreparedValue`, preserving emitted count while intentionally carrying no synthetic algorithm representation; `BuildCallableCallItems` consumes the prepared value directly, so there is no `Result` → `Expr` → evaluator round trip. A legacy counted-value algorithm view is reconstructed lazily only when an algorithm-only builtin position genuinely requests one. User wrappers and direct builtin callbacks therefore agree on result, error, item/string materialization, and cumulative boundaries without a cross-call cache or changed evaluation order. Regression coverage: `OperationalMetamorphicTests`.
  - **Three observation classes, and what may be compared with what.** Testing distinguishes them explicitly, because conflating them either weakens the Lean differential or wrongly demands that Lean mirror C# implementation strategy.
    - **Language-semantic** — result kind, atom/string value, sequence/list structure, emitted count, semantic error kind and stable payload, binding/branch/visibility outcome, spread-capture-collect behaviour. These are what the Lean differential corpus compares, and they must match Lean exactly.
    - **Host-policy** — every resource-limit error (depth, steps, stack backstop, per-collection size, cumulative materialized collection-item slots, per-string size, cumulative materialized string UTF-16 units, rendered-output length), optimizer selection, cache hit counts, CLR allocation, peak working set. These are C#-only and are NEVER required to match Lean; Lean models an unbounded evaluator.
    - **Operational** — evaluation steps, materialized item slots, materialized string units, peak dynamic depth, cache misses, frontend distinct-node counts. These may be compared BETWEEN C# executions, never against Lean. No exact operation counters were added to Lean to mirror C# internals.
  - The relation must match the pair. Equality is used only where the two executions are semantically expected to perform equivalent work — `count(range(1, 10))` vs `range(1, 10).count`, because the dotted form IS the ordinary receiver-first call. Where an implementation is permitted to do less, the relation is an inequality: optimized ≤ generic, cached ≤ rebuilt. Requiring equality there would forbid fusion. Harness: `OperationalMetamorphicTests`, reading the run's own `EvaluationBudget` through `Evaluator.RunCountedObserved` — run-scoped, no static counters, and observing it cannot change optimizer eligibility or re-evaluate anything.
  - **Operational counters are compared only when both executions complete.** When either side stops at a structured resource limit, semantic outcome, resource-limit kind, and structured payload remain comparable, but partial work counters are not: an aborted run's counters are the prefix recorded at the abort point, and two equivalent forms may legitimately have done different preparatory work before reaching the same limit (`reduce(R, contains, [1, 2])` materializes its initial accumulator before forcing `R`, while `R.reduce(contains, [1, 2])` prepares the receiver first and stops earlier). Ordinary, non-resource semantic failures are NOT exempt — their counters are compared exactly like a successful run's. Which side of that gate a case landed on is recorded in its fingerprint, so skipped work comparison is visible rather than silent. Coverage: `MetamorphicComparator.WorkIsComparable`, pinned by `MetamorphicPhase2FamilyTests.OperationalCounters_AreComparedUnlessAResourceLimitAbortedARun`.
  - **Optimizer eligibility is part of the execution policy, not just the optimizer flag.** `Evaluator.CreateRootCtx` computes `loopOptimize = !budget.HasStepLimit` and `sequenceOptimize = loopOptimize && !budget.HasConfiguredStringLimit`, and `EvaluationBudget` sets `HasConfiguredStringLimit` when either string limit was configured, so configuring any string or step budget — however generous — switches the sequence-pipeline optimizer off for the whole run. A test layer that keys a fusion-dependent relation on the optimizer flag alone therefore claims the weaker relation where the stronger one holds. The metamorphic harness owns that rule in one place (`MetamorphicLimitPolicy.SequencePipelineFusionCanApply`) and derives the chain relation from it; this is harness policy only and changes no production behaviour.

  - **Phase 2 extends the same layer to four further trusted families** (`MetamorphicPhase2FamilyTests`), all still testing-only: dotted collection builtins over every receiver value kind, user-defined extension calls, bounded dotted chains, and direct builtin callbacks against user wrappers. Two points are worth recording because they are LANGUAGE facts the harness had to be taught rather than defects. First, a wrapper's callback projection is not interchangeable with ordinary call binding: a collecting parameter COLLECTS the supplied slot into a list (`[[1, 2], [3]].map(count)` is `[2, 1]`, but a `MmWrap(*xs) = count(xs)` wrapper gives `[1, 1]`), and a flat multi-parameter callee opens a lone sequence element into rows, so both are rejected by explicit precondition instead of compared. Second, the dotted spelling of a CHAIN is the fusion-eligible one while the nested ordinary form is not, so where fusion is EFFECTIVELY eligible the relation is directional (the dotted form may charge less, never more — measured: 5 of 144 chain/receiver pairs charge less, none charge more) and cumulative-item limit modes are rejected there, because a fused pipeline is documented not to consume that budget while still enforcing the same per-collection ceiling; wherever fusion is ineligible — the optimizer-off policy and any configured string budget alike — the exact relation holds on all 144. The readiness probes additionally require a deterministic stratified sample to REACH every family, relation, optimizer path, cache profile, entry-point pair, budget law, resource dimension, run plan, and execution order. One harness gap was found and fixed by that requirement: the stratified enumerator fixed the offset byte in its exhaustive stratum, and because that byte is the signed BOUNDARY OFFSET rather than a limit knob under `FamilyDerived` limits, the exact boundary-failure relation (`SameResourceBoundary`) was unreachable from the sample — the campaign reached it, but no deterministic test could demonstrate it. The enumerator now crosses the offset wherever the stratum's own limit mode reads it, which is enumeration-only: no payload meaning, family identity, relation, or seed changed, and every tracked seed and retained corpus replays byte-identically. `scripts/fuzz-parser.ps1` also gained an optional `-FuzzerSeed` forwarded through `WSLENV` as `-Mode` already is, so a campaign is reproducible and a confirmation campaign is an independent sample rather than a second draw from the same stream. No production code and no Lean artifact were touched by Phase 4.
  - **Phase 5 adds a separate UTF-16 source-text target** (`KATLANG_FUZZ_MODE=utf16`, `fuzz/KatLang.ParserFuzz/Utf16`, covered by `Utf16FuzzHarnessTests`, `Utf16ReadinessTests`, `Utf16LexerContractTests`), also testing-only: no `src/KatLang` behaviour, public API, or Lean artifact is involved. Host UTF-16 handling and lexer/parser rejection policy are not modelled in Lean, which has no notion of surface syntax, so no Lean update applies. It fuzzes source text rather than programs — lexer, parser, recovery, front end, diagnostics, spans and line/column reporting — over isolated surrogates, combining marks, mixed line endings, zero-width format characters, NUL, and Unicode separators. The payload is not source bytes: an isolated surrogate has NO UTF-8 form, so the fuzzer instead selects a trusted template plus a named run of code units (or, in two bounded raw modes, builds them from the payload tail), and seeds are stored as hex payloads because a seed stored as source text would be silently rewritten to U+FFFD by git, an editor, or `File.ReadAllText`. Nothing normalizes source text to NFC/NFD/NFKC/NFKD and no ill-formed surrogate is replaced before the lexer sees it. The layer reuses `FuzzInvariants`, `FrontEndInvariants` and the shared `SourceSpanValidator` rather than restating their rules, and adds the code-unit-model invariants: the token stream covers the source with strictly increasing offsets ending at the source length (forward progress, structurally rather than by wall clock), no token slice spans a line break, every token's recorded line/column equals the one recomputed from its offset by the one shared helper, token text is the exact source slice, and diagnostics are bounded both linearly in source length and per position. `Utf16LexerContractTests` pins the coordinate contract that all of this rests on and that nothing else records: code-unit indexing, 1-based lines and columns with INCLUSIVE end positions, `'\n'` as the only line break, `'\r'` transparent to both line and column (a lone CR is therefore not a line break, though it does end a string literal and a comment), Unicode separators such as U+2028/U+2029/U+0085 as whitespace that never starts a line, zero-width format characters (U+200B/U+200D/U+FEFF) as bad tokens rather than trivia, `char.IsLetter`/`char.IsDigit` applied PER CODE UNIT so a surrogate pair never forms an identifier and a non-ASCII decimal digit starts a number token that `decimal.TryParse` then rejects, and string literals with no escape sequences whose code units survive unchanged to the evaluated value. One harness defect was found by the smoke campaign and fixed: the per-position diagnostic bound was justified as "the parser makes forward progress" and set to 16 from templates that never nest, but diagnostics stack at one position when nested constructs are left open — `[[[[` reports once per bracket at end of file while consuming every code unit — so the bound was measuring nesting, not stalling; it is now the parser's own `MaxNestingDepth`, with forward progress established separately by the token invariants. The only `src/KatLang` change in the phase is this documentation entry.
  - **Phase 7 adds a separate editor-tooling semantic target** (`KATLANG_FUZZ_MODE=editor`, `fuzz/KatLang.ParserFuzz/Editor`, covered by `EditorFuzzHarnessTests` and `EditorReadinessTests`), also testing-only: no `src/KatLang` behaviour, public API, or Lean artifact is involved. It fuzzes the editor-facing semantic model in `src/KatLang/Semantics/` (`SemanticModelBuilder` / `SemanticModel`) — classification, position resolution (hover), symbol lookup, go-to-definition, document symbols, and signature metadata — over arbitrary and malformed source with difficult UTF-16 code units, cursor placements, and bounded edits. Lean models neither surface syntax nor editor tooling (cursors, spans, classification, completion ordering, recovery), so no Lean update applies; the oracle is layered over the real lexer, parser, front end, and `BuiltinRegistry` metadata instead. The invariants are that tooling never throws unexpectedly (a structured "no result" and the documented unresolved-`load` DECLINE are valid outcomes — the harness pre-checks `LoadElaborationGuard.TryFindFirstUnresolvedLoad` and declines exactly as a correct editor caller must, because `SemanticModelBuilder.Build` throws on an unresolved load by contract), every source-backed span is valid under the shared `SourceSpanValidator` code-unit model, every occurrence's source slice equals its reported name, a resolution's target is a same-named declaration the model lists, builtins are non-source and match the registry's fixed-arity metadata, no synthetic `$`-name or comment/string-interior identifier leaks, ordinary and dotted spellings of one callable resolve identically, and results are deterministic and isolated across requests and small edits (A/A, A/B/A, concurrent, and no stale-source leak). The payload is a frozen 13-byte template selector reusing the Phase 5 UTF-16 code-unit tables; seeds are hex payloads for the same reason the UTF-16 ones are. The reused `SemanticModel` invariants align with `SemanticModelTests`; the editor target adds no semantic rule of its own. The only `src/KatLang` change in the phase is this documentation entry.
  - **Not claimed**: this is not complete memory safety. Source-text length, per-module download size after the downloader returns, aggregate accepted module source, distinct accepted-module count, and import depth are bounded by `SourceProcessingLimits` (see the source/module input-size note above). Still out of scope here: CLR overhead variation, host-constructed `Result` objects, live-memory (as opposed to created-slot) accounting, process-wide memory shared between runs, downloader-side buffering before a returned string can be measured, network fetch attempts (failed or policy-rejected fetches are uncharged and the number of load sites is bounded only by source length), and the lower-level caller-sized `Lexer.Tokenize` API. The cumulative evaluator counter measures slots CREATED and is deliberately not a live-memory measure.

- **Output formatting is host-side plain-text presentation, not KatLang semantics** (`KatLang.Formatting`: `OutputFormatter`, `OutputFormatters` with the stable ids `exact`/`readable`/`concise`, `OutputFormattingOptions`, `StringDelimiterMode`, `BoundedOutputWriter`, plus the public root-output view `RunResult.Success.OutputRows`). Formatters render ALREADY EVALUATED results only: they never re-parse or re-evaluate, never modify/spread/flatten/collect/reorder/merge/split values, and the parser and evaluator have no knowledge of formatter modes or options. `exact` and `RunResult.ToDisplayString` share the formatter-neutral `KatLang.Rendering.ValueTextRenderer` with the canonical raw-string strategy, so they are byte-identical without making `RunResult` depend on formatting policy; `readable`/`concise` change whitespace/layout and (optionally) string QUOTING only — string content is always verbatim, and an August 2026 audit confirmed no display path ever specially handled `_` (the only underscore consumption is the lexer's number-literal digit-separator rule), a contract now pinned by `Formatting/UnderscorePreservationTests`. All formatter rendering follows the established robustness rules: iterative indexed-continuation-frame traversal (never recursion, never sibling-granular stacks), width-CAPPED inline measurement (`CappedWidthSink`) so DAG-shared values cost at most O(width) per emitted node, and the all-or-nothing `MaxDisplayLength` contract through the same `BoundedDisplayWriter`/`Finish` path (a per-call option can only LOWER the run's limit). The delimiter policy is quoting-only by contract: `concise` structural elision is decided per concrete value through one shared raw-token safety predicate (`DelimitedStringTextPolicy.IsTokenSafe`, used identically by measurement and emission), so `StringDelimiterMode.Never` does not globally disable concise layout — ambiguous raw strings retain their CONTAINING sequence's punctuation while safe raw labels still elide. The safety predicate is conservative about invisible text: Unicode Format-category characters (bidi controls, zero-width spaces, BOM/ZWNBSP, soft hyphen, word joiner) and unpaired surrogates are never safe undelimited tokens and always need delimiters (well-formed surrogate pairs such as emoji are ordinary content), and numeric-looking detection follows the lexer's digit-separator grammar (`1_000` reads as a number) while non-ASCII digits do not — pinned by `Formatting/UnicodeTokenSafetyTests`. Layout selection uses width AND structural complexity (`StructuredLayoutRenderer.RequiresStructuredLayout`): a sequence with two or more structured children lays out multiline even when its flat text fits the preferred width, a safe nested multi-pair string/value child renders as pair lines (readable) or an indented pair block (concise) rather than a flat join, and the zero-root-spacing root-block gate admits a paren-hidden block only when a nested pair block visibly anchors it — all presentation-only line grouping over the evaluated value, never dictionary/record semantics, with spread-discarded structure never reconstructed. The separate `KatLang.Formatting.PublicApi.Tests` assembly proves extension without `InternalsVisibleTo`. Lean models no rendering, so no Lean update applies.

- Open declarations inside conditional clause bodies are **BRANCH-OWNED**. An `open` written in a clause body stays on that branch body (`Conditional.Branches[i].Body.Opens`), which is the location parameter detection, implicit-argument resolution, exposure, and evaluator lookup actually resolve through. `Algorithm.ElaborateClauseGroup` therefore constructs the family with `Conditional.Opens = []`. It previously also copied `clauses[0].Body.Opens` onto the conditional, leaving clause 0's open expressions reachable by two paths; that copy was redundant (removing it changes no observable behaviour — verified by the valid-program open matrix and the full suite) but harmful, because an open target may contain a nested algorithm (notably under malformed recovery such as an unclosed `(open(...`), so the duplicate ownership let `ImplicitArgumentResolver` and `PropertyExposureResolver` rebuild the same subtree once per path and unfold a linear-size reference DAG into an exponential (2^depth) tree. Parser-level/front-end representation only: the AST inductive, clause classification, lookup order, and evaluation semantics are unchanged, and Lean does not model surface clause-family elaboration, so no Lean update applies. Regression coverage: `ClauseFamilyOpenOwnershipTests`.

## Process

1. Identify the semantic area you are changing.
2. Find the matching row in this manifest.
3. If Lean update is required, update Lean first or in the same change, then update C# and tests.
4. If the change is C# implementation/tooling only, C# tests are sufficient.
5. If the change is optimization-only, add or preserve equivalence tests against the generic path.
6. If unsure, stop and ask before changing observable semantics.
