### The two-tier numeric model

The core NUMERIC model is TWO-TIER, and the tiers route differently (M12, August 2026; the manifest's "Core numeric semantics" row is the routing rule, this note the inventory). Lean models numbers with unbounded `Int` while the C# runtime computes end-to-end in IEEE 754 `System.Numerics.Decimal128` (34 significant decimal digits, exponent range about ±6144) — see the numeric-model header comment in `lean/KatLang.lean`. The SHARED tier is a set of laws over the COMMON EXACT integer subdomain, not every program whose source happens to contain integer literals: exact in-range integer arithmetic and unary negation, comparison on common integer values and logic on Boolean values, truncation-toward-zero `div`/`mod` behavior (`Int.tdiv`/`Int.tmod` against `Decimal128Numerics.IntegerDivide`/`%` — `-7 div 2 = -3`, `-7 mod 2 = -1`, and since G-3 EXACT wherever the truncated quotient is representable: `8999999999999999999999999999999999 div 3 = 2999999999999999999999999999999999` with the identity `x == y * (x div y) + (x mod y)`), the zero-divisor error rule where both models have a zero-valued divisor, `0 ^ negative` as an explicit error at its integer instance (the runtime rule rejects EVERY exponent below zero, integral or not — the fractional side is Decimal128-only, below), non-negative integer powers and the exact `1`/`-1`-base reciprocals when the Decimal128 result stays exact and finite, structural equality on common integer values, and Boolean-only predicate consumption (every numeric condition is rejected). Those laws change Lean and C# together, with Lean-comparable LanguageSpec coverage (`integer-division-truncates`, `integer-division-exact-quotient`, `division-by-zero`, `power-unary-precedence`, `first-program`). Precision/range remains decisive even for integral operands: large integral arithmetic may round or overflow where Lean remains exact, and a truncated `div` quotient that needs more than 34 significant digits is rounded TOWARD ZERO to 34 digits (G-3; `IntegerDivisionContractTests`) where Lean returns the exact integer — `div` never truncates a pre-rounded quotient any more. The DECIMAL128-ONLY tier has NO Lean witness and must never be given a fake one: 34-digit precision/range and rounding (including integral inputs), fractional literals/values, the Decimal128-selected arithmetic quantum exposed without value-changing canonicalization (`0.5 + 0.5` displays `1.0`), non-exact `/` quotients and the decimal `avg` mean (the Int core truncates both — its documented model limitation, never the runtime contract), NaN and the equality-vs-ordering split (structural `==`/`!=`/`contains`/`distinct` treat NaN as ONE value via `Decimal128.Equals` atom equality in `Result.ValueComparer`; the relational operators are IEEE, so every comparison with NaN is false; `order`/`orderDesc` instead use `Decimal128.CompareTo`'s TOTAL order, NaN before every other value ascending; `min`/`max` propagate NaN; NaN has no Boolean truth value), ±Infinity with overflow producing a signed infinity and subsequent IEEE propagation (`Infinity - Infinity` is NaN, an infinity is never a zero-valued divisor), signed zero representation/visibility (displays `-0`, equals `0` structurally and relationally, with no Boolean truth value, and is the smaller zero only for the `min`/`max` tie, decided by sign in every element order), gradual underflow/subnormals/eventual zero, and fractional/negative powers beyond the modeled cases (`2 ^ -2 = 0.25`, where Lean's `negativeIntPow` raises its explicit fractional-result error; a zero base with a FRACTIONAL negative exponent — `0 ^ -0.5`, `Math.Pow(0, -2.5)` — is the same `zero cannot be raised to a negative exponent` error as `0 ^ -1`, never IEEE `Infinity`: G-6, September 2026, C#-only `pow-zero-base-negative-exponent`) together with integer powers whose exact value does not fit 34 digits (rounded ONCE from the exact power, certified: `Decimal128Numerics.TryIntegerPower`, `Decimal128IntegerPowerReviewTests`). The zero-VALUED-divisor rule remains shared where applicable; C# additionally applies it to Decimal128-only representations such as `-0` and an underflowed-to-zero value, so `1 / -0` is the ordinary `divByZero` error rather than IEEE `-Infinity` without implying that Lean represents signed zero. ### The front-end elaboration boundary

`Parser.Parse` and `Parser.ParseAsync` return the complete elaboration. `KatLangEngine` uses the same pipeline, and `SemanticModelBuilder` consumes its `ParseResult`. Hosts configure module loading through the async entries with `RunOptions.DownloadCode` and `AllowedHosts`. `Evaluator.Run` and its host-AST counterparts evaluate the supplied tree after preflight and rely on the host for its exposure metadata.

Keep `Parser.ParseSyntax`, `ModuleLoader`, `ParameterDetector`, `ImplicitArgumentResolver`, `PropertyExposureResolver`, `PropertyDependencyGraphBuilder` and `FrontEndPipeline` internal. A partially processed tree can still contain raw name reads or a default `Exported` exposure. A future public elaborator for host ASTs would need one complete operation with the same result as `FrontEndPipeline.FinalizeElaboration` and equivalence coverage against `Parser.Parse`. Friend tests, fuzzing and benchmarks can exercise the internal stages. `FrontEndElaborationBoundaryTests` and the non-friend `PublicElaborationSurfaceTests` pin the boundary.

### Plain/counted evaluator ownership and its deliberate exceptions

Where the two evaluations agree on value, the counted operation owns the semantics. Lean's `eval` projects `evalCounted`, whose exhaustive dispatch handles every `Expr`. The plain call, builtin, callback, capture, property and algorithm-output operations are value projections in the fuel-indexed core. `lookupLexical` projects the algorithm of `lookupLexicalProperty`.

In C#, `Evaluator.ProjectCountedValue` discards the emitted count for ordinary calls and dot calls, parameter and name reads, expression spines, callback and output adapters, and the program root. `LookupLexicalResolvedAlgorithm` projects the binding from `LookupLexical`. One `EvalWiredRootProgramCounted` per engine owns the root error contract. Accesses with the same shape share their zero-argument property key (`ZeroArgPropertyCacheKey.FromExecution`).

Three distinctions matter when changing a dispatch.

1. `Eval`, `EvalCounted` and its async twin share `EvalLeafUncharged` for `Num`, `StringLiteral`, `BoolLiteral` and the defensive `Grace` arm. The counted dispatch wraps the value with its count. A native call can read arguments or suspend and has a dedicated async arm.
2. `EvalAlgOutputSlots` and the explicit sequence-value slot walks return item lists. Their result contract is the slot supply.
3. `LookupLexicalDirect` and Lean's `lookupLexicalDirect` perform opens-free lookup for open-target resolution.

Lean's CoreTests and `SemanticExplorerHarness` check plain/counted parity. Exhaustive dispatch and `AsyncExpressionDispatchTests` cover the C# variant and suspension boundaries.

### Host-API defensive branches

**Some evaluator branches are host-API defense, not language semantics** (August 2026, Track 12). `Expr.Grace` reaching its explicit illegal-in-eval leaf arm, a non-open-form or `Expr.SequenceConstruct` in an algorithm's open targets, and the runtime checks for duplicate properties and for a parameterized algorithm with no output cannot arise from any legal source program — the parser or an elaboration pass removes the shape first. They are revalidated because `Evaluator.Run`/`RunCounted` accept prebuilt ASTs from hosts and internal stages. Pin these at that boundary (`EvaluatorDefensiveBranchTests`), NOT with a LanguageSpec or Lean case, which would assert behavior the language cannot express. Note that `ResolveAllOpens`'s up-front form-validation loop duplicates the per-target rejection in `ResolveAlgForOpen`: the only observable difference is ORDERING (all shapes validated before any target resolves), so a test asserting merely "a bad form is rejected" cannot detect the loop's removal.

## Grace + DotCall semantic laws (normative)

These laws pin the final Grace + DotCall architecture. They are stated once, here, because collapsing them into one rule (ordering inferred from fallback-call assembly, extension-specific resolution modes) is a known drift direction; the separations below are what prevent it. The manifest row "Dot member/fallback binding and Grace composition" carries the Lean/C# ownership mapping; this section is the normative statement.

### 1. Grace is frontend-only

The law: `Expr.Grace(Inner, Weight)` is a front-end parameter-ordering annotation on exactly one bare name occurrence, and nothing downstream of parameter elaboration ever observes it.

- `Expr.Grace` may exist only in the raw/frontend AST; source-valid Grace wraps a single `Expr.Resolve` occurrence.
- Prefix `~x` contributes weight −1 per marker: the inferred parameter moves one position EARLIER.
- Postfix `x~` contributes weight +1 per marker: the inferred parameter moves one position LATER.
- Repeated markers and repeated graced occurrences of the same name in one owner SUM (`~~x` is −2; `~x~` nets 0 but retains a raw Grace node until binding validation; a redundant group is erased, so `(~x~)` is the very node `~x~` is). Weights are exact unbounded integers (`System.Numerics.BigInteger`). The general arithmetic is the X-49 movement law (decided 2026-10-08; `GraceMovement`) over the owner's OWN inferred list: every name with a positive weight takes one turn, from the last-occurring to the first-occurring, then every name with a negative weight, from the first-occurring to the last-occurring; a turn exchanges the name with its neighbour one unit at a time until its remaining weight is zero, it reaches the end of the list, or the neighbour moves the same way with at least as much REMAINING weight (strict comparison of current remaining weights); a passed name keeps its weight, and unused weight stays and keeps blocking — saturation, never an error. So `K = a * 100 + b~ * 10 + ~~c` is `K(c, a, b)`, as without `b~`, and `K = a~ * 100 + b * 10 + ~c` is `K(b, c, a)` (the full statement: `ownership-and-lookup.md` § Grace; pinned by `GraceMovementLawTests` and `GraceOwnershipSemanticsTests.X49Witness_FollowsFrontFirstMovement`).
- Grace applies only to a bare name/parameter occurrence, never to a compound expression (§8).
- Grace is OWNER-LOCAL and requires an OWN inferred parameter (F10; Q-16 G-O, decided 2026-10-07): a marker belongs to the innermost algorithm owner — the root, a property body, a brace block in any position, a clause-branch body — whose written rows (`AstHelpers.WrittenRows`: output rows and hoisted deconstruction right-hand sides) contain the occurrence, and it is ELIGIBLE exactly when that occurrence becomes one of the owner's OWN inferred parameters — the one place its weight is consumed — whether or not the weight then moves it (Q-16(1) E: a single own parameter, a name at its boundary, excess weight, a tie, a cancelled weight and the own/lifted boundary are saturation, never an error). Every other occurrence has no inferred parameter to weight and is the front-end error `DiagnosticCode.InvalidGraceMarker` ("Grace cannot reorder 'x' because …"): a FIXED binding — an explicit parameter or clause binder, a captured (enclosing) parameter, a visible property, a builtin, an opened name, a dot member that always resolves structurally (or any `.string` edge, which selects a declared member or the intrinsic, Q-17 S-C) — and any occurrence on a CLOSED level: under an explicit parameter list (`GraceEffectPolicy.ClosedExplicitList`) and on a clause branch's own rows, deconstruction right-hand sides included (`GraceEffectPolicy.ClosedBranch`; constitution PV-49). A branch is closed at its own level only (Q-16(2) O): an algorithm nested in it is an ordinary owner (`GraceEffectPolicy.ImplicitSignature`) in every spelling. The report is issued by `ParameterDetector.ReportIneffectiveGrace` from the REWRITE pass (`RewriteParamsCore`, Grace and DotCall-member arms): once per occurrence per region through a diagnostic visit set beside the rewrite memo — the ONE authority; the parser keeps Grace syntax only (its former lexical branch-body scan and the NotReported policy that relied on it are deleted). Automatic parameter forwarding never changes what a written name denotes (Q-04), so the detector's verdict is final and no provenance is stored on the executable AST (the former run-local GraceOrigins, which let ownership completion revalidate a marker after lifting, is deleted). The reason is derived from the same owner walk (`ElaboratedScopeLookup.SelectOwnedDeclaration`) the editor resolves with, so the report and `SemanticModel` classification cannot disagree, and it never names the family. C#-only by design: Lean receives the elaborated parameter list and never sees Grace. Pinned by `GraceOwnershipSemanticsTests`, `GraceEffectivenessTests`, `ConditionalBranchDeconstructionGraceTests` and the `grace-on-bound-name-rejected`, `grace-under-explicit-list-rejected`, `grace-in-branch-deconstruction-rejected`, `grace-saturation-is-valid`, `grace-in-branch-nested-block-belongs-to-the-block` and `grace-on-branch-binder-in-nested-block-rejected` `LanguageSpecCorpus` cases.
- Grace changes ONLY inferred parameter ordering (`Algorithm.User.Params`); it never changes resolution, selection, evaluation, or output.
- Grace MUST be consumed during parameter elaboration: `ParameterDetector` collects the weights and strips the wrapper, `DotCallElaborationInvariant` rejects any survivor, and an `Expr.Grace` reaching the evaluator is host-API defense only (§ Host-API defensive branches above), never a language state.
- No `Expr.Grace` node and no Grace provenance flag of any kind survives into the executable AST.

Lifecycle:

```text
source
  ↓
raw AST (Parser.ParseSyntax) — may contain Expr.Grace
  ↓
ParameterDetector (CollectFreeParams) — free-name occurrences in semantic source order; Grace weights summed exactly per name
  ↓
GraceMovement.Apply — the X-49 movement law over the OWN list; establishes Algorithm.User.Params
  ↓
Grace stripped (occurrences rewritten to ordinary Param/Resolve; DotCallElaborationInvariant rejects survivors)
  ↓
executable AST
  ↓
Evaluator / Optimizer / Lean (Expr.dotMember) — no Grace, no Grace provenance
```

### 2. The ordinary DotCall law — the only runtime law

```text
R.F(args...)

1. resolve R once (`resolveDotReceiver` / `ResolveDotReceiver`): an
   argumentless dot edge X.M used as R — a `.string` edge included — is
   NAVIGATED — when X (resolved the same way) structurally declares M (any
   visibility, any spelling), R IS that member; a declared M inaccessible from
   the site (K1-08: a local-only member outside its owner's activation) or a
   conditional-branch M is that edge's structural error; otherwise R is the
   ordinary dot RESULT (a value);
2. if the resolved receiver structurally owns member F — whatever its
   spelling, `string` included — use it (accessibility is checked after
   selection; a member declared only in clause branches is
   `LocalOnlyProperty`);
3. on a miss, string selects the number-to-text intrinsic. Invoke, Arguments
   and Algorithm select their respective call-reference intrinsics. Each
   intrinsic applies its own receiver and argument contract;
4. otherwise resolve the stored lexical fallback F, and
   invoke it as F(R, args...) — DOT-CALL PASSES A VALUE: the
   ORIGINAL receiver expression is the ordinary leading argument slot of the
   written call, assembled and bound by the ONE call funnel
   (`prepareLexicalDotCallArgs` / `BuildLexicalReceiverCallArgs` →
   `evalResolvedCallCounted` / `EvalResolvedCallCounted`), so a collecting
   parameter collects it as one item and only the spread marker (`R*.F`, the
   written spread slot) opens it (`sequences-lists-and-calls.md` § The
   dot-call receiver).
```

The invariant: this is the ONLY runtime DotCall law, and it holds at EVERY level of a chain (`Lib.Sub.Q` reads `Sub`'s own `Q` before any lexical `Q`; `3.A.B` is `B(A(3))`). There is no runtime "extension-dot" mode, no resolution-mode bit, and no second dispatch path for any spelling. Intrinsic selection is one arm of this law, and a dotted builtin call is nothing but the written builtin call reached through step 4 (there is no dotted sequence-builtin view or path). The steps are decided from ONE property lookup (Q-17 S-C, October 5 2026; formerly the intrinsic was tested before the member, so a declared `string` member was unreachable through dot syntax). Step 1 probes the receiver's structure. A runtime projection on that route can demand its retained receiver. Since Model C a SUPPLIED dot expression is projected the same identity-only way (NEED-06; Lean `projectNeedStructuralMember`, C# `ProjectDotPathCallable`): an argumentless structural path yields its member's own callable (aliases normalized). On an intrinsic miss an argumentless `R.Algorithm` projects the reference's callee, and every other computed dot expression has no callable — and since Q-18 C-B3 (October 5 2026) the CALLEE position reads the SAME projection (Lean `resolveCalleeAlg`, C# `ResolveCallee`, also the sequence optimizer's recognition), so a dot expression has ONE callable identity everywhere: `(R.M)(args)` is `R.M(args)` for a structural member, a computed dot callee is `NotAnAlgorithm`, and `R.M(a)()` no longer parses. `resolveAlg`'s zero-parameter dot wrapper (`ResolveDotCallAlgorithm`) survives only as the internal carrier of a dot RESULT used as a receiver (the former DOT-09 callee identity is retired).

### 3. Four independent semantic questions

Four questions, four owners. They must not be collapsed into one rule.

1. **Fallback participation** — "Can lexical fallback be needed?" Owned by the shared classification `AstHelpers.GetLexicalFallbackSelection` (`LexicalFallbackSelection.Never / Conditional / Always`), the projection — through `LexicalFallbackSelectionOf`, which gives each intrinsic miss `Never` — of the edge's structural-MISS verdict (`GetStructuralMissSelection`) that the detector computes with its scope-aware receiver classification and stamps on the edge (`Expr.DotCall.ElaboratedMissSelection`, read back through `EffectiveMissSelection`). Implicit-signature construction includes the member's fallback occurrence when selection MAY happen (`Conditional` or `Always`); exposure/dependency charging also uses MAY. Closed-list and branch-body checking uses the separate MUST projection (`Always` only; Q-75 F-A, October 5 2026 — formerly closed lists took no fallback contribution at all): `Get(obj) = 5.size` is the same `UndeclaredIdentifier` as `Get(obj) = size(5)`, at the member token, while `Get(obj) = obj.size` stays a runtime question.
2. **Source occurrence ordering** — "Where does the participating free-name occurrence appear in the semantic source traversal?" For a DotCall the traversal is: receiver occurrences, then the participating member/fallback occurrence, then written argument occurrences. Implicit parameter order follows first semantic source occurrence (`ParameterDetector.CollectFreeParams`). A spread receiver or a written marked call lowered to an extension call follows the source traversal of that call, as specified in the declaration-level output spreading row.
3. **Grace reordering** — "How does Grace modify the already-established inferred parameter order?" By the ONE ordinary prefix/postfix weight mechanism of §1, identically in every syntactic context. No construct gets its own permutation rule.
4. **Runtime dispatch** — "At execution time, does structural lookup win or is lexical fallback invoked?" Owned by `Evaluator` alone, decided per evaluation, independent of inferred parameter order and of Grace.

### 4. Source occurrence order is not fallback invocation order

Do not infer implicit parameter order from runtime lexical-fallback invocation order.

```text
a.t    has semantic source occurrence order (a, t)
```

even though the selected fallback executes conceptually as `t(a)`. Therefore:

```text
source occurrence order != fallback invocation order
```

This is a permanent architectural law, and its violation is a known regression class: question 2 of §3 is answered by the source traversal, question 4 by the runtime, and neither answers the other.

### 5. Grace + DotCall composition

There is no semantic concept of an "extension property call with Grace". The graced dot spellings compose from ordinary Grace (§1) and the ordinary DotCall (§2), and their parameter order falls out of §3. Informal names such as "extension call" in tests, fuzz families, and the patents refer to the dotted SPELLING, never to a separate semantic category.

`a.t` — base occurrence order `(a, t)`, inferred params `(a, t)`. Raw conceptual AST (`Args = null` is property-style access; `Args` omitted below):

```text
DotCall(
    Target = Resolve("a"),
    Name = "t",
    Args = null,
    LexicalFallback = Resolve("t"))
```

`a~.t` — postfix Grace on `a`, then ordinary DotCall:

```text
DotCall(
    Target = Grace(Resolve("a"), +1),
    Name = "t",
    LexicalFallback = Resolve("t"))
```

Base `(a, t)` becomes `(t, a)`: postfix Grace moves `a` one position later.

`a.~t` — ordinary DotCall with prefix Grace on the fallback/name occurrence `t`:

```text
DotCall(
    Target = Resolve("a"),
    Name = "t",
    LexicalFallback = Grace(Resolve("t"), -1))
```

Base `(a, t)` becomes `(t, a)`: prefix Grace moves `t` one position earlier.

### 6. Same executable body after elaboration

The invariant: after parameter elaboration, valid `a.t`, `a~.t`, and `a.~t` in the same lexical environment have the SAME ordinary executable DotCall body:

```text
DotCall(
    Target = Param("a"),
    Name = "t",
    LexicalFallback = Param("t"))
```

Only the enclosing `Algorithm.User.Params` may differ. Consequences:

- Grace does not bypass structural lookup.
- Grace does not force lexical fallback.
- Grace does not lower a DotCall to a direct `Call`.
- Grace does not alter `.string`.
- Grace does not alter dotted builtin-call semantics (`S~.count` is the ordinary `count(S)` reached through the dot edge).
- Grace does not alter optimizer or runtime dispatch.
- Lean needs no Grace or extension runtime form: it receives `Expr.dotMember` with the elaborated fallback and the finished parameter list.

### 7. Constitutional examples

Semantic laws, not implementation tests (pinned by `GraceEligibilityTests`, `GraceDotCompositionTests`, and the LanguageSpec `grace-dot-*` cases):

```katlang
K = a.t
K(7, {x+1})
# 8
# inferred params: (a,t)
```

```katlang
K = a~.t
K({x+1}, 7)
# 8
# inferred params: (t,a)
```

```katlang
K = a.~t
K({x+1}, 7)
# 8
# inferred params: (t,a)
```

```katlang
K = (x+y)+~z
# inferred params: (x,z,y)
```

Structural-collision law: when the receiver owns the member,

```text
Obj.t
Obj~.t
Obj.~t
```

must all select the SAME structural member whenever they are valid. Grace never converts a structural hit into a fallback call. Validity is the Q-16 G-O owner-local rule (2026-10-07): when `Obj` resolves to a visible property, `Obj~.t` is `InvalidGraceMarker` (Grace on a fixed binding), and when `t` is a statically certain structural member, so is `Obj.~t`; the law constrains the spellings that remain valid, such as a runtime-decided parameter receiver (`K = Obj~.t + 0` reads the member `t` of the argument bound to `Obj`).

### 8. Grace eligibility

The law: `~x` and `x~` operate on ONE bare name occurrence. Compound Grace is unsupported — `~(x+y)`, `(x+y)~`, `f(x)~`, `x.y~`, `[x]~`, `5~` are parse errors, and no ordering semantics are ever assigned to a multi-name operand.

The compositional consequence — decided by the one-name law itself, not by any special extension-receiver rule:

- `(x+y)~.t` is INVALID: the postfix marker would decorate the compound receiver `(x+y)`.
- `(x+y).~t` is VALID: the prefix marker decorates the bare fallback/member occurrence `t`.

The dot contributes nothing to eligibility.

### 9. Do not reintroduce

- The retired ExtensionOnly runtime resolution, or any extension-specific DotCall runtime mode.
- Lowering `a~.t` (or any graced dot) to a direct `t(a)` call.
- Synthetic "extension receiver Grace" injected by the parser or elaboration.
- Extension-specific parameter swapping outside the one general Grace pass.
- Parameter ordering derived from fallback call assembly (§4).
- Runtime branches keyed on whether the source spelled `~.`.
- Semantic provenance such as an IsExtensionReceiver flag — unless a strictly parser/recovery-only source fact is genuinely necessary, and then it must remain a frontend syntax concern and must not create a new semantic category.

Syntax-specific parser handling for slot separation, line boundaries, or recovery is legitimate frontend work; it never becomes a semantic mode.
